You push the greenhouse project to GitHub to show a friend. Line 9 of `main.py` reads `WIFI_PASSWORD = "maple-tree-42"`, and that is your family's Wi-Fi. You notice, delete the line, and push again. It doesn't help. Anyone who clones the repository can run `git log -p` and read every version of every file, including the one with the password.

This lesson has two halves that belong together: where secrets should live, and how the system behaves when things break. Both are about deciding in advance instead of finding out later.

## Where secrets leak from

A secret is anything that grants access: a Wi-Fi password, a broker password, an HMAC key, an API token. They escape through more doors than people expect:

| Leak | How it happens | Prevention |
| --- | --- | --- |
| Source code | `KEY = b"..."` in `main.py`, then the file is shared or pushed | Keep secrets in a separate file that never gets shared |
| Git history | The secret was committed once, then deleted | Rotate the secret; deleting it doesn't remove it from history |
| A public Wokwi project | Wokwi's free plan makes saved projects visible to everyone | Use throwaway keys in the simulator, never real passwords |
| Screenshots and screen recordings | The editor is open on the secrets file | Close it before you share your screen |
| Logs and audit messages | `print(config)` or an error message that includes the key | Log reasons and IDs, never secret values |
| The device itself | The Pico W has no locked storage, so anyone holding the board can copy every file off it over USB | One key per device, so a stolen board unlocks only itself |

The last row matters for IoT in particular. A web server lives in a locked room; your station sits in a greenhouse anyone can walk into.

## Split code from configuration

The standard fix is three files. The code imports its secrets; the secrets file stays on your machine and on the device; and an example file with fake values shows others what to fill in.

```python title="secrets.example.py (committed: fake values only)"
# Copy this file to secrets.py and fill in real values.
WIFI_SSID = "Wokwi-GUEST"
WIFI_PASSWORD = ""
FAN_KEY = b"replace-with-64-hex-characters-from-secrets.token_hex(32)"
```

```text title=".gitignore"
secrets.py
fan_seq.txt
```

```python title="top of main.py"
import network

try:
    from secrets import WIFI_SSID, WIFI_PASSWORD, FAN_KEY
except ImportError:
    print("No secrets.py on this board. Copy secrets.example.py to secrets.py and fill it in.")
    raise
```

The `try` block turns a confusing traceback into instructions. Add `.gitignore` **before** your first commit; git ignores a file only while it isn't already being tracked.

If a secret was committed anyway, three steps, in this order: **change the secret** (a new Wi-Fi password, a new key) so the leaked one is worthless; stop tracking the file with `git rm --cached secrets.py` and commit; then add it to `.gitignore`. Rewriting history with a tool like `git filter-repo` is optional cleanup. Rotation is the actual fix, because you can never be sure who already cloned the old version.

:::warning
**`secrets.py` on a Raspberry Pi breaks Python's own `secrets` module.** MicroPython has no module called `secrets`, so the name is safe on the Pico. Regular Python does, and a file with that name in your project folder is found first. Here is what happens to a script on a Pi that tries to make a key:
:::

```python run title="name_clash.py"
import os
import subprocess
import sys
import tempfile

project = os.path.realpath(tempfile.mkdtemp())
with open(os.path.join(project, "secrets.py"), "w") as f:
    f.write('WIFI_PASSWORD = "maple-tree-42"\n')
with open(os.path.join(project, "make_key.py"), "w") as f:
    f.write("import secrets\nprint(secrets.token_hex(16))\n")

result = subprocess.run([sys.executable, "make_key.py"], cwd=project, capture_output=True, text=True)
print(result.stderr.strip().splitlines()[-1].replace(project, "<project>"))
```

On a Pi or laptop, call the file `device_secrets.py` instead, or keep secrets out of the project folder completely: environment variables (`os.environ["BROKER_PASSWORD"]`) or a config file in your home folder that only your user can read (`chmod 600`).

## Rotate keys without breaking the station

Keys should change: after a leak, when someone leaves the team, or simply on a schedule. The hard part is the changeover. If the station switches to the new key before the controller does, every command fails, and vice versa.

The usual answer is a **key ID** (often written `kid`). Each command says which key signed it, and the station keeps a small **keyring**. During a changeover it holds both keys; once every controller has switched, you delete the old one:

```python run title="keyring.py"
import hashlib
import hmac

KEYRING = {                      # what the station holds during a changeover
    "k1": b"old-key-made-in-september-0000000000000000000000000000000000000",
    "k2": b"new-key-made-in-november-11111111111111111111111111111111111111",
}

def tag(key, text):
    return hmac.new(key, text.encode(), hashlib.sha256).hexdigest()

def verify(kid, text, sig, keyring):
    key = keyring.get(kid)
    if key is None:
        return "rejected: unknown or retired key " + kid
    if not hmac.compare_digest(tag(key, text), sig):
        return "rejected: bad signature"
    return "accepted (signed with " + kid + ")"

text = "station-01|fan_on|41"
old_controller = ("k1", text, tag(KEYRING["k1"], text))
new_controller = ("k2", text, tag(KEYRING["k2"], text))

print("During changeover:")
print("  old controller:", verify(*old_controller, KEYRING))
print("  new controller:", verify(*new_controller, KEYRING))

del KEYRING["k1"]                # every controller has switched: retire k1
print("After retiring k1:")
print("  old controller:", verify(*old_controller, KEYRING))
print("  new controller:", verify(*new_controller, KEYRING))
```

The `kid` is not a secret, so it can travel in plain JSON. It does belong inside the signed text in a real design, for the same reason every other field does.

## The whole system on one page

Before planning for failure you need a picture of what can fail. A good system diagram shows each part, what flows between them, and **trust boundaries**: the lines where data from someone else's control enters yours.

```mermaid caption="The greenhouse system. Anything crossing into the station or the dashboard from the broker must be checked."
flowchart LR
    subgraph Station["Station (trusted, but physically exposed)"]
        SEN["DHT22"] --> PICO["Pico W: validate, buffer, verify commands"]
        PICO --> FAN["Fan LED"]
    end
    subgraph Net["Network (untrusted)"]
        WIFI["Wi-Fi"] --> BRK["MQTT broker"]
    end
    subgraph Clients["Your computer"]
        DASH["Dashboard: validate, mark stale"]
        CTRL["Controller: holds the key, signs"]
    end
    PICO <--> WIFI
    BRK --> DASH
    CTRL --> BRK
```

The labels inside each box are its jobs at the boundary. The station validates sensor values and verifies commands; the dashboard validates payloads and judges staleness; only the controller holds the signing key besides the station.

## Decide what happens when each part fails

A **failure-mode table** lists, for each part: how it fails, how the system notices, and what it does then. Writing it before coding turns "it froze" into a designed behavior.

| Part | Failure | How it's noticed | Designed response |
| --- | --- | --- | --- |
| Sensor | Read raises `OSError`, or returns an impossible value | `try`/`except`; range check (DHT22: -40 to 80 °C) | Publish an error status; never publish a guessed value |
| Wi-Fi | Connection drops | `wlan.isconnected()` is `False`, or `publish` raises `OSError` | Keep sampling into a bounded buffer; reconnect with backoff |
| Broker | Down or unreachable | `connect()` raises | Same backoff; flush the buffer, oldest first, once back |
| Station | Power cut or crash | Broker publishes the last will | Dashboard shows `offline`; tiles go stale |
| Fan | Station reboots mid-command | Boot sequence | Fan starts **off**: `Pin(16, Pin.OUT, value=0)` |
| Counter file | Corrupted by a power cut during a write | `int()` raises `ValueError` | Refuse commands until it's fixed, rather than restarting at 0 |
| Dashboard | Closed, or loses its connection | Nothing for the station to notice | On reopen, retained status arrives at once |

The counter row is a correction to Module 6's `load_seq`, which returned 0 when the file was unreadable. That is **failing open**: a corrupted file would quietly re-accept every old command. For anything security-related, prefer **failing closed**, where the system refuses to act until a person looks.

## Reconnect with exponential backoff and jitter

When the broker goes away, the tempting code is `while True: try connect()`. It hammers a broker that is already struggling, and it drains a battery. **Exponential backoff** waits longer after each failure: 1 s, 2 s, 4 s, 8 s, up to a cap such as 60 s. After a success, the delay resets to the start.

Backoff alone has a flaw that shows up with many devices. A broker restart disconnects every station at the same moment, so with identical backoff they all retry at the same moments too, in synchronized waves. **Jitter** fixes that by picking a random delay between 0 and the current ceiling. Here are 30 stations losing a broker that comes back at t = 20 s:

```python run title="backoff_jitter.py" alt="Two scatter plots of reconnect attempts by 30 stations over 65 seconds. With doubling only, all 30 stations line up in vertical stripes at 1, 3, 7, 15, 31 and 63 seconds. With jitter, the attempts are scattered with no stripes." caption="Doubling alone makes every station retry in the same instant; jitter spreads them out"
import random
from collections import Counter
import matplotlib.pyplot as plt

BASE, CAP = 1, 60            # seconds
BACK_AT = 20                 # the broker restarts and is reachable again at t = 20 s

def retry_times(jitter, rng, attempts=6):
    """When one station retries after losing the broker at t = 0."""
    t, times = 0.0, []
    for n in range(attempts):
        ceiling = min(CAP, BASE * 2 ** n)
        t += rng.uniform(0, ceiling) if jitter else ceiling
        times.append(t)
    return times

def busiest_100ms(times):
    return max(Counter(int(t * 10) for t in times if t >= BACK_AT).values())

rng = random.Random(3)
fig, axes = plt.subplots(2, 1, figsize=(7, 4.5), sharex=True)
for ax, jitter, name in [(axes[0], False, "doubling only"), (axes[1], True, "doubling + jitter")]:
    everyone = []
    for station in range(30):
        times = retry_times(jitter, rng)
        everyone += times
        ax.scatter(times, [station] * len(times), s=8, color="#7892ee" if jitter else "#e8590c")
    ax.axvline(BACK_AT, color="gray", linestyle="--")
    ax.set_title(name, fontsize=10)
    ax.set_ylabel("station")
    print(f"{name:18}: most reconnects in one 100 ms slot after t=20: {busiest_100ms(everyone)}")
axes[1].set_xlabel("seconds after the broker went down (dashed line: broker back)")
plt.tight_layout()
```

With doubling only, all 30 stations hit the freshly restarted broker within the same instant at t = 31 s, which is how a restart turns into a second outage. With jitter, they trickle in.

The station's connection logic becomes a small state machine. Sampling never stops; only the network part waits:

```mermaid caption="Connection states. Readings keep going into the buffer in every state."
stateDiagram-v2
    [*] --> JoinWiFi
    JoinWiFi --> ConnectBroker: got an IP address
    JoinWiFi --> Backoff: timed out
    ConnectBroker --> Online: CONNACK accepted
    ConnectBroker --> Backoff: OSError or refused
    Online --> Backoff: publish or check_msg fails
    Backoff --> JoinWiFi: wait is over
    Online --> Online: flush buffer, publish, handle commands
```

:::warning
**Three reconnect bugs.** A `while not wlan.isconnected()` loop with no timeout hangs forever if the network never returns, so give every wait a deadline. A backoff that never resets after success makes the *next* outage start at a 60-second delay. And a reconnect that forgets to subscribe again leaves the station publishing happily but deaf to commands, because `umqtt.simple` starts each new connection with no subscriptions.
:::

:::quiz
Q: You committed `secrets.py` with your broker password last week. Today you add it to `.gitignore` and commit. Is the password safe?
- [ ] Yes, git now ignores the file
  `.gitignore` only affects files git isn't already tracking, and it never touches history.
- [ ] Yes, once you also run `git rm --cached secrets.py`
  That stops tracking the file from now on, but last week's commit still contains the password.
- [x] No. Change the password; the old one stays in the history that anyone may already have cloned
  Rotation makes the leaked value worthless. Cleaning the history is optional, rotation isn't.

Q: A station's key leaked. It shares one key with nine other stations. What does per-device keying change?
- [x] With per-device keys you rotate one key on one station; with a shared key all ten are exposed
  A shared key means one leak unlocks every device that holds it.
- [ ] Nothing, as long as the key is long enough
  Key length protects against guessing, not against a key that has been copied.
- [ ] Per-device keys stop the leak from happening
  They don't prevent leaks; they limit how much one leak can unlock.

Q: Fifty stations use exponential backoff without jitter, starting at 1 s and doubling. The broker restarts. What happens?
- [ ] They reconnect gradually as their delays grow
  Their delays grow, but identically, so they stay in step with each other.
- [x] All fifty retry at the same instants, so each wave hits the broker at once
  Same start time and same formula give the same retry times. Random jitter breaks the synchrony.
- [ ] Backoff makes them give up after the cap
  A cap limits the delay; it doesn't stop retrying.

Q: The counter file is unreadable after a power cut. Which response fails closed?
- [ ] Start counting from 0 and carry on
  That re-accepts every old command, which is failing open.
- [ ] Pick a random large number as the counter
  It might happen to work, but it can also lock out genuine commands unpredictably, and it hides the problem.
- [x] Refuse commands, publish an error status, and keep sending readings
  Security decisions wait for a human, while the harmless parts of the system keep working.
:::

:::takeaways
- Secrets leak from code, git history, public projects, screenshots, logs, and the device itself. Plan for each.
- Keep secrets in a git-ignored `secrets.py`, commit a `secrets.example.py`, and on regular Python avoid the name `secrets`.
- A leaked secret is fixed by rotating it, not by deleting it. Key IDs let you rotate without downtime.
- Draw the system with its trust boundaries, then write a failure-mode table: failure, how it's noticed, designed response.
- Fail closed for security decisions and fail safe for actuators: no command means the fan stays off.
- Reconnect with exponential backoff plus jitter, reset it after success, and resubscribe after every reconnect.
:::
