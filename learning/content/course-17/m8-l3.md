A demo that only shows the system working proves the least interesting thing about it. Anyone's station publishes a temperature when nothing goes wrong. Yours should also be shown going offline and coming back, refusing a replayed command, and marking a dead sensor as dead, because those are the behaviors you designed, and the ones a user would never see otherwise.

## Write a test plan with four kinds of test

| Kind | What it checks | Weather-station example |
| --- | --- | --- |
| **Unit** | One function's logic, on your computer | `test_logic.py` from the previous lesson: ten tests, all passing |
| **Normal use** | The whole system doing its job | Readings for every topic in the plan appear every 10 s with correct units |
| **Boundary** | Values at the edges of what's allowed | DHT22 slider at -40 °C and 80 °C is accepted; `set_interval` 5 and 300 accepted, 4 and 301 refused |
| **Failure** | Each row of your failure table | Wi-Fi cut for 2 minutes: no crash, readings resume in order, `dropped` reported |
| **Security** | Each row of your threat table | Every message from the attack kit below is refused with the expected reason |

Record each test as a row you can paste into your README:

```text
| ID | Test | Steps | Expected | Actual | Pass |
| F2 | Broker unreachable | Change BROKER to a wrong name, run 60 s, change it back | Backoff waits grow; no crash; online again after the fix | Waits 1, 0.4, 3.1, 6.8 s; online 9 s after the fix | yes |
```

The **Actual** column is the important one. "It worked" is not a result; numbers and quoted output are.

## Generate the attack kit for your station

Typing ten hand-edited attack messages into the web client is slow and error-prone. This script makes them from your key, your device name, and the last `seq` your station accepted, and says what the audit topic should report for each. Change the three settings at the top, run it on your computer, and publish each message in order to your command topic:

```python run title="attack_kit.py"
import hashlib
import hmac
import json

KEY = b"capstone-test-key-not-a-real-one-0123456789abcdef0123456789abcd"  # use your own
DEVICE = "ws-01"
LAST_SEQ = 7               # read it from your retained state or audit topic first

def signed(cmd, arg, seq, dev=DEVICE, key=KEY):
    text = dev + "|" + cmd + "|" + ("" if arg is None else str(arg)) + "|" + str(seq)
    sig = hmac.new(key, text.encode(), hashlib.sha256).hexdigest()
    return {"dev": dev, "cmd": cmd, "arg": arg, "seq": seq, "sig": sig}

n = LAST_SEQ + 1
good = signed("set_interval", 30, n)
tests = [
    ("S1", "genuine command", good, "accepted"),
    ("S2", "exact replay of S1", good, "replayed or old seq"),
    ("S3", "S1 with arg changed", dict(good, arg=3), "bad signature"),
    ("S4", "S1 with seq raised", dict(good, seq=n + 50), "bad signature"),
    ("S5", "signed, arg out of range", signed("set_interval", 1, n + 1), "argument out of range"),
    ("S6", "signed for another device", signed("set_interval", 30, n + 1, dev="ws-02"), "meant for another device"),
    ("S7", "signed, unknown command", signed("open_door", None, n + 1), "unknown command"),
    ("S8", "wrong key", signed("set_interval", 30, n + 1, key=b"guess"), "bad signature"),
    ("S9", "seq as a string", dict(good, seq=str(n + 1)), "missing or wrong-type field"),
    ("S10", "not JSON at all", "set_interval 30", "not JSON"),
]
for test_id, what, message, expected in tests:
    text = message if isinstance(message, str) else json.dumps(message)
    print(f"{test_id:4} {what}  ->  expect: {expected}")
    print(f"     {text}")
```

S3 and S4 are the same attack aimed at different fields: they show that the argument and the counter are both covered by the signature. S5 to S7 are signed with the real key, so they test the checks that protect you from your own mistakes. If any result differs from the expectation, you've found a real bug, which is the best possible outcome of a test. Fix it, add a unit test for it, and record both.

## Polish it for a stranger

Go through this list with your project open. Each item is something graders and classmates notice in the first two minutes.

-   [ ] `secrets.py` is not in the repository or the shared Wokwi project; `secrets.example.py` is, with fake values.
-   [ ] No `print` or MQTT message anywhere contains a key or password. Search your files for `KEY` and `PASSWORD`.
-   [ ] Every topic in the code matches the README's topic table exactly.
-   [ ] `config.py` holds every setting a user might change; nothing is buried in `main.py`.
-   [ ] Comments explain *why* ("fail closed: a damaged counter must not reset to 0"), not *what* ("set x to 0").
-   [ ] Debugging leftovers are gone: commented-out experiments, unused functions, `print("here")`.
-   [ ] Actuators start in their safe state, and anything that runs has an automatic off.
-   [ ] A fresh copy of the project, set up only by following the README, works on the first try.

The last item is the one people skip and the one that fails most often. Ask a classmate to do it while you watch without helping.

## Present it in four minutes

A good technical demo is a story with evidence. This order works because each part sets up the next:

```mermaid caption="A four-minute demo: show it work, then show it fail safely"
flowchart LR
    A["Problem: 30 s"] --> B["Architecture: 45 s"]
    B --> C["Normal use: 45 s"]
    C --> D["Failure: 45 s"]
    D --> E["Attack: 45 s"]
    E --> F["Limits and next: 30 s"]
```

1.  **Problem.** Who would use this and what goes wrong without it. One sentence, one picture.
2.  **Architecture.** Your diagram, pointing at the trust boundaries.
3.  **Normal use.** Dashboard live; drag a sensor slider; the tile updates.
4.  **Failure.** Press the Wi-Fi cut button or stop the simulation. Point at `offline` and the stale tiles, then show the recovery and the backlog arriving in order.
5.  **Attack.** Publish a genuine command (it works), then publish it again (refused, and the audit topic says why).
6.  **Limits and next.** Read your "What is NOT protected" section aloud. It shows you know where the edges of your design are.

Rehearse it twice with a timer. Prepare the signed commands in advance with the right `seq` values, and keep a short screen recording of a successful run in case the Wokwi gateway is slow on the day.

## Rubric

Score each row from 1 to 4. A 3 in every row is a strong project; a 4 means you went beyond what the brief asked for.

| Criterion | 1: Beginning | 2: Developing | 3: Proficient | 4: Exemplary |
| --- | --- | --- | --- | --- |
| **Sensors and data quality** | Readings print, no validation | Some range checks; failures crash or publish fake values | Every reading validated; failures reported on a health topic | Also detects stuck or implausible sensors; calibration documented |
| **MQTT design** | Topics ad hoc, bare numbers | Topic plan exists but code drifts from it; units missing in places | Code matches the plan; JSON with units, device, and `seq`; retained status with last will | Plan checked by script; QoS and retain choices justified in the README |
| **Dashboard** | Shows numbers | Shows latest values; staleness unclear | Fresh, stale, and offline states clear; junk payloads ignored; `textContent` only | Health banner, gap detection from `seq`, or history charts |
| **Remote action and authentication** | Unsigned commands | Signed, but replays or edited fields get through | HMAC over every field, counter replay protection, allowlist and range checks, audit topic | Per-device keys, key IDs, or a counter that survives Wokwi restarts |
| **Credentials** | Secrets in `main.py` | Separate file, but leaked in a log, repo, or shared project | `secrets.py` ignored, `secrets.example.py` shared, nothing secret printed or published | Rotation plan written and demonstrated |
| **Failure handling** | Crashes on the first outage | Recovers from some failures, or blocks while recovering | Outbox, backoff with jitter, resubscribe, safe defaults, fail-closed counter | Every failure-table row tested with recorded results |
| **Testing evidence** | None | A few manual checks, no records | Unit tests pass; attack kit run with results recorded; failure tests recorded | Found and fixed a real bug through testing, with a test added for it |
| **Documentation and presentation** | README missing or a few lines | README exists; a stranger needs help | A stranger can run and test it from the README; demo shows normal use, a failure, and an attack | Honest limits section; clear diagrams; demo within time and rehearsed |

## Reflect

Write short answers to these in your README, under a heading called **Reflection**:

1.  Which failure surprised you most when you triggered it, and what did you change because of it?
2.  Where does your system still trust something it shouldn't? What would it take to fix that?
3.  If 100 copies of your station shared one broker, what would break first?
4.  What would you do differently if you started again tomorrow?

## Where to go next

-   **Run your own broker.** Install Mosquitto on a Raspberry Pi or your laptop, turn on `allow_anonymous false` with a password file and an ACL file, then add TLS with a certificate. Everything you signed by hand becomes a second layer of defense instead of the only one.
-   **Give each device its own certificate.** Mutual TLS, where the broker also checks the device's certificate, is how large IoT platforms identify millions of devices.
-   **Store and chart history.** Send readings into a time-series database such as InfluxDB and chart them with Grafana, or build flows and dashboards in Node-RED.
-   **Build it for real.** A physical Pico W adds problems the simulator hides: power supplies, weatherproofing, Wi-Fi range, and sensors that drift.
-   **Learn MQTT 5.** It adds features such as message expiry, which is a cleaner answer to "is this retained reading too old?" than anything in MQTT 3.1.1.
