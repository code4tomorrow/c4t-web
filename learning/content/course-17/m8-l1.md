A greenhouse that texts you when it's too hot is easy to sketch on a napkin. The napkin version leaves out who else can switch the fan, what the dashboard shows when the station dies, and where the Wi-Fi password lives. Those parts take longer than the sensors, and they are what this capstone is graded on.

You'll build a complete monitoring system in Wokwi (or on a real Pico W, if you have one): sensors, a station that publishes over MQTT, a dashboard, at least one remote action that only you can trigger, and documentation that lets someone else understand and test it. This lesson is the plan. The next one builds it in milestones, and the last one tests, polishes, and grades it.

## The brief

Your system must have all eight of these. The project ideas below differ in how hard each one is, not in which ones they skip.

| # | Requirement | Where you learned it |
| --- | --- | --- |
| 1 | At least two sensor readings, validated against realistic ranges | Modules 3 and 7 |
| 2 | Readings collected on a non-blocking schedule, with sequence numbers | Modules 4 and 5 |
| 3 | MQTT with a written topic plan, JSON payloads with units, and a retained status with a last will | Module 5 |
| 4 | A dashboard that shows fresh, stale, and offline states clearly | Module 5 |
| 5 | At least one remote action protected by HMAC signatures and replay protection, with an audit topic | Module 6 |
| 6 | Every secret in a git-ignored `secrets.py`, with a `secrets.example.py` | Module 7 |
| 7 | Designed failure behavior: outbox, backoff with jitter, resubscribe, safe defaults, fail-closed security state | Module 7 |
| 8 | A README with an architecture diagram, topic plan, threat table, failure table, and test results | This module |

## Pick a project

| Project | Level | Wokwi parts | Remote action | What makes it interesting |
| --- | --- | --- | --- | --- |
| Plant-care monitor | Starter | Potentiometer standing in for a soil-moisture probe, photoresistor | Signed `water_now`; an LED is the pump | The pump must switch itself off after 10 s even if the "off" command never arrives |
| Smart greenhouse | Core | DHT22, photoresistor, LED fan, servo vent | Signed fan on/off and vent angle | Commands with an argument (the angle), range-checked after the signature |
| Weather station | Core | DHT22, photoresistor, pushbutton as a rain-gauge bucket | Signed `set_interval` | A configuration command that changes how the station behaves, plus counting events |
| Freezer monitor | Stretch | DS18B20 temperature sensor, buzzer | Signed `ack_alarm` | A local alarm that works with no network, and alerts that repeat until someone acknowledges them |
| Two-site monitor | Stretch | Two Pico W stations in two Wokwi tabs | Signed commands with a different key per station | Per-device keys, key IDs, and rotating one station's key while the other keeps working |

If you're unsure, pick a **core** project and do it well. A complete starter project with excellent tests beats a stretch project with three requirements half-done.

## Fill in the plan

Copy this template into a file called `PLAN.md` in your project and fill in every section. Short answers are fine; blank ones aren't.

```text
# Project: ____________
One sentence: what it monitors, for whom, and what it can do remotely.

## Parts
Wokwi part, pin, what it measures or does, realistic range.

## Topic plan  (prefix: c4t-lab/<your code>/<site>)
| Topic | Payload example | Unit | Every | Retained | QoS |

## Commands
| Command | Argument and allowed range | Effect | Safe default (at boot, after failure) |
Signed text format:   device|command|argument|seq

## Secrets inventory
| Secret | Who holds it | Where it is stored | How to rotate it |

## Architecture
A diagram with every part, every arrow, and the trust boundaries.

## Threats  (one row per arrow that crosses a boundary)
| Arrow | Read? | Faked? | Replayed? | Blocked? | Defense |

## Failures
| Part | Failure | How it's noticed | Designed response |

## Milestones and test plan
See lessons 2 and 3.
```

## Find the threats at each boundary

Threat modeling sounds grand, but for a project this size it is one question asked four times. For every arrow that crosses a trust boundary, ask whether someone could **read** it, **fake** it, **replay** it, or **block** it, and what stops them. For the weather station:

| Arrow | Read? | Faked? | Replayed? | Blocked? | Defense |
| --- | --- | --- | --- | --- | --- |
| Readings to broker | Yes, public broker | Yes, anyone can publish to the topic | Yes | Yes, a Wi-Fi outage | Nothing secret in them; the dashboard validates and checks `seq`; outbox through outages |
| `set_interval` to station | Yes | Only with the key | Yes, without a counter | Yes | HMAC over `device\|command\|argument\|seq`; counter saved to flash; range check 5 to 300 s |
| Status to dashboard | Yes | Yes | Yes | Yes | Accepted as a hint only; staleness is judged by the dashboard's own clock |
| Key on the station | Anyone holding the board can copy it | No | No | No | One key per station; a rotation plan in the secrets inventory |

The third row is an honest one. On a public broker, a stranger can publish a fake `online`, and the dashboard can't tell. Writing that down, along with "a private broker with ACLs would fix this," is better than pretending the problem doesn't exist.

:::video h_BC6QMWDbA
What to watch for: threat modeling as a habit done early, while changes are cheap, rather than a checklist after the build. The four questions in your threat table are a compact version of the same idea.
:::

## Check the plan with a script

Some design mistakes are mechanical enough to catch automatically. Write your plan as a Python dictionary and run it through this checker. The example has three deliberate mistakes:

```python run title="check_plan.py"
PLAN = {
    "prefix": "c4t-lab/q8z2rw/weather",
    "device": "ws-01",
    "readings": {
        "roof/temperature": {"unit": "C", "every_s": 10},
        "roof/humidity": {"unit": "%", "every_s": 10},
        "Roof/Light": {"unit": "%", "every_s": 10},
        "roof/rain": {"every_s": 60},
    },
    "status": {"topic": "devices/ws-01/status", "retain": True, "will": "offline"},
    "commands": {
        "config/interval/set": {"args": (5, 300), "safe_default": 10},
        "roof/heater/set": {"args": ("on", "off")},
    },
}

def check_plan(plan):
    problems = []
    every_topic = list(plan["readings"]) + [plan["status"]["topic"]] + list(plan["commands"])
    for tail in every_topic:
        full = plan["prefix"] + "/" + tail
        if full != full.lower() or " " in full:
            problems.append(f"{tail}: use lowercase with no spaces")
        if full.startswith("/") or "//" in full:
            problems.append(f"{tail}: empty level")
        if "+" in full or "#" in full:
            problems.append(f"{tail}: wildcards belong in subscriptions, not topic names")
    for tail, spec in plan["readings"].items():
        if "unit" not in spec:
            problems.append(f"{tail}: reading has no unit")
    status = plan["status"]
    if not (status.get("retain") and status.get("will")):
        problems.append("status: needs a retained message and a last will")
    for tail, spec in plan["commands"].items():
        if "safe_default" not in spec:
            problems.append(f"{tail}: command has no safe default for boot and failures")
    return problems

problems = check_plan(PLAN)
for p in problems:
    print("FIX:", p)
print(f"{len(problems)} problem(s) found")
```

The rain gauge is the instructive one: "no unit" for a count of bucket tips sounds pedantic until the dashboard has to decide whether `3` means millimetres, tips, or tips per hour. Replace the example with your own plan and run it until it prints `0 problem(s) found`.

:::tip
Add checks of your own as you go. If your project has commands with arguments, check that every argument has a range. If it has two stations, check that no two devices share a key ID.
:::

## Milestones

The next lesson builds the project in six milestones. Each ends with something you can see working, so you always have a version to fall back on.

| Milestone | Done when |
| --- | --- |
| M1: Sensors | Every reading prints with a unit, and out-of-range values are caught |
| M2: Publishing | Readings, retained status, and last will appear correctly in the HiveMQ web client |
| M3: Dashboard | Tiles show fresh, stale, and offline, and junk payloads are ignored |
| M4: Remote action | Genuine commands work; replays, forgeries, and out-of-range arguments are refused and audited |
| M5: Resilience | A Wi-Fi cut, a broker outage, and a reboot all recover without losing control or the counter |
| M6: Documentation | README complete; someone else can follow it to run and test the system |

Before moving on, check your plan against the eight requirements one more time. A missing requirement is cheap to add to a plan and expensive to add to finished code.
