:::objectives
- Connect a Wokwi Pico W to Wi-Fi and to `broker.hivemq.com` with `umqtt.simple`.
- Publish temperature and humidity as JSON on a topic tree you designed, without blocking the main loop.
- Announce `online` with a retained message and let a last will announce `offline`.
- Watch the traffic in the HiveMQ web client, then build a dashboard page that flags stale readings.
:::

By the end of this lesson a DHT22 sensor in your browser reports to a real broker on the internet, and a web page on your computer shows the numbers with their age. When you stop the simulation, the page notices.

## Step 1: Write down the topic plan

Decide the names before writing code, so the station and the dashboard agree. Replace `a7f3c9` with your own random code everywhere in this lesson.

| Topic | Payload | Retained? | QoS |
| --- | --- | --- | --- |
| `c4t-lab/a7f3c9/greenhouse/bed1/temperature` | `{"v": 24.0, "unit": "C", "dev": "station-01", "seq": 1}` | No | 0 |
| `c4t-lab/a7f3c9/greenhouse/bed1/humidity` | `{"v": 40.0, "unit": "%", "dev": "station-01", "seq": 1}` | No | 0 |
| `c4t-lab/a7f3c9/greenhouse/devices/station-01/status` | `online` or `offline` | Yes | 1 |

Readings repeat every five seconds, so a lost one costs nothing and they aren't retained. Status is current state that a late subscriber needs, so it is retained and sent with QoS 1.

## Step 2: Set up the Wokwi project

1.  Open the [Pico W MicroPython template](https://wokwi.com/projects/new/micropython-pi-pico-w). It starts with a `main.py` that prints a greeting.
2.  Click the **+** button above the diagram, search for **DHT22**, and drop it next to the board.
3.  Wire it by clicking a pin and then its partner:

| DHT22 pin | Pico W pin |
| --- | --- |
| VCC | 3V3 |
| SDA | GP15 |
| NC | (leave empty) |
| GND | any GND |

4.  Add the MQTT library. The official Pico W firmware doesn't include it, so open the [umqtt.simple source](https://raw.githubusercontent.com/micropython/micropython-lib/master/micropython/umqtt.simple/umqtt/simple.py), copy all of it, create a new file in your Wokwi project (from the arrow menu at the end of the file tabs), name it `umqttsimple.py`, and paste. Wokwi copies every project file onto the simulated board's flash, so `main.py` can import it.

:::tip
Wokwi's own documentation describes Wi-Fi for its **Pico 2 W** board. If your Pico W project never gets past `Joining Wi-Fi....`, start again from the [Pico 2 W MicroPython template](https://wokwi.com/projects/new/micropython-pi-pico-2w) and copy your files across; every line of code in this module runs unchanged on it.
:::

:::note
On a **real Pico W**, install the library instead: in Thonny use **Tools › Manage packages** and search for `micropython-umqtt.simple`, or run `import mip; mip.install("umqtt.simple")` once the board is on Wi-Fi. Then write `from umqtt.simple import MQTTClient` wherever this lesson writes `from umqttsimple import MQTTClient`.
:::

## Step 3: Join Wi-Fi and connect with a last will

Replace `main.py` with this and press the green play button.

```python title="main.py (step 3)"
import time
import network
from umqttsimple import MQTTClient

CODE = "a7f3c9"                      # your own random code
DEVICE = "station-01"
BROKER = "broker.hivemq.com"
BASE = "c4t-lab/" + CODE + "/greenhouse"
STATUS = BASE + "/devices/" + DEVICE + "/status"

wlan = network.WLAN(network.STA_IF)
wlan.active(True)
wlan.connect("Wokwi-GUEST", "")      # Wokwi's open network: no password
print("Joining Wi-Fi", end="")
while not wlan.isconnected():
    print(".", end="")
    time.sleep(0.25)
print(" ok")

client = MQTTClient(DEVICE + "-" + CODE, BROKER, keepalive=30)
client.set_last_will(STATUS, "offline", retain=True, qos=1)
client.connect()
client.publish(STATUS, "online", retain=True, qos=1)
print("Broker ok:", BROKER)
```

```text
Joining Wi-Fi........ ok
Broker ok: broker.hivemq.com
```

Three decisions hide in those last four lines. The client ID includes your code, because two clients with the same ID knock each other off the broker. `set_last_will` must come **before** `connect()`, since the will travels inside the CONNECT packet. And `keepalive=30` tells the broker to expect a sign of life at least every 30 seconds; without it, `umqtt.simple` asks for no keepalive at all, and the broker might wait a very long time before deciding the station is gone.

If you see `OSError` after `Joining Wi-Fi`, the simulator's internet gateway is busy; stop and start the simulation again. An `ImportError` for `umqttsimple` means the file name in Step 2 doesn't match exactly.

## Step 4: Publish readings without blocking

A station that calls `time.sleep(5)` between readings can't do anything else for those five seconds, and in Module 6 it must also listen for commands. So the loop wakes every 50 ms and checks whether a reading is due, using `ticks_ms()` and `ticks_diff()`, which handle the millisecond counter wrapping around.

Add this below Step 3's code:

```python title="main.py (step 4, added at the bottom)"
import json
import dht
from machine import Pin

sensor = dht.DHT22(Pin(15))
led = Pin("LED", Pin.OUT)
EVERY_MS = 5000

def publish_reading(where, what, value, unit, seq):
    topic = BASE + "/" + where + "/" + what
    payload = json.dumps({"v": value, "unit": unit, "dev": DEVICE, "seq": seq})
    client.publish(topic, payload)
    print(topic, payload)

seq = 0
next_due = time.ticks_ms()
while True:
    if time.ticks_diff(time.ticks_ms(), next_due) >= 0:
        next_due = time.ticks_add(next_due, EVERY_MS)
        try:
            sensor.measure()
        except OSError as err:
            print("Sensor read failed:", err)
            continue
        seq += 1
        publish_reading("bed1", "temperature", round(sensor.temperature(), 1), "C", seq)
        publish_reading("bed1", "humidity", round(sensor.humidity(), 1), "%", seq)
        led.toggle()                  # a heartbeat you can see
    time.sleep_ms(50)
```

```text
c4t-lab/a7f3c9/greenhouse/bed1/temperature {"v": 24.0, "unit": "C", "dev": "station-01", "seq": 1}
c4t-lab/a7f3c9/greenhouse/bed1/humidity {"v": 40.0, "unit": "%", "dev": "station-01", "seq": 1}
```

The JSON keys may print in a different order on the Pico, because MicroPython dictionaries don't promise to keep insertion order. JSON readers don't care. (Module 6 cares a lot, for signatures.)

A failed sensor read prints a message and skips the publish rather than sending a made-up value. A dashboard that shows nothing is honest; one that shows a stale number as if it were fresh is not.

## Step 5: Watch the traffic in the HiveMQ web client

1.  Open the [HiveMQ web client](https://www.hivemq.com/demos/websocket-client/) in a new tab. Leave **Host** and **Port** as they are and click **Connect**.
2.  Click **Add New Topic Subscription**, type `c4t-lab/a7f3c9/#` (with your code), and click **Subscribe**.
3.  The **Messages** panel fills up every five seconds. The status message arrives first, straight away, because it is retained.

Now test each feature on purpose:

-   **Change the world.** Click the DHT22 in Wokwi and drag its temperature slider. The next message carries the new value.
-   **Test the retained message.** Disconnect the web client, connect again, and resubscribe. `online` appears instantly; readings only arrive on the next publish.
-   **Test the last will.** Stop the Wokwi simulation. Within about 45 seconds (one and a half keepalive periods), sometimes sooner, `offline` arrives on the status topic. Start the simulation again and it flips back to `online`.

## Step 6: Build a dashboard that knows when data is stale

The web client is a debugging tool. A dashboard should show the latest value per sensor and how old it is. The rule here: a tile turns **stale** after 15 seconds without news, which means three missed readings in a row.

The preview below runs the dashboard code with a **demo feed** standing in for the broker: bed2's station stops after 20 seconds and station-01 goes offline after 45. Watch the tiles change.

```html preview height="330"

<style>

  .tile b { display: block; font-size: 26px; margin: 4px 0; }
  .tile small { color: #5b6478; }

<script>
  const STALE_MS = 15000;            // three missed readings at one every 5 s
  const UNITS = { C: "°C", F: "°F", "%": "%" };
  const tiles = {};
  const badges = {};

  // topicTail is the part after your prefix, e.g. "bed1/temperature"
  function show(topicTail, text) {
    const parts = topicTail.split("/");
    if (parts.length === 3 && parts[0] === "devices" && parts[2] === "status") {
      const name = parts[1];
      if (!badges[name]) {
        badges[name] = document.createElement("span");
        document.getElementById("devices").appendChild(badges[name]);

      badges[name].textContent = name + ": " + text;
      badges[name].className = "badge " + (text === "online" ? "ok" : "bad");
      return;
    }
    if (parts.length !== 2) return;  // not a reading topic
    let data;
    try { data = JSON.parse(text); } catch (err) { return; }

    if (!tiles[topicTail]) {
      const el = document.createElement("div");
      const label = document.createElement("small");
      const value = document.createElement("b");
      const age = document.createElement("small");
      el.append(label, value, age);
      document.getElementById("tiles").appendChild(el);
      tiles[topicTail] = { el, label, value, age };
    }
    Object.assign(tiles[topicTail], { data, at: Date.now(), name: parts.join(" / ") });
    draw(tiles[topicTail]);
  }

  function draw(t) {
    const ageMs = Date.now() - t.at;
    const stale = ageMs > STALE_MS;
    t.el.className = stale ? "tile stale" : "tile";
    t.label.textContent = t.name;
    t.value.textContent = t.data.v.toFixed(1) + " " + UNITS[t.data.unit];
    t.age.textContent = (stale ? "STALE, " : "") + Math.round(ageMs / 1000) + " s ago, #" + t.data.seq;
  }

  setInterval(() => Object.values(tiles).forEach(draw), 1000);

  const t0 = Date.now();

    seq += 1;

    show("bed1/temperature", JSON.stringify({ v: 23 + Math.sin(s / 8), unit: "C", dev: "station-01", seq }));
    show("bed1/humidity", JSON.stringify({ v: 41 + 2 * Math.cos(s / 8), unit: "%", dev: "station-01", seq }));
    if (s < 20) show("bed2/temperature", JSON.stringify({ v: 21.5, unit: "C", dev: "station-02", seq }));
    if (s >= 20 && s < 25) show("devices/station-02/status", "offline");
  }
  tick();
  const feed = setInterval(tick, 5000);
</script>
```

Look at how `show()` treats its input. Anyone on the internet can publish to your topics on a public broker, so the dashboard assumes every payload might be junk or an attack. It ignores anything that isn't valid JSON with a numeric `v` and a known unit, and it writes text with `textContent`, never `innerHTML`. With `innerHTML`, a stranger could publish `<img src=x onerror=...>` as a "unit" and run their own script in your page.

To make it real, select all the code in the preview, paste it into a new file called `dashboard.html`, and **delete the demo feed `<script>` block**. In its place, paste this, with your code in `PREFIX`:

```html title="dashboard.html (replaces the demo feed)"
<script src="https://unpkg.com/mqtt@5.10.1/dist/mqtt.min.js"></script>
<script>
  const PREFIX = "c4t-lab/a7f3c9/greenhouse/";   // your code, ending with a slash
  const conn = document.getElementById("conn");
  const client = mqtt.connect("wss://broker.hivemq.com:8884/mqtt", {
    clientId: "dash-" + Math.random().toString(16).slice(2, 10),
  });
  client.on("connect", () => {
    conn.textContent = "connected";
    client.subscribe(PREFIX + "#");
  });
  client.on("reconnect", () => (conn.textContent = "reconnecting..."));
  client.on("message", (topic, payload) => show(topic.slice(PREFIX.length), payload.toString()));
</script>
```

Save it and double-click it to open it in your browser while the Wokwi simulation runs. Browsers can't open raw MQTT connections, so the page uses **MQTT over secure WebSockets** on port 8884, which the HiveMQ broker also offers. The random client ID means two open tabs don't fight.

## The finished station

```python title="main.py"
# Greenhouse station: publishes labelled readings over MQTT
import json
import time

import dht
import network
from machine import Pin
from umqttsimple import MQTTClient

CODE = "a7f3c9"                      # your own random code
DEVICE = "station-01"
BROKER = "broker.hivemq.com"
BASE = "c4t-lab/" + CODE + "/greenhouse"
STATUS = BASE + "/devices/" + DEVICE + "/status"
EVERY_MS = 5000

sensor = dht.DHT22(Pin(15))
led = Pin("LED", Pin.OUT)


def connect_wifi():
    wlan = network.WLAN(network.STA_IF)
    wlan.active(True)
    wlan.connect("Wokwi-GUEST", "")
    print("Joining Wi-Fi", end="")
    while not wlan.isconnected():
        print(".", end="")
        time.sleep(0.25)
    print(" ok")


def connect_broker():
    client = MQTTClient(DEVICE + "-" + CODE, BROKER, keepalive=30)
    client.set_last_will(STATUS, "offline", retain=True, qos=1)
    client.connect()
    client.publish(STATUS, "online", retain=True, qos=1)
    print("Broker ok:", BROKER)
    return client


def publish_reading(client, where, what, value, unit, seq):
    topic = BASE + "/" + where + "/" + what
    payload = json.dumps({"v": value, "unit": unit, "dev": DEVICE, "seq": seq})
    client.publish(topic, payload)
    print(topic, payload)


connect_wifi()
client = connect_broker()
seq = 0
next_due = time.ticks_ms()

while True:
    if time.ticks_diff(time.ticks_ms(), next_due) >= 0:
        next_due = time.ticks_add(next_due, EVERY_MS)
        try:
            sensor.measure()
        except OSError as err:
            print("Sensor read failed:", err)
            continue
        seq += 1
        publish_reading(client, "bed1", "temperature", round(sensor.temperature(), 1), "C", seq)
        publish_reading(client, "bed1", "humidity", round(sensor.humidity(), 1), "%", seq)
        led.toggle()
    time.sleep_ms(50)
```

:::quiz
Q: Why is the status topic retained while the readings are not?
- [x] Status describes the station right now, and a dashboard that opens late needs it immediately; a reading is replaced five seconds later anyway
  Retain current state. A retained reading would show a new dashboard an old number with no hint of its age, unless the payload carried a trustworthy timestamp.
- [ ] Retained messages only work with QoS 1
  Retain and QoS are independent flags; any QoS can be retained.
- [ ] The broker refuses to retain JSON
  The broker never looks inside payloads, so it can retain anything.

Q: Someone publishes `{"v": 5, "unit": "<img src=x onerror=alert(1)>"}` to your temperature topic. What does the dashboard do?
- [ ] Shows a broken image and runs the alert
  That would happen with `innerHTML`. The dashboard never builds HTML from payloads.
- [x] Ignores it, because the unit isn't one of C, F, or %
  The `UNITS` check rejects it before anything is drawn, and even an accepted value is written with `textContent`, which displays characters instead of running them.
- [ ] Crashes, because `JSON.parse` fails
  The payload is valid JSON; the problem is what's inside it, which is why the checks after parsing matter.

Q: You open `dashboard.html` in two tabs. What happens, and why?
- [ ] The tabs keep disconnecting each other, like two boards with one ID
  That would happen with a fixed client ID. Each tab makes a random one, so both stay connected.
- [x] Both tabs show the same live data
  Each tab is a separate subscriber with its own client ID, and the broker sends each one a copy.
:::

:::takeaways
- Write the topic plan first; both the station and the dashboard depend on it.
- Call `set_last_will` before `connect()`, set a keepalive, and give every client a unique ID.
- A loop that checks `ticks_diff` every few milliseconds publishes on schedule and stays free for other work.
- Test each MQTT feature on purpose: slide the sensor, reconnect for the retained message, stop the simulation for the will.
- A dashboard on a public broker must treat every payload as untrusted: validate it, and display it with `textContent`.
- Staleness is decided by the dashboard's own clock: no news for three periods means stale.
:::

## Ideas to extend it

-   Add a second sensor (a photoresistor on GP26, read with `machine.ADC`) as `bed1/light` with unit `"%"`, and see the dashboard grow a tile with no dashboard changes.
-   Add a small history line under each tile showing the last 10 values.
-   Count gaps in `seq` per tile and show "3 lost" when numbers are skipped.
-   Try **Node-RED**, a free flow-based tool that also runs on a Raspberry Pi: an **mqtt in** node subscribed to your topic, a **json** node, and a gauge from the Node-RED Dashboard 2.0 package give you a dashboard without writing HTML.
