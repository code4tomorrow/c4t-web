A setup guide for a temperature sensor says: "Connect the sensor's data wire to pin 17, then run `sudo cp sensor.conf /boot/firmware/config.txt`." Both halves of that sentence can wreck your afternoon.

On a Raspberry Pi, physical pin 17 is a 3.3 V **power** pin. The guide meant GPIO17, which lives at physical pin 11. And that `cp` command silently replaces the file the Pi reads every time it boots, with no undo. Neither mistake produces an error message. The fix is the same for both: know exactly which numbering and which file a command refers to before you press Enter.

## Where am I? The prompt, `pwd`, `ls`, and `cd`

The terminal is a conversation. You type a command, press Enter, and the computer prints a reply. The commands in this lesson work in any Linux terminal: a Raspberry Pi over SSH, the Linux environment on a Chromebook, Ubuntu under WSL on Windows (run `wsl --install` in PowerShell to get it), or the macOS Terminal, which behaves almost the same.

```bash
pwd
ls
cd iot-lab
pwd
```

```text
/home/student
Desktop  Documents  Downloads  iot-lab
/home/student/iot-lab
```

`pwd` (print working directory) says where you are. `ls` lists what's here. `cd` changes directory. Linux has one tree of folders starting at `/`, the **root**, and your own files live in your **home** folder, `/home/student`, which you can always write as `~`.

A path that starts with `/` is **absolute**: it means the same place no matter where you are. Any other path is **relative** to where you are now. Two special names help: `.` means "this folder" and `..` means "the folder above". Watch how the shell resolves a relative path one piece at a time:

:::trace How `cd ../logs/./today` is resolved from `/home/student/iot-lab`
```python
current = "/home/student/iot-lab"
target = "../logs/./today"

parts = current.strip("/").split("/")
for step in target.split("/"):
    if step == "..":
        parts.pop()
    elif step != ".":
        parts.append(step)

print("/" + "/".join(parts))
```
:::

`..` removed `iot-lab`, `.` changed nothing, and the other names were added on. Press **Tab** while typing a path and the shell completes it for you, which also catches typos before they cause trouble. The **Up** arrow brings back your previous commands.

## Commands that change files, and the ones you can't undo

```bash
mkdir -p ~/iot-lab/logs      # make a folder (and any missing parents)
cd ~/iot-lab
nano notes.txt               # edit a file; Ctrl+O saves, Ctrl+X exits
cat notes.txt                # print a file
cp notes.txt notes-old.txt   # copy
mv notes-old.txt logs/       # move (or rename)
rm logs/notes-old.txt        # delete
```

Three of these deserve respect. `cp` and `mv` overwrite an existing file with the same name without asking, and `rm` deletes immediately. There is no recycle bin. Adding `-i` (`cp -i`, `mv -i`, `rm -i`) makes them ask first, which is a good habit when you're working near files you care about. When you're unsure what a command does, `man cp` shows its manual (press **q** to leave), and most commands also accept `--help`.

## `sudo`, `apt`, and why you shouldn't sudo everything

Your account can change your own files. System files, such as installed programs and boot settings, belong to the administrator account, **root**. `sudo` runs one command as root after asking for your password:

```bash
sudo apt update              # refresh the list of available packages
sudo apt install tree        # install a package
tree ~/iot-lab
```

```text
/home/student/iot-lab
├── logs
└── notes.txt

1 directory, 1 file
```

`apt` is the package manager on Raspberry Pi OS, Debian, and Ubuntu. Run `sudo apt update` first so it knows about the newest versions. Use `sudo` only for commands that really change the system. Running your own scripts with `sudo` "to make the error go away" gives every bug in them the power to damage the whole system.

## Permissions: who can read, write, and run a file

`ls -l` shows the details:

```bash
ls -l ~/iot-lab
```

```text
total 8
drwxr-xr-x 2 student student 4096 Nov 16 10:05 logs
-rw-r--r-- 1 student student   58 Nov 16 10:02 notes.txt
```

The first column packs in a lot. The first character is `d` for a directory or `-` for a file. Then come three groups of three: what the **owner** can do, what the **group** can do, and what **everyone else** can do. In each group, `r` means read, `w` means write, `x` means execute (run a program, or enter a directory), and `-` means no.

```python run title="permissions.py"
def describe(mode):
    labels = ["owner", "group", "others"]
    digits = ""
    for i, who in enumerate(labels):
        chunk = mode[i * 3 : i * 3 + 3]
        allowed = [word for flag, word in zip(chunk, ["read", "write", "run"]) if flag != "-"]
        value = (4 if chunk[0] == "r" else 0) + (2 if chunk[1] == "w" else 0) + (1 if chunk[2] == "x" else 0)
        digits += str(value)
        print(f"{who:>6}: {chunk} -> {', '.join(allowed) or 'nothing'}")
    print("as a number:", digits)

describe("rwxr-x---")
```

Each group is also a digit: read is 4, write is 2, run is 1, added together. So `rwxr-x---` is `750`, and `chmod 750 file` sets exactly that. You'll use this in Module 7, where a file holding a device password should be readable by its owner only (`600`).

The permission error you'll meet first comes from running a script you just wrote:

```text
bash: ./logger.py: Permission denied
```

New files aren't executable. Either run it through Python with `python3 logger.py`, or mark it as a program with `chmod +x logger.py` (and give it a first line of `#!/usr/bin/env python3` so the system knows which interpreter to use).

## Physical pins versus GPIO numbers

Both boards in this course number their pins twice. **Physical** (board) numbers count positions on the connector. **GPIO** numbers are the chip's names for the signals, and they're what code uses. They almost never match:

```python run title="pi_header.py"
PI_HEADER = {
    1: "3V3", 2: "5V", 3: "GPIO2", 4: "5V", 5: "GPIO3", 6: "GND", 7: "GPIO4", 8: "GPIO14",
    9: "GND", 10: "GPIO15", 11: "GPIO17", 12: "GPIO18", 13: "GPIO27", 14: "GND", 15: "GPIO22",
    16: "GPIO23", 17: "3V3", 18: "GPIO24", 19: "GPIO10", 20: "GND", 21: "GPIO9", 22: "GPIO25",
    23: "GPIO11", 24: "GPIO8", 25: "GND", 26: "GPIO7", 27: "GPIO0", 28: "GPIO1", 29: "GPIO5",
    30: "GND", 31: "GPIO6", 32: "GPIO12", 33: "GPIO13", 34: "GND", 35: "GPIO19", 36: "GPIO16",
    37: "GPIO26", 38: "GPIO20", 39: "GND", 40: "GPIO21",
}

def physical_pin_of(name):
    return [pin for pin, label in PI_HEADER.items() if label == name]

print("Physical pin 17 is:", PI_HEADER[17])
print("GPIO17 is at physical pin:", physical_pin_of("GPIO17"))
print("Ground pins:", physical_pin_of("GND"))
```

On a real Pi, the `pinout` command (installed with gpiozero on Raspberry Pi OS) prints this map in the terminal. gpiozero accepts either style if you're explicit: `LED(17)` and `LED("GPIO17")` mean GPIO17, while `LED("BOARD11")` means physical pin 11, which is the same wire. On the Pico W, code uses GP numbers (`Pin(15)` is GP15 at physical pin 20), and the drawing in Wokwi labels them.

## Electrical limits: 3.3 V logic and a small current budget

A GPIO pin set high outputs 3.3 V, and a pin used as an input expects somewhere between 0 and 3.3 V. Neither board's GPIO pins tolerate 5 V. The RP2040 chip on the Pico W is rated for at most 0.5 V above its 3.3 V supply on any pin, and Raspberry Pi's documentation warns that 5 V on a GPIO can permanently damage the processor. Many sensors sold for Arduino run at 5 V and output 5 V signals. Those need a level shifter or a voltage divider (two resistors that scale the voltage down) before they touch a GPIO pin.

Current is the other limit. Each pin can only supply a little, and the whole chip has a total budget:

| | Per pin | All GPIO pins together |
| --- | --- | --- |
| Raspberry Pi 4 / 5 | up to 16 mA | 50 mA |
| Pico W (RP2040) | 4 mA at the default drive setting (adjustable from 2 to 12 mA) | 50 mA sourced |

A series resistor sets an LED's current. Ohm's law says the current is the voltage left over after the LED, divided by the resistance:

```python run title="led_current.py"
supply = 3.3       # volts from a GPIO pin
led_drop = 2.0     # a typical red or green LED

for ohms in [100, 220, 330, 1000]:
    milliamps = (supply - led_drop) / ohms * 1000
    note = "ok for a Pico W pin" if milliamps <= 4 else "more than the Pico W's default 4 mA"
    print(f"{ohms:>5} ohms -> {milliamps:4.1f} mA  ({note})")
```

330 Ω gives about 4 mA, which is why the circuits in this course use it. Motors, relays, and long LED strips need far more than any pin can give, so they always go through a driver or transistor with their own supply.

:::warning
**Three mistakes that fail silently.** Wiring to the physical pin number when the guide meant the GPIO number (pin 17 versus GPIO17). Feeding a 5 V sensor output straight into a GPIO pin; it may even work for a while before the pin dies. And on Raspberry Pi OS, trying `sudo pip install` to fix a missing library: modern versions refuse with `error: externally-managed-environment`. Install the Debian package instead (`sudo apt install python3-gpiozero`), or create a virtual environment with `python3 -m venv`.
:::

:::quiz
Q: You're in `/home/student/iot-lab/logs`. Where does `cd ../../projects` take you?
- [ ] `/home/student/iot-lab/projects`
  That needs only one `..`. Each `..` climbs one level, and there are two.
- [x] `/home/student/projects`
  The first `..` leaves `logs`, the second leaves `iot-lab`, then `projects` is added.
- [ ] `/projects`
  Only an absolute path (starting with `/`) would jump to the root.

Q: `ls -l` shows `-rw-r----- 1 student iot 120 settings.env`. Who can read the file?
- [x] The owner `student` and members of the `iot` group
  The owner group is `rw-` and the group's is `r--`; everyone else gets `---`.
- [ ] Everyone, because the file isn't executable
  Read and execute are separate permissions. The last three characters, `---`, deny everything to others.
- [ ] Only `student`
  The middle group `r--` gives the `iot` group read access too.

Q: A tutorial says "connect the button to pin 12" on a Raspberry Pi and its code says `Button(12)`. What's the problem?
- [ ] Nothing; physical pin 12 and GPIO12 are the same wire
  Physical pin 12 is GPIO18. GPIO12 is at physical pin 32.
- [x] gpiozero's `Button(12)` means GPIO12, so if "pin 12" meant the physical pin, the code is reading the wrong wire
  Always check which numbering a guide uses. `Button("BOARD12")` would mean physical pin 12.
- [ ] Buttons can't use pin 12
  Any GPIO pin can read a button.

Q: A distance sensor runs on 5 V and its output pin swings between 0 and 5 V. How should it connect to a Pico W?
- [ ] Directly to GP26, since it's an analog pin
  Analog pins are still 3.3 V pins. 5 V on them can damage the chip.
- [x] Through a voltage divider or level shifter that brings the 5 V signal down to 3.3 V
  That keeps the pin inside its rating while still letting the Pico W see the signal change.
- [ ] Directly to VBUS
  VBUS is a 5 V power pin; connecting a signal there does nothing useful, and code can't read it.
:::

:::takeaways
- `pwd`, `ls`, and `cd` move you around; `..` goes up one folder and `~` is your home folder.
- `cp`, `mv`, and `rm` can destroy files without asking; add `-i` when it matters.
- Use `sudo` for system changes such as `apt install`, never as a fix for your own script's errors.
- `rwx` triplets for owner, group, and others; `chmod +x` makes a script runnable, and `600` locks a file to its owner.
- Code uses GPIO numbers, not physical pin positions. GPIO pins are 3.3 V only, and each has a small current budget.
:::
