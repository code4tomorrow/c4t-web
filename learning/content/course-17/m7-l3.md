## Warm-up: which lines leak?

Each line comes from a station's code. Mark it **safe**, **leaks**, or **avoid**.

1.  `print("Joining", WIFI_SSID, "with password", WIFI_PASSWORD)`
2.  `client.publish(AUDIT, json.dumps({"result": "rejected", "reason": "bad signature"}))`
3.  `client.publish(HEALTH, "crash: " + repr(err) + " key=" + FAN_KEY.decode())`
4.  `print("Using fan key", FAN_KEY[:6])`
5.  `print("Online. Queued messages:", len(box.items))`

:::solution
1.  **Leaks.** Serial output gets copied into chat messages, screenshots, and bug reports.
2.  **Safe.** A reason and nothing else.
3.  **Leaks**, and to a public broker, the worst audience there is.
4.  **Avoid.** Six characters don't hand over the key, but they do make it a little easier to guess, and the habit spreads. Print a key ID like `k2` instead.
5.  **Safe.**
:::

### Exercise 1: A tiny secret scanner

Write `scan(files)` that takes a dict of file names to contents and reports three kinds of problem: a name containing PASSWORD, KEY, TOKEN, or SECRET assigned a non-empty literal (placeholders such as `replace-me` don't count), any hex string 32 characters or longer, and a `print` that mentions KEY or PASSWORD.

```text
main.py:3: prints a secret
old_main.py:1: WIFI_PASSWORD is set to a literal value
notes.txt:1: long hex string (looks like a key)
```

:::hint
Two regular expressions do most of the work: `(\w*(PASSWORD|KEY|TOKEN|SECRET)\w*)\s*=\s*b?["']([^"']+)["']` for assignments (the `b?` allows `b"..."` bytes literals) and `\b[0-9a-f]{32,}\b` for hex. `[^"']+` needs at least one character, so `WIFI_PASSWORD = ""` doesn't match.
:::

:::solution
```python run title="secret_scan.py"
import re

project = {
    "main.py": 'from secrets import FAN_KEY\nBROKER = "broker.hivemq.com"\nprint("key is", FAN_KEY)\n',
    "old_main.py": 'WIFI_PASSWORD = "maple-tree-42"\nDEVICE = "station-01"\n',
    "secrets.example.py": 'WIFI_PASSWORD = ""\nFAN_KEY = b"replace-me"\n',
    "notes.txt": "test key: 9f2c71aa0d4f6a8c1e3b5d7f9a2c4e6b8d0f1a3c5e7b9d2f\n",
    "dashboard.html": 'const PREFIX = "c4t-lab/a7f3c9/greenhouse/";\n',
}

ASSIGN = re.compile(r"""(\w*(PASSWORD|KEY|TOKEN|SECRET)\w*)\s*=\s*b?["']([^"']+)["']""", re.IGNORECASE)
LONG_HEX = re.compile(r"\b[0-9a-f]{32,}\b")
PLACEHOLDERS = {"replace-me", "changeme", "xxx"}

def scan(files):
    findings = []
    for name, text in files.items():
        for number, line in enumerate(text.splitlines(), 1):
            m = ASSIGN.search(line)
            if m and m.group(3).lower() not in PLACEHOLDERS:
                findings.append(f"{name}:{number}: {m.group(1)} is set to a literal value")
            if LONG_HEX.search(line):
                findings.append(f"{name}:{number}: long hex string (looks like a key)")
            if re.search(r"print\(.*(KEY|PASSWORD)", line):
                findings.append(f"{name}:{number}: prints a secret")
    return findings

for finding in scan(project):
    print(finding)
```

The note in `notes.txt` is the sneaky one: no code at all, just a key pasted while testing. Real scanners such as GitHub's work the same way in principle, with hundreds of patterns for known token formats. None can catch everything, which is why secrets belong in a file git never sees.
:::

### Exercise 2: What does git actually keep?

A student runs these commands in a folder containing `main.py` and `secrets.py`:

```bash
git init
git add .
git commit -m "first version"
echo "secrets.py" > .gitignore
git add .gitignore
git commit -m "ignore secrets"
```

Answer three questions: Is `secrets.py` still tracked? Is the password in the history? What exactly should the student do now?

:::hint
`.gitignore` only stops *untracked* files from being added. Think about which commit already contains `secrets.py`, and whether anything since then removed it.
:::

:::solution
Yes, it is still tracked: the first commit added it, and git keeps tracking files it already knows about. Any later edit to `secrets.py` will show up in `git status` and can be committed. And yes, the password is in the history, in the first commit, readable with `git show HEAD~1:secrets.py`.

The fix, in order:

```bash
# 1. Change the password or key itself (router settings, a new token_hex key).
# 2. Stop tracking the file but keep your local copy:
git rm --cached secrets.py
git commit -m "stop tracking secrets.py"
```

The `.gitignore` entry is already in place, so the file won't come back. Rewriting history to remove the first commit's copy is optional cleanup; step 1 is the part that makes the leak harmless.
:::

### Exercise 3: Pick a backoff cap with numbers, not vibes

A longer cap means fewer reconnect attempts during an outage (less load) but a longer wait after the network comes back (more lag). Simulate 2,000 two-minute outages for caps of 4, 16, and 60 seconds, using full jitter from a 1-second base. Report the average number of attempts during the outage and the average and worst lag.

```text
cap   attempts during 120 s outage   average lag   worst lag
  4 s                        61.1         1.4 s       3.8 s
 16 s                        17.8         5.3 s      15.5 s
 60 s                         8.7        19.8 s      58.7 s
```

:::hint
For one outage: keep a clock `t` and a failure count `n`. Each round, add `uniform(0, min(cap, 2 ** n))` to `t`. While `t` is still inside the outage, that try failed: count it. The first try after the outage ends succeeds, and `t - outage` is the lag.
:::

:::solution
```python run title="cap_tradeoff.py"
import random

def one_outage(outage_s, cap_s, rng, base_s=1):
    """Returns (attempts during the outage, seconds of lag after it ends)."""
    t, n, attempts = 0.0, 0, 0
    while True:
        ceiling = min(cap_s, base_s * 2 ** n)
        t += rng.uniform(0, ceiling)
        n += 1
        if t >= outage_s:
            return attempts, t - outage_s
        attempts += 1

rng = random.Random(8)
print("cap   attempts during 120 s outage   average lag   worst lag")
for cap in (4, 16, 60):
    runs = [one_outage(120, cap, rng) for _ in range(2000)]
    attempts = sum(a for a, _ in runs) / len(runs)
    lags = [lag for _, lag in runs]
    print(f"{cap:3} s  {attempts:26.1f}   {sum(lags) / len(lags):9.1f} s  {max(lags):8.1f} s")
```

For one greenhouse station, 61 attempts in two minutes is nothing, and a cap of 4 s gives the fastest recovery. For 500 stations sharing one broker, that becomes 30,000 connection attempts against a broker that is already in trouble, and a cap of 30 to 60 s is kinder. The right cap depends on how many devices share the broker, which is why it's a setting and not a constant buried in the code.
:::

### Exercise 4: Never drop the frost alarm

The outbox from Lesson 2 drops the oldest message when it's full. That's fine for readings, and terrible for a one-off `FROST` alarm that got queued during an outage. Write `PriorityOutbox(capacity)` where `add(topic, payload, keep=False)` marks precious messages. When full, drop the oldest message that *isn't* marked keep; only if every message is precious, drop the oldest one and count it separately.

```text
['FROST', 'r3', 'r4', 'r5'] dropped: 2
['A2', 'A3', 'A4', 'A5'] dropped: 5 alarms lost: 1
```

:::hint
A `for ... else` loop is handy: search for the first item whose `keep` flag is `False` and delete it with `break`. The `else` branch runs only when the loop finished without a `break`, which means everything was precious.
:::

:::solution
```python run title="priority_outbox.py"
class PriorityOutbox:
    def __init__(self, capacity):
        self.capacity = capacity
        self.items = []                      # (topic, payload, keep)
        self.dropped = 0
        self.dropped_kept = 0

    def add(self, topic, payload, keep=False):
        if len(self.items) >= self.capacity:
            for i, item in enumerate(self.items):
                if not item[2]:              # oldest message we're allowed to lose
                    del self.items[i]
                    self.dropped += 1
                    break
            else:                            # everything is precious: lose the oldest anyway
                del self.items[0]
                self.dropped_kept += 1
        self.items.append((topic, payload, keep))

box = PriorityOutbox(capacity=4)
box.add("bed1/temperature", "r1")
box.add("bed1/alarm", "FROST", keep=True)
for r in ["r2", "r3", "r4", "r5"]:
    box.add("bed1/temperature", r)
print([p for _, p, _ in box.items], "dropped:", box.dropped)
for a in ["A2", "A3", "A4", "A5"]:
    box.add("bed1/alarm", a, keep=True)
print([p for _, p, _ in box.items], "dropped:", box.dropped, "alarms lost:", box.dropped_kept)
```

`FROST` survived four readings churning through the box. The second line shows the limit: a flood of alarms eventually pushes out the first one, and `alarms lost: 1` makes sure that loss is reported instead of silent. Messages still leave oldest first, so the alarm goes out before the readings that came after it.
:::

### Exercise 5: A failure-mode table for a freezer monitor

A school cafeteria wants a Pico W in its walk-in freezer: a temperature probe, a buzzer, and MQTT alerts to the kitchen manager's dashboard when the freezer rises above -15 °C. Write a failure-mode table with at least six rows: part, failure, how it's noticed, and designed response.

:::hint
Go part by part: probe, Pico, power, Wi-Fi (a metal freezer box is a famously bad place for radio), broker, dashboard, and the buzzer itself. For each response, ask: does this fail *safe*, meaning that it errs toward the manager finding out?
:::

:::solution
| Part | Failure | How it's noticed | Designed response |
| --- | --- | --- | --- |
| Probe | Unplugged or broken | Read error or impossible value | Sound the buzzer and send a `sensor failed` alert; a broken probe must never look like "all fine" |
| Probe | Stuck at one value | Value unchanged for 30 minutes (a real freezer always wobbles a little) | Send a `sensor suspicious` warning |
| Wi-Fi | No signal from inside the freezer | Connect times out | Mount the Pico outside the door with only the probe cable inside; the buzzer works with no network at all |
| Power | Outage or unplugged | Broker publishes the last will `offline` | Dashboard shows a red `offline` banner; a freezer monitor that's off is itself an alarm |
| Broker | Down | Station's connect fails | Back off and queue alerts with `keep=True`; the buzzer still sounds locally |
| Dashboard | Nobody looking | Alert not acknowledged within 10 minutes | Repeat the alert every 10 minutes until someone acknowledges it |
| Buzzer | Broken | Can't detect without extra hardware | Test it weekly with a "buzzer test" button and log each test |

The thread through every row: **silence must never mean "fine."** Each failure either makes noise locally, shows up as `offline` or `stale` remotely, or both.
:::

### Exercise 6: Review a design

A team presents this classroom CO2 monitor. Find at least six problems, and give a fix for each.

-   The Pico W publishes to `co2` on `broker.hivemq.com`, with the value as a bare number.
-   A teacher's phone app opens a window motor by publishing `open` to `co2/window`.
-   `main.py` contains `WIFI_PASSWORD = "Room214!"` and lives in a public GitHub repository.
-   The dashboard shows each value with `element.innerHTML = payload`.
-   If the sensor fails, the code publishes the last good value so the chart has no gaps.
-   When the broker is unreachable, the code retries `connect()` in a tight loop.

:::hint
Sort your findings into the three halves of this course: messages a dashboard can understand (Module 5), commands only the right person can send (Module 6), and secrets and failures (Module 7). Each bullet has at least one problem.
:::

:::solution
1.  **Ambiguous topic and payload.** Use `c4t-lab/<code>/school/room214/co2` with `{"v": 812, "unit": "ppm", "dev": "...", "seq": ...}`, and a retained status with a last will.
2.  **Anyone can open the window.** Sign commands with HMAC and a counter, or use a private broker with an ACL so only the teacher's account can write to the window topic. Ideally both.
3.  **A school Wi-Fi password in a public repo.** Change the password now, move it to a git-ignored `secrets.py`, and run `git rm --cached` on any tracked copy.
4.  **`innerHTML` with broker data** lets a stranger run script in the dashboard. Validate the payload and display it with `textContent`.
5.  **Publishing stale values as fresh hides the failure.** Publish a `sensor failed` health message and let the dashboard mark the tile stale; a gap in the chart is the truth.
6.  **The tight retry loop** hammers the broker and starves the rest of the program. Use exponential backoff with jitter, and keep the main loop non-blocking.

Bonus: a public broker is wrong for a real classroom anyway. Data about a specific room in a specific school is exactly what HiveMQ and Mosquitto ask you not to publish.
:::

### Challenge: Test a reconnect state machine without hardware

Model the station's connection logic in plain Python, with a fake clock that ticks once per second. `step(now, wifi_up, broker_up)` moves through `join_wifi`, `wait_wifi` (5-second deadline), `connect_broker`, `online`, and `backoff` (full jitter, 1-second base, 16-second cap). One step may pass through several states. Run a scenario with Wi-Fi down from 10 to 30 s and the broker down from 50 to 70 s, and check three properties: it subscribes on every connect, it's back online within 21 s of each outage ending, and the backoff has reset by the end.

```mermaid caption="States for the challenge. Each arrow is one check inside step()."
stateDiagram-v2
    [*] --> join_wifi
    join_wifi --> wait_wifi: start the 5 s deadline
    wait_wifi --> connect_broker: Wi-Fi up
    wait_wifi --> backoff: deadline passed
    connect_broker --> online: broker up, subscribe, reset backoff
    connect_broker --> backoff: broker down
    online --> backoff: Wi-Fi or broker lost
    backoff --> join_wifi: retry time reached
```

:::hint
Write `step()` as a chain of separate `if` statements rather than `if`/`elif`, in the same order as the arrows, so a station whose retry time arrives while Wi-Fi is already up can go from `backoff` all the way to `online` in one tick. Put the subscribe count and the backoff reset in the one place the station becomes `online`, and neither can be forgotten.
:::

:::solution
```python run title="state_machine_test.py"
import random

class Station:
    CAP_S = 16
    WIFI_DEADLINE_S = 5

    def __init__(self, rng):
        self.rng = rng
        self.state = "join_wifi"
        self.retry_at = 0
        self.deadline = 0
        self.failures = 0
        self.subscriptions = 0
        self.log = []

    def back_off(self, now, why):
        ceiling = min(self.CAP_S, 2 ** self.failures)
        self.failures = min(self.failures + 1, 16)
        wait = max(1, round(self.rng.uniform(0, ceiling)))
        self.retry_at = now + wait
        self.state = "backoff"
        self.log.append(f"t={now:3}  {why}, waiting {wait} s")

    def step(self, now, wifi_up, broker_up):
        if self.state == "backoff" and now >= self.retry_at:
            self.state = "join_wifi"
        if self.state == "join_wifi":
            self.deadline = now + self.WIFI_DEADLINE_S
            self.state = "wait_wifi"
        if self.state == "wait_wifi":
            if wifi_up:
                self.state = "connect_broker"
            elif now >= self.deadline:
                self.back_off(now, "Wi-Fi timed out")
        if self.state == "connect_broker":
            if broker_up:
                self.state = "online"
                self.subscriptions += 1          # resubscribe on every new connection
                self.failures = 0                # and reset the backoff
                self.log.append(f"t={now:3}  online, subscribed")
            else:
                self.back_off(now, "broker refused")
        elif self.state == "online" and not (wifi_up and broker_up):
            self.back_off(now, "connection lost")

station = Station(random.Random(2))
online_at = []
for now in range(121):
    wifi_up = not (10 <= now < 30)
    broker_up = not (50 <= now < 70)
    before = station.state
    station.step(now, wifi_up, broker_up)
    if station.state == "online" and before != "online":
        online_at.append(now)

for line in station.log:
    print(line)
print("online at:", online_at)
print("subscribed on every connect:", station.subscriptions == len(online_at))
print("back within 21 s of each outage ending:",
      all(any(end <= t <= end + 21 for t in online_at) for end in (30, 70)))
print("backoff reset at the end:", station.failures == 0)
```

The broker outage shows backoff growing (1, 1, 3, 2, 10, 10 s) while the Wi-Fi is fine, and the station returned at t = 77, seven seconds after the broker did: well inside the 21-second budget of a 16-second cap plus the 5-second Wi-Fi deadline. Testing the state machine this way takes a second; testing it by unplugging a router takes an afternoon.
:::
