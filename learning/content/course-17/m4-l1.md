One reading tells you the greenhouse is 22.4 °C right now. It can't tell you whether that's normal, whether it's rising, or whether the heater failed at 3 a.m. Those answers come from a **time series**: the same measurement, taken repeatedly, each with the time it was taken.

Getting a time series right means making five decisions: how often to sample, which clock to trust, how to store the readings, how to deal with noise, and what to do when the network disappears for twenty minutes. This lesson takes them in that order.

## How often to sample, and what aliasing looks like

Sampling too slowly misses events. Sampling too fast fills storage, drains batteries, and floods the network with near-identical numbers. The right interval depends on the fastest change you care about.

Slow sampling can do worse than miss things: it can invent patterns that aren't there. Suppose a heater cycles on and off every 10 minutes, swinging the temperature by ±1.5 °C. Watch what readings every 9 minutes show:

```python run alt="A temperature line oscillating every 10 minutes for three hours. Samples taken every minute follow it closely. Samples taken every 9 minutes form a slow wave with a 90-minute period that does not exist in the real signal." caption="Sampling every 9 minutes turns a 10-minute cycle into a fake 90-minute wave."
import numpy as np
import matplotlib.pyplot as plt

def room(minutes):
    return 22 + 1.5 * np.sin(2 * np.pi * minutes / 10)

t = np.linspace(0, 180, 1801)
fast = np.arange(0, 181, 1)
slow = np.arange(0, 181, 9)

plt.figure(figsize=(7.5, 3.2))
plt.plot(t, room(t), color="#bbbbbb", linewidth=1, label="real temperature")
plt.plot(fast, room(fast), ".", color="#4a6fe3", markersize=4, label="every 1 min")
plt.plot(slow, room(slow), "o-", color="#d9822b", label="every 9 min")
plt.xlabel("minutes")
plt.ylabel("°C")
plt.legend(loc="lower center", bbox_to_anchor=(0.5, 1.0), ncol=3, fontsize=8, frameon=False)
plt.tight_layout()
```

The orange line is a slow, smooth wave that never happened. This effect is **aliasing**. The theory (the Nyquist rate) says you need more than two samples per cycle of the fastest change to capture it at all; in practice, engineers aim for five to ten. Room air changes over minutes, so a reading every 10 to 60 seconds is plenty. A vibration sensor might need thousands of readings per second.

A clear walkthrough of sampling, aliasing, and the Nyquist theorem. Watch for the moment a fast wave, sampled too slowly, turns into a slower one. It's the same thing the 9-minute samples did above.
:::

## Which clock goes on each reading

The Pico W has more than one idea of "now", and they answer different questions:

| Clock | What it gives | Good for | Watch out |
| --- | --- | --- | --- |
| `time.ticks_ms()` | Milliseconds since power-up | Timers in the loop, measuring durations | Restarts at 0 on every reboot; wraps after about 12 days |
| `time.time()`, `time.gmtime()` | Calendar time from the board's clock | Timestamps in logs | Wrong until something sets it; a fresh board can think it's years in the past |
| `ntptime.settime()` | Sets the board's clock to UTC from an internet time server | Making `time.time()` correct after Wi-Fi connects | Needs the network; check it worked before trusting timestamps |

The pattern most IoT devices use: connect to Wi-Fi, set the clock with NTP, then stamp every reading with UTC. **UTC** never jumps for daylight saving, so 01:30 can't happen twice in one night. Convert to local time only when you display data. If NTP fails, record `ticks_ms` with the reading and mark the calendar time as unknown, rather than writing a wrong date that looks right.

## Logging to CSV, and how fast the flash fills

A CSV log stores one row per reading, with the units in the column names so nobody has to guess:

```text
time_utc,temp_c,light_pct
2026-11-16T14:03:20Z,22.4,61.5
2026-11-16T14:03:30Z,22.5,61.2
```

On the board, appending a row is `open("log.csv", "a")` and `write()`. The catch is space: the Pico W's MicroPython firmware leaves 848 KB of flash for files. Here's how long that lasts at different intervals:

```python run
row = "2026-11-16T14:03:20Z,22.4,61.5\n"
flash_bytes = 848 * 1024

print(f"one row is {len(row)} bytes")
for interval_s in [2, 10, 60]:
    per_day = 86_400 / interval_s * len(row)
    print(f"every {interval_s:>2} s: {per_day / 1024:7.1f} KB per day -> full in {flash_bytes / per_day:5.1f} days")
```

At one reading every 2 seconds the board fills in about half a day. That's one reason devices *send* their data somewhere rather than keeping it all. Flash also wears out after many rewrites of the same block, so loggers collect several rows in memory and write them in one go rather than opening the file for every reading.

## Smoothing: moving averages and exponential averages

Here are 90 minutes of simulated readings with sensor noise and one glitch at minute 40:

```python run
import pandas as pd

rng = np.random.default_rng(4)
minutes = np.arange(90)
true_temp = 21 + 2.5 * minutes / 90
raw = true_temp + rng.normal(0, 0.35, size=90)
raw[40] += 4.0  # a glitch: a loose wire for one reading

log = pd.DataFrame({"minute": minutes, "temp_c": raw.round(2)})
log["moving_avg_5"] = log["temp_c"].rolling(5).mean()
log["ema_0.3"] = log["temp_c"].ewm(alpha=0.3, adjust=False).mean()
print(log.iloc[36:46].round(2).to_string(index=False))
```

A **moving average** of 5 is the mean of the last five readings. An **exponential moving average** (EMA) keeps one running value and nudges it a fraction `alpha` of the way toward each new reading:

`smooth = smooth + alpha × (reading − smooth)`

Step through it with a short series that includes a glitch:

:::trace An exponential moving average absorbing a spike
```python
readings = [22.0, 22.1, 25.0, 22.2, 22.1]
alpha = 0.3
smooth = readings[0]
for reading in readings[1:]:
    smooth = smooth + alpha * (reading - smooth)
print(round(smooth, 2))
```
:::

The EMA only needs to remember one number, which makes it ideal on a microcontroller. Both kinds of smoothing pay for their calm with **lag**: the smoothed line reacts late to real changes.

```python run alt="Noisy temperature readings rising over 90 minutes with a spike at minute 40. A 5-point moving average and an exponential moving average both follow the trend more calmly; both bump up after the spike and lag slightly behind the raw readings." caption="Smoothing hides noise but adds lag, and a spike still leaves a bump."
plt.figure(figsize=(7.5, 3.4))
plt.plot(log["minute"], log["temp_c"], ".", color="#999999", label="raw")
plt.plot(log["minute"], log["moving_avg_5"], color="#4a6fe3", label="moving average (5)")
plt.plot(log["minute"], log["ema_0.3"], color="#d9822b", label="EMA (alpha 0.3)")
plt.xlabel("minute")
plt.ylabel("°C")
plt.legend(fontsize=8)
plt.tight_layout()
```

Notice the glitch: neither average removes it; they spread it into a smaller bump that lasts several minutes. Impossible values should be *rejected* (as the thermistor function in Module 3 did) before smoothing. And log the raw readings, smoothing only for display or decisions, because smoothing can't be undone later.

## JSON payloads: readings that describe themselves

A CSV row only makes sense next to its header. When a reading travels alone over a network, it needs to carry its own labels. **JSON** does that with the same syntax as a Python dictionary:

```python run
import json

reading = {"device": "greenhouse-01", "seq": 418, "time": "2026-11-16T14:03:20Z", "temp_c": 22.4, "light_pct": 61.5}
payload = json.dumps(reading)
print(payload)
print(len(payload), "bytes as JSON, versus", len(row), "bytes as a CSV row")

received = json.loads(payload)
print("the receiver gets a number back:", received["temp_c"] + 1)
```

The JSON is more than three times bigger, and that's usually worth it: any program can read it without knowing the column order, and adding a field later doesn't break old readers. MicroPython's `json` module has the same `dumps` and `loads`. The `seq` field is a counter that goes up by one with every reading, so the receiver can spot missing ones. Round values before sending: `0.1 + 0.2` is `0.30000000000000004` in both Pythons, and those digits travel in the payload.

## When the network drops: buffer, don't lose

A device that sends each reading the moment it's taken loses every reading taken while Wi-Fi is down. The fix is **store and forward**: put each payload in a queue, send from the front of the queue when the network is up, and remove a payload only after the receiver confirms it.

```mermaid caption="Store and forward: nothing leaves the queue until the receiver confirms it"
flowchart LR
    A[Take reading] --> B[Append to queue]
    B --> C{"Network up?"}
    C -->|no| D[Keep it; try later]
    C -->|yes| E[Send oldest batch]
    E --> F{"Receiver confirmed?"}
    F -->|yes| G[Remove batch from queue]
    F -->|no| D
```

Memory is limited, so the queue needs a maximum length, and you have to decide what happens when it's full. Dropping the **oldest** readings keeps the most recent picture accurate. This simulation runs a 40-minute outage at one reading a minute with two queue sizes:

```python run
from collections import deque

def run(queue_size, outage=range(20, 60), minutes=90):
    queue, delivered, dropped = deque(), [], 0
    for minute in range(minutes):
        queue.append(minute)
        if len(queue) > queue_size:
            queue.popleft()
            dropped += 1
        if minute not in outage:
            while queue:
                delivered.append(queue.popleft())
    return delivered, dropped

for size in [60, 25]:
    delivered, dropped = run(size)
    missing = sorted(set(range(90)) - set(delivered))
    print(f"queue of {size}: delivered {len(delivered)}, dropped {dropped}, first missing: {missing[:3]}")
```

With room for 60, nothing is lost. With room for 25, the 16 oldest readings from the outage are dropped (the queue also takes minute 60's reading before it can send), and because each reading has a `seq` number, the receiver can tell exactly which ones. A gap you can detect beats a gap nobody notices.

:::warning
**Time-series mistakes that hide in plain sight.** Using `ticks_ms()` as the timestamp in a log, which restarts at zero after every reboot so rows from different days interleave. Logging local time, which repeats an hour each autumn. Smoothing before logging, so the raw data is gone. Writing the log file on every reading, which wears the flash. And a queue with no limit, which works fine in testing and runs out of memory during the first long outage.
:::

:::quiz
Q: A door sensor must notice a door opened for at least 4 seconds. Which sampling interval is the most sensible?
- [ ] Every 10 seconds
  A 4-second opening could fall entirely between two readings and never be seen.
- [x] Every 0.5 seconds
  That gives about eight samples during the shortest event, comfortably above the two-per-event minimum.
- [ ] Every 1 millisecond
  It would work, but it creates 4,000 readings per event for no benefit.

Q: Why store `2026-11-16T14:03:20Z` rather than the local time?
- [x] UTC never repeats or skips an hour, so readings always sort and subtract correctly
  Local time jumps at daylight-saving changes; convert to local only for display.
- [ ] Local time takes more bytes
  The size is about the same; the problem is ambiguity.
- [ ] MicroPython can't print local time
  It can; the issue is what's stored, not what's possible.

Q: An EMA with `alpha = 0.3` is at 22.0 °C and the next reading is 25.0 °C. What is the new smoothed value?
- [ ] 25.0
  That would be `alpha = 1`, which is no smoothing at all.
- [x] 22.9
  22.0 + 0.3 × (25.0 − 22.0) = 22.9.
- [ ] 23.5
  That's the plain average of the two values, which an EMA doesn't compute.

Q: The queue holds 25 readings and a 40-minute outage produces 40. What should the device do with the extra 15?
- [ ] Crash with a memory error so someone notices
  A crash loses everything in memory, including the 25 readings you could have kept.
- [ ] Silently drop the newest readings
  New readings describe the current state, so they're usually the most valuable; dropping them hides what's happening now.
- [x] Drop the oldest, and let `seq` numbers reveal the gap
  The most recent data survives, and the receiver can see precisely which readings are missing.
:::

:::takeaways
- Sample five to ten times faster than the quickest change you care about; too slow causes aliasing, too fast wastes space and power.
- Timers use `ticks_ms`; log timestamps use UTC from a clock set by NTP, with "unknown" when it isn't set.
- A 30-byte CSV row every 2 s fills the Pico W's 848 KB in about half a day; write rows in batches.
- Moving averages and EMAs reduce noise but add lag; reject impossible values first and log the raw data.
- JSON payloads carry their own labels; a `seq` counter lets the receiver detect missing readings.
- Store and forward: queue every payload, delete only after confirmed delivery, and cap the queue by dropping the oldest.
:::
