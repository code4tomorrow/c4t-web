### Exercise 1: Where does this land?

Your home folder is `/home/student`. Predict what the last command prints, then write a small Python function that follows `cd` commands and check your answer.

```bash
cd ~
mkdir -p iot-lab/m3/logs
cd iot-lab/m3
cd logs/../..
pwd
```

```text
/home/student/iot-lab
```

:::hint
`mkdir` doesn't move you. After `cd iot-lab/m3` you're in `/home/student/iot-lab/m3`. Then go into `logs`, up one, up one more.
:::

:::solution
```python run title="follow_cd.py"
HOME = "/home/student"

def cd(current, target):
    if target.startswith("~"):
        current, target = HOME, target[1:].lstrip("/")
    elif target.startswith("/"):
        current, target = "/", target.lstrip("/")
    parts = [p for p in current.split("/") if p]
    for step in target.split("/"):
        if step == "..":
            if parts:
                parts.pop()
        elif step not in (".", ""):
            parts.append(step)
    return "/" + "/".join(parts)

where = "/tmp"
for target in ["~", "iot-lab/m3", "logs/../.."]:
    where = cd(where, target)
    print(f"cd {target:<12} -> {where}")
```

`logs/../..` goes into `logs`, back out to `m3`, then up to `iot-lab`. The `if parts:` guard copies a real shell rule: `cd ..` at `/` stays at `/`.
:::

### Exercise 2: Permissions for three kinds of file

Write `to_string("640")` that turns a `chmod` number into a permission string like `rw-r-----`. Then choose a number for each file:

1.  `logger.py`: you edit and run it; nobody else should touch it.
2.  `readings.csv`: you write it; your group (the dashboard account) reads it.
3.  `device.env`: holds a password; only you may read or change it.

```text
logger.py     700  rwx------
readings.csv  640  rw-r-----
device.env    600  rw-------
```

:::hint
Each digit is a sum: read 4, write 2, run 1. So `rw-` is 4 + 2 = 6 and `r--` is 4. Loop over the three digits and build three characters for each.
:::

:::solution
```python run title="chmod_numbers.py"
def to_string(number):
    result = ""
    for digit in number:
        value = int(digit)
        result += "r" if value & 4 else "-"
        result += "w" if value & 2 else "-"
        result += "x" if value & 1 else "-"
    return result

for name, number in [("logger.py", "700"), ("readings.csv", "640"), ("device.env", "600")]:
    print(f"{name:<13} {number}  {to_string(number)}")
```

`value & 4` tests whether the 4 bit is set in that digit. The secrets file gets no group or "others" access at all, which is the rule Module 7 relies on: a credential file should be `600`.
:::

### Exercise 3: Read four terminal errors

For each message, say what went wrong and give the command that fixes it.

```text
1. bash: ./pincheck.py: Permission denied
2. cp: cannot create regular file '/etc/iot-lab.conf': Permission denied
3. bash: pyhton3: command not found
4. /usr/bin/env: 'python3\r': No such file or directory
```

:::hint
Two of these are about permissions, but they need very different fixes. For the last one, look closely at the `\r`: what kind of computer adds that to the end of every line?
:::

:::solution
1.  The file isn't executable. Run `chmod +x pincheck.py`, or run it as `python3 pincheck.py`.
2.  `/etc` belongs to root. `sudo cp` would work, but first ask whether the file belongs there at all. A project's settings can live in `~/iot-lab`, which needs no special rights. Use `sudo` only when a system service really reads from `/etc`.
3.  A typo: the command is `python3`. Press the Up arrow, fix it, and press Enter.
4.  The file was saved with Windows line endings, so the first line ends in a hidden carriage return (`\r`) and the system looks for a program literally called `python3\r`. Convert it with `sed -i 's/\r$//' pincheck.py`, or set your editor to save with LF line endings.

```bash
chmod +x pincheck.py
sed -i 's/\r$//' pincheck.py
./pincheck.py plan.csv
```
:::

### Exercise 4: Audit a wiring list for a Raspberry Pi

A tutorial lists its connections by **physical** pin. Write `audit(wires)` that prints what each physical pin really is and flags any signal wire landing on a power or ground pin.

```python
wires = [("LED (via 330 ohm)", 11), ("button", 13), ("sensor data", 17), ("sensor ground", 14)]
```

```text
LED (via 330 ohm)  -> pin 11 = GPIO17
button             -> pin 13 = GPIO27
sensor data        -> pin 17 = 3V3  <-- a signal on a power pin!
sensor ground      -> pin 14 = GND
```

:::hint
Use a dictionary from physical pin to name, like the one in the notes. A wire is suspicious if its name doesn't contain "ground" but the pin is `3V3`, `5V`, or `GND`.
:::

:::solution
```python run title="audit_wires.py"
PI_HEADER = {
    1: "3V3", 2: "5V", 3: "GPIO2", 4: "5V", 5: "GPIO3", 6: "GND", 7: "GPIO4", 8: "GPIO14",
    9: "GND", 10: "GPIO15", 11: "GPIO17", 12: "GPIO18", 13: "GPIO27", 14: "GND", 15: "GPIO22",
    16: "GPIO23", 17: "3V3", 18: "GPIO24", 19: "GPIO10", 20: "GND", 21: "GPIO9", 22: "GPIO25",
    23: "GPIO11", 24: "GPIO8", 25: "GND", 26: "GPIO7", 27: "GPIO0", 28: "GPIO1", 29: "GPIO5",
    30: "GND", 31: "GPIO6", 32: "GPIO12", 33: "GPIO13", 34: "GND", 35: "GPIO19", 36: "GPIO16",
    37: "GPIO26", 38: "GPIO20", 39: "GND", 40: "GPIO21",
}
POWER = {"3V3", "5V", "GND"}

def audit(wires):
    for label, pin in wires:
        name = PI_HEADER[pin]
        flag = ""
        if name in POWER and "ground" not in label:
            flag = "  <-- a signal on a power pin!"
        print(f"{label:<18} -> pin {pin} = {name}{flag}")

audit([("LED (via 330 ohm)", 11), ("button", 13), ("sensor data", 17), ("sensor ground", 14)])
```

The tutorial almost certainly meant GPIO17 for the sensor, but GPIO17 already drives the LED. The honest fix is to choose a free GPIO pin, such as GPIO22 at physical pin 15, and update both the wire and the code.
:::

### Exercise 5: LED resistors on a 3.3 V pin

Aim for about 4 mA per LED from a 3.3 V pin. Find the smallest standard resistor (10, 12, 15, 18, 22, 27, 33, 39, 47, 56, 68, 82, times 1, 10, or 100) that keeps the current at or below 4 mA for a red LED (2.0 V), a green LED (2.2 V), and a blue LED (3.0 V). Then explain why the blue LED is a bad idea on 3.3 V.

```text
red    2.0 V: use 330 ohms -> 3.94 mA
green  2.2 V: use 330 ohms -> 3.33 mA
blue   3.0 V: use 82 ohms -> 3.66 mA
```

:::hint
The ideal resistance is (3.3 − LED voltage) / 0.004. Walk through the standard values from smallest to largest and stop at the first one that's at least that big. For the blue LED, try a forward voltage of 2.9 V and of 3.2 V; real LEDs from one bag vary that much.
:::

:::solution
```python run title="led_resistors.py"
BASES = [10, 12, 15, 18, 22, 27, 33, 39, 47, 56, 68, 82]
STANDARD = [base * scale for scale in (1, 10, 100) for base in BASES]

def pick(led_v, supply=3.3, target_ma=4.0):
    ideal = (supply - led_v) / (target_ma / 1000)
    ohms = next(value for value in STANDARD if value >= ideal)
    return ohms, (supply - led_v) / ohms * 1000

for color, led_v in [("red", 2.0), ("green", 2.2), ("blue", 3.0)]:
    ohms, ma = pick(led_v)
    print(f"{color:<6} {led_v} V: use {ohms} ohms -> {ma:.2f} mA")

print()
for led_v in [2.9, 3.0, 3.2]:
    print(f"blue LED at {led_v} V with 82 ohms: {(3.3 - led_v) / 82 * 1000:.1f} mA")
```

With only 0.3 V left over, small differences between LEDs swing the current from about 5 mA to about 1 mA, so one blue LED glows and its neighbor looks dead. Blue and white LEDs need a higher supply and a transistor, or a red, green, or yellow LED instead.
:::

### Exercise 6: A voltage divider for a 5 V sensor

A sensor's output swings from 0 to 5 V. A divider uses two resistors: R1 from the sensor's output to the GPIO pin, and R2 from the pin to ground. The pin sees `5 × R2 / (R1 + R2)`. Using standard values between 1 kΩ and 82 kΩ, list pairs whose output lands between 3.0 V and 3.3 V, with a total resistance of at least 10 kΩ so the divider doesn't load the sensor much. Print the five closest to 3.2 V.

```text
R1 = 22k  R2 = 39k  -> 3.20 V
R1 = 5.6k  R2 = 10k  -> 3.21 V
...
```

:::hint
Loop over every R1 and every R2 from the standard list, compute the output, keep the pairs that pass both tests, then sort them by `abs(volts - 3.2)`. Watch out: 10k and 20k gives 3.33 V, a hair too high.
:::

:::solution
```python run title="divider.py"
BASES = [10, 12, 15, 18, 22, 27, 33, 39, 47, 56, 68, 82]
VALUES = [base * 100 for base in BASES] + [base * 1000 for base in BASES]  # 1k to 82k

good = []
for r1 in VALUES:
    for r2 in VALUES:
        volts = 5.0 * r2 / (r1 + r2)
        if 3.0 <= volts <= 3.3 and r1 + r2 >= 10_000:
            good.append((abs(volts - 3.2), r1, r2, volts))

good.sort()
for _, r1, r2, volts in good[:5]:
    print(f"R1 = {r1 / 1000:g}k  R2 = {r2 / 1000:g}k  -> {volts:.2f} V")
print(len(good), "pairs pass")
```

Many pairs work because only the ratio matters: R2 needs to be a bit under twice R1. The minimum total keeps the divider from drawing much current from the sensor. A divider only works for signals going *into* the Pico W, and it's too slow for very fast signals; a level-shifter chip handles those.
:::

:::

### Challenge: Catch PWM pins that can't work together

On the Pico W's RP2040 chip, PWM comes from 8 **slices**, each with two **channels**, A and B. GPIO pin `n` uses slice `(n // 2) % 8` and channel A if `n` is even, B if odd. Two rules follow: pins on the **same slice** must run at the **same frequency**, and pins on the **same slice and channel** always get the **same duty cycle**, so they can't be controlled separately.

Write `pwm_conflicts(outputs)` for a list of `(part, pin_number, frequency_hz)` and report every broken rule. Test it with a servo on GP16 at 50 Hz, a status LED on GP17 at 1000 Hz, and a fan LED on GP0 at 50 Hz.

```text
servo (GP16) and status_led (GP17) share slice 0 but want 50 Hz and 1000 Hz
servo (GP16) and fan_led (GP0) share slice 0 channel A, so they can't have different brightness
status_led (GP17) and fan_led (GP0) share slice 0 but want 1000 Hz and 50 Hz
```

:::hint
Compute `(slice, channel)` for each output. Compare every pair with two nested loops (or `itertools.combinations`): same slice with different frequencies is one problem; same slice and channel is the other.
:::

:::solution
```python run title="pwm_conflicts.py"
from itertools import combinations

def slice_and_channel(pin):
    return (pin // 2) % 8, "A" if pin % 2 == 0 else "B"

def pwm_conflicts(outputs):
    found = []
    for (name1, pin1, hz1), (name2, pin2, hz2) in combinations(outputs, 2):
        s1, c1 = slice_and_channel(pin1)
        s2, c2 = slice_and_channel(pin2)
        if s1 != s2:
            continue
        label = f"{name1} (GP{pin1}) and {name2} (GP{pin2})"
        if c1 == c2:
            found.append(f"{label} share slice {s1} channel {c1}, so they can't have different brightness")
        elif hz1 != hz2:
            found.append(f"{label} share slice {s1} but want {hz1} Hz and {hz2} Hz")
    return found

outputs = [("servo", 16, 50), ("status_led", 17, 1000), ("fan_led", 0, 50)]
for problem in pwm_conflicts(outputs):
    print(problem)

print("after moving the LEDs to GP14 and GP15:", pwm_conflicts([("servo", 16, 50), ("status_led", 15, 1000), ("alarm_led", 14, 1000)]))
```

GP16 and GP17 are neighbors, so they share slice 0; the servo needs 50 Hz while LEDs usually run much faster, and one slice can't do both. GP0 is slice 0 channel A, exactly like GP16, and it drags the status LED into a third conflict. Moving both LEDs to GP14 and GP15 (slice 7, both at 1000 Hz) leaves the servo alone on its slice, which is the layout Module 3 uses.
:::
