## Warm-up: who hears this message?

A station publishes to `c4t-lab/q8z2rw/greenhouse/bed2/humidity`. Without running anything, decide which of these subscriptions receive it:

1.  `c4t-lab/q8z2rw/#`
2.  `c4t-lab/+/greenhouse/+/humidity`
3.  `c4t-lab/q8z2rw/greenhouse/+`
4.  `#`
5.  `c4t-lab/q8z2rw/greenhouse/bed2/humidity/#`

:::solution
1, 2, 4, and 5 receive it. Number 3 fails because `+` covers one level and the topic has two left (`bed2/humidity`). Number 5 surprises people: `#` also matches **zero** levels, so `x/#` receives messages on `x` itself.
:::

### Exercise 1: Untangle a messy topic scheme

A previous student's greenhouse sent these messages. Write a new topic and payload for each, using the prefix `c4t-lab/q8z2rw/greenhouse`.

| Old topic | Old payload | What it really was |
| --- | --- | --- |
| `temp` | `72` | Bed 1 air temperature, Fahrenheit |
| `temp` | `22.5` | Bed 2 air temperature, Celsius |
| `hum` | `0.41` | Bed 1 humidity as a fraction |
| `greenhouseTemp` | `23` | Bed 2 again, from a second board |
| `/Bed 2/Soil` | `310` | Bed 2 soil moisture, raw ADC count |
| `status` | `1` | Station 1 is running |

:::hint
One topic per measurement per place. Units go in the payload, and you can convert a fraction to a percentage before publishing. A raw ADC count is a legitimate unit if you say so.
:::

:::solution
| New topic | New payload |
| --- | --- |
| `.../bed1/temperature` | `{"v": 72, "unit": "F", "dev": "station-01", "seq": 1}` |
| `.../bed2/temperature` | `{"v": 22.5, "unit": "C", "dev": "station-02", "seq": 1}` |
| `.../bed1/humidity` | `{"v": 41, "unit": "%", "dev": "station-01", "seq": 1}` |
| `.../bed2/temperature` | `{"v": 23, "unit": "C", "dev": "station-03", "seq": 1}` |
| `.../bed2/soil` | `{"v": 310, "unit": "adc", "dev": "station-02", "seq": 1}` |
| `.../devices/station-01/status` | `online` (retained, with `offline` as the last will) |

Two boards now publish to `bed2/temperature`, and that is fine, because `dev` tells them apart. If you want them on separate tiles, add a level: `bed2/temperature/station-03`. The fractional humidity became a percentage so every humidity reading in the system means the same thing.
:::

### Exercise 2: Validate a topic filter

Write `valid_filter(f)` that returns `False` for filters a broker would reject. The rules: a filter can't be empty, `#` must be a whole level on its own and the last level, and `+` must be a whole level on its own. Empty levels (`a//b`) are allowed.

```text
'c4t-lab/a7f3c9/#'                       True
'c4t-lab/+/greenhouse/+/temperature'     True
'#'                                      True
'+'                                      True
'c4t-lab/#/temperature'                  False
'c4t-lab/bed#'                           False
'c4t-lab/bed+/temp'                      False
''                                       False
'c4t-lab//temp'                          True
```

:::hint
Split on `/` and use `enumerate` so you know when you're at the last level. For each level, ask: does it contain a wildcard character, and if so, is the level exactly that character?
:::

:::solution
```python run title="valid_filter.py"
def valid_filter(f):
    if f == "":
        return False
    levels = f.split("/")
    for i, level in enumerate(levels):
        if "#" in level and (level != "#" or i != len(levels) - 1):
            return False
        if "+" in level and level != "+":
            return False
    return True

tests = ["c4t-lab/a7f3c9/#", "c4t-lab/+/greenhouse/+/temperature", "#", "+",
         "c4t-lab/#/temperature", "c4t-lab/bed#", "c4t-lab/bed+/temp", "", "c4t-lab//temp"]
for f in tests:
    print(f"{f!r:40} {valid_filter(f)}")
```

`"#" in level` catches `bed#`, and the `i != len(levels) - 1` part catches a `#` that is a whole level but not the last one.
:::

### Exercise 3: Route messages, and keep `$SYS` private

Brokers publish their own statistics on topics that start with `$`, such as `$SYS/broker/uptime`. The MQTT rule: a filter that **starts** with a wildcard never matches a topic that starts with `$`, so a `#` subscriber doesn't drown in broker internals. Add that rule to the matcher from the notes, then write `route()` so it prints who receives each message.

```text
c4t-lab/q8z2rw/greenhouse/bed1/temperature    -> dashboard, logger, snoop
c4t-lab/q8z2rw/greenhouse/bed1/soil/alarm     -> dashboard, alarm, snoop
c4t-lab/q8z2rw/greenhouse                     -> dashboard, snoop
c4t-lab/zz9/greenhouse/bed1/temperature       -> snoop
$SYS/broker/uptime                            -> nobody
```

:::hint
The `$` check goes at the top of `matches()`, before any splitting: look at the topic's first character and the filter's first character. In `route()`, a list comprehension over `subscriptions.items()` collects the names.
:::

:::solution
```python run title="route.py"
def matches(pattern, topic):
    if topic.startswith("$") and pattern[:1] in ("+", "#"):
        return False
    p = pattern.split("/")
    t = topic.split("/")
    for i in range(len(p)):
        if p[i] == "#":
            return True
        if i >= len(t):
            return False
        if p[i] != "+" and p[i] != t[i]:
            return False
    return len(p) == len(t)

subscriptions = {
    "dashboard": "c4t-lab/q8z2rw/greenhouse/#",
    "logger": "c4t-lab/q8z2rw/greenhouse/+/temperature",
    "alarm": "c4t-lab/q8z2rw/greenhouse/+/+/alarm",
    "snoop": "#",
}
messages = [
    "c4t-lab/q8z2rw/greenhouse/bed1/temperature",
    "c4t-lab/q8z2rw/greenhouse/bed1/soil/alarm",
    "c4t-lab/q8z2rw/greenhouse",
    "c4t-lab/zz9/greenhouse/bed1/temperature",
    "$SYS/broker/uptime",
]

def route(messages, subscriptions):
    for topic in messages:
        who = [name for name, f in subscriptions.items() if matches(f, topic)]
        print(f"{topic:45} -> {', '.join(who) or 'nobody'}")

route(messages, subscriptions)
```

Look at the `snoop` column: a `#` subscriber receives every other student's messages too. That is what "public broker" means in practice.
:::

### Exercise 4: Reject payloads you shouldn't trust

Write `parse_reading(topic, payload)` for a dashboard. It returns a clean dict, converting Fahrenheit to Celsius, or a string saying why the message was rejected. It must survive everything in this inbox:

```text
{'where': 'bed1', 'what': 'temperature', 'v': 23.4, 'unit': 'C'}
{'where': 'bed2', 'what': 'temperature', 'v': 22.5, 'unit': 'C'}
rejected: v is not a number
rejected: v is not a number
rejected: unknown unit 'lux'
rejected: not a JSON object
rejected: not JSON
```

:::hint
`json.loads` raises `ValueError` on bad JSON, and `json.loads(b"23.4")` happily returns a float, so check that you got a dict. Watch out for `true`: in Python, `isinstance(True, int)` is `True`, so test for `bool` first.
:::

:::solution
```python run title="parse_reading.py"
import json

PREFIX = "c4t-lab/q8z2rw/greenhouse/"

def parse_reading(topic, payload):
    if not topic.startswith(PREFIX):
        return "rejected: not our topic"
    parts = topic[len(PREFIX):].split("/")
    if len(parts) != 2:
        return "rejected: not a reading topic"
    where, what = parts
    try:
        data = json.loads(payload)
    except ValueError:
        return "rejected: not JSON"
    if not isinstance(data, dict):
        return "rejected: not a JSON object"
    v = data.get("v")
    if isinstance(v, bool) or not isinstance(v, (int, float)):
        return "rejected: v is not a number"
    unit = data.get("unit")
    if unit == "F":
        v = (v - 32) * 5 / 9
        unit = "C"
    if unit not in ("C", "%"):
        return f"rejected: unknown unit {unit!r}"
    return {"where": where, "what": what, "v": round(v, 1), "unit": unit}

inbox = [
    ("c4t-lab/q8z2rw/greenhouse/bed1/temperature", b'{"v": 23.4, "unit": "C", "seq": 1}'),
    ("c4t-lab/q8z2rw/greenhouse/bed2/temperature", b'{"v": 72.5, "unit": "F", "seq": 9}'),
    ("c4t-lab/q8z2rw/greenhouse/bed1/humidity", b'{"v": "41", "unit": "%"}'),
    ("c4t-lab/q8z2rw/greenhouse/bed1/humidity", b'{"v": true, "unit": "%"}'),
    ("c4t-lab/q8z2rw/greenhouse/bed1/light", b'{"v": 300, "unit": "lux"}'),
    ("c4t-lab/q8z2rw/greenhouse/bed1/temperature", b"23.4"),
    ("c4t-lab/q8z2rw/greenhouse/bed1/temperature", b"hello"),
]
for topic, payload in inbox:
    print(parse_reading(topic, payload))
```

The string `"41"` is rejected on purpose. Quietly converting it would hide a bug in whichever station sent it.
:::

### Exercise 5: Find lost, repeated, and restarted messages

A dashboard logged these `seq` values from one station: `[1, 2, 3, 3, 5, 6, 6, 7, 10, 1, 2, 3]`. Write `audit(seqs)` that reports which numbers were lost, which arrived twice (QoS 1 at work), and when the station restarted its count.

```text
lost: [4, 8, 9]
duplicates: [3, 6]
restarts after seq: [10]
```

:::hint
Keep the last number you accepted. A jump from `last` to `s` loses `range(last + 1, s)`. A value you've already seen in this run is a duplicate. A `1` after a bigger number means the count started over, so reset what you remember.
:::

:::solution
```python run title="audit.py"
def audit(seqs):
    lost, dupes, restarts = [], [], []
    seen = set()
    last = 0
    for s in seqs:
        if s == 1 and last > 1:          # counting started again: a reboot
            restarts.append(last)
            seen, last = set(), 0
        if s in seen:
            dupes.append(s)
            continue
        lost.extend(range(last + 1, s))  # empty unless numbers were skipped
        seen.add(s)
        last = s
    return lost, dupes, restarts

lost, dupes, restarts = audit([1, 2, 3, 3, 5, 6, 6, 7, 10, 1, 2, 3])
print("lost:", lost)
print("duplicates:", dupes)
print("restarts after seq:", restarts)
```

The restart check matters more than it looks. Without it, the second `1, 2, 3` would be flagged as duplicates, and in Module 6 the same mistake, made in the other direction, lets an attacker replay old commands after a reboot.
:::

### Exercise 6: A chart dashboard that shows staleness

Here is a log of messages: bed1 reports every 5 seconds in Celsius, and bed2 reports in Fahrenheit until t = 40 s and then goes silent. At t = 75 s, print each bed's latest value in Celsius, its age, and whether it is stale (older than 15 s). Then chart both beds and shade the period where bed2 was stale.

```text
bed1: 25.0 C, 0 s old -> fresh
bed2: 22.8 C, 35 s old -> STALE
```

:::hint
Group readings per bed into lists of `(t, celsius)` pairs with `dict.setdefault`. The latest reading is the last pair. A bed becomes stale 15 s after its last message, so the shading runs from `last_t + 15` to now; `plt.axvspan` draws a shaded band.
:::

:::solution
```python run title="chart_dashboard.py" alt="Line chart of two greenhouse beds: bed1 rises steadily from 22 to 25 degrees Celsius over 75 seconds, bed2 stays near 22 degrees until 40 seconds and then stops, with an orange band from 55 to 75 seconds marking bed2 as stale" caption="bed2 stopped reporting at 40 s and turned stale at 55 s"
import json
import matplotlib.pyplot as plt

STALE_S = 15
NOW = 75
log = []
for t in range(0, 76, 5):
    log.append((t, "bed1/temperature", json.dumps({"v": 22 + t / 25, "unit": "C", "seq": t // 5 + 1})))
    if t <= 40:
        log.append((t, "bed2/temperature", json.dumps({"v": 71.0 + t / 20, "unit": "F", "seq": t // 5 + 1})))

series = {}
for t, topic, payload in log:
    data = json.loads(payload)
    v = data["v"] if data["unit"] == "C" else (data["v"] - 32) * 5 / 9
    where = topic.split("/")[0]
    series.setdefault(where, []).append((t, round(v, 1)))

for where, points in series.items():
    last_t, last_v = points[-1]
    age = NOW - last_t
    state = "STALE" if age > STALE_S else "fresh"
    print(f"{where}: {last_v} C, {age} s old -> {state}")
    times = [p[0] for p in points]
    values = [p[1] for p in points]
    plt.plot(times, values, marker="o", markersize=3, label=where)
    if age > STALE_S:
        plt.axvspan(last_t + STALE_S, NOW, color="#f0b44c", alpha=0.25, label=f"{where} stale")

plt.xlabel("seconds since start")
plt.ylabel("temperature (C)")
plt.title(f"Greenhouse at t = {NOW} s")
plt.legend()
```

Converting bed2 to Celsius before plotting is what makes the two lines comparable. Plotted raw, bed2 would sit near 72 and look like a heat wave.
:::

### Challenge: Build a broker that retains and keeps wills

Write a `MiniBroker` class that stores retained messages, sends them to new subscribers, keeps each client's last will, and publishes the will only when a client vanishes without a clean disconnect. Use any matcher from this lesson. Until your class exists, this test script stops with an error; once the class works, it must print the output below it:

```python
b = MiniBroker()
b.connect("station", will=("gh/status", "offline", True))
b.publish("gh/status", "online", retain=True)
b.connect("early")
b.subscribe("early", "gh/#")
b.publish("gh/bed1/temperature", "23.4")
b.connect("spare", will=("gh/spare/status", "offline", True))
b.disconnect("spare", clean=True)             # polite goodbye: no will
b.disconnect("station", clean=False)          # power cut: will is sent
b.connect("late")
b.subscribe("late", "gh/#")
```

```text
early
   gh/status = online (retained)
   gh/bed1/temperature = 23.4
   gh/status = offline
late
   gh/status = offline (retained)
```

:::video Ct5s4gXefn4
What to watch for: the broker keeps only one retained message per topic, a newer one replaces it, and an empty retained payload deletes it. Your `publish()` needs all three behaviors.
:::

:::hint
Four dictionaries or lists cover the state: subscriptions as `(client, filter)` pairs, `retained` as topic to payload, `wills` as client to `(topic, payload, retain)`, and an inbox per client. On `subscribe`, loop over `retained` and deliver matches. On an unclean `disconnect`, call your own `publish` with the will.
:::

:::solution
```python run title="mini_broker.py"
def matches(pattern, topic):
    p, t = pattern.split("/"), topic.split("/")
    for i in range(len(p)):
        if p[i] == "#":
            return True
        if i >= len(t) or (p[i] != "+" and p[i] != t[i]):
            return False
    return len(p) == len(t)

class MiniBroker:
    def __init__(self):
        self.subs = []       # (client, filter) pairs
        self.retained = {}   # topic -> payload
        self.wills = {}      # client -> (topic, payload, retain)
        self.inbox = {}      # client -> list of delivered messages

    def connect(self, client, will=None):
        self.inbox.setdefault(client, [])
        if will:
            self.wills[client] = will

    def subscribe(self, client, pattern):
        self.subs.append((client, pattern))
        for topic, payload in self.retained.items():
            if matches(pattern, topic):
                self.inbox[client].append(f"{topic} = {payload} (retained)")

    def publish(self, topic, payload, retain=False):
        if retain:
            if payload == "":
                self.retained.pop(topic, None)   # empty payload clears it
            else:
                self.retained[topic] = payload
        for client, pattern in self.subs:
            if matches(pattern, topic):
                self.inbox[client].append(f"{topic} = {payload}")

    def disconnect(self, client, clean=True):
        will = self.wills.pop(client, None)
        self.subs = [(c, p) for c, p in self.subs if c != client]
        if will and not clean:
            self.publish(*will)

b = MiniBroker()
b.connect("station", will=("gh/status", "offline", True))
b.publish("gh/status", "online", retain=True)
b.connect("early")
b.subscribe("early", "gh/#")
b.publish("gh/bed1/temperature", "23.4")
b.connect("spare", will=("gh/spare/status", "offline", True))
b.disconnect("spare", clean=True)             # polite goodbye: no will
b.disconnect("station", clean=False)          # power cut: will is sent
b.connect("late")
b.subscribe("late", "gh/#")
for name in ["early", "late"]:
    print(name)
    for line in b.inbox[name]:
        print("  ", line)
```

`late` never saw `23.4`: it wasn't retained, so it vanished the moment it was delivered. It did see `offline`, because the will was published with retain on and replaced `online`. `wills.pop` on a clean disconnect is what keeps `spare`'s will from firing.
:::
