Three Pico W boards publish to a topic called `temp`. The dashboard receives `21.5`, then `70.2`, then `22`. Is one greenhouse bed at 70 degrees and about to cook the tomatoes, or is one board reporting Fahrenheit? Which bed is the 22? Every number is correct and the dashboard still can't use any of them.

**MQTT**, the messaging protocol most IoT devices speak, can carry these readings to any number of screens. Naming them so the screens can make sense of them is still your job.

## Why devices talk through a broker

The obvious design has the dashboard ask each device for its reading. It breaks fast: the dashboard needs every device's address, home routers block incoming connections, and a board asleep to save battery can't answer.

MQTT turns this around. Every device opens **one outgoing connection** to a server called a **broker**. A device **publishes** a message to a **topic** (a name like `greenhouse/bed1/temperature`). Any client that has **subscribed** to that topic gets a copy from the broker. The publisher doesn't know who is listening, and the subscribers don't know who published. Either side can come and go.

```mermaid caption="One publish, two deliveries: the broker copies each message to every matching subscriber"
sequenceDiagram
    participant S as Pico W station-01
    participant B as Broker
    participant D as Dashboard
    participant L as Logger
    D->>B: SUBSCRIBE greenhouse, every topic below it
    L->>B: SUBSCRIBE every bed's temperature only
    S->>B: PUBLISH bed1/temperature = 23.4 C
    B->>D: bed1/temperature = 23.4 C
    B->>L: bed1/temperature = 23.4 C
    S->>B: PUBLISH bed1/humidity = 41 %
    B->>D: bed1/humidity = 41 %
```

Notice the logger never received the humidity message. It only asked for temperatures, and the broker filters for it.

Popular brokers include **Mosquitto** (open source; it runs happily on a Raspberry Pi), **HiveMQ**, and **EMQX**. For learning, there are free public brokers at `broker.hivemq.com` and `test.mosquitto.org`, both on port 1883, and the Pico W in Wokwi can reach either one.

## Topics are addresses you design

A topic is a UTF-8 string split into **levels** by `/`. Topics don't need to be created first: the first publish to a name brings it into existence. That convenience is also the trap, because a typo silently creates a new topic nobody listens to.

Build topics from general to specific, the way a postal address goes country, city, street:

```text
c4t-lab/a7f3c9/greenhouse/bed1/temperature
│       │      │          │    └─ what was measured
│       │      │          └────── where
│       │      └───────────────── which site
│       └──────────────────────── your private random code
└──────────────────────────────── the course's shared prefix
```

| Ambiguous topic | Better topic | Why |
| --- | --- | --- |
| `temp` | `c4t-lab/a7f3c9/greenhouse/bed1/temperature` | Says where, and leaves room for bed2 |
| `greenhouse/temp_F` | `.../bed1/temperature` with `"unit": "F"` in the payload | Units belong with the value, not in the name |
| `/greenhouse/bed1` | `greenhouse/bed1/...` | A leading `/` creates an empty first level |
| `Greenhouse/Bed 1/Temp` | `greenhouse/bed1/temperature` | Topics are case-sensitive; spaces invite typos |
| `.../bed1/2026-11-16T10:02` | `.../bed1/temperature` | Never put changing values in a topic; it makes a new topic every time |

The random code (`a7f3c9` here) matters on a public broker. Everyone in the world shares the same topic space, so a plain `greenhouse/bed1/temperature` collides with strangers who picked the same name. Make your own code by mashing six random letters and digits, and don't use your name or school.

## Wildcards: subscribe to many topics at once

Subscribers can use two wildcards in a **topic filter**:

-   `+` matches exactly one level. `c4t-lab/a7f3c9/greenhouse/+/temperature` gets the temperature of every bed.
-   `#` matches any number of levels, including zero, and must be the last character. `c4t-lab/a7f3c9/greenhouse/#` gets everything at the site.

Publishers can't use wildcards; a message always goes to one exact topic. Here is a short matcher that follows the same rules. Step through it and watch how it compares one level at a time and gives up at the first mismatch:

:::trace Compare a filter and a topic level by level
```python
def matches(pattern, topic):
    p = pattern.split("/")
    t = topic.split("/")
    for i in range(len(p)):
        if p[i] == "#":
            return True
        if i >= len(t):
            return False
        if p[i] != "+" and p[i] != t[i]:
            return False
    return len(p) == len(t)

print(matches("lab/+/temp", "lab/bed1/temp"))
print(matches("lab/+/temp", "lab/bed1/soil/temp"))
print(matches("lab/#", "lab/bed1/soil/temp"))
```
:::

The second call fails at the very end: every level it checked matched, but the topic has four levels and the filter only three. One `+` never swallows two levels.

## Payloads: say what the number means

The broker treats a payload as raw bytes and never looks inside. That freedom means you decide the format, and JSON is the usual choice because every language can read it. A good reading carries its value, its unit, which device sent it, and a sequence number that goes up by one each time:

```python run title="payload.py"
import json

reading = {"v": 23.4, "unit": "C", "dev": "station-01", "seq": 118}
payload = json.dumps(reading)
print("topic:  ", "c4t-lab/a7f3c9/greenhouse/bed1/temperature")
print("payload:", payload)
print("size:   ", len(payload.encode()), "bytes")

# What a subscriber does with it
data = json.loads(payload)
celsius = data["v"] if data["unit"] == "C" else (data["v"] - 32) * 5 / 9
print(f"{data['dev']} says bed1 is {celsius:.1f} C (message #{data['seq']})")
```

Sixty-odd bytes is tiny, even for a Pico. The `seq` field pays off later: if the dashboard sees 118 and then 120, it knows 119 went missing.

## QoS: how hard the network tries

Wi-Fi drops packets. MQTT lets each message choose a **Quality of Service** level:

| QoS | Promise | How | Good for |
| --- | --- | --- | --- |
| 0 | At most once | Send and forget | Readings that repeat every few seconds anyway |
| 1 | At least once | Resend until the receiver answers PUBACK | Status changes, alarms, commands; duplicates are possible |
| 2 | Exactly once | A four-packet handshake (PUBLISH, PUBREC, PUBREL, PUBCOMP) | Rare; when a duplicate would cause harm and the extra traffic is fine |

QoS 1 duplicates sound strange until you see why: if the message arrives but the PUBACK is lost on the way back, the sender can't tell the difference and sends again. This simulation pushes 20 messages over a link that loses a quarter of all packets:

```python run title="qos_sim.py"
import random

random.seed(2)
LOSS = 0.25   # chance any single packet vanishes on a flaky link

def qos0(n):
    received = []
    for seq in range(1, n + 1):
        if random.random() > LOSS:          # PUBLISH made it
            received.append(seq)
    return received

def qos1(n):
    received = []
    for seq in range(1, n + 1):
        while True:
            if random.random() > LOSS:      # PUBLISH made it
                received.append(seq)
                if random.random() > LOSS:  # PUBACK made it back
                    break
            # no PUBACK seen: the sender sends the same message again

    return received

for name, run in [("QoS 0", qos0), ("QoS 1", qos1)]:
    got = run(20)
    missing = sorted(set(range(1, 21)) - set(got))
    dupes = len(got) - len(set(got))
    print(f"{name}: {len(got)} deliveries, missing {missing}, duplicates {dupes}")
```

QoS 0 lost three readings and nobody noticed. QoS 1 lost none, but three arrived twice, so a subscriber that counts events should use `seq` to ignore repeats.

Two details trip people up. A subscriber gets the lower of the publisher's and its own QoS, so a QoS 1 publish to a QoS 0 subscription arrives as QoS 0. And `umqtt.simple`, the library you'll use on the Pico, supports only QoS 0 and 1.

What to watch for: the packet exchange for each level, and the point about QoS being agreed separately between publisher and broker and between broker and subscriber.
:::

## Retained messages and the last will

Open a dashboard at 10:02 and it shows nothing until the next reading arrives. Worse, it can't tell a quiet station from a dead one. Two MQTT features fix this.

A **retained message** is one the broker keeps. It stores the last retained message on each topic and hands it to every new subscriber immediately. Retain things that describe *current state*, like `online`, or `fan: on`. To erase a retained message, publish an empty payload to the same topic with the retain flag set.

A **last will** is a message a client gives the broker when it connects: "if I vanish without saying goodbye, publish this for me." The broker sends it if the connection dies, or if it hears nothing from the client for one and a half times the **keepalive** interval the client chose. A polite disconnect cancels it.

```mermaid caption="Retained status plus a last will: a dashboard that opens late still learns the station died"
sequenceDiagram
    participant S as Station
    participant B as Broker
    participant D as Dashboard
    S->>B: CONNECT, will = offline (retained)
    S->>B: PUBLISH status = online (retained)
    Note over S: Power cut, no goodbye
    B->>B: Silence for 1.5 x keepalive
    B->>B: Publish the will, status = offline
    D->>B: SUBSCRIBE status (ten minutes later)
    B->>D: offline (the retained copy)
```

## Public brokers are postcards

On `broker.hivemq.com` or `test.mosquitto.org` there are no passwords. Anyone can subscribe to `#` and read every message from every user, and anyone can publish to your topics. HiveMQ says its public broker "is not intended for private or production data", and the Mosquitto test server asks: "Please don't publish anything sensitive, anybody could be listening." Wokwi's public Wi-Fi gateway adds a third reader, since Wokwi monitors that traffic for abuse.

So the rules for this course are simple. Use your random code, never your name. Publish sensor numbers, never personal details, locations, or passwords. Never let a public-broker topic switch on anything real. Module 6 deals with the fact that strangers can publish to your topics; for a real project you'd run your own broker, such as Mosquitto on a Raspberry Pi, with accounts and access rules.

:::warning
**Four bugs that make messages "disappear."**

-   **Case and spelling.** The station publishes to `.../greenhouse/...` and the dashboard subscribes to `.../Greenhouse/#`. No error appears anywhere; the subscriber just hears nothing. Copy topic strings, don't retype them.
-   **A leading slash.** `/c4t-lab/...` and `c4t-lab/...` are different topics.
-   **`#` in the middle.** `c4t-lab/#/temperature` is not a valid filter; `#` must be last. Use `+` for a single level.
-   **Two clients with one client ID.** A broker allows one connection per client ID, so when a second one connects, the first is kicked off. If both reconnect automatically they take turns kicking each other off forever. Give every board and every browser tab its own ID.
:::

:::quiz
Q: The dashboard subscribes to `c4t-lab/a7f3c9/greenhouse/+/temperature`. Which message does it receive?
- [x] `c4t-lab/a7f3c9/greenhouse/bed2/temperature`
  `+` matches the single level `bed2`, and every other level matches exactly.
- [ ] `c4t-lab/a7f3c9/greenhouse/bed2/soil/temperature`
  There are two levels (`bed2/soil`) where the filter has one `+`. A `+` never spans levels.
- [ ] `c4t-lab/a7f3c9/greenhouse/temperature`
  This topic has one level fewer than the filter, so the `+` has nothing to match.

Q: A soil sensor sends a reading every 10 seconds, and a missed one doesn't matter. A "frost alarm" message goes out once when the temperature drops below 2 °C. Which QoS levels fit?
- [ ] QoS 2 for both, to be safe
  QoS 2 costs four packets per message. A reading that is replaced in 10 seconds doesn't need that.
- [x] QoS 0 for readings, QoS 1 for the alarm
  A lost reading is replaced soon, but a lost alarm is never repeated. QoS 1 might deliver it twice, which is harmless for an alarm.
- [ ] QoS 1 for readings, QoS 0 for the alarm
  This is backwards: the one-off message is the one that must not be lost.

Q: Your station sets a last will of `offline` with retain on, publishes a retained `online`, then you press Stop in Wokwi. A dashboard connects five minutes later. What does it see on the status topic?
- [ ] Nothing, because the station is no longer connected
  The broker, not the station, delivers retained messages, so the station doesn't need to be there.
- [ ] `online`, because that was the last thing the station published
  The station did publish `online`, but the broker then published the will, which replaced it.
- [x] `offline`, delivered straight away as a retained message
  The connection died without a goodbye, so the broker published the will. It was retained, so new subscribers get it right away.

Q: Which topic is safest to use on `broker.hivemq.com`?
- [ ] `riverside-high/room-12/maya/temperature`
  It names a school, a room, and a person, and anyone subscribed to `#` sees it.
- [x] `c4t-lab/q8z2rw/greenhouse/bed1/temperature`
  The random code avoids collisions and says nothing about who you are.
- [ ] `temperature`
  It reveals nothing, but every stranger using the same name will mix their readings with yours.
:::

:::takeaways
- A broker sits in the middle: devices publish to topics, and the broker copies each message to every subscriber whose filter matches.
- Design topics from general to specific, keep them lowercase with no leading slash, and put units, device ID, and a sequence number in the payload.
- `+` matches one level; `#` matches everything below and must come last.
- QoS 0 may lose messages, QoS 1 may duplicate them, QoS 2 does neither at a higher cost.
- Retain current state, and set a retained last will so silence turns into a clear `offline`.
- Public brokers are readable and writable by everyone: random codes, no personal data, nothing that controls real hardware.
:::
