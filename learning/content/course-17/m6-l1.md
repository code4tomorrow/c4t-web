Your greenhouse station is about to get a fan it can switch on when the air gets hot. The obvious design: the station subscribes to `c4t-lab/a7f3c9/greenhouse/bed1/fan/set`, and when a message saying `on` arrives, it turns the fan on.

Here is what a stranger subscribed to `#` on the public broker sees a few minutes after you test it:

```text
c4t-lab/a7f3c9/greenhouse/bed1/temperature   {"v": 31.2, "unit": "C", "dev": "station-01", "seq": 88}
c4t-lab/a7f3c9/greenhouse/bed1/fan/set       on
c4t-lab/a7f3c9/greenhouse/bed1/fan/set       off
```

They don't need to guess anything. They can publish `on` at 3 a.m., or every half second, and your station obeys. A random code in the topic stops accidental collisions, but it isn't a secret, because every message carries it in plain view.

## Identity, authentication, authorization

These three words sound alike and answer different questions.

| Question | Name | Greenhouse example |
| --- | --- | --- |
| Who do you **say** you are? | Identity | Client ID `station-01`, or the board's `machine.unique_id()` |
| Can you **prove** it? | Authentication | A password, a secret key, or a certificate's private key |
| What are you **allowed** to do? | Authorization | `station-01` may publish readings; only the controller may publish to `fan/set` |

An identity on its own is just a claim. Anyone can connect with the client ID `station-01`, and a chip's unique ID is printed in plain sight by the first line of code that reads it. Authentication needs something only the real device knows.

A private broker, such as Mosquitto on a Raspberry Pi, can do the first two jobs itself: each device logs in with a username and password, and an access control list (ACL) says which topics each username can read or write. A Mosquitto ACL file looks like this:

```text
# /etc/mosquitto/acl: rules apply to the username above them
user station-01
topic write greenhouse/bed1/temperature
topic write greenhouse/bed1/humidity
topic write greenhouse/devices/station-01/status
topic read greenhouse/bed1/fan/set

user controller
topic write greenhouse/bed1/fan/set
topic read greenhouse/#
```

With `allow_anonymous false` and a password file in its configuration, that broker simply refuses a stranger's publish to `fan/set`. The public brokers you're using can't do any of this, which is why this module also protects each message on its own.

## TLS in plain words

A username and password sent over a plain MQTT connection (port 1883) travel as readable text. Everyone on the path can read them: the Wi-Fi network, the internet provider, and in this course Wokwi's public gateway too.

**TLS** (the same technology as the padlock in your browser) wraps the connection in three protections:

1.  **Encryption.** An eavesdropper sees scrambled bytes instead of your password and readings.
2.  **Server authentication.** The broker shows a certificate signed by an authority your device already trusts. A fake broker can't produce one for your broker's name, so the device knows it reached the real thing.
3.  **Integrity.** Change a single byte in transit and the receiver notices and drops the connection.

MQTT over TLS normally uses port **8883**, and MQTT over secure WebSockets (what your dashboard uses) port 8884 on HiveMQ's broker. On a real Pico W with a private broker, the connection looks something like this:

```python title="TLS connection (real Pico W, private broker)"
import ssl
import ntptime
from umqtt.simple import MQTTClient

ntptime.settime()                       # certificates have dates, so the clock must be right
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
ctx.verify_mode = ssl.CERT_REQUIRED     # refuse a server that can't prove who it is
ctx.load_verify_locations(cafile="broker_ca.pem")
client = MQTTClient("station-01", "mqtt.example.org", port=8883, ssl=ctx,
                    user="station-01", password=DEVICE_PASSWORD)
client.connect()
```

The two comments carry the lessons. MicroPython's documentation warns that `CERT_REQUIRED` needs the device's date and time set properly. And with `CERT_NONE`, the connection is encrypted but the Pico never checks the certificate, so it would happily send its password to an impostor.

Notice what TLS does **not** do. It protects the pipe between one client and the broker. On a public broker, a stranger opens their own perfectly valid TLS connection and publishes to your topic. TLS can't tell you whether a message came from someone you trust; only a key you share with your controller can.

## Why a plain hash isn't a signature

A hash function like SHA-256 turns any message into a 64-character fingerprint, and changing one character changes the whole fingerprint. That makes it tempting to send a command along with its hash. Try it:

```python run title="hash_is_not_enough.py"
import hashlib

def fingerprint(text):
    return hashlib.sha256(text.encode()).hexdigest()

# The controller sends a command and its SHA-256 fingerprint
sent = "station-01|fan_on|7"
print("sent:   ", sent, fingerprint(sent)[:16], "...")

# An attacker changes the command and simply computes a new fingerprint
forged = "station-01|heater_on|8"
forged_tag = fingerprint(forged)
print("forged: ", forged, forged_tag[:16], "...")

# The device checks the fingerprint the only way it can
print("device accepts the forgery:", fingerprint(forged) == forged_tag)
```

A hash catches *accidents*, like a corrupted byte. It does nothing against an attacker, because the attacker can run SHA-256 too.

## HMAC: a tag only key holders can make

The fix is to mix a **secret key** into the hash. **HMAC** (hash-based message authentication code) does that in a careful, standard way: `HMAC-SHA256(key, message)` gives a 32-byte **tag**. Anyone can see the message and the tag, but making a valid tag for a new message requires the key. The controller and the station share the key; nobody else has it.

To verify, the station recomputes the tag from the message it received and its own copy of the key, then compares.

```python run title="hmac_sign_verify.py"
import hashlib
import hmac

KEY = b"5b1e0f7c2a9d4e8b6f3a1c0d9e8f7a6b5c4d3e2f1a0b9c8d7e6f5a4b3c2d1e0f"  # demo only

def sign(text):
    return hmac.new(KEY, text.encode(), hashlib.sha256).hexdigest()

def verify(text, tag):
    return hmac.compare_digest(sign(text), tag)

message = "station-01|fan_on|7"
tag = sign(message)
print("tag:", tag)
print("genuine message:       ", verify(message, tag))
print("one field changed:     ", verify("station-01|fan_on|8", tag))

# An attacker without KEY can only guess at a key
guess = hmac.new(b"password123", b"station-01|heater_on|8", hashlib.sha256).hexdigest()
print("attacker's best guess: ", verify("station-01|heater_on|8", guess))
```

Three details in that code matter:

-   **What gets signed** is a string built from the fields in a fixed order, joined with `|`. Signing JSON text is fragile: JSON with different spacing or key order means the same thing but produces a different tag, and MicroPython dictionaries don't even keep keys in order. Both sides build the same string from the same fields.
-   **Every field the device acts on is signed**, including the device name. Leave a field out of the signed string and an attacker can change it freely.
-   **`hmac.compare_digest`** takes the same time whether the first character differs or the last. A normal `==` stops at the first mismatch, and with enough attempts an attacker can time those tiny differences to discover a valid tag one character at a time.

:::video wlSG3pEiQdc
What to watch for: why scrambling a message doesn't stop someone from changing it, and how HMAC folds the key in twice (an inner and an outer hash). You'll write that two-step structure yourself in the next lesson, because the Pico has `hashlib` but no `hmac` module.
:::

## Replay attacks: a valid message, used twice

HMAC proves a message came from a key holder. It says nothing about **when**. An attacker who records your genuine, correctly signed `fan_on` can publish an exact copy of it tonight, tomorrow, or a thousand times, and every copy passes the signature check.

```mermaid caption="A replay attack needs no key: the attacker resends a message you signed yourself"
sequenceDiagram
    participant C as Your controller
    participant B as Public broker
    participant S as Station
    participant A as Attacker
    A->>B: SUBSCRIBE #
    C->>B: fan_on, signed
    B->>S: fan_on, signed (fan starts)
    B->>A: fan_on, signed (recorded)
    Note over A: Hours later
    A->>B: the same bytes again
    B->>S: fan_on, signed (fan starts again)
```

The defense is to sign something that makes each message usable only once:

-   **A counter.** Each command carries a number one higher than the last. The station remembers the highest number it accepted and rejects anything not above it. No clock needed, but the station must remember the number even after it reboots.
-   **A timestamp window.** Each command carries the time it was made, and the station rejects anything older than, say, 30 seconds. This needs the two clocks to agree, which is harder than it sounds: a Wokwi simulation can run slower than real time, so the board's clock drifts.
-   **A nonce** ("number used once"). Each command carries a random value, and the station remembers the values it has seen. Pair it with a timestamp so the station only has to remember nonces from inside the window.

Here is a timestamp plus a nonce, tested against four attacks:

```python run title="replay_guard.py"
import hashlib
import hmac

KEY = b"5b1e0f7c2a9d4e8b6f3a1c0d9e8f7a6b5c4d3e2f1a0b9c8d7e6f5a4b3c2d1e0f"
WINDOW_S = 30

def sign(dev, cmd, ts, nonce):
    text = f"{dev}|{cmd}|{ts}|{nonce}"
    return hmac.new(KEY, text.encode(), hashlib.sha256).hexdigest()

class Fan:
    def __init__(self, name):
        self.name = name
        self.used = {}                     # nonce -> ts

    def handle(self, msg, now):
        # forget nonces older than the window; the time check covers those
        self.used = {n: ts for n, ts in self.used.items() if now - ts <= WINDOW_S}
        expected = sign(msg["dev"], msg["cmd"], msg["ts"], msg["nonce"])
        if not hmac.compare_digest(expected, msg["sig"]):
            return "rejected: bad signature"
        if msg["dev"] != self.name:
            return "rejected: meant for another device"
        if abs(now - msg["ts"]) > WINDOW_S:
            return "rejected: too old, or from the future"
        if msg["nonce"] in self.used:
            return "rejected: nonce already used"
        self.used[msg["nonce"]] = msg["ts"]
        return "ACCEPTED " + msg["cmd"]

t = 1_763_290_000                          # the controller's clock, in seconds
cmd = {"dev": "station-01", "cmd": "fan_on", "ts": t, "nonce": "9f2c71aa"}
cmd["sig"] = sign(cmd["dev"], cmd["cmd"], cmd["ts"], cmd["nonce"])

fan = Fan("station-01")
print("t+2    genuine:          ", fan.handle(cmd, now=t + 2))
print("t+5    replayed:         ", fan.handle(cmd, now=t + 5))
print("t+600  replayed later:   ", fan.handle(cmd, now=t + 600))
print("t+600  ts edited to now: ", fan.handle(dict(cmd, ts=t + 600), now=t + 600))
print("t+3    sent to station-02:", Fan("station-02").handle(cmd, now=t + 3))
```

Read the results as a list of attacks that failed. A quick replay hits the nonce check. A late replay hits the time window. Editing `ts` to look fresh breaks the signature, because `ts` is part of the signed string. And a command signed for `station-01` doesn't work on `station-02`, even though both happen to share this demo key.

:::warning
**Signed, but still unsafe.** Four mistakes show up again and again in student projects:

-   **Acting before checking.** `led.on()` placed above the signature check runs for every message. Verify first, act second.
-   **Signing part of the message.** If the tag covers `fan_on|7` but the device also reads a `duration` field, an attacker can change the duration to 10 hours without breaking the tag.
-   **Comparing tags with `==`.** Use `hmac.compare_digest` in Python, or the loop you'll write for MicroPython.
-   **Putting the key where it travels.** A key printed to the console, published in an error message, or pasted into a public Wokwi project is no longer a secret. Module 7 is about where keys should live.
:::

:::quiz
Q: Your station checks that the client ID in a command's payload is `controller` before acting. What does this stop?
- [ ] Anyone who doesn't have the key
  There is no key involved: the client ID is a claim, and anyone can type `controller`.
- [x] Almost nothing; it is identity without authentication
  Identity says who someone claims to be. Without a secret to prove it, any stranger can make the same claim.
- [ ] Replay attacks
  A replayed message carries the same client ID as the original, so this check passes it straight through.

Q: The broker connection uses TLS with certificate checking on. Which attack is still possible on a public broker?
- [ ] Reading your messages as they cross the school Wi-Fi
  That is exactly what TLS encryption prevents.
- [ ] A fake broker pretending to be `broker.hivemq.com`
  Certificate checking stops impostor brokers, as long as `verify_mode` is `CERT_REQUIRED`.
- [x] A stranger connecting with their own TLS connection and publishing `on` to your fan topic
  TLS protects each client's pipe to the broker, not who is allowed to publish. That needs broker ACLs or signed messages.

Q: A command's tag is `HMAC(key, "fan_on")`, and the payload is `{"cmd": "fan_on", "minutes": 5, "sig": ...}`. What can an attacker who records it do?
- [ ] Nothing, because the message is signed
  The tag only covers the text `fan_on`, so everything else in the payload is unprotected.
- [x] Replay it, or change `minutes` to 600, and the tag still verifies
  The tag doesn't cover `minutes`, and nothing in it makes the message one-use. Sign every field the device uses, plus a counter or a timestamp and nonce.
- [ ] Work out the key from the tag
  HMAC-SHA256 is designed so that seeing tags, even many of them, doesn't reveal the key.

Q: A Wokwi station uses a 30-second timestamp window. After an hour of simulation, every genuine command is rejected as too old. What is the most likely cause?
- [ ] The key changed
  A wrong key would give "bad signature", not "too old".
- [x] The simulated clock drifted behind real time because the simulation ran slower than full speed
  The station's clock and the controller's clock disagree by more than the window. A counter avoids depending on clocks at all.
- [ ] The nonce cache is full
  The cache only rejects repeated nonces, and each genuine command has a new one.
:::

:::takeaways
- Topic names are public. Anyone on a public broker can read them and publish to them.
- Identity is a claim, authentication is proof, authorization is a list of what each proven identity may do.
- TLS gives encryption, a verified broker, and tamper detection on the connection; it needs certificate checking on and a correct clock, and it doesn't decide who may publish.
- HMAC-SHA256 with a shared key gives a tag only key holders can create. Sign a fixed-order string of every field the device acts on, and compare with `compare_digest`.
- A valid signature can be replayed. Add a counter, or a timestamp plus a nonce, inside the signed string.
:::
