:::objectives
- Replace matched `wait` timers with `broadcast` so several sprites start at exactly the right moment.
- Choose between `broadcast` and `broadcast and wait`.
- Make variables for all sprites or for one sprite, and reset them at the start.
- Write conditions with comparisons, `and`, `or`, and `not`, and use `wait until` and `repeat until`.
- Track what mode a game is in with a state variable.
:::

Here's a race start that seems to work. The referee counts down, and the runner waits the same amount of time before taking off:

```scratch
when green flag clicked
say [Ready...] for (1) seconds
say [Set...] for (1) seconds
say [GO!] for (1) seconds

when green flag clicked
wait (2) seconds
glide (2) secs to x: (200) y: (0)
```

The first script is the referee; the second belongs to the runner. Now make "Ready..." last 2 seconds for drama. The runner leaves on "Set...", because its `wait (2)` has no idea the referee changed. Add four more runners and you have five separate timers to keep in sync by hand. Scripts timed this way break the moment anything about the timing changes.

## Broadcasts: one sender, many listeners

The fix is to have the referee *tell* everyone when to go. `broadcast` sends a message; every script that starts with `when I receive` for that message begins at once, in every sprite and on the Stage.

```scratch
when green flag clicked
say [Ready...] for (2) seconds
say [Set...] for (1) seconds
broadcast (go v)
say [GO!] for (1) seconds

when I receive [go v]
glide (2) secs to x: (200) y: (0)
```

Now the runners don't keep time at all. Change the countdown however you like and they still leave on "GO!".

```mermaid caption="One broadcast reaches every listener at the same moment"
sequenceDiagram
    participant Ref as Referee
    participant R1 as Runner 1
    participant R2 as Runner 2
    participant St as Stage
    Ref->>Ref: say Ready, say Set
    Ref->>R1: go
    Ref->>R2: go
    Ref->>St: go
    Note over R1,St: all three scripts start in the same frame
    Ref->>Ref: say GO! (doesn't wait for them)
```

Three rules cover almost everything about broadcasts:

1.  Every matching `when I receive` script starts, however many there are.
2.  The sender keeps going right away. The blocks after `broadcast` don't wait for anyone.
3.  If nobody is listening, nothing happens and there's no error message. A broadcast to an empty room is silent.

## `broadcast and wait`: when order matters

Sometimes the sender needs to wait. Say a title card should explain the controls *before* the game starts. With `broadcast and wait`, the sender pauses until every script that received the message has finished:

```scratch
when green flag clicked
broadcast (show instructions v) and wait
broadcast (start game v)

when I receive [show instructions v]
show
say [Mash A or L to run. Don't jump the gun!] for (3) seconds
hide
```

The first script is on the Stage; the second belongs to an Instructions sprite. The Stage waits the full three seconds, then sends `start game`. If you make the instructions longer later, the game still starts at the right time.

```mermaid caption="broadcast and wait holds the sender until every receiver is done"
sequenceDiagram
    participant St as Stage
    participant In as Instructions
    participant Pl as Player
    St->>In: show instructions (and wait)
    activate In
    In-->>In: show, say for 3 seconds, hide
    In-->>St: done
    deactivate In
    St->>Pl: start game
```

:::warning
**A `broadcast and wait` that never returns.** If any receiving script contains a `forever` loop, it never finishes, so the sender waits forever and the game freezes before it starts. Use `broadcast and wait` only for messages whose receivers end on their own.
:::

## Variables: the game's memory

A **variable** is a named box that holds one value, like a score, a number of lives, or a word. Click **Make a Variable** in the Variables category, type a name, and choose:

-   **For all sprites**: one shared box that every sprite and the Stage can read and change. Use it for things the whole game cares about, like `score`.
-   **For this sprite only**: each sprite gets its own private box. Use it for things like each enemy's `health`. Other sprites can only *read* it, using the `of` block in Sensing.

Variables made on the Stage are always for all sprites.

```scratch
when green flag clicked
set [score v] to (0)

when this sprite clicked
change [score v] by (1)
```

`set` replaces the value; `change` adds to it (use a negative number to subtract). Tick the checkbox beside a variable to show its **monitor** on the stage. Right-click the monitor to switch between a normal readout, a large readout, and a slider.

Two facts trip people up. First, a variable keeps its value after you press the stop sign, and even after you save and reopen the project, so every game needs a `set` at the start. Second, a variable can hold words as well as numbers: `set [state v] to [playing]` is perfectly fine, and it's the basis of game states below.

:::

## Conditions, and loops that wait for them

A **condition** is a pointy block that's either true or false. The green Operators blocks build them:

| Block | True when… |
| --- | --- |
| `<(score) > (9)>` | score is more than 9 |
| `<(lives) = (0)>` | lives is exactly 0 |
| `<<(score) > (9)> and <(lives) > (0)>>` | both are true |
| `<<key (a v) pressed?> or <key (l v) pressed?>>` | at least one is true |
| `<not <(state) = [playing]>>` | state is anything except playing |

Text comparisons ignore capital letters in Scratch, so `<[Playing] = [playing]>` is true.

Conditions go in `if` blocks, which run their inside once if the condition is true, and in two loops that *wait* for a condition. `wait until` pauses a script until something becomes true. `repeat until` repeats its inside until something becomes true:

```scratch
when I receive [start game v]
wait until <(score) > (9)>
broadcast (you win v)

when I receive [start game v]
repeat until <(lives) < (1)>
next costume
wait (0.2) seconds
end
broadcast (game over v)
```

Both loops check their condition again every frame, about 30 times a second. Neither needs a `forever` around it, and that's a good thing, as you'll see in the next warning.

:::warning
**A broadcast inside `forever` restarts its receiver every frame.** When a message arrives for a script that's already running, Scratch restarts that script from the top. So this never works:

```scratch
when green flag clicked
forever
if <(score) > (9)> then
broadcast (level up v)
end
end

when I receive [level up v]
say [Level up!] for (2) seconds
change [level v] by (1)
```

Once the score passes 9, `level up` is sent 30 times a second. The receiver keeps restarting its 2-second `say`, so the bubble never goes away and `level` never changes. Send the message once instead: replace the `forever` and `if` with `wait until <(score) > (9)>`, then `broadcast (level up v)`.
:::

## Game states: what mode is the game in?

Most games have modes: a title screen, a countdown, play, pause, game over. The same key might do different things in each, or nothing at all. Keep the current mode in a variable called `state`, and change it at each turning point:

```mermaid caption="A typical game's states, and what moves it between them"
stateDiagram-v2
    [*] --> Title
    Title --> Countdown: space pressed
    Countdown --> Playing: GO
    Playing --> Paused: P pressed
    Paused --> Playing: P pressed
    Playing --> GameOver: lives reach 0
    GameOver --> Title: green flag
```

Then every input checks the state before acting:

```scratch
when [space v] key pressed
if <(state) = [playing]> then
change y by (40)
end
```

In the title screen, pressing space does nothing here, because the state isn't `playing` yet. Broadcasts and states work as a pair: a broadcast says "something just happened," and the state variable remembers "this is the mode we're in now."

:::warning
**The score starts at 14.** If the green flag script doesn't `set [score v] to (0)`, the score carries over from the last game. The same goes for `lives`, `state`, and every other variable. Reset them all in one place, usually a green flag script on the Stage.
:::

:::quiz
Q: The referee runs `broadcast (go v)` and then `say [sent]`. The runner runs `when I receive [go v]`, `wait (1) seconds`, `say [got it]`. Which bubble appears first?
- [x] "sent"
  `broadcast` doesn't wait, so the referee says "sent" right away while the runner is still waiting its 1 second.
- [ ] "got it"
  The runner has to wait 1 second first, and the referee isn't held up by the broadcast.
- [ ] Both at the same moment
  They'd only be close if the runner had no wait.

Q: Same scripts, but the referee uses `broadcast (go v) and wait`. Now what?
- [ ] "sent" still comes first
  `broadcast and wait` holds the referee until the runner's script ends.
- [x] "got it" first, then "sent"
  The referee waits for the runner's whole script, including the 1-second wait and the `say`, before moving on.
- [ ] Nothing appears, because the referee freezes
  It would only freeze if the runner's script never ended.

Q: Once the score passes 9, a "Level up!" bubble appears and never goes away, and `level` stays at 1. What's the likely cause?
- [ ] The `level` variable is for this sprite only
  That would stop other sprites from changing it, but it wouldn't keep the bubble on screen.
- [x] `level up` is broadcast from inside a `forever` loop
  The receiver restarts every frame, so its 2-second `say` never finishes and the change never runs.
- [ ] `say` blocks can't be used in receivers
  Any block works in a receiver; the problem is the receiver restarting.

Q: Three Ghost sprites each have a `health` variable made "for this sprite only." You click Ghost2 and its script runs `change [health v] by (-1)`. Whose health changes?
- [ ] All three ghosts'
  That's what would happen with one variable for all sprites.
- [x] Only Ghost2's
  Each sprite has its own private copy, and the script changes the copy belonging to its own sprite.
- [ ] Nobody's, because local variables can't be changed
  The sprite that owns a local variable can change it freely.
:::

:::takeaways
- Use `broadcast` instead of matching `wait` timers, so sprites react to events instead of guessing when they'll happen.
- `broadcast and wait` holds the sender until every receiving script finishes; never use it with a receiver that loops forever.
- Variables keep their values between runs, so reset every one at the green flag.
- `wait until` and `repeat until` check a condition every frame; you rarely need `forever` plus `if` around a broadcast.
- A `state` variable records the game's current mode, and every input should check it before acting.
:::
