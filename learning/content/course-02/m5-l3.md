:::objectives
- Pick the right sensing block for hazards, pickups, and sight ranges.
- Make a touch count exactly once.
- Run two scripts in one sprite: one that moves, one that watches.
- Track a player's state across frames to build a double jump.
:::

Most exercises add to Crystal Climb from the Build-along, so open that project first. If you're signed in, **File › Save as a copy** keeps the original untouched.

## Warm-up: name the block

For each situation, decide which sensing block you'd use before you check the answer: `touching (sprite)?`, `touching color?`, `color is touching color?`, or `distance to`.

1. A bat swoops into the player.
2. The player's sword tip (painted bright yellow) hits a red balloon.
3. A dog starts barking when the player gets near.
4. The player steps in a puddle painted into the backdrop.

:::solution
1. `touching (Bat v)?`, because both are sprites and you care about real overlap.
2. `color [yellow] is touching [red]?`, run by the player sprite, so only the sword tip counts and a bump with your elbow doesn't.
3. `distance to (Player v)`, compared with a number like 150. Nearness isn't overlap.
4. `touching color [puddle blue]?`, since the puddle isn't a sprite at all.
:::

### Exercise 1: Spikes that send you home

Paint a new sprite called `Spikes` (a row of triangles) and put it on platform B. When Pip touches the spikes, it should go back to the start, stop moving, and add 1 to a `falls` variable that the game shows on the stage. Falling into the pit should also count as a fall.

```text
Pip touches the spikes  ->  Pip appears at (-200, -90), standing still
falls: 0  ->  falls: 1   (exactly 1, not 3 or 4)
```

:::hint
You already have respawn code for the pit. Turn its condition into "fell below −160 **or** touching Spikes". The count goes up only once because Pip is teleported away in the same frame, so the next frame isn't touching anything.
:::

:::solution
Replace the pit check at the end of Pip's loop, and add `set [falls v] to (0)` near the top of the script.

```scratch
if <<(y position) < (-160)> or <touching (Spikes v)?>> then
  go to x: (-200) y: (-90)
  set [y speed v] to (0)
  change [falls v] by (1)
end
```

Make `falls` **For all sprites** so its monitor reads "falls" on the stage and other sprites can read it later.
:::

### Exercise 2: Count the coin once

Here's a coin script with a bug. Paint a small yellow circle called `Coin`, give it this script, and walk Pip through it.

```scratch
when green flag clicked
set [score v] to (0)
forever
  if <touching (Pip v)?> then
    change [score v] by (1)
  end
end
```

Fix it so each touch adds exactly 1, the coin disappears, and it comes back 2 seconds later somewhere random in the top half of the stage.

```text
Walk through the coin  ->  score: 1, coin vanishes
2 seconds later        ->  coin appears somewhere new
```

:::hint
The score climbs for every frame of overlap. What's the quickest way to make `touching` stop being true?
:::

:::solution
```scratch
when green flag clicked
set [score v] to (0)
show
forever
  if <touching (Pip v)?> then
    change [score v] by (1)
    hide
    wait (2) seconds
    go to x: (pick random (-200) to (200)) y: (pick random (0) to (150))
    show
  end
end
```

`hide` is the important line. A hidden sprite never counts as touching, so the loop can't see Pip again until the coin reappears.
:::

### Exercise 3: A guard who sees you coming

Add the library sprite **Knight** (or any character) on the right-hand ground, at about size 50. It should patrol back and forth forever. When Pip comes within 120 steps, the knight says "Halt!" and turns to face Pip. When Pip leaves that range, the knight stops talking.

:::hint
Use two scripts in the knight: one that only patrols with `glide`, and one that only watches with `distance to`. Both start with the green flag and run at the same time.
:::

:::solution
```scratch
when green flag clicked
go to x: (80) y: (-95)
forever
  glide (2) secs to x: (200) y: (-95)
  glide (2) secs to x: (80) y: (-95)
end

when green flag clicked
forever
  if <(distance to (Pip v)) < (120)> then
    say [Halt!]
    point towards (Pip v)
  else
    say []
    point in direction (90)
  end
end
```

`say []` with nothing in it clears the speech bubble. Set the knight's rotation style to left-right (in the sprite's direction settings, or with `set rotation style [left-right v]`) so pointing at Pip flips it instead of tipping it over.
:::

### Exercise 4: A bounce pad

Add the library sprite **Trampoline** on the right-hand ground. When Pip lands on it, Pip should shoot upward much higher than a normal jump.

```text
Pip drops onto the trampoline  ->  y speed set to 20, Pip rises about 190 steps
```

:::hint
Check right after `change y by (y speed)` and *before* the Level landing check, which sets `y speed` to 0. "Lands on" means touching the trampoline while moving down.
:::

:::solution
```scratch
if <<touching (Trampoline v)?> and <(y speed) < (0)>> then
  set [y speed v] to (20)
end
```

The `y speed < 0` part matters: without it, Pip would be launched again on the way up while still overlapping the pad. Gravity takes away 1 per frame, so a speed of 20 climbs 19 + 18 + … + 1 = 190 steps.
:::

### Exercise 5: Slide along walls in a top-down game

Start a new project with the library sprite **Beetle** at size 40 and a `Walls` sprite painted as a simple room with a few inside walls. Make the beetle move in all four directions with the arrow keys at 3 steps per frame, stopping at walls. Then test it: hold right and up together against a wall on the right. The beetle should slide up along the wall, not freeze.

:::hint
Four `if key pressed?` blocks, each with its own move and its own undo. If you move on both axes and check once, a diagonal push freezes the beetle.
:::

:::solution
```scratch
when green flag clicked
go to x: (0) y: (0)
forever
  if <key (right arrow v) pressed?> then
    change x by (3)
    if <touching (Walls v)?> then
      change x by (-3)
    end
  end
  if <key (left arrow v) pressed?> then
    change x by (-3)
    if <touching (Walls v)?> then
      change x by (3)
    end
  end
  if <key (up arrow v) pressed?> then
    change y by (3)
    if <touching (Walls v)?> then
      change y by (-3)
    end
  end
  if <key (down arrow v) pressed?> then
    change y by (-3)
    if <touching (Walls v)?> then
      change y by (3)
    end
  end
end
```

Pressing right into the wall gets undone, but the separate up move doesn't touch anything, so it stays. Slide along walls comes for free. If the beetle catches on corners, its costume is too detailed; try a smaller size.
:::

### Exercise 6: Double jump

Let Pip jump once more while in the air. Each press of the up arrow gives one jump, holding it down doesn't use up both jumps, and landing restores both.

```text
Press up on the ground  ->  jump (jumps left: 1)
Press up again mid-air  ->  second jump (jumps left: 0)
Press up a third time   ->  nothing until Pip lands
```

:::hint
You need two new variables. `jumps left` replaces `on ground`: set it to 2 whenever Pip lands. `up held` remembers whether the up arrow was already down last frame, so a jump only happens on a *new* press. The diagram below shows the states.
:::

:::solution
In the landing check, replace `set [on ground v] to (1)` with `set [jumps left v] to (2)`, and delete `set [on ground v] to (0)`. Then replace the old jump `if` with this:

```scratch
if <key (up arrow v) pressed?> then
  if <<(up held) = (0)> and <(jumps left) > (0)>> then
    set [y speed v] to (13)
    change [jumps left v] by (-1)
  end
  set [up held v] to (1)
else
  set [up held v] to (0)
end
```

On the first frame of a press, `up held` is still 0, so the jump fires. Every frame after that, `up held` is 1, so holding the key does nothing more. Letting go sets it back to 0, ready for the next press. One quirk: walking off a ledge leaves both jumps unused, so Pip gets two air jumps. If you don't want that, give the landing check an `else`: when Pip isn't touching the level and `jumps left` is 2, set it to 1.
:::

```mermaid caption="Double jump states. A new press moves Pip one state to the right; landing goes back to the start."

```

### Challenge: momentum and ice

Right now Pip starts and stops instantly. Give it momentum: add an `x speed` variable. The arrow keys change `x speed` by 1 (or −1), every frame multiplies it by 0.8 for friction, and Pip moves by `x speed` with the usual undo. Then paint one platform light blue in the Level costume and make it icy: on ice, Pip should be slow to speed up and slow to stop.

:::hint
After undoing a horizontal move into a wall, set `x speed` to 0, or Pip will keep pressing into it. For ice, the tricky part is *when* to check. Pip only overlaps the floor right after `change y by (y speed)` and before the undo, so test `touching color` there and store the answer in a variable.
:::

:::solution
Replace the two arrow-key `if` blocks at the top of Pip's loop with this:

```scratch
if <(on ice) = (1)> then
  set [grip v] to (0.25)
  set [friction v] to (0.96)
else
  set [grip v] to (1)
  set [friction v] to (0.8)
end
if <key (right arrow v) pressed?> then
  change [x speed v] by (grip)
end
if <key (left arrow v) pressed?> then
  change [x speed v] by ((0) - (grip))
end
set [x speed v] to ((x speed) * (friction))
change x by (x speed)
if <touching (Level v)?> then
  change x by ((0) - (x speed))
  set [x speed v] to (0)
end
```

Inside the vertical landing check, before the undo, add:

```scratch
if <touching color [#9fd8ff]?> then
  set [on ice v] to (1)
else
  set [on ice v] to (0)
end
```

Use the color picker's eyedropper to choose the exact blue from your costume. On normal ground, holding a key settles at a top speed of 4 steps per frame, the same as before, and Pip stops almost at once. On ice, Pip speeds up slowly to a top speed of 6 and takes about two seconds to slide to a stop. Ice needs both changes: low friction alone (0.97 with a grip of 1) gives a top speed above 30, and Pip rockets off the stage.
:::
