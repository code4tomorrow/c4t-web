Make a new project, drag out `go to x: (300) y: (0)`, and click it. The cat doesn't go to 300. It stops at the right edge with part of its body still showing. Click `go to x: (0) y: (-500)` and the same thing happens at the bottom.

There's a reason: the stage is only 480 pixels wide and 360 tall, and Scratch won't let a sprite leave it completely. Every game you'll build depends on knowing exactly where things are on that small rectangle, so that's where we start.

## The stage is a 480 by 360 grid

Every point on the stage has two numbers. **x** says how far left or right, and **y** says how far up or down. The center is (0, 0).

-   x runs from **−240** at the left edge to **240** at the right edge.
-   y runs from **−180** at the bottom to **180** at the top.
-   Positive x is right of center, negative x is left. Positive y is above center, negative y is below.

Move your mouse over this practice stage to read coordinates the way Scratch does, and click to drop pins. (The code is only the web page that draws the grid; you don't need to read it.)

```html preview height="450" title="practice-stage.html"

</style>

<script>
  const svg = document.getElementById("stage");
  const read = document.getElementById("read");
  const add = (tag, attrs, text) => {
    const el = document.createElementNS("http://www.w3.org/2000/svg", tag);
    for (const key in attrs) el.setAttribute(key, attrs[key]);
    if (text) el.textContent = text;
    svg.appendChild(el);
    return el;
  };
  for (let x = -240; x <= 240; x += 60) add("line", { x1: x + 240, y1: 0, x2: x + 240, y2: 360, stroke: x ? "#e2e2e2" : "#777777", "stroke-width": x ? 1 : 2 });
  for (let y = -180; y <= 180; y += 60) add("line", { x1: 0, y1: 180 - y, x2: 480, y2: 180 - y, stroke: y ? "#e2e2e2" : "#777777", "stroke-width": y ? 1 : 2 });

  add("text", { ...label, x: 4, y: 174 }, "x = -240");
  add("text", { ...label, x: 476, y: 174, "text-anchor": "end" }, "x = 240");
  add("text", { ...label, x: 246, y: 14 }, "y = 180");
  add("text", { ...label, x: 246, y: 354 }, "y = -180");

    const [x, y] = toStage(e);
    add("circle", { cx: x + 240, cy: 180 - y, r: 4, fill: "#4c97ff" });
    add("text", { x: x > 150 ? x + 234 : x + 246, y: 176 - y, "font-size": 12, fill: "#1f5fbf", "text-anchor": x > 150 ? "end" : "start" }, "(" + x + ", " + y + ")");
```

Try to land a pin on (−120, 60). It's left of center, so x is negative, and above center, so y is positive. If you can find a spot before you click, you can place sprites without guessing.

## A sprite's position is its costume center

When the sprite pane says a sprite is at x 100, y 50, it means one particular point of the sprite is there: its **costume center**. For the cat, that's roughly the middle of its body. When the sprite turns, it spins around that same point.

Four Motion blocks change position, and they behave differently:

| Block | What it does |
| --- | --- |
| `go to x: () y: ()` | Jumps straight to that point, with no animation |
| `glide (1) secs to x: () y: ()` | Travels there smoothly; the script waits until it arrives |
| `change x by ()` | Moves *relative* to where the sprite is now |
| `set x to ()` | Moves to an *exact* x and leaves y alone |

Predict where the cat ends up, then build it and check the x and y boxes:

```scratch
when green flag clicked
go to x: (-200) y: (-100)
glide (2) secs to x: (0) y: (-100)
change x by (50)
change y by (150)
set x to (-60)
```

| After this block | x | y |
| --- | --- | --- |
| `go to x: (-200) y: (-100)` | −200 | −100 |
| `glide (2) secs…` | 0 | −100 |
| `change x by (50)` | 50 | −100 |
| `change y by (150)` | 50 | 50 |
| `set x to (-60)` | −60 | 50 |

Notice that `change` blocks add to whatever is there already, while `set` throws the old value away. Mixing them up is the most common source of "why is my sprite over there?"

## Direction: 90 means right

Scratch measures direction in degrees, like a compass that starts at the top:

| Direction | The sprite faces |
| --- | --- |
| 0 | up |
| 90 | right (every new sprite starts here) |
| 180 | down |
| −90 | left |

`point in direction (-90)` turns the cat to face left, but it also flips it upside down, because by default sprites rotate **all around**. For characters that walk left and right, pick a different rotation style:

```scratch
set rotation style [left-right v]
point in direction (-90)
```

Now the cat mirrors itself to face left and stays upright. The third style, **don't rotate**, keeps the costume exactly as drawn no matter the direction, which suits things like buttons and score signs.

## Costumes, backdrops, and layers

A **costume** is one picture of a sprite. Many library sprites come with two or more, and flipping between them quickly is how Scratch animation works. Open the **Costumes** tab to see them, rename them, or paint new ones.

```scratch
switch costume to (cat-b v)
wait (0.2) seconds
next costume
```

`next costume` moves to the following costume in the list and wraps back to the first after the last. `switch costume to` picks one by name, which is safer when the order might change.

The **Stage** has its own pictures, called **backdrops**. Only the Stage owns backdrops, but any sprite can change them with `switch backdrop to`. Sprites are always drawn in front of the backdrop.

Sprites are also stacked in **layers**, like sheets of paper. When two sprites overlap, the one on the higher layer covers the other. `go to [front v] layer` moves a sprite to the top of the pile, and `go [backward v] (1) layers` sinks it one step. Dragging a sprite around the stage in the editor also brings it to the front.

## Events start scripts, and scripts run side by side

A script only runs when something starts it. That's the job of the round-topped **hat blocks** in Events:

| Hat block | Starts its script when… |
| --- | --- |
| `when green flag clicked` | the green flag is clicked |
| `when [space v] key pressed` | that key is pressed (the dropdown lists every key) |
| `when this sprite clicked` | someone clicks this sprite |
| `when backdrop switches to [ v]` | the Stage changes to that backdrop |
| `when [loudness v] > (10)` | the microphone hears something loud, or the timer passes a number |
| `when I receive [ v]` | another script sends that message with `broadcast` |

A program built this way is called **event-driven**: nothing happens until an event arrives, and then every script waiting for that event starts. They don't take turns. They all run at the same time.

```mermaid caption="One green flag click starts every script that's waiting for it"
flowchart LR
    F((Green flag)) --> A["Cat: go to start, then glide"]
    F --> B["Cat: blink forever"]
    F --> C["Bat: flap forever"]
    F --> D["Stage: switch backdrop"]
    K((Space key)) --> E["Cat: say Hi"]
```

Here's one sprite with two scripts on the same hat block. Run it and both happen at once: the cat glides across the stage *while* it changes costume.

```scratch
when green flag clicked
go to x: (-180) y: (0)
glide (3) secs to x: (180) y: (0)

when green flag clicked
repeat (15)
next costume
wait (0.2) seconds
end
```

The last hat in the table, `when I receive`, is how sprites signal each other: one script broadcasts a message like `start`, and every script waiting for `start` begins. You'll use it once in the next lesson, and Module 3 is all about it.

:::warning
**Two scripts fighting over one sprite.** If one script is gliding the cat and another does `go to x: (0) y: (0)`, the jump seems to do nothing. The glide works out its position fresh every frame from where it started and where it's going, so on the very next frame it puts the cat back on its path. When a sprite won't go where you told it, look for another script that's also moving it.
:::

:::warning
**No reset at the start.** If your green flag script starts with a `glide` instead of a `go to`, every run begins wherever the last one ended. Start each sprite's green flag script by setting its position, direction, costume, and size.
:::

:::quiz
Q: A sprite is at (100, 50). It runs `change x by (-150)` and then `change y by (-100)`. Where is it now?
- [ ] (−150, −100)
  That's what two `set` blocks would do. `change` adds to the current position.
- [x] (−50, −50)
  100 − 150 = −50 for x, and 50 − 100 = −50 for y.
- [ ] (250, 150)
  The changes are negative, so both numbers get smaller.

Q: You want a car sprite to face down the stage. Which block?
- [ ] `point in direction (0)`
  0 is up in Scratch, not down.
- [ ] `point in direction (-90)`
  −90 is left.
- [x] `point in direction (180)`
  180 is straight down, the opposite of 0.

Q: A sprite has two green flag scripts. One says "Hello!" for 2 seconds; the other glides across the stage in 2 seconds. What do you see?
- [ ] First it says hello, then it glides
  Scripts with the same hat don't take turns.
- [x] It glides across while saying hello
  Both scripts start on the same click and run at the same time.
- [ ] Only the script nearest the top runs
  Where a script sits in the code area doesn't matter; every matching hat fires.

Q: You run `go to x: (0) y: (500)`. Where does the sprite end up?
- [ ] At y = 500, off the stage and invisible
  Scratch doesn't let sprites leave the stage completely.
- [x] At the top edge, with part of it still showing
  The stage only goes up to y = 180, and Scratch stops the sprite while a piece is still visible.
- [ ] Back at (0, 0)
  Scratch doesn't reset the sprite; it stops it at the edge.
:::

:::takeaways
- The stage is 480 × 360: x from −240 to 240, y from −180 to 180, with (0, 0) in the center.
- A sprite's x and y are the position of its costume center.
- `change` moves relative to where you are; `set` and `go to` move to an exact spot; `glide` moves over time and makes the script wait.
- Direction 90 is right, 0 is up, 180 is down, −90 is left. Use the left-right rotation style for walking characters.
- Hat blocks start scripts, and every script triggered by the same event runs at the same time.
:::
