Here's the most common way Scratch projects get lost, and it isn't a crash. Someone saves `Scratch Project.sb3` into Downloads, then saves again the next day, and the browser names it `Scratch Project (1).sb3`, then `(2)`, then `(3)`. A week later there are six files with the same name and nobody remembers which one has the working jump. Ten minutes of routine now prevents all of that.

## How this course fits together

Module 1 is setup. Modules 2 to 7 each teach one big idea in three lessons:

| Lesson | What you do | Time to plan for |
| --- | --- | --- |
| **Notes** | Learn the idea with small examples, then check yourself with a quiz | 30 to 45 minutes |
| **Build-along** | Build one real game or scene step by step | 45 to 90 minutes |
| **Practice** | Solve new problems with hints and full solutions, then try a challenge | 45 to 90 minutes |

Module 8 is your capstone: a multi-level game you design, build, test, and present. It uses something from every module, so don't skip ahead.

Two habits make the lessons work much better. First, keep Scratch open next to the lesson and build as you read. Second, when a lesson asks you to predict what a script will do, actually decide before you click. Being wrong about a prediction teaches you more than reading the answer.

## Save early, and keep old versions

Each way of running Scratch saves differently, but the rule is the same: save after every step that works.

:::tabs
@tab No account
**File › Save to your computer** creates a new file each time. Use that to your advantage: give every save a version number.

```text
race-v1-places.sb3
race-v2-countdown.sb3
race-v3-winner.sb3
```

If version 3 breaks badly, open version 2 and you've lost one step, not the whole game.
@tab With an account
**File › Save now** saves to your account, and Scratch also saves on its own every so often. Before a risky change, like rewriting your movement script, use **File › Save as a copy**. You get a second project to experiment in while the original stays safe. Your copies all appear in **My Stuff**.
@tab Scratch app
**File › Save to your computer** opens a save window. Use the same version numbers as in the No account tab, and keep every file in one course folder. On a Chromebook, export important projects to Google Drive now and then. Projects stored inside the app can be lost if the app is removed or the Chromebook is reset.
:::

Two rescue tools are worth knowing before you need them:

-   **Edit › Restore** brings back the last sprite, costume, sound, or backdrop you deleted. It only remembers the most recent deletion, so use it right away.
-   **Undo** in the code area (right-click empty space and choose **Undo**, or press Ctrl+Z on Windows and Chromebook, Cmd+Z on Mac) takes back block moves and deletions.

## Organize your files and your project

Make one folder called `Scratch course` with a folder inside for each module. Name files `module-project-version`, like `m4-reef-catch-v2.sb3`. Future you will be grateful.

Inside a project, names matter even more, because your scripts use them:

-   Rename sprites in the sprite pane: `Crab`, not `Sprite1`. A block like `touching (Sprite3 v)?` tells you nothing, while `touching (Jellyfish v)?` reads like a sentence.
-   Name costumes for what they show: `glow` and `dim`, not `costume1` and `costume2`.
-   Name variables for what they count: `score`, `lives`, `fall speed`.
-   Right-click the code area and choose **Clean up Blocks** to line your scripts up neatly. **Add Comment** sticks a note on the code area, or on a block if you right-click the block. Notes like "resets everything at the flag" help you later.

## Carry code between projects

Later modules reuse pieces of earlier games. There are two ways to move them.

**With an account, use the Backpack.** It's the bar along the bottom of the editor. Drag a script, sprite, costume, or sound onto it, open another project, and drag it back out. Your Backpack follows you to any computer you sign in on.

**Without an account, export a sprite.** Right-click the sprite in the sprite pane and choose **export**. You get a `.sprite3` file with all of that sprite's scripts, costumes, and sounds. In another project, hover over the **Choose a Sprite** button and click **Upload Sprite** to bring it in.

## A routine for getting unstuck

Every programmer writes code that doesn't work. What separates beginners from experienced coders is mostly having a routine instead of staring at the screen. Here's one that fits Scratch:

```mermaid caption="Work around the loop until the script does what you expect"
flowchart TD
    A["Say exactly what's wrong"] --> B[Make it happen again on purpose]
    B --> C[Run one script by itself]
    C --> D[Look at the values]
    D --> E[Change one thing]
    E --> F{Fixed?}
    F -->|no| C
    F -->|yes| G[Save a new version]
```

1.  **Say exactly what's wrong.** "It's broken" can't be fixed. "The crab moves, but the score stays at 0 when it touches a starfish" can.
2.  **Make it happen again on purpose.** If you can't trigger the bug every time, you can't tell when you've fixed it.
3.  **Run one script by itself.** Click a script in the code area and it runs on its own, glowing yellow while it runs. If a script never glows, its hat block never fired.
4.  **Look at the values.** Tick the checkbox next to a variable, or next to `x position`, and a live monitor appears on the stage. Click any round reporter block to see its current value in a bubble. To watch a value inside a loop, drop in a temporary `say` block:

```scratch
say (join [fall speed is ] (fall speed))
```

5.  **Change one thing at a time,** then test. If you change three things and it starts working, you don't know which one fixed it, or whether the other two broke something new.

Scratch has its own help for this. The **Debug** button in the menu bar opens a set of cards with strategies like **Read Aloud**, **Slow It Down**, **Check the Values**, and **Take a Break, Step Away**. Slowing down helps more often than you'd think: a temporary `wait (1) seconds` between blocks lets you watch each step happen.

:::tip
Read your script out loud as if you were the sprite, block by block, doing only what each block says. You'll often hear the bug: "go to the top... fall... touching the crab? No... fall... touching? No..." and realize the score block sits outside the loop.
:::

## Asking for help so people can help you

If the routine doesn't crack it, ask. A good question has four parts:

1.  What you expected to happen.
2.  What happened instead.
3.  What you already tried.
4.  The script itself: a link to a shared project, or a screenshot of the code.

With an account, the **Help with Scripts** forum on the Scratch website is full of people who answer these. Never post your real name, school, or anything that says where you live, and remember that the Scratch Community Guidelines apply there too.

:::quiz
Q: You deleted a sprite by accident, then deleted a sound. Which can **Edit › Restore** bring back?
- [ ] The sprite
  Restore only remembers the most recent deletion, which was the sound.
- [x] The sound
  It undoes the last deletion only, so restore right after the mistake.
- [ ] Both
  It doesn't keep a history of deletions, just the last one.

Q: While your game runs, you watch the code area and the `when I receive [start v]` script never glows. What does that tell you?
- [x] The script never started, so check whatever is supposed to send `start`
  A script glows while it runs. No glow means its hat block never fired.
- [ ] One of the blocks inside the script is broken
  The blocks inside never got a chance to run; the problem is before the script starts.
- [ ] The project has to be saved before messages work
  Scripts and messages work the same whether or not the project is saved.
:::
