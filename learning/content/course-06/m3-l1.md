:::objectives
- Divide a page into landmarks: `<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<aside>`, and `<footer>`.
- Choose between `<ul>` and `<ol>`, and nest one list inside another.
- Build a data table with a caption and proper header cells.
- Write forms where every field has a `<label>`, the right input `type`, and sensible grouping and validation.
:::

Picture two recipe pages that look identical on screen. One is built from meaningful elements. The other is built entirely from `<div>`, the "generic box" element. A sighted visitor can't tell them apart.

Now open both with a screen reader. Screen readers have a shortcut that lists a page's regions and another that jumps straight to the main content. On the first page those shortcuts work: "banner, navigation, main, content info". On the `<div>` page they find nothing, and the visitor has to listen to the menu, the logo, and the ads every time before reaching the recipe. Browsers' reader modes, search engines, and translation tools lean on the same structure.

Choosing elements by what content *is*, rather than how it looks, is called **semantic HTML**. This lesson covers the elements you'll use on almost every page.

## Landmarks name the big regions of a page

```html preview height="470"
<header>
  <p>Weekend Kitchen</p>
  <nav>
    <a href="#">Recipes</a> | <a href="#">Tips</a> | <a href="#">About</a>
  </nav>
</header>
<main>
  <article>
    <h1>Fluffy blueberry pancakes</h1>
    <section>
      <h2>Ingredients</h2>
      <p>Flour, milk, an egg, and a cup of blueberries.</p>
    </section>
  </article>
  <aside>
    <p>Tip: frozen blueberries work too.</p>
  </aside>
</main>
<footer>
  <p>Weekend Kitchen, a student cooking project</p>
</footer>

<style>
  /* This CSS only draws and labels the boxes. Ignore it until Module 4. */
  header, nav, main, article, section, aside, footer {
    border: 2px dashed #64748b; padding: 4px 10px; margin: 6px 0;
  }
  header::before { content: "header"; }  nav::before { content: "nav"; }
  main::before { content: "main"; }  article::before { content: "article"; }
  section::before { content: "section"; }  aside::before { content: "aside"; }
  footer::before { content: "footer"; }
  header::before, nav::before, main::before, article::before,
  section::before, aside::before, footer::before {
    display: block; font: bold 12px monospace; color: #b45309;
  }
</style>
```

| Element | Use it for | How many |
| --- | --- | --- |
| `<header>` | The introductory area: site name or logo, often with the main navigation | Usually one for the page |
| `<nav>` | A block of major navigation links | One per menu |
| `<main>` | The content that's unique to this page | Exactly one |
| `<article>` | A piece that would make sense on its own if shared elsewhere: a blog post, a recipe, a news story | Any number |
| `<section>` | A themed part of something bigger, almost always starting with a heading | Any number |
| `<aside>` | Related but secondary content: a tip, a sidebar, a "see also" box | Any number |
| `<footer>` | Closing information: credits, copyright, contact links | Usually one for the page |

The quickest test for `<article>` versus `<section>`: could you copy this chunk onto another site and have it still make sense? A recipe could; its "Ingredients" part could not.

`<div>` and `<span>` still have a job. They're meaningless wrappers you add when you need a hook for CSS and no semantic element fits. `<div>` wraps blocks; `<span>` wraps a few words inside a line.

## Lists: does the order matter?

-   `<ul>` (unordered list) when the order doesn't matter: a packing list, a set of features. Browsers show bullets.
-   `<ol>` (ordered list) when it does: steps in a recipe, a top-five ranking. Browsers show numbers, and they renumber automatically if you add a step in the middle.
-   Every item is an `<li>`, and **only** `<li>` elements can sit directly inside a list.

To nest a list, put the inner list *inside* an `<li>`:

```html preview height="250"
<h2>Camping checklist</h2>
<ul>
  <li>Tent</li>
  <li>Food
    <ol>
      <li>Breakfast for both mornings</li>
      <li>Lunch for Saturday</li>
    </ol>
  </li>
  <li>Flashlight</li>
</ul>
```

Lists are also the standard way to mark up navigation: a `<nav>` containing a `<ul>` of links. A screen reader then announces that it's a list of three items before reading the links, so the visitor knows how long the menu is before going through it.

## Tables are for data with rows and columns

If information makes sense as a grid, where each cell is the meeting point of a row and a column, use a table:

```html preview height="200"
<table>
  <caption>Robotics club meetings</caption>
  <thead>
    <tr><th scope="col">Day</th><th scope="col">Time</th><th scope="col">Room</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row">Monday</th><td>3:30 PM</td><td>214</td></tr>
    <tr><th scope="row">Thursday</th><td>3:45 PM</td><td>Library</td></tr>
  </tbody>
</table>

<style>
  /* Borders only, so you can see the cells. */
  table { border-collapse: collapse; }
  th, td { border: 1px solid #94a3b8; padding: 4px 10px; }
</style>
```

-   `<caption>` is the table's title. Screen readers announce it when entering the table.
-   `<tr>` is a table row. Inside it, `<th>` is a header cell and `<td>` is a data cell.
-   `scope="col"` says "I'm the heading for this column"; `scope="row"` says the same for a row. When a screen reader user lands on "Library", they hear "Thursday, Room, Library" instead of a bare word.
-   `<thead>` and `<tbody>` separate the header rows from the data.

Before CSS could do layout, people built entire page designs out of invisible tables. Don't. A screen reader announces a layout table as data, row by row, and the result is nonsense.

## Forms that everyone can fill in

A form is a set of fields inside `<form>`. Here's a small sign-up form. Click the words "Saturday morning" in the result and watch the radio button select itself.

```html preview height="330"
<form>
  <p>
    <label for="name">Your name</label>
    <input type="text" id="name" name="name" required>
  </p>
  <p>
    <label for="email">Email</label>
    <input type="email" id="email" name="email" required>
  </p>
  <fieldset>
    <legend>Which session?</legend>
    <input type="radio" id="sat" name="session" value="saturday">
    <label for="sat">Saturday morning</label>
    <input type="radio" id="sun" name="session" value="sunday">
    <label for="sun">Sunday afternoon</label>
  </fieldset>
  <p>
    <input type="checkbox" id="news" name="news">
    <label for="news">Send me the monthly newsletter</label>
  </p>
  <button>Sign up</button>
</form>
```

The pieces, and why each one matters:

-   **`<label for="email">` and `<input id="email">`** are a pair because `for` matches `id` exactly. Clicking the label focuses or ticks the field (a bigger target for fingers and shaky hands), and a screen reader reads the label aloud when the field gets focus, something like "Email, edit text, required". A field without a label is announced as little more than "edit text".
-   **`name`** is the field's key in the data the form sends. Fields without a `name` aren't sent at all.
-   **`type`** changes the field. `type="email"` checks for an `@`, and on phones it brings up a keyboard with `@` on it.
-   **`<fieldset>` and `<legend>`** group related controls. For radio buttons, the legend is the question ("Which session?") and the labels are the answers.
-   **Radio buttons with the same `name`** form one group, so choosing one unchooses the others. `value` is what gets sent for the chosen one.
-   **`required`** makes the browser refuse to send the form until the field is filled in, with a message pointing at the empty field.
-   **`<button>`** inside a form submits it.

You can also wrap a control inside its label, with no `for` or `id` needed: `<label><input type="checkbox" name="news"> Send me the newsletter</label>`. Both styles are correct.

| Field | Markup | What the visitor gets |
| --- | --- | --- |
| Short text | `<input type="text">` | A one-line box |
| Email | `<input type="email">` | A check for a valid address, `@` keyboard on phones |
| Password | `<input type="password">` | Dots instead of letters |
| Number | `<input type="number" min="1" max="20">` | Number keypad, values outside the range rejected |
| Phone | `<input type="tel">` | Phone keypad (no format checking) |
| Date | `<input type="date">` | A date picker |
| Pick several | `<input type="checkbox">` | Each box on or off |
| Pick one | `<input type="radio">` | One choice per `name` group |
| Pick from a list | `<select>` with `<option>`s | A drop-down menu |
| Longer text | `<textarea>` | A multi-line box |

:::try
The result frames in these lessons block forms from sending, so the button does nothing here. Copy the form into a page in your own project and open it with Live Server. Click **Sign up** with the name empty, and the browser stops you with a message. Fill everything in and click again: the page reloads, and the address bar ends with something like `?name=Jordan&email=j%40example.com&session=saturday`. Those are your `name`s and values. A real site would send them to a server instead of back to the same page.
:::

## Mistakes that make forms hard to use

:::warning
**Using `placeholder` instead of a label.** `<input placeholder="Email">` looks tidy, but the hint vanishes the moment someone starts typing, so they can't check what the field wanted. Placeholder text is usually pale gray and hard to read, too. Always use a real `<label>`. Keep `placeholder` for a format example, like `placeholder="name@example.com"`.
:::

:::warning
**A `for` that doesn't match its `id`.** `<label for="e-mail">` with `<input id="email">` silently links nothing. The quick test: click every label on your form. If the field doesn't light up, the pair is broken. A related bug: radio buttons with *different* `name`s, which lets visitors select every option at once.
:::

:::quiz
Q: You're marking up the steps of a recipe: "Whisk the dry ingredients", "Add the milk", "Cook for 2 minutes". Which list?
- [x] `<ol>`, because the order matters
  Steps only work in sequence, and the numbers help a cook keep their place.
- [ ] `<ul>`, because it's the default list
  There's no default. Use `<ul>` only when the items could be shuffled without losing meaning.
- [ ] Three `<p>` elements
  That loses the information that these items belong together, and how many there are.

Q: A school news page shows five stories, each with its own headline and text. What should wrap each story?
- [ ] `<section>`
  A section is a part of something bigger. Each story makes sense on its own.
- [x] `<article>`
  Each story could be copied to another site and still make sense, which is exactly what `<article>` is for.
- [ ] `<aside>`
  The stories are the main content, not side notes.

Q: You click the label "Email" and the cursor doesn't jump to the email field. What's the most likely cause?
- [ ] The input needs `type="email"` for labels to work
  Labels work with every type of input.
- [x] The label's `for` doesn't exactly match the input's `id`
  The link only exists when the two values are identical, letter for letter.
- [ ] Labels only work with a mouse
  Labels also give the field its spoken name for screen reader users.

Q: Visitors can select all three of your "T-shirt size" radio buttons at once. What's wrong?
- [ ] The buttons need to be inside a `<fieldset>`
  A fieldset groups them visually and for screen readers, but it doesn't make them exclusive.
- [ ] They should be checkboxes instead
  Checkboxes allow several choices, which is the problem you're trying to fix.
- [x] They have different `name` values
  Radio buttons only act as one group when they share the same `name`.
:::

:::takeaways
- Pick elements for what content *is*: landmarks for regions, `<article>` for self-contained pieces, `<section>` for themed parts, and `<div>`/`<span>` only as styling hooks.
- `<ol>` when order matters, `<ul>` when it doesn't. Only `<li>` goes directly inside a list, and nested lists go inside an `<li>`.
- Tables are for data grids, with a `<caption>` and `<th scope>` header cells, never for layout.
- Every form field needs a `<label>` whose `for` matches its `id`, plus a `name`. Use the right `type`, group radio buttons with a shared `name` and a `<fieldset>`/`<legend>`, and add `required` where it applies.
:::
