:::objectives
- Link an external stylesheet and organize it into commented sections.
- Use `box-sizing: border-box`, padding, borders, and `margin: 0 auto` to build a centered card.
- Style labels, inputs, radio buttons, and a button with class and descendant selectors.
- Diagnose and fix two specificity conflicts by reading selector scores.
- Add hover, focus, and error states with pseudo-classes, ordered so the right one wins.
:::

## Step 1: The files and the HTML

```text
signup/
├── index.html
└── css/
    └── styles.css
```

The form uses everything from Module 3: a label for every field, real input types, `required`, and a `<fieldset>` for the radio group. Two new details: the radio buttons and checkbox are wrapped *inside* their labels (the other correct way to pair them), and each field sits in a `<div class="field">`. That `<div>` carries no meaning; it's a hook for CSS, which is exactly what `<div>` is for.

## Step 2: A base layer

Start `styles.css` with rules that affect the whole page:

```css
/* 1. Base */
*, *::before, *::after {
  box-sizing: border-box;
}

body {
  margin: 0;
  padding: 32px 16px;
  background: #eef2ff;
  color: #1e293b;
  font-family: system-ui, sans-serif;
  line-height: 1.5;
}
```

The first rule switches every element to `border-box`, so a `width` always includes padding and border. `body` loses the browser's default 8px margin and gets padding instead, so the card never touches the screen edge on a phone. `system-ui` uses the operating system's own font, and `line-height: 1.5` spaces lines comfortably. Text properties like `color` and `font-family` inherit, so setting them on `body` styles the whole page at once.

## Step 3: The card

```css
/* 2. The card */
.card {
  max-width: 420px;
  margin: 0 auto;
  padding: 32px;
  background: white;
  border: 1px solid #c7d2fe;
  border-radius: 16px;
}

.card h1 {
  margin: 0 0 8px;
  font-size: 28px;
  line-height: 1.2;
}

.intro {
  margin: 0 0 24px;
  color: #475569;
}
```

`max-width: 420px` lets the card shrink on a narrow phone but never grow wider than 420px. `margin: 0 auto` means "no margin top and bottom, and split the leftover space equally left and right", which centers any block that's narrower than its container.

`.card h1` scores 0-1-1, and it only touches headings inside the card. It overrides the browser's default `<h1>` margin so the heading sits snugly above the intro. Using margins only on the bottom of things, as here, keeps vertical spacing predictable and avoids most margin-collapse surprises.

## Step 4: Labels and text inputs

```css
/* 3. Fields */
.field {
  margin: 0 0 20px;
}

.field label {
  display: block;
  margin-bottom: 6px;
  font-weight: 600;
}

.field input {
  width: 100%;
  padding: 10px 12px;
  border: 2px solid #94a3b8;
  border-radius: 8px;
  font: inherit;
}

.hint {
  margin: 6px 0 0;
  font-size: 14px;
  color: #64748b;
}
```

Labels are inline by default, so `display: block` puts each one on its own line above its input. The inputs stretch to `width: 100%` of the card's content area.

`font: inherit` matters more than it looks. Form controls are an exception to inheritance: browsers give them their own small font, so without this line the text people type is smaller than the rest of the page.

Here's why Step 2's `box-sizing` rule earns its place. This demo leaves it out. It also starts with `<!DOCTYPE html>`, so the frame runs in standards mode like your real pages:

```html preview height="150"
<!DOCTYPE html>
<div class="card">
  <label for="demo">Email</label>
  <input id="demo" type="email">
</div>
<style>
  /* No border-box reset in this demo */
  .card { width: 260px; padding: 16px; border: 2px solid #c7d2fe; font-family: system-ui, sans-serif; }
  label { display: block; }
  input { width: 100%; padding: 10px 12px; border: 2px solid #94a3b8; font: inherit; }
</style>
```

The input pokes out of the card. Under `content-box`, its 100% width is the full content width of the card, and then 24px of padding and 4px of border are added on top. With the reset, those are included in the 100%, and it fits. (Delete the doctype line and the input suddenly fits, because quirks mode, from Module 2, gives inputs `border-box`. Old browser behavior like that is exactly why the doctype matters.)

## Step 5: Fix the radio buttons (a real specificity bug)

Save and look at the "Which track?" group. Here it is with only the Step 4 rules applied:

```html preview height="190"
<!DOCTYPE html>
<fieldset class="field">
  <legend>Which track?</legend>
  <label class="choice"><input type="radio" name="track" value="web"> Web pages</label>
  <label class="choice"><input type="radio" name="track" value="games"> Games</label>
</fieldset>
<style>
  *, *::before, *::after { box-sizing: border-box; }
  body { font-family: system-ui, sans-serif; }
  .field label { display: block; margin-bottom: 6px; font-weight: 600; }
  .field input { width: 100%; padding: 10px 12px; border: 2px solid #94a3b8; border-radius: 8px; font: inherit; }
</style>
```

Each radio button floats in the middle of its own line above its label, and the answers are bold. Nothing in your CSS asked for that.

Inspect a radio button in DevTools and the Styles pane tells you why: `.field input` is styling it. The `<fieldset>` has `class="field"`, so `.field input` matches the radios inside it, and `.field label` matches their labels. Your rules reached further than you meant.

The fix is a rule that describes the special case *more specifically*:

```css
/* 4. Radio and checkbox choices */
fieldset {
  padding: 12px 16px;
  border: 2px solid #c7d2fe;
  border-radius: 8px;
}

legend {
  padding: 0 6px;
  font-weight: 600;
}

.field .choice {
  display: block;
  margin: 4px 0;
  font-weight: normal;
}

.field .choice input {
  width: auto;
  margin: 0 8px 0 0;
  accent-color: #4f46e5;
}
```

Check the scores. `.field .choice` (0-2-0) beats `.field label` (0-1-1) because the middle column is higher. `.field .choice input` (0-2-1) beats `.field input` (0-1-1) the same way. Because both fixes win on specificity, they'd work even if you moved them above the rules they override.

A plain `.choice` (0-1-0) would *lose* to `.field label` (0-1-1), wherever you put it. If you try that, DevTools shows `font-weight: normal` crossed out: the struck-through line is a declaration that lost the cascade. `accent-color` tints the radio and checkbox to match the button.

## Step 6: The button, and focus you can see

```css
/* 5. Button */
.button {
  display: block;
  width: 100%;
  padding: 12px;
  border: 0;
  border-radius: 8px;
  background: #4f46e5;
  color: white;
  font: inherit;
  font-weight: 700;
  cursor: pointer;
}

.button:hover {
  background: #4338ca;
}

.button:focus-visible {
  outline: 3px solid #f59e0b;
  outline-offset: 3px;
}

/* 6. States */
.field input:focus {
  border-color: #4f46e5;
  outline: 3px solid #c7d2fe;
}
```

`font: inherit` comes before `font-weight: 700` on purpose. `font` is a *shorthand* that resets the weight along with everything else, so the later `font-weight` line puts bold back. Swap the two lines and the button text goes back to normal weight.

`:focus-visible` matches when the browser decides a focus ring is needed, which mostly means keyboard users. Press **Tab** through the finished card at the top of this page: every field and the button light up as you reach them. Never remove focus outlines without replacing them. Keyboard users rely on them to see where they are.

`.field input:focus` scores 0-2-1, so it beats `.field input` (0-1-1) no matter where it sits in the file.

## Step 7: An error state, where order decides

```css
.field input:user-invalid {
  border-color: #dc2626;
}
```

`:user-invalid` matches a field that breaks its rules (empty but `required`, or an email without an `@`) *after* the visitor has interacted with it, so the form doesn't start out covered in red. Browsers older than about 2023 ignore it, and the form still works.

This rule and `.field input:focus` both score 0-2-1, a tie, so **source order** decides. With the error rule last, a field that's both focused and invalid shows a red border inside the light focus outline. Put it before the focus rule and the red disappears whenever someone clicks back in to fix the mistake, which is exactly when they need to see it.

## Step 8: Read the cascade in DevTools

Right-click the email field and choose **Inspect**. In the Styles pane:

-   The strongest rules are listed at the top. Crossed-out declarations lost the cascade to something above them.
-   Use the **:hov** button (Chrome) or the **:hov** toggle in Firefox's Rules view to force `:focus` or `:hover` on, so you can study those states without holding the mouse still.
-   Select the `<main class="card">` and open **Computed** (Chrome) or **Layout** (Firefox). The box diagram shows 32px of padding and a 1px border around the content, and the margin on each side is whatever space was left over.

:::quiz
Q: Why does `.field input` include `font: inherit`?
- [ ] Without it, the input's border disappears
  `font` has nothing to do with borders.
- [x] Form controls don't inherit the page's font by default, so typed text would look smaller and different
  Inputs and buttons get their own font from the browser. `font: inherit` makes them match the page.
- [ ] It makes the input inherit the card's width
  Width is a box property and never inherits. `width: 100%` handles that.

Q: Why did the fix for the bold radio labels need `.field .choice` rather than just `.choice`?
- [ ] Class names only work when combined with another class
  A single class works fine on its own. The problem was what it was competing against.
- [x] `.choice` scores 0-1-0, which loses to `.field label` at 0-1-1, wherever it's placed
  `.field .choice` scores 0-2-0, which wins on the middle column.
- [ ] `.choice` would also style the button
  The button doesn't have the `choice` class, so `.choice` can't select it.

Q: Both `.field input:focus` and `.field input:user-invalid` set `border-color`. Why must the `:user-invalid` rule come last?
- [ ] Pseudo-classes only work at the end of a stylesheet
  Pseudo-classes work anywhere in the file.
- [x] They tie at 0-2-1, so the later rule wins, and the red border should still show while someone is fixing the field
  On a specificity tie, source order decides. Last means red wins over the focus color.
- [ ] `:user-invalid` has lower specificity, so it needs to be later to win
  It has the same specificity as `:focus`; if it were lower, being later wouldn't help.
:::

:::takeaways
- Start every stylesheet with the `border-box` reset, and put page-wide text styles on `body` so they inherit.
- `max-width` plus `margin: 0 auto` makes a centered card that still shrinks on small screens.
- Form controls need `font: inherit`, and focus styles should never be removed without a replacement.
- When a rule hits more than you meant, inspect the element, read the scores, and write a more specific rule for the special case.
- On a specificity tie, order decides, so put state rules like errors after the rules they should beat.
:::
