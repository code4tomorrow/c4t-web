Your obstacle-avoider dodged every box in your bedroom ten times in a row. At school, on the first run, it drove straight into a chair leg.

Nothing in the code changed. What changed was everything else: a thin round leg instead of a flat box, a smooth floor instead of carpet, a battery that had been on all morning. The HC-SR04 datasheet even says so: it wants a target of at least 0.5 square meters with a smooth, flat face. A chair leg is neither. Ten passes in one room didn't test the robot; they tested that room ten times.

## One success proves almost nothing

A **test plan** decides in advance what you'll vary and what counts as passing. Start by listing the factors that could change the robot's behavior, then the levels each one can take:

```python run
from itertools import product

factors = {
    "obstacle": ["box", "chair leg", "wall at 45 degrees"],
    "start distance": ["100 cm", "30 cm"],
    "floor": ["tile", "carpet"],
    "battery": ["fresh", "after 20 min"],
}

all_combos = list(product(*factors.values()))
print("Every combination:", len(all_combos), "tests")

baseline = {name: levels[0] for name, levels in factors.items()}
tests = [baseline]
for name, levels in factors.items():
    for level in levels[1:]:
        tests.append({**baseline, name: level})   # change exactly one factor

print("Baseline plus one change at a time:", len(tests), "tests")
for number, test in enumerate(tests, start=1):
    changed = [f"{k}={v}" for k, v in test.items() if v != baseline[k]]
    print(f"T{number}:", ", ".join(changed) or "baseline")
```

Twenty-four combinations is a lot of trials. Changing **one factor at a time** from a baseline gets you six, and when one fails you know exactly which factor did it. Add one "worst case" run (chair leg, carpet, tired battery) and you've covered most of what goes wrong.

Each test needs an expected result you can check with a number, not "it works":

| ID | Setup | Action | Expected | Actual |
| --- | --- | --- | --- | --- |
| T1 | Box, 100 cm, tile, fresh | Drive toward it | Starts backing up between 15 and 25 cm | |
| T2 | Chair leg instead of box | Drive toward it | Same as T1 | |
| T3 | Wall at 45 degrees | Drive toward it | Same as T1; no contact | |
| T6 | Battery after 20 min | Turn after a stop | Heading changes 70 to 110 degrees | |

## Make the robot tell you what it's thinking

You can't watch variables inside a moving robot, so make it describe itself. A **log line** every 100 ms, in comma-separated values, records time, state, the sensor, and the motor commands:

```arduino
const bool LOGGING = true;
const unsigned long LOG_MS = 100;
unsigned long lastLog = 0;

void logLine(const char* state, long cm, int left, int right) {
  if (!LOGGING) return;
  unsigned long now = millis();
  if (now - lastLog < LOG_MS) return;
  lastLog = now;
  Serial.print(now);   Serial.print(',');
  Serial.print(state); Serial.print(',');
  Serial.print(cm);    Serial.print(',');
  Serial.print(left);  Serial.print(',');
  Serial.println(right);
}
```

Why every 100 ms and not every pass? At 115200 baud each character takes about 87 µs to send, so a 25-character line costs around 2 ms. Once the Uno's 64-byte send buffer fills, `Serial.print()` *waits*, and your carefully non-blocking loop slows down. Remember from the last module what a slower loop does to a P controller.

Copy the log out of the Serial Monitor and the computer can read it for you. This sample came from a robot approaching a wall at an angle:

```python run
log = """ms,state,cm,left,right
0,DRIVING,64,160,160
100,DRIVING,47,160,160
200,DRIVING,31,160,160
300,DRIVING,21,160,160
400,TURNING,19,-140,140
500,DRIVING,22,160,160
600,TURNING,19,-140,140
700,DRIVING,21,160,160
800,TURNING,18,-140,140
900,TURNING,17,-140,140
1000,DRIVING,24,160,160
1100,DRIVING,29,160,160"""

rows = [line.split(",") for line in log.splitlines()[1:]]
changes = []
for previous, row in zip(rows, rows[1:]):
    if row[1] != previous[1]:
        changes.append((int(row[0]), previous[1], row[1], row[2]))

print("State changes:", len(changes))
for ms, old, new, cm in changes:
    print(f"  {ms:5d} ms  {old} -> {new}  at {cm} cm")

quick = [b[0] - a[0] for a, b in zip(changes, changes[1:]) if b[0] - a[0] < 300]
print("Changes less than 300 ms apart:", len(quick))
```

Six state changes in 600 ms, all at readings between 18 and 24 cm, is the signature of a single threshold with no hysteresis and no minimum turn time. The log turned "it acts weird near walls" into a cause you can fix.

## Calibrate instead of guessing

A **calibration** compares what the sensor says with what's actually true, then corrects the difference. For a distance sensor, put a target at measured distances, record readings, and fit a straight line. Here's what a session with a real HC-SR04 and a tape measure might produce (illustrative numbers):

```python run alt="Scatter of measured against true distance from 10 to 150 centimeters with a fitted line slightly steeper than the dashed ideal line" caption="The fitted line shows a small scale error and offset you can subtract out"
import numpy as np
import matplotlib.pyplot as plt

true_cm = np.array([10, 20, 30, 50, 75, 100, 125, 150])
measured = np.array([11.2, 21.4, 31.8, 52.6, 78.1, 103.9, 129.4, 155.0])

slope, offset = np.polyfit(true_cm, measured, 1)
print(f"measured = {slope:.3f} x true + {offset:.2f}")

corrected = (measured - offset) / slope
print("Worst error before:", round(max(abs(measured - true_cm)), 1), "cm")
print("Worst error after: ", round(max(abs(corrected - true_cm)), 1), "cm")

plt.plot(true_cm, measured, "o", color="#7892ee", label="readings")
plt.plot(true_cm, slope * true_cm + offset, color="#e8590c", label="fitted line")
plt.plot(true_cm, true_cm, "--", color="#adb5bd", label="perfect sensor")
plt.xlabel("true distance (cm)")
plt.ylabel("measured (cm)")
plt.legend()
```

A slope above 1 means every reading is stretched, which is what happens when the speed of sound in your room differs from the 343 m/s in the formula. Sound is about 6% slower at 0 °C than at 35 °C. Your code applies `(reading - offset) / slope` and the error shrinks to a few millimeters.

Line sensors need a different calibration because brightness depends on the room. Before each run, sweep each sensor over the floor and the line for a few seconds, keep the lowest and highest readings, and rescale to 0..1000:

```arduino
int lowL = 1023, highL = 0;

void calibrateLeft() {
  unsigned long start = millis();
  while (millis() - start < 3000) {     // blocking is fine: the robot isn't driving yet
    int raw = analogRead(A0);
    if (raw < lowL) lowL = raw;
    if (raw > highL) highL = raw;
  }
}

int normalizedLeft() {
  int raw = constrain(analogRead(A0), lowL, highL);
  return map(raw, lowL, highL, 0, 1000);
}
```

Now "500" means "halfway between floor and line" under any lighting, so one threshold works in a dim gym and a sunny classroom. In Wokwi, drag the photoresistor's light slider up and down during those three seconds.

## Plan for how robots really fail

Every sensor and motor has known failure modes. Listing them before testing tells you which tests to write and what defensive code to add:

| Failure | What you see | Cause | Defense in code |
| --- | --- | --- | --- |
| No echo | Robot hits a wall while the log says 999 | Sound bounced off an angled or soft surface | Treat several no-echo readings in a row as "unknown" and slow down |
| Spike | One reading of 5 cm in open space | Echo from something else, electrical noise | Median filter: a single wild value never wins |
| Too close | Readings jump around under 3 cm | Below the sensor's 2 cm minimum | Never let it get there: start backing up at 15 cm or more |
| Weak battery | Turns come out short | Time-based turns at lower speed | Turn until the sensor sees clear space, not for a fixed time |
| Stuck | Wheels spin, robot doesn't move | Obstacle below the sensor's beam | Watchdog: no distance change for 3 s while driving means STUCK |
| Lighting | Line follower loses the line in sunlight | Ambient light swamps the sensor | Calibrate at the start of every run |

Then iterate in a fixed rhythm:

```mermaid caption="The test-and-iterate loop. Changing one thing per lap is what makes the results mean something."
flowchart LR
    A["Run the whole test plan"] --> B["Read the logs of failures"]
    B --> C["Form one hypothesis"]
    C --> D["Change one thing"]
    D --> A
```

The arrow back to "run the whole plan" matters. A fix for the chair leg can break the box test, and only rerunning every test (a **regression test**) catches it.

:::warning
**Testing habits that waste afternoons.**
1. **Changing two things at once.** If it improves, you don't know which change helped; if it gets worse, you don't know which one hurt.
2. **Only testing the happy path.** The box in the middle of the floor always works. Test corners, angles, thin objects, and a tired battery.
3. **Trusting the simulator's sensor.** Wokwi's HC-SR04 returns a clean, exact echo every time. Real sensors miss echoes and spike, so inject those faults yourself (the next lesson shows how).
:::

:::quiz
Q: A robot turns 90 degrees with a fresh battery but only about 60 degrees after twenty minutes. The turn code is `spinLeft(140)` for 500 ms. What's the best fix?
- [ ] Increase the turn time to 750 ms
  That fixes it for a tired battery and over-turns with a fresh one.
- [x] End the turn on a sensor condition (path clear) instead of a fixed time
  A weaker battery means slower wheels, so a fixed time covers less angle. Ending on what the sensor sees works at any speed.
- [ ] Log the battery voltage
  Logging helps you see the cause, but it doesn't change how far the robot turns.

Q: Which expected result belongs in a test plan?
- [ ] "The robot avoids the obstacle"
  Not measurable: avoids by how much, and how do you check it?
- [ ] "The robot works well near walls"
  "Well" can't pass or fail.
- [x] "Starts backing up when the reading is between 15 and 25 cm, with no contact"
  Two things you can check from the log and by watching.

Q: Your fitted calibration line is `measured = 1.04 x true + 0.5`. The sensor reads 104.5 cm. What's the true distance?
- [x] 100 cm
  Undo the fit: (104.5 − 0.5) / 1.04 = 100.
- [ ] 108.7 cm
  That applies the error a second time instead of removing it.
- [ ] 104 cm
  That removes the offset but not the 4% scale error.
:::

:::takeaways
- One success in one place proves little. Vary one factor at a time from a baseline, and add a worst case.
- Expected results must be numbers you can check.
- Log state and sensors as CSV every 100 ms or so, plus every state change. Logging every pass slows the loop.
- Calibrate distance with a straight-line fit and line sensors with per-run min/max readings.
- List failure modes before testing, and rerun the whole plan after every fix.
:::
