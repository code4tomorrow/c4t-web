Here's the first obstacle-avoider almost everyone writes:

```arduino
void loop() {
  long cm = readDistanceCm();
  if (cm < 20) {
    spinLeft(150);
  } else {
    forward(150);
  }
}
```

In an empty hallway it looks great. Then it meets a wall at an angle, the reading hovers around 19 to 21 cm, and the robot buzzes in place: spin, drive, spin, drive, dozens of times a second, never committing to a turn. Nothing is broken. The code simply has no memory. Every 10 ms it makes a brand-new decision from one noisy number.

This lesson fixes that three ways: timers that don't freeze the robot, states that remember what it's doing, and feedback that reacts in proportion instead of all-or-nothing.

## The delay() trap

The obvious patch is "when you see a wall, turn for 600 ms":

```arduino
if (cm < 20) {
  spinLeft(150);
  delay(600);
}
```

The twitching stops, but now the robot is blind for 0.6 s. At 30 cm/s it travels 18 cm in that time without reading a single sensor, and a STOP button pressed during the turn is ignored. `delay()` stops *everything*.

The fix is to check the clock instead of waiting on it. `millis()` returns the milliseconds since the board started, as an `unsigned long`. Save the time something started, and each pass through `loop()` ask "has enough time passed?":

```arduino
const unsigned long BLINK_MS = 500;
unsigned long lastBlink = 0;

void setup() {
  pinMode(LED_BUILTIN, OUTPUT);
}

void loop() {
  unsigned long now = millis();
  if (now - lastBlink >= BLINK_MS) {
    lastBlink += BLINK_MS;
    digitalWrite(LED_BUILTIN, !digitalRead(LED_BUILTIN));
  }
  // loop() keeps spinning: read sensors here, thousands of times a second
}
```

The line that matters is `now - lastBlink >= BLINK_MS`. Written as a subtraction of two `unsigned long` values, it keeps working even when `millis()` wraps back to zero after about 49.7 days. That's why every timer in this course looks exactly like it.

## State machines: give the robot a memory

A **state** is what the robot is doing right now: driving, backing up, turning. A **transition** is a rule for switching, triggered by a sensor reading or a timer. Drawing them first saves hours of debugging:

```mermaid caption="An obstacle-avoider with three states. Each arrow is a rule; nothing else can change the state."
stateDiagram-v2
    [*] --> DRIVING
    DRIVING --> BACKING_UP: wall closer than 20 cm
    BACKING_UP --> TURNING: 400 ms have passed
    TURNING --> DRIVING: 500 ms passed and path clear beyond 35 cm
```

In Arduino code, an `enum` names the states, one variable holds the current one, and a `switch` runs only that state's code:

```arduino
enum State { DRIVING, BACKING_UP, TURNING };
State state = DRIVING;
unsigned long stateStart = 0;

void enterState(State next) {
  state = next;
  stateStart = millis();     // every state gets its own stopwatch
}

void loop() {
  long cm = readDistanceCm();
  unsigned long inState = millis() - stateStart;

  switch (state) {
    case DRIVING:
      forward(160);
      if (cm < 20) enterState(BACKING_UP);
      break;
    case BACKING_UP:
      drive(-120, -120);
      if (inState >= 400) enterState(TURNING);
      break;
    case TURNING:
      spinLeft(140);
      if (inState >= 500 && cm > 35) enterState(DRIVING);
      break;
  }
}
```

The robot reads the sensor on *every* pass, even mid-turn, yet it can't be talked out of a turn by one noisy number. Here's the same logic in Python, one sensor reading per step. Watch the 21 cm reading: the twitchy version would have driven forward again.

:::trace Step through the states as readings arrive
```python
readings = [90, 60, 19, 21, 18, 25, 40, 70]
state = "DRIVING"
steps_in_state = 0
for cm in readings:
    steps_in_state += 1
    if state == "DRIVING" and cm < 20:
        state, steps_in_state = "TURNING", 0
    elif state == "TURNING" and steps_in_state >= 3 and cm > 35:
        state, steps_in_state = "DRIVING", 0
    print(cm, state)
```
:::

## Hysteresis: one threshold to enter, another to leave

Notice the two different numbers: turn when closer than 20 cm, but only drive again beyond 35 cm. That gap is **hysteresis**, and a thermostat uses the same trick so the heater doesn't click on and off every second. A noisy reading near one threshold can flip the decision; it can't jump a 15 cm gap.

Here's a robot creeping toward a wall with ±1.5 cm of sensor noise, decided both ways:

```python run alt="Top: noisy distance readings drifting from 24 down to 16 centimeters, with dashed lines at 20 and 25. Bottom: the one-threshold decision flips between DRIVE and TURN many times, the hysteresis decision switches once" caption="One threshold chatters; two thresholds commit"
import random
import matplotlib.pyplot as plt

random.seed(7)
times = [i * 0.02 for i in range(100)]                  # 2 s, one reading every 20 ms
readings = [24 - 4 * t + random.uniform(-1.5, 1.5) for t in times]

one = ["TURN" if cm < 20 else "DRIVE" for cm in readings]

two, state = [], "DRIVE"
for cm in readings:
    if state == "DRIVE" and cm < 20:
        state = "TURN"
    elif state == "TURN" and cm > 25:
        state = "DRIVE"
    two.append(state)

def changes(states):
    return sum(1 for a, b in zip(states, states[1:]) if a != b)

print("Decision changes with one threshold:", changes(one))
print("Decision changes with hysteresis:   ", changes(two))

fig, (top, bottom) = plt.subplots(2, 1, figsize=(7, 5), sharex=True)
top.plot(times, readings, ".", color="#7892ee", markersize=4)
top.axhline(20, color="#e8590c", linestyle="--", label="turn below 20 cm")
top.axhline(25, color="#2b8a3e", linestyle=":", label="drive again above 25 cm")
top.set_ylabel("distance (cm)")
top.legend(fontsize=8)
bottom.step(times, [1 if s == "TURN" else 0 for s in one], where="post", color="#e8590c", label="one threshold")
bottom.step(times, [1.1 if s == "TURN" else 0.1 for s in two], where="post", color="#2b8a3e", label="hysteresis")
bottom.set_yticks([0, 1], ["DRIVE", "TURN"])
bottom.set_xlabel("time (s)")
bottom.legend(fontsize=8, loc="center left")
plt.tight_layout()
```

Each orange flip would be a real motor reversal: wasted battery and a robot that looks broken.

## Feedback: measure, compare, correct

So far the robot's choices are all-or-nothing. A line follower needs something finer. It has two light sensors straddling a dark line; when the robot drifts left, the left sensor sees more white than the right one.

The **error** is how far you are from where you want to be. A **proportional controller** steers by an amount proportional to it:

```arduino
const int BASE = 150;      // forward speed
const float KP = 1.0;      // gain: PWM counts of steering per unit of error

int error = readLineError();          // -100 (far right of line) .. 100 (far left)
int correction = KP * error;
drive(BASE + correction, BASE - correction);
```

Small drift, gentle correction. Big drift, hard correction. Zero error, straight ahead. Sense, compare, act, repeat: that loop is **feedback**, and it's the same idea the servo used internally in the last module.

The one number you choose is the **gain**, `KP`. This simulation models a two-wheel robot that starts 2.5 cm off the line, with the sensor 12 cm ahead of the wheels, a 40 ms control loop, and motors that take 0.1 s to change speed:

```python run alt="Sensor offset over 3 seconds for three gains. Kp 0.3 swings slowly and widely before settling, Kp 1.0 settles within about 1.5 seconds, Kp 6.0 keeps oscillating about plus or minus 1.2 centimeters" caption="Too little gain is sluggish; too much never settles"
import math
import matplotlib.pyplot as plt

def follow_line(kp, loop_ms=40, seconds=3.0):
    dt = 0.005                        # physics step: 5 ms
    y, heading = 2.5, 0.0             # start 2.5 cm left of the line, pointing straight
    v_left = v_right = 0.0            # actual wheel speeds, cm/s
    left_pwm = right_pwm = 150
    times, offsets = [], []
    next_update = 0.0
    for step in range(int(seconds / dt)):
        t = step * dt
        sensor = y + 12 * math.sin(heading)            # sensor sits 12 cm ahead of the wheels
        if t >= next_update:                           # --- this part is the Arduino's loop() ---
            next_update += loop_ms / 1000
            error = max(-100, min(100, sensor / 3 * 100))   # maxes out 3 cm off the line
            correction = kp * error
            left_pwm = max(0, min(255, 150 + correction))
            right_pwm = max(0, min(255, 150 - correction))
        v_left += (left_pwm / 255 * 50 - v_left) * dt / 0.1   # motors lag by about 0.1 s
        v_right += (right_pwm / 255 * 50 - v_right) * dt / 0.1
        heading += (v_right - v_left) / 13 * dt        # wheels 13 cm apart
        y += (v_left + v_right) / 2 * math.sin(heading) * dt
        times.append(t)
        offsets.append(sensor)
    return times, offsets

for kp, color in [(0.3, "#adb5bd"), (1.0, "#7892ee"), (6.0, "#e8590c")]:
    times, offsets = follow_line(kp)
    late = [abs(o) for o, t in zip(offsets, times) if t >= 2.0]
    print(f"Kp = {kp}: worst offset in the last second = {max(late):.2f} cm")
    plt.plot(times, offsets, color=color, label=f"Kp = {kp}")
plt.axhline(0, color="black", linewidth=0.6)
plt.xlabel("time (s)")
plt.ylabel("sensor offset from line (cm)")
plt.legend()
```

Read the three curves. At **0.3** the robot corrects so gently that it swings wide and takes ages to settle; on a curve it would fall off. At **1.0** it overshoots, swings back a little, and settles within about a second and a half. At **6.0** it never settles: by the time the 40 ms loop and the slow motors have acted on a reading, the robot has already crossed the line, so it overcorrects the other way, forever. That wobble is the oscillation from the top of the lesson, now with a cause you can tune.

:::warning
**Three bugs that break state machines and timers.**
1. **Calling `enterState()` every pass.** Writing `enterState(BACKING_UP)` inside `case BACKING_UP:` resets the stopwatch each loop, so `inState` never reaches 400 and the robot backs up forever. Only call it when the state *changes*.
2. **Storing `millis()` in an `int`.** On an Uno an `int` holds up to 32,767, so after about 33 seconds the timer goes negative and comparisons fail. Use `unsigned long`.
3. **Writing `if (millis() > start + 500)`.** It looks the same as the subtraction, but it fails when the clock wraps. Always write `millis() - start >= 500`.
:::

:::quiz
Q: Inside `case TURNING:` someone adds `enterState(TURNING);` on the first line. What happens?
- [ ] Nothing; entering the state you're already in is harmless
  It isn't harmless here, because `enterState` also restarts the state's stopwatch.
- [x] The robot spins forever
  `stateStart` is reset every pass, so `inState >= 500` is never true and the exit rule can't fire.
- [ ] The robot leaves TURNING immediately
  Resetting the timer delays the exit; it never speeds it up.

Q: A line follower with `KP = 6` wobbles across the line nonstop. Which change is most likely to calm it?
- [x] Lower `KP`, or make the loop run more often
  The wobble comes from overcorrecting on stale information. Less gain, or fresher information, both reduce the overshoot.
- [ ] Raise `KP` so it corrects faster
  More gain makes each overcorrection bigger.
- [ ] Add `delay(100)` so the motors have time to respond
  A delay makes the information older still, which makes the wobble worse.

Q: With "turn below 20 cm, drive again above 35 cm", the robot is TURNING and readings arrive: 22, 30, 34, 36. On which reading does it go back to DRIVING (ignoring the minimum turn time)?
- [ ] 22
  22 is above 20, but the exit rule needs more than 35.
- [ ] 34
  Close, but 34 is not above 35.
- [x] 36
  It's the first reading past the exit threshold. The gap between 20 and 35 is the hysteresis.
:::

:::takeaways
- Code that decides from scratch on every reading twitches near thresholds. States give the robot a memory.
- `delay()` blinds the robot. Use `unsigned long` timestamps and `millis() - start >= interval`.
- Draw the state diagram first; then code it as an `enum`, a `switch`, and an `enterState()` that resets the state's timer.
- Hysteresis uses one threshold to enter a state and a different one to leave it.
- A P controller corrects in proportion to the error. Too little gain is sluggish; too much, plus delay, oscillates.
:::
