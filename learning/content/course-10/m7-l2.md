:::objectives
- Build a logging harness that records raw and filtered readings with timestamps.
- Use known slider distances to find and fix a systematic error.
- Inject missed echoes, spikes, and phantom readings on purpose with a switch.
- Implement a median-of-5 filter, test it against pass criteria, and measure the delay it adds.
:::

Wokwi's HC-SR04 is a perfect sensor: set the slider to 100 cm and it answers 100 cm forever. Real ones miss echoes off angled walls, catch a stray echo from across the room, and occasionally report something 4 cm away that isn't there. Code tested only against a perfect sensor fails on its first real floor.

So this lesson builds a **test harness**: a small sketch whose whole job is to exercise one part of the robot, the distance reading, and print evidence. By the end, a slide switch injects realistic faults, and a filter you've tested handles them.

## Step 2: Log first, and let the log find a bug

Before filtering anything, log the raw reading next to the time. Here's the reading function exactly as the door used it, plus a CSV line every 60 ms:

```arduino
const int TRIG = 10;
const int ECHO = 11;
const unsigned long SAMPLE_MS = 60;
unsigned long lastSample = 0;

long readRawCm() {
  digitalWrite(TRIG, LOW);
  delayMicroseconds(2);
  digitalWrite(TRIG, HIGH);
  delayMicroseconds(10);
  digitalWrite(TRIG, LOW);
  unsigned long duration = pulseIn(ECHO, HIGH, 30000UL);
  if (duration == 0) return -1;              // -1 means "no echo"
  return duration * 0.0343 / 2;
}

void setup() {
  pinMode(TRIG, OUTPUT);
  pinMode(ECHO, INPUT);
  Serial.begin(115200);
  Serial.println("ms,raw");
}

void loop() {
  unsigned long now = millis();
  if (now - lastSample < SAMPLE_MS) return;
  lastSample = now;
  Serial.print(now);
  Serial.print(',');
  Serial.println(readRawCm());
}
```

Now run a mini calibration: set the slider to 30, 100, and 250 cm and note what the log says at each. You'll likely see readings a little **under** the slider, such as 29 for 30. Wokwi's docs give its echo as about 58 µs per centimeter, so 30 cm makes a pulse near 1,740 µs, and 1,740 × 0.0343 / 2 = 29.84. Converting that to `long` throws away the .84, so the log says 29.

That's a **systematic error**: the same direction every time, so averaging won't remove it. Rounding does. This version stays in whole numbers (cheap on an Uno) and adds half a unit before dividing:

```arduino
return (duration * 343UL + 10000UL) / 20000UL;   // = duration * 0.0343 / 2, rounded
```

Rerun the three distances. The readings should now land within a centimeter of the slider. If 250 still shows 249, that's a different, smaller error: 58 µs per centimeter corresponds to sound at about 345 m/s, slightly faster than the 343 in our formula. That's a slope error, the kind the calibration fit in the notes removes.

## Step 3: Inject faults on purpose

Real sensors fail in three typical ways, so the harness fakes all three when the switch is on:

```arduino
const int FAULT_SWITCH = 4;

long injectFault(long cm) {
  int roll = random(100);                       // 0..99
  if (roll < 5) return -1;                      // 5%: missed echo
  if (roll < 9) return cm + random(50, 200);    // 4%: spike from a far echo
  if (roll < 11) return random(3, 10);          // 2%: phantom close object
  return cm;                                    // 89%: the truth
}
```

Add `pinMode(FAULT_SWITCH, INPUT_PULLUP);` to `setup()`. Slide the switch right and watch the raw column: mostly 100, with the occasional -1, 213, or 6. That's ugly, but it's honest, and a robot that brakes for every 6 will stutter across the room.

## Step 4: A median filter

Earlier in the course you smoothed readings with a moving average. An average **dilutes** a spike: one reading of 250 among four 100s averages to 130, which is still wrong. A **median** sorts the window and takes the middle value, so a single wild reading lands at one end of the list and is simply ignored.

```arduino
long history[5] = {-1, -1, -1, -1, -1};   // -1 = empty or no echo
int nextSlot = 0;

long medianCm() {
  long sorted[5];
  int n = 0;
  for (int i = 0; i < 5; i++) {
    if (history[i] >= 0) sorted[n++] = history[i];   // skip missed echoes
  }
  if (n == 0) return -1;                             // nothing valid at all
  for (int i = 1; i < n; i++) {                      // insertion sort: fine for 5 items
    long value = sorted[i];
    int j = i - 1;
    while (j >= 0 && sorted[j] > value) {
      sorted[j + 1] = sorted[j];
      j--;
    }
    sorted[j + 1] = value;
  }
  return sorted[n / 2];
}
```

Each sample goes into `history[nextSlot]`, and `nextSlot = (nextSlot + 1) % 5` wraps around, so the array always holds the latest five. Missed echoes are skipped instead of counted as 0, which would drag the median toward "obstacle!".

Before trusting it, test the idea in Python with the same fault rates, against a distance that jumps from 100 to 40 cm (someone stepping in front of the robot):

```python run alt="Raw readings at 100 then 40 centimeters with scattered spikes above 200 and phantom readings near 5; the 5-sample mean jumps by up to about 35 centimeters; the 5-sample median stays flat at 100 then 40, switching two samples after the step" caption="The mean is dragged by every spike. The median ignores them, at the cost of a short delay."
import random
import matplotlib.pyplot as plt

random.seed(5)
SAMPLE_MS = 60
truth = [100] * 120 + [40] * 120

def inject_fault(cm):
    roll = random.randrange(100)
    if roll < 5:
        return -1
    if roll < 9:
        return cm + random.randrange(50, 200)
    if roll < 11:
        return random.randrange(3, 10)
    return cm

raw = [inject_fault(cm) for cm in truth]
median, mean = [], []
for i in range(len(raw)):
    window = [r for r in raw[max(0, i - 4): i + 1] if r >= 0]
    median.append(sorted(window)[len(window) // 2])
    mean.append(sum(window) / len(window))

settled = [i for i in range(len(truth)) if i % 120 >= 5]   # skip 5 samples after each change
for name, series in [("raw", raw), ("mean", mean), ("median", median)]:
    worst = max(abs(series[i] - truth[i]) for i in settled if series[i] >= 0)
    print(f"{name:6s} worst error: {worst:5.1f} cm")
lag = next(i for i in range(120, len(median)) if all(m == 40 for m in median[i:i + 5])) - 120
print(f"median lag after the step: {lag} samples = {lag * SAMPLE_MS} ms")

times = [i * SAMPLE_MS / 1000 for i in range(len(raw))]
plt.figure(figsize=(8, 4))
plt.plot(times, [r if r >= 0 else None for r in raw], ".", color="#adb5bd", label="raw")
plt.plot(times, mean, color="#e8590c", label="mean of 5")
plt.plot(times, median, color="#7892ee", linewidth=2, label="median of 5")
plt.xlabel("time (s)")
plt.ylabel("distance (cm)")
plt.legend()
```

Two results. The median's worst error in the steady parts is zero, while the mean's is tens of centimeters. And the median takes a couple of samples to accept the new distance, because the old value is still the majority. At 60 ms per sample that's roughly 120 to 180 ms, or about 5 cm of travel at 30 cm/s. Filters always trade noise for delay; now you know the price.

## The finished harness

```arduino
const int TRIG = 10;
const int ECHO = 11;
const int FAULT_SWITCH = 4;          // slide right = inject faults
const unsigned long SAMPLE_MS = 60;
const bool LOGGING = true;

long history[5] = {-1, -1, -1, -1, -1};
int nextSlot = 0;
unsigned long lastSample = 0;

long readRawCm() {
  digitalWrite(TRIG, LOW);
  delayMicroseconds(2);
  digitalWrite(TRIG, HIGH);
  delayMicroseconds(10);
  digitalWrite(TRIG, LOW);
  unsigned long duration = pulseIn(ECHO, HIGH, 30000UL);
  if (duration == 0) return -1;
  return (duration * 343UL + 10000UL) / 20000UL;
}

long injectFault(long cm) {
  int roll = random(100);
  if (roll < 5) return -1;
  if (roll < 9) return cm + random(50, 200);
  if (roll < 11) return random(3, 10);
  return cm;
}

long medianCm() {
  long sorted[5];
  int n = 0;
  for (int i = 0; i < 5; i++) {
    if (history[i] >= 0) sorted[n++] = history[i];
  }
  if (n == 0) return -1;
  for (int i = 1; i < n; i++) {
    long value = sorted[i];
    int j = i - 1;
    while (j >= 0 && sorted[j] > value) {
      sorted[j + 1] = sorted[j];
      j--;
    }
    sorted[j + 1] = value;
  }
  return sorted[n / 2];
}

void setup() {
  pinMode(TRIG, OUTPUT);
  pinMode(ECHO, INPUT);
  pinMode(FAULT_SWITCH, INPUT_PULLUP);
  randomSeed(analogRead(A5));        // varies on real hardware; Wokwi may repeat it
  Serial.begin(115200);
  Serial.println("ms,faults,raw,filtered");
}

void loop() {
  unsigned long now = millis();
  if (now - lastSample < SAMPLE_MS) return;
  lastSample = now;

  bool faults = digitalRead(FAULT_SWITCH) == LOW;
  long raw = readRawCm();
  if (faults && raw >= 0) raw = injectFault(raw);

  history[nextSlot] = raw;
  nextSlot = (nextSlot + 1) % 5;
  long filtered = medianCm();

  if (LOGGING) {
    Serial.print(now);
    Serial.print(',');
    Serial.print(faults ? 1 : 0);
    Serial.print(',');
    Serial.print(raw);
    Serial.print(',');
    Serial.println(filtered);
  }
}
```

With faults on and the slider at 100, the log looks like this; the filtered column holds steady while the raw one misbehaves:

```text

4080,1,100,100
4140,1,-1,100
4200,1,100,100
4260,1,231,100
4320,1,100,100
4380,1,6,100
```

## Step 5: Run the harness tests

A harness earns its keep when the tests have pass criteria written down before you run them:

| ID | Setup | Pass if |
| --- | --- | --- |
| H1 | Faults off; slider at 30, 100, 250 | `filtered` is within 1 cm of the slider at each distance |
| H2 | Faults on; slider at 100 for 30 s | `filtered` never leaves 100 |
| H3 | Faults on; slider at 4 cm | `filtered` stays near 4 even though phantoms read 3 to 9 |
| H4 | Faults off; jump the slider from 100 to 40 | `filtered` reaches 40 within 3 samples |
Write down what these tests *can't* catch, too. Every fault here comes from `injectFault()`, so H2 and H3 prove the filter handles the faults you imagined, at the rates you chose. Whether a real sensor facing a chair leg behaves like that is a question only real hardware (or a wider fault model) can answer. On a real Uno, `randomSeed(analogRead(A5))` gives a different fault pattern each run; in Wokwi the unconnected pin may read the same every time, which conveniently makes a failing run repeatable.

:::quiz
Q: Why does `medianCm()` skip readings of -1 instead of sorting them in with the rest?
- [ ] Sorting can't handle negative numbers
  Insertion sort handles negatives fine.
- [x] A missed echo isn't a distance; counted as a value, a few of them would drag the median toward "something is very close"
  -1 sorts to the bottom of the list, so two or three missed echoes would pull the middle value down toward an obstacle that isn't there.
- [ ] To make the filter faster
  The speed difference for five items is negligible; the reason is correctness.

Q: Every log line reads exactly 1 cm less than the slider. Which fix addresses the cause?
- [ ] Use a median of 9 instead of 5
  A median removes random outliers, not an error that's the same every time.
- [x] Round the conversion instead of truncating it
  The error comes from dropping the fraction when converting to `long`, which always rounds down.
- [ ] Sample every 30 ms instead of 60 ms
  More samples of the same biased number are still biased.

Q: The median adds about 150 ms of delay. When would that matter most?
- [x] When the robot drives fast toward an obstacle and must brake at a fixed distance
  At higher speed the robot covers more ground during the delay, so it reacts later. Brake earlier, or drive slower near obstacles.
- [ ] When the robot is stopped
  A stopped robot isn't covering distance during the delay.
- [ ] Never, because 150 ms is too short to notice
  At 50 cm/s, 150 ms is 7.5 cm, which can be the difference between stopping and touching.
:::

:::takeaways
- Log first: a timestamped CSV of raw values exposes systematic errors like truncation.
- A systematic error needs a correction (here, rounding); random errors need filtering.
- Inject the faults the simulator doesn't produce: missed echoes, spikes, phantoms.
- A median of 5 removes single outliers that an average only dilutes, and costs a few samples of delay.
- Write pass criteria before running tests, and note what a test can't catch.
:::
