## Warm-up: duty cycle in your head

Before running this, guess the average voltage for `analogWrite` values 64, 128, and 191 on a 6 V motor supply.

```python run
supply = 6.0
for value in [0, 64, 128, 191, 255]:
    duty = value / 255
    print(f"analogWrite {value:3d}: {duty:6.1%} duty, about {duty * supply:.2f} V average")
```

A quarter, a half, three quarters: 255 is the full scale, so dividing by 255 gives the fraction of time the pin is on.

### Exercise 1: Read the driver like a truth table

An L298N channel has ENA, IN1, and IN2. For each row, say what the motor does: forward, reverse, brake, or coast.

| | ENA | IN1 | IN2 |
| --- | --- | --- | --- |
| a | 200 | LOW | HIGH |
| b | 0 | HIGH | LOW |
| c | 255 | LOW | LOW |
| d | 90 | HIGH | LOW |

:::hint
ENA decides whether the bridge is connected at all. If it is, compare IN1 and IN2: different means spin, the same means brake.
:::

:::solution
| | Result | Why |
| --- | --- | --- |
| a | Reverse, fairly fast | IN1 LOW, IN2 HIGH is reverse; 200/255 is about 78% duty. |
| b | Coast | ENA = 0 disconnects the motor, whatever the IN pins say. |
| c | Brake | IN1 equals IN2 with the bridge enabled, so both terminals are tied together. |
| d | Forward, slowly, or not at all | 90 is about 35% duty; on a weak battery that may sit in the dead zone. |
:::

### Exercise 2: Skip the dead zone

Your motor doesn't turn below `analogWrite` 70. Write `scaledPwm(percent)` so that 0% gives 0 (stopped), and 1% to 100% spread evenly across 70 to 255. Sample output:

```text
0% -> 0
1% -> 70
50% -> 162
100% -> 255
```

:::hint
Treat 0 as a special case. For everything else, the range 1..100 maps onto 70..255: start at 70 and add a fraction of the 185 counts left.
:::

:::solution
Test the arithmetic in Python first:

```python run
def scaled_pwm(percent):
    if percent <= 0:
        return 0
    percent = min(percent, 100)
    return round(70 + (percent - 1) * (255 - 70) / 99)

for p in [0, 1, 25, 50, 100, 120]:
    print(f"{p}% -> {scaled_pwm(p)}")
```

Then the Arduino version. `map()` uses whole-number math, which is fine here:

```arduino
int scaledPwm(int percent) {
  if (percent <= 0) return 0;
  percent = constrain(percent, 1, 100);
  return map(percent, 1, 100, 70, 255);
}
```

`map()` rounds down rather than to the nearest value, so a few results differ from Python by 1. A wheel will never notice.
:::

### Exercise 3: Will the battery last, and can it cope?

A two-wheel robot runs from 4 × AA NiMH cells rated 2000 mAh. Use Adafruit's measurements for TT motors at 4.5 V (155 mA running, 1.2 A stalled), and assume a micro servo draws 250 mA while moving and the Arduino plus sensor draw 60 mA. Find:

1. The current while driving with the servo moving.
2. The worst case: both wheels stalled against a wall, servo moving.
3. Runtime at the driving current, if only 80% of the rated capacity is usable.

:::hint
Currents add. Runtime in hours is usable mAh divided by mA.
:::

:::solution
```python run alt="Bar chart: driving draws 620 milliamps, the stalled worst case draws 2710 milliamps, with a dashed line marking the 500 milliamp USB limit" caption="Two operating points against the USB port's 500 mA"
import matplotlib.pyplot as plt

motor_running, motor_stalled = 155, 1200   # mA each, TT motor at 4.5 V
servo_moving = 250
arduino_and_sensor = 60
capacity_mah = 2000 * 0.8                  # usable part of the rated capacity

driving = 2 * motor_running + servo_moving + arduino_and_sensor
worst = 2 * motor_stalled + servo_moving + arduino_and_sensor
hours = capacity_mah / driving

print("Driving:", driving, "mA")
print("Worst case:", worst, "mA")
print(f"Runtime while driving: {hours:.1f} h (about {hours * 60:.0f} minutes)")

plt.bar(["driving", "both wheels stalled"], [driving, worst], color=["#7892ee", "#e8590c"])
plt.axhline(500, color="black", linestyle="--", label="USB port limit, 500 mA")
plt.ylabel("current (mA)")
plt.legend()
```

The worst case is more than five times what a USB port supplies. That's the numerical case for a separate motor battery, and for code that stops the motors when the robot stops moving.
:::

### Exercise 4: Find the wiring faults

Maya's robot resets every time the motors start, and the motor speed never changes no matter what `analogWrite()` she sends. Her wiring:

- The L298N motor-supply terminal is wired to the Arduino's 5 V pin.
- The L298N's GND goes to the battery's negative terminal only.
- ENA goes to Arduino pin 10, and the ENA jumper is still on the board.
- A servo on pin 9 uses the `Servo` library.
- On her test bench, a third motor is switched by a single transistor with nothing across the motor.

Find at least four problems and the fix for each.

:::hint
Sort the symptoms: resets point to power, "speed never changes" points to the speed pin. Then look for anything missing that protects a transistor.
:::

:::solution
1. **Motors powered from the Arduino's 5 V pin.** The surge drags the Arduino's supply down and it resets. Wire a battery pack to the driver's motor-supply terminal.
2. **No shared ground.** Add a wire from Arduino GND to the driver's GND.
3. **ENA jumper still on.** It holds ENA at 5 V (full speed). Remove it.
4. **ENA on pin 10 with the Servo library.** PWM is disabled on pins 9 and 10. Move ENA to pin 5 or 6.
5. **No flyback diode on the transistor circuit.** Add a diode across the motor, stripe toward the positive supply, so switch-off spikes don't destroy the transistor.
:::

:::video 6R_3jHeimiE
What to watch for: what the motor's voltage does at the instant the switch opens, with and without the flyback diode (fault 5 above).
:::

### Exercise 5: A servo with safe limits

A servo aims an ultrasonic sensor, but the bracket hits the chassis below 30° and above 150°. Read a potentiometer on A0 and point the servo, never leaving 30..150. Print the angle when it changes.

```text
Angle: 90
Angle: 112
Angle: 150
```

:::hint
`map()` the reading to 30..150 directly, or map to 0..180 and then `constrain()`. Which one keeps the full knob travel useful?
:::

:::solution
```arduino
#include <Servo.h>

const int KNOB = A0;
const int MIN_ANGLE = 30;
const int MAX_ANGLE = 150;

Servo turret;
int lastAngle = -1;

void setup() {
  turret.attach(9);
  Serial.begin(115200);
}

void loop() {
  int angle = map(analogRead(KNOB), 0, 1023, MIN_ANGLE, MAX_ANGLE);
  angle = constrain(angle, MIN_ANGLE, MAX_ANGLE);   // belt and braces
  if (angle != lastAngle) {
    turret.write(angle);
    Serial.print("Angle: ");
    Serial.println(angle);
    lastAngle = angle;
  }
  delay(20);
}
```

Mapping straight to 30..150 uses the whole knob for the safe range. The `constrain()` looks redundant, but it guards against a later edit to the `map()` line. Printing only on change keeps the Serial Monitor readable.
:::

### Exercise 6: Two motors, one vocabulary

Add a second channel (ENB on pin 6, IN3 on pin 4, IN4 on pin 3). Write `drive(left, right)` that takes two signed speeds, then three helpers built on it: `forward(speed)`, `spinLeft(speed)` (wheels in opposite directions), and `stopAll()`.

:::hint
Write one function that takes the three pin numbers and a speed, then call it twice. Spinning left means the left wheel goes backward.
:::

:::solution
```arduino
const int ENA = 5, IN1 = 7, IN2 = 8;   // left motor
const int ENB = 6, IN3 = 4, IN4 = 3;   // right motor

void setChannel(int en, int a, int b, int speed) {
  speed = constrain(speed, -255, 255);
  digitalWrite(a, speed > 0 ? HIGH : LOW);
  digitalWrite(b, speed < 0 ? HIGH : LOW);
  analogWrite(en, abs(speed));
}

void drive(int left, int right) {
  setChannel(ENA, IN1, IN2, left);
  setChannel(ENB, IN3, IN4, right);
}

void forward(int speed)  { drive(speed, speed); }
void spinLeft(int speed) { drive(-speed, speed); }
void stopAll()           { drive(0, 0); }

void setup() {
  int pins[] = {ENA, IN1, IN2, ENB, IN3, IN4};
  for (int i = 0; i < 6; i++) pinMode(pins[i], OUTPUT);
  stopAll();
}

void loop() {
  forward(180);  delay(1500);
  spinLeft(150); delay(800);
  stopAll();     delay(1000);
}
```

`setChannel` packs the H-bridge logic into two lines: IN-a is HIGH only for positive speeds, IN-b only for negative ones, and both stay LOW at zero. With LEDs on all six pins in Wokwi, `spinLeft` lights IN2 and IN3 together.
:::

### Challenge: Joystick arcade drive

Drive both motors from Wokwi's analog joystick: up/down is throttle, left/right is turning. Wokwi's docs say VERT goes from 0 (bottom) to 1023 (top), and HORZ goes from 0 (**right**) to 1023 (left). Its joystick only moves fully to each side, so test the corners and edges.

The standard mix is `left = throttle + turn` and `right = throttle - turn`. The catch: full throttle plus full turn gives 510, and `constrain` would chop it to 255 and change the turn. Scale both wheels down by the same factor instead.

```mermaid caption="Arcade mixing: combine, then scale both wheels together so their ratio survives"
flowchart LR
    V["VERT 0..1023"] --> T["throttle -255..255"]
    H["HORZ 0..1023, left is high"] --> R["turn -255..255, right is positive"]
    T --> M["left = throttle + turn, right = throttle - turn"]
    R --> M
    M --> Q{"either above 255?"}
    Q -->|yes| S["multiply both by 255 / biggest"]
    Q -->|no| D["drive(left, right)"]
    S --> D
```

:::hint
Find `biggest = max(abs(left), abs(right))`. If it's over 255, multiply both by `255.0 / biggest`. Check the math in Python before writing C++.
:::

:::solution
```python run
def mix(throttle, turn):
    left, right = throttle + turn, throttle - turn
    biggest = max(abs(left), abs(right))
    if biggest > 255:
        left = round(left * 255 / biggest)
        right = round(right * 255 / biggest)
    return left, right

for throttle, turn in [(255, 0), (0, 255), (255, 255), (255, -255), (-255, 255), (128, 64)]:
    left, right = mix(throttle, turn)
    print(f"throttle {throttle:4d}, turn {turn:4d} -> left {left:4d}, right {right:4d}")
```

Full forward plus full right gives (255, 0): a pivot around the right wheel. Turn alone gives a spin in place. The Arduino version reads the joystick and reuses `drive()` from Exercise 6:

```arduino
void arcadeDrive(int vert, int horz) {
  long throttle = map(vert, 0, 1023, -255, 255);
  long turn = map(horz, 0, 1023, 255, -255);       // HORZ is high on the left
  long left = throttle + turn;
  long right = throttle - turn;
  long biggest = max(abs(left), abs(right));
  if (biggest > 255) {
    left = left * 255 / biggest;
    right = right * 255 / biggest;
  }
  drive(left, right);
}
```

The `long` type matters: on an Uno an `int` tops out at 32,767, and `510 * 255` is 130,050.
:::
