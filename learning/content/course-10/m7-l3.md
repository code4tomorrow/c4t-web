## Warm-up: echo time and distance

Sound travels about 0.0343 cm per microsecond, and the echo time covers the trip there and back. Predict the first number before you run this.

```python run
SPEED = 0.0343   # cm per microsecond at about 20 °C

def echo_us(cm):
    return cm * 2 / SPEED

def distance_cm(us):
    return us * SPEED / 2

print(f"25 cm   -> echo of {echo_us(25):.0f} µs")
print(f"1500 µs -> {distance_cm(1500):.1f} cm")
print(f"400 cm  -> echo of {echo_us(400):.0f} µs (the sensor's maximum range)")
```

The last line explains the `30000UL` timeout used throughout this course: an echo from anything within the sensor's 4 m range arrives within about 23,300 µs, so waiting 30,000 µs is enough, and waiting longer only freezes the robot.

### Exercise 1: The cold gym problem

Your code assumes sound travels at 343 m/s, its speed at about 20 °C. The speed changes with air temperature by roughly `331.3 + 0.606 × T` m/s (T in °C). A target is exactly 100 cm away. What does the robot report at 5 °C and at 35 °C? Then write an Arduino function that takes the temperature into account.

:::hint
The sensor measures time. The real time is distance divided by the real speed; the code then multiplies that time by the speed it *assumes*.
:::

:::solution
```python run
ASSUMED = 343.0

def reported(true_cm, temp_c):
    actual = 331.3 + 0.606 * temp_c
    return true_cm * ASSUMED / actual

for temp in [5, 20, 35]:
    print(f"{temp:2d} °C: robot reports {reported(100, temp):.1f} cm for a 100 cm target")
```

Cold air is slower, so echoes take longer and the robot thinks things are farther away: a robot that brakes at "20 cm" touches a little sooner in a cold gym. If you have a temperature sensor, use the real speed:

```arduino
float distanceCm(unsigned long echoUs, float tempC) {
  float cmPerUs = (331.3 + 0.606 * tempC) / 10000.0;   // m/s to cm/µs
  return echoUs * cmPerUs / 2;
}
```

Dividing by 10,000 converts m/s to cm/µs (100 cm per meter, 1,000,000 µs per second).
:::

### Exercise 2: A test plan for a line follower

Write at least six tests for a two-sensor line follower. Include at least two edge cases, and give every test a pass criterion you could check with a stopwatch, a ruler, or the log.

:::hint
Vary one thing per test: the track shape (straight, gentle curve, sharp corner, gap), the lighting, the starting position, and the battery. A sharp corner and a gap in the line are classic edge cases.
:::

:::solution
| ID | Setup | Pass if |
| --- | --- | --- |
| L1 | Straight line, start centered, room lights | Completes 1 m without either sensor reading "off line" for over 200 ms |
| L2 | Start 2 cm off center | Back on the line (error under 10) within 0.5 s |
| L3 | Gentle curve, 30 cm radius | Completes it with no SEARCHING state in the log |
| L4 | Sharp 90-degree corner (edge case) | Enters SEARCHING at most once, and is FOLLOWING again within 1.5 s |
| L5 | 3 cm gap in the line (edge case) | Crosses the gap and is FOLLOWING on the far side |
| L6 | Bright sunlight on half the track | Same as L1, after re-running calibration |
| L7 | Battery after 20 minutes | Same as L3 |
| L8 | Line removed entirely | Reaches STOPPED within 3.5 s and stays there |

L8 tests the failure path on purpose: a robot that keeps searching forever is a robot driving off a table.
:::

### Exercise 3: Find the flip-flop bursts

Write `find_bursts(rows, window_ms=500, min_changes=3)` that returns the start time of every burst: a stretch where the state changed at least `min_changes` times within `window_ms`. Test it on this log.

```text
Bursts start at: [700, 3300]
```

:::hint
First build the list of times when the state changed. Then, for each change, count how many changes (including itself) fall within the next `window_ms`. Skip changes that belong to a burst you already reported.
:::

:::solution
```python run
log = """ms,state
0,DRIVING
500,DRIVING
700,TURNING
800,DRIVING
900,TURNING
1000,DRIVING
1500,DRIVING
2500,BACKING_UP
2800,TURNING
3300,DRIVING
3400,TURNING
3500,DRIVING
3600,TURNING
4200,DRIVING"""

def find_bursts(rows, window_ms=500, min_changes=3):
    change_times = [int(b[0]) for a, b in zip(rows, rows[1:]) if a[1] != b[1]]
    bursts, covered_until = [], -1
    for i, start in enumerate(change_times):
        if start <= covered_until:
            continue
        inside = [t for t in change_times[i:] if t - start <= window_ms]
        if len(inside) >= min_changes:
            bursts.append(start)
            covered_until = inside[-1]
    return bursts

rows = [line.split(",") for line in log.splitlines()[1:]]
print("Bursts start at:", find_bursts(rows))
```

The BACKING_UP and TURNING changes at 2500 and 2800 are only 300 ms apart, but that's the robot doing its job, not flip-flopping: only two changes, below the threshold. Tuning `min_changes` and `window_ms` decides what "suspicious" means for your robot.
:::

### Exercise 4: Two sensors that disagree

A robot sits perfectly centered over the line, yet the raw readings say left 500, right 570, so the P controller steers. Calibration sweeps measured left: white 180, black 820; right: white 240, black 900. Normalize both to 0..1000 and recompute the error.

:::hint
Normalized = (raw − white) / (black − white) × 1000. Do it for each sensor with its own white and black.
:::

:::solution
```python run
cal = {"left": (180, 820), "right": (240, 900)}

def normalize(raw, side):
    white, black = cal[side]
    raw = max(white, min(black, raw))
    return round((raw - white) * 1000 / (black - white))

left, right = 500, 570
print("raw error:", right - left)
left_n, right_n = normalize(left, "left"), normalize(right, "right")
print("normalized:", left_n, right_n, " error:", right_n - left_n)
```

The raw error of 70 was a difference between the two sensors, not between the sensors and the line. After normalizing, both read halfway between white and black and the error is zero. On the Arduino it's one line per sensor: `map(constrain(raw, white, black), white, black, 0, 1000)`.
:::

### Exercise 5: The one-second freeze

This robot runs smoothly until its ECHO wire works loose on a bumpy floor. Then it lurches: frozen for about a second, a sudden stop, frozen again. A loose wire is a hardware fault, but the code turns it into something much worse. Find both problems in the reading function.

```arduino
long readDistanceCm() {
  digitalWrite(TRIG, HIGH);
  delayMicroseconds(10);
  digitalWrite(TRIG, LOW);
  long duration = pulseIn(ECHO, HIGH);
  return duration * 0.0343 / 2;
}
```

:::hint
With the wire loose, ECHO never goes HIGH. How long does `pulseIn()` wait by default, what does it return when it gives up, and what does the robot do with that number?
:::

:::solution
1. **No timeout.** With no pulse arriving, `pulseIn()` waits for its default timeout of one second, and the whole loop freezes with it. Pass a timeout: `pulseIn(ECHO, HIGH, 30000UL)`.
2. **Timeouts become 0 cm.** `pulseIn()` returns 0 when it gives up, and this function turns that into "0 cm away", so after each freeze the robot brakes for an obstacle that isn't there. Return a sentinel instead:

```arduino
long readDistanceCm() {
  digitalWrite(TRIG, LOW);
  delayMicroseconds(2);
  digitalWrite(TRIG, HIGH);
  delayMicroseconds(10);
  digitalWrite(TRIG, LOW);
  unsigned long duration = pulseIn(ECHO, HIGH, 30000UL);
  if (duration == 0) return -1;      // caller decides what "no echo" means
  return (duration * 343UL + 10000UL) / 20000UL;
}
```

The `LOW` pulse first makes sure TRIG starts from a clean low level, and `unsigned long` matches what `pulseIn()` actually returns.
:::

### Exercise 6: Notice when the robot is stuck

A robot pushing against a low step that the sensor can't see keeps "driving", but its distance reading doesn't change. Write a watchdog: if the reading hasn't moved by 2 cm or more in 3 seconds of DRIVING, report STUCK. Test it in Python on a moving log and a stuck log.

```text
moving: never stuck
stuck: STUCK at 3000 ms
```

:::hint
Keep a reference reading and the time you took it. Whenever the distance has moved 2 cm or more from the reference, take a new reference. If the reference gets 3 seconds old, you're stuck.
:::

:::solution
```python run
def watchdog(samples, move_cm=2, limit_ms=3000):
    ref_cm, ref_ms = samples[0][1], samples[0][0]
    for ms, cm in samples:
        if abs(cm - ref_cm) >= move_cm:
            ref_cm, ref_ms = cm, ms          # it moved: restart the clock
        elif ms - ref_ms >= limit_ms:
            return f"STUCK at {ms} ms"
    return "never stuck"

moving = [(ms, 120 - ms * 0.02) for ms in range(0, 5000, 100)]       # closing at 20 cm/s
stuck = [(ms, 42 + (ms // 100) % 2) for ms in range(0, 5000, 100)]   # wobbles between 42 and 43
print("moving:", watchdog(moving))
print("stuck:", watchdog(stuck))
```

The Arduino version keeps the same two variables:

```arduino
if (labs(cm - refCm) >= 2) {
  refCm = cm;
  refTime = now;
} else if (now - refTime >= 3000 && cm < 150) {
  enterState(STUCK);
}
```

Notice the `cm < 150`. A robot cruising down a long, empty corridor also sees an unchanging distance (no echo, or the far wall), and without that condition it would declare itself stuck. Every watchdog needs a test for its false alarms, not just its alarms.
:::

### Challenge: Replay tests for the state machine

Testing by dragging a slider is slow, and you can't repeat it exactly. Instead, port the obstacle-avoider's transition rules to Python, then **replay** recorded distance sequences through it and compare the states it visits with what you expected. Use one reading per 60 ms and these rules: DRIVING to BACKING_UP under 20 cm; BACKING_UP to TURNING after 400 ms; TURNING to DRIVING after 500 ms once the reading is over 35 cm. Write four scenarios: a wall ahead, a noisy wall hovering at 19 to 21 cm, sensor dropouts while driving, and a robot boxed in so the path never clears. One of them will fail. Add a rule that fixes it.

```mermaid caption="Replay testing: the same recorded readings, the same rules, every time"
flowchart LR
    A["Recorded or scripted readings"] --> B["Python copy of the state rules"]
    B --> C["States visited"]
    C --> D{"Matches expected?"}
    D -->|yes| E["PASS"]
    D -->|no| F["FAIL: fix rules, then rerun all"]
```

:::hint
Represent a run by the list of *distinct* states it passed through, such as `["DRIVING", "BACKING_UP", "TURNING", "DRIVING"]`. The boxed-in robot turns forever under the original rules; what should it do instead?
:::

:::solution
```python run
def replay(readings, sample_ms=60):
    state, since, visited = "DRIVING", 0, ["DRIVING"]
    for i, cm in enumerate(readings):
        now = i * sample_ms
        in_state = now - since
        new = state
        if state == "DRIVING" and 0 <= cm < 20:
            new = "BACKING_UP"
        elif state == "BACKING_UP" and in_state >= 400:
            new = "TURNING"
        elif state == "TURNING" and in_state >= 500 and cm > 35:
            new = "DRIVING"
        elif state == "TURNING" and in_state >= 3000:
            new = "STUCK"                    # the fix: give up instead of spinning forever
        if new != state:
            state, since = new, now
            visited.append(state)
    return visited

scenarios = {
    "wall ahead": ([100, 60, 30, 18] + [16] * 7 + [25, 40, 60] + [90] * 6,
                   ["DRIVING", "BACKING_UP", "TURNING", "DRIVING"]),
    "noisy wall": ([30, 25, 21, 19, 21, 19, 22, 20, 19, 21, 20, 21],
                   ["DRIVING", "BACKING_UP", "TURNING"]),
    "dropouts": ([80, 80, -1, 80, -1, -1, 80, 80],
                 ["DRIVING"]),
    "boxed in": ([50, 30, 15] + [15] * 70,
                 ["DRIVING", "BACKING_UP", "TURNING", "STUCK"]),
}

for name, (readings, expected) in scenarios.items():
    visited = replay(readings)
    result = "PASS" if visited == expected else f"FAIL, got {visited}"
    print(f"{name:11s} {result}")
```

Without the `in_state >= 3000` rule, "boxed in" fails: the robot ends in TURNING and would spin until the battery dies. Two other details earn their place. The `0 <= cm` check makes dropouts (-1) harmless, which the "dropouts" scenario proves. And "noisy wall" checks that the robot never flips back to DRIVING while readings hover around 20 cm. On the Arduino, STUCK would stop the motors and flash an LED, waiting for a human.
:::
