## Warm-up: why the subtraction survives the wrap

An `unsigned long` counts up to 4,294,967,295 and then wraps to 0. Python's integers never wrap, so `% 2**32` imitates the Arduino. A timer starts 100 ms before the wrap, and only 10 ms have passed. Predict which check fires early.

```python run
WRAP = 2 ** 32
start = WRAP - 100            # timer started just before the wrap
now = start + 10              # only 10 ms later

elapsed = (now - start) % WRAP
deadline = (start + 300) % WRAP          # this addition wraps around to 200

print("now - start >= 300 :", elapsed >= 300)
print("now > start + 300  :", now > deadline)
```

The addition wrapped to a tiny number, so the second check fired after 10 ms instead of 300. The subtraction measured the 10 ms correctly.

### Exercise 1: Three rhythms in one loop

Blink an LED on pin 12 every 250 ms, another on pin 13 every 1000 ms, and print `alive` with the time every 5 seconds. No `delay()` anywhere.

```text
alive at 5000 ms
alive at 10000 ms
alive at 15000 ms
```

:::hint
One `unsigned long` "last time" variable per rhythm, and one `if (now - last >= interval)` block per rhythm.
:::

:::solution
```arduino
unsigned long lastFast = 0, lastSlow = 0, lastAlive = 0;

void setup() {
  pinMode(12, OUTPUT);
  pinMode(13, OUTPUT);
  Serial.begin(115200);
}

void loop() {
  unsigned long now = millis();
  if (now - lastFast >= 250) {
    lastFast += 250;
    digitalWrite(12, !digitalRead(12));
  }
  if (now - lastSlow >= 1000) {
    lastSlow += 1000;
    digitalWrite(13, !digitalRead(13));
  }
  if (now - lastAlive >= 5000) {
    lastAlive += 5000;
    Serial.print("alive at ");
    Serial.print(lastAlive);
    Serial.println(" ms");
  }
}
```

Adding the interval to `last` (rather than setting `last = now`) keeps each rhythm from drifting when a pass through `loop()` runs late.
:::

### Exercise 2: Sweep a servo without freezing

The Sweep sketch from module 5 spends 5.4 seconds of every cycle inside `delay()`. Rewrite it so the servo on pin 9 still sweeps 0° to 180° and back at one degree per 15 ms, while a button on pin 2 (to GND, `INPUT_PULLUP`) lights the LED on pin 13 the instant it's pressed.

There's no Serial output to compare. Success looks like this: the servo sweeps without pausing, and the LED follows the button with no lag at any point in the sweep.

:::hint
Keep the angle and the direction (+1 or -1) in global variables. Every 15 ms, take one step and flip the direction at either end. The button check sits outside the timer block so it runs on every pass.
:::

:::solution
```arduino
#include <Servo.h>

Servo arm;
int angle = 0;
int stepDir = 1;                 // +1 sweeping up, -1 sweeping down
unsigned long lastStep = 0;

void setup() {
  arm.attach(9);
  pinMode(2, INPUT_PULLUP);
  pinMode(13, OUTPUT);
}

void loop() {
  unsigned long now = millis();
  if (now - lastStep >= 15) {
    lastStep += 15;
    angle += stepDir;
    if (angle >= 180 || angle <= 0) {
      stepDir = -stepDir;        // bounce off the ends
    }
    arm.write(angle);
  }
  digitalWrite(13, digitalRead(2) == LOW ? HIGH : LOW);
}
```

The `for` loops are gone. Their job, remembering where the sweep is, moved into `angle` and `stepDir`, which survive between passes because they're global. That's the general recipe for turning any blocking sequence into a non-blocking one.
:::

### Exercise 3: The robot that only reverses

This robot should drive forward until something is closer than 20 cm. Instead, with nothing in front of it, it backs up from the moment it's switched on, then spins, then backs up again. The log shows `DRIVING -> TURNING` and never mentions BACKING_UP. Find the bug.

```arduino
switch (state) {
  case DRIVING:
    drive(160, 160);
    if (cm < 20) enterState(BACKING_UP);
  case BACKING_UP:
    drive(-120, -120);
    if (millis() - stateStart >= 400) enterState(TURNING);
    break;
  case TURNING:
    spinLeft(140);
    if (millis() - stateStart >= 500) enterState(DRIVING);
    break;
}
```

:::hint
Read the DRIVING case line by line and ask where execution goes after its `if`.
:::

:::solution
`case DRIVING:` has no `break`, so execution falls through into the BACKING_UP code. Every pass calls `drive(160, 160)` and then immediately `drive(-120, -120)`; the last command wins, so the wheels turn backward. The fall-through code's timer check fires too: 400 ms after the robot entered DRIVING, it calls `enterState(TURNING)` straight from DRIVING, which is why the log skips BACKING_UP. Add `break;` at the end of the DRIVING case. The compiler won't warn you, so check by eye that every `case` ends in `break`.
:::

### Exercise 4: Hysteresis for a cooling fan

A fan should switch on above 28 °C and off below 26 °C. Write `fan_state(readings)` in Python that returns the fan's state after each reading, starting OFF, and test it.

```text
26.5 OFF
27.9 OFF
28.2 ON
27.1 ON
26.4 ON
25.9 OFF
27.5 OFF
```

:::hint
Two rules, each checked only from the matching state: OFF looks for "above 28", ON looks for "below 26". Readings in between change nothing.
:::

:::solution
```python run
def fan_state(readings, on_above=28.0, off_below=26.0):
    fan, states = "OFF", []
    for temp in readings:
        if fan == "OFF" and temp > on_above:
            fan = "ON"
        elif fan == "ON" and temp < off_below:
            fan = "OFF"
        states.append(fan)
    return states

temps = [26.5, 27.9, 28.2, 27.1, 26.4, 25.9, 27.5]
for temp, state in zip(temps, fan_state(temps)):
    print(temp, state)
```

The Arduino version is the same shape:

```arduino
if (!fanOn && tempC > 28.0) fanOn = true;
else if (fanOn && tempC < 26.0) fanOn = false;
digitalWrite(FAN_PIN, fanOn ? HIGH : LOW);
```

Readings like 27.1 and 27.5 fall inside the 2-degree band, so they leave the fan as it was. That band is what stops it clicking on and off.
:::

### Exercise 5: A patrol route with a pause

Design a robot that drives a square: FORWARD for 2 s, then TURN for 0.7 s, four times, then DONE. At any time during FORWARD, an obstacle closer than 15 cm sends it to PAUSED; when the path is clear beyond 25 cm it resumes FORWARD with a fresh 2-second timer. Draw the diagram, then write the `switch`.

:::hint
Count completed sides in a variable that `TURN` increments when it finishes. DONE is reached from TURN when the count hits 4.
:::

:::solution
```mermaid caption="Patrol: four sides, with a pause that only FORWARD can trigger"
stateDiagram-v2
    [*] --> FORWARD
    FORWARD --> TURN: 2 s passed
    FORWARD --> PAUSED: obstacle under 15 cm
    PAUSED --> FORWARD: clear beyond 25 cm
    TURN --> FORWARD: 0.7 s passed and sides under 4
    TURN --> DONE: 0.7 s passed and sides reach 4
```

```arduino
enum State { FORWARD, TURN, PAUSED, DONE };
State state = FORWARD;
unsigned long stateStart = 0;
int sides = 0;

void enterState(State next) {
  state = next;
  stateStart = millis();
}

void loop() {
  long cm = readDistanceCm();
  unsigned long inState = millis() - stateStart;

  switch (state) {
    case FORWARD:
      forward(160);
      if (cm < 15) enterState(PAUSED);
      else if (inState >= 2000) enterState(TURN);
      break;
    case TURN:
      spinLeft(140);
      if (inState >= 700) {
        sides++;
        if (sides >= 4) enterState(DONE);
        else enterState(FORWARD);
      }
      break;
    case PAUSED:
      stopAll();
      if (cm > 25) enterState(FORWARD);
      break;
    case DONE:
      stopAll();
      break;
  }
}
```

The obstacle check comes before the timer check in FORWARD, so an obstacle at the 2-second mark pauses the robot rather than turning it into the obstacle. The 15/25 pair is hysteresis again.
:::

### Exercise 6: Tune the gain, then speed up the loop

Using the line-follower model from the notes, find which gain settles inside ±0.3 cm fastest with a 40 ms loop. Then run the same gains with a 10 ms loop. What happens to `Kp = 6`, and why?

:::hint
"Settled" means the offset never leaves ±0.3 cm again. Find the last moment it was outside the band.
:::

:::solution
```python run
import math

def follow_line(kp, loop_ms=40, seconds=3.0):
    dt, y, heading = 0.005, 2.5, 0.0
    v_left = v_right = 0.0
    left_pwm = right_pwm = 150
    times, offsets, next_update = [], [], 0.0
    for step in range(int(seconds / dt)):
        t = step * dt
        sensor = y + 12 * math.sin(heading)
        if t >= next_update:
            next_update += loop_ms / 1000
            error = max(-100, min(100, sensor / 3 * 100))
            left_pwm = max(0, min(255, 150 + kp * error))
            right_pwm = max(0, min(255, 150 - kp * error))
        v_left += (left_pwm / 255 * 50 - v_left) * dt / 0.1
        v_right += (right_pwm / 255 * 50 - v_right) * dt / 0.1
        heading += (v_right - v_left) / 13 * dt
        y += (v_left + v_right) / 2 * math.sin(heading) * dt
        times.append(t)
        offsets.append(sensor)
    return times, offsets

def settle_time(kp, loop_ms):
    times, offsets = follow_line(kp, loop_ms)
    outside = [t for t, o in zip(times, offsets) if abs(o) > 0.3]
    last = outside[-1] if outside else 0
    return "never" if last > times[-1] - 0.05 else f"{last:.2f} s"

print(" Kp   40 ms loop   10 ms loop")
for kp in [0.3, 0.5, 1.0, 1.5, 2.0, 3.0, 6.0]:
    print(f"{kp:4}   {settle_time(kp, 40):>9}   {settle_time(kp, 10):>9}")
```

With a 40 ms loop, `Kp = 1.0` settles fastest; at 3 it takes over two seconds, and at 6 it never settles. With a 10 ms loop, `Kp = 6` settles within about 0.6 s. The robot overcorrects when it acts on old information; a faster loop means fresher information, so it tolerates more gain. That's one more reason to keep `delay()` out of `loop()`.
:::

### Challenge: A line follower that finds its way back

On a sharp bend, both sensors can slide off the line onto white floor. A pure P controller sees zero error there and drives straight on. Add states: **FOLLOWING** (P control), **SEARCHING** (both sensors off the line for 200 ms: spin toward the side where the line was last seen), and **STOPPED** (searched for 3 s with no luck). In Wokwi, two photoresistor modules on A0 and A1 stand in for line sensors; with that module, less light gives a *higher* reading, so a dark line reads high.

:::hint
Remember the sign of the last error you computed *while the line was visible*, and use it to choose the spin direction. Inside a `case`, declaring a variable needs braces: `case FOLLOWING: { ... break; }`.
:::

:::solution
```arduino
const int LEFT_SENSOR = A0;
const int RIGHT_SENSOR = A1;
const int LINE_THRESHOLD = 600;    // above this, a sensor is over the dark line
const int BASE = 150;
const float KP = 1.0;

enum Mode { FOLLOWING, SEARCHING, STOPPED };
Mode mode = FOLLOWING;
unsigned long modeStart = 0;
unsigned long lastSeen = 0;
int lastError = 0;

void enterMode(Mode next) {
  mode = next;
  modeStart = millis();
}

void loop() {
  int left = analogRead(LEFT_SENSOR);
  int right = analogRead(RIGHT_SENSOR);
  bool lineSeen = left > LINE_THRESHOLD || right > LINE_THRESHOLD;
  unsigned long now = millis();

  switch (mode) {
    case FOLLOWING: {
      int error = (right - left) / 8;    // positive: the line is to the robot's right
      int correction = KP * error;
      drive(BASE + correction, BASE - correction);
      if (lineSeen) {
        lastSeen = now;
        lastError = error;
      } else if (now - lastSeen >= 200) {
        enterMode(SEARCHING);
      }
      break;
    }
    case SEARCHING:
      if (lastError > 0) drive(120, -120);   // line was to the right: spin right
      else drive(-120, 120);
      if (lineSeen) enterMode(FOLLOWING);
      else if (now - modeStart >= 3000) enterMode(STOPPED);
      break;
    case STOPPED:
      drive(0, 0);
      break;
  }
}
```

The 200 ms grace period keeps a single dropout from triggering a search, and `lastError` is only updated while the line is visible, so a few frames of white floor can't erase the memory of which way it went. Your `LINE_THRESHOLD` will depend on your sensors; the next module shows how to measure it instead of guessing.
