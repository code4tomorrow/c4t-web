Predict what this prints before you look at the output. Ana makes a deposit; we print Ben's history.

```python run title="shared_history.py"
class Account:
    def __init__(self, owner, history=[]):
        self.owner = owner
        self.history = history

    def deposit(self, amount):
        self.history.append(amount)


ana = Account("Ana")
ben = Account("Ben")
ana.deposit(100)
print(ben.history)
print(ana.history is ben.history)
```

Ben's history contains Ana's deposit, and the second line shows why: both accounts hold the *same* list. Nothing in the code looks shared. The bug comes from how defaults work, and fixing it starts with knowing exactly what a constructor does.

## What happens when you call a class

`Account("Ana")` does two things. First Python creates a new, empty object of that class. Then it calls `__init__` on that object with your arguments, and hands the object back to you. `__init__` doesn't create the object, it *initializes* it, which is why it must not return anything.

```mermaid caption="Calling a class: create an empty object, then initialize it"
sequenceDiagram
    participant You
    participant Account as Account class
    participant obj as new object
    You->>Account: Account("Ana", 50)
    Account->>obj: create empty object
    Account->>obj: __init__(obj, "Ana", 50)
    obj-->>Account: attributes set
    Account-->>You: the finished object
```

That makes `__init__` the one place every object passes through, so it is the right place to refuse bad input. If the constructor raises, the caller never gets an invalid object at all:

```python run raises title="validated.py"
class Account:
    def __init__(self, owner, opening_deposit=0):
        if not owner.strip():
            raise ValueError("an account needs an owner's name")
        if opening_deposit < 0:
            raise ValueError("opening deposit can't be negative")
        self.owner = owner.strip()
        self.balance = opening_deposit


print(Account("  Ana ", 50).owner)
Account("Ben", -20)
```

The first account is created and its name tidied. The second never exists.

## Defaults are evaluated once

A default value is created **once**, when Python runs the `def` line, not each time the function is called. For numbers and strings that doesn't matter, since you can't change them in place. For a list, every call that uses the default gets that one list, so every account appends to it.

The fix is to use `None` as the default and make a fresh list inside the method:

```python run title="safe_default.py"
class Account:
    def __init__(self, owner, history=None):
        self.owner = owner
        self.history = [] if history is None else list(history)

    def deposit(self, amount):
        self.history.append(amount)


ana = Account("Ana")
ben = Account("Ben")
ana.deposit(100)
print(ben.history, ana.history is ben.history)
```

`list(history)` also copies any list a caller passes in, so the account can't be changed behind its back by someone still holding the original.

## Class attributes are shared by every instance

Attributes assigned on `self` belong to one instance. Attributes written directly in the class body belong to the **class**, and every instance can read them. That suits values that are the same for everyone, like an interest rate, or a counter for handing out account numbers.

When you read `ana.rate`, Python looks on `ana` first, and if it isn't there, on the class. Step through this and watch what `ben.rate = 0.05` really does:

:::trace Class attributes, instance attributes, and a counter
```python
class Account:
    rate = 0.02
    next_number = 1

    def __init__(self, owner):
        self.owner = owner
        self.number = Account.next_number
        Account.next_number += 1

ana = Account("Ana")
ben = Account("Ben")
ben.rate = 0.05
print(ana.rate, ben.rate, Account.rate)
print(ana.number, ben.number, Account.next_number)
```
:::

When `ben.rate = 0.05` runs, `ben` gains its own `rate` attribute (it appears in his box), which hides the class value *for Ben only*. The class still says 0.02, and so does Ana. Assigning through an instance never changes the class. That is also why `__init__` writes `Account.next_number += 1`: writing `self.next_number += 1` would read the class's 1, then store 2 on that one instance, and every account would get number 1.

## Inheritance: a SavingsAccount is an Account

Sometimes a new class is a more specific version of an existing one. A savings account *is* an account: it has an owner and a balance and can be withdrawn from, but it also earns interest and limits withdrawals. **Inheritance** says that directly:

```python run title="savings.py"
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("not enough money")
        self.balance -= amount


class SavingsAccount(Account):
    def __init__(self, owner, balance=0, rate=0.02):
        super().__init__(owner, balance)
        self.rate = rate
        self.withdrawals = 0

    def withdraw(self, amount):
        if self.withdrawals == 3:
            raise ValueError("savings accounts allow 3 withdrawals a month")
        super().withdraw(amount)
        self.withdrawals += 1


s = SavingsAccount("Ana", 100)
s.withdraw(30)
print(s.balance, s.withdrawals, isinstance(s, Account))
```

`class SavingsAccount(Account)` means "start with everything `Account` has". `SavingsAccount` **overrides** `withdraw` with its own version, and inside it, `super().withdraw(amount)` runs the parent's version, so the overdraft check isn't copied. `super().__init__(owner, balance)` does the same for setup: the parent sets `owner` and `balance`, then the child adds its own attributes.

Step through it and look at the call stack while `withdraw` runs. There are two `withdraw()` frames: the savings version underneath, and `Account`'s version on top, called through `super()`. Both have the same `self`.

:::trace super() runs the parent's method on the same object
```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("not enough money")
        self.balance -= amount

        super().__init__(owner, balance)
        self.rate = rate
        self.withdrawals = 0

    def withdraw(self, amount):
        if self.withdrawals == 3:
            raise ValueError("3 withdrawals a month")
        super().withdraw(amount)
        self.withdrawals += 1

s = SavingsAccount("Ana", 100)
s.withdraw(30)
print(s.balance, s.withdrawals)
```
:::

## Composition: a Bank has accounts

Is a bank an account? No. A bank **has** accounts. That is **composition**: one object holds others as attributes and uses them. Inheritance is tempting here because it gives you methods for free, so it is worth seeing what goes wrong:

```python run title="bank_is_a_list.py"
class Account:
    def __init__(self, owner):
        self.owner = owner


class Bank(list):  # "a bank is a list of accounts"
    def total_accounts(self):
        return len(self)


bank = Bank()
bank.append(Account("Ana"))
bank.append(Account("Ben"))
bank.clear()  # inherited, and now anyone can do this
print(bank.total_accounts())
```

By inheriting from `list`, `Bank` picked up all eleven public list methods, including `clear`, `pop`, and `sort`, none of which a bank should offer. With composition, the bank keeps its list private-ish and offers only the operations that make sense:

```python run title="bank_has_accounts.py"
class Account:
    def __init__(self, owner):
        self.owner = owner


class Bank:
    def __init__(self):
        self.accounts = []

    def open_account(self, owner):
        account = Account(owner)
        self.accounts.append(account)
        return account

    def total_accounts(self):
        return len(self.accounts)


bank = Bank()
bank.open_account("Ana")
bank.open_account("Ben")
print(bank.total_accounts(), hasattr(bank, "clear"))
```

```mermaid caption="Inheritance (hollow arrow) versus composition (filled diamond)"
classDiagram
    class Account {
        +owner
        +balance
        +withdraw(amount)
    }
    class SavingsAccount {
        +rate
        +withdrawals
        +withdraw(amount)
    }
    class Bank {
        +accounts
        +open_account(owner)
    }
    Account <|-- SavingsAccount : is a
    Bank *-- Account : has many
```

A good test for inheritance is substitution: could you hand a `SavingsAccount` to any code that expects an `Account` and have it still make sense? Yes, so inheritance fits. Could you hand a `Bank` to code expecting a `list`? Technically yes, which is exactly the problem. When the honest answer is "has a", use composition.

## Mistakes to watch for

:::warning Forgetting super().__init__()
If the child's `__init__` doesn't call the parent's, the parent's attributes are never set. With `SavingsAccount.__init__` setting only `self.rate`, the first use of the balance fails with `AttributeError: 'SavingsAccount' object has no attribute 'balance'`. Call `super().__init__(...)` first.
:::

:::warning A list, dict, or set as a default argument
`def __init__(self, items=[])` shares one list between every object that uses the default. Use `items=None` and create the list inside.
:::

:::warning Updating a class attribute through self
`self.count += 1` creates an instance attribute and leaves the class's value alone. To change the shared value, write the class name: `Account.count += 1`.
:::

:::quiz
Q: `def __init__(self, tags=[])` is used to create two objects without passing `tags`. One object appends `"new"` to its tags. What do the other object's tags contain?
- [ ] `[]`, because each object runs `__init__` separately
  `__init__` does run twice, but both runs get the same default list.
- [x] `["new"]`, because the default list was created once and is shared
  The default is created when `def` runs, so every call using it gets the same list.
- [ ] An error, because lists can't be default values
  Python allows it, which is what makes the bug easy to write.

Q: The class has `rate = 0.02`. You run `a.rate = 0.1`. What is `Account.rate` now?
- [x] `0.02`
  Assigning through an instance creates an attribute on that instance only.
- [ ] `0.1`
  That would need `Account.rate = 0.1`.
- [ ] It raises `AttributeError`
  Assigning a new attribute to an instance is always allowed.

Q: A `Library` needs to store books and look them up by title. Which design fits best?
- [ ] `class Library(dict)`, so it gets lookup for free
  It also gets `clear`, `popitem`, and everything else a dict offers, which a library shouldn't expose.
- [x] A `Library` class that holds a dict of books and offers `add` and `find`
  A library has books. Composition exposes only the operations that make sense.
- [ ] `class Book(Library)`
  A book isn't a kind of library, so this inheritance is backwards.

Q: Inside `SavingsAccount.withdraw`, what does `super().withdraw(amount)` do?
- [ ] Withdraws from a separate parent object
  There is only one object. `super()` finds the parent's method, not a parent object.
- [x] Runs `Account.withdraw` on the same `self`
  It looks up the next class in line and runs its method on this same savings account.
- [ ] Calls `SavingsAccount.withdraw` again
  That would recurse forever; `super()` skips the current class.
:::

:::takeaways
- Calling a class creates an empty object, then `__init__` initializes it. Validate there and no invalid object can exist.
- Defaults are created once. Use `None` for lists, dicts, and sets, and build a fresh one inside.
- Reading an attribute checks the instance, then the class. Assigning through an instance only ever changes that instance.
- Use inheritance for "is a" (and only when a child can stand in anywhere the parent is used), with `super()` to reuse the parent's code. Use composition for "has a".
:::
