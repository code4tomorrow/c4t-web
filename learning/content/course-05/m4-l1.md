Here's the bank account from earlier modules, used carelessly. Four lines, four problems:

```python run raises title="leaky_account.py"
class Account:
    def __init__(self, owner):
        self.owner = owner
        self.balance = 0

    def deposit(self, amount):
        self.balance += amount


acct = Account("Ana")
acct.balance = -500                       # 1. nothing stops this
print(acct)                               # 2. unreadable
print(Account("Ana") == Account("Ana"))   # 3. same data, "not equal"
acct.deposit("20")                        # 4. crashes, far from the real mistake
```

The class works when used exactly as its author intended. This lesson is about the **interface**: the part of a class that other code is allowed to touch, and how to make that part hard to misuse.

## An underscore means "not part of the interface"

Python has no `private` keyword. Instead there is a convention every Python programmer follows: a name starting with one underscore, like `_balance`, is internal. Code outside the class can technically reach it, but doing so is like reaching behind the counter at a shop: nobody locks you out, and nobody promises it'll still work tomorrow.

Two leading underscores (`__pin`) trigger **name mangling**: Python renames the attribute to `_Account__pin` so a subclass can't accidentally overwrite it. It isn't security, and most code never needs it. A single underscore is the everyday tool.

## @property: an attribute that runs code

Renaming `balance` to `_balance` hides it, but callers still need to *read* the balance. A **property** gives them a read-only door. It looks like an attribute from outside but runs a method:

```python run title="read_only_balance.py"
class Account:
    def __init__(self, owner):
        self.owner = owner
        self._balance = 0

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposits must be positive")
        self._balance += amount


acct = Account("Ana")
acct.deposit(50)
print(acct.balance)       # no parentheses: it reads like an attribute
try:
    acct.balance = -500
except AttributeError as err:
    print("Refused:", err)
```

Without a setter, assignment fails. The only way to change the balance is through `deposit`, which checks its input. A property can also have a **setter** that validates new values. Step through this one and notice that `self.owner = owner` inside `__init__` runs the setter too, so the rule is enforced from the very first moment:

:::trace Assigning to a property calls its setter
```python
class Account:
    def __init__(self, owner):
        self.owner = owner
        self._balance = 0

    @property
    def owner(self):
        return self._owner

    @owner.setter
    def owner(self, name):
        name = name.strip()
        if not name:
            raise ValueError("owner can't be blank")
        self._owner = name

acct = Account("Ana")
acct.owner = "  Bea "
print(acct.owner)
```
:::

Each assignment to `acct.owner` opens an `owner()` frame on the call stack: that's the setter running. The value actually lives in `_owner`, which is why the object's box shows `_owner='Bea'`. Because callers write `acct.owner` either way, you can start with a plain attribute and turn it into a property later without changing any code that uses it.

```mermaid caption="The interface (+) is what callers use; internals (-) can change freely"

        -_owner: str
        -_balance: int
        +owner: str
        +balance: int

    }
```

## Dunder methods plug your class into Python's syntax

Methods with double underscores on both sides ("dunder" methods) are hooks that Python calls for you. `print(x)` calls `x.__str__()`, `x == y` calls `x.__eq__(y)`, `sorted(items)` uses `__lt__`, and `len(x)` calls `x.__len__()`.

```python run title="dunders.py"
class Account:
    def __init__(self, number, owner):
        self.number = number
        self.owner = owner

    def __repr__(self):
        return f"Account(number={self.number}, owner={self.owner!r})"

    def __eq__(self, other):
        if not isinstance(other, Account):
            return NotImplemented
        return self.number == other.number

    def __hash__(self):
        return hash(self.number)


a = Account(1001, "Ana")
print(a)
print([a, Account(1002, "Ben")])
print(a == Account(1001, "Ana B."), a == "Ana")
print(len({a, Account(1001, "Ana")}))
```

- `__repr__` should be unambiguous, ideally looking like code that would rebuild the object. Lists, the debugger, and the REPL all use it. If you also want a friendlier version for `print`, add `__str__`.
- `__eq__` decides what "equal" means. Two account objects are the same account when their numbers match. Returning `NotImplemented` for other types lets Python fall back sensibly, so `a == "Ana"` is just `False`.
- Defining `__eq__` switches off the default hashing, so the class can no longer go in sets or be a dict key. `__hash__` restores that, using the same field `__eq__` compares.

Ordering deserves a moment of design thought. Should accounts sort by number? By balance? There's no single obvious answer, so leave out `__lt__` and pass a `key` when you sort: `sorted(accounts, key=lambda a: a.balance)`. Books on a shelf *do* have a natural order, author and then title, so `__lt__` makes sense there:

```python run title="shelf_order.py"
class Book:
    def __init__(self, title, author):
        self.title = title
        self.author = author

    def __lt__(self, other):
        return (self.author, self.title) < (other.author, other.title)

    def __repr__(self):
        return f"{self.author}: {self.title}"


shelf = [Book("Holes", "Sachar"), Book("Dune", "Herbert"), Book("Children of Dune", "Herbert")]
print(sorted(shelf))
```

## @dataclass writes the boring parts for you

Some classes are mostly data: a transaction, a book record, a point. Writing `__init__`, `__repr__`, and `__eq__` for each is tedious and easy to get subtly wrong. The `@dataclass` decorator reads the class's annotated fields and generates those methods:

```python run title="dataclass_demo.py"
from dataclasses import dataclass, field, FrozenInstanceError


@dataclass
class Book:
    title: str
    author: str
    tags: list[str] = field(default_factory=list)


@dataclass(frozen=True)
class Transaction:
    note: str
    amount: int


b = Book("Dune", "Herbert")
b.tags.append("sci-fi")
print(b)
print(b == Book("Dune", "Herbert", ["sci-fi"]))

t = Transaction("deposit", 50)
try:
    t.amount = 5000
except FrozenInstanceError as err:
    print("Refused:", err)
```

`field(default_factory=list)` is the dataclass answer to module 3's shared-list bug: it calls `list()` fresh for every object. `frozen=True` makes instances read-only after creation, which suits records of things that already happened. `order=True` would also generate `__lt__` and friends, comparing fields in order like tuples.

Use a dataclass when the object is a bundle of values. Keep a regular class, with properties guarding the state, when there are rules to protect, like an account's balance.

## Type hints say what you mean

A **type hint** writes down what type a variable, parameter, or return value should be. It's documentation the tools can read:

```python run title="hints.py"
def deposit(balance: int, amount: int) -> int:
    return balance + amount


print(deposit(10, 5))
print(deposit.__annotations__)
print(repr(deposit("10", "5")))   # Python doesn't stop this
```

Python stores the hints but **does not enforce them** when the program runs: `deposit("10", "5")` happily glues two strings into `'105'`, and the quotes from `repr` are the only clue it isn't a number. The checking happens in your editor. In VS Code, Pylance underlines calls that don't match the hints; set **Python › Analysis: Type Checking Mode** to `basic` in Settings to see more of them. Hints you'll use often: `list[str]`, `dict[str, int]`, `tuple[int, ...]`, and `str | None` for "a string or nothing".

## Mistakes that bite

:::warning A property that reads itself
Inside `def balance(self)`, writing `return self.balance` calls the property again, which calls it again... until `RecursionError: maximum recursion depth exceeded`. The property reads the underscored name: `return self._balance`.
:::

:::warning A list as a dataclass default
`tags: list[str] = []` fails as soon as the class is defined, with `ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory`. Write `field(default_factory=list)`.
:::

:::warning Defining __eq__ and losing hashing
After adding `__eq__`, putting an object in a set raises `TypeError: unhashable type: 'Account'`. Add a `__hash__` based on the same fields `__eq__` compares, or use `@dataclass(frozen=True)`, which generates both.
:::

:::quiz
Q: `balance` is a property with no setter. What does `acct.balance = 10` do?
- [ ] Sets `_balance` to 10
  Nothing connects the assignment to `_balance` unless you write a setter that does it.
- [x] Raises `AttributeError`, because the property has no setter
  A property without a setter is read-only.
- [ ] Creates a new instance attribute that hides the property
  Properties live on the class and take priority, so the assignment is refused instead.

Q: An `Account` class defines `__eq__` comparing account numbers, but no `__hash__`. What happens with `{acct}`?
- [ ] A set with one account
  That needs a `__hash__`, which Python removed when `__eq__` was defined.
- [x] `TypeError: unhashable type: 'Account'`
  Define `__hash__` from the same field (`hash(self.number)`) to fix it.
- [ ] A set containing the account's number
  Sets store the objects themselves, not a field of them.

Q: With hints `def area(w: int, h: int) -> int`, what does `area("ab", 3)` do when the program runs?
- [ ] Raises `TypeError` because the hint says `int`
  Python doesn't check hints at runtime.
- [x] Returns `"ababab"`, because hints aren't enforced; an editor would flag it
  `"ab" * 3` is valid Python. Pylance warns you before you run it.
- [ ] Converts `"ab"` to an int first
  Hints never convert values.

Q: Which class is the best fit for `@dataclass(frozen=True)`?
- [x] A `Transaction` recording a deposit that already happened
  It's pure data that should never change, so frozen fits perfectly.
- [ ] An `Account` whose balance changes with every deposit
  Frozen objects can't change, and an account must.
- [ ] A `Bank` that opens and closes accounts
  The bank's state changes constantly; it needs methods guarding it, not frozen fields.
:::

:::takeaways
- One leading underscore marks internals. `@property` exposes them read-only, or with a setter that validates.
- Dunder methods connect your class to `print`, `==`, `sorted`, `len`, and friends. Pair `__eq__` with `__hash__`, and only add `__lt__` when there's one natural order.
- `@dataclass` generates `__init__`, `__repr__`, and `__eq__` from annotated fields. Use `field(default_factory=...)` for lists and `frozen=True` for records that must not change.
- Type hints document intent and power editor checks, but Python ignores them at runtime.
:::
