## Step 1: Look at what we're replacing

This is a typical "before" script. It works, but look at what every function needs: an index `i` into three lists that must stay perfectly in line.

```python run title="bank_lists.py"
owners = ["Ana", "Ben"]
balances = [0, 0]
histories = [[], []]


def deposit(i, amount):
    balances[i] = balances[i] + amount
    histories[i].append(("deposit", amount))


deposit(0, 120)
deposit(1, 30)
print(owners, balances, histories)
```

Adding a fourth piece of data (say, an account type) means a fourth list and edits to every function. Anyone can also write `balances[0] = -500` and nothing stops them.

## Step 2: One object per account

Start `account.py` with a class whose `__init__` sets up the three pieces of state. Every new account starts empty, with its *own* history list.

```python run title="account.py (step 2)"
class Account:
    def __init__(self, owner):
        self.owner = owner
        self.balance = 0
        self.history = []


ana = Account("Ana")
ben = Account("Ben")
ana.history.append("test entry")
print(vars(ana))
print(vars(ben))
```

Adding to `ana.history` doesn't touch `ben.history`, because `__init__` runs once per account and makes a fresh `[]` each time. Keep that in mind; module 3 shows a sneaky way to accidentally share one list between every account.

## Step 3: Deposits and withdrawals that enforce the rules

Now the methods. Each one checks its input first, then changes the balance, then records what happened. If a request is impossible, it **raises** a `ValueError` instead of quietly doing nothing.

```python run title="account.py (step 3)"
class Account:
    def __init__(self, owner):
        self.owner = owner
        self.balance = 0
        self.history = []

    def deposit(self, amount, note="deposit"):
        if amount <= 0:
            raise ValueError("deposits must be positive")
        self.balance = self.balance + amount
        self.history.append((note, amount, self.balance))

    def withdraw(self, amount, note="withdraw"):
        if amount <= 0:
            raise ValueError("withdrawals must be positive")
        if amount > self.balance:
            raise ValueError(f"{self.owner} only has ${self.balance}")
        self.balance = self.balance - amount
        self.history.append((note, -amount, self.balance))


ana = Account("Ana")
ana.deposit(120)
ana.withdraw(45)
print(ana.balance, ana.history)
```

Each history entry is a tuple: a note, the signed amount, and the balance *after* the change. Storing the running balance means a statement never has to recompute anything. Now try to overdraw:

```python run raises title="overdraw.py"
class Account:
    def __init__(self, owner):
        self.owner = owner
        self.balance = 0

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError(f"{self.owner} only has ${self.balance}")
        self.balance = self.balance - amount


Account("Ana").withdraw(500)
```

The program stops with a clear message, and the balance never went negative. A `raise` ends the method immediately, so the lines that change the balance never run. Module 5 covers catching these errors and making your own error types; for now, a crash with a good message is exactly what we want.

## Step 4: A statement the account prints about itself

Add a `statement` method. It reads the object's own state and builds a string; it changes nothing.

```python
    def statement(self):
        lines = [f"Statement for {self.owner}"]
        for note, amount, balance in self.history:
            lines.append(f"  {note:<10}{amount:>+6}   balance {balance:>4}")
        lines.append(f"Balance: ${self.balance}")
        return "\n".join(lines)
```

The format codes line the columns up: `<10` pads the note to 10 characters on the left, `>+6` right-aligns the amount in 6 characters with a `+` or `-` sign, and `>4` right-aligns the balance. Returning a string instead of printing makes the method easy to test.

## Step 5: Transfers, and why withdraw raises

A transfer is a withdrawal from one account and a deposit into another. The method takes the *other account object* as a parameter, so two objects cooperate:

```python
    def transfer(self, other, amount):
        self.withdraw(amount, note=f"to {other.owner}")
        other.deposit(amount, note=f"from {self.owner}")
```

Here is why raising matters. Suppose `withdraw` returned `False` on failure, like the version in the Notes lesson, and `transfer` forgot to check it:

```python run title="free_money.py"
class Account:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            return False
        self.balance = self.balance - amount
        return True

    def deposit(self, amount):
        self.balance = self.balance + amount

    def transfer(self, other, amount):
        self.withdraw(amount)       # the False is ignored
        other.deposit(amount)


ana = Account("Ana", 10)
ben = Account("Ben", 0)
ana.transfer(ben, 500)
print(ana.balance, ben.balance)
```

Ben received 500 dollars that never existed. A return value is easy to ignore; an exception is not. With the raising `withdraw`, the error stops `transfer` on its first line, so `other.deposit` never runs. Step through a successful transfer and watch three frames stack up, then watch both objects change:

:::trace A transfer calls withdraw on one object and deposit on another
```python
class Account:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("not enough money")
        self.balance = self.balance - amount

    def deposit(self, amount):
        self.balance = self.balance + amount

    def transfer(self, other, amount):
        self.withdraw(amount)
        other.deposit(amount)

ana = Account("Ana", 75)
ben = Account("Ben", 0)
ana.transfer(ben, 30)
print(ana.balance, ben.balance)
```
:::

Inside `transfer`, `self` is `ana` and `other` is `ben`. When `transfer` calls `self.withdraw(amount)`, a new frame opens on top with its own `self`, which is still `ana`. When it calls `other.deposit(amount)`, the new frame's `self` is `ben`. Same method code, different object.

## Step 6: Lock it in with tests

Make `test_account.py` next to `account.py`. On this page the class and tests share one block; in your project, the tests go in their own file starting with `import pytest` and `from account import Account`. `pytest.raises(ValueError)` is a check that passes only if the code inside it raises that error.

```python run title="account.py + test_account.py"
import pytest


class Account:
    def __init__(self, owner):
        self.owner = owner
        self.balance = 0
        self.history = []

    def deposit(self, amount, note="deposit"):
        if amount <= 0:
            raise ValueError("deposits must be positive")
        self.balance = self.balance + amount
        self.history.append((note, amount, self.balance))

    def withdraw(self, amount, note="withdraw"):
        if amount <= 0:
            raise ValueError("withdrawals must be positive")
        if amount > self.balance:
            raise ValueError(f"{self.owner} only has ${self.balance}")
        self.balance = self.balance - amount
        self.history.append((note, -amount, self.balance))

    def transfer(self, other, amount):
        self.withdraw(amount, note=f"to {other.owner}")
        other.deposit(amount, note=f"from {self.owner}")


def test_new_account_is_empty():
    acct = Account("Ana")
    assert acct.balance == 0
    assert acct.history == []


def test_deposit_then_withdraw():
    acct = Account("Ana")
    acct.deposit(100)
    acct.withdraw(30)
    assert acct.balance == 70


def test_cannot_overdraw():
    acct = Account("Ana")
    acct.deposit(10)
    with pytest.raises(ValueError):
        acct.withdraw(50)
    assert acct.balance == 10


def test_transfer_moves_money_both_ways():
    ana, ben = Account("Ana"), Account("Ben")
    ana.deposit(50)
    ana.transfer(ben, 20)
    assert (ana.balance, ben.balance) == (30, 20)


def test_failed_transfer_changes_nothing():
    ana, ben = Account("Ana"), Account("Ben")
    with pytest.raises(ValueError):
        ana.transfer(ben, 20)
    assert (ana.balance, ben.balance) == (0, 0)


for test in [test_new_account_is_empty, test_deposit_then_withdraw, test_cannot_overdraw,
             test_transfer_moves_money_both_ways, test_failed_transfer_changes_nothing]:
    test()
    print("passed:", test.__name__)
```

## The finished account.py

```python run title="account.py"
class Account:
    def __init__(self, owner):
        self.owner = owner
        self.balance = 0
        self.history = []

    def deposit(self, amount, note="deposit"):
        if amount <= 0:
            raise ValueError("deposits must be positive")
        self.balance = self.balance + amount
        self.history.append((note, amount, self.balance))

    def withdraw(self, amount, note="withdraw"):
        if amount <= 0:
            raise ValueError("withdrawals must be positive")
        if amount > self.balance:
            raise ValueError(f"{self.owner} only has ${self.balance}")
        self.balance = self.balance - amount
        self.history.append((note, -amount, self.balance))

    def transfer(self, other, amount):
        self.withdraw(amount, note=f"to {other.owner}")
        other.deposit(amount, note=f"from {self.owner}")

    def statement(self):
        lines = [f"Statement for {self.owner}"]
        for note, amount, balance in self.history:
            lines.append(f"  {note:<10}{amount:>+6}   balance {balance:>4}")
        lines.append(f"Balance: ${self.balance}")
        return "\n".join(lines)


if __name__ == "__main__":
    ana = Account("Ana")
    ben = Account("Ben")
    ana.deposit(120)
    ana.withdraw(45)
    ana.transfer(ben, 30)
    print(ana.statement())
    print(ben.statement())
```

The demo sits under `if __name__ == "__main__":` so it runs when you press play on `account.py`, but not when `test_account.py` imports the class.

:::quiz
Q: Why does `withdraw` raise `ValueError` instead of returning `False` when there isn't enough money?
- [ ] Exceptions run faster than return values
  Speed isn't the reason; the difference is whether the caller can ignore the failure.
- [x] A caller like `transfer` can't accidentally ignore it, so no deposit happens after a failed withdrawal
  The exception stops `transfer` before `other.deposit` runs, which is what keeps money from appearing.
- [ ] Python methods aren't allowed to return booleans
  They can; it just makes this particular failure easy to miss.

Q: Why does `transfer` call `self.withdraw(...)` instead of writing `self.balance = self.balance - amount` directly?
- [x] So the overdraft check and the history entry happen in exactly one place
  Reusing `withdraw` means every rule applies to transfers automatically, and fixing a rule fixes it everywhere.
- [ ] Because methods can't change `self.balance`
  They can; `withdraw` itself does.
- [ ] To make the code shorter
  It is shorter, but the real win is having one place that enforces the rules.

Q: Each history entry stores the balance *after* the change. What does that buy us?
- [ ] It makes deposits impossible to undo
  Storing the balance doesn't affect undoing.
- [x] `statement` can print the running balance without recomputing it
  Each line already knows the balance at that moment.
:::

:::takeaways
- An object owns its data, so adding a new piece of state is one line in `__init__`, not a new list threaded through every function.
- Methods validate first, then change state, then record. If a change is impossible, raise, so nobody can ignore the failure.
- Methods can take other objects as arguments; inside them, `self` and `other` are just two different instances.
- A test for the failure case (`test_failed_transfer_changes_nothing`) is what stops an old bug from returning.
:::
