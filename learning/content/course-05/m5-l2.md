:::objectives
- Lay out a Python package with `__init__.py`, separate modules, and a `__main__.py` entry point.
- Design an exception hierarchy where each class has one clear meaning.
- Translate low-level errors (`ValueError`, `JSONDecodeError`) into your own with `raise ... from`.
- Catch errors at the boundary of the program, and use `finally` so data is always saved.
:::

By the end of this build you'll have a small hotel booking program that you start with `python -m booking`. It books rooms, refuses double bookings, rejects nonsense dates, survives a damaged save file, and always saves on the way out. Each failure has its own exception class, and only one place in the whole program decides what to print about them.

Here is the folder you'll create, and the path an error takes when someone tries to book a taken room:

```text
hotel/
└── booking/
    ├── __init__.py    marks the folder as a package
    ├── errors.py      the exception classes (imports nothing from the app)
    ├── models.py      parse_date, Stay, Hotel
    ├── storage.py     save and load a JSON file
    └── __main__.py    the menu; the only module that talks to the user
```

Every code cell below is one file of the package, and the cells share their names like a notebook. In a real project the files find each other through `import` lines; each step tells you exactly which lines to put at the top of the file.

## Step 1: Create the package in VS Code

Open an empty folder called `hotel` in VS Code (**File › Open Folder…**). In the Explorer, use the **New Folder…** button to make `booking`, then the **New File…** button to add the five files from the tree above, all inside `booking`. Put a one-line docstring in `__init__.py`:

```python title="booking/__init__.py"
"""A small hotel booking package."""
```

Python treats a folder with an `__init__.py` as a **regular package**. The file can stay this short. Later you can re-export names from it, like `from booking.models import Hotel`, so that users can write `from booking import Hotel`.

## Step 2: Name every failure in errors.py

Start with the vocabulary of things that can go wrong. Write the hierarchy before any logic, so each later function can say exactly which failure it means.

```python run title="booking/errors.py"
class BookingError(Exception):
    """Base class for every problem the booking package reports."""


class InvalidDates(BookingError):
    """A date is malformed, or check-out isn't after check-in."""


class UnknownRoom(BookingError):
    def __init__(self, room: int) -> None:
        super().__init__(f"there is no room {room}")
        self.room = room


class RoomUnavailable(BookingError):
    def __init__(self, room: int, clash: str) -> None:
        super().__init__(f"room {room} is taken ({clash})")
        self.room = room
        self.clash = clash


class StorageError(BookingError):
    """The bookings file exists but can't be used."""
```

This file defines classes and prints nothing, so the cell has no output. Poke at it to check that the family tree is what you meant:

```python run
err = RoomUnavailable(101, "Ana, 2026-12-01 to 2026-12-04")
print(err)
print(err.room)
print(isinstance(err, BookingError), isinstance(err, InvalidDates))
```

`RoomUnavailable` keeps a description of the clashing stay as a plain string rather than a `Stay` object. That's deliberate: `errors.py` stays free of imports from the rest of the app, so any module can import it without creating a loop.

## Step 3: Raise from the models

`models.py` holds the rules. Its first line in the real file is `from booking.errors import InvalidDates, RoomUnavailable, UnknownRoom`; in this notebook those names already exist.

```python run title="booking/models.py"
from datetime import date


def parse_date(text: str) -> date:
    try:
        return date.fromisoformat(text)
    except ValueError as err:
        raise InvalidDates(f"{text!r} is not a date like 2026-12-01") from err


class Stay:
    def __init__(self, guest: str, check_in: date, check_out: date) -> None:
        if check_out <= check_in:
            raise InvalidDates(f"check-out {check_out} must be after check-in {check_in}")
        self.guest = guest
        self.check_in = check_in
        self.check_out = check_out

    def overlaps(self, other: "Stay") -> bool:
        return self.check_in < other.check_out and other.check_in < self.check_out

    def __str__(self) -> str:
        return f"{self.guest}, {self.check_in} to {self.check_out}"


class Hotel:
    def __init__(self, rooms: list[int]) -> None:
        self._stays: dict[int, list[Stay]] = {room: [] for room in rooms}

    def book(self, room: int, stay: Stay) -> None:
        for existing in self.stays_in(room):
            if existing.overlaps(stay):
                raise RoomUnavailable(room, str(existing))
        self._stays[room].append(stay)

    def stays_in(self, room: int) -> list[Stay]:
        if room not in self._stays:
            raise UnknownRoom(room)
        return list(self._stays[room])

    def rooms(self) -> list[int]:
        return list(self._stays)
```

Notice what's missing: there isn't a single `print` or `except BookingError` in this module. `parse_date` translates Python's `ValueError` into the app's `InvalidDates`, `Stay` refuses backwards dates, and `Hotel.book` refuses overlaps. The overlap test uses `<`, not `<=`, so a guest can check in on the morning another checks out. Try four bookings, catching only `BookingError` so you can see which class each failure is:

```python run
hotel = Hotel([101, 102])
attempts = [
    (101, "Ana", "2026-12-01", "2026-12-04"),
    (101, "Ben", "2026-12-03", "2026-12-05"),
    (101, "Ben", "2026-12-04", "2026-12-06"),
    (102, "Cy", "2026-12-10", "2026-12-32"),
]
for room, guest, check_in, check_out in attempts:
    try:
        hotel.book(room, Stay(guest, parse_date(check_in), parse_date(check_out)))
        print("booked:", guest)
    except BookingError as err:
        print(f"{type(err).__name__}: {err}")
```

## Step 4: Save and load without losing the cause

`storage.py` starts with `from booking.errors import StorageError` and `from booking.models import Hotel, Stay, parse_date`. A missing file is normal on the very first run, so `load` handles it by returning an empty hotel. A damaged file isn't normal, so it becomes a `StorageError` with the JSON error attached as its cause.

```python run title="booking/storage.py"
import json
from pathlib import Path


def save(hotel: Hotel, path: Path) -> None:
    data = {
        str(room): [[s.guest, str(s.check_in), str(s.check_out)] for s in hotel.stays_in(room)]
        for room in hotel.rooms()
    }
    path.write_text(json.dumps(data, indent=2))


def load(path: Path, rooms: list[int]) -> Hotel:
    hotel = Hotel(rooms)
    try:
        data = json.loads(path.read_text())
    except FileNotFoundError:
        return hotel  # first run: nothing saved yet
    except json.JSONDecodeError as err:
        raise StorageError(f"{path} is damaged ({err})") from err
    for room, stays in data.items():
        for guest, check_in, check_out in stays:
            hotel.book(int(room), Stay(guest, parse_date(check_in), parse_date(check_out)))
    return hotel
```

Test all three situations: a round trip, a missing file, and a file someone half-edited by hand.

```python run
save(hotel, Path("demo.json"))
print("round trip:", [str(s) for s in load(Path("demo.json"), [101, 102]).stays_in(101)])
print("missing file:", load(Path("nope.json"), [101]).stays_in(101))

Path("broken.json").write_text('{"101": [["Ana", "2026-12-01"')
try:
    load(Path("broken.json"), [101])
except StorageError as err:
    print("StorageError:", err)
    print("caused by:", type(err.__cause__).__name__)
```

Because of `from err`, the original `JSONDecodeError` rides along as `__cause__`. If this error ever reached the top of the program uncaught, the traceback would show both, with the line *"The above exception was the direct cause of the following exception"* between them.

## Step 5: Catch at the boundary in __main__.py

The menu imports `BookingError` from `booking.errors`, `Hotel`, `Stay`, and `parse_date` from `booking.models`, and `load` and `save` from `booking.storage`. It's the one place that turns exceptions into messages.

```python run title="booking/__main__.py" input="book 101 Ana 2026-12-01 2026-12-04|book 101 Ben 2026-12-03 2026-12-05|book 101 Ben 2026-12-04 2026-12-06|book 305 Cy 2026-12-01 2026-12-02|book 102 Dee 2026-12-09 2026-12-07|list 101|quit"
from pathlib import Path

HELP = "Commands: book ROOM GUEST CHECK-IN CHECK-OUT | list ROOM | quit"


def handle(hotel: Hotel, words: list[str]) -> str:
    if len(words) == 5 and words[0] == "book" and words[1].isdigit():
        room, guest = int(words[1]), words[2]
        stay = Stay(guest, parse_date(words[3]), parse_date(words[4]))
        hotel.book(room, stay)
        return f"Booked room {room}: {stay}"
    if len(words) == 2 and words[0] == "list" and words[1].isdigit():
        stays = hotel.stays_in(int(words[1]))
        return "\n".join(str(stay) for stay in stays) or "No bookings yet"
    return HELP


def main(path: Path = Path("bookings.json")) -> None:
    hotel = load(path, rooms=[101, 102, 201])
    try:
        while True:
            line = input("> ").strip()
            if line == "quit":
                break
            try:
                print(handle(hotel, line.split()))
            except BookingError as err:
                print(f"Can't do that: {err}")
    finally:
        save(hotel, path)
        print(f"Saved to {path}")


if __name__ == "__main__":
    main()
```

Two `try` blocks, two jobs. The inner one wraps a single command, so one bad booking prints a message and the loop carries on. The outer one has no `except` at all, only `finally`: whether the user types `quit`, presses **Ctrl+C** (a `KeyboardInterrupt`, which `except BookingError` deliberately doesn't catch), or a bug crashes the loop, the bookings are saved first.

## Step 6: Run it as a package

In VS Code's terminal, make sure you're in the `hotel` folder (the one that *contains* `booking`), then run:

```bash
python -m booking
```

```text
> book 201 Eli 2026-12-20 2026-12-22
Booked room 201: Eli, 2026-12-20 to 2026-12-22
> list 201
Eli, 2026-12-20 to 2026-12-22
> quit
Saved to bookings.json
```

`-m booking` tells Python to find the package called `booking` and run its `__main__.py`. Python puts the current folder on its import path, which is why `from booking.errors import BookingError` works inside the package. Run it a second time and `list 201` still shows Eli's stay, because `load` read it back from `bookings.json`.

:::warning
**`ModuleNotFoundError: No module named 'booking'`.** You'll see this if you run `python booking/__main__.py` instead of `python -m booking`, or run `python -m booking` from *inside* the `booking` folder. In both cases the folder that contains `booking` isn't on the import path. Go up to `hotel` and use `-m`.
:::

## The finished package

| File | Starts with | Holds |
| --- | --- | --- |
| `booking/__init__.py` | (a docstring) | marks the package |
| `booking/errors.py` | no imports | `BookingError` and its four subclasses |
| `booking/models.py` | `from datetime import date`, `from booking.errors import InvalidDates, RoomUnavailable, UnknownRoom` | `parse_date`, `Stay`, `Hotel` |
| `booking/storage.py` | `import json`, `from pathlib import Path`, `from booking.errors import StorageError`, `from booking.models import Hotel, Stay, parse_date` | `save`, `load` |
| `booking/__main__.py` | `from pathlib import Path`, plus the imports listed in Step 5 | `handle`, `main`, and the `__main__` guard |

The imports only point one way: `__main__` → `storage` → `models` → `errors`. Keeping that direction is what stops circular imports as the package grows.

:::quiz
Q: Why does `load` turn `json.JSONDecodeError` into `StorageError` instead of letting it escape?
- [ ] Because `JSONDecodeError` can't be caught
  It can; `load` catches it right there.
- [x] So the menu only needs to know about `BookingError` and its subclasses
  Callers deal with the package's own vocabulary, and `from err` still keeps the JSON details for debugging.
- [ ] So the damaged file gets repaired
  Nothing repairs the file; the error just gets a clearer name.

Q: A typo in `handle` calls `hotel.bok(room, stay)`. What happens when someone books a room?
- [ ] The menu prints "Can't do that: ..." and carries on
  That would happen only if the menu caught `Exception`. It catches `BookingError`, and an `AttributeError` isn't one.
- [x] The program stops with an `AttributeError` traceback, after `finally` saves the bookings
  The bug surfaces immediately with a line number, and the data is still saved on the way out.
- [ ] Python refuses to run the file at all
  Misspelled attribute names are only noticed when that line actually runs.

Q: Why is `save(hotel, path)` in a `finally` block rather than after the loop?
- [ ] `finally` makes saving faster
  Speed is the same; what changes is *when* it's guaranteed to run.
- [x] Code after the loop would be skipped if the loop raised, including on Ctrl+C
  `finally` runs on every way out of the `try`: normal exit, `break`, or an exception.
:::

:::takeaways
- Put exceptions in their own import-free module so every other module can use them.
- Models raise specific errors and print nothing; only the boundary (the menu) turns errors into messages.
- Translate errors from other libraries into your own with `raise ... from err` so callers learn one vocabulary.
- A loop-level `try`/`except` keeps one bad command from ending the session; an outer `finally` guarantees cleanup.
- Run packages from the folder that contains them with `python -m package_name`.
:::
