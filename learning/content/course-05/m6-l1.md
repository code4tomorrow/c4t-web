Three student projects at one school each needed "do these two date ranges overlap?": the hotel app from last module, a library's loan tracker, and the robotics club's room scheduler. Each project pasted in its own copy. In March someone noticed that a stay ending on the 4th and one starting on the 4th were reported as clashing, and fixed it, in one copy. The other two still had the bug in June.

The cure is one shared component that every project imports. For that to work, the component needs a **clear interface** (what callers can rely on) and **tests** (proof that it keeps those promises after every change). This lesson covers both, starting with how Python decides what a method call does.

## Polymorphism: one call, many behaviors

A booking app has to confirm bookings by email for some guests and by text message for others. You could write `if channel == "email": ... elif channel == "sms": ...` everywhere you send something. Or you could give each channel a class with the same method name, and let the object decide what `send` means.

Step through this program. Watch the line `return channel.send(...)` inside `confirm`: it's the same line both times, but it jumps into a different class's method each time around the loop.

:::trace Same call, different method
```python
class Email:
    def send(self, to, text):
        return f"email to {to}: {text}"

class Sms:
    def send(self, to, text):
        return f"SMS to {to}: {text[:12]}..."

def confirm(guest, channel):
    return channel.send(guest, "Room 101 is booked")

for channel in [Email(), Sms()]:
    print(confirm("Ana", channel))
```
:::

That's **polymorphism**: code written against one method name works with many classes. `confirm` will never need editing when you add a `Push` or `Discord` class tomorrow.

## Duck typing: Python checks behavior, not ancestry

Notice that `Email` and `Sms` don't share a parent class. Python doesn't care. When `channel.send(...)` runs, Python looks for a `send` attribute on that particular object, right then. If it has one, the call works. This is **duck typing**: if it walks like a duck and quacks like a duck, it's treated as a duck.

The flip side is that a mistake is only discovered when the call actually happens:

```python run raises title="duck.py"
class Email:
    def send(self, to: str, text: str) -> str:
        return f"email to {to}: {text}"

def confirm(guest: str, channel) -> str:
    return channel.send(guest, "Room 101 is booked")

print(confirm("Ana", Email()))
print(confirm("Ana", "email"))
```

Passing the *string* `"email"` instead of an `Email` object only fails when `confirm` tries to call `.send` on it. In a big program, that line might run rarely. That's where an explicit interface helps.

## abc.ABC: write the contract down

The `abc` module (abstract base classes) lets you declare an interface as a class. Methods marked `@abstractmethod` have no real body; they're promises. Python refuses to create an object from any class that still has an unkept promise.

```mermaid caption="Notifier is the interface; each channel implements send()"
classDiagram
    class Notifier {
        <<abstract>>
        +send(to, text)*
        +send_all(people, text)
    }
    Notifier <|-- EmailNotifier
    Notifier <|-- SmsNotifier
    class EmailNotifier {
        +send(to, text)
    }
    class SmsNotifier {
        +send(to, text)
    }
```

```python run raises title="notifier.py"
from abc import ABC, abstractmethod


class Notifier(ABC):
    @abstractmethod
    def send(self, to: str, text: str) -> None:
        """Deliver one message."""

    def send_all(self, people: list[str], text: str) -> None:
        for person in people:
            self.send(person, text)


class EmailNotifier(Notifier):
    def send(self, to: str, text: str) -> None:
        print(f"[email] {to}: {text}")


class SmsNotifier(Notifier):
    def sned(self, to: str, text: str) -> None:  # typo!
        print(f"[sms] {to}: {text}")


EmailNotifier().send_all(["ana@example.com", "ben@example.com"], "Pool closes at 9")
SmsNotifier()
```

Two things happened. `EmailNotifier` kept the promise, and it also inherited `send_all`, a normal method written once in the base class that calls whichever `send` the subclass provides. `SmsNotifier` misspelled `send`, and Python stopped it the moment you tried to *create* one, long before any message needed sending. That's the trade: an ABC moves the error from "whenever this line happens to run" to "as soon as the object is made".

:::note
Python also has `typing.Protocol`, which describes an interface without requiring inheritance. A tool like mypy then checks that any object you pass has the right methods. Use an ABC when you want shared methods like `send_all` and a runtime check; a `Protocol` when you just want type checking of duck-typed code.
:::

## Unit tests: one behavior, one test

A **unit test** is a tiny program that calls one piece of your code and checks one result. You met pytest in Module 1: files named `test_*.py`, functions named `test_*`, and plain `assert`. Here is a test file for the shared overlap function. For a first look, the function and its tests share one file, the way pytest's own getting-started guide does it:

```python title="test_overlap.py"
from datetime import date

import pytest


def overlaps(start_a: date, end_a: date, start_b: date, end_b: date) -> bool:
    """True if two stays share a night. Each end date is a check-out day."""
    if end_a <= start_a or end_b <= start_b:
        raise ValueError("a stay must end after it starts")
    return start_a < end_b and start_b < end_a


def d(day: int) -> date:
    return date(2026, 12, day)


def test_stays_sharing_a_night_overlap():
    assert overlaps(d(1), d(4), d(3), d(5))


def test_back_to_back_stays_do_not_overlap():
    assert not overlaps(d(1), d(4), d(4), d(6))


def test_backwards_stay_is_rejected():
    with pytest.raises(ValueError, match="must end after"):
        overlaps(d(4), d(1), d(1), d(2))
```

```bash
python -m pytest -v test_overlap.py
```


The second test is the March bug, written down forever. `pytest.raises` passes only if the code inside the `with` block raises that exception, and `match=` checks the message too. Test names are sentences, so a failure report reads like a bug report.

Python's standard library has its own testing module, `unittest`. pytest can run `unittest` tests too, and since `unittest` needs no install, it's what runs on this page. The same three tests:

```python run title="test_overlap_unittest.py"
import sys
import unittest
from datetime import date


def overlaps(start_a: date, end_a: date, start_b: date, end_b: date) -> bool:
    if end_a <= start_a or end_b <= start_b:
        raise ValueError("a stay must end after it starts")
    return start_a < end_b and start_b < end_a


def d(day: int) -> date:
    return date(2026, 12, day)


class OverlapTests(unittest.TestCase):
    def test_stays_sharing_a_night_overlap(self):
        self.assertTrue(overlaps(d(1), d(4), d(3), d(5)))

    def test_back_to_back_stays_do_not_overlap(self):
        self.assertFalse(overlaps(d(1), d(4), d(4), d(6)))

    def test_backwards_stay_is_rejected(self):
        with self.assertRaises(ValueError):
            overlaps(d(4), d(1), d(1), d(2))


suite = unittest.TestLoader().loadTestsFromTestCase(OverlapTests)
unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)
```

`unittest` groups tests as methods of a `TestCase` subclass and uses methods like `assertTrue` and `assertRaises` instead of bare `assert`. In your own files, `unittest.main()` at the bottom finds and runs the tests for you; the last two lines here do the same thing explicitly.

## Fixtures and fakes: testing code that talks to the world

How do you test `confirm_booking` without emailing a real person? Because of duck typing, you can pass a **fake**: an object with the same `send` method that just records what it was asked to do. And because several tests need a fresh fake, pytest lets you write a **fixture**, a function marked `@pytest.fixture` that builds it. Any test that names the fixture as a parameter gets a brand-new copy.

```python title="test_confirm.py"
import pytest


class FakeNotifier:
    """Records messages instead of sending them."""

    def __init__(self) -> None:
        self.sent: list[tuple[str, str]] = []

    def send(self, to: str, text: str) -> None:
        self.sent.append((to, text))


def confirm_booking(guest: str, room: int, notifier) -> None:
    notifier.send(guest, f"Room {room} is booked. See you soon!")


@pytest.fixture
def notifier() -> FakeNotifier:
    return FakeNotifier()


def test_confirmation_goes_to_the_guest(notifier):
    confirm_booking("ana@example.com", 101, notifier)
    assert notifier.sent[0][0] == "ana@example.com"


def test_confirmation_names_the_room(notifier):
    confirm_booking("ana@example.com", 101, notifier)
    assert "Room 101" in notifier.sent[0][1]
```

The `unittest` version of a fixture is a `setUp` method, which runs before every test method:

```python run title="test_confirm_unittest.py"
import sys
import unittest


class FakeNotifier:
    def __init__(self) -> None:
        self.sent: list[tuple[str, str]] = []

    def send(self, to: str, text: str) -> None:
        self.sent.append((to, text))


def confirm_booking(guest: str, room: int, notifier) -> None:
    notifier.send(guest, f"Room {room} is booked. See you soon!")


class ConfirmTests(unittest.TestCase):
    def setUp(self):
        self.notifier = FakeNotifier()  # fresh for every test

    def test_confirmation_goes_to_the_guest(self):
        confirm_booking("ana@example.com", 101, self.notifier)
        self.assertEqual(self.notifier.sent[0][0], "ana@example.com")

    def test_only_one_message_is_sent(self):
        confirm_booking("ana@example.com", 101, self.notifier)
        self.assertEqual(len(self.notifier.sent), 1)


suite = unittest.TestLoader().loadTestsFromTestCase(ConfirmTests)
unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)
```

`test_only_one_message_is_sent` passes only because each test gets its own fake. If both tests shared one, the second would see two messages and fail depending on the order the tests ran in. Fresh setup per test is the whole point.

This also shows why interfaces and tests go together. `confirm_booking` depends on "something with `send`", not on a real email library, so a fake slots in. Writing a test *before* the code (test-first) pushes you toward that kind of design, because it's the first moment you have to call your code from outside. You'll work that way in the build-along.

:::warning
**A test that never runs.** pytest only collects functions whose names start with `test`, in files named `test_*.py` or `*_test.py`. Name one `check_overlap` and pytest silently skips it; `unittest` likewise ignores methods not starting with `test`. If the count of tests in the summary is lower than you expected, check the names.
:::

:::warning
**Fighting duck typing.** Code like `if isinstance(channel, EmailNotifier): ... elif isinstance(channel, SmsNotifier): ...` brings back the `if` chain polymorphism was meant to remove, and it rejects fakes in tests. Call the method and let each class handle it.
:::

:::quiz
Q: `channels = [EmailNotifier(), FakeNotifier()]`, and the loop calls `channel.send("ana", "hi")` on each. `FakeNotifier` doesn't inherit from `Notifier`. What happens?
- [x] Both calls work
  Python only looks for a `send` method on each object when the call runs. Inheritance isn't required.
- [ ] The second call raises `TypeError` because `FakeNotifier` isn't a `Notifier`
  Nothing checks the class at call time; that only happens if you write an `isinstance` check yourself.
- [ ] The list can't be created because the types differ
  Python lists hold any mix of objects.

Q: `PushNotifier(Notifier)` defines `def push(self, to, text)` but no `send`. When do you first get an error?
- [ ] When Python reads the class definition
  Defining the class is allowed; it just stays abstract.
- [x] At `PushNotifier()`, with a `TypeError` about the abstract method `send`
  An ABC blocks creating objects from classes with unimplemented abstract methods.
- [ ] Only when `send` is eventually called
  That's how plain duck typing behaves. The ABC moves the error earlier.

Q: Two pytest tests both use the `notifier` fixture. The first test sends one message. How many messages does the second test's notifier start with?
- [x] Zero
  A fixture runs again for each test that asks for it, so every test gets a new `FakeNotifier`.
- [ ] One
  That would happen if the tests shared one object, which is the problem fixtures solve.
- [ ] It depends on which test pytest runs first
  Fresh fixtures make the order irrelevant.
:::

:::takeaways
- Polymorphism means one method name, many implementations; callers stay the same when you add a new class.
- Duck typing checks for the method when it's called; an `abc.ABC` with `@abstractmethod` catches a missing method when the object is created.
- An ABC can also hold shared concrete methods, like `send_all`, written once for every implementation.
- A unit test checks one behavior; `pytest.raises` and `assertRaises` test that the right exception happens.
- Fixtures (pytest) and `setUp` (unittest) give every test fresh objects, so tests can't affect each other.
- Code that depends on an interface instead of a concrete class can be tested with a fake.
:::
