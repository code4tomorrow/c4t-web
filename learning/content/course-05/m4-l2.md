## Step 1: Transactions become frozen dataclasses

A transaction records something that already happened, so nothing should be able to change it. A frozen dataclass gives us the constructor, a readable `repr`, equality by value, and immutability, in five lines:

```python run title="bank.py (step 1)"
from dataclasses import dataclass, FrozenInstanceError


@dataclass(frozen=True)
class Transaction:
    note: str
    amount: int
    balance_after: int


t = Transaction("deposit", 120, 120)
print(t)
print(t == Transaction("deposit", 120, 120))
try:
    t.amount = 1_000_000
except FrozenInstanceError as err:
    print("Refused:", err)
```

Equality by value is exactly right here: two deposits of 120 that left the balance at 120 are, as records, the same.

## Step 2: State goes behind properties

Each piece of account state gets an underscore, and callers get a property to read it. Only `owner` has a setter, because renaming an account is allowed, as long as the new name isn't blank. Look at `history`: it returns a *tuple copy*, so a caller who tries to append to it gets an error, and the real list stays untouched.

```python run title="bank.py (step 2)"
class Account:
    next_number = 1001

    def __init__(self, owner, opening_deposit=0):
        self.owner = owner  # runs the validating setter below
        self._number = Account.next_number
        Account.next_number += 1
        self._balance = 0
        self._history = []
        if opening_deposit:
            self.deposit(opening_deposit, "opening")

    @property
    def owner(self):
        return self._owner

    @owner.setter
    def owner(self, name):
        name = name.strip()
        if not name:
            raise ValueError("an account needs an owner")
        self._owner = name

    @property
    def number(self):
        return self._number

    @property
    def balance(self):
        return self._balance

    @property
    def history(self):
        return tuple(self._history)

    def deposit(self, amount, note="deposit"):
        if amount <= 0:
            raise ValueError("amounts must be positive")
        self._balance += amount
        self._history.append(Transaction(note, amount, self._balance))


ana = Account(" Ana ", 200)
print(repr(ana.owner), ana.number, ana.balance)

try:
    ana.balance = 1_000_000
except AttributeError as err:
    print("Refused:", err)
try:
    ana.history.append("fake")
except AttributeError as err:
    print("Refused:", err)
try:
    ana.owner = "   "
except ValueError as err:
    print("Refused:", err)

print(ana.balance, len(ana.history), ana.owner)
```

All three attacks bounce off, and the account is unchanged. Inside the class, methods still use `self._balance` freely. The underscore is a boundary between the class and its callers, not between methods of the same class.

## Step 3: Check amounts at the door, and write down the types

The notes lesson ended with `deposit("20")` crashing deep inside the method with a confusing message. Two tools fix that, and they work at different times.

**Type hints** say what you mean, and a type checker reads them *before* the program runs. Add hints to every method, for example `def deposit(self, amount: int, note: str = "deposit") -> None:`. Then a file that misuses the class gets flagged without running it. Pylance does this in VS Code as you type; the command-line checker mypy (`python -m pip install mypy`, then `python -m mypy misuse.py`) reports the same problems:

```text
misuse.py:3: error: Argument 1 to "deposit" of "Account" has incompatible type "str"; expected "int"  [arg-type]
misuse.py:4: error: Property "balance" defined in "Account" is read-only  [misc]
Found 2 errors in 1 file (checked 1 source file)
```

**A runtime check** catches whatever the type checker didn't see, such as a value read from a file. Because both `deposit` and `withdraw` need it, it goes in one small helper:

```python run title="bank.py (step 3)"
def _check_amount(amount: int) -> None:
    if type(amount) is not int:
        raise TypeError(f"amounts must be whole dollars (int), got {amount!r}")
    if amount <= 0:
        raise ValueError("amounts must be positive")


for value in [20, "20", 2.5, True, -5]:
    try:
        _check_amount(value)
        print(repr(value), "accepted")
    except (TypeError, ValueError) as err:
        print(repr(value), "refused:", err)
```

`type(amount) is not int` is stricter than `isinstance`, on purpose: `True` is technically an `int` in Python, and nobody means to deposit `True` dollars. The leading underscore on `_check_amount` says it's a helper for this module, not something callers should use.

## Step 4: A repr for debugging, and a decision about equality

Add a `__repr__` to `Account`, so lists of accounts, the debugger, and error messages show something useful. Using `type(self).__name__` means a savings account labels itself correctly without its own `__repr__`:

```python
    def __repr__(self) -> str:
        kind = type(self).__name__
        return f"{kind}(number={self._number}, owner={self._owner!r}, balance={self._balance})"
```

Should `Account` also get an `__eq__`? Ask what equality would *mean*. Two accounts with the same owner and balance are still two different accounts; and since the bank hands out unique numbers, no two account objects can share a number. Python's default, where an object is only equal to itself, is already correct. So we deliberately leave `__eq__` out. `Transaction` is the opposite case: it's a value, and the dataclass compares it by value.

## Step 5: The Bank acts like a collection

Callers often want to ask "how many accounts?", "is 1002 here?", and "give me each account". Three dunder methods answer those using the familiar syntax, without exposing the dict itself:

```python
    def __len__(self) -> int:
        return len(self._accounts)

    def __contains__(self, number: object) -> bool:
        return number in self._accounts

    def __iter__(self) -> Iterator[Account]:
        return iter(self._accounts.values())
```

`__iter__` hands back an iterator over the accounts, so `for account in bank:` works, and so do `sorted(bank, ...)`, `list(bank)`, and `sum(...)` over the bank. `month_end` and `total_held` can now loop over `self` directly. `Iterator` comes from `collections.abc`, imported at the top of the file.

## Step 6: The finished bank.py

```python run title="bank.py"
from collections.abc import Iterator
from dataclasses import dataclass


@dataclass(frozen=True)
class Transaction:
    note: str
    amount: int
    balance_after: int


def _check_amount(amount: int) -> None:
    if type(amount) is not int:
        raise TypeError(f"amounts must be whole dollars (int), got {amount!r}")
    if amount <= 0:
        raise ValueError("amounts must be positive")


class Account:
    next_number = 1001

    def __init__(self, owner: str, opening_deposit: int = 0) -> None:
        self.owner = owner  # runs the validating setter below
        self._number = Account.next_number
        Account.next_number += 1
        self._balance = 0
        self._history: list[Transaction] = []
        if opening_deposit:
            self.deposit(opening_deposit, "opening")

    @property
    def owner(self) -> str:
        return self._owner

    @owner.setter
    def owner(self, name: str) -> None:
        name = name.strip()
        if not name:
            raise ValueError("an account needs an owner")
        self._owner = name

    @property
    def number(self) -> int:
        return self._number

    @property
    def balance(self) -> int:
        return self._balance

    @property
    def history(self) -> tuple[Transaction, ...]:
        return tuple(self._history)

    def deposit(self, amount: int, note: str = "deposit") -> None:
        _check_amount(amount)
        self._balance += amount
        self._history.append(Transaction(note, amount, self._balance))

    def withdraw(self, amount: int, note: str = "withdraw") -> None:
        _check_amount(amount)
        if amount > self._balance:
            raise ValueError(f"account {self._number} only has ${self._balance}")
        self._balance -= amount
        self._history.append(Transaction(note, -amount, self._balance))

    def month_end(self) -> None:
        pass  # an ordinary account has nothing to do at month end

    def __repr__(self) -> str:
        kind = type(self).__name__
        return f"{kind}(number={self._number}, owner={self._owner!r}, balance={self._balance})"


class SavingsAccount(Account):
    max_withdrawals = 3

    def __init__(self, owner: str, opening_deposit: int = 0, rate: float = 0.02) -> None:
        super().__init__(owner, opening_deposit)
        self._rate = rate
        self._withdrawals_this_month = 0

    @property
    def rate(self) -> float:
        return self._rate

    def withdraw(self, amount: int, note: str = "withdraw") -> None:
        if self._withdrawals_this_month >= SavingsAccount.max_withdrawals:
            raise ValueError("savings accounts allow 3 withdrawals a month")
        super().withdraw(amount, note)
        self._withdrawals_this_month += 1

    def month_end(self) -> None:
        interest = round(self.balance * self._rate)
        if interest > 0:
            self.deposit(interest, "interest")
        self._withdrawals_this_month = 0


class Bank:
    def __init__(self, name: str) -> None:
        self.name = name
        self._accounts: dict[int, Account] = {}

    def add(self, account: Account) -> Account:
        if account.number in self._accounts:
            raise ValueError(f"account {account.number} is already in this bank")
        self._accounts[account.number] = account
        return account

    def find(self, number: int) -> Account:
        if number not in self._accounts:
            raise ValueError(f"no account {number}")
        return self._accounts[number]

    def transfer(self, from_number: int, to_number: int, amount: int) -> None:
        source = self.find(from_number)
        target = self.find(to_number)
        source.withdraw(amount, f"to {target.number}")
        target.deposit(amount, f"from {source.number}")

    def month_end(self) -> None:
        for account in self:
            account.month_end()

    def total_held(self) -> int:
        return sum(account.balance for account in self)

    def __len__(self) -> int:
        return len(self._accounts)

    def __contains__(self, number: object) -> bool:
        return number in self._accounts

    def __iter__(self) -> Iterator[Account]:
        return iter(self._accounts.values())


if __name__ == "__main__":
    bank = Bank("Maple Street Bank")
    ana = bank.add(Account("Ana", 200))
    ben = bank.add(SavingsAccount("Ben", 500))
    bank.transfer(ana.number, ben.number, 50)
    bank.month_end()

    print(len(bank), 1002 in bank, 9999 in bank)
    for account in sorted(bank, key=lambda a: a.balance, reverse=True):
        print(account)
    print(ben.history[-1])

    try:
        ana.balance = 1_000_000
    except AttributeError as err:
        print("Refused:", err)
    try:
        ana.deposit("20")
    except TypeError as err:
        print("Refused:", err)
```

`SavingsAccount.month_end` reads `self.balance` (the property) but changes the balance only through `self.deposit`, so even a subclass goes through the front door and every change is recorded.

## Step 7: Tests that prove the interface holds

Each test tries to misuse the class and checks that it can't. In your project, `test_bank.py` starts with `from dataclasses import FrozenInstanceError`, `import pytest`, and `from bank import Account, Bank, SavingsAccount, Transaction`.

```python run title="test_bank.py"
from dataclasses import FrozenInstanceError

import pytest


def test_balance_is_read_only():
    acct = Account("Ana", 50)
    with pytest.raises(AttributeError):
        acct.balance = 1_000_000
    assert acct.balance == 50


def test_history_cannot_be_edited_from_outside():
    acct = Account("Ana", 50)
    with pytest.raises(AttributeError):
        acct.history.append(Transaction("fake", 999, 999))
    assert len(acct.history) == 1


def test_transactions_are_frozen():
    t = Transaction("deposit", 50, 50)
    with pytest.raises(FrozenInstanceError):
        t.amount = 5000


def test_amounts_must_be_whole_dollars():
    acct = Account("Ana")
    for bad in ["20", 2.5, True]:
        with pytest.raises(TypeError):
            acct.deposit(bad)
    assert acct.balance == 0


def test_owner_is_cleaned_and_required():
    acct = Account("  Ana ")
    assert acct.owner == "Ana"
    with pytest.raises(ValueError):
        acct.owner = "   "
    assert acct.owner == "Ana"


def test_bank_behaves_like_a_collection():
    bank = Bank("Test")
    a = bank.add(Account("Ana"))
    b = bank.add(SavingsAccount("Ben"))
    assert len(bank) == 2
    assert a.number in bank and 1 not in bank
    assert list(bank) == [a, b]


def test_month_end_interest_is_recorded():
    bank = Bank("Test")
    ben = bank.add(SavingsAccount("Ben", 500, rate=0.02))
    bank.month_end()
    assert ben.history[-1] == Transaction("interest", 10, 510)


for name, test in list(globals().items()):
    if name.startswith("test_") and callable(test):
        test()
        print("passed:", name)
```

`python -m pytest` in `m4_interfaces` reports `7 passed`. The last test compares a whole `Transaction` with `==` in one line, which only reads that cleanly because dataclasses compare by value.

:::quiz
Q: Why does the `history` property return `tuple(self._history)` instead of `self._history`?
- [ ] Tuples use less memory, so the bank runs faster
  Memory isn't the reason. The point is who can change the history.
- [x] Callers get a read-only copy, so the only way to add a transaction is through `deposit` or `withdraw`
  Returning the real list would let any caller append fake entries or clear it.
- [ ] Properties aren't allowed to return lists
  They can return anything; returning the internal list just defeats the purpose.

Q: Why does `Account` deliberately have no `__eq__`?
- [x] Each account object is a distinct account with a unique number, so "equal only to itself" is already right
  Equality by value fits values like `Transaction`; accounts are things with identity.
- [ ] Classes with properties can't define `__eq__`
  They can; there was just no good meaning for it here.
- [ ] Without `__eq__`, `list(bank) == [a, b]` would fail
  It passes using the default identity comparison, because the list holds those exact objects.

Q: A type checker already flags `deposit("20")`. Why keep the runtime `_check_amount` too?
- [ ] Type checkers are often wrong
  They're reliable for what they can see; the issue is what they can't see.
- [x] Values that arrive while the program runs, like from a file or `input()`, are never seen by the type checker
  Hints check your code before it runs; the runtime check guards the data it meets later.
- [ ] Python requires a runtime check whenever hints are used
  Python never requires one; hints are optional and unenforced.
:::

:::takeaways
- A frozen dataclass is the right shape for a record that must not change; it compares by value for free.
- Underscored state plus read-only properties means state changes only through methods that validate and record.
- Type hints let tools catch misuse before running; a small runtime check guards values that arrive while running.
- Only define `__eq__` when equality has a clear meaning. Objects with identity, like accounts, are often best left with the default.
- `__len__`, `__contains__`, and `__iter__` let a container class work with `len`, `in`, and `for` without exposing its insides.
:::
