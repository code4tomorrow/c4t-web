Here is a hotel booking loop that a student shipped to their family's guesthouse. It looks careful: every booking is wrapped in `try`, so the program never crashes. Run it and read the third line of output.

```python run title="booking_v0.py"
rooms = {101: [], 102: []}

def book(room, night):
    if night in rooms[room]:
        raise ValueError("taken")
    rooms[room].append(night)

requests = [(101, "Dec 1"), (101, "Dec 1"), (103, "Dec 2"), (102, "Dec 3")]
for room, night in requests:
    try:
        book(room, night)
        print(f"Booked room {room} for {night}")
    except Exception:
        print(f"Sorry, room {room} is taken on {night}")
```

There is no room 103. `rooms[103]` raised a `KeyError`, and `except Exception` caught it and reported a lie. If someone later mistypes `append` as `apend`, the same line will tell every guest their room is taken, and nobody will see the real `AttributeError`. Not crashing is easy. Failing *accurately* takes design, and that design is what this lesson builds.

## An exception travels up the call stack until something catches it

When Python hits a problem it can't continue past, it creates an **exception object** and *raises* it. The current function stops right there. Python then checks the caller: is this call inside a `try` with a matching `except`? If not, that function stops too, and the exception moves up again. If it reaches the top with nobody catching it, the program ends and prints a **traceback**.

```python run raises title="checkin.py"
from datetime import date

def parse_night(text):
    return date.fromisoformat(text)

def book(room, text):
    night = parse_night(text)
    print(f"Room {room} booked for {night}")

book(101, "2026-12-01")
book(101, "2026-02-30")
```

Read a traceback from the bottom up. The last line names the exception type and its message: February has no 30th. The lines above it are the path the exception took, oldest call first: the top of the file called `book`, which called `parse_night`, whose call to `date.fromisoformat` raised. The first booking printed normally because nothing went wrong until the second call.

Now catch it at the top instead. Step through this and watch the call stack: when `int("two")` fails, both `parse_guests` and `make_booking` vanish from the stack at once, and execution lands in the `except` block.

:::trace Watch the exception skip two functions
```python
def parse_guests(text):
    return int(text)

def make_booking(text):
    guests = parse_guests(text)
    return f"{guests} guests"

for text in ["2", "two"]:
    try:
        print(make_booking(text))
    except ValueError as err:
        print("Bad input:", err)
```
:::

## try, except, else, finally: who runs when

Each of the four blocks has one job. `try` holds the code that might fail. `except` runs only if that code raised a matching exception. `else` runs only if `try` finished *without* an exception. `finally` runs no matter what, even when another block returns.

```python run title="four_blocks.py"
def read_guests(text):
    try:
        guests = int(text)
    except ValueError:
        print(f"  except: {text!r} is not a whole number")
        return None
    else:
        print(f"  else: got {guests}")
        return guests
    finally:
        print("  finally: always runs")

for text in ["3", "three"]:
    print(f"read_guests({text!r})")
    print("  returned", read_guests(text))
```

Both calls `return` from inside `except` or `else`, yet `finally` still prints before the value comes back. That makes `finally` the place for cleanup that must happen: closing a connection, saving a file, releasing a lock. Keep the `try` block small. Only `int(text)` can raise the `ValueError` we're expecting, so it's the only line inside `try`; the success path goes in `else`, where a bug can't be mistaken for bad input.

## raise: refuse to continue when a rule is broken

Your own classes should raise exceptions too. A constructor is a good place, because it guards the moment an object comes into existence. If a check-out date comes before the check-in date, the right response is to refuse to build the object at all.

```python run raises title="stay.py"
from datetime import date

class Stay:
    def __init__(self, check_in: date, check_out: date) -> None:
        if check_out <= check_in:
            raise ValueError(f"check-out {check_out} must be after check-in {check_in}")
        self.check_in = check_in
        self.check_out = check_out

    def nights(self) -> int:
        return (self.check_out - self.check_in).days

print(Stay(date(2026, 12, 1), date(2026, 12, 4)).nights())
Stay(date(2026, 12, 4), date(2026, 12, 1))
```

Every `Stay` that exists is now valid, so no other method has to re-check the dates. A useful rule of thumb: **raise where you detect the problem, catch where you know what to do about it.** `Stay` can detect a backwards date but can't decide whether to re-prompt a user, log it, or reject a web request. Its caller can.

## Custom exception classes give each failure a name

`ValueError` says "a value was wrong", but a booking app fails in several distinct ways, and callers need to tell them apart without reading message strings. The fix is a small family of exception classes. They're ordinary classes that inherit from `Exception`, often with no body beyond a docstring.

```mermaid caption="One base class lets callers catch every booking problem, or just one kind"
classDiagram
    Exception <|-- BookingError
    BookingError <|-- InvalidDates
    BookingError <|-- RoomUnavailable
    class RoomUnavailable {
        +int room
        +date night
    }
```

```python run title="booking_errors.py"
from datetime import date

class BookingError(Exception):
    """Base class: catch this to handle any booking problem."""

class InvalidDates(BookingError):
    """The dates are malformed or impossible."""

class RoomUnavailable(BookingError):
    def __init__(self, room: int, night: date) -> None:
        super().__init__(f"room {room} is already booked on {night}")
        self.room = room
        self.night = night

def parse_night(text: str) -> date:
    try:
        return date.fromisoformat(text)
    except ValueError as err:
        raise InvalidDates(f"{text!r} is not a real date (use YYYY-MM-DD)") from err

booked = {(101, date(2026, 12, 1))}

def book(room: int, text: str) -> None:
    night = parse_night(text)
    if (room, night) in booked:
        raise RoomUnavailable(room, night)
    booked.add((room, night))
    print(f"Booked room {room} on {night}")

for room, text in [(101, "2026-12-02"), (101, "2026-12-01"), (102, "2026-13-01")]:
    try:
        book(room, text)
    except RoomUnavailable as err:
        print(f"Taken. Room {err.room} is busy on {err.night}; try another room.")
    except BookingError as err:
        print(f"Can't book: {err}")
```

Three details matter here. `RoomUnavailable` stores `room` and `night` as attributes, so the handler can use them instead of parsing text. `raise InvalidDates(...) from err` **translates** a low-level `ValueError` into the app's own vocabulary while keeping the original attached as `err.__cause__`, so a traceback would show both. And Python checks `except` clauses top to bottom, taking the first match, so the specific class goes before its base class.

:::warning
**Catching too much.** A bare `except:` or `except Exception:` around a big block catches your typos too (`NameError`, `AttributeError`), as the guesthouse loop showed. Catch the narrowest class you can actually handle, like `except BookingError:`, and let everything else crash loudly during development. A crash with a traceback is a bug report; a wrong message is a mystery.
:::

:::warning
**Base class first.** If `except BookingError` comes before `except RoomUnavailable`, the second clause can never run, because every `RoomUnavailable` is already a `BookingError`. Python won't warn you. Order handlers from most specific to most general.
:::

## Modules, packages, and the `__main__` guard

As the app grows, one file gets hard to navigate. A **module** is just a `.py` file; `import` runs that file once and gives you access to the names it defined. A **package** is a folder of modules with an `__init__.py` file. A booking app might be laid out like this:

```text
hotel/                 <- open this folder in VS Code
├── booking/
│   ├── __init__.py
│   ├── errors.py      BookingError, InvalidDates, RoomUnavailable
│   ├── models.py      Stay, Hotel
│   └── __main__.py    the text menu (the only module that prints)
└── tests/
    └── test_models.py
```

Inside `models.py` you'd write `from booking.errors import InvalidDates, RoomUnavailable`. Giving the exceptions their own module pays off: every other module can import them, and `errors.py` imports nothing from the app, so it can never be part of a circular import.

Every module has a variable called `__name__`. When you run a file directly, Python sets it to `"__main__"`. When the file is imported, `__name__` is the module's own name. That's what the familiar guard checks. This cell writes two tiny files and runs each one with the same Python interpreter, the way you would in VS Code's terminal:

```python run title="name_demo.py"
import subprocess
import sys
from pathlib import Path

Path("greet.py").write_text(
    'print("greet.py: __name__ is", repr(__name__))\n'
    'if __name__ == "__main__":\n'
    '    print("greet.py: run directly, so the demo runs")\n'
)
Path("app.py").write_text('import greet\nprint("app.py: __name__ is", repr(__name__))\n')

for script in ["greet.py", "app.py"]:
    print(f"$ python {script}")
    result = subprocess.run([sys.executable, script], capture_output=True, text=True)
    print(result.stdout)
```

Run directly, `greet.py` sees `"__main__"` and runs its demo. Imported by `app.py`, it sees `"greet"`, so the guarded block is skipped. Put the code that *starts* your program under the guard, and importing the module (from tests, for example) won't launch a menu or print anything.

:::warning
**Don't shadow the standard library.** Name your file `random.py` or `json.py` and `import random` will import *your* file instead of Python's, giving errors like `AttributeError: module 'random' has no attribute 'randint'`. Pick specific names like `dice.py`.
:::

:::quiz
Q: `book()` raises `RoomUnavailable`. The handlers are `except BookingError:` (prints "A") and then `except RoomUnavailable:` (prints "B"). What prints?
- [x] A
  Python takes the first matching clause. `RoomUnavailable` is a `BookingError`, so the first clause wins and "B" is unreachable.
- [ ] B
  That needs the specific clause listed first. Order matters.
- [ ] A, then B
  At most one `except` clause runs per exception.

Q: What does this function return, and what does it print? `try: return "try"` followed by `finally: print("cleanup")`
- [ ] Returns "try" and prints nothing
  `finally` runs even when `try` returns, so "cleanup" is printed.
- [x] Prints "cleanup", then returns "try"
  The return value is set aside, `finally` runs, then the function returns.
- [ ] Prints "cleanup" and returns `None`
  `finally` doesn't discard the return value unless it has its own `return`.

Q: `Hotel.book()` detects that a room is taken. Where should the `except RoomUnavailable` that prints "please pick another room" live?
- [ ] Inside `Hotel.book()`, right after the check
  Then `book()` would have to know about printing and menus, and a web version or a test couldn't react differently.
- [x] In the menu code that called `book()`
  The menu knows how to talk to the user. `book()` detects the problem and raises; the caller decides what to do.
- [ ] Nowhere; print the message instead of raising
  Printing hides the failure from the caller, which then carries on as if the booking worked.

Q: `booking/models.py` is imported by `booking/__main__.py`, and you run `python -m booking`. What is `__name__` inside `models.py`?
- [ ] `"__main__"`
  Only the module Python was asked to run gets that name; here that's `booking/__main__.py`.
- [x] `"booking.models"`
  An imported module's `__name__` is its full dotted import name.
- [ ] `"models.py"`
  `__name__` holds the import name, not the file name.
:::

:::takeaways
- An exception climbs the call stack until an `except` matches it; a traceback is that path, read bottom-up.
- Keep `try` blocks tiny, catch the narrowest exception you can handle, and use `finally` for cleanup that must happen.
- Raise where you detect a problem; catch where you know what to do about it.
- A base exception like `BookingError`, with specific subclasses carrying useful attributes, lets callers handle failures by kind.
- `raise NewError(...) from err` translates low-level errors without losing the original.
- Modules are files, packages are folders with `__init__.py`, and `if __name__ == "__main__":` keeps start-up code from running on import.
:::
