## Warm-up: name the status code

For each request to the notes API from the last lesson, decide which status comes back before reading the answers.

1. `POST /notes` with a valid token and `{"title": ""}`.
2. `PATCH /notes/4` with no `Authorization` header.
3. `DELETE /notes/4` with Ben's token, where note 4 is Ana's.
4. `PATCH /notes/999` with Ana's token, where no note 999 exists.
5. The sixth wrong password for `ana` within a minute, on an API with a 5-per-minute limit.

:::solution
1. **422**: the body fails `min_length=1`. FastAPI validates the body before your code runs.
2. **401**: nobody is identified, so permission can't even be asked.
3. **403** (or 404 if the API hides other people's records): Ben is known but not allowed.
4. **404**: Ana is allowed to look, and there's nothing there.
5. **429**: the limiter refuses before the password is even checked.
:::

### Exercise 1: Validate an event sign-up form

The club's sign-up form sends `name`, `grade` (6 to 12), `email`, `shirt` (`S`, `M`, `L`, or `XL`), and optional `guests` (0 to 2). Write an `EventSignup` model that rejects blank names (even all spaces), unknown keys, and anything outside those ranges, then run these five payloads through it.

```text
accepted: {'name': 'Priya', 'grade': 10, 'email': 'priya@school.org', 'shirt': 'M', 'guests': 0}
rejected: ['name: String should have at least 1 character']
rejected: ['grade: Input should be less than or equal to 12', "email: String should match pattern ..."]
rejected: ["shirt: Input should be 'S', 'M', 'L' or 'XL'", 'guests: Input should be less than or equal to 2']
rejected: ['paid: Extra inputs are not permitted']
```

:::hint
`Literal["S", "M", "L", "XL"]` from `typing` limits a field to fixed choices. `str_strip_whitespace=True` in the `ConfigDict` trims spaces before `min_length` is checked, which is what catches `"   "`.
:::

:::solution
```python run title="ex1_signup.py"
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, ValidationError

class EventSignup(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    name: str = Field(min_length=1, max_length=50)
    grade: int = Field(ge=6, le=12)
    email: str = Field(max_length=254, pattern=r"^[^@\s]+@[^@\s]+\.[a-z]{2,}$")
    shirt: Literal["S", "M", "L", "XL"]
    guests: int = Field(default=0, ge=0, le=2)

attempts = [
    {"name": "Priya", "grade": 10, "email": "priya@school.org", "shirt": "M"},
    {"name": "   ", "grade": 10, "email": "priya@school.org", "shirt": "M"},
    {"name": "Leo", "grade": 13, "email": "leo@school", "shirt": "M"},
    {"name": "Sam", "grade": 9, "email": "sam@school.org", "shirt": "XXL", "guests": 5},
    {"name": "Ana", "grade": 11, "email": "ana@school.org", "shirt": "S", "paid": True},
]
for data in attempts:
    try:
        print("accepted:", EventSignup(**data).model_dump())
    except ValidationError as error:
        print("rejected:", [f"{e['loc'][0]}: {e['msg']}" for e in error.errors()])
```

The email pattern only checks the rough shape (something, `@`, something, dot, letters). That's as far as validation should go; the only real proof that an address works is sending it a message. Pydantic also has an `EmailStr` type, which needs the separate `email-validator` package.
:::

### Exercise 2: Close the hole in a search box

This search was meant to find Ana's notes whose title contains a word. Show that searching for `%' --` leaks Ben's notes, then fix it so the same input finds nothing.

```text
unsafe, normal: [('Chem lab checklist',), ('Chess openings',)]
unsafe, attack: [('Chem lab checklist',), ('Chess openings',), ('Bank PIN hint',)]
safe, normal:   [('Chem lab checklist',), ('Chess openings',)]
safe, attack:   []
```

:::hint
The `%` wildcards can't sit inside the quotes around a `?`. Either build the pattern in Python and pass `f"%{term}%"` as the parameter, or let SQL glue it together with `'%' || ? || '%'` (`||` joins strings in SQL).
:::

:::solution
```python run title="ex2_search.py"
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE notes (id INTEGER PRIMARY KEY, owner TEXT, title TEXT);
    INSERT INTO notes (owner, title) VALUES
        ('ana', 'Chem lab checklist'), ('ana', 'Chess openings'), ('ben', 'Bank PIN hint');
""")

def search_unsafe(owner, term):
    sql = f"SELECT title FROM notes WHERE title LIKE '%{term}%' AND owner = '{owner}'"
    return db.execute(sql).fetchall()

def search(owner, term):
    return db.execute(
        "SELECT title FROM notes WHERE title LIKE '%' || ? || '%' AND owner = ? ORDER BY title",
        (term, owner),
    ).fetchall()

print("unsafe, normal:", search_unsafe("ana", "Ch"))
print("unsafe, attack:", search_unsafe("ana", "%' --"))
print("safe, normal:  ", search("ana", "Ch"))
print("safe, attack:  ", search("ana", "%' --"))
```

In the unsafe version, `--` starts an SQL comment, so `AND owner = 'ana'` is thrown away. With placeholders the attack text is only a search term, and no title contains it.
:::

### Exercise 3: Let users choose the sort order, safely

`GET /books?sort=year` should sort by the column the user picks. Write `list_books(sort)` that accepts `title`, `year`, or `newest`, and refuses anything else, including `year; DROP TABLE books`.

```text
[('The Hobbit', 1937), ('Dune', 1965), ('Hatchet', 1987)]
[('Hatchet', 1987), ('Dune', 1965), ('The Hobbit', 1937)]
Refused: sort must be one of ['newest', 'title', 'year']
Books still there: 3
```

:::hint
`ORDER BY ?` runs without an error but sorts by the constant text `'year'`, which means not sorting at all. Placeholders only stand in for values. Map each allowed choice to a piece of SQL you wrote yourself, in a dictionary.
:::

:::solution
```python run title="ex3_sort.py"
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT, year INTEGER);
    INSERT INTO books (title, year) VALUES ('Dune', 1965), ('Hatchet', 1987), ('The Hobbit', 1937);
""")
SORTABLE = {"title": "title", "year": "year", "newest": "year DESC"}

def list_books(sort="title"):
    if sort not in SORTABLE:
        raise ValueError(f"sort must be one of {sorted(SORTABLE)}")
    return db.execute(f"SELECT title, year FROM books ORDER BY {SORTABLE[sort]}").fetchall()

print(list_books("year"))
print(list_books("newest"))
try:
    list_books("year; DROP TABLE books")
except ValueError as error:
    print("Refused:", error)
print("Books still there:", db.execute("SELECT COUNT(*) FROM books").fetchone()[0])
```

The f-string is safe here only because every possible value comes from `SORTABLE`, text you wrote. In a FastAPI route, `sort: Literal["title", "year", "newest"] = "title"` gives the same protection and a 422 for anything else.
:::

### Exercise 4: Password hashes that can be upgraded

Write `hash_password` and `verify_password` with `hashlib.pbkdf2_hmac` and SHA-256. The stored string must record the algorithm and iteration count, as `pbkdf2_sha256$600000$<salt>$<hash>`, so an old hash made with fewer iterations still verifies. Add `needs_rehash(stored)` that says when a hash is weaker than today's setting.

```text
['pbkdf2_sha256', '100000'] needs rehash: True
['pbkdf2_sha256', '600000'] needs rehash: False
old hash still verifies: True
wrong password: False
```

:::hint
`verify_password` must read the iteration count out of the stored string, not use the current constant. `pbkdf2_hmac(name, password_bytes, salt, iterations)` takes the algorithm name as a string.
:::

:::solution
```python run title="ex4_pbkdf2.py"
import hashlib
import hmac
import secrets

ITERATIONS = 600_000  # OWASP's current recommendation for PBKDF2-HMAC-SHA256

def hash_password(password, iterations=ITERATIONS):
    salt = secrets.token_bytes(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, iterations)
    return f"pbkdf2_sha256${iterations}${salt.hex()}${digest.hex()}"

def verify_password(password, stored):
    algorithm, iterations, salt_hex, digest_hex = stored.split("$")
    if algorithm != "pbkdf2_sha256":
        return False
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), bytes.fromhex(salt_hex), int(iterations))
    return hmac.compare_digest(digest.hex(), digest_hex)

def needs_rehash(stored):
    return int(stored.split("$")[1]) < ITERATIONS

old = hash_password("tuba practice", iterations=100_000)  # made by last year's app
new = hash_password("tuba practice")
print(old.split("$")[:2], "needs rehash:", needs_rehash(old))
print(new.split("$")[:2], "needs rehash:", needs_rehash(new))
print("old hash still verifies:", verify_password("tuba practice", old))
print("wrong password:", verify_password("tuba practise", new))
```

The upgrade happens at login, the only moment the server sees the real password: if it verifies and `needs_rehash` is true, hash it again with today's setting and save the new string.
:::

### Exercise 5: Write the permission rule as a function

On the club's message board, members can edit their own posts and organizers can edit any post, but nobody can edit a post once its event is archived. Write `can_edit(user, post)` and check it against every combination below.

```text
ok   maya  post 10: True
ok   leo   post 10: False
ok   ms_k  post 10: True
ok   maya  post 11: False
ok   ms_k  post 11: False
```

:::hint
Check the rule that overrides everything (archived) first, then the role, then ownership. Writing the expected answers down as a list of `(user, post, expected)` tuples before writing the function is how you catch a rule in the wrong order.
:::

:::solution
```python run title="ex5_can_edit.py"
def can_edit(user, post):
    if post["archived"]:
        return False
    if user["role"] == "organizer":
        return True
    return post["author_id"] == user["id"]

maya = {"id": 1, "role": "member"}
leo = {"id": 2, "role": "member"}
ms_k = {"id": 3, "role": "organizer"}
post = {"id": 10, "author_id": 1, "archived": False}
old_post = {"id": 11, "author_id": 1, "archived": True}

cases = [
    (maya, post, True), (leo, post, False), (ms_k, post, True),
    (maya, old_post, False), (ms_k, old_post, False),
]
names = {1: "maya", 2: "leo", 3: "ms_k"}
for user, p, expected in cases:
    got = can_edit(user, p)
    mark = "ok  " if got == expected else "FAIL"
    print(f"{mark} {names[user['id']]:5} post {p['id']}: {got}")
```

Swap the first two `if` blocks and the last case fails: the organizer could edit an archived post. Keeping the rule in one plain function makes it testable without any HTTP at all; routes call it and raise 403 when it says no.
:::

### Exercise 6: Rate-limit the login route

Write a `FixedWindowLimiter` that allows `limit` attempts per `window` seconds for each key, and use it in a `/login` route keyed by username. The sixth attempt in a minute gets 429 with a `Retry-After` header. Pass the limiter a fake clock so the test can jump forward in time instead of sleeping.

```text
[401, 401, 401, 401, 401]
429 {'detail': 'Too many attempts. Try again later.'} Retry-After: 60
30 s later: 429
61 s later: 200
Ben unaffected: 401
```

:::hint
Store `(window_start, count)` per key. On each hit: if the window has expired, start a new one with count 0; if the count has reached the limit, refuse and report `ceil(window_start + window - now)` seconds; otherwise add one. Check the limiter before checking the password, so blocked guesses cost the server nothing.
:::

:::solution
```python run title="ex6_rate_limit.py"
import hashlib
import hmac
import math
import secrets

from fastapi import FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel

class FixedWindowLimiter:
    def __init__(self, limit, window, clock):
        self.limit, self.window, self.clock = limit, window, clock
        self.windows = {}  # key -> (window start, count)

    def hit(self, key):
        """Count one attempt. Returns (allowed, seconds to wait)."""
        now = self.clock()
        start, count = self.windows.get(key, (now, 0))
        if now - start >= self.window:
            start, count = now, 0
        if count >= self.limit:
            return False, max(1, math.ceil(start + self.window - now))
        self.windows[key] = (start, count + 1)
        return True, 0

fake_now = [1000.0]
limiter = FixedWindowLimiter(limit=5, window=60, clock=lambda: fake_now[0])

def scrypt(password, salt):
    return hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1)

SALT = secrets.token_bytes(16)
ANA_HASH = scrypt("correct horse", SALT)

class Login(BaseModel):
    username: str
    password: str

app = FastAPI()

@app.post("/login")
def login(creds: Login):
    allowed, wait = limiter.hit(creds.username)
    if not allowed:
        raise HTTPException(429, "Too many attempts. Try again later.",
                            headers={"Retry-After": str(wait)})
    if creds.username != "ana" or not hmac.compare_digest(scrypt(creds.password, SALT), ANA_HASH):
        raise HTTPException(401, "Wrong username or password")
    return {"token": secrets.token_urlsafe(32)}

client = TestClient(app)
guess = {"username": "ana", "password": "password123"}
right = {"username": "ana", "password": "correct horse"}
print([client.post("/login", json=guess).status_code for _ in range(5)])
blocked = client.post("/login", json=guess)
print(blocked.status_code, blocked.json(), "Retry-After:", blocked.headers["retry-after"])
fake_now[0] += 30
print("30 s later:", client.post("/login", json=right).status_code)
fake_now[0] += 31
print("61 s later:", client.post("/login", json=right).status_code)
print("Ben unaffected:", client.post("/login", json={"username": "ben", "password": "x"}).status_code)
```

Even the right password is refused 30 seconds in, because the window hasn't ended. Keying only by username has a downside: anyone can lock Ana out by guessing wrong on purpose. Real systems combine a per-account limit with a per-IP limit (FastAPI gives you the caller's address as `request.client.host`), and keep the counts somewhere shared, such as a database, when there's more than one server process.
:::

### Challenge: Prove your CORS setup does what you think

Your page runs at `http://localhost:5500` and calls the API with `PATCH` and an `Authorization` header. Configure `CORSMiddleware` for exactly that, then use `TestClient` to send the **preflight** request a browser sends first (`OPTIONS` with `Origin` and `Access-Control-Request-Method` headers). Check three preflights (your origin, a stranger's origin, and your origin asking for `PUT`), then send a plain `GET` from the stranger's origin and look closely at whether the route ran.

:::video 4KHiSt0oLJ0
What to watch for: the preflight request, and which side (browser or server) does the blocking. That's the key to reading the last line of the output below.
:::

:::hint
A preflight is `client.options("/notes", headers={"Origin": ..., "Access-Control-Request-Method": "PATCH", "Access-Control-Request-Headers": "authorization"})`. Print the status, the `access-control-allow-origin` response header, and the body. For the `GET`, keep a list that the route appends to, so you can see whether it ran.
:::

:::solution
```python run title="cors_check.py"
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from fastapi.testclient import TestClient

app = FastAPI()
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5500"],
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)
calls = []

@app.get("/notes")
def list_notes():
    calls.append("route ran")
    return [{"id": 1, "title": "Diary"}]

client = TestClient(app)

def preflight(origin, method="PATCH"):
    r = client.options("/notes", headers={
        "Origin": origin,
        "Access-Control-Request-Method": method,
        "Access-Control-Request-Headers": "authorization",
    })
    return r.status_code, r.headers.get("access-control-allow-origin"), r.text

print("ours:    ", preflight("http://localhost:5500"))
print("stranger:", preflight("https://evil.example"))
print("PUT:     ", preflight("http://localhost:5500", "PUT"))
r = client.get("/notes", headers={"Origin": "https://evil.example"})
print("stranger GET:", r.status_code, r.headers.get("access-control-allow-origin"), r.json(), calls)
```

The last line is the lesson. The stranger's `GET` got a 200, the route ran, and the data came back; the only difference is the missing `access-control-allow-origin` header. A browser would see that and refuse to hand the response to the stranger's JavaScript, but `TestClient`, `curl`, and any script read it fine. CORS stops other websites from reading responses **inside a visitor's browser**. Anything private still needs the token and ownership checks.
:::
