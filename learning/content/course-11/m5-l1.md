The robotics club keeps its sign-ups in one table: event, date, member name, member email. Maya changes her email address. The organizer fixes the row for the Hackathon, the one on screen, and moves on. Now ask the table for Maya's email:

```python run title="flat_table.py"
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE signups (event TEXT, event_date TEXT, member TEXT, email TEXT)")
db.executemany(
    "INSERT INTO signups VALUES (?, ?, ?, ?)",
    [
        ("Robot build night", "2026-09-12", "Maya", "maya@club.org"),
        ("Robot build night", "2026-09-12", "Leo", "leo@club.org"),
        ("Hackathon", "2026-10-03", "Maya", "maya@club.org"),
        ("Hackathon", "2026-10-03", "Priya", "priya@club.org"),
    ],
)

# Maya gets a new address. Someone fixes the row they happen to see.
db.execute("UPDATE signups SET email = 'maya.k@club.org' WHERE member = 'Maya' AND event = 'Hackathon'")

for row in db.execute("SELECT DISTINCT member, email FROM signups ORDER BY member"):
    print(row)
```

Maya now has two email addresses, and nothing in the data says which one is real. Nobody typed anything wrong. The table's shape caused it: her email was stored twice, so it could change in one place and not the other. The same shape causes two more bugs. A new member who hasn't signed up for anything has no row to live in, and deleting the last sign-up for an event deletes every trace that the event exists.

The fix is a rule database designers call **normalization**, and the plain-words version is short: **store each fact once, in the table about that thing.** Maya's email is a fact about Maya, so it belongs in a members table. The Hackathon's date is a fact about the Hackathon. "Maya is going to the Hackathon" is a fact about a sign-up, and that table only needs to point at the other two.

## A table per kind of thing, a primary key per row

A relational database is a set of tables. Each table holds one kind of thing, each **row** is one of those things, and each **column** is one property with a type. Every row gets a **primary key**: a value that identifies it and never changes, even when the name or email does.

In SQLite, a column declared `INTEGER PRIMARY KEY` is filled in for you with 1, 2, 3, and so on. This program saves the club as three tables in a file called `club.db`, then asks a question with `WHERE` (which rows) and `ORDER BY` (in what order):

```python run title="club_setup.py"
import sqlite3

db = sqlite3.connect("club.db")
db.executescript("""
    CREATE TABLE members (
        id    INTEGER PRIMARY KEY,
        name  TEXT NOT NULL,
        email TEXT NOT NULL UNIQUE
    );
    CREATE TABLE events (
        id   INTEGER PRIMARY KEY,
        name TEXT NOT NULL,
        day  TEXT NOT NULL
    );
    CREATE TABLE signups (
        member_id INTEGER NOT NULL REFERENCES members(id),
        event_id  INTEGER NOT NULL REFERENCES events(id),
        PRIMARY KEY (member_id, event_id)
    );

    INSERT INTO members (name, email) VALUES
        ('Maya', 'maya@club.org'), ('Leo', 'leo@club.org'),
        ('Priya', 'priya@club.org'), ('Sam', 'sam@club.org');
    INSERT INTO events (name, day) VALUES
        ('Robot build night', '2026-09-12'),
        ('Hackathon', '2026-10-03'),
        ('Field trip', '2026-11-07');
    INSERT INTO signups (member_id, event_id) VALUES (1, 1), (2, 1), (1, 2), (3, 2);
""")
db.commit()

for row in db.execute("SELECT id, name, day FROM events WHERE day >= '2026-10-01' ORDER BY day"):
    print(row)
```

Three things to notice. `NOT NULL` refuses a missing value and `UNIQUE` refuses a second member with the same email, so the database itself enforces rules your Python might forget. Dates are stored as `'YYYY-MM-DD'` text, which sorts and compares correctly as plain strings. And Sam is in the members table even though he hasn't signed up for anything, which the flat table couldn't do.

## Foreign keys point at a row in another table

The `signups` table holds only two numbers per row. `member_id` is a **foreign key**: it must match the `id` of some row in `members`. The pair `(member_id, event_id)` is the table's primary key, so Maya can't sign up for the same event twice.

```mermaid caption="Each member and each event appears once. A sign-up row links one member to one event."
erDiagram
    MEMBERS ||--o{ SIGNUPS : "makes"
    EVENTS ||--o{ SIGNUPS : "has"
    MEMBERS {
        int id PK
        text name
        text email
    }
    EVENTS {
        int id PK
        text name
        text day
    }
    SIGNUPS {
        int member_id FK
        int event_id FK
    }
```

Read `||--o{` as "one to zero-or-more": one member makes any number of sign-ups. A member who goes to many events and an event with many members is a **many-to-many** relationship, and a linking table like `signups` is how every relational database stores one.

There's a catch that surprises almost everyone the first time:

```python run raises title="foreign_keys.py"
import sqlite3

db = sqlite3.connect("club.db")
db.execute("INSERT INTO signups (member_id, event_id) VALUES (99, 1)")
print("Saved a sign-up for member 99, who does not exist.")
db.rollback()

db.execute("PRAGMA foreign_keys = ON")
with db:  # undoes the insert if it fails; the next lesson explains this
    db.execute("INSERT INTO signups (member_id, event_id) VALUES (99, 1)")
```

SQLite keeps foreign key checks **off** unless each connection turns them on with `PRAGMA foreign_keys = ON`. The first insert pointed at a member who doesn't exist and was accepted anyway. After the pragma, the same insert fails with `FOREIGN KEY constraint failed`. Most other databases check foreign keys by default; with SQLite, put that pragma right after every `connect`.

## JOIN puts the pieces back together

Splitting the data was the easy part. Now you need "who is going to what" as readable names again. Here's the intuition before the SQL: for each sign-up, look up the member with that id and the event with that id, and glue the results into one row.

:::trace Watch each sign-up get matched to a name and an event
```python
members = {1: "Maya", 2: "Leo", 3: "Priya"}
events = {1: "Build night", 2: "Hackathon"}
signups = [(1, 1), (2, 1), (1, 2), (3, 2)]

joined = []
for member_id, event_id in signups:
    row = (members[member_id], events[event_id])
    joined.append(row)
print(joined)
```
:::

That loop is what a `JOIN` describes. You write the matching rule after `ON`, and the database works out how to do the lookups. Because Maya's email now lives in one row, changing it once changes it everywhere it shows up:

```python run title="join.py"
import sqlite3

db = sqlite3.connect("club.db")
db.execute("UPDATE members SET email = 'maya.k@club.org' WHERE id = 1")
db.commit()

query = """
    SELECT members.name, members.email, events.name
    FROM signups
    JOIN members ON members.id = signups.member_id
    JOIN events  ON events.id  = signups.event_id
    ORDER BY events.day, members.name
"""
for row in db.execute(query):
    print(row)
```

Both of Maya's rows show the new address. A plain `JOIN` (also spelled `INNER JOIN`) keeps only rows that found a match, which is why Sam and the Field trip are missing: no sign-up mentions them.

## LEFT JOIN and GROUP BY answer "how many?"

The organizer wants a head count for every event, including events nobody has signed up for yet. `LEFT JOIN` keeps every row from the table on the left (`events`), filling the sign-up columns with `NULL` when there's no match. `GROUP BY` then squashes the rows for each event into one, and `COUNT` counts them.

```python run title="head_count.py"
import sqlite3

db = sqlite3.connect("club.db")
query = """
    SELECT events.name, COUNT(signups.member_id) AS going
    FROM events
    LEFT JOIN signups ON signups.event_id = events.id
    GROUP BY events.id
    ORDER BY going DESC, events.name
"""
for row in db.execute(query):
    print(row)

print("With COUNT(*) instead:")
print(db.execute("""
    SELECT events.name, COUNT(*) FROM events
    LEFT JOIN signups ON signups.event_id = events.id
    GROUP BY events.id
""").fetchall())
```

The Field trip shows 0 going, which is right. The second query says 1, which is wrong, and the reason is subtle: `COUNT(*)` counts rows, and the `LEFT JOIN` produced one row for the Field trip (with `NULL` sign-up columns). `COUNT(signups.member_id)` counts only non-`NULL` values. To keep only some groups, add `HAVING` after `GROUP BY`, for example `HAVING going >= 2`. `WHERE` filters rows before grouping; `HAVING` filters the groups after.

:::warning
**Three bugs almost everyone meets in their first days of SQL.**

1. Foreign keys silently unchecked. Without `PRAGMA foreign_keys = ON`, SQLite accepts a sign-up for member 99. Run the pragma after every `connect`.
2. `COUNT(*)` after a `LEFT JOIN` reports 1 for an empty group. Count a column from the right-hand table instead.
3. `sqlite3.OperationalError: ambiguous column name: name`. Both `members` and `events` have a `name` column, so `SELECT name ... JOIN ...` can't tell which one you mean. Write `members.name` or `events.name`.
:::

:::quiz
Q: A new member, Ana, joins the club but hasn't signed up for an event. In the three-table design, where does her email go?
- [ ] Nowhere until she signs up
  That was the flat table's problem. The members table holds members whether or not they have sign-ups.
- [x] One new row in `members`
  Her email is a fact about her, so it's stored once in the table about members.
- [ ] A new row in `signups` with an empty event
  `event_id` is `NOT NULL` and a foreign key, so that row would be rejected, and it would mix two kinds of facts anyway.

Q: You run `SELECT events.name, COUNT(*) FROM events LEFT JOIN signups ON signups.event_id = events.id GROUP BY events.id`. What does it report for an event with no sign-ups?
- [ ] 0
  That's what you want, but `COUNT(*)` counts the single row the `LEFT JOIN` created for the event.
- [x] 1
  The unmatched event still produces one row (with `NULL` sign-up columns), and `COUNT(*)` counts rows.
- [ ] The event is left out
  A plain `JOIN` would leave it out. `LEFT JOIN` keeps every event.

Q: Which query lists every member, including members with no sign-ups?
- [ ] `SELECT ... FROM signups JOIN members ON members.id = signups.member_id`
  An inner join drops members who have no matching sign-up row.
- [x] `SELECT ... FROM members LEFT JOIN signups ON signups.member_id = members.id`
  `LEFT JOIN` keeps every row of the left table, `members`, matched or not.
- [ ] `SELECT ... FROM signups LEFT JOIN members ON members.id = signups.member_id`
  This keeps every sign-up, not every member. Sam still wouldn't appear.

Q: A program inserts `(member_id=99, event_id=1)` into `signups` on a fresh connection and no error appears. Why?
- [ ] Foreign keys only check `UPDATE`, not `INSERT`
  They check both, once they're switched on.
- [ ] Member 99 was created automatically
  Databases never invent the parent row for you.
- [x] The connection never ran `PRAGMA foreign_keys = ON`
  SQLite leaves foreign key enforcement off per connection unless you turn it on.
:::

:::takeaways
- Store each fact once, in the table about that thing. Repeated facts drift apart.
- A primary key identifies a row forever; a foreign key stores another row's primary key.
- Many-to-many relationships get their own linking table, like `signups`.
- `JOIN ... ON` reassembles related rows; `LEFT JOIN` keeps unmatched rows from the left table.
- `GROUP BY` with `COUNT(column)` gives per-group totals, and `HAVING` filters the groups.
- In SQLite, run `PRAGMA foreign_keys = ON` on every connection.
:::
