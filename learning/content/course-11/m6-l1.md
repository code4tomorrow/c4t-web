A server can't trust anything in a request: not the body, not the URL, not the claim of who sent it. So each request passes a series of checks at the **boundary**, the point where outside data enters your code, and each failed check has its own status code.

```mermaid caption="The order of checks for a request that changes data. Each failure stops the request with a different status."

    D -->|no| E3["403"]
    D -->|yes| F["Run SQL with ? placeholders"]
```

## Pydantic checks the shape before your code runs

A FastAPI route that takes a Pydantic model never sees a request that breaks the model's rules. `Field` adds limits on top of the type, and `extra="forbid"` rejects keys you didn't ask for.

```python run title="validate.py"
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, ConfigDict, Field

class NoteIn(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: str = Field(min_length=1, max_length=100)
    body: str = Field(default="", max_length=2000)
    priority: int = Field(default=1, ge=1, le=3)

app = FastAPI()

@app.post("/notes", status_code=201)
def create_note(note: NoteIn):
    return note

client = TestClient(app)
attempts = [
    {"title": "Chem lab", "priority": 2},
    {"title": "", "priority": 2},
    {"title": "Chem lab", "priority": 9},
    {"title": "Chem lab", "owner_id": 1},
    {"title": "Chem lab", "priority": "2"},
]
for payload in attempts:
    response = client.post("/notes", json=payload)
    if response.status_code == 201:
        print(201, response.json())
    else:
        problems = [f"{e['loc'][-1]}: {e['msg']}" for e in response.json()["detail"]]
        print(response.status_code, problems)
```

Look at the fourth attempt: a client tried to set `owner_id` itself, hoping the server would save whatever it sent. Without `extra="forbid"` Pydantic would silently drop the key; forbidding it tells the client the request was wrong. The last attempt shows Pydantic converting the string `"2"` to the integer `2`; add `strict=True` to a `Field` to refuse that.

Validation answers "is this well-formed?" It does not make data safe to paste into SQL or HTML. A perfectly valid title can still be an attack.

## SQL injection: when a value turns into code

Here's a function that looks up notes by owner by gluing the owner's name into the SQL text with an f-string:

```python run title="injection.py"
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE notes (id INTEGER PRIMARY KEY, owner TEXT, title TEXT);
    INSERT INTO notes (owner, title) VALUES
        ('ana', 'Chem lab checklist'), ('ana', 'Diary: Nov 3'), ('ben', 'Bank PIN hint');
""")

def notes_by_owner_unsafe(owner):
    sql = f"SELECT owner, title FROM notes WHERE owner = '{owner}'"
    print("SQL sent:", sql)
    return db.execute(sql).fetchall()

print(notes_by_owner_unsafe("ben"))
print(notes_by_owner_unsafe("nobody' OR '1'='1"))
```

The second "name" contains a quote that closes the string early, so the rest, `OR '1'='1'`, becomes part of the query's logic. That's true for every row, so the attacker gets everyone's notes. The database did what it was told; the bug is that user data became SQL code.

The fix is the `?` placeholder you've used since the last module. The SQL text and the values travel to SQLite separately, so a value can never be read as code:

```python run title="placeholders.py"
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE notes (id INTEGER PRIMARY KEY, owner TEXT, title TEXT);
    INSERT INTO notes (owner, title) VALUES
        ('ana', 'Chem lab checklist'), ('ana', 'Diary: Nov 3'), ('ben', 'Bank PIN hint');
""")

def notes_by_owner(owner):
    return db.execute("SELECT owner, title FROM notes WHERE owner = ?", (owner,)).fetchall()

print(notes_by_owner("ben"))
print(notes_by_owner("nobody' OR '1'='1"))
```

The attack string is now just an odd name that matches nobody. Placeholders work for values only. If a user chooses a column to sort by, you can't write `ORDER BY ?`; check their choice against a fixed set of allowed names instead.

What to watch for: the moment the injected text changes the shape of the query. It's the same quote trick as above, tried on a real web page, and it's the reason placeholders exist.
:::

## Store a password so a stolen database doesn't reveal it

Databases leak through misplaced backups, bugs, and stolen laptops. If passwords are stored as typed, every account is exposed, along with every other site where people reused them. So servers store a **hash**, the output of a one-way function, and at login they hash what was typed and compare.

Two details matter. A **salt** (random bytes stored next to the hash) makes the same password hash differently for every user, so an attacker can't crack everyone at once with a precomputed table. And the hash must be **slow**. A general-purpose hash like SHA-256 is built for speed, which helps an attacker try billions of guesses. `scrypt` is deliberately slow and memory-hungry.

```python run title="passwords.py"
import hashlib
import hmac
import secrets

def hash_password(password: str) -> str:
    salt = secrets.token_bytes(16)
    digest = hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1)
    return f"{salt.hex()}${digest.hex()}"

def verify_password(password: str, stored: str) -> bool:
    salt_hex, digest_hex = stored.split("$")
    digest = hashlib.scrypt(password.encode(), salt=bytes.fromhex(salt_hex), n=2**14, r=8, p=1)
    return hmac.compare_digest(digest.hex(), digest_hex)

first = hash_password("correct horse battery")
second = hash_password("correct horse battery")
print(first[:40] + "...")
print(second[:40] + "...")
print("Same stored text?", first == second)
print("Right password:", verify_password("correct horse battery", first))
print("Wrong password:", verify_password("correct horse batter", first))
```

Same password, two different stored strings, because each got its own salt. `secrets` (not `random`) generates the salt, since `random` is predictable by design. `hmac.compare_digest` compares in constant time, so response timing doesn't hint at how many characters matched.

:::note
`n=2**14` keeps this course's tests quick. The OWASP Password Storage Cheat Sheet currently recommends at least `n=2**17` for scrypt; at that size you also need to pass `maxmem=2**28`, because Python's default memory cap is too small for it.
:::

## Authentication asks who; authorization asks whether

**Authentication** proves who is sending the request. After a correct password, the server creates a random **token** with `secrets.token_urlsafe(32)`, remembers which user it belongs to, and gives it to the client. The client sends it back on every request in a header: `Authorization: Bearer <token>`.

```mermaid caption="Log in once, then prove who you are with the token on each request."
sequenceDiagram
    participant B as Browser
    participant A as API
    B->>A: POST /login (username, password)
    A->>A: verify scrypt hash
    A-->>B: 200 {"token": "3Bt-D6..."}
    B->>A: PATCH /notes/7 + Authorization: Bearer 3Bt-D6...
    A->>A: token belongs to ben, note 7 belongs to ana
    A-->>B: 403 Forbidden
```

**Authorization** decides whether this user may do this action to this record. It's a separate check, and it has to happen on every route that reads or changes something private. This app has the buggy route from the opening next to a fixed one:

```python run title="ownership.py"
import secrets
from fastapi import Depends, FastAPI, Header, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel

notes = {7: {"owner": "ana", "title": "Diary: Nov 3"}}
tokens = {secrets.token_urlsafe(32): "ana", secrets.token_urlsafe(32): "ben"}
token_for = {user: token for token, user in tokens.items()}

class NoteEdit(BaseModel):
    title: str

app = FastAPI()

def current_user(authorization: str = Header(default="")) -> str:
    scheme, _, token = authorization.partition(" ")
    if scheme != "Bearer" or token not in tokens:
        raise HTTPException(401, "Log in first", headers={"WWW-Authenticate": "Bearer"})
    return tokens[token]

@app.patch("/buggy/notes/{note_id}")
def edit_note_buggy(note_id: int, edit: NoteEdit, user: str = Depends(current_user)):
    notes[note_id]["title"] = edit.title  # logged in? yes. owner? never checked
    return notes[note_id]

@app.patch("/notes/{note_id}")
def edit_note(note_id: int, edit: NoteEdit, user: str = Depends(current_user)):
    note = notes.get(note_id)
    if note is None:
        raise HTTPException(404, "Note not found")
    if note["owner"] != user:
        raise HTTPException(403, "That note belongs to someone else")
    note["title"] = edit.title
    return note

client = TestClient(app)
as_user = lambda name: {"Authorization": f"Bearer {token_for[name]}"}
print("ben, buggy route:", client.patch("/buggy/notes/7", json={"title": "lol"}, headers=as_user("ben")).json())
print("no token:  ", client.patch("/notes/7", json={"title": "x"}).status_code)
print("ben:       ", client.patch("/notes/7", json={"title": "x"}, headers=as_user("ben")).status_code)
print("ana:       ", client.patch("/notes/7", json={"title": "Diary"}, headers=as_user("ana")).json())
```

The buggy route let Ben rewrite Ana's note. The fixed one gives 401 with no token ("who are you?") and 403 for Ben ("I know who you are, and no"). Some APIs answer 404 instead, so outsiders can't even learn that note 7 exists.

## CORS and rate limits: two rules people mix up

**CORS** (Cross-Origin Resource Sharing) is enforced by browsers. By default, JavaScript on one origin, such as `https://notes-frontend.example`, can't read responses from a different origin, such as your API. The API opts in by sending an `Access-Control-Allow-Origin` header, which FastAPI's middleware adds for the origins you list:

```python title="cors.py"
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5500"],  # the exact origin of your page
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)
```

CORS protects people's browsers from other websites; it does **not** protect your API. Scripts and `curl` ignore it completely. If the page and the API share an origin, you don't need CORS at all.

A **rate limit** caps how many requests one client (an IP address, an account) can make per time window, say 5 login attempts a minute. Past the limit the server answers `429 Too Many Requests`, often with a `Retry-After` header giving the seconds to wait. That shrinks a password-guessing attack from millions of tries a day to a handful. In production it usually lives in a reverse proxy, the hosting platform, or a library; you'll write a small one in the practice lesson.

:::warning
**Classic mistakes at the boundary.**

- Building SQL with f-strings or `+`. Even "trusted" values like usernames can contain quotes.
- Checking login but not ownership. Every route with a record id in the URL needs the ownership check.
- Hashing with plain `hashlib.sha256(password)`: fast and unsalted means crackable.
- "Fixing" a CORS error with `allow_origins=["*"]` and assuming the API is now protected.
:::

:::quiz
Q: A search route runs `f"SELECT title FROM notes WHERE title LIKE '%{term}%' AND owner = 'ana'"`. Someone searches for `%' --`. What happens?
- [ ] Nothing; `LIKE` can't be injected
  Any value pasted into SQL text can change the query.
- [x] The quote closes the pattern and `--` comments out the owner check, so every user's notes come back
  The rest of the line becomes a comment, so the `AND owner = 'ana'` filter disappears.
- [ ] SQLite raises a syntax error, so it's safe
  The resulting SQL is valid; attackers craft it to be.

Q: Ben sends a valid token and asks to delete Ana's note. Which status best describes the refusal?
- [ ] 401 Unauthorized
  401 means "we don't know who you are". The token proved he's Ben.
- [x] 403 Forbidden (or 404 to hide that the note exists)
  He's authenticated but not authorized for this record.
- [ ] 422 Unprocessable Content
  422 is for malformed input. His request was well-formed.

Q: Why does each user's password get its own random salt?
- [x] So two users with the same password get different hashes, and precomputed tables don't work
  A salt makes every hash unique, forcing an attacker to crack each account separately.
- [ ] So the server can decrypt the password later
  Hashing is one-way; there is nothing to decrypt.
- [ ] Because scrypt runs faster with a salt
  The salt doesn't change speed. Slowness comes from the `n`, `r`, and `p` settings.

Q: Your teammate says "We set CORS to only allow our frontend, so nobody else can call our API." What's wrong?
- [ ] Nothing; that's what CORS is for
  CORS only controls what browsers let other pages read.
- [x] Scripts and tools like `curl` ignore CORS, so the API still needs its own authentication and authorization
  CORS protects users' browsers from other websites, not your server from direct requests.
- [ ] CORS only applies to `GET` requests
  It applies to all methods; some requests even get a preflight `OPTIONS` check.
:::

:::takeaways
- Check every request at the boundary: shape (422), identity (401), permission (403), then run the action.
- Pydantic `Field` limits and `extra="forbid"` stop malformed and over-posted data before your code runs.
- Never build SQL from strings. `?` placeholders keep values from becoming code.
- Store salted, slow hashes (`scrypt`, `pbkdf2_hmac`) and compare with `hmac.compare_digest`.
- Logged in is not the same as allowed: check ownership on every route that touches a private record.
- CORS is a browser rule for reading responses; rate limits slow down guessing. Neither replaces authorization.
:::
