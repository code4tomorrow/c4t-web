Your capstone is a small web app that a real group could start using right away: a book club, a robotics team, a study group, your family's recipe collection. It has a page in the browser, an API behind it, and a SQLite database behind that. People sign up, log in, and can change only what's theirs. When something goes wrong, the page says what and why.

You've already built every piece separately. What's new is fitting them together under your own design, and that goes much faster with an hour of planning first. Most capstones that stall do so because the tables were wrong and every route had to be rewritten.

## What every project must include

| Requirement | What it looks like | Where you learned it |
| --- | --- | --- |
| Relational data | 3+ tables, at least one foreign key, constraints (`NOT NULL`, `UNIQUE`, `CHECK`) | Module 5 |
| Full CRUD | Create, list, view one, update, and delete your main resource | Modules 4 and 7 |
| Accounts | Sign-up, login, salted password hashes, bearer tokens | Module 6 |
| Protected actions | Only the owner (or a role you define) can change or delete a record | Module 6 |
| Validation | A Pydantic model on every body and parameter, with limits | Modules 4 and 6 |
| Useful errors | 401, 403, 404, 409, 422 with clear `detail`; no tracebacks to the client | Module 7 |
| Browser page | Served by the API, uses `fetch`, shows errors on screen | Module 7 |
| Automated tests | `TestClient` tests for each rule, run against a test database | Modules 4 to 7 |
| Documentation | A README with a route table and example JSON, plus FastAPI's `/docs` | This module |

## Pick a project

Choose by what you can finish well. A polished core project beats a half-working stretch one, and the rubric in the last lesson rewards finishing.

| Project | Level | Tables | The interesting part |
| --- | --- | --- | --- |
| **Book club tracker** (built step by step in the next lesson) | Core | users, books, reviews | Average ratings with `GROUP BY`; one review per person per book |
| Club event sign-ups | Core | users, events, signups | A capacity limit: the sign-up that would overfill an event gets 409, checked inside a transaction |
| Recipe box | Core+ | users, recipes, ingredients, recipe_ingredients | A many-to-many with an extra column (quantity), and search by ingredient |
| Study flashcards | Stretch | users, decks, cards, reviews | A "due today" query from review dates, and sharing a deck read-only with a friend |
| Team bug tracker | Stretch | users, projects, memberships, issues | Roles per project (owner, member, viewer) and status rules: only some changes are allowed from each state |

You can propose your own idea too. Check it against the requirements table: if you can't name three tables and one rule about who may change what, it's too small.

## A worked plan: the book club tracker

**User stories** say what people do, in their words. Keep them short and concrete:

1. As a member, I can add a book the club is reading, so others can find it.
2. As a member, I can rate a book from 1 to 5 and leave a comment.
3. As anyone, I can see every book with its average rating and number of reviews.
4. As a reviewer, I can edit or delete my own review, but not someone else's.
5. As the person who added a book, I can remove it (and its reviews go with it).

**Tables** come from the nouns. "Book" and "member" are things, so they're tables. "Rates" connects a member to a book and carries data of its own (the rating and comment), so it's a table too: `reviews`. Rule 2 says one rating per member per book, which becomes `UNIQUE (book_id, user_id)`. Rule 5 becomes `ON DELETE CASCADE`.

## Test the schema before writing any routes

Ten minutes in SQLite now saves hours later. Create the tables, add a few realistic rows, run the hardest query your app needs, and try to break each rule on purpose. If the database refuses the bad rows, those rules can't be skipped by a buggy route later.

```python run title="schema_check.py"
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("PRAGMA foreign_keys = ON")
db.executescript("""
    CREATE TABLE users (
        id INTEGER PRIMARY KEY,
        username TEXT NOT NULL UNIQUE
    );
    CREATE TABLE books (
        id       INTEGER PRIMARY KEY,
        title    TEXT NOT NULL,
        author   TEXT NOT NULL,
        added_by INTEGER NOT NULL REFERENCES users(id),
        UNIQUE (title, author)
    );
    CREATE TABLE reviews (
        id      INTEGER PRIMARY KEY,
        book_id INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
        user_id INTEGER NOT NULL REFERENCES users(id),
        rating  INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5),
        comment TEXT NOT NULL DEFAULT '',
        UNIQUE (book_id, user_id)
    );
    INSERT INTO users (username) VALUES ('ana'), ('ben'), ('chloe');
    INSERT INTO books (title, author, added_by) VALUES
        ('Project Hail Mary', 'Andy Weir', 1),
        ('The Hate U Give', 'Angie Thomas', 2),
        ('Piranesi', 'Susanna Clarke', 1);
    INSERT INTO reviews (book_id, user_id, rating, comment) VALUES
        (1, 1, 5, 'Rocky!'), (1, 2, 4, ''), (2, 3, 5, 'Read it in one night'), (1, 3, 3, 'Slow start');
""")

summary = """
    SELECT books.title, users.username AS added_by,
           COUNT(reviews.id) AS reviews, ROUND(AVG(reviews.rating), 1) AS avg_rating
    FROM books
    JOIN users ON users.id = books.added_by
    LEFT JOIN reviews ON reviews.book_id = books.id
    GROUP BY books.id
    ORDER BY books.title
"""
for row in db.execute(summary):
    print(row)

for bad in ["INSERT INTO reviews (book_id, user_id, rating) VALUES (1, 1, 2)",
            "INSERT INTO reviews (book_id, user_id, rating) VALUES (3, 2, 6)",
            "INSERT INTO reviews (book_id, user_id, rating) VALUES (99, 2, 4)"]:
    try:
        db.execute(bad)
    except sqlite3.IntegrityError as error:
        print("Refused:", error)
```

Piranesi has 0 reviews and an average of `None`, which will arrive in JSON as `null`. That's a decision to make now: the page should show "no ratings yet", not "0 stars". The three refusals are Ana reviewing a book twice, a rating of 6, and a review of a book that doesn't exist. All three are stopped by the schema alone.

## The route table

Each user story becomes one or two routes. Write down, for each, whether it needs a token, who is allowed, and every status it can return. This table becomes both your README and your test plan.

| Route | Token? | Who may | Success | Failures |
| --- | --- | --- | --- | --- |
| `POST /api/signup` | no | anyone | 201 | 409 name taken, 422 |
| `POST /api/login` | no | anyone | 200 `{"token": ...}` | 401 |
| `GET /api/books` | no | anyone | 200, list with ratings | none |
| `POST /api/books` | yes | any member | 201 | 401, 409 already listed, 422 |
| `GET /api/books/{id}` | no | anyone | 200, book with its reviews | 404 |
| `DELETE /api/books/{id}` | yes | whoever added it | 204 | 401, 403, 404 |
| `POST /api/books/{id}/reviews` | yes | any member, once per book | 201 | 401, 404, 409 already reviewed, 422 |
| `PATCH /api/reviews/{id}` | yes | the review's author | 200 | 401, 403, 404, 422 |
| `DELETE /api/reviews/{id}` | yes | the review's author | 204 | 401, 403, 404 |

Write example JSON for the two most important requests too, so the page and the API agree on field names before either exists:

```http
POST /api/books/1/reviews
{"rating": 5, "comment": "Rocky!"}

201 Created
{"id": 1, "book_id": 1, "username": "ana", "rating": 5, "comment": "Rocky!", "created_at": "2026-11-16 18:02:11"}
```

## Your planning template

Copy this into a `PLAN.md` in your project folder and fill it in before you code. Keep it short; a page is plenty.

```text
PROJECT: ____________________   WHO WILL USE IT: ____________________

USER STORIES (4 to 6)
1. As a ______, I can ______, so that ______.

TABLES (name, columns, keys, constraints)
- ______ (id PK, ...)
- ______ (id PK, ..._id FK -> ______, UNIQUE(...), CHECK(...))

THE HARDEST QUERY (write the SQL and test it in SQLite):

ROUTES (method, path, token?, who may, success code, failure codes)

VALIDATION RULES (field: type, limits)

PERMISSION RULES (who may change or delete what)

WHAT THE PAGE SHOWS (screens or sections, and where errors appear)

STRETCH GOALS (only after everything above works)
```

:::tip
Plan the page in plain words too: "a list of books; a form to add one; click a book to see reviews and a form to add mine; a login box at the top". You'll build exactly that, and nothing more until it works.
:::

:::quiz
Q: In the book club, ratings live in their own `reviews` table instead of a `rating` column on `books`. Why?
- [ ] SQLite doesn't allow integer columns on a table that has text columns
  Tables can mix column types freely.
- [x] Many members rate the same book, and each rating also has an author and a comment
  One column can hold one value per book. A rating is a fact about a member and a book together.
- [ ] So the average can be stored instead of computed
  The design computes the average with `AVG`, so it can never go stale.

Q: Which rule is better enforced by the schema than only by route code?
- [ ] "Only the review's author can edit it"
  That depends on who is asking, which only the route knows. It belongs in route code (and tests).
- [x] "A member can review a book at most once"
  `UNIQUE (book_id, user_id)` makes duplicates impossible, even if two requests arrive at the same moment.
- [ ] "Show books in title order"
  That's a choice about how to display data, made with `ORDER BY` in a query.

Q: Your plan's route table lists `DELETE /api/books/{id}` with failures 401, 403, and 404. How does that table help after you've written the code?
- [x] Each failure listed is a test to write, so the table doubles as a test plan
  Every row with three failure codes is three tests, plus one for success.
- [ ] FastAPI reads the table and generates the routes
  FastAPI reads your Python, not your notes.
- [ ] It replaces the need for `/docs`
  `/docs` lists inputs and outputs; your table adds who may do what, which `/docs` doesn't know.
:::

:::takeaways
- Plan first: user stories, then tables, then routes. Nouns become tables; "who does what to which" becomes rules.
- Put every rule the database can enforce into the schema, and test the schema with bad rows before coding.
- A route table with permissions and failure codes is your README and your test plan in one.
- Decide JSON field names and what `null` means on the page before building either side.
:::
