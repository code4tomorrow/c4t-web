## Step 1: Define the resource

A note has three fields. Two of them come from the client, and one is the server's job:

| Field | Type | Rule |
| ----- | ---- | ---- |
| `id` | integer | Set by the server, starting at 1. Never changes, never reused. |
| `title` | string | Required. 1 to 100 characters. |
| `body` | string | Optional, defaults to `""`. At most 2,000 characters. |

"Never reused" is a real decision. If note 1 is deleted and the next note also gets id 1, a client holding a link to `/notes/1` would silently open someone else's note. Limits are decisions too: a title with no maximum lets one request store a 50 MB "title".

The validation rules become a function. Problems use the same `loc` shape FastAPI uses, so clients can find the bad field the same way in the mock and in the real server:

```python run title="notes_contract.py (step 1)"
from urllib.parse import parse_qs, urlsplit

MAX_TITLE = 100
MAX_BODY = 2000
notes = []
next_id = 1


def bad(where, field, msg):
    return {"loc": [where, field], "msg": msg}


def check_note(data, partial=False):
    if not isinstance(data, dict):
        return [{"loc": ["body"], "msg": "must be a JSON object"}]
    problems = []
    if "title" in data or not partial:
        title = data.get("title")
        if not isinstance(title, str):
            problems.append(bad("body", "title", "title is required and must be text"))
        elif not 1 <= len(title) <= MAX_TITLE:
            problems.append(bad("body", "title", f"title must be 1 to {MAX_TITLE} characters"))
    if "body" in data:
        if not isinstance(data["body"], str) or len(data["body"]) > MAX_BODY:
            problems.append(bad("body", "body", f"body must be text of at most {MAX_BODY} characters"))
    return problems


print(check_note({"title": "Buy milk"}))
print(check_note({"body": "no title"}))
print(check_note({"body": "x" * 2001}, partial=True))
```

An empty list means the data passes. `partial=True` is for updates, where the client may send only the fields it wants to change. A missing title is fine there, but a title that **is** sent still has to follow the rules.

## Step 2: Write the endpoint table

This table is the contract. Put it in a docstring at the top of your file so it travels with the code:

| Method and path | Request body | Success | Errors |
| --------------- | ------------ | ------- | ------ |
| `GET /notes?q=&limit=&offset=` | none | `200`, a list of notes | `422` bad `limit` or `offset` |
| `POST /notes` | `{"title", "body"?}` | `201`, the new note | `422` bad fields |
| `GET /notes/{id}` | none | `200`, the note | `404`, `422` id isn't a number |
| `PATCH /notes/{id}` | any of `title`, `body` | `200`, the updated note | `404`, `422` |
| `DELETE /notes/{id}` | none | `204`, no body | `404` |

Errors use `{"detail": "..."}`, and validation errors use `{"detail": [{"loc": [...], "msg": "..."}]}`. For the list: `q` matches title or body, ignoring case; `limit` is 1 to 100 and defaults to 20; `offset` defaults to 0.

Three choices here are worth defending. **PATCH instead of PUT**: a phone app editing a body shouldn't have to resend the title. **A bare list from `GET /notes`**: simpler for clients, and nothing needs a total count yet. (Switching to an envelope later would break clients, so it would go in `/v2`.) **No delete-everything endpoint**: `DELETE /notes` would be one typo away from disaster, so it doesn't exist, and asking gets a `405`.

## Step 3: The collection functions

Each endpoint becomes a function that returns `(status, json)`. These two handle `/notes`. Remember from Module 2 that query values arrive as **strings**, so `limit` has to be checked and converted:

```python run title="notes_contract.py (step 3)"
def read_int(query, name, default, low, high):
    text = query.get(name, [str(default)])[0]
    if not text.isdigit() or not low <= int(text) <= high:
        return None, bad("query", name, f"{name} must be a whole number from {low} to {high}")
    return int(text), None


def list_notes(query):
    limit, problem1 = read_int(query, "limit", 20, 1, 100)
    offset, problem2 = read_int(query, "offset", 0, 0, 10**9)
    problems = [p for p in (problem1, problem2) if p]
    if problems:
        return 422, {"detail": problems}
    q = query.get("q", [""])[0].lower()
    matches = [n for n in notes if q in n["title"].lower() or q in n["body"].lower()]
    return 200, matches[offset:offset + limit]


def create_note(data):
    global next_id
    problems = check_note(data)
    if problems:
        return 422, {"detail": problems}
    note = {"id": next_id, "title": data["title"], "body": data.get("body", "")}
    next_id += 1
    notes.append(note)
    return 201, note


print(create_note({"title": "Buy milk"}))
print(create_note({"title": ""}))
print(list_notes({"limit": ["5"]}))
print(list_notes({"limit": ["500"]}))
```

`create_note` builds the stored note itself, field by field, instead of saving whatever the client sent. A client that sends `{"title": "Hi", "id": 999, "admin": true}` gets id 1 and nothing else. That habit matters a lot in Module 6.

## Step 4: The item functions

These handle `/notes/{id}`. All three start with the same lookup, and all three give the same `404` when it fails:

```python run title="notes_contract.py (step 4)"
def find(note_id):
    for note in notes:
        if note["id"] == note_id:
            return note
    return None


def get_note(note_id):
    note = find(note_id)
    if note is None:
        return 404, {"detail": f"Note {note_id} not found"}
    return 200, note


def update_note(note_id, data):
    note = find(note_id)
    if note is None:
        return 404, {"detail": f"Note {note_id} not found"}
    problems = check_note(data, partial=True)
    if problems:
        return 422, {"detail": problems}
    for field in ("title", "body"):
        if field in data:
            note[field] = data[field]
    return 200, note


def delete_note(note_id):
    note = find(note_id)
    if note is None:
        return 404, {"detail": f"Note {note_id} not found"}
    notes.remove(note)
    return 204, None


print(update_note(1, {"body": "2 cartons"}))
print(get_note(42))
print(delete_note(1), delete_note(1))
```

The 404 check comes **before** validation in `update_note`. If you PATCH a note that doesn't exist with bad data, "not found" is the more useful answer; there's no point fixing the data for a note that isn't there.

## Step 5: The router

A real server receives a method and a URL, not a function call. The router's job is to pick the function, and it's the part FastAPI will do for you next module:

```python run title="notes_contract.py (step 5)"
def handle(method, url, body=None):
    parts = urlsplit(url)
    segments = [s for s in parts.path.split("/") if s]
    query = parse_qs(parts.query)
    if segments == ["notes"]:
        if method == "GET":
            return list_notes(query)
        if method == "POST":
            return create_note(body)
        return 405, {"detail": "Method Not Allowed"}
    if len(segments) == 2 and segments[0] == "notes":
        if not segments[1].isdigit():
            return 422, {"detail": [bad("path", "note_id", "note_id must be a whole number")]}
        note_id = int(segments[1])
        if method == "GET":
            return get_note(note_id)
        if method == "PATCH":
            return update_note(note_id, body)
        if method == "DELETE":
            return delete_note(note_id)
        return 405, {"detail": "Method Not Allowed"}
    return 404, {"detail": "Not Found"}


print(handle("POST", "/notes", {"title": "Essay outline"}))
print(handle("DELETE", "/notes"))
print(handle("GET", "/notes/abc"))
print(handle("GET", "/tasks"))
```

Notice the order of questions: does the path exist (404), does it allow this method (405), is the id well formed (422), does the note exist (404 from the function). That order matches what FastAPI does, which is why the mock and the real server will agree.

## Step 6: Examples that check any implementation

Now the most valuable part. Each example is one exchange from the contract: method, URL, body, expected status, and expected JSON. For `422` it's the `loc` that must appear, not the exact message, because message wording is allowed to change but the field it points at isn't.

```python run title="notes_contract.py (step 6)"
MILK = {"id": 1, "title": "Buy milk", "body": ""}
ESSAY = {"id": 2, "title": "Essay outline", "body": "Intro, three points, conclusion"}

EXAMPLES = [
    ("POST", "/notes", {"title": "Buy milk"}, 201, MILK),
    ("POST", "/notes", {"title": "Essay outline", "body": "Intro, three points, conclusion"}, 201, ESSAY),
    ("GET", "/notes", None, 200, [MILK, ESSAY]),
    ("GET", "/notes?q=ESSAY", None, 200, [ESSAY]),
    ("GET", "/notes?limit=1&offset=1", None, 200, [ESSAY]),
    ("GET", "/notes/2", None, 200, ESSAY),
    ("GET", "/notes/99", None, 404, {"detail": "Note 99 not found"}),
    ("GET", "/notes/abc", None, 422, ["path", "note_id"]),
    ("GET", "/notes?limit=0", None, 422, ["query", "limit"]),
    ("POST", "/notes", {"body": "no title"}, 422, ["body", "title"]),
    ("POST", "/notes", {"title": ""}, 422, ["body", "title"]),
    ("PATCH", "/notes/1", {"body": "2 cartons"}, 200, {**MILK, "body": "2 cartons"}),
    ("DELETE", "/notes/1", None, 204, None),
    ("DELETE", "/notes/1", None, 404, {"detail": "Note 1 not found"}),
    ("POST", "/notes", {"title": "Call Sam"}, 201, {"id": 3, "title": "Call Sam", "body": ""}),
]


def check_examples(send):
    passed = 0
    for method, url, body, status, expected in EXAMPLES:
        got_status, got = send(method, url, body)
        if got_status != status:
            ok = False
        elif status == 422:
            ok = any(problem["loc"] == expected for problem in got["detail"])
        else:
            ok = got == expected
        passed += ok
        print(f"{'PASS' if ok else 'FAIL'}  {method:6} {url:24} {got_status}")
    print(f"{passed} of {len(EXAMPLES)} examples match the contract")


notes.clear()   # start from an empty store, as a fresh server would
next_id = 1
check_examples(handle)
```

`check_examples` takes a `send` function instead of calling `handle` directly. That one choice is what lets you reuse it: in Module 4 you'll write a three-line `send` that uses TestClient, and the same examples will check your FastAPI server. The last example proves the "never reuse ids" rule: after note 1 is deleted, the next note is 3.

## The finished file

Here's `notes_contract.py` in one piece, with the endpoint table in a docstring at the top. Run it with the play button. If a change to the mock ever makes an example fail, you've either found a bug or changed the contract, and both are worth knowing before a client finds out.

```python run title="http-practice/notes_contract.py"
"""Notes API contract, version 1.

GET    /notes?q=&limit=&offset=   200 list of notes        422 bad limit/offset
POST   /notes                     201 the new note         422 bad fields
GET    /notes/{id}                200 the note             404, 422 id not a number
PATCH  /notes/{id}                200 the updated note     404, 422
DELETE /notes/{id}                204 no body              404

Note: id (int, set by server, never reused), title (1-100 chars),
body (0-2000 chars, default ""). Errors: {"detail": "..."}; validation
errors: {"detail": [{"loc": [...], "msg": "..."}]}. limit 1-100 (default 20).
"""
from urllib.parse import parse_qs, urlsplit

MAX_TITLE = 100
MAX_BODY = 2000
notes = []
next_id = 1


def bad(where, field, msg):
    return {"loc": [where, field], "msg": msg}


def check_note(data, partial=False):
    if not isinstance(data, dict):
        return [{"loc": ["body"], "msg": "must be a JSON object"}]
    problems = []
    if "title" in data or not partial:
        title = data.get("title")
        if not isinstance(title, str):
            problems.append(bad("body", "title", "title is required and must be text"))
        elif not 1 <= len(title) <= MAX_TITLE:
            problems.append(bad("body", "title", f"title must be 1 to {MAX_TITLE} characters"))
    if "body" in data:
        if not isinstance(data["body"], str) or len(data["body"]) > MAX_BODY:
            problems.append(bad("body", "body", f"body must be text of at most {MAX_BODY} characters"))
    return problems


def find(note_id):
    for note in notes:
        if note["id"] == note_id:
            return note
    return None


def read_int(query, name, default, low, high):
    text = query.get(name, [str(default)])[0]
    if not text.isdigit() or not low <= int(text) <= high:
        return None, bad("query", name, f"{name} must be a whole number from {low} to {high}")
    return int(text), None
```

:::quiz
Q: Why does the contract say ids are never reused after a delete?
- [ ] Reusing ids is impossible in Python
  It's easy; the risk is what clients do with old ids.
- [x] A client holding `/notes/1` could open a different note that later got id 1
  Ids are addresses. Reusing one quietly redirects every saved link to the wrong thing.
- [ ] It makes the list endpoint faster
  Speed doesn't change. It's about every saved link pointing at the right note.

Q: Why do the `422` examples check `loc` rather than the exact `msg` text?
- [x] The contract promises which field was wrong, but message wording may change
  Clients should highlight the field named in `loc`. FastAPI and the mock word their messages differently, yet both pass.
- [ ] `msg` is always empty in a 422
  Both the mock and FastAPI fill in `msg` for people to read.
- [ ] `loc` is shorter to type
  The reason is stability: `loc` is part of the contract, wording isn't.

Q: Why does `check_examples` take a `send` function instead of calling `handle` itself?
- [ ] Python requires it
  It would run fine calling `handle` directly.
- [x] So the same examples can check a different implementation, like the FastAPI server, without changes
  Swap in a `send` that uses TestClient, and the contract checks the real thing.
:::

:::takeaways
- Write the contract first: fields with rules, an endpoint table, success codes, error codes, and one error shape.
- Limits, defaults, and "never reuse ids" are design decisions. Write them down.
- Build stored data yourself instead of saving whatever the client sent.
- Example exchanges make a contract checkable. Compare status and JSON, and for `422`, the `loc`.
:::

## Ideas to extend it

- Add a `pinned` field (boolean, default `false`) and a `?pinned=true` filter. Update the table and the examples first, then the mock.
- Change `GET /notes` to return an envelope `{"items": [...], "total": n}` in a `/v2/notes` route, keeping `/notes` as it is.
- Add `PUT /notes/{id}`, which replaces both fields, and write examples showing how it differs from PATCH when `body` is left out.
