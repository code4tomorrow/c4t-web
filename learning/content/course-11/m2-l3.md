## Warm-up: who moves next?

Without looking anything up, say who has to act after each response: the client, the server's developers, or nobody.

`201` · `304` · `403` · `422` · `503` · `204`

:::solution
`201` and `204`: nobody, it worked. `304`: nobody, really; the client uses the copy it already has. `403` and `422`: the client, which must change the request (or accept the answer). `503`: the server's side, since it's down or overloaded, and the client can only try again later.
:::

### Exercise 1: Take a URL apart

Write `describe(url)` that prints the host, the path as a list of segments, and the query as a dict of **single** values (not lists). Test it on `https://api.github.com/repos/fastapi/fastapi/issues?state=open&per_page=5`.

```text
host: api.github.com
segments: ['repos', 'fastapi', 'fastapi', 'issues']
query: {'state': 'open', 'per_page': '5'}
```

:::hint
`urlsplit` gives you `.netloc`, `.path`, and `.query`. Split the path on `/` and drop empty strings. `parse_qs` returns lists, so keep the first item of each.
:::

:::solution
```python run title="http-practice/describe_url.py"
from urllib.parse import parse_qs, urlsplit


def describe(url):
    parts = urlsplit(url)
    segments = [piece for piece in parts.path.split("/") if piece]
    query = {name: values[0] for name, values in parse_qs(parts.query).items()}
    print("host:", parts.netloc)
    print("segments:", segments)
    print("query:", query)


describe("https://api.github.com/repos/fastapi/fastapi/issues?state=open&per_page=5")
```

The path starts with `/`, so splitting it gives an empty string first; the `if piece` filter drops it. Notice `'5'` is still a string. Query values are always text until your code converts them.
:::

### Exercise 2: Build a search URL safely

Write `search_url(text, page=1)` that returns a GitHub repository search URL like `https://api.github.com/search/repositories?q=...&page=...`. It must work for `"fastapi tutorial"` and for `"c++ & rust"`.

```text
https://api.github.com/search/repositories?q=fastapi+tutorial&page=1
https://api.github.com/search/repositories?q=c%2B%2B+%26+rust&page=3
```

:::hint
Gluing strings with f-strings breaks on the second example: the `&` would start a new parameter, and the server would read each `+` as a space. `urllib.parse.urlencode` takes a dict and escapes every value.
:::

:::solution
```python run title="http-practice/search_url.py"
from urllib.parse import urlencode

BASE = "https://api.github.com/search/repositories"


def search_url(text, page=1):
    return f"{BASE}?{urlencode({'q': text, 'page': page})}"


print(search_url("fastapi tutorial"))
print(search_url("c++ & rust", page=3))
```

`+` became `%2B` because in a query string a bare `+` means a space. Without the encoding, the pluses would turn into spaces, the server would search for just `c`, and ` rust` would arrive as a stray parameter with no value.
:::

### Exercise 3: Who acts next, in code

Write `who_acts(code)` that returns `"nobody"` for 2xx, `"client (redirect or cache)"` for 3xx, `"client (fix the request)"` for 4xx, and `"server"` for 5xx. Anything outside 100–599 should raise `ValueError`. Then print a line for `[200, 304, 404, 422, 500, 99]`.

```text
200 nobody
304 client (redirect or cache)
404 client (fix the request)
422 client (fix the request)
500 server
99 ValueError: not an HTTP status: 99
```

:::hint
Integer division by 100 gives the class: `404 // 100` is `4`. Handle the 1xx informational codes however you like; the sample doesn't use one.
:::

:::solution
```python run title="http-practice/who_acts.py"
def who_acts(code):
    if not 100 <= code <= 599:
        raise ValueError(f"not an HTTP status: {code}")
    return {
        1: "nobody (still working)",
        2: "nobody",
        3: "client (redirect or cache)",
        4: "client (fix the request)",
        5: "server",
    }[code // 100]


for code in [200, 304, 404, 422, 500, 99]:
    try:
        print(code, who_acts(code))
    except ValueError as error:
        print(code, f"ValueError: {error}")
```

A lookup dict keyed by the first digit replaces a chain of `if` statements, and the range check runs first so `99 // 100` (which is `0`) never reaches the lookup.
:::

### Exercise 4: Diagnose four failed exchanges

For each one, say which side is at fault and what change fixes it. No code needed.

1. In bash, `curl https://api.github.com/users/octocat/repos?per_page=2&sort=updated` returns two repos, but not sorted by update time.
2. `POST /notes` with body `{"text": "Buy milk"}` returns `422` and `{"detail":[{"type":"missing","loc":["body","title"],"msg":"Field required"}]}`.
3. `GET /notes/7` returns `500` and the plain text `Internal Server Error`.
4. `DELETE /notes` returns `405` and the header `allow: GET, POST`.

:::hint
For each, read the status class first, then the detail. `loc` in a 422 is a path to the bad field. An `allow` header lists the methods the path does accept.
:::

:::solution
| # | At fault | Fix |
| - | -------- | --- |
| 1 | Client (the shell) | The unquoted `&` sent curl to the background with only `per_page=2`. Quote the URL. |
| 2 | Client | The server wants `title`, and `loc: ["body", "title"]` says so. Send `{"title": "Buy milk"}`. |
| 3 | Server | A 500 is always a server bug. Read the traceback in the server terminal and handle that case with a 4xx. |
| 4 | Client | `/notes` is the whole collection and doesn't accept DELETE. Delete one note: `DELETE /notes/7`. |
:::

### Exercise 5: Build a response by hand

Write `make_response(status, data)` that returns the full bytes of an HTTP/1.1 response: status line, `content-type: application/json`, a correct `content-length`, a blank line, and the JSON body. Lines end in `\r\n`. Test it with `{"city": "São Paulo"}`, keeping the `ã` as is.

```text
HTTP/1.1 200 OK
content-type: application/json
content-length: 22

{"city": "São Paulo"}
```

:::hint
`content-length` counts **bytes**, not characters. `ã` is one character but two bytes in UTF-8, so `len()` of the string gives the wrong answer. Encode first, then measure.
:::

:::solution
```python run title="http-practice/make_response.py"
import json
from http import HTTPStatus


def make_response(status, data):
    body = json.dumps(data, ensure_ascii=False).encode("utf-8")
    head = (
        f"HTTP/1.1 {status} {HTTPStatus(status).phrase}\r\n"
        "content-type: application/json\r\n"
        f"content-length: {len(body)}\r\n"
        "\r\n"
    )
    return head.encode("ascii") + body


data = {"city": "São Paulo"}
print("characters:", len(json.dumps(data, ensure_ascii=False)))
print(make_response(200, data).decode("utf-8"))
```

The string is 21 characters but 22 bytes. A server that sent `content-length: 21` would cut off the closing `}`, and the client's JSON parser would fail on a response that looks fine when you print it.
:::

### Exercise 6: Parse a request with a body

A server receives this text. Write `parse_request(raw)` that returns a dict with `method`, `path`, `query` (single values), `headers` (lowercase names), and `json` (the parsed body, or `None` if the content type isn't JSON).

```python
raw = (
    "POST /notes?draft=true HTTP/1.1\r\n"
    "Host: 127.0.0.1:8000\r\n"
    "Content-Type: application/json\r\n"
    "Content-Length: 39\r\n"
    "\r\n"
    '{"title": "Buy milk", "body": "2 cartons"}'
)
```

```text
POST /notes {'draft': 'true'}
{'host': '127.0.0.1:8000', 'content-type': 'application/json', 'content-length': '39'}
{'title': 'Buy milk', 'body': '2 cartons'}
```

:::hint
Reuse the trace from the Notes lesson for the head, `partition("?")` for the query, and only call `json.loads` when the content type contains `json`. (The `Content-Length` here is wrong on purpose; the solution explains why that matters.)
:::

:::solution
```python run title="http-practice/parse_request.py"
import json
from urllib.parse import parse_qs


def parse_request(raw):
    head, _, body = raw.partition("\r\n\r\n")
    request_line, *header_lines = head.split("\r\n")
    method, target, _version = request_line.split(" ")
    path, _, query_text = target.partition("?")
    headers = {}
    for line in header_lines:
        name, _, value = line.partition(":")
        headers[name.strip().lower()] = value.strip()
    parsed = json.loads(body) if "json" in headers.get("content-type", "") else None
    return {
        "method": method,
        "path": path,
        "query": {k: v[0] for k, v in parse_qs(query_text).items()},
        "headers": headers,
        "json": parsed,
    }


raw = (
    "POST /notes?draft=true HTTP/1.1\r\n"
    "Host: 127.0.0.1:8000\r\n"
    "Content-Type: application/json\r\n"
    "Content-Length: 39\r\n"
    "\r\n"
    '{"title": "Buy milk", "body": "2 cartons"}'
)
request = parse_request(raw)
print(request["method"], request["path"], request["query"])
print(request["headers"])
print(request["json"])
print("body is really", len('{"title": "Buy milk", "body": "2 cartons"}'.encode()), "bytes")
```

`partition(":")` splits at the first colon only, which matters for the `Host` header: its value `127.0.0.1:8000` contains another colon. The last line shows the body is 42 bytes, not 39. A real server trusts `Content-Length` to know where the body ends, so it would read 39 bytes and hand your code broken JSON. Libraries like curl and httpx compute it for you, which is a good reason never to set it by hand.
:::

### Challenge: Answer "has it changed?" with an ETag

GitHub sent `etag: W/"937b..."` with octocat's profile. A client can send that value back in an `If-None-Match` header, and if nothing changed, the server answers `304 Not Modified` with no body. That saves sending 1,350 bytes again.

Write `respond(request_headers, data)` that computes an ETag from the JSON body (use `hashlib.sha256`, first 12 hex characters, wrapped in double quotes) and returns `(status, headers, body)`: a `304` with an empty body if `If-None-Match` matches, otherwise a `200` with the body and an `etag` header. Show three calls: a first visit, a repeat visit with the ETag, and a visit after the data changed.

:::hint
Compute the body bytes first, hash them, then compare with `request_headers.get("if-none-match")`. Return the `etag` header on the 304 too, so the client keeps the current value.
:::

:::solution
```python run title="http-practice/etag.py"
import hashlib
import json


def respond(request_headers, data):
    body = json.dumps(data).encode("utf-8")
    etag = '"' + hashlib.sha256(body).hexdigest()[:12] + '"'
    if request_headers.get("if-none-match") == etag:
        return 304, {"etag": etag}, b""
    return 200, {"etag": etag, "content-length": str(len(body))}, body


profile = {"login": "octocat", "public_repos": 8}
status, headers, body = respond({}, profile)
print("first visit: ", status, headers, len(body), "bytes")

status, again, body = respond({"if-none-match": headers["etag"]}, profile)
print("repeat visit:", status, again, len(body), "bytes")

profile["public_repos"] = 9
status, changed, body = respond({"if-none-match": headers["etag"]}, profile)
print("after change:", status, changed, len(body), "bytes")
```

The hash changes whenever a single byte of the body changes, so the third request gets a full `200` with a new ETag. That's the whole idea behind `304`: the client proves which version it has, and the server only sends data when there's something new. GitHub's `W/` prefix marks a "weak" ETag, which promises the same meaning rather than identical bytes.
:::
