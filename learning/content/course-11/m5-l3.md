summary: Write filters, joins, grouped counts, a many-to-many design, a transactional checkout, and a normalization script against a small SQLite library.

:::objectives
- Write `WHERE`/`ORDER BY` filters and multi-table joins from a plain-English request.
- Find missing matches with `LEFT JOIN ... IS NULL`.
- Summarize with `GROUP BY` and `HAVING`.
- Design a many-to-many table and a transaction that keeps two tables consistent.
:::

Every exercise uses the same small school library. Run the setup program once; it writes `library.db` next to it, and each solution opens that file. Exercises 5 and 6 change the database, so if you want to start over, delete `library.db` and run the setup again.

```python run title="library_setup.py"
import sqlite3

db = sqlite3.connect("library.db")
db.executescript("""
    CREATE TABLE students (
        id    INTEGER PRIMARY KEY,
        name  TEXT NOT NULL,
        grade INTEGER NOT NULL CHECK (grade BETWEEN 6 AND 12)
    );
    CREATE TABLE books (
        id     INTEGER PRIMARY KEY,
        title  TEXT NOT NULL,
        author TEXT NOT NULL,
        year   INTEGER NOT NULL,
        copies_available INTEGER NOT NULL CHECK (copies_available >= 0)
    );
    CREATE TABLE loans (
        id          INTEGER PRIMARY KEY,
        book_id     INTEGER NOT NULL REFERENCES books(id),
        student_id  INTEGER NOT NULL REFERENCES students(id),
        borrowed_on TEXT NOT NULL,
        returned_on TEXT
    );
    INSERT INTO students (name, grade) VALUES
        ('Ava', 10), ('Jonah', 9), ('Mei', 11), ('Tariq', 10);
    INSERT INTO books (title, author, year, copies_available) VALUES
        ('The Hobbit', 'J.R.R. Tolkien', 1937, 1),
        ('Dune', 'Frank Herbert', 1965, 0),
        ('Hatchet', 'Gary Paulsen', 1987, 2),
        ('The Hate U Give', 'Angie Thomas', 2017, 0),
        ('Project Hail Mary', 'Andy Weir', 2021, 1),
        ('Ready Player One', 'Ernest Cline', 2011, 1);
    INSERT INTO loans (book_id, student_id, borrowed_on, returned_on) VALUES
        (1, 1, '2026-09-03', '2026-09-20'),
        (2, 1, '2026-09-21', NULL),
        (5, 2, '2026-10-01', '2026-10-15'),
        (4, 3, '2026-10-05', NULL),
        (1, 3, '2026-10-20', NULL),
        (5, 1, '2026-11-01', NULL),
        (3, 2, '2026-11-02', NULL);
""")
db.commit()
for table in ["students", "books", "loans"]:  # our own table names, never user input
    print(table, db.execute(f"SELECT COUNT(*) FROM {table}").fetchone()[0])
db.close()
```

## Warm-up: predict the order

Before running it, write down what this prints: `SELECT title FROM books WHERE year < 1990 ORDER BY year DESC`.

```python run title="warmup.py"
import sqlite3

db = sqlite3.connect("library.db")
print(db.execute("SELECT title FROM books WHERE year < 1990 ORDER BY year DESC").fetchall())
```

`WHERE` keeps the three older books, then `DESC` puts the largest year (1987) first. Each row comes back as a tuple, which is why every title sits inside its own parentheses.

### Exercise 1: Recent books, newest first

Print the title and year of every book published in 2000 or later, newest first.

```text
('Project Hail Mary', 2021)
('The Hate U Give', 2017)
('Ready Player One', 2011)
```

:::hint
One `WHERE` with `>=`, then `ORDER BY` the same column with `DESC`. Select only the two columns you need.
:::

:::solution
```python run title="ex1_recent.py"
import sqlite3

db = sqlite3.connect("library.db")
for row in db.execute("SELECT title, year FROM books WHERE year >= 2000 ORDER BY year DESC"):
    print(row)
```

`>= 2000` includes the boundary year. Asking for `title, year` instead of `*` keeps the output to what the request asked for, which is also what an API response should do.
:::

### Exercise 2: Who has which book right now?

List every loan that hasn't been returned, as (student name, book title, borrowed date), oldest loan first.

```text
('Ava', 'Dune', '2026-09-21')
('Mei', 'The Hate U Give', '2026-10-05')
('Mei', 'The Hobbit', '2026-10-20')
('Ava', 'Project Hail Mary', '2026-11-01')
('Jonah', 'Hatchet', '2026-11-02')
```

:::hint
Start `FROM loans` and join `students` and `books` to it. An unreturned loan has `returned_on` set to `NULL`, and `returned_on = NULL` is never true, not even for `NULL`. SQL has a special operator for this test.
:::

:::solution
```python run title="ex2_out_now.py"
import sqlite3

db = sqlite3.connect("library.db")
print("Using = NULL finds", db.execute("SELECT COUNT(*) FROM loans WHERE returned_on = NULL").fetchone()[0], "loans")
query = """
    SELECT students.name, books.title, loans.borrowed_on
    FROM loans
    JOIN students ON students.id = loans.student_id
    JOIN books    ON books.id = loans.book_id
    WHERE loans.returned_on IS NULL
    ORDER BY loans.borrowed_on
"""
for row in db.execute(query):
    print(row)
```

`NULL` means "unknown", and comparing anything to unknown gives unknown, so `= NULL` matches nothing. `IS NULL` is the test that works.
:::

### Exercise 3: Never borrowed

Print the titles of books that have never been borrowed, then the names of students who have never borrowed anything.

```text
[('Ready Player One',)]
[('Tariq',)]
```

:::hint
A `LEFT JOIN` from `books` to `loans` keeps every book. For a book with no loans, every `loans` column in that row is `NULL`. Filter on one of them.
:::

:::solution
```python run title="ex3_never.py"
import sqlite3

db = sqlite3.connect("library.db")
print(db.execute("""
    SELECT books.title FROM books
    LEFT JOIN loans ON loans.book_id = books.id
    WHERE loans.id IS NULL
""").fetchall())
print(db.execute("""
    SELECT students.name FROM students
    LEFT JOIN loans ON loans.student_id = students.id
    WHERE loans.id IS NULL
""").fetchall())
```

This "anti-join" pattern answers every "which X has no Y?" question. Test a column that can never be `NULL` in a real match, like the primary key `loans.id`.
:::

### Exercise 4: Frequent borrowers

For each student with **two or more** loans in total, print their name, total loans, and how many are still out. Sort by total, highest first, then by name.

```text
('Ava', 3, 2)
('Jonah', 2, 1)
('Mei', 2, 2)
```

:::hint
`GROUP BY students.id`, `COUNT(loans.id)` for the total, and `HAVING` for the "two or more" rule. In SQLite a comparison like `returned_on IS NULL` evaluates to 1 or 0, so you can add it up with `SUM`.
:::

:::solution
```python run title="ex4_frequent.py"
import sqlite3

db = sqlite3.connect("library.db")
query = """
    SELECT students.name,
           COUNT(loans.id) AS total,
           SUM(loans.returned_on IS NULL) AS still_out
    FROM students
    JOIN loans ON loans.student_id = students.id
    GROUP BY students.id
    HAVING total >= 2
    ORDER BY total DESC, students.name
"""
for row in db.execute(query):
    print(row)
```

`HAVING` runs after the groups are built, so it can use the `total` alias. A `WHERE total >= 2` would fail, because `WHERE` runs on single rows before any counting happens.
:::

### Exercise 5: Design the clubs feature

The library runs reading clubs, and a student can join any number of them. Add `clubs` and `club_members` tables, put Ava, Jonah, and Tariq in the Sci-fi club and Mei and Ava in the Poetry club, and create an empty Manga club. Show that adding Jonah to the Sci-fi club a second time is rejected, then print every club with its member count.

```text
Rejected: UNIQUE constraint failed: club_members.club_id, club_members.student_id
('Sci-fi club', 3)
('Poetry club', 2)
('Manga club', 0)
```

:::hint
This is many-to-many, so it needs a linking table with two foreign keys. Making the pair of columns the primary key is what rejects the duplicate. For the counts, remember the `COUNT(*)` trap with `LEFT JOIN`.
:::

:::solution
```python run title="ex5_clubs.py"
import sqlite3

db = sqlite3.connect("library.db")
db.execute("PRAGMA foreign_keys = ON")
db.executescript("""
    CREATE TABLE clubs (
        id   INTEGER PRIMARY KEY,
        name TEXT NOT NULL UNIQUE
    );
    CREATE TABLE club_members (
        club_id    INTEGER NOT NULL REFERENCES clubs(id),
        student_id INTEGER NOT NULL REFERENCES students(id),
        PRIMARY KEY (club_id, student_id)
    );
    INSERT INTO clubs (name) VALUES ('Sci-fi club'), ('Poetry club'), ('Manga club');
    INSERT INTO club_members VALUES (1, 1), (1, 2), (1, 4), (2, 3), (2, 1);
""")
try:
    db.execute("INSERT INTO club_members VALUES (1, 2)")
except sqlite3.IntegrityError as error:
    print("Rejected:", error)

for row in db.execute("""
    SELECT clubs.name, COUNT(club_members.student_id) AS members
    FROM clubs LEFT JOIN club_members ON club_members.club_id = clubs.id
    GROUP BY clubs.id
    ORDER BY members DESC, clubs.name
"""):
    print(row)
db.commit()
db.close()
```

The error names both columns because the uniqueness rule covers the pair. Ava appears in two clubs, which is fine: only the same pair twice is refused.
:::

### Exercise 6: A checkout that can't half-happen

Write `checkout(conn, book_id, student_id, day)` that adds a loan **and** lowers that book's `copies_available` by one. If either step fails, neither should stick. Check out Hatchet (book 3) for Tariq (student 4), then try Dune (book 2), which has no copies left.

```text
Hatchet copies: 1 | loans: 8
Dune checkout failed: CHECK constraint failed: copies_available >= 0
Dune copies: 0 | loans: 8
```

:::hint
Do the `INSERT` first and the `UPDATE` second, inside one `with conn:` block. The `CHECK (copies_available >= 0)` rule from the setup refuses the update, and the block has to undo the insert that already ran.
:::

:::video GAe5oB742dw
What to watch for: the "atomicity" part, which is exactly the guarantee this exercise relies on. The rest of ACID (consistency, isolation, durability) is worth a listen too.
:::

:::solution
```python run title="ex6_checkout.py"
import sqlite3

def checkout(conn, book_id, student_id, day):
    with conn:
        conn.execute(
            "INSERT INTO loans (book_id, student_id, borrowed_on) VALUES (?, ?, ?)",
            (book_id, student_id, day),
        )
        conn.execute(
            "UPDATE books SET copies_available = copies_available - 1 WHERE id = ?",
            (book_id,),
        )

conn = sqlite3.connect("library.db")
conn.execute("PRAGMA foreign_keys = ON")
loans = lambda: conn.execute("SELECT COUNT(*) FROM loans").fetchone()[0]
copies = lambda book_id: conn.execute(
    "SELECT copies_available FROM books WHERE id = ?", (book_id,)
).fetchone()[0]

checkout(conn, 3, 4, "2026-11-10")
print("Hatchet copies:", copies(3), "| loans:", loans())
try:
    checkout(conn, 2, 4, "2026-11-10")
except sqlite3.IntegrityError as error:
    print("Dune checkout failed:", error)
print("Dune copies:", copies(2), "| loans:", loans())
conn.close()
```

The loan count stayed at 8 after the Dune attempt, so the inserted loan was rolled back with the failed update. Without `with conn:` (and with a `commit()` after each statement), the library would record a loan for a book it doesn't have. Notice also that `copies_available - 1` is computed inside SQL, so two checkouts at once can't both read "1" and both write "0".
:::

### Challenge: Normalize a flat order sheet with SQL alone

The school store logged orders in one table that repeats each customer's email and each product's price on every line. Split it into `customers`, `products`, `orders`, and `order_lines` using only `INSERT INTO ... SELECT` (no Python loops). Then prove nothing was lost: a join across the new tables should give back exactly the original rows.

```text
Rows in each table: {'customers': 3, 'products': 3, 'orders': 4, 'order_lines': 5}
Rows lost: [] | Rows invented: []
```

:::hint
`SELECT DISTINCT customer, email FROM flat_orders` gives one row per customer. To fill `orders` and `order_lines`, join `flat_orders` to the new tables on a column that's unique there (email for customers, name for products) to look up the new ids. SQL's `EXCEPT` returns rows in the first query that aren't in the second; try it in both directions.
:::

:::solution
```python run title="normalize_orders.py"
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE flat_orders (order_id INTEGER, customer TEXT, email TEXT,
                              product TEXT, price REAL, qty INTEGER);
    INSERT INTO flat_orders VALUES
        (1, 'Ava',   'ava@school.org',   'Notebook', 3.50, 2),
        (1, 'Ava',   'ava@school.org',   'Pen',      1.25, 5),
        (2, 'Jonah', 'jonah@school.org', 'Notebook', 3.50, 1),
        (3, 'Ava',   'ava@school.org',   'Stickers', 2.00, 1),
        (4, 'Mei',   'mei@school.org',   'Pen',      1.25, 3);

    CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL UNIQUE);
    CREATE TABLE products  (id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE, price REAL NOT NULL);
    CREATE TABLE orders    (id INTEGER PRIMARY KEY,
                            customer_id INTEGER NOT NULL REFERENCES customers(id));
    CREATE TABLE order_lines (
        order_id   INTEGER NOT NULL REFERENCES orders(id),
        product_id INTEGER NOT NULL REFERENCES products(id),
        qty        INTEGER NOT NULL CHECK (qty > 0),
        PRIMARY KEY (order_id, product_id)
    );

    INSERT INTO customers (name, email) SELECT DISTINCT customer, email FROM flat_orders;
    INSERT INTO products (name, price)  SELECT DISTINCT product, price FROM flat_orders;
    INSERT INTO orders (id, customer_id)
        SELECT DISTINCT f.order_id, c.id FROM flat_orders f JOIN customers c ON c.email = f.email;
    INSERT INTO order_lines (order_id, product_id, qty)
        SELECT f.order_id, p.id, f.qty FROM flat_orders f JOIN products p ON p.name = f.product;
""")

rebuilt = """
    SELECT o.id, c.name, c.email, p.name, p.price, l.qty
    FROM order_lines l
    JOIN orders o    ON o.id = l.order_id
    JOIN customers c ON c.id = o.customer_id
    JOIN products p  ON p.id = l.product_id
"""
original = "SELECT * FROM flat_orders"
counts = {t: db.execute(f"SELECT COUNT(*) FROM {t}").fetchone()[0]
          for t in ["customers", "products", "orders", "order_lines"]}
print("Rows in each table:", counts)
print("Rows lost:", db.execute(f"{original} EXCEPT {rebuilt}").fetchall(),
      "| Rows invented:", db.execute(f"{rebuilt} EXCEPT {original}").fetchall())
```

Ava's email is now stored once instead of three times, and the Notebook's price once instead of twice. Two empty `EXCEPT` results in both directions mean the new design holds exactly the same information as the old one. This is a real technique: migrations that restructure a live database usually end with a check like this one.
:::
