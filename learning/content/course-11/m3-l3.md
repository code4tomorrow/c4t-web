:::objectives
- Turn action-style routes into resources and methods.
- Pick status codes for cases that look alike: 400 vs 422, 401 vs 403, 404 vs 409.
- Write code that converts mixed error shapes into one, and pages a list with an envelope.
- Detect breaking changes between two versions of a response.
- Explain why offset pagination can show the same item twice.
:::

The school library has an API that grew one route at a time. These exercises redesign it piece by piece. The first two are design problems you answer in writing; the rest are code you can run in `http-practice`.

## Warm-up

Rewrite each route in REST style: `GET /fetchAllBooks`, `POST /addNewMember`, `GET /bookInfo?isbn=9780441013593`.

:::solution
`GET /books`, `POST /members`, and `GET /books/9780441013593`. The id goes in the path, and an ISBN is a fine id for a book because it never changes.
:::

### Exercise 1: Redesign the library's routes

Rewrite all six. Think about which resource each one acts on, and whether something belongs to something else.

1. `POST /checkoutBook?book=12&member=5`
2. `GET /getLoansForMember?member=5`
3. `POST /returnBook?loan=88`
4. `GET /searchBooks?text=dune`
5. `POST /updateMemberEmail?member=5&email=ana@school.org`
6. `GET /overdueLoans`

:::hint
A checkout creates something: a **loan**. Returning a book changes that loan. Searching and "overdue" are filters on a collection, so they belong in the query string.
:::

:::solution
| Old | New |
| --- | --- |
| `POST /checkoutBook?book=12&member=5` | `POST /loans` with `{"book_id": 12, "member_id": 5}` |
| `GET /getLoansForMember?member=5` | `GET /members/5/loans` |
| `POST /returnBook?loan=88` | `PATCH /loans/88` with `{"returned_on": "2026-11-16"}` |
| `GET /searchBooks?text=dune` | `GET /books?q=dune` |
| `POST /updateMemberEmail?...` | `PATCH /members/5` with `{"email": "ana@school.org"}` |
| `GET /overdueLoans` | `GET /loans?overdue=true` |

Turning "checkout" into "create a loan" is the key move: a loan has its own id, dates, and history, so it's a resource in its own right. Notice the data moved from the query string into JSON bodies. An email address in a URL ends up in server logs and browser history.
:::

### Exercise 2: Pick the status code

1. `POST /loans` for a book that's already checked out.
2. `POST /loans` with `{"book_id": "twelve"}`.
3. `POST /loans` with a body that isn't valid JSON at all: `{"book_id": 12`.
4. `DELETE /members/5` with no login.
5. `DELETE /members/5`, logged in as a student who isn't a librarian.
6. `GET /books/0000000000` for an ISBN that isn't in the catalog.
7. `PATCH /loans/88` that works and returns the updated loan.
8. `DELETE /loans/88` that works.

:::hint
Ask, in order: did it work? If not, is the data unreadable, readable but against the rules, or fine but clashing with what's stored? For logins: is it "who are you?" or "I know who you are, and no"?
:::

:::solution
| # | Code | Why |
| - | ---- | --- |
| 1 | `409 Conflict` | The request is valid; it clashes with the book's current state. |
| 2 | `422` | Readable JSON, but `book_id` breaks the "integer" rule. |
| 3 | `400 Bad Request` | The server can't even parse it. (FastAPI actually answers this with `422` too, and a `json_invalid` error type.) |
| 4 | `401 Unauthorized` | No login, so the server doesn't know who's asking. |
| 5 | `403 Forbidden` | The server knows who's asking, and they aren't allowed. |
| 6 | `404 Not Found` | No such book. |
| 7 | `200 OK` | It worked, with a body. |
| 8 | `204 No Content` | It worked, with nothing to send back. |
:::

### Exercise 3: One error shape

The old API answers errors in three different ways. Write `to_detail(body)` that converts each into `{"detail": "..."}` and leaves already-correct errors alone.

```text
{'error': 'no such book'} -> {'detail': 'no such book'}
{'message': 'Member banned', 'code': 403} -> {'detail': 'Member banned'}
'Loan not found' -> {'detail': 'Loan not found'}
{'detail': 'Book 9 not found'} -> {'detail': 'Book 9 not found'}
```

:::hint
Check the most specific case first: a dict that already has `detail`. Then each old key. A plain string falls through to the end.
:::

:::solution
```python run title="http-practice/to_detail.py"
def to_detail(body):
    if isinstance(body, dict) and "detail" in body:
        return body
    if isinstance(body, dict) and "error" in body:
        return {"detail": body["error"]}
    if isinstance(body, dict) and "message" in body:
        return {"detail": body["message"]}
    return {"detail": str(body)}


old_errors = [
    {"error": "no such book"},
    {"message": "Member banned", "code": 403},
    "Loan not found",
    {"detail": "Book 9 not found"},
]
for old in old_errors:
    print(repr(old), "->", to_detail(old))
```

The `code: 403` inside the second body is dropped on purpose. The status code belongs in the status line, where every tool looks for it, not repeated in the body. A function like this is useful during a migration: put it in front of the old API so clients can switch to one error shape before the server code is rewritten.
:::

### Exercise 4: Pages with an envelope

Write `page(items, limit=20, offset=0)` that returns `{"items", "total", "limit", "offset", "next_offset"}`, where `next_offset` is `None` on the last page. Raise `ValueError` if `limit` is outside 1–100 or `offset` is negative. Then loop through seven book titles three at a time.

```text
{'items': ['Dune', 'Emma', 'Ivanhoe'], 'total': 7, 'limit': 3, 'offset': 0, 'next_offset': 3}
{'items': ['Kindred', 'Matilda', 'Persuasion'], 'total': 7, 'limit': 3, 'offset': 3, 'next_offset': 6}
{'items': ['Rebecca'], 'total': 7, 'limit': 3, 'offset': 6, 'next_offset': None}
```

:::hint
Slicing never fails: `items[6:9]` on seven items returns one. The next page starts where this one ended, `offset + len(chunk)`, and there's no next page when that reaches `len(items)`.
:::

:::solution
```python run title="http-practice/page.py"
def page(items, limit=20, offset=0):
    if not 1 <= limit <= 100:
        raise ValueError("limit must be 1 to 100")
    if offset < 0:
        raise ValueError("offset can't be negative")
    chunk = items[offset:offset + limit]
    end = offset + len(chunk)
    return {
        "items": chunk,
        "total": len(items),
        "limit": limit,
        "offset": offset,
        "next_offset": end if end < len(items) else None,
    }


books = ["Dune", "Emma", "Ivanhoe", "Kindred", "Matilda", "Persuasion", "Rebecca"]
offset = 0
while offset is not None:
    result = page(books, limit=3, offset=offset)
    print(result)
    offset = result["next_offset"]

for limit, offset in [(0, 0), (3, -1)]:
    try:
        page(books, limit, offset)
    except ValueError as error:
        print("ValueError:", error)
```

With `next_offset`, the client loop is one line of logic: keep going while it isn't `None`. Unlike the bare-list loop in the Notes lesson, this one never makes an extra request for an empty page. In a FastAPI route, those `ValueError`s become `422` responses, which `Query(ge=1, le=100)` will do for you in Module 4.
:::

### Exercise 5: Spot the breaking changes

Write `breaking_changes(old, new)` that compares an old example response with a new one and lists every removed field and every type change, looking inside nested objects too. Added fields are safe and shouldn't be reported.

```python
v1 = {"id": 7, "title": "Lab report", "done": False, "due": "2026-11-20", "owner": {"id": 3, "name": "Ana"}}
v2 = {"id": 7, "name": "Lab report", "done": False, "due": 5, "owner": {"id": "3", "name": "Ana"}, "tags": []}
```

```text
['removed title', 'due: str -> int', 'owner.id: int -> str']
[]
```

The second line is for `v1` compared with itself plus a new `tags` field.

:::hint
Loop over the **old** keys: anything missing from `new` was removed. Compare `type()` of each pair. When both values are dicts, call the function again with a prefix like `"owner."`.
:::

:::solution
```python run title="http-practice/breaking_changes.py"
def breaking_changes(old, new, path=""):
    problems = []
    for key, value in old.items():
        where = f"{path}{key}"
        if key not in new:
            problems.append(f"removed {where}")
        elif type(new[key]) is not type(value):
            problems.append(f"{where}: {type(value).__name__} -> {type(new[key]).__name__}")
        elif isinstance(value, dict):
            problems += breaking_changes(value, new[key], where + ".")
    return problems


v1 = {"id": 7, "title": "Lab report", "done": False, "due": "2026-11-20", "owner": {"id": 3, "name": "Ana"}}
v2 = {"id": 7, "name": "Lab report", "done": False, "due": 5, "owner": {"id": "3", "name": "Ana"}, "tags": []}
print(breaking_changes(v1, v2))
print(breaking_changes(v1, {**v1, "tags": ["school"]}))
```

Renaming `title` to `name` shows up only as "removed title", because from an old client's point of view that's exactly what happened. `owner.id` turning into a string is the sneaky one: it looks the same when printed, and it breaks any client that does arithmetic or comparisons with it. Big API teams run checks like this on every change.
:::

### Exercise 6: Design a new resource

Students can form **study groups**, and each group has members. Write the endpoint table (method, path, success code, error codes) for: listing groups, creating one, viewing one, renaming one, deleting one, listing a group's members, adding a member, and removing a member. Then write one example request and response for adding a member.

:::hint
Members of a group are a nested collection: `/study-groups/{id}/members`. Removing a member deletes the membership, not the student. What should happen if the student is already in the group?
:::

:::solution
| Method and path | Success | Errors |
| --------------- | ------- | ------ |
| `GET /study-groups` | `200` list | `422` bad paging |
| `POST /study-groups` | `201` group | `422` |
| `GET /study-groups/{id}` | `200` group | `404` |
| `PATCH /study-groups/{id}` | `200` group | `404`, `422` |
| `DELETE /study-groups/{id}` | `204` | `404` |
| `GET /study-groups/{id}/members` | `200` list | `404` no such group |
| `POST /study-groups/{id}/members` | `201` membership | `404`, `409` already a member, `422` |
| `DELETE /study-groups/{id}/members/{student_id}` | `204` | `404` |

Example: `POST /study-groups/4/members` with `{"student_id": 31}` returns `201` and `{"group_id": 4, "student_id": 31, "joined_on": "2026-11-16"}`. Sending it again returns `409` and `{"detail": "Student 31 is already in group 4"}`. You could argue for making the repeat a harmless `200` instead; either is defensible as long as the contract says which.
:::

### Challenge: Why the feed showed a post twice

A social feed lists posts newest first, three per page, using `offset`. A user loads page 1, someone publishes a new post, and then the user loads page 2. Show what goes wrong, then fix it with **cursor** pagination: instead of "skip 3", the client asks for "the 3 posts after the last one I saw" (`?after=8`).

Write `offset_page(items, limit, offset)` and `cursor_page(items, limit, after=None)`, run both through that sequence of events, and print the ids each client sees.

:::hint
For the cursor version, find the position of the item whose id is `after`, then slice from the position after it. The new post lands at index 0, which shifts every offset by one but doesn't move any post relative to post 8.
:::

:::solution
```python run title="http-practice/cursor_vs_offset.py"
def offset_page(items, limit, offset):
    return items[offset:offset + limit]


def cursor_page(items, limit, after=None):
    start = 0
    if after is not None:
        start = next(i for i, item in enumerate(items) if item["id"] == after) + 1
    return items[start:start + limit]


feed = [{"id": n, "text": f"post {n}"} for n in range(10, 4, -1)]  # newest first: 10 down to 5
first = offset_page(feed, 3, 0)
first_by_cursor = cursor_page(feed, 3)

feed.insert(0, {"id": 11, "text": "post 11"})  # someone posts between the two requests

second = offset_page(feed, 3, 3)
second_by_cursor = cursor_page(feed, 3, after=first_by_cursor[-1]["id"])
print("offset:", [p["id"] for p in first], [p["id"] for p in second])
print("cursor:", [p["id"] for p in first_by_cursor], [p["id"] for p in second_by_cursor])
```

With offsets, post 8 appears on both pages: the new post pushed everything down one slot, so "skip 3" now lands on 8 again. (Deleting a post does the opposite and silently skips one.) The cursor says "after post 8", which stays true no matter what's added in front. That's why large feeds, Stripe's API, and GitHub's newer endpoints use cursors. Offsets are still fine for small lists that rarely change, like your notes.
:::
