A student leaves the title box empty and clicks **Save**. The page says "Saved!" The API had answered `422` with a clear message about the empty title, the database never saw a thing, and the student walks away thinking their note exists.

Nothing crashed. Each piece did its job alone: the API validated, the database stayed consistent, and the page ran its code. They just didn't pass the failure along to each other. Making a full application means deciding, for every kind of failure, who notices it, what status code it becomes, and what the person at the keyboard sees.

## One click, three programs

```mermaid caption="A save request. Each layer can stop the trip and send back a different status."
sequenceDiagram
    participant P as Page (fetch)
    participant A as FastAPI
    participant D as SQLite
    P->>A: POST /api/notes {"title": ""}
    A-->>P: 422 if the body breaks the model
    A->>D: INSERT ... VALUES (?, ?)
    D-->>A: IntegrityError if a rule is broken
    A-->>P: 409 with a message
    D-->>A: new row id
    A-->>P: 201 {"id": 7, "title": "..."}
    P->>P: show the note, or show the error text
```

Read it as three conversations. The page talks HTTP to the API. The API talks SQL to the database. And the page talks to a human. A failure in the middle is only useful if it's translated at each boundary: from a Python exception into a status code and JSON, then from JSON into a sentence on screen.

## A dependency opens one connection per request

In the SQL module you opened one connection and kept it. A web server handles many requests, sometimes at the same moment on different threads, so the usual pattern is a fresh connection per request, closed when the response is done. A FastAPI dependency written with `yield` does exactly this: code before `yield` runs before the route, and the `finally` block runs after the response, even if the route raised.

```python run title="members_api.py"
import sqlite3
from fastapi import Depends, FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

DB_PATH = "club.db"

with sqlite3.connect(DB_PATH) as conn:
    conn.execute("""CREATE TABLE IF NOT EXISTS members (
        id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL UNIQUE)""")

def get_db():
    conn = sqlite3.connect(DB_PATH, check_same_thread=False)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA foreign_keys = ON")
    print("  [get_db] opened")
    try:
        yield conn
    finally:
        conn.close()
        print("  [get_db] closed")

class MemberIn(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    email: str = Field(pattern=r"^[^@\s]+@[^@\s]+$")

app = FastAPI()

@app.post("/api/members", status_code=201)
def add_member(member: MemberIn, db: sqlite3.Connection = Depends(get_db)):
    print("  [route] inserting", member.email)
    try:
        with db:
            cur = db.execute("INSERT INTO members (name, email) VALUES (?, ?)",
                             (member.name, member.email))
    except sqlite3.IntegrityError:
        raise HTTPException(409, "A member with that email already exists")
    return {"id": cur.lastrowid, **member.model_dump()}

@app.get("/api/members/{member_id}")
def get_member(member_id: int, db: sqlite3.Connection = Depends(get_db)):
    row = db.execute("SELECT id, name, email FROM members WHERE id = ?", (member_id,)).fetchone()
    if row is None:
        raise HTTPException(404, "No member with that id")
    return dict(row)

client = TestClient(app)
print("create")
print(" ", client.post("/api/members", json={"name": "Maya", "email": "maya@club.org"}).json())
print("same email again")
r = client.post("/api/members", json={"name": "Maya K", "email": "maya@club.org"})
print(" ", r.status_code, r.json())
print("missing id")
r = client.get("/api/members/99")
print(" ", r.status_code, r.json())
```

The prints show the order: open, route, close, on every request, including the one that failed with 409. Three details in `get_db` are easy to miss:

- `check_same_thread=False`. FastAPI may run the dependency and the route on different worker threads, and Python's `sqlite3` refuses by default to use a connection from a thread that didn't create it. Since each connection belongs to one request, sharing it within that request is safe.
- `row_factory = sqlite3.Row`, so `dict(row)` gives JSON-ready dictionaries.
- `PRAGMA foreign_keys = ON`, because it's per connection, and this is now where every connection is born.

A dependency also makes testing easier. `app.dependency_overrides[get_db] = some_other_function` swaps in a different database for a test run without touching the routes, which you'll do in the build.

## Turn failures into the right status code

Every failure should end up as a status code the client can act on and a `detail` message a person can read. Most of the mapping is a habit:

| What went wrong | Who notices | Status | Example `detail` |
| --- | --- | --- | --- |
| Body or parameter breaks the model | Pydantic, before your code | 422 | a list of field errors |
| No token, or a bad one | your auth dependency | 401 | "Missing or invalid token" |
| Not the owner | your route | 403 | "You can only change your own notes" |
| No such row | your route, after a `SELECT` | 404 | "No member with that id" |
| `UNIQUE` or other constraint fails | SQLite, as `IntegrityError` | 409 | "A member with that email already exists" |
| A bug: typo in SQL, `None` where a row was expected | nobody, until it crashes | 500 | "Internal Server Error" |

The last row is special. An uncaught exception becomes a plain-text `500 Internal Server Error`, and the full traceback goes to the server's terminal, not to the client. That's the right default: a traceback tells an attacker which tables and files you have. Your job is to make 500s rare, not to make them chatty.

:::warning
**Catching too much.** `except Exception: raise HTTPException(400, "Bad request")` around a route hides real bugs as the client's fault, and you'll never see the traceback. Catch the specific exception you expect (`sqlite3.IntegrityError`) and let surprises become 500s you can find in the server log.
:::

## fetch resolves even when the server says no

This is the bug from the start. `fetch` only rejects its promise when the request couldn't be made at all, such as the server being down or the network being off. A 404, 409, 422, or 500 is a perfectly successful *delivery* of bad news, so the code after `await fetch(...)` runs either way. You have to look at `response.ok` (true for 200 to 299) yourself.

The program below runs in Node. A fake `fetch` at the top stands in for the server and answers the way FastAPI does, including the plain-text 500, which is not JSON.

```javascript run title="save_note.js"
// A stand-in for the server, so this file runs without one.
// It answers the way FastAPI does: 201 JSON, 422 JSON, or a plain-text 500.
async function fetch(path, options) {
  const { title } = JSON.parse(options.body);
  if (title === "crash") {
    return new Response("Internal Server Error", { status: 500, headers: { "Content-Type": "text/plain" } });
  }
  if (title === "") {
    const detail = [{ type: "string_too_short", loc: ["body", "title"], msg: "String should have at least 1 character" }];
    return Response.json({ detail }, { status: 422 });
  }
  return Response.json({ id: 7, title }, { status: 201 });
}

async function saveNaive(title) {
  try {
    await fetch("/api/notes", { method: "POST", body: JSON.stringify({ title }) });
    return "Saved!";
  } catch {
    return "Network error";
  }
}

function messageFrom(body, status) {
  if (Array.isArray(body?.detail)) {
    return body.detail.map((e) => `${e.loc.at(-1)}: ${e.msg}`).join("; ");
  }
  if (typeof body?.detail === "string") return body.detail;
  return `The server had a problem (${status}). Try again in a minute.`;
}

async function api(method, path, data) {
  const response = await fetch(path, {
    method,
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(data),
  });
  const isJson = (response.headers.get("Content-Type") || "").includes("application/json");
  const body = isJson ? await response.json() : null;
  if (!response.ok) throw new Error(messageFrom(body, response.status));
  return body;
}

async function main() {
  for (const title of ["Chem lab", "", "crash"]) {
    const careful = await api("POST", "/api/notes", { title })
      .then((note) => `Saved note ${note.id}`)
      .catch((error) => `Error: ${error.message}`);
    console.log(JSON.stringify(title).padEnd(11), "naive:", (await saveNaive(title)).padEnd(7), "| careful:", careful);
  }
}
main();
```

The naive version says "Saved!" three times. The careful `api` helper does three things: checks `response.ok`, reads JSON only when the response says it is JSON (calling `.json()` on "Internal Server Error" would throw a confusing `SyntaxError`), and turns FastAPI's two `detail` shapes, a string or a list of field errors, into one readable sentence. Every call in the page goes through this one function, so no button can forget the check.

What to watch for: a request that comes back with an error status but still lands in the success branch, and the `res.ok` check that fixes it. That's the same trap as above.

## Serve the page from the API, and CORS goes away

If the page lives at `http://127.0.0.1:5500` (say, from a live-preview extension) and the API at `http://127.0.0.1:8000`, the ports differ, so they are different **origins** and the browser applies CORS. The simplest fix is to not have two origins: let FastAPI serve the HTML file too.

```python title="serve_page.py"
from fastapi import FastAPI
from fastapi.staticfiles import StaticFiles

app = FastAPI()

@app.get("/api/health")
def health():
    return {"ok": True}

# Last, so it doesn't shadow the /api routes: serves static/index.html at "/".
app.mount("/", StaticFiles(directory="static", html=True, check_dir=False), name="static")
```

Now the page calls `fetch("/api/notes")` with a path and no host, the browser sends it to the same origin it loaded the page from, and there's no CORS to configure. Putting every API route under `/api` keeps them clearly apart from page files. (`check_dir=False` only lets this snippet start without a `static` folder; leave it out in your project so a missing folder is reported right away.)

:::quiz
Q: The API returns `409` with `{"detail": "A member with that email already exists"}`. What does `await fetch(...)` do?
- [ ] Throws an error, so the `catch` block runs
  `fetch` only rejects when no response arrives at all. A 409 is a response.
- [x] Resolves normally with `response.ok === false` and `response.status === 409`
  Your code has to check `ok` and read the `detail` itself.
- [ ] Retries the request automatically
  `fetch` doesn't retry anything on its own; your code decides what happens next.

Q: Why does `get_db` use `yield` inside `try`/`finally` instead of `return conn`?
- [ ] `return` isn't allowed in a FastAPI dependency
  Plain `return` dependencies are common; they just can't clean up afterwards.
- [x] So the connection is closed after the response, even when the route raises an exception
  Code after `yield` runs once the request is finished, and `finally` makes it run on errors too.
- [ ] `yield` makes the query run faster
  It changes when cleanup happens, not how fast SQL runs.

Q: A route has a typo, `SELECT * FROM memberz`. What does the client receive?
- [ ] 404, because the table isn't found
  404 is for a resource the client asked about. This is a server bug.
- [ ] A 422 with the SQLite error message
  422 means the client's input was invalid; the client did nothing wrong here.
- [x] 500 Internal Server Error, with the traceback printed only in the server's terminal
  Uncaught exceptions become a 500, and the details stay on the server.

Q: The page is served by FastAPI at `http://127.0.0.1:8000/` and calls `fetch("/api/notes")`. Do you need `CORSMiddleware`?
- [x] No; the page and the API share an origin
  Same scheme, host, and port, so the browser applies no cross-origin rules.
- [ ] Yes; every `fetch` call needs CORS headers
  CORS only applies when the page's origin differs from the API's.
- [ ] Only for `POST` requests
  Method doesn't matter when the origin is the same.
:::

:::takeaways
- Every failure should cross each boundary as something the next layer understands: exception, then status and `detail`, then a sentence on screen.
- Use a `yield` dependency to open one SQLite connection per request and close it in `finally`; add `check_same_thread=False`.
- Catch the exceptions you expect (`IntegrityError` becomes 409, a missing row becomes 404) and let real bugs become logged 500s.
- `fetch` resolves on 4xx and 5xx. Check `response.ok`, parse JSON only when it is JSON, and show `detail`.
- Serving the page and the API from one FastAPI app means one origin and no CORS setup.
:::
