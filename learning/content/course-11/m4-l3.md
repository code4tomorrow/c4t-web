:::objectives
- Add routes to a FastAPI app without breaking existing ones, including fixed paths next to `{param}` paths.
- Set response headers and choose between 201, 204, 404, 409, and 422.
- Explain the difference between PUT and PATCH by implementing both.
- Add a `/v2` route without changing `/v1` behavior.
- Write a test that fails on a real bug, then make it pass.
:::

Each exercise adds one feature to the notes API from the last lesson. Write your answer in `notes-api/main.py`, check it with TestClient (in `test_main.py`, or a scratch file), then compare with the solution.

All cells on this page share one Python session. The starter below is the finished app from the last lesson, plus two helpers: `reset()` empties the store and restarts ids at 1, and `add()` puts a note straight into the list so exercises can start with data. To keep each solution easy to read, it builds a fresh small app containing only the routes that exercise is about.

```python run title="starter: the notes API so far"
import sys
import unittest
from itertools import count
from typing import Annotated

from fastapi import FastAPI, HTTPException, Query, Response, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

app = FastAPI(title="Notes API")


class NoteIn(BaseModel):
    title: str = Field(min_length=1, max_length=100)
    body: str = Field(default="", max_length=2000)


class NoteUpdate(BaseModel):
    title: str | None = Field(default=None, min_length=1, max_length=100)
    body: str | None = Field(default=None, max_length=2000)


class Note(BaseModel):
    id: int
    title: str
    body: str


notes: list[Note] = []
ids = count(1)


def find_note(note_id: int) -> Note:
    for note in notes:
        if note.id == note_id:
            return note
    raise HTTPException(status.HTTP_404_NOT_FOUND, f"Note {note_id} not found")


@app.get("/notes")
def list_notes(
    q: str = "",
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
    offset: Annotated[int, Query(ge=0)] = 0,
) -> list[Note]:
    text = q.lower()
    matches = [n for n in notes if text in n.title.lower() or text in n.body.lower()]
    return matches[offset : offset + limit]


@app.post("/notes", status_code=status.HTTP_201_CREATED)
def create_note(note_in: NoteIn) -> Note:
    note = Note(id=next(ids), **note_in.model_dump())
    notes.append(note)
    return note


@app.get("/notes/{note_id}")
def get_note(note_id: int) -> Note:
    return find_note(note_id)


@app.patch("/notes/{note_id}")
def update_note(note_id: int, changes: NoteUpdate) -> Note:
    note = find_note(note_id)
    for field, value in changes.model_dump(exclude_none=True).items():
        setattr(note, field, value)
    return note


@app.delete("/notes/{note_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_note(note_id: int) -> None:
    notes.remove(find_note(note_id))


def reset():
    global ids
    notes.clear()
    ids = count(1)


def add(title, body=""):
    note = Note(id=next(ids), title=title, body=body)
    notes.append(note)
    return note


starter_client = TestClient(app)
print([f"{sorted(route.methods)[0]} {route.path}" for route in app.routes][-5:])
```

### Exercise 1: Count the notes

Add `GET /notes/count`, which returns `{"count": n}` and accepts the same `q` filter as the list. Make sure `GET /notes/1` still works afterwards.

```text
/notes/count       200 {'count': 3}
/notes/count?q=mi  200 {'count': 2}
/notes/1           200 {'id': 1, 'title': 'Buy milk', 'body': ''}
```

:::hint
Remember the route-order trap from the Notes lesson. Which has to come first in the file, `/notes/count` or `/notes/{note_id}`? Test both URLs to be sure.
:::

:::solution
```python run title="count"
reset()
add("Buy milk")
add("Mix the paint")
add("Call Sam")

app = FastAPI()


@app.get("/notes/count")
def count_notes(q: str = ""):
    text = q.lower()
    return {"count": sum(1 for n in notes if text in n.title.lower() or text in n.body.lower())}


@app.get("/notes/{note_id}")
def get_note(note_id: int) -> Note:
    return find_note(note_id)


client = TestClient(app)
for url in ["/notes/count", "/notes/count?q=mi", "/notes/1"]:
    response = client.get(url)
    print(f"{url:18} {response.status_code} {response.json()}")
```

`/notes/count` is declared first. The other way round, `count` would be read as a `note_id` and fail the `int` check with a 422. In your `main.py`, put `count_notes` above `get_note`. Copying the filter line from `list_notes` works, but if the two ever drift apart, the count and the list will disagree; pulling the filter into a small `matching(q)` helper fixes that for good.
:::

### Exercise 2: Say where the new note lives

`201 Created` responses traditionally include a `Location` header with the new resource's URL. Make `POST /notes` send `Location: /notes/{id}`.

```text
201 /notes/1 {'id': 1, 'title': 'Buy milk', 'body': ''}
```

:::hint
Add a parameter `response: Response` to the route function. FastAPI fills it in, and anything you put in `response.headers` is sent along with your return value.
:::

:::solution
```python run title="location"
reset()
app = FastAPI()


@app.post("/notes", status_code=status.HTTP_201_CREATED)
def create_note(note_in: NoteIn, response: Response) -> Note:
    note = Note(id=next(ids), **note_in.model_dump())
    notes.append(note)
    response.headers["Location"] = f"/notes/{note.id}"
    return note


client = TestClient(app)
created = client.post("/notes", json={"title": "Buy milk"})
print(created.status_code, created.headers["location"], created.json())
```

A client can now follow the header instead of building the URL itself. That matters more than it seems: if you later move notes to `/v2/notes/{id}`, clients that follow `Location` keep working.
:::

### Exercise 3: PUT replaces, PATCH changes

Add `PUT /notes/{note_id}`, which replaces the whole note with a `NoteIn` body. Then show the difference: start with `{"title": "Buy milk", "body": "2 cartons"}`, send `{"title": "Buy oat milk"}` with PATCH to one copy and with PUT to another, and print both results.

```text
PATCH: {'id': 1, 'title': 'Buy oat milk', 'body': '2 cartons'}
PUT:   {'id': 2, 'title': 'Buy oat milk', 'body': ''}
```

:::hint
PUT's body is a complete note, so use `NoteIn`, not `NoteUpdate`. A field the client leaves out takes its **default**, which for `body` is `""`. Keep the same id.
:::

:::solution
```python run title="put_vs_patch"
reset()
add("Buy milk", "2 cartons")
add("Buy milk", "2 cartons")

app = FastAPI()


@app.patch("/notes/{note_id}")
def update_note(note_id: int, changes: NoteUpdate) -> Note:
    note = find_note(note_id)
    for field, value in changes.model_dump(exclude_none=True).items():
        setattr(note, field, value)
    return note


@app.put("/notes/{note_id}")
def replace_note(note_id: int, note_in: NoteIn) -> Note:
    note = find_note(note_id)
    note.title = note_in.title
    note.body = note_in.body
    return note


client = TestClient(app)
print("PATCH:", client.patch("/notes/1", json={"title": "Buy oat milk"}).json())
print("PUT:  ", client.put("/notes/2", json={"title": "Buy oat milk"}).json())
print("PUT without title:", client.put("/notes/2", json={"body": "x"}).status_code)
```

Same body, different meaning. PATCH says "change these fields", so the body survives. PUT says "here is the whole note", so the missing body becomes the default. PUT also requires `title`, which is why the last request gets a 422. PUT is idempotent (sending it twice leaves the same note), which makes it safe for a client to retry.
:::

### Exercise 4: Refuse duplicate titles

Make `POST /notes` answer `409 Conflict` with `{"detail": "A note titled 'Buy milk' already exists"}` if a note with the same title exists, ignoring case.

```text
201 {'id': 1, 'title': 'Buy milk', 'body': ''}
409 {'detail': "A note titled 'BUY MILK' already exists"}
201 {'id': 2, 'title': 'Buy bread', 'body': ''}
```

:::hint
Check before creating anything: `any(...)` over the existing notes, comparing `.lower()` of both titles. Raise, don't return. Use the title the client sent in the message.
:::

:::solution
```python run title="conflict"
reset()
app = FastAPI()


@app.post("/notes", status_code=status.HTTP_201_CREATED)
def create_note(note_in: NoteIn) -> Note:
    wanted = note_in.title.lower()
    if any(n.title.lower() == wanted for n in notes):
        raise HTTPException(status.HTTP_409_CONFLICT, f"A note titled '{note_in.title}' already exists")
    note = Note(id=next(ids), **note_in.model_dump())
    notes.append(note)
    return note


client = TestClient(app)
for title in ["Buy milk", "BUY MILK", "Buy bread"]:
    response = client.post("/notes", json={"title": title})
    print(response.status_code, response.json())
```

`409` is right because `"BUY MILK"` is a perfectly valid title on its own (so not 422); it only clashes with what's stored. A complete version would also check `PATCH` and `PUT`, since renaming a note to an existing title is the same conflict through a different door. Also notice the failed attempt didn't use up an id: "Buy bread" got 2, because the check runs before `next(ids)`.
:::

### Exercise 5: A versioned list with a total

A client wants to show "Page 2 of 5", which needs a total count. Changing `GET /notes` to return an object would break every existing client, so add `GET /v2/notes` that returns `{"items": [...], "total": n, "limit": ..., "offset": ...}`, and leave `GET /notes` exactly as it is.

```text
v1: ['Buy milk']
v2: {'items': [{'id': 1, 'title': 'Buy milk', 'body': ''}], 'total': 2, 'limit': 1, 'offset': 0}
```

That's both endpoints called with `?q=milk&limit=1` when two notes mention milk.

:::hint
Make a `NotePage` model with the four fields, and use it as the return type. Both routes need the same filtering, so move it into one helper function that both call.
:::

:::solution
```python run title="v2_list"
reset()
add("Buy milk")
add("Essay outline", "milk prices paragraph")
add("Call Sam")


class NotePage(BaseModel):
    items: list[Note]
    total: int
    limit: int
    offset: int


def matching(q: str) -> list[Note]:
    text = q.lower()
    return [n for n in notes if text in n.title.lower() or text in n.body.lower()]


app = FastAPI()


@app.get("/notes")
def list_notes(
    q: str = "",
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
    offset: Annotated[int, Query(ge=0)] = 0,
) -> list[Note]:
    return matching(q)[offset : offset + limit]


@app.get("/v2/notes")
def list_notes_v2(
    q: str = "",
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
    offset: Annotated[int, Query(ge=0)] = 0,
) -> NotePage:
    found = matching(q)
    return NotePage(items=found[offset : offset + limit], total=len(found), limit=limit, offset=offset)


client = TestClient(app)
print("v1:", [n["title"] for n in client.get("/notes?q=milk&limit=1").json()])
print("v2:", client.get("/v2/notes?q=milk&limit=1").json())
```

Old clients keep calling `/notes` and see no change, and new clients opt in to `/v2/notes`. The shared `matching` helper guarantees both versions agree on which notes match, so the only difference between them is the shape. That's the safe way to make a breaking change.
:::

### Exercise 6: A test that catches a paging bug

A teammate "simplified" the list route to this, and all their manual checks passed:

```python run title="buggy_list"
reset()
for title in ["Note A", "Note B", "Note C", "Note D", "Note E"]:
    add(title)

app = FastAPI()


@app.get("/notes")
def list_notes(
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
    offset: Annotated[int, Query(ge=0)] = 0,
) -> list[Note]:
    return notes[offset:limit]


client = TestClient(app)
print([n["title"] for n in client.get("/notes").json()])
print([n["title"] for n in client.get("/notes?limit=2").json()])
```

Both of those look right. Write a unittest test that fails on this route, run it to see it fail, then fix the route and run the test again.

:::hint
The first page always works, because when `offset` is 0, `notes[0:limit]` is correct. What should `?limit=2&offset=2` return, and what does `notes[2:2]` give?
:::

:::solution
```python run title="catch_the_bug"
class PagingTests(unittest.TestCase):
    def test_second_page(self):
        titles = [n["title"] for n in client.get("/notes?limit=2&offset=2").json()]
        self.assertEqual(titles, ["Note C", "Note D"])


def run_tests():
    suite = unittest.defaultTestLoader.loadTestsFromTestCase(PagingTests)
    unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)


run_tests()
```

The test fails with `[] != ['Note C', 'Note D']`: the slice stops at `limit` instead of `offset + limit`. (On your computer, the traceback names your test file and the line of the failing assert.) Now fix the route and run the same test:

```python run title="catch_the_bug (fixed)"
app = FastAPI()


@app.get("/notes")
def list_notes(
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
    offset: Annotated[int, Query(ge=0)] = 0,
) -> list[Note]:
    return notes[offset : offset + limit]


client = TestClient(app)
run_tests()
```

The bug only shows up when `offset` is more than 0, which is exactly the case people forget to try by hand. Good tests aim at the edges: the second page, the last page, an empty list, one past the end.
:::

### Challenge: Replay the Module 3 contract

In Module 3, `check_examples(send)` checked the mock against fifteen example exchanges. Run the same examples against the **starter app** (the real FastAPI API) by writing a `send(method, url, body)` that uses `starter_client` and returns `(status_code, json_or_None)`.

:::hint
`starter_client.request(method, url, json=body)` sends any method. A 204 has an empty body, so only call `.json()` when `response.content` isn't empty. Call `reset()` first, since the examples expect ids to start at 1.
:::

:::solution
```python run title="contract_replay"
MILK = {"id": 1, "title": "Buy milk", "body": ""}
ESSAY = {"id": 2, "title": "Essay outline", "body": "Intro, three points, conclusion"}

EXAMPLES = [
    ("POST", "/notes", {"title": "Buy milk"}, 201, MILK),
    ("POST", "/notes", {"title": "Essay outline", "body": "Intro, three points, conclusion"}, 201, ESSAY),
    ("GET", "/notes", None, 200, [MILK, ESSAY]),
    ("GET", "/notes?q=ESSAY", None, 200, [ESSAY]),
    ("GET", "/notes?limit=1&offset=1", None, 200, [ESSAY]),
    ("GET", "/notes/2", None, 200, ESSAY),
    ("GET", "/notes/99", None, 404, {"detail": "Note 99 not found"}),
    ("GET", "/notes/abc", None, 422, ["path", "note_id"]),
    ("GET", "/notes?limit=0", None, 422, ["query", "limit"]),
    ("POST", "/notes", {"body": "no title"}, 422, ["body", "title"]),
    ("POST", "/notes", {"title": ""}, 422, ["body", "title"]),
    ("PATCH", "/notes/1", {"body": "2 cartons"}, 200, {**MILK, "body": "2 cartons"}),
    ("DELETE", "/notes/1", None, 204, None),
    ("DELETE", "/notes/1", None, 404, {"detail": "Note 1 not found"}),
    ("POST", "/notes", {"title": "Call Sam"}, 201, {"id": 3, "title": "Call Sam", "body": ""}),
]


def check_examples(send):
    passed = 0
    for method, url, body, status_code, expected in EXAMPLES:
        got_status, got = send(method, url, body)
        if got_status != status_code:
            ok = False
        elif status_code == 422:
            ok = any(problem["loc"] == expected for problem in got["detail"])
        else:
            ok = got == expected
        passed += ok
        print(f"{'PASS' if ok else 'FAIL'}  {method:6} {url:24} {got_status}")
    print(f"{passed} of {len(EXAMPLES)} examples match the contract")


def send(method, url, body):
    response = starter_client.request(method, url, json=body)
    return response.status_code, (response.json() if response.content else None)


reset()
check_examples(send)
```

Fifteen out of fifteen, from a server whose code looks nothing like the mock's. That's what a contract buys you: the mock, the FastAPI version, and the SQLite version you'll build next module can all be checked by the same list. (The loop variable is called `status_code` here, not `status` as in Module 3, so that inside the function it doesn't hide FastAPI's `status` module.) Keep this check in your project and run it after every big change.
