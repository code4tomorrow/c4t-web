:::objectives
- Break a build into milestones that each end with a passing test.
- Build the change maker step by step: skeleton, decisions, loops, edge cases, tests, and measurement.
- Start your own project from a starter script and grow it one milestone at a time.
- Keep a fix log as you go, so your explanation has real evidence in it.
:::

The fastest way to build something that doesn't work is to build all of it at once. When 40 blocks all go in before the first test, and the result is wrong, the bug could be anywhere. Build in **milestones** instead: small chunks that each end with something that runs and a test it passes. When a test fails, the bug is almost always in the few blocks you just added.

## The six milestones

| # | Milestone | What you add | Done when |
| --- | --- | --- | --- |
| 1 | Skeleton | Inputs and outputs, with the simplest path from one to the other | One ordinary test passes |
| 2 | Decisions | Every if/else from your plan | You've seen every path run at least once |
| 3 | Repetition | The loops | Loops repeat the right number of times for 3 different inputs |
| 4 | Edge cases | Input checks and boundary handling | Every edge-case test passes |
| 5 | Full test run | Nothing new: run the whole test table | Every row passes, and every fix is in your fix log |
| 6 | Measure | A step counter, and a comparison | You have numbers for your evidence table |

After each milestone, save a copy with the milestone in its name (like `capstone-m3.sb3`), using **File › Save to your computer** or **Save now** if you're signed in. If milestone 4 goes badly wrong, you can go back to milestone 3 in seconds.

Keep a **fix log** next to your test table. Every time a test fails, write one row:

| Test that failed | What I expected | What happened | The cause | The fix |
| --- | --- | --- | --- | --- |
| price 100, paid 50 | "That's not enough" | 0 coins given | no check for paying too little | added the paid < price decision |

Your fix log is the best material you'll have when you present. "Here's a bug I found and how I proved it was fixed" beats "it works" every time.

## Worked example: the change maker

This is the change maker planned in the last lesson, built milestone by milestone. Follow along, or read it as a model for your own project.

### Milestone 1: The skeleton

Make the variables `price`, `paid`, and `owed`. Build the straightest path from input to output:

```scratch
when green flag clicked
ask [Price in cents?] and wait
set [price v] to (answer)
ask [Amount paid in cents?] and wait
set [paid v] to (answer)
set [owed v] to ((paid) - (price))
say (join [Change owed: ] (owed)) for (2) seconds
```

Test: price 32, paid 100. It says "Change owed: 68". Milestone 1 done. It's tiny, but every later milestone builds on something you know works.

### Milestone 2: Decisions

The plan has two special cases before any coins come out: paying too little, and paying exactly. Add these after the `set [owed v]` block:

```scratch
if <(paid) < (price)> then
  say [That's not enough money.] for (2) seconds
  stop [this script v]
end
if <(owed) = (0)> then
  say [Exact change, thanks!] for (2) seconds
  stop [this script v]
end
```

Test both paths and one ordinary case: (100, 50) → not enough. (50, 50) → exact. (32, 100) → carries on.

### Milestone 3: Repetition

First, make a list called `coin sizes` and fill it once by clicking this stack (it has no hat block, so it only runs when you click it):

```scratch
delete all of [coin sizes v]
add (25) to [coin sizes v]
add (10) to [coin sizes v]
add (5) to [coin sizes v]
add (1) to [coin sizes v]
```

Make a second list, `given`, and the variables `coin`, `count`, and `i`. Then add the two loops from the plan, one inside the other. The outer loop walks through the coin sizes. The inner loop keeps giving the current coin while it still fits:

```scratch
delete all of [given v]
set [count v] to (0)
set [i v] to (1)
repeat (length of [coin sizes v])
  set [coin v] to (item (i) of [coin sizes v])
  repeat until <(coin) > (owed)>
    add (coin) to [given v]
    set [owed v] to ((owed) - (coin))
    change [count v] by (1)
  end
  change [i v] by (1)
end
say (join [Here are your ] (join (count) [ coins!])) for (3) seconds
```

Test three amounts and check the `given` list on the stage: 68¢ (25, 25, 10, 5, 1, 1, 1), 30¢ (25, 5), and 4¢ (1, 1, 1, 1).

### Milestone 4: Edge cases

What if someone types `five`, or leaves the answer blank, or types `-20`? Try it. With `five` as the amount paid, Scratch treats the word as 0 when it subtracts, so you get strange results instead of a helpful message.

A neat Scratch check for "is this a whole number?" is `<(round (answer)) = (answer)>`. A word like `five` rounds to 0, which doesn't equal `five`. A blank rounds to 0, which doesn't equal blank. A decimal like `5.5` rounds to 6. Only whole numbers survive. Add this right after each `ask`:

```scratch
if <not <(round (answer)) = (answer)>> then
  say [Please type a whole number of cents.] for (2) seconds
  stop [this script v]
end
```

And after both answers are in, catch negatives:

```scratch
if <<(price) < (0)> or <(paid) < (0)>> then
  say [Prices and payments can't be negative.] for (2) seconds
  stop [this script v]
end
```

### Milestone 5: The full test run

Run every row of your test table and fill in the Actual column. When a row fails, add a line to your fix log, fix it, and **re-run the whole table**, as you did with Sam's alarm.

You can't type all 100 possible amounts of change by hand, but a program can check them. Here is the same greedy algorithm in a text language, Python, tested on every amount from 0 to 99¢. For each amount it checks two things: the coins add up to the right total, and no other mix of coins uses fewer. (The `fewest` function works out the true minimum the slow, careful way, by building up from smaller amounts.)

```python run title="check_every_amount.py"
def greedy(owed, sizes):
    coins = []
    for coin in sizes:
        while coin <= owed:
            coins.append(coin)
            owed = owed - coin
    return coins

def fewest(amount, sizes):
    best = [0] + [None] * amount
    for x in range(1, amount + 1):
        best[x] = min(best[x - c] + 1 for c in sizes if c <= x)
    return best[amount]

us = [25, 10, 5, 1]
wrong_total = [a for a in range(100) if sum(greedy(a, us)) != a]
not_fewest = [a for a in range(100) if len(greedy(a, us)) != fewest(a, us)]
most = max(range(100), key=lambda a: len(greedy(a, us)))
print("Amounts with the wrong total:", wrong_total)
print("Amounts where greedy isn't the fewest coins:", not_fewest)
print("Most coins needed:", len(greedy(most, us)), "for", most, "cents:", greedy(most, us))

odd = [4, 3, 1]
print("With 4, 3, and 1 cent coins, greedy loses at:",
      [a for a in range(20) if len(greedy(a, odd)) != fewest(a, odd)])
```

For US coins, two empty lists: greedy is right for every amount. With made-up 4¢, 3¢, and 1¢ coins it fails for 6, 10, 14, and 18¢. That's a real finding you could put in your explanation.

### Milestone 6: Measure and compare

The `count` variable already counts coins, which is the step you chose in your plan. Add a comparison row to your evidence table, such as "pennies only: 68 coins for 68¢; greedy: 7 coins." If you have time, make a second version that gives only dimes and pennies, and compare all three on the same five amounts.

## Starters for the other projects

Each starter is milestones 1 to 3 in a rough form. None of them is finished, and some have a bug waiting for an edge case. Find it with a test.

**Animal guesser.** Two yes/no questions can tell apart 4 animals. Three questions can tell apart 8. That's binary search again: every question splits the possibilities in half.

```scratch title="Animal guesser starter"
when green flag clicked
ask [Does your animal live in water? (yes/no)] and wait
if <(answer) = [yes]> then
  ask [Does it have legs? (yes/no)] and wait
  if <(answer) = [yes]> then
    say [Is it a frog?]
  else
    say [Is it a goldfish?]
  end
else
  ask [Can it fly? (yes/no)] and wait
  if <(answer) = [yes]> then
    say [Is it an eagle?]
  else
    say [Is it a dog?]
  end
end
```

**Fair sign-up.** Fill a list called `line` with names (use a click-once stack, like the coin sizes), then:

```scratch title="Fair sign-up starter"
when green flag clicked
ask [How many computers work today?] and wait
set [computers v] to (answer)
set [round v] to (1)
repeat until <(length of [line v]) = (0)>
  say (join [Round ] (round)) for (1) seconds
  repeat (computers)
    if <(length of [line v]) > (0)> then
      say (join (item (1) of [line v]) [, take a computer!]) for (1) seconds
      delete (1) of [line v]
    end
  end
  change [round v] by (1)
end
```

**Maze runner.** Paint a backdrop with thick black walls and corridors about 40 steps wide, and a green square at the exit. In each `touching color` block, click the color swatch, then the eyedropper at the bottom of the color picker, then a wall (or the exit) on the stage, so the colors match exactly. The script tries right, then straight, then left, then back, at every square:

```scratch title="Maze runner starter"
when green flag clicked
set size to (20) %
go to x: (-200) y: (-140)
point in direction (90)
set [moves v] to (0)
repeat until <touching color [#00ff00] ?>
  turn right (90) degrees
  move (40) steps
  repeat until <not <touching color [#000000] ?>>
    move (-40) steps
    turn left (90) degrees
    move (40) steps
  end
  change [moves v] by (1)
  wait (0.2) seconds
end
say (join [Out in ] (join (moves) [ moves!]))
```

Change the starting `go to` position and the step size to fit your maze. If the sprite slips through walls, make the walls thicker or the sprite smaller.

**Sorting machine.** Bubble sort on a list called `numbers`, counting comparisons and swaps. The `temp` variable holds one number during a swap, the way you'd need an empty glass to swap the drinks in two full ones:

```scratch title="Sorting machine starter"
when green flag clicked
delete all of [numbers v]
repeat (8)
  add (pick random (1) to (99)) to [numbers v]
end
set [comparisons v] to (0)
set [swaps v] to (0)
set [swapped v] to [yes]
repeat until <(swapped) = [no]>
  set [swapped v] to [no]
  set [i v] to (1)
  repeat ((length of [numbers v]) - (1))
    change [comparisons v] by (1)
    if <(item (i) of [numbers v]) > (item ((i) + (1)) of [numbers v])> then
      set [temp v] to (item (i) of [numbers v])
      replace item (i) of [numbers v] with (item ((i) + (1)) of [numbers v])
      replace item ((i) + (1)) of [numbers v] with (temp)
      change [swaps v] by (1)
      set [swapped v] to [yes]
    end
    change [i v] by (1)
  end
  wait (0.5) seconds
end
say (join (comparisons) (join [ comparisons, ] (join (swaps) [ swaps])))
```

Random numbers make testing hard, because every run is different. For your test table, replace the random `repeat (8)` with a click-once stack that fills `numbers` with a fixed list you choose: one jumbled, one already sorted, one backwards, one with repeated numbers.

:::tip
Stuck on a milestone for more than 15 minutes? Go back to the last saved milestone that worked, re-read your plan for the next step, and add *less* this time. Then use the debugging routine from Module 6: make it fail, find the first block where expected and actual split, change one thing.
:::

:::quiz
Q: The change maker's milestone 3 test for 30¢ gives 25, 1, 1, 1, 1, 1. Where is the bug most likely to be?
- [ ] In milestone 1's `ask` blocks
  Milestone 1 passed its test, and the total (30¢) is still right. The problem is which coins were chosen.
- [x] In the coin loop or the `coin sizes` list
  The 5¢ coin was skipped, so either the list is missing 5 or the loop isn't reaching it. Check the list on the stage first.
- [ ] In the "exact change" decision
  That decision only runs when nothing is owed, so it can't change which coins come out.

Q: Why does the sorting machine starter need to replace its random numbers before testing?
- [ ] Scratch can't sort random numbers
  It can sort any numbers.
- [x] With random input, you can't write the expected result in advance
  A test needs a known input and a predicted output. Fixed lists (jumbled, sorted, backwards, repeats) make every run repeatable.
- [ ] Random numbers make the sort slower
  The count of comparisons depends on the order, not on whether the numbers were random.
:::
