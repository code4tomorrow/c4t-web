:::objectives
- Plan a route as numbered steps and check it with a state table before building.
- Use Scratch's x and y coordinates and directions to describe exactly where a sprite is.
- Set a sprite's starting state with `go to` and `point in direction`.
- Slow a program down with `wait` so you can watch each step happen.
- Use a second event to reset the robot, and test from several starting states.
:::

A delivery robot waits by the door of an office. Its job: carry a package to the laptop on the far side of the room, without driving through the pile of rocks someone has left in the middle of the floor. (It's a strange office.) You'll plan the route on paper, prove it works with a state table, and then make it run in Scratch.

## What we're building

Here's the stage seen from above, with the route the robot will drive. The numbers in brackets are positions on the stage, which Step 1 explains.

```text
 (-240, 180)                                          (240, 180)
     +-----------------------------------------------------+
     |                                                     |
     |          (-60, 80) -------------------> (160, 80)   |
     |              ^                          [LAPTOP]    |
     |              |                                      |
     |              |            [ROCKS]                   |
     |              |            (60, -30)                 |
     |              |                                      |
     |  [ROBOT] ----+                                      |
     |  (-180, -120)   (-60, -120)                         |
     +-----------------------------------------------------+
 (-240, -180)                                         (240, -180)
```

And here's the algorithm the robot will follow:

```mermaid caption="The delivery algorithm: set the start, drive three legs with two turns, then deliver"
flowchart TD
    A([Green flag]) --> B["Start at the door, facing right"]
    B --> C[Forward 120]
    C --> D[Turn left 90]
    D --> E[Forward 200]
    E --> F[Turn right 90]
    F --> G[Forward 220]
    G --> H["Say 'Package delivered!'"]
```

## Step 1: Learn the stage's addresses

Every spot on the Scratch stage has an address made of two numbers:

-   **x** says how far left or right. It runs from -240 at the left edge to 240 at the right edge.
-   **y** says how far up or down. It runs from -180 at the bottom to 180 at the top.
-   The center is x: 0, y: 0.

A sprite also has a **direction**, measured in degrees: **90** is facing right, **0** is facing up, **-90** is facing left, and **180** is facing down. Position plus direction is the robot's whole state, just like column, row, and facing on the grid in the Notes lesson.

## Step 2: Plan the route and check it on paper

Write this plan in your notebook:

```text
1. Start at the door: x -180, y -120, facing right (90).
2. Drive forward 120 steps.
3. Turn left 90 degrees.
4. Drive forward 200 steps.
5. Turn right 90 degrees.
6. Drive forward 220 steps.
7. Say "Package delivered!" for 2 seconds.
```

Now be the computer. Track the state after every step:

| After step | x | y | Direction |
| --- | --- | --- | --- |
| 1 | -180 | -120 | 90 (right) |
| 2 | -60 | -120 | 90 (right) |
| 3 | -60 | -120 | 0 (up) |
| 4 | -60 | 80 | 0 (up) |
| 5 | -60 | 80 | 90 (right) |
| 6 | 160 | 80 | 90 (right) |

Moving right adds to x. Moving up adds to y. Turning changes only the direction. The final row puts the robot at (160, 80), right next to the laptop at (190, 80), and the route never comes within 100 steps of the rocks. The plan works before you've touched a single block. That's the value of checking on paper: a wrong number found here costs ten seconds to fix.

## Step 3: Set the stage

1.  **Backdrop.** Under the stage at the bottom-right, click the **Choose a Backdrop** button. Search for `Xy-grid` and click it. It draws the x and y axes on the stage, which makes positions easier to judge.
2.  **Robot.** Hover over the **Choose a Sprite** button (the cat face in the bottom-right corner of the sprite list), click the magnifying glass, search for `Robot`, and click it. You can delete the cat by clicking the small trash can on its thumbnail.
3.  **Laptop and rocks.** Add the `Laptop` sprite and the `Rocks` sprite the same way. Select each one and type its position into the **x** and **y** boxes above the sprite list: Laptop at x `190`, y `80`; Rocks at x `60`, y `-30`.

Click the robot in the sprite list so that the code you build next belongs to it.

## Step 4: Set the starting state

```scratch
when green flag clicked
set size to (50) %
go to x: (-180) y: (-120)
point in direction (90)
```

`set size to` is in **Looks**; the others are in **Motion**. Click the green flag. The robot shrinks, jumps to the door, and faces right.

**Test it.** Drag the robot somewhere else on the stage, then click the flag again. It jumps back to the door. That's the whole point of these blocks: whatever state the robot was left in, every run starts from the same place.

## Step 5: The first leg, and why you can't see it

Add a `move` block for step 2 of the plan:

```scratch
move (120) steps
```

Click the flag. The robot appears at its new spot instantly. You never see it travel, because Scratch runs blocks far faster than your eyes can follow. Check that it worked by looking at the **x** box above the sprite list: it should say `-60`.

To watch the algorithm happen, slow it down. From **Control**, add `wait (0.5) seconds` after every move and every turn. The robot will still jump, but in visible steps, one per instruction.

## Step 6: The turns and the other two legs

Add steps 3 to 6 of the plan, each followed by a wait. In the Motion category, `turn left` is the block with the arrow curving counterclockwise (↺), and `turn right` has the arrow curving clockwise (↻).

```scratch
turn left (90) degrees
wait (0.5) seconds
move (200) steps
wait (0.5) seconds
turn right (90) degrees
wait (0.5) seconds
move (220) steps
wait (0.5) seconds
```

Click the flag and watch. When the robot turns to face up, the whole picture tips sideways. That's Scratch rotating the sprite to show its direction, and it's handy here: you can see which way the robot is about to drive.

:::warning
**The robot heads down instead of up.** You used `turn right` where the plan says `turn left`. The robot then drives toward the bottom of the stage, and because Scratch won't let a sprite leave the stage completely, it gets stuck at the bottom edge. Compare your blocks with the plan one line at a time; the arrows on the two turn blocks look very similar.
:::

## Step 7: Deliver the package

Add the final step from **Looks**:

```scratch
say [Package delivered!] for (2) seconds
```

## Step 8: Add a reset button with a second event

It would be handy to put the robot back at the door without running the whole delivery. A second event can do that. Build this as a separate script, next to the first one:

```scratch
when [r v] key pressed
go to x: (-180) y: (-120)
point in direction (90)
```

Now pressing **R** resets the robot, and clicking the flag runs the delivery. Two events, two scripts, one robot.

## The finished program

```scratch
when green flag clicked
set size to (50) %
go to x: (-180) y: (-120)
point in direction (90)
move (120) steps
wait (0.5) seconds
turn left (90) degrees
wait (0.5) seconds
move (200) steps
wait (0.5) seconds
turn right (90) degrees
wait (0.5) seconds
move (220) steps
wait (0.5) seconds
say [Package delivered!] for (2) seconds
```

```scratch
when [r v] key pressed
go to x: (-180) y: (-120)
point in direction (90)
```

Save it as `m3-delivery-robot.sb3`.

## Test it like a skeptic

A program that worked once hasn't been tested. Try to break it:

1.  Click the flag. Does the robot reach the laptop and say its line?
2.  Drag the robot to the top-right corner, and type `180` into the **Direction** box above the sprite list so it faces down. Click the flag. It should still deliver, because the script sets its own starting state.
3.  Click the red stop sign halfway through a delivery. Then click the flag. Does it start cleanly from the door?

:::try
Press **R** while the robot is halfway through a delivery. The reset script puts it back at the door, but the delivery script doesn't stop: it carries on with its next blocks, starting from the door. The robot ends up somewhere strange. Two scripts were changing the same robot's state at once, and neither knew about the other. Keep that in mind whenever you give one sprite more than one event.
:::

:::quiz
Q: After a full delivery, the robot is already facing right. Why keep `point in direction (90)` at the top of the script?
- [x] The robot might not be facing right when the next run starts
  Someone could drag it, the stop sign could interrupt a run after a turn, or another script could turn it. Setting the direction makes every run start the same way.
- [ ] Scratch requires every script to set a direction
  Scripts can run without it. The block is there for reliability, not because Scratch demands it.
- [ ] It makes the robot move faster
  Direction has nothing to do with speed; it only decides which way `move` goes.

Q: What would you see if you removed all the `wait` blocks?
- [ ] The robot would crash into the rocks
  The moves and turns are the same, so the route is the same. Only the timing changes.
- [x] The robot would appear at the laptop almost instantly
  Scratch runs the moves faster than you can see. The waits don't change where the robot goes, only whether you can watch it get there.
- [ ] Scratch would show an error
  Scripts don't need waits to run. They're for the humans watching.

Q: In step 3 you use `turn right (90) degrees` by mistake. What happens next?
- [x] The robot faces down, drives toward the bottom, and gets stuck at the edge
  Turning right from facing right points it down (180). Moving 200 steps from y -120 would take it far below the stage, so Scratch stops it at the bottom edge.
- [ ] Scratch notices and turns it left anyway
  Scratch never guesses what you meant. It follows the block you used.
- [ ] It turns around and drives back to the door
  Turning around would need 180 degrees. A 90-degree right turn from facing right points it straight down.
:::

:::takeaways
- Check a plan on paper with a state table first. Wrong numbers are cheapest to fix before you build.
- x is left and right, y is up and down, and direction 90 means facing right.
- Set the starting state at the top of the script so every run starts the same way.
- Computers run too fast to watch. A `wait` after each step lets you see the algorithm happen.
- Each event starts its own script. Two scripts can change the same sprite at the same time, which can cause surprises.
:::

## Ideas to extend it

-   Replace each `move` and `wait` pair with a `glide (1) secs to x: () y: ()` block so the robot drives smoothly. What information do you need for each glide that you didn't need before?
-   Add a second stop: the robot delivers to the laptop, then goes on to another sprite somewhere else in the room.
-   Write a return trip that runs when you press the space bar. To drive the route backwards, you have to turn around, reverse the order of the legs, and swap every left turn for a right. Plan it on paper first.
