## What we're building

Sam's alarm is getting an upgrade. The new version should:

- ring at 6:30 a.m. on school days (Monday to Friday),
- stay quiet on Saturdays, Sundays, and holidays,
- ring exactly **3 times**, then stop.

Sam already wrote it, and it's wrong in three different ways. You'll build Sam's version exactly as written, test it properly, and fix it. When you're done, it will pass this plan:

```text
Mon 3/9      →  BEEP! BEEP! BEEP!   (3 rings)
Fri 3/13     →  BEEP! BEEP! BEEP!   (3 rings)
Sat 3/14     →  Sleep in!
Sun 3/15     →  Sleep in!
Fri 12/25    →  Sleep in!           (holiday on a school day)
Sat 7/4      →  Sleep in!           (holiday on a weekend)
```

The alarm's logic has two questions in a row and one loop:

```mermaid caption="The plan for the alarm: one decision, then a loop that rings 3 times"
flowchart TD
    A["Get day and date"] --> B{"Holiday or weekend?"}
    B -->|yes| C["Say: Sleep in!"]
    B -->|no| D["Wait until 6:30"]
    D --> E["Ring 3 times"]
```

## Step 1: Make the variables and the holiday list

1.  Open [scratch.mit.edu](https://scratch.mit.edu), click **Create**, and keep the cat as your alarm clock.
2.  In **Variables**, click **Make a Variable** and create `day`, `today`, `alarm`, and `rings`.
3.  Click **Make a List** and create a list called `holidays`. An empty list box appears on the stage.
4.  Build this small stack of list blocks (no hat block on top) and click it once:

```scratch
delete all of [holidays v]
add [1/1] to [holidays v]
add [7/4] to [holidays v]
add [12/25] to [holidays v]
```

The list box on the stage fills with three dates. Lists are saved with the project, so you only need to click the stack once (and again if you ever change it). The dates are stored as month/day text, like `12/25`, so the holiday check can compare them directly.

## Step 2: Build Sam's script, with a test mode

Sam's real version reads the day from `(current [day of week v])`. You can't wait for Sunday to test Sunday, so this version **asks** for the day and date instead. That's the test mode, and you'll switch it off at the end.

```scratch title="Sam's alarm (buggy, test mode)"
when green flag clicked
ask [TEST MODE: day number? (1 = Sunday, 7 = Saturday)] and wait
set [day v] to (answer)
ask [TEST MODE: date? (like 12/25)] and wait
set [today v] to (answer)
set [alarm v] to [on]
if <[holidays v] contains (today) ?> then
  set [alarm v] to [off]
end
if <<(day) = (6)> or <(day) = (7)>> then
  set [alarm v] to [off]
else
  set [alarm v] to [on]
end
if <(alarm) = [on]> then
  set [rings v] to (0)
  repeat until <(rings) > (3)>
    say [BEEP! BEEP!] for (1) seconds
    change [rings v] by (1)
  end
else
  say [Sleep in!] for (2) seconds
end
```

The `contains` block is in **Variables**, below the list blocks. Build the script exactly like this, bugs and all: fixing things before you've seen them fail teaches you nothing about finding them.

## Step 3: Write the test plan first, then run it

Here's the plan. The Expected column comes from the requirements, written before anyone clicked the green flag. Copy it onto paper with the Actual column blank.

| # | Test | `day` | `today` | Expected | Actual |
| --- | --- | --- | --- | --- | --- |
| 1 | Monday | 2 | 3/9 | 3 rings | |
| 2 | Friday | 6 | 3/13 | 3 rings | |
| 3 | Saturday | 7 | 3/14 | sleep in | |
| 4 | Sunday | 1 | 3/15 | sleep in | |
| 5 | Holiday, Friday | 6 | 12/25 | sleep in | |
| 6 | Holiday, Saturday | 7 | 7/4 | sleep in | |

Run each test in Scratch. Tick the checkbox next to `rings` so you can see it on the stage, and count the BEEPs.

Here is Sam's logic in a text language, Python, running the same plan. Each `if` and `else` matches a block in the script, and `while not rings > 3` is Python's way of saying `repeat until <(rings) > (3)>`. Your Scratch results should match its output:

```python run title="alarm_tests.py"
holidays = ["1/1", "7/4", "12/25"]
plan = [
    ("Monday", 2, "3/9", 3),
    ("Friday", 6, "3/13", 3),
    ("Saturday", 7, "3/14", 0),
    ("Sunday", 1, "3/15", 0),
    ("Holiday, Friday", 6, "12/25", 0),
    ("Holiday, Saturday", 7, "7/4", 0),
]

def run_plan(alarm):
    for name, day, today, expected in plan:
        actual = alarm(day, today)
        verdict = "pass" if actual == expected else "FAIL"
        print(f"{name:<18} expected {expected} rings, got {actual}   {verdict}")

def sams_alarm(day, today):
    alarm = "on"
    if today in holidays:
        alarm = "off"
    if day == 6 or day == 7:
        alarm = "off"
    else:
        alarm = "on"
    rings = 0
    if alarm == "on":
        while not rings > 3:
            rings = rings + 1
    return rings

run_plan(sams_alarm)
```

Three failures out of six, and that's good news: you now have exact evidence. There are two different symptoms. Friday and Sunday get the wrong *decision*, and the days that ring get 4 rings instead of 3. Fix one bug at a time, starting with the decision.

## Step 4: Fix bug 1, the day numbers

The Friday and Sunday failures point at the weekend check. Is 6 really Saturday? Find out with evidence, not memory: in the **Sensing** category, click the `(current [day of week v])` block itself. A bubble pops up with today's number. Compare it with today's actual day, and you'll find that Scratch counts **1 = Sunday** up to **7 = Saturday**.

So Sam's `6 or 7` meant Friday or Saturday. Change the 6 to 1:

```scratch
if <<(day) = (1)> or <(day) = (7)>> then
  set [alarm v] to [off]
else
  set [alarm v] to [on]
end
```

Now re-run the **whole** plan, not just the two failed tests:

```python run title="alarm_tests.py (fix 1)"
def alarm_fix1(day, today):
    alarm = "on"
    if today in holidays:
        alarm = "off"
    if day == 1 or day == 7:
        alarm = "off"
    else:
        alarm = "on"
    rings = 0
    if alarm == "on":
        while not rings > 3:
            rings = rings + 1
    return rings

run_plan(alarm_fix1)
```

Sunday passes now, and Friday rings (4 times, but that's the loop bug, which comes later). Now look at test 5: the Christmas test **passed before and fails now**. Bug 1 was hiding a second bug. The wrong day numbers happened to treat Friday 12/25 as a weekend, which covered up a broken holiday check. Re-running only the Sunday test would never have shown it.

## Step 5: Fix bug 2, the order of the checks

Trace test 5 by hand and write down `alarm` after each block:

| Block | `alarm` |
| --- | --- |
| `set alarm to on` | on |
| holiday check: 12/25 is in the list, so `set alarm to off` | off |
| weekend check: day 6 isn't 1 or 7, so the `else` runs `set alarm to on` | **on** |

There it is. The holiday check works, and then the weekend check's `else` overwrites it a moment later. This is a **sequence bug**: each block does its own job correctly, but the second one undoes the first.

You can see it happen in Scratch, too. Add a temporary `say (alarm) for (1) seconds` just after each of the two `if` blocks and run test 5. You'll see `off`, then `on`.

The cleanest fix is to ask one combined question, so nothing can overwrite anything. Delete both `if` blocks and the `set [alarm v] to [on]` above them, and put this in their place:

```scratch
if <<[holidays v] contains (today) ?> or <<(day) = (1)> or <(day) = (7)>>> then
  set [alarm v] to [off]
else
  set [alarm v] to [on]
end
```

Read it out loud: "if it's a holiday, or it's Sunday, or it's Saturday, the alarm is off. Otherwise it's on." Run all six tests again. Test 5 passes, and only the ring-count failures are left.

## Step 6: Fix bug 3, the extra ring

Every school day rings 4 times. Watch the `rings` monitor during a test: 0, 1, 2, 3, 4. Here is the loop on its own, as a text-language trace, so you can watch exactly when it decides to stop:

:::trace Count the rings: when does `rings > 3` finally become true?
```python
rings = 0
while not rings > 3:
    print("BEEP! BEEP!")
    rings = rings + 1
print("Stopped with rings =", rings)
```
:::

The loop checks `rings > 3` before each ring. At 0, 1, 2, and 3 the answer is no, so it rings four times, and only stops at 4. That's an **off-by-one error**: the stopping condition is one step too late.

You could change it to `repeat until <(rings) = (3)>`, but Scratch has a block that says exactly what the requirement says. Replace the whole `repeat until` loop with:

```scratch
repeat (3)
  say [BEEP! BEEP!] for (1) seconds
  wait (0.5) seconds
end
```

The `rings` counter isn't needed any more, so you can delete the `set [rings v] to (0)` block too. The `wait (0.5) seconds` adds a gap between the bubbles so you can count three separate rings.

## Step 7: Re-run everything, then switch off test mode

One last full run of the plan, with all three fixes:

```python run title="alarm_tests.py (all fixes)"
def alarm_fixed(day, today):
    if today in holidays or day == 1 or day == 7:
        return 0
    rings = 0
    for ring in range(3):
        rings = rings + 1
    return rings

run_plan(alarm_fixed)
```

Six out of six. Run the six tests in Scratch too, and check every row of your Actual column matches.

Now switch test mode off. Replace the two `ask` blocks and their `set` blocks with the real clock, and add a `wait until` so the alarm really waits for 6:30. Scratch's `current [hour]` uses 24-hour time, so 6:30 a.m. is hour 6, minute 30.

Moving to the real clock raises two new edge cases, so think them through before you build:

- **When is the day checked?** If the script reads the day once, when you click the green flag, then starting it on Sunday evening means it decides "Sleep in!" and never rings on Monday. The day has to be read each morning at 6:30, inside a `forever` loop.
- **What happens after the rings?** Three rings take about 5 seconds. Then the loop goes back to `wait until` 6:30, and it's *still* 6:30, so it would ring again and again for the whole minute. A second `wait until` makes it wait for the minute to change first.

## The finished alarm

```scratch title="Alarm clock (fixed)"
when green flag clicked
say [Alarm is running. Leave this project open.] for (2) seconds
forever
  wait until <<(current [hour v]) = (6)> and <(current [minute v]) = (30)>>
  set [day v] to (current [day of week v])
  set [today v] to (join (current [month v]) (join [/] (current [date v])))
  if <<[holidays v] contains (today) ?> or <<(day) = (1)> or <(day) = (7)>>> then
    say [No school today. Sleep in!] for (2) seconds
  else
    repeat (3)
      say [BEEP! BEEP!] for (1) seconds
      wait (0.5) seconds
    end
  end
  wait until <not <(current [minute v]) = (30)>>
end
```

The `join` blocks build today's date as text in the same month/day shape as the list, like `3/9`, so `contains` can match it. The `alarm` variable has gone: once the decision was a single if/else, it had nothing left to remember. To try the real-clock version without waking up at 6:30, temporarily change the hour and minute in the `wait until` to a time two minutes from now.

:::quiz
Q: Why did the Christmas test pass with Sam's original script but fail after the first fix?
- [ ] The first fix broke the holiday list
  The list never changed. The holiday check was already broken.
- [x] The wrong day numbers happened to treat Friday as a weekend, which hid the holiday bug
  Two bugs cancelled each other out for that one test. Fixing one revealed the other, and only re-running the whole plan showed it.
- [ ] Christmas isn't in the list
  `12/25` is in the list, and the trace in Step 5 shows the holiday check working.

Q: Why does the build use `ask` blocks for the day and date instead of the real clock while testing?
- [ ] The real clock blocks don't work in Scratch
  `current [day of week]` works fine. It just always gives *today's* answer.
- [x] So you can test Sunday, Friday, and Christmas without waiting for them
  A test mode makes the input controllable, so every row of the plan can be run in a few minutes.
- [ ] Because `ask` blocks run faster
  Speed isn't the reason. Control over the input is.

Q: The original loop was `repeat until <(rings) > (3)>` with `rings` starting at 0. Why did it ring 4 times?
- [ ] Because `say` blocks always run once extra
  `say` runs once each time the loop body runs.
- [ ] Because `rings` started at 1
  It started at 0, which is part of why there was one extra ring.
- [x] Because `rings > 3` is false at 0, 1, 2, and 3, so the body runs four times
  The loop only stops once `rings` reaches 4: a classic off-by-one error.
:::

:::takeaways
- Build the buggy version as written, then let a test plan show you exactly what's wrong.
- Use evidence: click a reporter block to see its real value instead of trusting your memory.
- One bug can hide another. Re-run the whole plan after every fix, not just the failing test.
- If one check overwrites another, combine them into a single decision.
- When the requirement says "exactly 3 times," `repeat (3)` says it directly and leaves no room for off-by-one errors.
:::
