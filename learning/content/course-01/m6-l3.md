:::objectives
- Predict a script's output by tracing it with a table of values.
- Pick test inputs that make a hidden bug show itself.
- Name each bug as a sequence, condition, or loop bug, and fix it.
- Re-test with a plan instead of trying one input and hoping.
:::

Every script below has something wrong with it, except the warm-up. For each one: predict first, trace if you need to, find the bug, fix it, then test the fix with more than one input. Build the scripts in Scratch if you want to see them fail for real.

## Warm-up: what does it say?

Predict the final value before you build it.

```scratch
when green flag clicked
set [x v] to (2)
repeat (3)
  change [x v] by (x)
end
say (x)
```

:::solution
It says **16**. `change [x v] by (x)` adds x to itself, which doubles it: 2 → 4 → 8 → 16. Three passes, three doublings. If you guessed 8, you probably counted the starting value as a pass.
:::

### Exercise 1: Fill in the trace table

Trace this script on paper. Make a table with columns for the step, `n`, and `total`, and fill in a row every time a variable changes. What does the sprite say?

```scratch
when green flag clicked
set [total v] to (0)
set [n v] to (1)
repeat until <(n) > (4)>
  change [total v] by (n)
  change [n v] by (1)
end
say (total)
```

:::hint
The loop checks `n > 4` at the top of every pass. The body runs while that's false, so it runs with n = 1, 2, 3, and 4. What is `total` after each one?
:::

:::solution
| After | `n` | `total` |
| --- | --- | --- |
| the two `set` blocks | 1 | 0 |
| pass 1 | 2 | 1 |
| pass 2 | 3 | 3 |
| pass 3 | 4 | 6 |
| pass 4 | 5 | 10 |

At the next check, 5 > 4 is true, so the loop ends and the sprite says **10** (1 + 2 + 3 + 4). Here is the same loop in a text language, printing a row each pass so you can check your table:

```python run title="trace_total.py"
total = 0
n = 1
while not n > 4:
    total = total + n
    n = n + 1
    print("n =", n, "  total =", total)
print("says", total)
```
:::

### Exercise 2: The invisible square

This script should draw a square with the **Pen** extension (click **Add Extension** at the bottom left of the editor, then choose **Pen**). It runs without any error, but nothing appears on the stage. Find the bug and fix it.

```scratch
when green flag clicked
erase all
go to x: (0) y: (0)
point in direction (90)
repeat (4)
  move (100) steps
  turn right (90) degrees
end
pen down
```

:::hint
Every block here is the right block. Is each one in the right place? Read the script aloud as instructions to a person holding a pen.
:::

:::solution
It's a **sequence bug**: `pen down` comes after the drawing, so the sprite walks the whole square with the pen up, then puts the pen down at the very end. Move `pen down` up to just before `repeat (4)`:

```scratch
when green flag clicked
erase all
pen up
go to x: (0) y: (0)
point in direction (90)
pen down
repeat (4)
  move (100) steps
  turn right (90) degrees
end
pen up
```

The extra `pen up` blocks at the start and end are good habits: the sprite won't leave a stray line when it jumps to the start, or when the project runs again.
:::

### Exercise 3: Counting to 10, almost

This should say every number from 1 to 10. Before you build it, predict the last number it says. Then fix it in two different ways.

```scratch
when green flag clicked
set [n v] to (1)
repeat until <(n) = (10)>
  say (n) for (0.5) seconds
  change [n v] by (1)
end
```

:::hint
Trace just the last two passes. When `n` becomes 10, what happens at the top of the loop before anything is said?
:::

:::solution
It says 1 to **9**. When `n` reaches 10, the loop's check is true, so it stops before saying 10. That's an **off-by-one loop bug**.

Fix 1: change the condition to `repeat until <(n) > (10)>`, so the body still runs when n is 10.

Fix 2: say exactly what you mean with a counting loop:

```scratch
when green flag clicked
set [n v] to (1)
repeat (10)
  say (n) for (0.5) seconds
  change [n v] by (1)
end
```

For both fixes, test the first and last numbers said, not just "it counts."
:::

### Exercise 4: Which version is broken?

A shop promises **free shipping on orders of $50 or more.** Three programmers wrote the check three ways:

```scratch
if <(total) > (50)> then
```

```scratch
if <not <(total) < (50)>> then
```

```scratch
if <(total) > (49)> then
```

Each one says "Free shipping!" when its condition is true. Choose three test totals that, between them, prove which versions are wrong. Then fill in a table of expected and actual results for all three versions.

:::hint
Each wrong version fails at a different total. One is wrong exactly *on* the boundary. The other is wrong for an amount with cents, just under the boundary.
:::

:::solution
Use **$49.50, $50.00, and $60.00**.

| Total | Expected | A: `> 50` | B: `not < 50` | C: `> 49` |
| --- | --- | --- | --- | --- |
| $49.50 | no | no | no | **yes** (wrong) |
| $50.00 | yes | **no** (wrong) | yes | yes |
| $60.00 | yes | yes | yes | yes |

Version A fails on the boundary. Version C only fails with cents, so if you'd tested whole-dollar totals like $49 and $50, it would have looked perfect. Version B is the correct one. Notice that $60 doesn't catch anything: tests far from the boundary rarely do.
:::

### Exercise 5: The sprite that won't stop

The sprite should glide right and stop at x = 200. Instead it slides to the right edge of the stage and stays pressed against it. The script never ends. Why?

```scratch
when green flag clicked
go to x: (0) y: (0)
repeat until <(x position) = (200)>
  change x by (15)
end
say [Made it!]
```

:::hint
Write down the x positions the sprite visits: 0, 15, 30… Does 200 ever appear in that list?
:::

:::solution
x goes 0, 15, 30, …, 180, 195, 210. It jumps straight over 200, so `x position = 200` is never true and the loop runs forever. This is a **loop bug** caused by an exact-match stopping condition. Stop on "reached or passed" instead:

```scratch
repeat until <(x position) > (199)>
  change x by (15)
end
```

Exact `=` checks are fine for stopping a loop only when you're certain the value lands on that number. With steps of 15, it never lands on 200. Test your fix with a different step size too, like 7 or 40.
:::

### Exercise 6: The warmest day of the week

A list called `temps` holds seven daily temperatures. This script should say the highest one. Find **two** bugs. For each, write a test list that exposes it.

```scratch
when green flag clicked
set [warmest v] to (0)
set [i v] to (1)
repeat (length of [temps v])
  if <(item (i) of [temps v]) > (warmest)> then
    set [warmest v] to (item (i) of [temps v])
  end
end
say (warmest)
```

:::hint
For the first bug: which item does the `if` look at on the second pass? On the third? For the second bug, think about a very cold week in Minnesota or northern Canada.
:::

:::solution
**Bug 1 (loop):** `i` never changes, so every pass looks at item 1 again. The test list `3, 9, 4` exposes it: the script says 3 instead of 9. Fix it by adding `change [i v] by (1)` at the end of the loop body.

**Bug 2 (edge case):** `warmest` starts at 0. In a week where every day is below freezing, like `-5, -12, -3`, nothing is bigger than 0, so the script says **0**, a temperature that never happened. Fix it by starting with the first item instead: `set [warmest v] to (item (1) of [temps v])`.

```scratch
when green flag clicked
set [warmest v] to (item (1) of [temps v])
set [i v] to (1)
repeat (length of [temps v])
  if <(item (i) of [temps v]) > (warmest)> then
    set [warmest v] to (item (i) of [temps v])
  end
  change [i v] by (1)
end
say (warmest)
```

Here is the fixed version in a text language, run against a whole test plan at once. Notice the tests that put the biggest value first, last, and in the middle:

```python run title="warmest.py"
def warmest(temps):
    best = temps[0]
    for t in temps:
        if t > best:
            best = t
    return best

tests = [
    ([3, 9, 4], 9),
    ([9, 3, 4], 9),
    ([3, 4, 9], 9),
    ([-5, -12, -3], -3),
    ([7], 7),
    ([5, 5, 5], 5),
]
for temps, expected in tests:
    got = warmest(temps)
    print(temps, "expected", expected, "got", got, "pass" if got == expected else "FAIL")
```
:::

### Challenge: Three bugs, one of each kind

This quiz should ask "What is 1 + 5?", then "2 + 5?", then "3 + 5?", and report how many you got right out of 3. It has exactly one sequence bug, one condition bug, and one loop bug. Write a test plan first (what do you type, and what score do you expect?), then find and fix all three.

```scratch
when green flag clicked
set [score v] to (0)
set [question v] to (1)
repeat (3)
  set [score v] to (0)
  ask (join [What is ] (join (question) [ + 5?])) and wait
  if <(answer) = ((question) + (6))> then
    change [score v] by (1)
    say [Correct!] for (1) seconds
  else
    say [Not quite.] for (1) seconds
  end
end
say (join [You scored ] (score)) for (2) seconds
```

:::hint
Good tests: answer all three correctly (expect 3), answer all three wrong (expect 0), and get only the first one right (expect 1). Watch the `score` and `question` monitors while you run each test.
:::

:::solution
- **Sequence bug:** `set [score v] to (0)` is inside the loop, so the score resets before every question and can never be more than 1. Delete the copy inside the loop.
- **Condition bug:** the correct answer is `(question) + (5)`, not `+ (6)`. Typing 6 for "1 + 5" is marked wrong.
- **Loop bug:** `question` never changes, so the quiz asks "What is 1 + 5?" three times. Add `change [question v] by (1)` at the end of the loop body.

With all three fixes, the three test runs should report scores of 3, 0, and 1.
:::

## Which kind of bug is it?

When a test fails, the *pattern* of the failure is a strong clue about where to look:

```mermaid caption="Use the shape of the failure to decide where to look first"
flowchart TD
    A["A test fails"] --> B{"Wrong for every input?"}
    B -->|yes| C["Check the ORDER of blocks"]
    B -->|no| D{"Never ends, or repeats the wrong number of times?"}
    D -->|yes| E["Check the LOOP and its stopping condition"]
    D -->|no| F["Check the CONDITIONS near the failing input"]
```

It's a starting point, not a rule. The invisible square was wrong every single time (order). The shipping checks were right everywhere except near $50 (conditions). The sprite that wouldn't stop never finished at all (loop).
