A school office buys a small delivery robot to carry packages from the front door to the principal's desk. On its first day, someone types in: "Go to the desk." The robot rolls straight ahead, bumps into a table, and stops. It isn't broken. It did exactly what it was built to do with the instruction it got. The instruction just didn't say enough.

Robots, and computers in general, have no common sense to fill in the gaps. Every gap you leave, they fill with something literal, and usually wrong. This module is about writing instructions with no gaps.

## What makes a list of steps an algorithm

A recipe, a set of directions, and a Scratch script are all lists of steps. Here's what an **algorithm** has to have, stated exactly: it's a list of steps that is

1.  **Exact.** Each step means one thing. "Turn" isn't exact (which way? how far?). "Turn right 90 degrees" is.
2.  **Ordered.** It's always clear which step comes next.
3.  **Finishing.** It ends, and you can tell when. "Keep walking" never finishes. "Walk 4 squares" does.

"Go to the desk" fails the first test. It describes the *goal*, but it doesn't give the robot a single action it can do. The robot needs the steps that *reach* the goal.

## A robot on a grid

Here's the office as a grid. The robot only understands three commands:

-   **F**: move forward one square.
-   **L**: turn left 90 degrees, staying on the same square.
-   **R**: turn right 90 degrees, staying on the same square.

```text
       1     2     3     4     5
    +-----+-----+-----+-----+-----+
  4 |     |     |     |     |  D  |
    +-----+-----+-----+-----+-----+
  3 |     |  #  |  #  |     |     |
    +-----+-----+-----+-----+-----+
  2 |     |  #  |  #  |     |     |
    +-----+-----+-----+-----+-----+
  1 |  >  |     |     |     |     |
    +-----+-----+-----+-----+-----+

  >  the robot, at column 1, row 1, facing right (east)
  #  a table the robot can't drive through
  D  the desk
```

One algorithm that works: **F F F F L F F F**. The robot drives along the bottom row to column 5, turns to face up the page (north), and drives up three squares to the desk.

## State: what the robot "knows" after each step

To check that route, you have to keep track of two things after every command: where the robot is, and which way it's facing. Together, those are the robot's **state**. Every step either changes the state or leaves it alone.

| After step | Command | Column | Row | Facing |
| --- | --- | --- | --- | --- |
| start | | 1 | 1 | east |
| 1 | F | 2 | 1 | east |
| 2 | F | 3 | 1 | east |
| 3 | F | 4 | 1 | east |
| 4 | F | 5 | 1 | east |
| 5 | L | 5 | 1 | north |
| 6 | F | 5 | 2 | north |
| 7 | F | 5 | 3 | north |
| 8 | F | 5 | 4 | north |

Look at row 5 of the table. **L** changed the direction but not the position. Beginners very often move the robot a square when it turns, and then every step after that is off by one.

Here's the same route in a text language. Each line is one command, written as the change it makes to the state. Step through it and watch `column`, `row`, and `facing` in the variables panel:

:::trace The delivery route, one command at a time
```python
column = 1
row = 1
facing = "east"
column = column + 1   # F
column = column + 1   # F
column = column + 1   # F
column = column + 1   # F
facing = "north"      # L
row = row + 1         # F
row = row + 1         # F
row = row + 1         # F
print("Robot at column", column, "row", row, "facing", facing)
```
:::

The text after each `#` is a comment for human readers; the computer skips it. Notice the line for **L** only touches `facing`, just like the table.

## Inputs and outputs

Every algorithm takes something in and gives something back. A recipe takes ingredients and gives you a cake. Directions take a starting point and give you an arrival.

For the delivery robot:

-   **Inputs:** the map (where the tables are), the robot's starting square, the way it starts out facing, and where the desk is.
-   **Output:** the robot arriving at the desk.

Here's why that matters. **F F F F L F F F** only works if the robot starts at column 1, row 1, facing east. Turn the robot to face north before you start, and the very same commands drive it up the left side and straight into the wall. The starting state is an input, even though nobody typed it in. A precise algorithm either sets the starting state itself or says exactly what it has to be.

## Events: what starts the steps

Steps don't run by themselves. Something has to start them. In Scratch, that something is an **event**, and the yellow hat-shaped blocks in the **Events** category wait for one: the green flag being clicked, a key being pressed, a sprite being clicked.

Real life works the same way. "When the bell rings, line up." "When the microwave beeps, take the food out." The event is the *when*; the steps under it are the *what*.

```scratch
when green flag clicked
go to x: (-180) y: (-120)
point in direction (90)
say [Ready to deliver!] for (2) seconds
```

```scratch
when [space v] key pressed
move (50) steps
```

These are two scripts on the same sprite, started by two different events. The green flag script sets the starting state: it puts the robot at the door and points it right (in Scratch, direction 90 means "facing right"). Each press of the space bar runs the second script once and moves the robot 50 steps. Press the space bar four times and the robot moves 200 steps, because each run starts from wherever the last one left it.

## Test for gaps by acting it out

You can't spot your own gaps by rereading, because your brain fills them in for you. You have to *act it out*: be the robot yourself, or ask a helper to follow your steps exactly, with no guessing allowed.

Try this instruction on the grid above: "Go forward until you reach the table, then turn and go to the desk."

Act it out. Facing east from column 1, row 1, the robot drives forward... and there is no table in row 1. It reaches the wall at column 5 and has no idea what to do. Even if it did reach a table, "turn" doesn't say left or right, and "go to the desk" is the goal again, not a step.

Words that almost always hide a gap:

-   **Amounts without numbers:** *a bit*, *a few*, *for a while*, *enough*.
-   **Directions without a side:** *turn*, *go around*, *move over*.
-   **Stopping points the reader can't check:** *until it looks right*, *when it's ready*.
-   **"It" and "there"**, when there's more than one thing they could mean.

## Mistakes to watch for

:::warning
**Forgetting the starting state.** A script with no `go to` and no `point in direction` at the top starts from wherever the sprite was left last time. It might work the first time and fail the second, which is the most confusing kind of bug. Set the starting state at the top of every algorithm.
:::

:::warning
**Mixing up the robot's left with yours.** L means the *robot's* left. When the robot is facing down the page, toward you, its left is your right. If a route keeps going the wrong way after a turn, turn your notebook so the robot is facing away from you, and check again.
:::

:::warning
**Counting the starting square.** Going from column 1 to column 5 takes 4 moves, not 5. The robot is already standing on column 1. Count the gaps you cross, not the squares you see.
:::

:::quiz
Q: On an empty grid, a robot starts at column 1, row 1, facing east. It runs **F F L F**. Where does it end up?
- [x] Column 3, row 2, facing north
  Two moves east take it to column 3, L turns it north without moving, and the last F moves it up to row 2.
- [ ] Column 4, row 1, facing north
  That treats L as a move. Turning changes the direction only; the robot stays on its square.
- [ ] Column 2, row 3, facing north
  That swaps columns and rows. Columns go across (east is +1 column), rows go up (north is +1 row).

Q: Which instruction would a robot find ambiguous?
- [ ] Move forward 1 square
  Exact: one action, one amount.
- [x] Turn toward the door
  Left or right? How far? And which door? A robot can't fill in any of that.
- [ ] Turn right 90 degrees
  Exact: a direction and an amount.

Q: You click the green flag twice, and the robot ends up in a different place each time. What's the most likely cause?
- [ ] Scratch moves sprites a little randomly
  `move` always moves exactly the number of steps you give it. Nothing here is random.
- [x] The script doesn't set a starting position and direction
  Without `go to` and `point in direction` at the top, the second run starts where the first one finished.
- [ ] The green flag was clicked too quickly
  Clicking the flag restarts the script from the top. The problem is what the top of the script does.

Q: For the algorithm "drive the robot to the desk", which of these is an **input**?
- [x] The square and direction the robot starts in
  The same commands give different results from different starting states, so the start is something the algorithm depends on.
- [ ] The robot arriving at the desk
  That's what the algorithm produces: the output.
- [ ] The color of the robot
  The route doesn't depend on it at all, so it isn't an input to this algorithm.
:::

:::takeaways
- An algorithm is exact, ordered, and finishes. A goal like "go to the desk" isn't an algorithm.
- State is what's true right now: here, the robot's position and direction. Every step changes it or leaves it alone.
- Turning changes direction, not position. Track both after every step.
- The starting state is an input. Set it at the top of the algorithm.
- Events decide when steps start. In Scratch, each hat block begins its own script.
- Find gaps by acting your steps out literally, not by rereading them.
:::
