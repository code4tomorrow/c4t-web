I'm thinking of a whole number from 1 to 100. You guess, and I tell you "higher" or "lower." How many guesses do you need?

If you guess 1, then 2, then 3, and so on, you'll always find it eventually. But if my number is 100, that's 100 guesses. There's another way that **never** needs more than 7, whatever the number is. And for a number from 1 to a million, that second way never needs more than 20.

Both ways are correct. They both always find the number. But one of them is wildly faster, and that difference is what this module is about: how to compare algorithms that all work, and pick the best one for the job.

## Two right answers can still be different

When two teams solve the same problem in different ways, "does it work?" is only the first question. The next ones are:

- **How many steps does it take?** Not seconds, because a fast laptop and an old tablet would give different times for the same algorithm. Count the main action instead: guesses, checks, comparisons, swaps.
- **What's the best case and the worst case?** In the counting-up game, the best case is my number being 1 (one guess). The worst case is 100 (a hundred guesses). The worst case is usually the one that matters, because it's the promise you can make.
- **What does it need?** Some algorithms only work if the data is already sorted, or if there's enough space.
- **Is it clear?** A slightly slower algorithm that everyone understands can beat a fast one nobody can check.

## Linear search: check every item in order

**Linear search** is the counting-up strategy. Here it is in plain English:

1. Look at the first item.
2. If it's the one you want, stop: you found it.
3. Otherwise, move to the next item and go back to step 2.
4. If you run out of items, it isn't there.

This is how you look for your phone in a lost-and-found box: pick things up one at a time. In Scratch, with a list called `box` and a variable `target`:

```scratch
set [i v] to (1)
repeat (length of [box v])
  if <(item (i) of [box v]) = (target)> then
    say (join [Found it at position ] (i))
    stop [this script v]
  end
  change [i v] by (1)
end
say [It isn't in the box.]
```

And here it is in a text language, Python, counting each check as it goes. `for item in box` means "take each item from the box in turn," and `break` means "stop the loop right now," like Scratch's `stop` block. Step through it and watch `checks`:

:::trace Linear search through the lost-and-found box
```python
box = ["hat", "scarf", "glove", "lunchbox", "phone", "umbrella"]
target = "phone"
checks = 0
found = False
for item in box:
    checks = checks + 1
    if item == target:
        found = True
        break
print("found:", found, "  checks:", checks)
```
:::

Five checks for the phone. The best case is 1 check (it's on top). The worst case is 6: the phone is at the bottom, or it isn't there at all, and you can only know *that* by checking everything. For a box of `n` items, linear search needs up to `n` checks.

The upside: linear search works on **any** list, in any order. The box doesn't need to be organized.

## Binary search: throw away half every time

The 7-guess strategy for the number game is **binary search**. Guess the middle (50). If I say "higher," every number from 1 to 50 is gone in one guess. Guess the middle of what's left (75), and half of *that* is gone. Each guess cuts the problem in half.

This only works because the numbers are in order. "Higher" tells you something about *all* the numbers below your guess. In a jumbled list, the middle item tells you nothing about the others.

The plain-English steps, for a sorted list:

1. Look at the middle item of the part you haven't ruled out.
2. If it's the target, stop.
3. If the target comes before it, rule out the middle and everything after it. Otherwise rule out the middle and everything before it.
4. If nothing is left, the target isn't there. Otherwise go back to step 1.

```mermaid caption="Binary search: every check either finds the target or halves what's left"
flowchart TD
    A["Look at the middle of what's left"] --> B{"Is it the target?"}
    B -->|yes| C["Found it"]
    B -->|no| D{"Target smaller?"}
    D -->|yes| E["Keep only the left half"]
    D -->|no| F["Keep only the right half"]
    E --> G{"Anything left?"}
    F --> G
    G -->|yes| A
    G -->|no| H["It isn't there"]
```

Here it is in Python on 15 sorted locker numbers. Two details: Python counts positions from **0**, so the first locker is position 0 and the last is position 14. And `//` means "divide and round down," which finds the middle position. Keep your eye on `low` and `high`, the two ends of the part that's still in play:

:::trace Binary search: watch low and high close in on locker 63
```python
lockers = [3, 8, 12, 17, 21, 26, 30, 34, 41, 45, 52, 58, 63, 70, 77]
target = 63
low = 0
high = len(lockers) - 1
checks = 0
while low <= high:
    middle = (low + high) // 2
    checks = checks + 1
    if lockers[middle] == target:
        print("Found", target, "after", checks, "checks")
        break
    elif lockers[middle] < target:
        low = middle + 1
    else:
        high = middle - 1
```
:::

Four checks: 34, 58, 70, 63. With 15 lockers, that's the worst case. Linear search could have needed 15.

## How the step counts grow

The real difference shows up as lists get bigger. Here is the worst case for both searches. The `binary_worst` function counts how many times you can halve a list before nothing is left, which is the most checks binary search can ever need:

```python run title="growth.py"
def binary_worst(n):
    steps = 0
    while n > 0:
        steps = steps + 1
        n = n // 2
    return steps

print(f"{'items':>15} {'linear':>15} {'binary':>8}")
for n in [10, 100, 1000, 1_000_000, 8_000_000_000]:
    print(f"{n:>15,} {n:>15,} {binary_worst(n):>8}")
```

The last row is roughly every person on Earth. If everyone's name were in one sorted list, binary search would find anyone in at most 33 checks.

Notice the pattern. When the list gets 10 times bigger, linear search needs 10 times as many checks. Binary search needs only about 3 more. **Doubling** the list adds just *one* binary check, because the first check cuts it back down to the old size. Here's what that looks like on a chart:

```python run alt="Line chart: linear search worst-case checks rise in a straight line from 1 to 1,000 as the list grows to 1,000 items, while binary search stays almost flat, ending at 10 checks." caption="Linear search grows with the list; binary search barely moves"
import matplotlib.pyplot as plt

def binary_worst(n):
    steps = 0
    while n > 0:
        steps = steps + 1
        n = n // 2
    return steps

sizes = list(range(1, 1001))
fig, ax = plt.subplots(figsize=(7, 4))
ax.plot(sizes, sizes, color="#2a78d6", linewidth=2, label="Linear search")
ax.plot(sizes, [binary_worst(n) for n in sizes], color="#eb6834", linewidth=2, label="Binary search")
ax.annotate("linear: 1,000 checks", (1000, 1000), xytext=(-8, -4), textcoords="offset points", ha="right", va="top", color="#0b0b0b")
ax.annotate("binary: 10 checks", (1000, 10), xytext=(-8, 8), textcoords="offset points", ha="right", va="bottom", color="#0b0b0b")
ax.set_xlabel("Items in the list")
ax.set_ylabel("Checks in the worst case")
ax.set_title("Worst-case checks as the list grows", loc="left")
ax.spines[["top", "right"]].set_visible(False)
ax.grid(axis="y", color="#e5e4e0", linewidth=0.8)
ax.legend(frameon=False, loc="upper left")
```

## Sorting: the price of binary search

Binary search needs sorted data, and sorting takes steps too. One of the simplest sorting algorithms is **selection sort**. You can do it with five playing cards right now:

1. Look through all the cards and find the smallest.
2. Swap it into the first position.
3. Now ignore the first card and repeat with the rest: find the smallest, swap it into the second position.
4. Keep going until only one card is left.

Here it is in Python with a counter for comparisons (each time two cards are compared). The line `cards[start], cards[smallest] = cards[smallest], cards[start]` swaps two cards' places:

:::trace Selection sort: count every comparison
```python
cards = [7, 3, 9, 1, 5]
comparisons = 0
for start in range(len(cards) - 1):
    smallest = start
    for i in range(start + 1, len(cards)):
        comparisons = comparisons + 1
        if cards[i] < cards[smallest]:
            smallest = i
    cards[start], cards[smallest] = cards[smallest], cards[start]
print(cards, "after", comparisons, "comparisons")
```
:::

Five cards take 4 + 3 + 2 + 1 = 10 comparisons. For 100 cards it's 99 + 98 + … + 1 = 4,950. Sorting is much more expensive than a single search.

So which should you use? It depends on how often you search:

- **Search once, in a jumble:** linear search. Sorting first would cost far more than it saves.
- **Search many times:** sort once, then use binary search every time. That's why dictionaries, phone contact lists, and library catalogs are kept in order. The sorting cost is paid once, and every lookup after that is fast.

:::warning
**Binary search on a list that isn't sorted.** It doesn't crash. It just gives wrong answers:

```python run title="unsorted.py"
def binary_search(items, target):
    low = 0
    high = len(items) - 1
    while low <= high:
        middle = (low + high) // 2
        if items[middle] == target:
            return "found"
        elif items[middle] < target:
            low = middle + 1
        else:
            high = middle - 1
    return "not found"

print(binary_search([1, 3, 5, 8, 9], 1))
print(binary_search([8, 3, 9, 1, 5], 1))
```

Both lists contain 1. In the jumbled one, the middle is 9, so the search throws away the right half, then sees 8 and throws away everything else, and reports "not found." Always check the input is sorted first.
:::

:::warning
**Judging an algorithm by one lucky run.** If you test the counting-up strategy with the secret number 3, it looks brilliant: 3 guesses! Compare algorithms on their worst case, or on the average over many inputs, never on a single run.
:::

:::quiz
Q: You play the guessing game with numbers from 1 to 1,000, always guessing the middle. What's the most guesses you'll ever need?
- [ ] 500
  That's about what linear search needs on average. Halving is much faster.
- [x] 10
  Each wrong guess roughly halves what's left: 1,000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1. That's ten sizes, so at most ten guesses.
- [ ] 1,000
  That's the worst case for counting up, not for halving.

Q: A sorted list grows from 500 names to 1,000 names. What happens to the worst-case checks?
- [ ] Both searches need twice as many
  That's true for linear search only.
- [x] Linear search doubles; binary search needs one more check
  Binary search's first check cuts 1,000 back to 500, so doubling the list adds just one step.
- [ ] Both stay the same
  Linear search has to check every name, so more names means more checks.

Q: You're looking for your friend's jacket in a heap of 30 coats, just once. Which approach makes sense?
- [x] Linear search: check each coat
  The heap isn't sorted, and sorting 30 coats to search once would take far more steps than just looking.
- [ ] Sort the coats by color, then binary search
  Sorting costs far more than one search saves. It only pays off if you'll search many times.
- [ ] Binary search right away
  The heap isn't in order, so the middle coat tells you nothing about the others.

Q: How many comparisons does selection sort make on 6 cards?
- [ ] 6
  Each pass compares the current card with all the cards after it, so it's more than one per card.
- [ ] 36
  That would be comparing every card with every card, including itself.
- [x] 15
  5 + 4 + 3 + 2 + 1 = 15. Each pass has one fewer card left to look through.
:::

:::takeaways
- Two correct algorithms can need very different numbers of steps. Compare them by counting the main action, not by timing them.
- Linear search works on any list and needs up to `n` checks for `n` items.
- Binary search needs a sorted list and halves the problem each check: at most 10 checks for 1,000 items, and 20 for a million.
- Selection sort on `n` cards makes (n − 1) + (n − 2) + … + 1 comparisons. Sorting is worth it when you'll search many times.
- Judge an algorithm by its worst case (or average), never by one lucky run.
:::
