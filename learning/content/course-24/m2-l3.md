summary: Decide which tool fits a request, turn vague requests into specs, write a spec linter, and make an agent loop survive bad tool calls, repeated actions, huge outputs, and a failed finish line.
---

:::objectives
- Match requests to autocomplete, chat, an agent, or doing it yourself.
- Rewrite a vague request as a spec and find the holes in someone else's.
- Write a linter that flags missing sections and uncheckable acceptance criteria.
- Harden a loop against bad tool calls, repeated actions, and oversized results, and add one retry with feedback.
:::

The first three exercises are about the words you hand an agent; the last three and the challenge are about the code wrapped around it. Every code solution is plain Python with a scripted model, so you can run it offline.

## Warm-up: pick the right tool

:::quiz
Q: You're writing a loop and know exactly what the next three lines should be.
- [x] Autocomplete
  You already know the answer; you just want it typed. Accept with Tab, reading it as you do.
- [ ] An agent
  Spinning up a multi-step loop for three lines you could type is slower and harder to review.
- [ ] Chat
  Chat works, but copying an answer back is slower than an inline suggestion.

Q: A test fails with `KeyError: 'total'` and you don't understand the traceback.
- [ ] An agent with permission to edit
  You don't know the cause yet, so you can't write acceptance criteria for a fix.
- [x] Chat, with the traceback and the function pasted in
  You need an explanation first. Once you understand the bug, you can decide whether to fix it yourself or delegate.
- [ ] Autocomplete
  Autocomplete continues code; it doesn't explain errors.

Q: Rename `char_count` to `count_chars` in four files and update every call and test.
- [ ] Do it by hand
  Possible, but it's mechanical, multi-file, and easy to verify, which is the sweet spot for an agent.
- [x] An agent, on a branch, with "all tests pass and `git grep char_count` finds nothing" as acceptance criteria
  Bounded, checkable with two commands, and reversible.
- [ ] Chat
  Chat would hand you edits to paste into four files yourself.

Q: Decide whether the project should move from `unittest` to `pytest`.
- [ ] An agent, so it can make the switch
  A tooling decision has trade-offs only you and your team can weigh. Letting an agent decide by doing it skips the decision.
- [x] Chat, asking for a comparison for this repo, then decide yourself
  The model can lay out trade-offs; the choice and its consequences stay with you.
:::

### Exercise 1: Turn a complaint into a spec

A teammate sends: *"top_words is weird with some inputs, can you get the AI to fix it?"* You investigate and find:

```text
>>> top_words("a b c", n=-1)
[('a', 1), ('b', 1)]
```

A negative `n` slices from the end (`ranked[:-1]`) and silently drops the last word. Write a complete task spec for an agent, using the sections from the Notes lesson: goal, context, in scope, out of scope, acceptance criteria, stop and ask if, report.

:::hint
Decide the behavior before you write the spec. Should `n=-1` raise an error, return `[]`, or return everything? An agent will pick one if you don't. Then make each acceptance criterion a single input with an exact expected result.
:::

:::solution
One good spec (yours may choose different behavior, as long as it states it):

```text
Goal: top_words(text, n) raises ValueError when n is negative.

Context: textstats.py; the bug is ranked[:n] with negative n slicing
from the end. n=0 returning [] is fine and should stay.

In scope: top_words in textstats.py; test_textstats.py.
Out of scope: every other function, new files, new dependencies.

Acceptance criteria:
1. top_words("a b c", n=-1) raises ValueError
2. top_words("a b c", n=0) returns []
3. top_words("b a", n=2) still returns [("a", 1), ("b", 1)]
4. python -m unittest -v passes with no existing test removed or skipped

Stop and ask if: any caller in the repo passes a negative n on purpose.

Report: files changed, full test output, and the error message you chose.
```

Criterion 2 matters: it pins down the edge next to the bug, so the fix can't accidentally break `n=0`. The "stop and ask" line covers the one thing that would make the fix wrong, which is code that relies on the old behavior.
:::

### Exercise 2: Find the holes in this spec

```text
Goal: Clean up textstats.py.
Acceptance criteria:
1. Code is cleaner and more readable
2. All tests pass
3. Performance is good
```

List at least four problems, and say what an agent might do because of each one.

:::hint
Go section by section: which of the usual sections are missing? Then, for each criterion, ask "what command would show this passed?"
:::

:::solution
- **No scope.** The agent may "clean up" the tests too, or add new files. Name the functions and files.
- **No out of scope.** Nothing stops it from renaming public functions, which breaks every caller.
- **Criterion 1 can't be checked.** "Cleaner" is a matter of taste; the agent decides alone what it means.
- **Criterion 2 can be gamed.** Tests can pass because tests were deleted, skipped, or loosened. Say "with no test removed, skipped, or edited."
- **Criterion 3 can't be checked.** No number and no benchmark.
- **No stop condition and no report.** The agent never pauses, and you get a summary instead of evidence.

The deeper problem: "clean up" isn't a task, it's a mood. Rewrite it as one concrete change (for example, "replace the manual counting dict in `top_words` with `collections.Counter`, no behavior change"), and most of these holes close on their own.
:::

### Exercise 3: A spec linter

Write `lint_spec(text)` that returns a list of problems. It should report each missing section heading (`Goal:`, `In scope:`, `Out of scope:`, `Acceptance criteria:`, `Stop and ask if:`) and each acceptance criterion that uses a vague word (`clean`, `better`, `properly`, `fast`, and so on) without any number in it. Sample output for the spec in the solution:

```text
missing section: Out of scope:
missing section: Stop and ask if:
uncheckable (properly): The code handles edge cases properly
uncheckable (clean): The result is clean
```

:::hint
Walk the lines with a flag that turns on after `Acceptance criteria:` and off at the next line that looks like a heading. Strip the list number (`1.`) before checking for digits, or every numbered criterion will look measurable.
:::

:::solution
```python run title="lint_spec.py"
import re

REQUIRED = ["Goal:", "In scope:", "Out of scope:", "Acceptance criteria:", "Stop and ask if:"]
VAGUE = {"clean", "better", "properly", "nice", "robust", "efficient", "fast", "good", "correctly"}


def lint_spec(text):
    problems = [f"missing section: {heading}" for heading in REQUIRED if heading not in text]
    in_criteria = False
    for line in text.splitlines():
        if line.startswith("Acceptance criteria:"):
            in_criteria = True
            continue
        if re.match(r"[A-Z][a-z ]*:", line):  # the next section heading
            in_criteria = False
        if in_criteria and line.strip():
            criterion = re.sub(r"^\s*\d+[.)]\s*", "", line)  # drop the "1." numbering
            vague = sorted(set(re.findall(r"[a-z]+", criterion.lower())) & VAGUE)
            if vague and not re.search(r"\d", criterion):
                problems.append(f"uncheckable ({', '.join(vague)}): {criterion}")
    return problems


spec = """Goal: make top_words handle bad n values.
In scope: top_words in textstats.py; test_textstats.py.
Acceptance criteria:
1. top_words("a b", n=-1) raises ValueError
2. The code handles edge cases properly
3. top_words stays fast on 10000 words
4. The result is clean
Report: test output."""

for problem in lint_spec(spec):
    print(problem)
```

Criterion 3 passes the linter because "10000 words" gives it something to measure. A linter like this can't judge whether a criterion is *good*, only whether it's the kind of sentence that could possibly be checked. That's still enough to catch the most common mistake.
:::

### Exercise 4: Turn every tool failure into a result

This line from the harness is a crash waiting to happen on three kinds of bad request: an unknown tool name, wrong argument names, and a tool that raises.

```python
result = TOOLS[reply["tool"]](**reply["args"])
```

Write `call_tool(name, args)` that always returns a string. Error messages should help the model fix its next request (for example, by listing the tools that do exist).

```text
print('hi')
error: unknown tool 'delete_file'; available: read_file, word_total
error: bad arguments for read_file: read_file() got an unexpected keyword argument 'filename'
error: read_file failed with KeyError: 'missing.py'
```

:::hint
Check the name before calling. Then wrap the call in `try`, catching `TypeError` (raised when keyword arguments don't match the function) separately from everything else.
:::

:::solution
```python run title="call_tool.py"
def read_file(path):
    files = {"app.py": "print('hi')"}
    return files[path]


def word_total(text):
    return str(len(text.split()))


TOOLS = {"read_file": read_file, "word_total": word_total}


def call_tool(name, args):
    """Run a tool and always return a string, even when something goes wrong."""
    if name not in TOOLS:
        return f"error: unknown tool {name!r}; available: {', '.join(sorted(TOOLS))}"
    try:
        return TOOLS[name](**args)
    except TypeError as exc:
        return f"error: bad arguments for {name}: {exc}"
    except Exception as exc:
        return f"error: {name} failed with {type(exc).__name__}: {exc}"


print(call_tool("read_file", {"path": "app.py"}))
print(call_tool("delete_file", {"path": "app.py"}))
print(call_tool("read_file", {"filename": "app.py"}))
print(call_tool("read_file", {"path": "missing.py"}))
```

One caution: catching `TypeError` around the call also catches a `TypeError` raised *inside* the tool, which would get the misleading "bad arguments" label. Module 5 fixes this properly by validating arguments against a schema before the call.
:::

### Exercise 5: Stop a model that repeats itself

Add stuck detection to a loop: if the model makes the exact same tool call (same name and same arguments) three times in a row, stop with a message. A model that alternates between different calls should not be stopped.

```text
stopped at step 4: run_tests called 3 times in a row
answer after 4 steps: found it
```

:::hint
Turn each call into something hashable, like `(name, tuple(sorted(args.items())))`, keep the last three in a list, and stop when the list is full and `len(set(recent)) == 1`.
:::

:::solution
```python run title="stuck.py"
class ScriptedModel:
    def __init__(self, replies):
        self.replies = list(replies)

    def respond(self, messages):
        return self.replies.pop(0)


def run_tests():
    return "ran 2 tests, 1 failed"


TOOLS = {"run_tests": run_tests, "read_file": lambda path: f"<contents of {path}>"}


def run_agent(model, max_steps=10, max_repeats=3):
    messages = []
    recent = []
    for step in range(1, max_steps + 1):
        reply = model.respond(messages)
        if "tool" not in reply:
            return f"answer after {step} steps: {reply['text']}"
        call = (reply["tool"], tuple(sorted(reply.get("args", {}).items())))
        recent = (recent + [call])[-max_repeats:]
        if len(recent) == max_repeats and len(set(recent)) == 1:
            return f"stopped at step {step}: {reply['tool']} called {max_repeats} times in a row"
        result = TOOLS[reply["tool"]](**reply.get("args", {}))
        messages.append({"role": "tool", "content": result})
    return "stopped: step limit"


stuck = ScriptedModel([{"tool": "read_file", "args": {"path": "a.py"}}] + [{"tool": "run_tests"}] * 9)
print(run_agent(stuck))
varied = ScriptedModel([
    {"tool": "run_tests"},
    {"tool": "read_file", "args": {"path": "a.py"}},
    {"tool": "run_tests"},
    {"text": "found it"},
])
print(run_agent(varied))
```

The stuck model is stopped at step 4, long before the 10-step limit, which saves six model calls. The varied model calls `run_tests` twice but not in a row, so it's left alone. Repeating a test run *after an edit* is normal; repeating it with nothing changed in between is the sign of a stuck loop.
:::

### Exercise 6: Keep huge tool results from flooding the context

A test run over 300 tests prints thousands of characters, and every one of them goes back to the model on every later step. Write `clip(result, limit=120)` that returns short results unchanged and shortens long ones, keeping the **start and the end** with a marker in between that says how much was cut.

:::hint
The end of a test log is where the summary lives (`FAILED (failures=1)`). Keep `limit // 2` characters from each end.
:::

:::solution
```python run title="clip.py"
def clip(result, limit=120):
    """Shorten a long tool result, keeping its start and its end."""
    if len(result) <= limit:
        return result
    half = limit // 2
    hidden = len(result) - 2 * half
    return result[:half] + f"\n[... {hidden:,} characters cut ...]\n" + result[-half:]


log = "\n".join([f"test_case_{n} ... ok" for n in range(1, 300)]
                + ["test_rounding ... FAIL", "", "Ran 300 tests in 0.410s", "", "FAILED (failures=1)"])
print(clip("ran 2 tests, 0 failed"))
print("---")
print(clip(log))
```

If you kept only the first 120 characters, the model would see a wall of `ok` lines and never learn that a test failed. The marker matters as well: it tells the model (and you, reading the transcript) that something was left out, so neither of you mistakes the clipped text for the whole output.
:::

### Challenge: One retry with feedback, then stop

Write `run_with_one_retry(model, task)`. It runs the agent loop; if the acceptance check fails, it appends a user message describing the failure and runs the loop **once** more on the same conversation. If the check still fails, it gives up and says a human should take over. Use a scripted model whose first fix is wrong and whose second is right.

```mermaid caption="The retry rule: one chance to use feedback, then a human"
stateDiagram-v2
    [*] --> Attempt1
    Attempt1 --> Review: check passes
    Attempt1 --> Attempt2: check fails, failure sent back
    Attempt2 --> Review: check passes
    Attempt2 --> HandOff: check fails again
    Review --> [*]
    HandOff --> [*]
```

:::hint
Keep `messages` outside the inner loop so the second attempt can see the first attempt's tool results *and* your feedback. Make the acceptance check run real code (`exec` the file and call the function) rather than searching the source for a string.
:::

:::solution
```python run title="retry.py"
class ScriptedModel:
    def __init__(self, replies):
        self.replies = list(replies)

    def respond(self, messages):
        return self.replies.pop(0)


files = {"pricing.py": "def apply_discount(p, pct):\n    return p - p * pct // 10\n"}


def write_file(path, content):
    files[path] = content
    return f"wrote {path}"


def check():
    """The acceptance check runs the code instead of reading it."""
    namespace = {}
    exec(files["pricing.py"], namespace)
    return namespace["apply_discount"](2000, 10) == 1800


TOOLS = {"write_file": write_file}


def run_agent(model, messages, max_steps=5):
    for _ in range(max_steps):
        reply = model.respond(messages)
        if "tool" not in reply:
            return reply["text"]
        result = TOOLS[reply["tool"]](**reply["args"])
        messages.append({"role": "tool", "content": result})
    return None


def run_with_one_retry(model, task):
    messages = [{"role": "user", "content": task}]
    for attempt in (1, 2):
        claim = run_agent(model, messages)
        passed = check()
        print(f"attempt {attempt}: model says {claim!r}; check {'PASS' if passed else 'FAIL'}")
        if passed:
            return "ready for human review"
        messages.append({"role": "user",
                         "content": "Acceptance check failed: apply_discount(2000, 10) should be 1800."})
    return "gave up after 2 attempts: hand this to a human"


model = ScriptedModel([
    {"tool": "write_file", "args": {"path": "pricing.py",
                                    "content": "def apply_discount(p, pct):\n    return p - p * pct // 1000\n"}},
    {"text": "Fixed."},
    {"tool": "write_file", "args": {"path": "pricing.py",
                                    "content": "def apply_discount(p, pct):\n    return p - p * pct // 100\n"}},
    {"text": "Fixed the divisor: a percent is out of 100."},
])
print(run_with_one_retry(model, "Fix the discount bug in pricing.py"))
```

The first "fix" gives `2000 - 20 = 1980`, so the check fails and the model gets one concrete sentence of feedback. Why only one retry? Each extra attempt costs model calls and adds more failed work to the context, and after two misses the problem is usually the task or the model, not bad luck. A human looking at it fresh is cheaper.
:::
