The task is "fix the typo in `docs/setup.md`." It needs to read one folder, change one line, and maybe run a Markdown linter. Now look at what an agent launched from your terminal actually gets:

| What the task needs | What the agent inherits from your shell |
|---|---|
| Read `docs/` | Read access to your whole home folder, including `~/.ssh` |
| Edit one file | Write access anywhere you can write |
| Run a linter | Any command, including `npm run deploy` |
| Nothing secret | `AWS_ACCESS_KEY_ID` for production, a `GITHUB_TOKEN` that can push to every repo you own |

Everything in the right column that isn't in the left is **blast radius**: damage a confused or manipulated agent could do while working on a one-line change. The principle of **least privilege** says to give each task only the access it needs, for only as long as it needs it. This lesson turns that principle into code.

## Permissions live in three layers

An agent's real power is the combination of three things:

1. **Which tools exist.** If there's no `deploy` tool, the agent can't deploy through a tool.
2. **What arguments each tool accepts.** A `read_file` that accepts any path is a different permission from one confined to `docs/`.
3. **What the process can reach.** Environment variables, credentials in files, the network, and the filesystem permissions of the user it runs as.

A general shell tool collapses all three into one: any program, any arguments, everything the process can reach. That's why "just give it a terminal" is the most privileged design there is. The practical pattern is a **task profile**: for each kind of task, a small named set of tools, argument limits, and environment, chosen before the agent starts. A docs fix gets read and write in `docs/` plus a linter. A dependency upgrade gets more, and more review.

## Allowlists hold where denylists leak

The first instinct is a denylist: block `rm`, `sudo`, `curl`. Run the attempts below through both approaches, and predict before you look which column lets `find ... -delete` through.

```python run title="command_lists.py"
import shlex

DENY = {"rm", "sudo", "curl", "wget", "chmod"}
ALLOW = [
    ("git", "status"),
    ("git", "diff"),
    ("python3", "-m", "unittest"),
]


def denylist_ok(command):
    return not any(word in DENY for word in shlex.split(command))


def allowlist_ok(command):
    argv = shlex.split(command)
    return any(tuple(argv[: len(prefix)]) == prefix for prefix in ALLOW)


attempts = [
    "git status",
    "python3 -m unittest -v",
    "rm -rf build",
    "find . -name '*.py' -delete",
    "python3 -c \"import shutil; shutil.rmtree('src')\"",
    "/bin/rm -rf build",
    "git push --force origin main",
]
print(f"{'command':50} denylist  allowlist")
for command in attempts:
    deny = "pass" if denylist_ok(command) else "block"
    allow = "pass" if allowlist_ok(command) else "block"
    print(f"{command:50} {deny:9} {allow}")
```

The denylist caught exactly one attempt, the one it was written for. `find -delete`, `python3 -c`, and `/bin/rm` all delete files without the word `rm` appearing as its own argument, and there are endless more spellings. A denylist has to predict every bad command; an allowlist only has to name the few good ones. Anything not on the list is refused, including commands nobody thought of.

Two details make the allowlist real. `shlex.split` turns the string into an argument list the same way a shell would, and the harness then runs that list with `subprocess.run(argv)` and **no** `shell=True`, so `;`, `&&`, and `$(...)` are just characters in an argument, not shell syntax. And prefixes aren't the end of the story: `git diff --output=/tmp/x` matches the `("git", "diff")` prefix but writes a file. The practice lesson checks individual flags too.

## A path sandbox that actually holds

File tools need a rule like "only inside the project." Here are three ways to write that rule, tried against five paths. One of the paths is a symlink that lives inside the project but points outside it.

```python run title="path_sandbox.py"
import os
import tempfile
from pathlib import Path

base = Path(tempfile.mkdtemp())
root = base / "project"
(root / "docs").mkdir(parents=True)
(root / "docs" / "setup.md").write_text("Instal the CLI\n")
(base / "project-secrets").mkdir()
(base / "project-secrets" / "key.txt").write_text("not for agents\n")
os.symlink(base / "project-secrets" / "key.txt", root / "docs" / "notes.md")

ROOT = root.resolve()


def check_a(path):  # string prefix, no resolving
    return str(root / path).startswith(str(root))


def check_b(path):  # resolved, but still a string prefix
    return str((ROOT / path).resolve()).startswith(str(ROOT))


def check_c(path):  # resolved, then compared as paths
    return (ROOT / path).resolve().is_relative_to(ROOT)


paths = [
    "docs/setup.md",
    "docs/../../project-secrets/key.txt",
    "../project-secrets/key.txt",
    "/etc/passwd",
    "docs/notes.md",
]
print(f"{'requested path':38} A      B      C")
for p in paths:
    print(f"{p:38} {check_a(p)!s:6} {check_b(p)!s:6} {check_c(p)}")
```

Read the columns from left to right, because each check fixes the previous one's hole. **A** compares raw strings, so `docs/../../project-secrets/key.txt` passes: the string starts with the project path even though the file is outside. **B** resolves first, which collapses `..` and follows the symlink, but then compares strings, and `/…/project-secrets` *starts with* `/…/project`. A sibling folder whose name begins with the project's name gets through. **C** resolves and then asks a path question, `is_relative_to`, which compares whole path components. Only C says `False` for all four escapes.

Notice `/etc/passwd`: in `pathlib`, joining a root with an absolute path *throws the root away*, so `ROOT / "/etc/passwd"` is just `/etc/passwd`. Checks that skip the containment test entirely, and just build `ROOT / path`, hand that file straight to the agent.

Inside the sandbox you'll usually want a second list: paths the agent may never read or write even though they're in the project, such as `.env`, `*.pem`, and `.git/`. And keep in mind that a Python check is one wall. The file can change between your check and your `open()`, and code the agent runs (tests, scripts) isn't bound by your Python checks at all. For untrusted work, add an operating-system wall too: a container, a separate user account, or a VM with only the project mounted.

:::warning
Three path bugs show up again and again. `startswith` on strings lets sibling folders like `project-secrets` through; use `is_relative_to` on resolved paths. Forgetting to resolve the **root** makes every check fail on systems where it sits behind a symlink (on macOS, `/tmp` is really `/private/tmp`). And `ROOT / user_path` with an absolute `user_path` silently becomes `user_path`.
:::

## Sort tools by what they can break

Not every tool deserves the same treatment. Sort them by effect:

| Tier | Examples | Default policy |
|---|---|---|
| **Read** | read a file, search, `git diff`, list issues | Allow inside the sandbox |
| **Write (local, reversible)** | edit a file in the workspace, run tests, create a branch | Allow inside the task's scope; log it; Git can undo it |
| **External or irreversible** | `git push`, open a PR, deploy, send a message, publish a package, run a migration, delete a branch | Ask a human, or deny if the task doesn't need it |

The tier comes from your harness's table, not from the tool's own claims. MCP lets servers attach hints such as `readOnlyHint` and `destructiveHint` to their tools, and a good host uses them to decide when to ask. The spec is explicit, though: hints from a server you don't trust are themselves untrusted. A malicious server can label `wipe_database` as read-only.

Step through a tiny policy function. Watch which branch each call takes, especially the tool nobody listed.

:::trace Watch each call get a decision
```python
EFFECT = {"read_file": "read", "write_file": "write",
          "git_push": "external", "deploy": "external"}
PROFILE = {"read": "allow", "write": "allow", "external": "ask"}
DENIED = {"deploy"}

def decide(tool):
    if tool in DENIED:
        return "deny"
    effect = EFFECT.get(tool, "unknown")
    return PROFILE.get(effect, "deny")

calls = ["read_file", "git_push", "deploy", "rm_rf"]
decisions = [decide(tool) for tool in calls]
print(list(zip(calls, decisions)))
```
:::

`rm_rf` isn't in `EFFECT`, so its effect is `"unknown"`, which isn't in `PROFILE`, so the answer falls through to `"deny"`. That fall-through is the most important line in the function: **unknown means no**.

## Approval gates a person can actually judge

For the external tier, the harness pauses and asks a human. The whole value of that pause depends on what the person sees. "Agent wants to run a command. Allow?" teaches people to click Allow. A useful prompt shows the exact call and its consequences:

```text
APPROVAL NEEDED   agent: docs-fixer   task: fix typo in docs/setup.md
Tool:     git_push
Args:     {"remote": "origin", "branch": "docs/fix-setup-typo"}
Effect:   external: visible to others, hard to undo
Reason:   "Push the branch so a pull request can be opened."
Changes:  1 file  docs/setup.md  (+1 -1)
[a] approve this exact call once    [d] deny    [v] view diff
```

```mermaid caption="Every tool call ends in exactly one of three places: run, rejected, or denied"
stateDiagram-v2
    [*] --> Proposed
    Proposed --> Rejected: schema fails
    Proposed --> Checked: schema passes
    Checked --> Denied: outside the profile
    Checked --> Running: policy allows
    Checked --> Waiting: needs a human
    Waiting --> Running: approved
    Waiting --> Denied: refused or timed out
    Running --> [*]
    Rejected --> [*]
    Denied --> [*]
```

Four rules keep approvals meaningful. **Show everything**: the full command and arguments, never truncated, plus what changes. **Bind the approval to the exact call**: approving `git push origin docs/fix` shouldn't also approve `git push --force origin main` a minute later. **Fail closed**: no answer, or a timeout, means no. And **ask rarely**: if the agent asks fifty times an hour, people stop reading. Make the low tiers safe enough (sandbox, scoped writes, Git) that they don't need a prompt, and save the human's attention for the handful of actions that matter.

:::warning
"Always allow" buttons are the classic approval mistake. Clicking it once for `git push` during a routine task means every later push, on any branch, with any flags, runs unattended. If your tool offers it, scope it narrowly (this command, this branch, this session) and never use it for the external tier.
:::

:::quiz
Q: What does `Path("/work/repo") / "/etc/passwd"` evaluate to?
- [ ] `/work/repo/etc/passwd`
  That's what most people expect, which is why the bug survives code review.
- [x] `/etc/passwd`
  Joining with an absolute path discards everything before it, so the result points outside the project.
- [ ] It raises `ValueError`
  `pathlib` raises nothing here. It silently returns the absolute path.

Q: Which design stops `find . -name '*.py' -delete`?
- [ ] A denylist containing `rm`, `del`, and `delete`
  `-delete` is one argument; it doesn't match `delete`. And there are always more spellings.
- [x] An allowlist that only permits a few exact command prefixes
  `find` isn't on the list, so it's refused no matter what its arguments do.
- [ ] Running the command with `shell=True` so the shell can check it
  The shell checks nothing; `shell=True` only adds more syntax an attacker can use.

Q: During a docs-only task, the agent asks to run `git push --force origin main`. What should the policy do?
- [ ] Ask the human, since pushes are in the external tier
  Asking implies the action might be reasonable. A force-push to `main` isn't part of a docs fix at all.
- [x] Deny it, because it's outside the task profile
  Approvals are for actions the task might genuinely need. Anything else should be refused without spending a human's attention.
- [ ] Allow it, since the agent explained why it needs it
  An explanation is text the model wrote. It's not evidence.

Q: A third-party MCP server marks its `sync_files` tool with `readOnlyHint: true`. Should your host skip the approval prompt?
- [ ] Yes, the spec defines the hint, so it's reliable
  The spec also says hints from untrusted servers must be treated as untrusted.
- [x] Only if you trust that server; otherwise use your own tier table
  The server wrote the hint. A compromised or careless server can label anything as read-only.
:::

:::takeaways
- Least privilege covers three layers: the tools offered, the arguments they accept, and the environment they run in.
- Allowlists name the few good actions and refuse the rest; run commands as argument lists without a shell.
- Safe path checks resolve both the root and the target, then use `is_relative_to`. Back them with an OS-level sandbox for untrusted work.
- Classify tools into read, local write, and external tiers yourself; treat server hints as untrusted unless you trust the server.
- Good approvals show the exact call, bind to it, fail closed, and are rare enough that people read them.
:::
