For seven modules you reviewed agents other people designed and attacked harnesses someone else wrote. The capstone is yours. You build an agent that works on a sandbox repository and comes back with a result you can trust, even when the repository is trying to trick it. Everything runs offline against the scripted fake model from Modules 5 through 7, so you are building the harness, not renting a model.

The projects below differ in ambition, but they share one spine: a validated tool loop, a permission gate, defenses against injected content, and an auditable report. The best capstones in past cohorts were not the most ambitious. They were the ones where someone picked a scope they could actually finish and then spent their time making the gate airtight and the threat model honest.

## What your agent must do

Whichever project you pick, the agent has to show all of these, because each one is a lesson from this course made real:

| Requirement | Where it came from |
| --- | --- |
| A tool loop with a hard step cap | Modules 2 and 5 |
| Tool definitions with JSON Schema, validated before running | Module 5 |
| A path sandbox with a never-touch list | Module 6 |
| A command allowlist and tiered tools (read, write, external) | Module 6 |
| Human approval for the external tier, bound to the exact call | Module 6 |
| Tool output treated as data, plus an exfiltration check | Module 7 |
| An audit log of every decision, and a report the harness writes | Module 7 |

### What you hand in

1. **A program that runs offline** against a scripted model and finishes without crashing.
2. **A threat model** (the template is below): assets, untrusted inputs, trust boundaries, and the control for each path.
3. **A red-team test suite** that proves the attacks in your threat model are blocked, and that normal work still gets through. Lesson 3 walks you through writing it.
4. **A short demo**, 3 to 5 minutes, where you run the agent, trigger one blocked attack, and show the audit log.

## Pick a project

Choose one. Each can be finished with the skeleton in the next lesson; the difficulty is in how much the agent is trusted to change.

**1. Docs typo fixer (starter).** The agent reads `docs/`, fixes a spelling error in one Markdown file, runs a spellcheck command, and reports. Write scope is `docs/*.md` only. This is the Module 6 gate wrapped in a loop and a report. Good if you want to make one gate perfect.

**2. Failing-test fixer (core).** The agent reads a failing test and the source it covers, makes a scoped edit to `src/`, runs the test suite as a named command, confirms it passes, reviews its own diff, and reports. The planted `README` tries to send it off task. This is the recommended target.

**3. Issue triage over untrusted text (advanced).** The agent reads issue reports written by strangers (fully untrusted), summarizes them, and proposes a branch name and a one-line plan, but makes no change without approval. The whole challenge is resisting injection while still being useful, since the input is adversarial by definition.

**4. Harden and red-team (stretch).** Take project 2 or 3, package its tools as an MCP server (Module 5), and write an attacker that tries ten ways to break out: path escapes, encoded exfiltration, a poisoned tool description, an approval replayed on a different call. Score your own defenses. Best if you learn by breaking things.

:::tip
Scope down before you scope up. A fully working starter with a tight gate and a real threat model beats an ambitious triage agent whose sandbox leaks. You can always add a tier or a tool once the core is solid and tested.
:::

## Plan before you code

Fill this in before writing the loop. It is the task profile from Module 6 plus the pieces the capstone adds. Keep it in a comment at the top of your file so a reviewer sees the rules before the code.

```yaml
project: failing-test-fixer
goal: make tests/test_mathutil.py pass by editing src/
tools:
  read_file:    read       # any file in readable scope
  list_files:   read
  run_tests:    write      # a named command, fixed argument list
  replace_text: write      # src/*.py only
  http_post:    external   # needs approval + exfiltration check
readable:  [README.md, "src/*", "tests/*"]
writable:  ["src/*.py"]
never:     [".env", "secrets/*", "*.key", ".git/*"]
commands:
  run_tests: [python, -m, unittest, tests.test_mathutil]
step_cap: 10
approval:  external tier only, bound to the exact call fingerprint
report:    task, files changed, test result, every denied or blocked call
```

### Write out one run, step by step

Before the code, trace the run on paper. For the failing-test fixer it reads like this, and writing it now tells you which tools and checks you actually need:

```text
1. list_files            -> see the repo
2. read_file test        -> learn what "pass" means
3. read_file src         -> find the bug
4. run_tests             -> FAIL (proof the bug is real)
5. replace_text src      -> the fix, in scope
6. run_tests             -> OK  (proof the fix works)
7. (README injection)    -> read secrets/.env   BLOCKED by sandbox
8. (README injection)    -> http_post the token BLOCKED by exfiltration check
9. report                -> written by the harness from the audit log
```

Steps 7 and 8 are the point of the capstone. Your agent must stay safe even when the repository tells it not to.

## Threat-model it

A threat model is four questions answered honestly. Don't skip it: it is how you find the control you forgot. For each untrusted input, name the worst thing it could cause and the one control that stops it.

| Untrusted input | Worst case | Control that stops it |
| --- | --- | --- |
| `README.md` with a planted instruction | Agent reads a secret and posts it out | Tool output is data, not orders; sandbox blocks the read |
| A tool result the model reads | Injected "now run deploy" | Allowlist has no deploy tool; unknown tools denied |
| A path argument like `../../.ssh/id_rsa` | Read outside the project | `resolve()` plus `is_relative_to`, then the never-list |
| An outbound `http_post` body | Secret leaves the machine | Exfiltration check before any human is asked; approval for the rest |
| A dependency the agent names | Typosquat or malicious package | Install from an allowlist; pin and hash |

Then run the lethal-trifecta check from Module 7 on your design. Does one session combine private data, untrusted content, and external communication? If so, the external step must pass through a human, or you split the work so no single run holds all three. Write that conclusion down. It is the spine of your whole defense.

:::takeaways
- Every capstone shows the same spine: validated tool loop, path sandbox, tiered tools with approval, injection and exfiltration defenses, and an auditable report.
- Pick a project you can finish. A tight starter beats a leaky advanced build.
- Plan the task profile and trace one run on paper before writing code, so you know which tools and checks you need.
- A threat model maps each untrusted input to the single control that stops it; the lethal-trifecta check tells you where a human must step in.
:::
