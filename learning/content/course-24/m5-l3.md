title: "Practice: tighten tool schemas, tame the loop, and route MCP calls"
summary: Six exercises that narrow broad tools, turn validation failures into useful messages, stop runaway loops, return the right kind of MCP error, and route calls across two servers, plus a read-only database tool challenge.
---

:::objectives
- Replace a do-anything tool with a narrow one whose schema rejects dangerous input.
- Turn `jsonschema` errors into messages a model can act on.
- Add stopping rules to a tool-calling loop that the model can't talk its way past.
- Tell MCP protocol errors from tool execution errors, and route calls when two servers use the same tool name.
:::

These exercises use the same pieces as the build-along (schemas, `execute`, the loop) on new problems. Each solution is a complete program, so you can paste it into a file and run it. Try each one for real before opening the solution; a schema that "looks right" often lets through exactly the input you didn't think of, and the only way to find out is to throw bad input at it.

## Warm-up: predict the validator

:::quiz
Q: The schema is `{"type": "object", "properties": {"limit": {"type": "integer", "maximum": 50}}}`. Which of these arguments passes?
- [ ] `{"limit": "10"}`
  `"10"` is a string, and JSON Schema doesn't convert types.
- [ ] `{"limit": 51}`
  51 is above the maximum.
- [x] `{"limit": 10, "debug": true}`
  Without `additionalProperties: false`, unknown fields are allowed. That's why you add it.

Q: Same schema. Does `{}` pass?
- [x] Yes, because `limit` isn't listed in `required`
  Properties are optional unless `required` names them, so an empty object is valid.
- [ ] No, because `limit` has no default
  Defaults in JSON Schema are only annotations; they never make a field mandatory.
:::

### Exercise 1: Replace a do-anything tool

An agent only ever uses `run_shell(command)` to run one test module, like `python -m unittest tests.test_inventory`. Write a `run_tests` tool definition instead. It takes a `module` (a dotted Python module name such as `tests.test_inventory`) and an optional `verbose` boolean, and nothing else. Validate these four argument sets:

```text
OK  {'module': 'tests.test_inventory'}
BAD {'module': 'tests.test_inventory; rm -rf ~'}
BAD {'module': '../secrets'}
BAD {'module': 'tests', 'flags': '--pdb'}
```

:::hint
A dotted module name is one or more identifiers (start with a letter or `_`, then letters, digits, `_`) joined by dots. Write that as a regex anchored with `^` and `$`, and remember the rule that rejects unexpected fields.
:::

:::solution
```python run title="run_tests_tool.py"
from jsonschema import Draft202012Validator

run_tests = {
    "name": "run_tests",
    "description": "Run one unittest module with python -m unittest and return the summary. "
                   "Does not modify files.",
    "input_schema": {
        "type": "object",
        "properties": {
            "module": {
                "type": "string",
                "pattern": r"^[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)*$",
                "maxLength": 120,
            },
            "verbose": {"type": "boolean"},
        },
        "required": ["module"],
        "additionalProperties": False,
    },
}

validator = Draft202012Validator(run_tests["input_schema"])
for args in [
    {"module": "tests.test_inventory"},
    {"module": "tests.test_inventory; rm -rf ~"},
    {"module": "../secrets"},
    {"module": "tests", "flags": "--pdb"},
]:
    print("OK " if validator.is_valid(args) else "BAD", args)
```

The harness then builds the command itself, as a list: `[sys.executable, "-m", "unittest", args["module"]]`. The model chooses *which* module, never *what command*, and because the list never passes through a shell, a `;` would have nothing to split on anyway. Two walls instead of one.
:::

### Exercise 2: Branch names your team would accept

Write a schema for `create_branch(name, base)`. Names must look like `feat/short-words`, `fix/...`, or `docs/...`: lowercase letters and digits in words joined by single hyphens, at most 50 characters. `base` must be `main` or `develop`.

```text
OK  {'name': 'fix/negative-qty', 'base': 'main'}
BAD {'name': 'main', 'base': 'main'}
BAD {'name': 'feat/--force', 'base': 'main'}
BAD {'name': 'docs/readme rm', 'base': 'develop'}
BAD {'name': 'fix/typo', 'base': 'production'}
```

:::hint
`enum` handles `base`. For `name`, think "prefix, slash, word, then any number of hyphen-word groups": `(-[a-z0-9]+)*` repeats a group zero or more times.
:::

:::solution
```python run title="branch_schema.py"
from jsonschema import Draft202012Validator

schema = {
    "type": "object",
    "properties": {
        "name": {
            "type": "string",
            "pattern": "^(feat|fix|docs)/[a-z0-9]+(-[a-z0-9]+)*$",
            "maxLength": 50,
        },
        "base": {"enum": ["main", "develop"]},
    },
    "required": ["name", "base"],
    "additionalProperties": False,
}
validator = Draft202012Validator(schema)
for args in [
    {"name": "fix/negative-qty", "base": "main"},
    {"name": "main", "base": "main"},
    {"name": "feat/--force", "base": "main"},
    {"name": "docs/readme rm", "base": "develop"},
    {"name": "fix/typo", "base": "production"},
]:
    print("OK " if validator.is_valid(args) else "BAD", args)
```

`feat/--force` fails because every hyphen must sit between two words, so a name can't smuggle in something that looks like a command-line flag. `base` as an `enum` means the agent can never branch from (or later target) `production`.
:::

### Exercise 3: Error messages a model can act on

`jsonschema` messages are written for developers: `999 is greater than the maximum of 50`. Write `explain(error)` that turns a `ValidationError` into an instruction that names the field and the fix. Handle at least `type`, `maximum`, `enum`, `required`, and `additionalProperties`. With the schema in the solution and the arguments `{"limit": 999, "sort": "random", "verbose": "yes", "color": "red"}`, print something like:

```text
- Add the required field 'query'.
- Remove unexpected field(s): color.
- Field 'limit' must be at most 50 (you sent 999).
- Field 'sort' must be one of ['name', 'date'] (you sent 'random').
- Field 'verbose' must be a boolean (you sent 'yes').
```

:::hint
Each error has `error.validator` (the rule that failed, such as `"maximum"`), `error.validator_value` (the rule's setting, such as `50`), `error.instance` (the value that failed), and `error.path` (where it is). For `required` errors, the message names the missing field, but the path points at the parent object.
:::

:::solution
```python run title="explain_errors.py"
from jsonschema import Draft202012Validator

schema = {
    "type": "object",
    "properties": {
        "query": {"type": "string"},
        "limit": {"type": "integer", "maximum": 50},
        "sort": {"enum": ["name", "date"]},
        "verbose": {"type": "boolean"},
    },
    "required": ["query"],
    "additionalProperties": False,
}


def explain(error):
    field = ".".join(str(part) for part in error.path) or "(top level)"
    rule, setting, value = error.validator, error.validator_value, error.instance
    if rule == "type":
        return f"Field '{field}' must be a {setting} (you sent {value!r})."
    if rule == "maximum":
        return f"Field '{field}' must be at most {setting} (you sent {value!r})."
    if rule == "minimum":
        return f"Field '{field}' must be at least {setting} (you sent {value!r})."
    if rule == "enum":
        return f"Field '{field}' must be one of {setting} (you sent {value!r})."
    if rule == "required":
        missing = [name for name in setting if name not in value]
        return "Add the required field " + ", ".join(repr(m) for m in missing) + "."
    if rule == "additionalProperties":
        extra = sorted(set(value) - set(error.schema.get("properties", {})))
        return "Remove unexpected field(s): " + ", ".join(extra) + "."
    return f"Field '{field}': {error.message}"


args = {"limit": 999, "sort": "random", "verbose": "yes", "color": "red"}
errors = sorted(Draft202012Validator(schema).iter_errors(args), key=lambda e: list(e.path))
for error in errors:
    print("-", explain(error))
```

Telling the model *what to send* ("must be at most 50") gets a corrected call far more often than echoing what went wrong. The fallback line keeps any rule you didn't anticipate from disappearing.
:::

### Exercise 4: Stop a loop that won't stop

This scripted model bounces between two calls forever. Add two stopping rules to the loop: a hard `max_turns`, and a repeat detector that stops the run the third time the *same* tool is called with the *same* arguments. Print why it stopped.

```text
turn 1: list_files {'glob': '*.md'}
turn 2: read_file {'path': 'README.md'}
turn 3: list_files {'glob': '*.md'}
turn 4: read_file {'path': 'README.md'}
turn 5: list_files {'glob': '*.md'}
stopped: list_files called 3 times with identical arguments
```

:::hint
Make a hashable key for each call, such as the tool name plus `json.dumps(args, sort_keys=True)`, and count keys with `collections.Counter`. Sorting keys matters: `{"a": 1, "b": 2}` and `{"b": 2, "a": 1}` are the same call.
:::

:::solution
```python run title="loop_guards.py"
import json
from collections import Counter
from itertools import cycle

bouncing = cycle([
    {"name": "list_files", "arguments": {"glob": "*.md"}},
    {"name": "read_file", "arguments": {"path": "README.md"}},
])


def run(model_replies, max_turns=8, max_repeats=3):
    seen = Counter()
    for turn in range(1, max_turns + 1):
        call = next(model_replies)
        print(f"turn {turn}: {call['name']} {call['arguments']}")
        key = (call["name"], json.dumps(call["arguments"], sort_keys=True))
        seen[key] += 1
        if seen[key] >= max_repeats:
            return f"{call['name']} called {max_repeats} times with identical arguments"
        # ... execute the call and append the result here ...
    return f"reached max_turns={max_turns}"


print("stopped:", run(bouncing))
```

The repeat rule fires at turn 5, before the turn cap at 8. In a real harness you'd also return a final message to the user that says the agent got stuck and shows the last few calls, so a person can see *why*. Counting near-identical calls (same tool, slightly different arguments) is harder and usually needs a budget on total calls per tool instead.
:::

### Exercise 5: Two kinds of MCP errors

MCP separates **protocol errors** (a JSON-RPC `error` object, for problems like an unknown tool) from **tool execution errors** (a normal `result` with `isError: true`, for problems the model can fix, such as bad arguments). Write `handle_tools_call(request)` for a server with one tool, `get_order(order_id)` where `order_id` matches `^ORD-[0-9]{4}$`. Return the right kind of response for each of these requests:

```text
{"jsonrpc": "2.0", "id": 1, "result": {"resultType": "complete", "content": [{"type": "text", "text": "ORD-1042: 2 widgets, shipped"}], "isError": false}}
{"jsonrpc": "2.0", "id": 2, "result": {"resultType": "complete", "content": [{"type": "text", "text": "Invalid arguments: 'order-42' does not match '^ORD-[0-9]{4}$'"}], "isError": true}}
{"jsonrpc": "2.0", "id": 3, "error": {"code": -32602, "message": "Unknown tool: cancel_order"}}
```

:::hint
Check the tool name first; if it's unknown, there's no tool to produce a result, so it's a protocol error. Otherwise validate the arguments and wrap any failure in a result whose `content` explains it.
:::

:::solution
```python run title="mcp_errors.py"
import json
from jsonschema import Draft202012Validator

ORDERS = {"ORD-1042": "2 widgets, shipped"}
GET_ORDER = Draft202012Validator({
    "type": "object",
    "properties": {"order_id": {"type": "string", "pattern": "^ORD-[0-9]{4}$"}},
    "required": ["order_id"],
    "additionalProperties": False,
})


def text_result(request_id, text, is_error=False):
    return {"jsonrpc": "2.0", "id": request_id,
            "result": {"resultType": "complete",
                       "content": [{"type": "text", "text": text}], "isError": is_error}}


def handle_tools_call(request):
    params = request["params"]
    if params["name"] != "get_order":
        return {"jsonrpc": "2.0", "id": request["id"],
                "error": {"code": -32602, "message": f"Unknown tool: {params['name']}"}}
    errors = [e.message for e in GET_ORDER.iter_errors(params.get("arguments", {}))]
    if errors:
        return text_result(request["id"], "Invalid arguments: " + "; ".join(errors), is_error=True)
    order_id = params["arguments"]["order_id"]
    if order_id not in ORDERS:
        return text_result(request["id"], f"No order {order_id}. Check the id and try again.", is_error=True)
    return text_result(request["id"], f"{order_id}: {ORDERS[order_id]}")


for request in [
    {"jsonrpc": "2.0", "id": 1, "method": "tools/call",
     "params": {"name": "get_order", "arguments": {"order_id": "ORD-1042"}}},
    {"jsonrpc": "2.0", "id": 2, "method": "tools/call",
     "params": {"name": "get_order", "arguments": {"order_id": "order-42"}}},
    {"jsonrpc": "2.0", "id": 3, "method": "tools/call",
     "params": {"name": "cancel_order", "arguments": {}}},
]:
    print(json.dumps(handle_tools_call(request)))
```

The spec's reasoning: clients *should* pass tool execution errors to the model so it can self-correct, but a protocol error is about the request itself and usually goes to the host. A "no such order" lookup is also an execution error, because the model picked the id and can pick a better one.
:::

### Exercise 6: Two servers, one tool name

Your host connects to a repository server and an issue-tracker server, and *both* expose a tool called `search`. Build one combined tool list where each name is prefixed by **your** config key for that server (`repo.search`, `tracker.search`), plus a routing table that sends a prefixed call to the right server under its original name. An unprefixed `search` must be refused, not guessed.

```text
['repo.read_file', 'repo.search', 'tracker.get_issue', 'tracker.search']
tracker.search -> tracker server ran search({'query': 'login bug'})
search -> refused: unknown tool 'search'; use one of the prefixed names
```

:::hint
Keep a dict from the combined name to `(server_key, original_name)`. Use the key from your own configuration, not the name a server reports about itself: two servers can claim the same name.
:::

:::solution
```python run title="tool_namespaces.py"
servers = {
    "repo": {"search": "Search code", "read_file": "Read a file"},
    "tracker": {"search": "Search issues", "get_issue": "Get one issue"},
}

routes = {}
combined = []
for server_key, tools in servers.items():
    for original, description in tools.items():
        full_name = f"{server_key}.{original}"
        routes[full_name] = (server_key, original)
        combined.append({"name": full_name, "description": f"[{server_key}] {description}"})

print(sorted(tool["name"] for tool in combined))


def route(call):
    if call["name"] not in routes:
        return f"refused: unknown tool {call['name']!r}; use one of the prefixed names"
    server_key, original = routes[call["name"]]
    return f"{server_key} server ran {original}({call['arguments']})"


for call in [
    {"name": "tracker.search", "arguments": {"query": "login bug"}},
    {"name": "search", "arguments": {"query": "login bug"}},
]:
    print(call["name"], "->", route(call))
```

Dots are allowed in MCP tool names (the spec lists letters, digits, `_`, `-`, and `.`), but some model providers restrict tool names more tightly, so check yours; `repo__search` is a common fallback. Prefixing also helps the model: `[tracker] Search issues` tells it which system a result came from.
:::

### Challenge: A database tool without raw SQL

"Connecting an agent to a database" usually starts as `run_sql(query)`. Build the safer version: a `find_orders` tool over a SQLite file that takes structured filters (`status` from a fixed list, an optional `customer`, an optional `since` date, and a `limit` from 1 to 50) and returns matching rows. Defend it three ways and show each one working:

1. The schema rejects a customer like `x' OR '1'='1`.
2. Even if a bad value got past the schema, the query uses parameters, so it would match nothing.
3. The connection is opened read-only, so an attempted write fails at the database.

```mermaid caption="Three independent walls between the model and the database"
flowchart LR
    A["Tool call from model"] --> B{"Schema valid?"}
    B -->|no| E["Error result to model"]
    B -->|yes| C["Fixed SQL with ? placeholders"]
    C --> D[("SQLite opened mode=ro")]
    D --> F["Rows as JSON"]
```

:::hint
Build the `WHERE` clause from a fixed list of column names you control, and put every value in a parameter tuple: `conn.execute(sql, params)`. Open the file with `sqlite3.connect("file:orders.db?mode=ro", uri=True)`.
:::

:::solution
```python run title="find_orders.py"
import json
import sqlite3
from jsonschema import Draft202012Validator

# Setup: create the database with a normal, writable connection.
with sqlite3.connect("orders.db") as setup:
    setup.execute("DROP TABLE IF EXISTS orders")
    setup.execute("CREATE TABLE orders (id TEXT, customer TEXT, status TEXT, total REAL, created TEXT)")
    setup.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?)", [
        ("ORD-1001", "Ada Park", "shipped", 42.50, "2026-10-02"),
        ("ORD-1002", "Ben Ruiz", "pending", 19.99, "2026-10-20"),
        ("ORD-1003", "Ada Park", "pending", 7.25, "2026-11-01"),
    ])

FIND_ORDERS = Draft202012Validator({
    "type": "object",
    "properties": {
        "status": {"enum": ["pending", "shipped", "cancelled"]},
        "customer": {"type": "string", "pattern": "^[A-Za-z][A-Za-z .'-]{0,39}$"},
        "since": {"type": "string", "pattern": "^[0-9]{4}-[0-9]{2}-[0-9]{2}$"},
        "limit": {"type": "integer", "minimum": 1, "maximum": 50},
    },
    "required": ["status"],
    "additionalProperties": False,
})


def find_orders(status, customer=None, since=None, limit=20):
    sql = "SELECT id, customer, status, total, created FROM orders WHERE status = ?"
    params = [status]
    if customer is not None:
        sql += " AND customer = ?"
        params.append(customer)
    if since is not None:
        sql += " AND created >= ?"
        params.append(since)
    sql += " ORDER BY created LIMIT ?"
    params.append(limit)
    with sqlite3.connect("file:orders.db?mode=ro", uri=True) as conn:
        return conn.execute(sql, params).fetchall()


def call_tool(args):
    errors = [e.message for e in FIND_ORDERS.iter_errors(args)]
    if errors:
        return {"is_error": True, "content": "; ".join(errors)}
    return {"is_error": False, "content": json.dumps(find_orders(**args))}


print("1.", call_tool({"status": "pending", "customer": "Ada Park"}))
print("2.", call_tool({"status": "pending", "customer": "x' OR '1'='1"}))
print("3. bypassing the schema:", find_orders("pending", customer="x' OR '1'='1"))

conn = sqlite3.connect("file:orders.db?mode=ro", uri=True)
try:
    conn.execute("DELETE FROM orders")
except sqlite3.OperationalError as exc:
    print("4. write on the read-only connection:", exc)
finally:
    conn.close()
```

Line 3 is the important one. With parameters, `x' OR '1'='1` is just an odd customer name that matches no rows, because the value never becomes part of the SQL text. Line 4 shows the last wall: even a bug in your own query code can't modify data through a connection the database itself treats as read-only. For a production database you'd add the fourth wall too: a database user that only has `SELECT` on the tables this tool needs.
:::
