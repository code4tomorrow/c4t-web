The agent's summary is short and sure of itself: *"Fixed `to_dollars` so amounts always show two decimal places. All tests pass."* Then you run `git diff --stat`:

```text
 .github/workflows/ci.yml | 2 +-
 money.py                 | 2 +-
 tests/test_money.py      | 2 +-
 3 files changed, 3 insertions(+), 3 deletions(-)
```

A formatting fix touched the CI configuration? You scroll up in the agent's terminal and find the last line of its own test run: `FAILED (failures=1)`. The summary, the diff, and the evidence tell three different stories, and only two of them are facts. This lesson is about reading those two.

## Reading a unified diff

A diff is a list of instructions for turning the old file into the new one. Python's `difflib` writes the same unified format as `git diff`, so you can make one from two strings:

```python run title="make_diff.py"
import difflib

before = '''def to_dollars(cents):
    """Format whole cents as dollars, like $10.05."""
    return "$" + str(cents / 100)


def to_cents(dollars):
    return int(dollars * 100)
'''
after = before.replace('return "$" + str(cents / 100)', 'return f"${cents / 100:.2f}"')

diff = difflib.unified_diff(before.splitlines(), after.splitlines(),
                            fromfile="a/money.py", tofile="b/money.py", lineterm="")
print("\n".join(diff))
```

Read it top to bottom:

- `--- a/money.py` and `+++ b/money.py` name the old and new versions of the file.
- `@@ -1,6 +1,6 @@` is a **hunk header**: this chunk covers 6 lines starting at line 1 in the old file, and 6 lines starting at line 1 in the new one. When the two counts differ, the change added or removed lines.
- Lines starting with a space are **context**, unchanged and shown so you can see where you are.
- `-` lines were removed and `+` lines were added. A changed line shows up as one of each.

`git diff` adds a `diff --git` line and an `index` line per file, and often the enclosing function name after the second `@@`. Otherwise it's the same format.

## Check the shape before the lines

Before reading a single `+`, look at `git diff --stat` and ask:

1.  **Are these the files I expected?** Compare with the task's scope.
2.  **Did tests change?** Fine if tests were *added*. A reason to slow down if existing ones were *edited*.
3.  **Did configuration, CI, or dependency files change?** Those affect everyone, not just this feature.
4.  **Is the size proportional?** A one-line bug with a 400-line diff needs an explanation.

The hook's diff fails questions 2 and 3. Here's what it actually says:

```diff
diff --git a/money.py b/money.py
@@ -1,3 +1,3 @@
 def to_dollars(cents):
     """Format whole cents as dollars, like $10.05."""
-    return "$" + str(cents / 100)
+    return "$" + str(round(cents / 100, 2))
diff --git a/tests/test_money.py b/tests/test_money.py
@@ -6,4 +6,4 @@ class ToDollarsTests(unittest.TestCase):
     def test_whole_dollars(self):
-        self.assertEqual(to_dollars(1000), "$10.00")
+        self.assertEqual(to_dollars(1000), "$10.0")
 
     def test_cents(self):
diff --git a/.github/workflows/ci.yml b/.github/workflows/ci.yml
@@ -12,2 +12,2 @@ jobs:
       - name: Run tests
-        run: python -m unittest -v
+        run: python -m unittest -v || true
```

Three problems, one per file. `round(10.0, 2)` is still `10.0`, so the "fix" changes nothing for whole dollars or for `1050` (still `$10.5`). The test's expected value was edited to match the broken output. And `|| true` makes the CI step succeed even when the tests fail, so the build would show green forever.

## Changes that deserve a second look

These patterns are worth a pause in any diff, and they come up often in agent-written code because they're quick ways to make a failing check stop failing:

- **Edited expectations.** An `assertEqual` whose expected value changed in the same diff as the code it tests.
- **Removed or skipped tests.** Deleted test methods, `@unittest.skip`, `pytest.mark.skip`, or a test body replaced by `pass`.
- **Swallowed failures.** `except Exception: pass`, a bare `except:`, `|| true` in a script, or `continue-on-error` in CI.
- **Special cases that match the test inputs.** `if cents == 1050: return "$10.50"` passes the test and fixes nothing.
- **New dependencies** for something the standard library already does.
- **Comments that promise more than the code does**, like `# handles all currencies` above a line that hard-codes `$`.

## Plausible but wrong

The hardest bugs to catch in review are fixes that look right and pass the tests they were given. A bug report says `is_leap(1900)` wrongly returns `True`. The agent adds `and year % 100 != 0`. The existing tests (2024, 2023, 1900) all pass. Before stepping through, predict what it says about 2000.

:::trace A fix that passes every test it was given
```python
def is_leap(year):
    # Agent's fix for "1900 is not a leap year"
    return year % 4 == 0 and year % 100 != 0


for year in [2024, 1900, 2000]:
    print(year, is_leap(year))
```
:::

2000 *was* a leap year: years divisible by 400 are the exception to the exception. The fix handled the case in the bug report and broke one nobody tested. The defense is to write a test for the **neighbors** of every bug (here, 2000 and 2100) before accepting the fix. You'll do exactly that in the next lesson.

## Evidence you can trust

"All tests pass" is a sentence. Evidence is something you could reproduce:

| Claim | Evidence |
| --- | --- |
| "Tests pass" | The exact command, its full output, and the exit code |
| "I ran them after the fix" | The run comes after the last edit, ideally tied to a commit hash |
| "Nothing else changed" | `git diff --stat` matches the files in the task |
| "I added tests" | The new test names appear in the diff *and* in the `-v` output |

Know what the end of a `unittest` run can say, because two of the endings look like success and aren't:

```text
OK                     <- every test ran and passed
FAILED (failures=1)    <- at least one assertion failed; exit code 1
OK (skipped=1)         <- passed, but a test was skipped; find out why
NO TESTS RAN           <- zero tests found (exit code 5); usually a wrong folder or file name
```

Check the exit code yourself right after a run: `echo $?` in bash and zsh, `$LASTEXITCODE` in PowerShell. Zero means success. Best of all, don't rely on anyone's report: run the command yourself, on the final code.

## Linters and type checkers catch what tests don't

Tests only check the paths they run. This file has a typo in a branch no test exercises and a type mistake in a function nobody has called yet:

```python title="receipts.py"
import os


def to_dollars(cents: int) -> str:
    return f"${cents / 100:.2f}"


def receipt_line(item: str, cents: int, gift: bool = False) -> str:
    if gift:
        return f"{item}: {to_dollar(cents)} (gift)"
    return f"{item}: {to_dollars(cents)}"


def line_from_csv(row: dict[str, str]) -> str:
    return receipt_line(row["item"], row["cents"])
```

A test calling `receipt_line("Tea", 250)` passes. Two optional tools, installed into your course environment with `python -m pip install ruff mypy`, find the rest without running anything. Ruff is a fast linter:

```bash
ruff check --output-format concise receipts.py
```

```text
receipts.py:1:8: F401 [*] `os` imported but unused
receipts.py:10:27: F821 Undefined name `to_dollar`
Found 2 errors.
[*] 1 fixable with the `--fix` option.
```

mypy reads the type hints and checks that calls match them:

```bash
mypy receipts.py
```

```text
receipts.py:10: error: Name "to_dollar" is not defined; did you mean "to_dollars"?  [name-defined]
receipts.py:15: error: Argument 2 to "receipt_line" has incompatible type "str"; expected "int"  [arg-type]
Found 2 errors in 1 file (checked 1 source file)
```

Line 15 is a real bug: values read from a CSV are strings, and `"250" / 100` raises `TypeError` the first time anyone uses it. Both tools exit with code 1 when they find problems, so they make good acceptance criteria: "`ruff check .` and `mypy .` report no errors."

:::warning
**Reviewing the summary instead of the diff.** The summary is the agent's description of its intent, written by the same process that made the change. Read `git diff --stat` first and the summary last, if at all.
:::

:::warning
**Trusting a green CI badge.** Green means the configured commands exited with 0. If the diff changed those commands (`|| true`, a skip flag, a narrower test path), green tells you nothing. Always read CI changes with extra care.
:::

:::quiz
Q: A hunk header reads `@@ -10,4 +10,6 @@`. What does it tell you?
- [ ] Lines 4 and 6 changed
  The numbers after the commas are line counts, not line numbers.
- [x] Four old lines starting at line 10 became six new lines; the change added two lines overall
  `-start,count` describes the old file and `+start,count` the new one.
- [ ] The file grew from 10 to 16 lines
  The header describes this chunk only, not the whole file.

Q: The diff for a bug fix changes `money.py` and also changes an expected value in `tests/test_money.py`. What should you do?
- [ ] Approve it; updating tests is normal
  Adding tests is normal. Changing what an existing test expects, in the same change as the code, is how broken code gets a passing test.
- [x] Ask why the old expectation was wrong, and check the new value against the original requirement
  Sometimes the old test really was wrong, but that needs a reason you can verify, not the agent's word.
- [ ] Revert the test change and merge the rest
  You'd merge code whose test you haven't seen pass. Understand the change first.

Q: An agent reports its test run ended with `OK (skipped=2)`. What does that tell you?
- [ ] Two tests failed but were tolerated
  Skipped tests didn't run at all, so they neither passed nor failed.
- [x] The suite passed, but two tests didn't run; find out what skipped them and whether the diff added the skips
  A skip added in the same diff as a fix is the same red flag as an edited expectation.
- [ ] The run is invalid and must be repeated
  It's a valid run; it's just incomplete evidence.

Q: Why did the `is_leap` fix pass review-by-tests?
- [x] The tests only covered the years in the bug report and two easy cases
  2000 is the neighboring case that the new condition breaks, and nobody tested it.
- [ ] `%` behaves differently on large years
  `%` works the same for every integer here; the logic is what's wrong.
- [ ] Trace programs can't run real tests
  The trace ran the real function; the problem is which inputs were checked.
:::

:::takeaways
- In `@@ -a,b +c,d @@`, `a` and `c` are starting lines, `b` and `d` are line counts for the old and new versions.
- Check the shape first: expected files, edited tests, changed config or dependencies, proportional size.
- Edited expectations, skips, swallowed failures, and special cases are the usual ways a failing check gets silenced.
- Evidence is a reproducible command, its full output, and its exit code, run after the last edit, preferably by you.
- Linters and type checkers find errors on paths your tests never run.
:::
