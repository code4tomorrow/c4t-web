Type "improve the app" into an agent that can edit files and run commands, then go get a snack. When you come back there are 31 changed files, a new dependency, a renamed database column, and a cheerful summary. Was any of it wrong? You can't say, because the request never defined what "improved" means, which files were fair game, or when to stop.

An agent will always do *something* with a vague request. The fix isn't a smarter model. It's a better task.

## Three tools that act at three different scales

All three are the same kind of model underneath. What differs is how much of your project they can see and how much they can change before you look.

| | Autocomplete | Chat | Agent |
| --- | --- | --- | --- |
| What it sees | Code around your cursor | What you paste or attach | Whatever its tools can reach |
| What it changes | Nothing until you press Tab | Nothing until you apply a suggestion | Files and commands, by itself, in a loop |
| Size of one step | A line or a block | An answer or a snippet | A multi-file change |
| How you review | Read it before accepting | Read it before applying | Read the diff and rerun the checks |

Use autocomplete when you know what you're writing and want it typed faster, chat for questions and small snippets you'll read before pasting, and an agent when the work needs dependent steps: read these files, change them, run the tests, fix what broke.

Each step up the table saves more typing and removes one more moment where you'd naturally notice a mistake. That trade is the subject of this whole course.

## What actually makes something an agent

Here's the intuition. A language model only produces text. It can't open a file. What it *can* do is write a structured request ("call `read_file` with `path='textstats.py'`"). A program wrapped around the model, called the **harness**, reads that request, runs the real function, and sends the result back as the next message. The model reads the result and decides what to request next.

Now precisely: an **agent** is a loop in which a model chooses actions, a harness executes them as tool calls, and each result is appended to the conversation before the model is called again. The loop ends when the model replies with no tool call, or when the harness stops it.

```mermaid caption="One turn of the agent loop. The model asks; only the harness acts."
sequenceDiagram
    participant U as You
    participant H as Harness
    participant M as Model
    participant T as Tools
    U->>H: task
    H->>M: conversation so far
    M-->>H: tool call: read_file("textstats.py")
    H->>T: run read_file
    T-->>H: file contents
    H->>M: conversation + result
    M-->>H: final answer (no tool call)
    H-->>U: answer
```

You can see the mechanics without any real model. This `ScriptedModel` returns pre-written replies in order, the way a test double stands in for a real service. Everything else is exactly what a harness does.

```python run title="agent_loop.py"
REPO = {
    "README.md": "Text helpers. Run tests with: python -m unittest -v\n",
    "textstats.py": "def word_count(text):\n    return len(text.split())\n",
    "test_textstats.py": "import unittest\nfrom textstats import word_count\n...\n",
}


def list_files():
    return "\n".join(sorted(REPO))


def read_file(path):
    if path not in REPO:
        return f"error: no file named {path}"
    return REPO[path]


TOOLS = {"list_files": list_files, "read_file": read_file}


class ScriptedModel:
    """Stands in for a real model by returning pre-written replies in order."""

    def __init__(self, replies):
        self.replies = list(replies)
        self.calls = 0

    def respond(self, messages):
        self.calls += 1
        return self.replies.pop(0)


model = ScriptedModel([
    {"tool": "list_files", "args": {}},
    {"tool": "read_file", "args": {"path": "textstats.py"}},
    {"text": "textstats.py defines one function, word_count(text)."},
])

messages = [{"role": "user", "content": "What functions does textstats.py define?"}]
MAX_STEPS = 5
for step in range(1, MAX_STEPS + 1):
    reply = model.respond(messages)
    if "tool" not in reply:
        print(f"step {step}: model answers -> {reply['text']}")
        break
    result = TOOLS[reply["tool"]](**reply["args"])
    print(f"step {step}: model requests {reply['tool']}({reply['args']})")
    print(f"        harness runs it, returns {result!r:.50}")
    messages.append({"role": "assistant", "tool_call": reply})
    messages.append({"role": "tool", "content": result})
else:
    print("stopped: hit the step limit")

print(f"model called {model.calls} times; conversation has {len(messages)} messages")
```

Three things to notice. One question cost three model calls, because every tool result goes back to the model; that's why agents are slower and pricier than chat. The line `TOOLS[reply["tool"]](**reply["args"])` is the only place anything happens, and it belongs to the harness, so the harness is where limits and permissions belong. And `for ... else` gives the loop a ceiling: if the model never stops asking, `MAX_STEPS` stops it.

A real harness differs in one place: `respond` sends `messages` to a model and parses the tool call out of its reply. Module 5 covers how real tool calls are described and validated.

## Watching the loop handle a missing file

Step through this smaller loop. Watch `context` grow and look at what happens on the second tool call, which asks for a file that doesn't exist.

:::trace Errors come back as results, not crashes
```python
replies = [
    {"tool": "read_file", "path": "app.py"},
    {"tool": "read_file", "path": "notes.txt"},
    {"text": "app.py prints a greeting."},
]
files = {"app.py": "print('hello')"}
context = []
step = 0
answer = None
while step < 5:
    reply = replies[step]
    step += 1
    if "text" in reply:
        answer = reply["text"]
        break
    result = files.get(reply["path"], "error: not found")
    context.append(result)
print(answer)
print(context)
```
:::

The missing file doesn't crash anything. The harness returns `"error: not found"` as an ordinary result, and a real model would read it and adjust, perhaps by listing files first. Returning errors as results is what lets an agent recover from its own wrong guesses.

## The loop stops, but "done" isn't proof

An agent loop ends in one of four ways: the model sends a reply without a tool call, the harness hits a step or cost limit, a tool fails in a way the harness treats as fatal, or a human presses stop. Only the first looks like success, and it's just the model's claim. A model can answer "Done, all tests pass" without ever having run them.

So a good task says, in advance, what evidence will count as done. You'll check that evidence yourself (Module 4), and in the next lesson you'll build a harness that checks it automatically.

## What to delegate, and what not to

A task is a good fit for an agent when it is **bounded** (you can name the files), **checkable** (a command can show it worked), and **reversible** (a branch and `git restore` undo it).

| Task | Delegate to an agent? | Why |
| --- | --- | --- |
| Add tests for `top_words` covering ties and punctuation | Yes | Small scope, and the tests themselves are the evidence |
| Rename `char_count` to `count_chars` everywhere in the repo | Yes | Mechanical; search and the test suite confirm it |
| Fix the failing test in `test_textstats.py` (error output attached) | Yes | The cause is visible and the test defines done |
| Improve the app | No | No boundary, no acceptance test, no stopping point |
| Rotate the production database password | No | Needs secrets and can't be undone with Git |
| Decide whether we should switch web frameworks | Not as an edit task | A judgment call; ask for a written comparison, then decide yourself |
| Change one string literal | No (just do it) | Faster to type than to describe and review |

## Anatomy of a task spec

Here's the punctuation gap from the previous module's `longest_word`, written as a task an agent can't misread:

```text
Goal: make longest_word(text) ignore punctuation at the ends of words.

Context: textstats.py and test_textstats.py. top_words() already strips
punctuation with word.strip(".,!?;:\"'()"). Reuse that same set.

In scope: longest_word in textstats.py; test_textstats.py.
Out of scope: every other function, new files, new dependencies.

Acceptance criteria:
1. longest_word("Hello, world!") returns "Hello"
2. longest_word("...") returns ""
3. Ties still return the first longest word.
4. python -m unittest -v passes, with no existing test removed or skipped.

Stop and ask if: you think a file outside the scope needs changing, or a
test fails for a reason you can't explain.

Report: files changed, the full test output, and any assumption you made.
```

Every section answers a question the agent would otherwise guess at. **Context** saves it from rediscovering what you already know. **Scope** and **out of scope** give it a boundary. **Acceptance criteria** are things a command can check, so "done" has a meaning. **Stop and ask** turns the risky moments into a pause instead of a guess. **Report** tells it what evidence to bring back.

Look at criterion 1 closely. `"Hello"` and `"world"` are both five letters once the punctuation is gone, so this one example checks the stripping *and* the tie rule.

:::warning
**Criteria a command can't check.** "The code should be clean and efficient" gives the agent nothing to aim at and you nothing to verify. Replace it with something testable: "runs `top_words` on a 10,000-word text in under 0.1 s," or "no function longer than 30 lines."
:::

:::warning
**Handing over the whole repo when two files matter.** An agent with no scope reads widely and edits widely. Name the files. If you don't know which files are involved, that's a separate, read-only task: ask it to find them first.
:::

:::quiz
Q: In `agent_loop.py`, why did one question lead to three calls to the model?
- [ ] The harness retried after an error
  No error occurred; both tool calls succeeded.
- [x] Each tool result goes back to the model, which then decides the next step
  Two tool calls plus the final answer means three model calls. More tools, more calls.
- [ ] `MAX_STEPS` forces at least three steps
  `MAX_STEPS` is a ceiling, not a minimum; the loop broke out at step 3 on its own.

Q: Where is the right place to enforce "the agent may not delete files"?
- [ ] In the prompt, by asking the model nicely
  A prompt is a request. The model can misread it, ignore it, or be talked out of it.
- [x] In the harness, at the line that executes tool calls
  The model can only ask. If the harness never runs a delete, no reply can cause one.
- [ ] In the model's training
  You don't control training, and no training guarantees behavior on every input.

Q: Which acceptance criterion could a reviewer actually check?
- [ ] The function handles edge cases properly
  Which edge cases? "Properly" by whose standard? Nothing here can pass or fail.
- [ ] The change is high quality
  This is an opinion, not a check.
- [x] `longest_word("...")` returns `""`
  One input, one exact expected output. A test can confirm or refute it in milliseconds.
:::

:::takeaways
- Autocomplete, chat, and agents differ in how much they can see and change before you review.
- An agent is a loop: the model requests a tool, the harness runs it, the result goes back to the model.
- Only the harness acts, so limits and permissions belong in the harness, not the prompt.
- A loop ending with "done" is a claim; the task should say what evidence proves it.
- A good task spec states the goal, context, scope, checkable acceptance criteria, when to stop and ask, and what to report.
:::
