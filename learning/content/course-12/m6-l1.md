The first enemy most people write is one line: every frame, move toward the player. Play it and three things go wrong. It glues itself to the wall between you and it. It's either unbeatable or trivially dodged, with nothing in between. And it gives no warning, so getting hit feels random.

The level around it often has the same problem. Spikes appear in the first room, a moving platform over spikes in the second, and nothing ever showed the player what spikes do when failure was cheap. Both problems have the same fix: decide what the player should notice, and when.

## An enemy is a few states and the rules for switching

Watch a guard in a stealth game. It walks a route. When it spots you it runs at you. When you break line of sight it goes to where it last saw you, looks around, and gives up. Each of those is a **state**: one behavior plus the rules that end it.

```mermaid caption="The sentry drone built in this module. Each arrow is checked every physics step while the drone is in the state it leaves."
stateDiagram-v2
    [*] --> Patrol
    Patrol --> Chase: sees player within 5
    Chase --> Search: loses sight, or farther than 7
    Search --> Chase: sees player again
    Search --> Patrol: 2 seconds pass
```

In C#, an `enum` names the states and a `switch` runs the current one:

```csharp
enum State { Patrol, Chase, Search }

State state = State.Patrol;

void FixedUpdate()
{
    switch (state)
    {
        case State.Patrol: UpdatePatrol(); break;
        case State.Chase:  UpdateChase();  break;
        case State.Search: UpdateSearch(); break;
    }
}
```

Why not two Bools, `isChasing` and `isSearching`? Because nothing stops both from being true, and then which behavior runs depends on which `if` you happened to write first. An `enum` can hold exactly one value, so impossible combinations can't happen. The code runs in `FixedUpdate` because the enemy moves a Rigidbody2D, and physics moves happen on the physics clock.

## Patrol: follow a route of waypoints

A route is an array of empty GameObjects placed in the scene. The enemy moves toward the current one, and on arrival advances to the next:

```csharp
[SerializeField] Transform[] waypoints;
[SerializeField] float patrolSpeed = 2f;

int index;
Rigidbody2D rb;

void UpdatePatrol()
{
    Vector2 target = waypoints[index].position;
    MoveTowards(target, patrolSpeed);

    if (Vector2.Distance(rb.position, target) < 0.05f)
        index = (index + 1) % waypoints.Length;
}

void MoveTowards(Vector2 target, float speed)
{
    Vector2 next = Vector2.MoveTowards(rb.position, target, speed * Time.fixedDeltaTime);
    rb.MovePosition(next);
}
```

`Vector2.MoveTowards` steps at most `speed * Time.fixedDeltaTime` toward the target and never overshoots, so the arrival check is guaranteed to pass eventually. `% waypoints.Length` wraps the index: with four waypoints it goes 0, 1, 2, 3, 0, 1. For a flying enemy, give the Rigidbody2D a **Body Type** of **Kinematic**. A kinematic body goes exactly where `MovePosition` puts it, ignores gravity, and still triggers collision events with the dynamic player.

You can see the radii while you tune them by drawing gizmos, which appear in the Scene view only:

```csharp
void OnDrawGizmosSelected()
{
    Gizmos.color = Color.yellow;
    Gizmos.DrawWireSphere(transform.position, detectRadius);
    Gizmos.color = Color.red;
    Gizmos.DrawWireSphere(transform.position, loseRadius);
}
```

## Sensing: distance, line of sight, and a gap between "see" and "lose"

Sensing has two checks, cheapest first. Is the player close enough? Then, is there a wall in between? `Physics2D.Linecast` answers the second by testing the straight segment between two points against colliders on the layers you choose:

```csharp
[SerializeField] Transform player;
[SerializeField] float detectRadius = 5f;
[SerializeField] float loseRadius = 7f;
[SerializeField] LayerMask sightBlockers;   // just the Ground layer

bool CanSeePlayer(float radius)
{
    Vector2 toPlayer = (Vector2)player.position - rb.position;
    if (toPlayer.magnitude > radius) return false;
    return !Physics2D.Linecast(rb.position, player.position, sightBlockers);
}
```

A `RaycastHit2D` converts to `true` when it hit something, so `!Physics2D.Linecast(...)` reads as "nothing blocked the line."

Notice there are two radii. Patrol switches to Chase at 5, but Chase only gives up beyond 7. With a single radius, a player standing right at the edge makes the enemy flip between states every physics step, and it visibly jitters. The gap between the two thresholds is called **hysteresis**, and thermostats use it for the same reason. Step through the drone's decision with the player hovering around the edge:

:::trace Patrol and Chase with a detect radius of 5 and a lose radius of 7
```python
distances = [6.0, 5.2, 4.9, 5.1, 4.8, 5.3, 6.5, 7.4]
state = "Patrol"
for d in distances:
    if state == "Patrol" and d < 5:
        state = "Chase"
    elif state == "Chase" and d > 7:
        state = "Patrol"
    print(d, state)
```
:::

Once the drone starts chasing at 4.9, wobbling between 4.8 and 5.3 doesn't matter; only moving past 7 ends the chase. Here's how many times the state flips with a single radius instead:

```python run title="flips.py"
distances = [6.0, 5.2, 4.9, 5.1, 4.8, 5.3, 6.5, 7.4]

def count_flips(detect, lose):
    state, flips = "Patrol", 0
    for d in distances:
        new = state
        if state == "Patrol" and d < detect:
            new = "Chase"
        elif state == "Chase" and d > lose:
            new = "Patrol"
        flips += new != state
        state = new
    return flips

print("one radius (5 and 5):", count_flips(5, 5), "flips")
print("hysteresis (5 and 7):", count_flips(5, 7), "flips")
```

Four flips in eight frames with one radius, against two (start chasing, then give up) with hysteresis. At 50 physics steps a second, the single-radius drone shakes in place.

## Spawners: prefabs stamped out on a timer, with a cap

A spawner makes copies of a prefab while the game runs. `Instantiate(prefab, position, rotation)` returns the new copy. If the prefab field is typed as a component, such as `EnemyAI`, you get that component back directly:

```csharp
[SerializeField] EnemyAI enemyPrefab;
[SerializeField] Transform spawnPoint;
[SerializeField] Transform player;
[SerializeField] Transform[] route;

void SpawnOne()
{
    EnemyAI enemy = Instantiate(enemyPrefab, spawnPoint.position, Quaternion.identity);
    enemy.Setup(player, route);
}
```

That `Setup` call solves a problem you'll hit the first time you make an enemy prefab: its **Player** slot can't be filled. A prefab is an asset on disk, and assets can't point at objects inside one particular scene. The spawner lives in the scene, so it knows the player and hands the reference over at spawn time.

Every spawner also needs a cap (for example, "at most 3 alive"). Without one, a player who hides in a corner gets buried under an endless stream of enemies, and the frame rate goes with it.

## Difficulty is a handful of numbers

"Make it harder" is too vague to act on. Difficulty in an action game comes down to a few knobs: enemy speed, detect radius, how long the enemy warns before it acts, damage per hit, spawn interval, and the cap. Change one knob at a time, then playtest.

To ramp a knob over time, Unity's `AnimationCurve` gives you an editable graph in the Inspector:

```csharp
[SerializeField] AnimationCurve secondsBetweenSpawns = AnimationCurve.Linear(0f, 6f, 120f, 2f);

float Interval(float elapsed) => secondsBetweenSpawns.Evaluate(elapsed);
```

This curve starts at 6 seconds between spawns and slides to 2 seconds by the two-minute mark. Click the curve in the Inspector to bend it: an easy first minute and a steep second one is a single drag.

## Levels that teach, test, and then twist

Unity builds 2D levels with **Tilemaps**. A **Grid** object holds one or more **Tilemap** layers, and you paint tiles onto them from the **Tile Palette** (**Window > 2D > Tile Palette**). Keep separate tilemaps for separate jobs: a Background with no collider, a Ground layer with a collider, and a Hazards layer whose collider is a trigger. The build-along sets all of this up.

The tools are the easy part. The hard part is deciding what goes where, and a widely used structure is to give each mechanic four beats:

```mermaid caption="One mechanic, four beats. Each beat is a short section of the level."
flowchart LR
    T["Teach: meet it where failure is cheap"] --> D["Test: use it under mild pressure"]
    D --> W["Twist: combine it with something else"]
    W --> C["Conclude: one confident run, then the exit"]
```

For a patrolling drone, that might look like this. **Teach**: the player first sees the drone from a ledge, outside its detect radius, crossing an empty room. **Test**: its route crosses the only path, with a pillar to hide behind while it passes. **Twist**: two drones and a spike floor, so stopping to hide is no longer free. **Conclude**: a short stretch the player now handles easily, then the exit.

A few more principles to keep in mind:

- **One new idea per section.** If a player dies to a spike-and-drone combination before seeing either alone, they learn nothing from it.
- **Show before it matters.** Frame threats so the camera reveals them before they can reach the player; your Cinemachine setup from Module 4 helps here.
- **Use coins as signposts.** A trail of coins says "go this way" without a word of text.
- **Pace tension with rest.** Put a quiet stretch and a checkpoint before each twist, so a failure there doesn't repeat the easy parts.
- **Fit the space to the AI.** A simple drone flies in straight lines. Give it an open room, and players read that room as "the drone's territory," which costs far less than writing pathfinding.

:::warning
**Waypoints parented to the enemy.** If the waypoint objects are children of the drone, they move with it, so the drone chases a target that keeps moving away and drifts off forever. Put the waypoints under a separate `Route` object in the scene.
:::

:::warning
**A line of sight that's always blocked.** If `sightBlockers` includes the enemy's own layer (or Everything), the linecast starts inside the enemy's collider and hits it, so the enemy never sees anyone. Set the mask to just the layers that block sight, usually Ground.
:::

:::quiz
Q: A drone uses one radius of 5 for both "start chasing" and "stop chasing." The player stands about 5 units away. What does the drone do?
- [ ] Chases smoothly
  It would if the start and stop thresholds were different.
- [x] Jitters as it flips between Patrol and Chase every few physics steps
  Small changes in distance cross the single threshold back and forth.
- [ ] Ignores the player completely
  It does notice the player, many times a second, and then forgets again.

Q: Your drone prefab has a **Player** field, but you can't drag the scene's Player into it while editing the prefab. Why?
- [ ] The field must be `public`, not `[SerializeField]`
  Both show in the Inspector. Visibility isn't the problem.
- [x] A prefab is an asset, and assets can't reference objects in a particular scene
  The spawner, which lives in the scene, passes the reference in with `Setup` after `Instantiate`.
- [ ] Transforms can't be serialized
  Transform fields serialize fine; that's how waypoints work.

Q: With four waypoints, `index = (index + 1) % waypoints.Length;` runs six times starting from 0. Which indexes does the drone visit?
- [ ] 1, 2, 3, 4, 5, 6
  Index 4 doesn't exist in a four-item array; `%` wraps it back to 0.
- [x] 1, 2, 3, 0, 1, 2
  The remainder after dividing by 4 cycles through 0 to 3.
- [ ] 1, 2, 3, 3, 3, 3
  That would be clamping, not wrapping.

Q: Where should the player first meet the drone?
- [ ] In a narrow corridor, so the encounter feels tense
  A tense first meeting means the player learns the rules by dying.
- [x] Where they can watch it patrol from outside its detect radius
  They learn its route and range while failure is impossible, then get tested on it next.
- [ ] Next to a spike pit, so the level feels dangerous right away
  Two unknown threats at once teach neither one.
:::

:::takeaways
- An enemy is an `enum` of states, a `switch` that runs the current one, and an exit rule for each.
- `Vector2.MoveTowards` plus `MovePosition` on a kinematic body gives exact, overshoot-free patrols.
- Sense with a cheap distance check first, then a `Linecast` against the walls; use separate detect and lose radii.
- Spawners need a cap, and they pass scene references to each prefab copy they create.
- Give each mechanic a teach, test, twist, and conclude beat, and shape the space to fit what your AI can do.
:::
