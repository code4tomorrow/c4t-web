Your friend plays to the third checkpoint on Friday. On Monday they open the game again and it starts at the beginning, score 0. Nothing crashed, nothing was "wrong," and they still won't play a fourth time. A game that forgets is a game that feels unfinished.

The same weekend, you send them a build. In the Editor the Restart button works; in the build it does nothing, because the scene was never added to the build's scene list. The Editor quietly forgives things a build won't, and this module is about closing both gaps.

## Decide what to save before deciding how

Not everything needs saving, and the right storage depends on what the data is:

| Data | Example | Store it in |
| --- | --- | --- |
| Settings | Volume, "reduce flashing" | `PlayerPrefs` |
| A single record | Best score, best time | `PlayerPrefs` |
| Progress | Level, checkpoint, score, health, coins collected | A JSON save file |
| Things you can rebuild | Where each drone was mid-patrol | Nothing; reset them on load |

That last row is a design decision as much as a technical one. Saving at checkpoints and restoring "you're at checkpoint 2 with 340 points" is far simpler than freezing every object, and players expect it.

## PlayerPrefs: a tiny key-value store

`PlayerPrefs` stores ints, floats, and strings under string keys, and it survives quitting the game:

```csharp
int best = PlayerPrefs.GetInt("bestScore", 0);   // 0 if the key doesn't exist yet
if (score > best)
{
    PlayerPrefs.SetInt("bestScore", score);
    PlayerPrefs.Save();
}
```

The second argument of `GetInt` is the default for a key that doesn't exist, so the first run needs no special case. `PlayerPrefs.Save()` writes to disk now instead of waiting for the game to quit, which matters if the game crashes or the browser tab closes.

Where the data goes depends on the platform: the registry on Windows, a `.plist` file on macOS, and the browser's IndexedDB storage (up to 1 MB) in a Web build. It isn't encrypted, so a curious player can edit it. Keep it to small values you wouldn't mind someone changing.

## JSON save files with JsonUtility

For progress, write a plain C# class with the fields you need and mark it `[Serializable]`:

```csharp
using System;

[Serializable]
public class SaveData
{
    public int version = 1;
    public string sceneName = "Level1";
    public string checkpointId = "";
    public int score;
    public int health = 5;
}
```

`JsonUtility.ToJson` turns an instance into text, and `File.WriteAllText` writes that text to a file in a folder Unity guarantees is writable:

```csharp
using System.IO;
using UnityEngine;

public static class SaveFile
{
    static string FilePath => Path.Combine(Application.persistentDataPath, "save.json");

    public static void Write(SaveData data)
    {
        File.WriteAllText(FilePath, JsonUtility.ToJson(data, true));
    }

    public static SaveData Read()
    {
        if (!File.Exists(FilePath)) return null;
        return JsonUtility.FromJson<SaveData>(File.ReadAllText(FilePath));
    }
}
```

With `prettyPrint` set to `true`, the file is readable, which helps a lot when debugging:

```text
{
    "version": 1,
    "sceneName": "Level1",
    "checkpointId": "cp2",
    "score": 340,
    "health": 3
}
```

`JsonUtility` is fast and built in, but strict about what it will serialize:

- The class needs `[Serializable]`, and so does any class you nest inside it.
- Only fields are saved: public ones, or private ones marked `[SerializeField]`. Properties such as `public int Score { get; set; }` are skipped.
- `List<T>` and arrays of serializable types work as fields. `Dictionary` doesn't, and the top-level value must be an object, not a bare array.

One behavior works in your favor. When `FromJson` reads a file that's missing a field, that field keeps the value from its initializer. Add `public float bestTime = 0f;` next month, and old save files still load, with `bestTime` at 0. The `version` field lets you detect old files when you need to convert them.

`Application.persistentDataPath` is a different folder on each platform. On Windows it's usually `%userprofile%\AppData\LocalLow\<company>\<product>`, and on macOS it's `~/Library/Application Support/<company>/<product>`. Print it once with `Debug.Log(Application.persistentDataPath)` so you can find and delete the file while testing.

## A build is not Play mode

The Editor is generous. A build is literal. Before you send a build to anyone, check the differences that bite most often:

- **Only listed scenes exist.** A scene that isn't in the build's **Scene List** can't be loaded, and `SceneManager.LoadScene` logs an error instead.
- **There's no Console window.** In a desktop build, `Debug.Log` output and errors go to a log file; in a Web build, they go to the browser's developer console (open it with **F12**, or **Cmd+Option+I** on a Mac). Test with a **Development Build**, which adds debug information and can connect to the Profiler, before your final build.
- **The frame rate changes.** A build may run at 60, 144, or 30 frames per second. Anything that moves without `Time.deltaTime` (or outside `FixedUpdate`) changes speed.
- **The screen changes.** A browser window or a laptop screen is a different size and shape from your Game view, which is what the Canvas Scaler settings from Module 5 are for.
- **Startup order can change.** If one script reads another's data in `Awake`, it may work in the Editor by luck. Set up your own state in `Awake`, and read other objects in `Start`.
- **Web builds have browser rules.** The page must be served by a web server, so double-clicking `index.html` doesn't work. Browsers keep audio silent until the player clicks or presses a key, and the keyboard only reaches the game after the player clicks on it.

## Playtesting: watch, don't explain

You can't see your own game fresh. Someone who has never played it can, but only if you stay quiet. A playtest that produces useful evidence goes like this:

1. Give one sentence of setup ("It's a platformer; arrow keys and space"), then stop talking.
2. Ask them to think out loud: what they're trying to do and what they expect.
3. Write down every hesitation, death, and "wait, what?" along with the section it happened in. Count deaths per section.
4. Don't help. If they're stuck for two minutes, note it, then help and carry on.
5. Afterward, ask three questions: "What was hardest?", "When were you confused?", and "What did the drones do?"

Fix the top three problems, then test with a different person. If you can, log events from the game with `Debug.Log` (a checkpoint reached, a death and where it happened), and count them afterward instead of relying on memory.

## The Profiler: measure before you optimize

At 60 frames per second each frame has 16.7 milliseconds. When the game stutters, something is taking longer, and guessing what is usually wrong. Open **Window > Analysis > Profiler**, press Play, and let it record. The **CPU Usage** chart at the top shows each frame's time. Click a tall spike, switch the lower panel to **Hierarchy**, and sort by **Total** time, or by **GC Alloc** to find code that creates garbage.

Here's a script that shows up badly:

```csharp
void Update()
{
    var player = FindFirstObjectByType<Health>();            // searches the scene every frame
    label.text = "HP " + player.Current + "/" + player.Max;  // builds a new string every frame
}
```

`FindFirstObjectByType` searches every object in the scene, and Unity's documentation warns against calling it every frame. The string concatenation allocates memory each frame, and the garbage collector eventually pauses the game to clean it up. The fix is what you already did in Module 5: keep a reference set in the Inspector, and change the text only when the `Changed` event fires.

Profiling in the Editor includes the Editor's own overhead, so the numbers run high. For real figures, make a Development Build with **Autoconnect Profiler** ticked, and the Profiler attaches to the running build.

## Build Profiles and the Web platform

Unity 6 replaced the old Build Settings window with **File > Build Profiles**. The left side lists **Platforms** such as Windows, macOS, Linux, and Web, and you can also create your own profiles. Each platform has a **Scene List**: the scenes included in the build, in order, with the first one loading at startup. **Add Open Scenes** adds what you have open, and dragging reorders.

To make a Web build, select **Web**. If its module isn't installed, add **Web Build Support** to your Editor from Unity Hub. Switch the active platform to Web, set the scene list, and click **Build**, choosing an empty folder outside `Assets`. You get an `index.html` and the files it loads. Settings that change how the page loads, such as **Compression Format** and **Decompression Fallback**, live in **Edit > Project Settings > Player** under the Web tab's **Publishing Settings**.

That folder is what itch.io hosts. Zip its contents, upload the zip as an HTML project, and itch.io plays it in the page. The build-along walks through every click.

:::warning
**The save file says `{}`.** If `SaveData` uses properties (`public int Score { get; set; }`) or is missing `[Serializable]`, `JsonUtility.ToJson` writes an empty object without any error, and loading gives you defaults. Use public fields, or private fields with `[SerializeField]`, and open the file to check it.
:::

:::warning
**Web saves on itch.io and new uploads.** itch.io serves each new upload from a different path, and browser storage is tied to the path, so uploading a new build can reset players' saves. Tell players in your update notes, and test saving in the uploaded build itself.
:::

:::quiz
Q: Where should the music volume setting and the player's current checkpoint be stored?
- [x] Volume in `PlayerPrefs`, checkpoint in the JSON save file
  Volume is one small setting; the checkpoint belongs with the rest of the progress data.
- [ ] Both in `PlayerPrefs`
  It would work for two values, but progress grows (coins, levels, health) and is easier to manage as one file.
- [ ] Both in the JSON save file
  Then "New Game," which deletes the save, would also reset the player's volume.

Q: `SaveData` has `public int Score { get; set; }` and `[Serializable]`. What does `JsonUtility.ToJson(data)` produce?
- [ ] `{"Score":340}`
  That's what a library that reads properties would produce. `JsonUtility` serializes fields only.
- [x] `{}`
  The property's hidden backing field isn't serialized, so nothing is written, and no error is shown.
- [ ] An exception explaining that properties aren't supported
  There's no error at all, which is why this bug is easy to miss.

Q: You double-click `index.html` in your Web build folder and the game doesn't load. What's the problem?
- [ ] The build is broken and needs rebuilding
  The files are fine; the way they were opened is the problem.
- [x] Web builds must be served by a web server, not opened from disk
  Use **Build and Run**, which starts a local server, or upload to itch.io.
- [ ] Web builds only run in one specific browser
  They run in current versions of the major desktop browsers.

Q: The Profiler shows `ScoreLabel.Update` allocating memory every frame, and the game stutters every few seconds. What's the most likely cause?
- [ ] The score is too large a number
  The size of the number doesn't matter.
- [x] It builds a new string and assigns the text every frame, and the garbage collector pauses to clean up
  Updating the text only when the score changes removes almost all of that garbage.
- [ ] TextMeshPro can't run in `Update`
  It can, but rebuilding text every frame for no reason is wasted work.
:::

:::takeaways
- Settings and single records go in `PlayerPrefs`; progress goes in a `[Serializable]` class written as JSON.
- `JsonUtility` saves fields, not properties; missing fields keep their initializer values, which makes adding fields safe.
- Save under `Application.persistentDataPath`, and print the path so you can find the file.
- Test a Development Build before shipping: scene list, frame rate, screen size, startup order, and browser rules.
- Playtest in silence, count where people struggle, and measure with the Profiler before optimizing.
:::
