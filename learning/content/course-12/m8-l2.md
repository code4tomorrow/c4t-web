Your Module 7 project already has most of the systems. What it lacks is a skeleton: a title screen, more than one level, a way to win, and one place that decides whether the game is playing, paused, won, or lost. Build that skeleton first and every milestone after it is "fill in the content."

## Step 1: Folders, scenes, and the Scene List

Keep the project tidy from the start; you'll be in it for a while:

```text
Assets/
  Art/          sprites, tiles, animations, palettes
  Audio/        music and effects
  Prefabs/      Player, enemies, coins, checkpoint, exit, HUD
  Scenes/       Title, Level1, Level2, End
  Scripts/      one file per class, grouped in subfolders if it grows
DESIGN.md       your one-page design doc (next to Assets, not inside it)
```

Make the **Player** and **HUD** prefabs now, by dragging them from your Module 7 scene into `Prefabs`. Each level then starts by dragging both in, and a fix to the prefab fixes every level.

Create the four scenes, then open **File > Build Profiles** and arrange the **Scene List** in the order shown in the diagram: Title first, because the first scene in the list is the one the build loads at startup, then the levels in play order, then End.

## Step 2: One GameManager for the game's state

The player, enemies, and HUD each have their own little state machines. The game as a whole needs one too. Put this on a `GameSystems` object in each level (it's a good candidate for a prefab):

```csharp
using System;
using UnityEngine;
using UnityEngine.InputSystem;
using UnityEngine.SceneManagement;

public class GameManager : MonoBehaviour
{
    public enum GameState { Playing, Paused, Won, Lost }

    public static GameManager Instance { get; private set; }

    public GameState State { get; private set; } = GameState.Playing;
    public event Action<GameState> StateChanged;

    [SerializeField] Health playerHealth;

    void Awake()
    {
        Instance = this;
        Time.timeScale = 1f;
    }

    void OnEnable() => playerHealth.Died += Lose;
    void OnDisable() => playerHealth.Died -= Lose;

    void Update()
    {
        if (Keyboard.current == null || !Keyboard.current.escapeKey.wasPressedThisFrame) return;

        if (State == GameState.Playing) SetState(GameState.Paused);
        else if (State == GameState.Paused) SetState(GameState.Playing);
    }

    public void Resume() => SetState(GameState.Playing);
    public void Win() => SetState(GameState.Won);
    void Lose() => SetState(GameState.Lost);

    void SetState(GameState next)
    {
        if (State == next) return;
        State = next;
        Time.timeScale = next == GameState.Playing ? 1f : 0f;
        AudioListener.pause = next == GameState.Paused;
        StateChanged?.Invoke(next);
    }

    public void Restart()
    {
        Time.timeScale = 1f;
        SceneManager.LoadScene(SceneManager.GetActiveScene().buildIndex);
    }

    public void LoadNextLevel()
    {
        Time.timeScale = 1f;
        int next = SceneManager.GetActiveScene().buildIndex + 1;
        if (next >= SceneManager.sceneCountInBuildSettings) next = 0;
        SceneManager.LoadScene(next);
    }

    public void QuitToTitle()
    {
        Time.timeScale = 1f;
        SceneManager.LoadScene(0);
    }
}
```

Every rule about the game's flow is in one place: Escape only toggles between Playing and Paused, so it can't unpause a Game Over screen, and the time scale always matches the state. `Awake` resets `Time.timeScale` to 1 as a safety net, so no scene can ever start frozen because the last one ended paused.

The HUD shows the right panel for each state. It takes the GameManager as an Inspector reference rather than through `Instance`, so subscribing in `OnEnable` is safe no matter which object wakes up first:

```csharp
using UnityEngine;

public class StatePanels : MonoBehaviour
{
    [SerializeField] GameManager game;
    [SerializeField] GameObject pausePanel;
    [SerializeField] GameObject winPanel;
    [SerializeField] GameObject losePanel;

    void OnEnable() => game.StateChanged += Show;
    void OnDisable() => game.StateChanged -= Show;
    void Start() => Show(game.State);

    void Show(GameManager.GameState state)
    {
        pausePanel.SetActive(state == GameManager.GameState.Paused);
        winPanel.SetActive(state == GameManager.GameState.Won);
        losePanel.SetActive(state == GameManager.GameState.Lost);
    }
}
```

This replaces the separate `GameOverScreen` and `PauseMenu` scripts from Module 5. Point the panels' buttons at `GameManager.Resume`, `Restart`, `LoadNextLevel`, and `QuitToTitle`.

## Step 3: An exit that saves and moves on

The exit trigger wins the level and saves a "start of the next level" record, so **Continue** on the title screen picks up there:

```csharp
using System.IO;
using UnityEngine;
using UnityEngine.SceneManagement;

public class LevelExit : MonoBehaviour
{
    [SerializeField] bool finalLevel;   // tick on the last level, the one before End

    void OnTriggerEnter2D(Collider2D other)
    {
        if (!other.CompareTag("Player") || GameManager.Instance.State != GameManager.GameState.Playing) return;

        if (finalLevel)
        {
            SaveSystem.Delete();   // the game is finished, so there's nothing to continue
        }
        else
        {
            int next = SceneManager.GetActiveScene().buildIndex + 1;
            string path = SceneUtility.GetScenePathByBuildIndex(next);
            SaveSystem.Save(new SaveData
            {
                sceneName = Path.GetFileNameWithoutExtension(path),
                checkpointId = "",
                score = ScoreKeeper.Instance.Score
            });
        }

        GameManager.Instance.Win();
    }
}
```

On the final level the exit deletes the save instead, so Continue never drops a player onto the End screen. `SceneUtility.GetScenePathByBuildIndex` turns a Scene List position into a path like `Assets/Scenes/Level2.unity`, and `Path.GetFileNameWithoutExtension` trims it to `Level2`. In `SaveLoader`, only move the player to a checkpoint when `data.sceneName` matches the current scene; the score is restored either way, so it carries from level to level.

## Step 4: A title screen with Continue and New Game

In the Title scene, add a Canvas with the game's name, two buttons, and this script:

```csharp
using UnityEngine;
using UnityEngine.SceneManagement;
using UnityEngine.UI;

public class TitleMenu : MonoBehaviour
{
    [SerializeField] Button continueButton;
    [SerializeField] string firstLevel = "Level1";

    void Start()
    {
        continueButton.interactable = SaveSystem.TryLoad(out _);
    }

    public void NewGame()
    {
        SaveSystem.Delete();
        SceneManager.LoadScene(firstLevel);
    }

    public void Continue()
    {
        if (SaveSystem.TryLoad(out SaveData data))
            SceneManager.LoadScene(data.sceneName);
    }
}
```

`out _` throws away the loaded data when all you need to know is whether a save exists. A greyed-out Continue button tells a first-time player there's nothing to continue, without any text. The End scene needs only a "Thanks for playing" line, the final score, and a button that loads scene 0.

Now check the skeleton by playing the game from the Title scene: New Game, reach the exit, Next, reach the exit, End, back to Title, Continue. Do this from the Title scene at the start of every work session, so you always test the path a real player takes.

## Milestone 1: Grey box

Build every level out of plain shapes (**Create > 2D > Sprites > Square** gives you a placeholder sprite) and tiles in flat colors. No art, no sound. The question this milestone answers is "is moving through this level interesting?"

Done when:

- [ ] Every level from your design doc exists, start to exit, in grey box.
- [ ] The player can move, jump, and collide everywhere, and the camera follows.
- [ ] The full scene flow works from Title to End.
- [ ] You've written one line per level on what it teaches, tests, and twists.

## Milestone 2: Vertical slice

Pick the first level and make it finished: real art, the Animator, the HUD, sounds, at least one enemy with its state machine, checkpoints, and saving. Leave the other levels in grey box.

Done when:

- [ ] Level 1 looks, sounds, and plays the way you want the whole game to.
- [ ] Someone else has played it while you watched in silence, and you've written down what they struggled with.
- [ ] You've compared the time it took with your estimate, and cut or kept levels based on that.

## Milestone 3: Content complete

Bring every level up to the slice's quality and finish every menu. After this milestone comes the **feature freeze**: no new mechanics, enemies, or levels, only fixes and polish. Ideas that arrive later go on a "next version" list.

Done when:

- [ ] Every requirement from the capstone table is in the game.
- [ ] Saving works across quitting and reopening, and a damaged save starts fresh.
- [ ] A Development Build runs from Title to End without errors.

## Milestone 4: Ship

Make the Web build, put it on itch.io as a draft, and work through the bug list and the test plan from the next lesson. Make the screenshots and trailer, and publish.

## Keep a bug list and commit when things work

When a playtester or your own testing finds a problem, write it down instead of fixing it immediately, so you fix the worst ones first:

| # | Bug | Steps to reproduce | Severity | Status |
| --- | --- | --- | --- | --- |
| 1 | Drone flies through the right wall of room 3 | Lose it behind the pillar, wait 2 s | Medium | Fixed: widened room |
| 2 | Score resets to 0 when Level 2 starts | Finish Level 1, press Next | High | Open |
| 3 | Coin chime is louder than music | Grab any coin | Low | Open |

**High** means a player can't finish or loses progress; fix those first. **Low** is cosmetic.

Commit (or zip a backup, as Module 1 showed) every time something new works: "Drone patrols level 2," "Continue works." When a change breaks everything at midnight, a commit from an hour earlier turns a disaster into a five-minute rollback.

:::quiz
Q: Why does the Title scene have to be first in the Scene List?
- [ ] Unity sorts the list alphabetically at build time
  It keeps your order; that's why the order matters.
- [x] The first scene in the list is the one the build loads when it starts
  Put the levels after it in play order so `buildIndex + 1` is always the next level.
- [ ] Only the first scene can contain UI
  Any scene can have UI.

Q: A playtester can press Escape on the Game Over screen and keep playing with zero health. With this starter's GameManager, why can't that happen?
- [ ] Escape is disabled when health is zero
  Nothing checks health directly in `Update`.
- [x] Escape only switches between Playing and Paused, so from Lost it does nothing
  Keeping every flow rule in one state machine means one place enforces them all.
- [ ] `Time.timeScale` is 0, so `Update` doesn't run
  `Update` still runs at a time scale of 0; only time-based movement and physics stop.

Q: After the vertical slice, you realize a level takes about three times longer to build than you planned. What's the best move?
- [ ] Keep the plan and work faster
  The slice just measured your real speed; the plan should change, not you.
- [x] Cut levels or features now, using your Should and Could lists, so the rest fits
  This is what the vertical slice is for: finding out early while there's still time to adjust.
- [ ] Skip the test plan in Milestone 4 to make up the time
  Untested games ship with the bugs that make players quit.
:::

:::takeaways
- Build the skeleton (scene flow, GameManager, exit, title) before the content.
- One game-level state machine owns pause, win, lose, and the time scale.
- Each milestone ends with a checklist, and the vertical slice is your reality check on scope.
- After content complete, freeze features and spend the remaining time on fixes and polish.
- Play from the Title scene every session, track bugs by severity, and commit whenever something works.
:::
