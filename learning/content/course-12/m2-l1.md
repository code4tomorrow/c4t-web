Picture a level with twelve spinning saw blades. You made one, then pressed **Ctrl+D** eleven times and dragged the copies into place. A playtester says the saws are too slow, so you click through all twelve and raise the speed. You miss one. Now a single saw in the middle of the level spins at half speed, and a month later someone files a bug about the "easy saw".

Copy-paste made twelve independent objects that happen to look alike. Unity's answer is the **prefab**, one saved definition all twelve follow. First, the model underneath it.

## A GameObject is an empty box; components are what it can do

Every object in a scene, whether a player, a saw, a camera, or an invisible spawn point, is a **GameObject**. On its own a GameObject does almost nothing. It has a name, a tag, a layer, and one **Transform** that says where it is.

Everything else comes from **components** you add to it. Select a saw in the Inspector and you might see:

| Component | What it adds |
| --- | --- |
| **Transform** | Position, rotation, and scale (every GameObject has exactly one) |
| **Sprite Renderer** | Draws an image, with a color tint and a sorting order |
| **Circle Collider 2D** | A shape the physics engine can detect touching |
| **Spinner** (your script) | Rotates the object every frame |

For a saw that also bobs, you don't write a new kind of saw; you add a `Bobber` script to the same GameObject. Unity games are built from small one-job components combined on objects.

```mermaid caption="One GameObject, four components. Each component is a separate piece you can add, remove, or reuse elsewhere."
flowchart LR
    G((Saw GameObject)) --- T["Transform: where it is"]
    G --- R["Sprite Renderer: what it looks like"]
    G --- C["Circle Collider 2D: its physical shape"]
    G --- S["Spinner script: what it does"]
```

## Transforms, parents, and local positions

Drag one object onto another in the Hierarchy and it becomes a **child**. A child moves, rotates, and scales with its parent, and the numbers you see in its Inspector become **local**: measured from the parent, in the parent's scaled units.

Intuitively, a tooth sits "one unit right of the blade's center" wherever the blade goes, and if the blade doubles in size, so does that unit. Precisely: world position = parent position + the local position after the parent's scale and rotation are applied. Suppose:

-   **Blade** (parent): position (5, 2), scale (2, 2), rotation 0.
-   **Tooth** (child): local position (1, 0).

The tooth's world position is (5 + 2 × 1, 2 + 2 × 0) = **(7, 2)**. Rotate the blade 90 degrees and the tooth swings around to (5, 4). This script prints both versions:

```csharp title="WhereAmI.cs"
using UnityEngine;

public class WhereAmI : MonoBehaviour
{
    void Start()
    {
        Debug.Log($"{name}: local {transform.localPosition}, world {transform.position}");
    }
}
```

Attached to the tooth, it logs:

```text
Tooth: local (1.00, 0.00, 0.00), world (7.00, 2.00, 0.00)
```

In code, `transform.localPosition` is what the Inspector shows for a child, and `transform.position` is always world space. Mixing them up is the most common reason an object teleports to the "wrong" place.

## Your scripts are components too

`public class Spinner : MonoBehaviour` defines a new kind of component, and each attached copy has its own fields. To reach another component on the same object, use `GetComponent<T>()`:

```csharp title="BlinkingLight.cs"
using UnityEngine;

[RequireComponent(typeof(SpriteRenderer))]
public class BlinkingLight : MonoBehaviour
{
    [SerializeField] private Color onColor = Color.yellow;
    [SerializeField] private float secondsPerBlink = 1f;

    private SpriteRenderer sprite;
    private Color offColor;

    void Awake()
    {
        sprite = GetComponent<SpriteRenderer>();
        offColor = sprite.color;
    }

    void Update()
    {
        bool isOn = Mathf.Repeat(Time.time, secondsPerBlink) < secondsPerBlink / 2f;
        sprite.color = isOn ? onColor : offColor;
    }
}
```

`GetComponent` runs once in `Awake` and the result is kept in a field, rather than searched for every frame. `[RequireComponent]` adds a Sprite Renderer automatically if one is missing, so `sprite` can't be null. For objects elsewhere in the scene, use a `[SerializeField]` field and drag the object into its Inspector slot.

## When Unity calls your code: the frame loop

There's no `main` function in Unity. Unity calls specially named methods at set moments, in the same cycle every frame.

```mermaid caption="The order Unity calls your script's methods. The loop repeats every frame until the object is destroyed."
flowchart TD
    A["Scene loads"] --> B["Awake: on every object"]
    B --> C["OnEnable"]
    C --> D["Start: on every object"]
    D --> E["FixedUpdate: 0, 1, or more times"]
    E --> F["Update: once per frame"]
    F --> G["LateUpdate: once per frame"]
    G --> H["Draw the frame"]
    H --> E
    H -.->|object destroyed| I[OnDestroy]
```

What each one is for:

-   **Awake** runs once, as soon as the object exists. Set up the object itself here, such as `GetComponent` calls.
-   **Start** runs once, just before the object's first `Update`. For objects in the scene when it loads, every `Awake` finishes before any `Start` begins, so in `Start` it's safe to talk to other objects.
-   **Update** runs every frame. Read input and move non-physics objects here.
-   **FixedUpdate** runs on a fixed clock (50 times a second by default), independent of frame rate. Physics code goes here, which Module 4 covers.
-   **LateUpdate** runs after every `Update` that frame, which makes it right for things that follow other things.

Suppose two objects in the scene, `A` and `B`, both have a script that logs each call. You'd see something like:

```text
A: Awake
A: OnEnable
B: Awake
B: OnEnable
A: Start
B: Start
A: Update 1
B: Update 1
A: Update 2
B: Update 2
```

Whether `A` or `B` goes first isn't guaranteed, but both Awakes always come before either Start. Hence the rule: set yourself up in Awake, use others in Start.

## Prefabs: one definition, many copies

A **prefab** is a GameObject saved as an asset, with all its components, values, and children. Drag a configured saw from the Hierarchy into the Project window and it becomes `Saw.prefab`. Its name in the Hierarchy turns blue, which marks it as an **instance** of the prefab. Drag the prefab from the Project window into the scene as often as you like.

Three ideas make prefabs useful:

1.  **Edit the prefab, every instance updates.** Double-click the prefab asset to open **Prefab Mode**. Change the speed there, and all twelve saws change at once.
2.  **Overrides.** Change a value on one instance and that value is now overridden: its label turns bold with a blue bar beside it. The **Overrides** dropdown at the top of that instance's Inspector lets you **Apply All** (send the change to the prefab) or **Revert All** (go back to the prefab's value).
3.  **Variants.** Right-click a prefab and choose **Create > Prefab Variant**. The variant starts as an exact copy that keeps following its base, and you add or override only what's different, such as a bobbing saw that's also tinted orange. Change the base saw's sprite later and the variant gets it too.

Prefabs also work from code. `Instantiate` makes a new instance while the game runs:

```csharp title="SawRow.cs"
using UnityEngine;

public class SawRow : MonoBehaviour
{
    [SerializeField] private GameObject sawPrefab;
    [SerializeField] private int count = 5;
    [SerializeField] private float spacing = 2f;

    void Start()
    {
        for (int i = 0; i < count; i++)
        {
            Vector3 position = transform.position + new Vector3(i * spacing, 0f, 0f);
            Instantiate(sawPrefab, position, Quaternion.identity);
        }
    }
}
```

Drag `Saw.prefab` from the Project window into **Saw Prefab**, press Play, and five saws appear two units apart, starting at the spawner. `Quaternion.identity` means "no rotation".

## Mistakes that cost an afternoon

:::warning You changed an instance, and the others didn't follow
Editing a saw in the scene only changes that one saw; its fields go bold to show the override. If you meant to change all saws, use **Overrides > Apply All** on that instance, or make the change in Prefab Mode in the first place.
:::

:::warning NullReferenceException right after GetComponent
`GetComponent<SpriteRenderer>()` returns null when the component isn't on *this* GameObject. It's often on a child instead. Use `GetComponentInChildren<SpriteRenderer>()`, move the script to the object that has the component, or add `[RequireComponent]` so it can't be missing.
:::

:::quiz
Q: A parent is at position (3, 0) with scale (2, 2). Its child has local position (0, 1.5). Where is the child in the world?
- [ ] (3, 1.5)
  That adds the local position without the parent's scale.
- [x] (3, 3)
  The local offset (0, 1.5) is scaled by 2 to (0, 3), then added to (3, 0).
- [ ] (0, 1.5)
  That's the local position, which is relative to the parent, not the world.

Q: Script X uses another object's component in `Awake`, and that component is filled in by its own `Awake`. Sometimes X gets null. What's the fix?
- [ ] Move X's code to `Update`
  It would work eventually, but it runs every frame and hides the real problem.
- [x] Move X's code to `Start`
  Every object's Awake finishes before any Start, so the other object is set up by then.
- [ ] Rename X so it runs first
  Script names don't control the call order.

Q: You need ten saws that all spin, and two of them should also bob. What's the cleanest setup?
- [ ] Twelve independent copies, configured by hand
  That's exactly the drift problem prefabs solve.
- [ ] One prefab, then add a Bobber by hand to two instances
  It works, but the bobbing saws are now one-off overrides that are easy to break.
- [x] A Saw prefab and a BobbingSaw prefab variant with the extra Bobber component
  Shared settings live in the base, and the variant adds only what's different.

Q: Where should a camera that follows the player update its position?
- [ ] `Awake`
  Awake runs once; the camera must move every frame.
- [ ] `FixedUpdate`
  That's for physics and doesn't run in step with drawing.
- [x] `LateUpdate`
  It runs after every Update, so the player has already moved this frame.
:::

:::takeaways
- A GameObject is a container. Its components (Transform, Sprite Renderer, colliders, your scripts) give it looks and behavior.
- A child's Inspector values are local to its parent; `transform.position` is always the world position.
- Unity calls `Awake`, then `Start`, then `Update` and `LateUpdate` every frame. Set yourself up in Awake and reach for other objects in Start.
- Prefabs keep repeated objects in sync. Overrides customize one instance, and variants define a family of related objects.
:::
