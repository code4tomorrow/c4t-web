A game is finished when someone who has never seen it can find it, understand it, play it to the end, and want to tell a friend. Everything here serves that sentence. The code is mostly done; what's left is making sure it works for other people, and showing them why it's worth their time.

## Run a written test plan

"I played it and it seemed fine" isn't a test. Copy this plan into your design doc, add rows for your own mechanics, and fill in both result columns. A row isn't passing until it passes in the Web build, because that's the version players get.

| # | Area | Steps | Expected | Editor | Web build |
| --- | --- | --- | --- | --- | --- |
| 1 | Start | Open the game | Title screen, music after first click, Continue greyed out on first run | | |
| 2 | Controls | Move, jump, and use every action listed on the page | Each one works, and the page lists them correctly | | |
| 3 | Collision | Walk into every wall type, fall into a pit | No passing through walls; falling has a result (damage or respawn) | | |
| 4 | Camera | Run the whole of Level 1 | Threats appear on screen before they reach you | | |
| 5 | Animation | Idle, run, jump, take a hit | Each state shows, with no frozen first frame | | |
| 6 | Damage | Take hits until you die | Bar drops, flash and sound on each hit, Game Over panel at zero | | |
| 7 | Enemy | Get spotted, then hide | Every state change is visible and audible | | |
| 8 | Pause | Escape during play, then Resume | Everything stops, including sound, then continues | | |
| 9 | Saving | Reach a checkpoint, reload the page or relaunch | Resume at that checkpoint with the same score | | |
| 10 | Damaged save | Corrupt the save (desktop) or clear site data (Web) | Game starts fresh without errors | | |
| 11 | Full run | Play from Title to End | Every scene loads in order, End returns to Title | | |
| 12 | Screen sizes | Try a small browser window and fullscreen | HUD stays readable and in its corners | | |

Any failure goes on your bug list with steps to reproduce. Fix the High ones before anything else in this lesson.

## Playtest again, and compare

Run the Module 7 playtest a second time with two or three people who haven't played before. Use the same logging, so you get the same numbers: deaths per section, checkpoints reached, and where anyone quit. Put the old and new counts side by side. "Deaths in the test corridor went from 7 to 2 after widening the pillar" is evidence your design work did something, and it's exactly what the rubric's playtesting row asks for.

## Polish in order of impact

With limited time, polish what players notice most first:

1. **Readability.** Can players always tell what's dangerous, what they can stand on, what they can collect, and what just happened? Check contrast between the background and the play layer, and make sure every hit, pickup, and save has feedback.
2. **Feel.** Small touches make actions satisfying: a squash of the sprite on landing, a few particles when a coin is collected (**Effects > Particle System** in the Hierarchy menu), a two-frame hit pause, a short camera shake on damage. Keep each one subtle, and keep flashes to three per second or fewer.
3. **Looks.** A consistent art style, a background layer, and a font that matches the mood. Consistency beats detail: one simple style used everywhere looks better than a mix of beautiful and placeholder art.

Stop polishing when the test plan passes and the next fix is cosmetic. Shipping matters more than one more effect.

## Screenshots that sell the game

Screenshots are the first thing people see on itch.io. Take them during real play, at moments with something happening, not menus. Set the Game view to **Full HD (1920x1080)** from its aspect dropdown, then use a key that saves the frame:

```csharp
using UnityEngine;
using UnityEngine.InputSystem;

public class ScreenshotKey : MonoBehaviour
{
    void Update()
    {
        if (Keyboard.current == null || !Keyboard.current.f12Key.wasPressedThisFrame) return;

        string fileName = $"shot-{System.DateTime.Now:yyyyMMdd-HHmmss}.png";
        ScreenCapture.CaptureScreenshot(fileName);
        Debug.Log($"Saved {fileName}");
    }
}
```

In the Editor, the file appears in your project folder, next to `Assets`. Take twenty and keep the best three to five: one that shows the core loop clearly, one with an enemy mid-chase, one of a later level, and one of something surprising. Remove the script (or disable it) before your final build.

## A 30 to 60 second trailer

A short gameplay trailer is how most people decide to click. A simple structure that works:

1. **0 to 5 seconds**: gameplay immediately, at its most readable. No logos first.
2. **5 to 25 seconds**: the core loop, one idea per clip, each clip two to four seconds long.
3. **25 to 45 seconds**: escalation, meaning a harder room, more enemies, the twist from each level.
4. **Final 5 seconds**: the title, "Play free in your browser," and the itch.io address.

To record, install **Recorder** from **Window > Package Manager** (it's in the Unity Registry), open **Window > General > Recorder > Recorder Window**, choose **Add Recorder > Movie**, and press **Start Recording**; it records the Game view in Play mode. [OBS Studio](https://obsproject.com/) is a free alternative that records the Web build in a browser. Play the same section several times and keep your best runs. Cut the clips together in any free video editor and add your game's music.

## The itch.io page

Your page is your game's front door. Before switching from Draft to Public, make sure it has:

- a **cover image** (itch.io's editor shows the recommended size) with the title readable at a small size,
- three to five **screenshots** and the trailer (itch.io embeds a YouTube link),
- a **short description**: the pitch in one sentence, then two or three sentences on what makes it fun,
- the **controls**, as a short list,
- **credits** for every asset you didn't make, with licenses,
- a few accurate **tags** (platformer, pixel art, short), and a note if anything was made with generative AI.

## Present it in three minutes

When you show the game to your class, family, or a club, use a plan so the time goes to the best parts:

```text
0:00  Pitch: one sentence, and the trailer or 20 seconds of live play
0:30  Play the vertical-slice level live, narrating the core loop
1:30  One system you're proud of (the drone's states, the save system) with its diagram or code
2:15  One playtest finding and what you changed, with before-and-after numbers
2:45  What you'd add next, and where people can play it
```

Practice once with a timer. Have the game already running with a save at a good checkpoint, so you don't spend the demo on the title screen.

## The rubric

Score your own project honestly before anyone else does. Each row is worth the points shown, for 100 in total.

| Area (points) | Excellent | Solid | Needs work |
| --- | --- | --- | --- |
| Core requirements (25) | Every row of the requirements table works in the Web build | One or two rows partly done | Several missing or only in the Editor |
| Code quality (15) | Small scripts with one job each, events between systems, no per-frame searches, no errors in the Console | Works, with a few long scripts or direct references | Errors or warnings during play; hard to change |
| Feedback (15) | Every important event is seen and heard; HUD readable at any size | Most events have feedback | Players miss hits, pickups, or saves |
| Level and enemy design (15) | Each level teaches, tests, and twists; enemy states are readable and fair | Levels are playable but uneven | Difficulty spikes or unclear threats |
| Saving and build (10) | Saves survive relaunch, damaged saves start fresh, the Web build runs end to end | Saving works with rough edges | Saving or the build is broken |
| Playtesting (10) | Two rounds with recorded numbers and changes that improved them | One round with notes | No playtest evidence |
| Presentation (10) | Complete itch.io page, trailer, screenshots, credits, a timed three-minute demo | Page and demo with gaps | Missing page or demo |

## Reflect, then keep going

Write a short reflection in your design doc while it's fresh. Answer three questions: What took much longer than you expected, and why? Which playtest finding surprised you most? If you started this game again tomorrow, what would you plan differently?

Then decide what's next. Some good directions:

- **Enter a game jam.** Jams give you a theme and a deadline (often 48 hours to a week) and a community that plays your game. The [itch.io jams calendar](https://itch.io/jams) lists many that are open to everyone; check each jam's rules and age requirements.
- **Learn the next tools.** Unity's [Junior Programmer pathway](https://learn.unity.com/pathway/junior-programmer) covers 3D, and from there pathfinding (the A* Pathfinding Project or Unity's NavMesh), object pooling with `UnityEngine.Pool`, `ScriptableObject` assets for game data, and Input System actions for gamepad support.
- **Ship a second, smaller game.** The fastest way to get better is to finish another one, using everything this one taught you about scope.
