## Warm-up: predict the JSON

Using the `SaveData` class from this module (fields `version = 1`, `sceneName = "Level1"`, `checkpointId = ""`, `score`, and `health = 5`), what does this log?

```csharp
var data = new SaveData { checkpointId = "cp2", score = 120 };
Debug.Log(JsonUtility.ToJson(data));
```

Decide before reading on. Every field is written, including the ones you didn't set, which keep their initializer values. With `prettyPrint` left at `false`, it's all on one line:

```text
{"version":1,"sceneName":"Level1","checkpointId":"cp2","score":120,"health":5}
```

### Exercise 1: A best score that only goes up

When the player reaches the exit, compare the score with the best score in `PlayerPrefs`. If it's higher, store it and show `New best: 450`; otherwise show `Best: 520`.

:::hint
`PlayerPrefs.GetInt(key, 0)` returns 0 the first time, so any score beats it. Call `PlayerPrefs.Save()` after setting, in case the browser tab closes right away.
:::

:::solution
```csharp
using TMPro;
using UnityEngine;

public class BestScore : MonoBehaviour
{
    const string Key = "bestScore";

    [SerializeField] TextMeshProUGUI label;

    public void Submit(int score)
    {
        int best = PlayerPrefs.GetInt(Key, 0);
        if (score > best)
        {
            PlayerPrefs.SetInt(Key, score);
            PlayerPrefs.Save();
            label.text = $"New best: {score}";
        }
        else
        {
            label.text = $"Best: {best}";
        }
    }
}
```

Call `Submit(ScoreKeeper.Instance.Score)` from your exit trigger. A best score is a single record that should survive "New Game," which is why it lives in `PlayerPrefs` and not in the progress save.
:::

### Exercise 2: Where did the stats go?

A teammate added stats to the save. The game saves without errors, but after loading, jumps and deaths are always 0. This is the code and the file it wrote:

```csharp
using System;

[Serializable]
public class SaveData
{
    public int score;
    public PlayerStats stats = new PlayerStats();
}

public class PlayerStats
{
    public int jumps;
    public int deaths;
}
```

```text
{"score":340}
```

Explain what's missing and fix it.

:::hint
Look at which classes have an attribute above them. `JsonUtility` decides what to write separately for each nested class.
:::

:::solution
`PlayerStats` has no `[Serializable]` attribute, so Unity's serializer treats the `stats` field as something it can't save and skips it, without an error. Add the attribute:

```csharp
[Serializable]
public class PlayerStats
{
    public int jumps;
    public int deaths;
}
```

Now the file contains `"stats":{"jumps":12,"deaths":3}`. Whenever a save seems to lose data, open the file before debugging the loading code: if the data isn't in the file, the bug is in saving.
:::

### Exercise 3: Remember which coins were collected

Right now, reloading at a checkpoint brings back every coin, so a player can farm points. Save the IDs of collected coins, and on load, remove those coins from the level. Coins collected after the last checkpoint should come back, since that progress wasn't saved.

:::hint
Each coin needs an ID that is the same every time the scene loads. A field set by `Reset()` is shared by every instance of a prefab, so it doesn't work. A coin that never moves can build its ID from the scene name and its position. Keep the collected IDs in a static `HashSet<string>`, and load it in `Awake`, which runs before any coin's `Start`.
:::

:::solution
Add `public List<string> collectedCoins = new List<string>();` to `SaveData` (with `using System.Collections.Generic;`). Then a small shared set:

```csharp
using System.Collections.Generic;

public static class CoinTracker
{
    public static readonly HashSet<string> Collected = new HashSet<string>();
}
```

In `Coin`:

```csharp
string Id => $"{gameObject.scene.name}:{transform.position.x:F2},{transform.position.y:F2}";

void Start()
{
    if (CoinTracker.Collected.Contains(Id)) Destroy(gameObject);
}

// in OnTriggerEnter2D, next to ScoreKeeper.Instance.Add(points):
CoinTracker.Collected.Add(Id);
```

In `Checkpoint`, when building the `SaveData`, add `collectedCoins = new List<string>(CoinTracker.Collected)`. In `SaveLoader`, load the set in `Awake`:

```csharp
void Awake()
{
    CoinTracker.Collected.Clear();
    if (SaveSystem.TryLoad(out SaveData data))
        CoinTracker.Collected.UnionWith(data.collectedCoins);
}
```

`Awake` matters: Unity runs every `Awake` before any `Start`, so the set is ready before coins check it. Clearing first also throws away coins grabbed after the last checkpoint, which then reappear. The cost of position-based IDs is that moving a coin in the Editor gives it a new ID, so old saves won't recognize it.
:::

### Exercise 4: Load saves from an older version

Version 1 of your game saved the checkpoint as a number, `"checkpoint": 2`. Version 2 uses string IDs like `"cp2"`. Players have version 1 saves. Make version 2 load them correctly.

:::hint
Keep the old field in the class so `JsonUtility` still reads it, with a default that means "not present." Fields missing from a file keep their initializer values. After loading, check `version`.
:::

:::solution
```csharp
[Serializable]
public class SaveData
{
    public int version = 2;
    public string checkpointId = "";
    public int checkpoint = -1;   // version 1 only; kept so old files still load
    public int score;
    public int health = 5;
}
```

In `SaveSystem.TryLoad`, after `FromJson` succeeds:

```csharp
if (data.version < 2)
{
    if (data.checkpoint >= 0) data.checkpointId = "cp" + data.checkpoint;
    data.version = 2;
}
```

A version 1 file contains `"version":1`, so the check runs; a version 2 file doesn't contain `checkpoint`, so it stays -1 and is ignored. The next save writes a clean version 2 file. Bumping `version` whenever the format changes is what makes this possible, so include it from the first release.
:::

### Exercise 5: Fix what the Profiler found

The Profiler's **Hierarchy** view, sorted by **GC Alloc**, puts this script at the top every frame, and the frame time spikes every few seconds:

```csharp
using TMPro;
using UnityEngine;

public class EnemyCounter : MonoBehaviour
{
    [SerializeField] TextMeshProUGUI label;

    void Update()
    {
        GameObject[] enemies = GameObject.FindGameObjectsWithTag("Enemy");
        label.text = "Enemies: " + enemies.Length;

        foreach (GameObject enemy in enemies)
        {
            SpriteRenderer sprite = enemy.GetComponent<SpriteRenderer>();
            sprite.color = Color.Lerp(Color.white, Color.red, Mathf.PingPong(Time.time, 1f));
        }

        Debug.Log("Counted " + enemies.Length);
    }
}
```

Name four costs, and rewrite it so nothing allocates per frame.

:::hint
Ask of each line: does it search, create something new, or do I/O, every frame? Then ask whether the value it computes changes every frame at all.
:::

:::solution
The four costs: `FindGameObjectsWithTag` searches the scene and allocates a new array every frame; the string concatenation creates a new string every frame; `GetComponent` runs once per enemy per frame; and `Debug.Log` every frame is slow and also allocates. The count only changes when an enemy appears or disappears, so make the enemies report that:

```csharp
// In EnemyAI
public static int Alive { get; private set; }
public static event System.Action<int> AliveChanged;

void OnEnable()  { Alive++; AliveChanged?.Invoke(Alive); }
void OnDisable() { Alive--; AliveChanged?.Invoke(Alive); }
```

```csharp
using TMPro;
using UnityEngine;

public class EnemyCounter : MonoBehaviour
{
    [SerializeField] TextMeshProUGUI label;

    void OnEnable() => EnemyAI.AliveChanged += Show;
    void OnDisable() => EnemyAI.AliveChanged -= Show;
    void Start() => Show(EnemyAI.Alive);

    void Show(int count) => label.SetText("Enemies: {0}", count);
}
```

TextMeshPro's `SetText` with a `{0}` placeholder formats the number without creating a new string. The pulsing color moves into `EnemyAI` itself, which already has its `SpriteRenderer` in a field. Profile again and `EnemyCounter` disappears from the GC Alloc list.
:::

### Exercise 6: Turn a playtest into a decision

You logged events during three playtests with `Debug.Log($"PLAYTEST {Time.time:F1} {eventName} {section}")` and copied the lines out of the Console. Count deaths per section and how many testers reached each checkpoint, then decide which section to change first.

:::hint
Split each line on spaces. Testers are separated by `start` lines. Count `death` lines by section, and count `checkpoint` lines by name.
:::

:::solution
```python run title="playtest.py"
log = """
PLAYTEST 0.0 start level
PLAYTEST 18.2 death teach
PLAYTEST 40.5 checkpoint cp1
PLAYTEST 61.0 death test
PLAYTEST 75.3 death test
PLAYTEST 92.8 death test
PLAYTEST 110.4 checkpoint cp2
PLAYTEST 131.9 death twist
PLAYTEST 0.0 start level
PLAYTEST 35.1 checkpoint cp1
PLAYTEST 58.7 death test
PLAYTEST 70.2 death test
PLAYTEST 81.6 death test
PLAYTEST 96.0 death test
PLAYTEST 101.3 quit test
PLAYTEST 0.0 start level
PLAYTEST 29.9 checkpoint cp1
PLAYTEST 66.4 checkpoint cp2
PLAYTEST 88.0 death twist
PLAYTEST 120.5 exit level
"""

deaths, checkpoints, quits, testers = {}, {}, [], 0
for line in log.strip().splitlines():
    _, time, event, where = line.split()
    if event == "start":
        testers += 1
    elif event == "death":
        deaths[where] = deaths.get(where, 0) + 1
    elif event == "checkpoint":
        checkpoints[where] = checkpoints.get(where, 0) + 1
    elif event == "quit":
        quits.append(where)

print("testers:", testers)
print("deaths by section:", deaths)
print("reached:", {cp: f"{n}/{testers}" for cp, n in checkpoints.items()})
print("quit in:", quits)
```

The test corridor causes 7 of the 10 deaths and the only quit, and one tester never got past it. That's the section to fix first, even though the twist room is meant to be harder. Make the pillar wider, or slow the drone there from 2 to 1.5, then test again with someone new and compare the counts.
:::

### Challenge: Three save slots

Let the player choose one of three save slots from a menu. Each slot button shows what's in it, like `Slot 2: cp2, 340 points, saved 14 Nov 18:05`, or `Slot 3: empty`.

:::hint
Give `SaveSystem` a `slot` parameter and build the file name (or `PlayerPrefs` key) from it, such as `save1.json`. `JsonUtility` can't serialize `DateTime`, so store the time as a string with `DateTime.Now.ToString("o")` and read it back with `DateTime.Parse`. Remember which slot is active with a static field, or in `PlayerPrefs` if it should survive a restart.
