"My random forest got 97% and my logistic regression got 96%, so the forest wins." Before you believe a sentence like that, ask three questions. Were both models scored on the same rows? Was the preprocessing refit inside each fold? Is a one-point gap bigger than the noise you measured last week? This week is about comparisons that survive those questions, and then about turning each model's knobs without fooling yourself.

## Three model families, three different bets

-   **Decision tree:** a flowchart of yes/no questions. Easy to explain, needs no scaling, and overfits readily, as last week's learning curves showed.
-   **Random forest:** a few hundred trees, each trained on a random resample of the rows and allowed to look at only a random subset of features at each split. Their votes are averaged, which cancels much of each tree's individual variance. Usually strong with default settings.
-   **Logistic regression:** a weighted sum of the features squashed into a probability. Fast, interpretable, and it gives sensible probabilities, but it needs scaled features and draws straight-line boundaries.

None of them is best in general. Your data decides, and cross-validation is how you ask it.

## A fair fight: same folds, same metric, same rules

Four rules make a comparison fair: **one `cv` object** shared by every model, **every preprocessing step inside a pipeline**, **one metric chosen before you look**, and **a baseline** so you know what "good" means. Here they are in code, using ROC AUC, which measures how well a model *ranks* positives above negatives (0.5 is coin-flipping, 1.0 is perfect):

```python run
import matplotlib.pyplot as plt
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.dummy import DummyClassifier
from sklearn.ensemble import RandomForestClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import StratifiedKFold, cross_val_score
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.tree import DecisionTreeClassifier

X, y = load_breast_cancer(return_X_y=True)
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=7)

models = {
    "baseline": DummyClassifier(strategy="prior"),
    "tree": Pipeline([("model", DecisionTreeClassifier(random_state=0))]),
    "forest": Pipeline([("model", RandomForestClassifier(random_state=0))]),
    "logistic": Pipeline([("scale", StandardScaler()),
                          ("model", LogisticRegression(max_iter=1000))]),
}
fold_scores = {}
for name, model in models.items():
    fold_scores[name] = cross_val_score(model, X, y, cv=cv, scoring="roc_auc")
    s = fold_scores[name]
    print(f"{name:>8}: {s.mean():.3f} ± {s.std():.3f}   folds {s.round(3)}")
```

Every model is wrapped in a `Pipeline` whose estimator step is called `"model"`, even the ones with nothing to preprocess. That consistent name pays off in a minute, when you start tuning.

Because the folds are shared, fold 3 for the forest and fold 3 for logistic regression contain exactly the same tumors. So compare them fold by fold:

```python run alt="Slope chart of ROC AUC across the five shared folds for tree, forest, and logistic regression. The tree's line sits far below, between about 0.88 and 0.95. The forest and logistic lines are both near 0.98 to 1.0, with logistic on top in most folds." caption="Paired scores: each x position is the same set of tumors for every model"
wins = (fold_scores["logistic"] > fold_scores["forest"]).sum()
print(f"logistic beats forest on {wins} of 5 folds")

plt.figure(figsize=(7, 3.2))
for name in ["tree", "forest", "logistic"]:
    plt.plot(range(1, 6), fold_scores[name], "o-", label=name)
plt.xticks(range(1, 6), [f"fold {i}" for i in range(1, 6)])
plt.ylabel("ROC AUC")
plt.legend()
```

Winning most of the paired matchups is stronger evidence than a gap between two means, because each matchup holds the data fixed and changes only the model. The single tree is clearly behind. Forest and logistic regression are close, so which one "wins" deserves a careful sentence, not a headline.

## Parameters are learned; hyperparameters are chosen

**Parameters** are what `fit` learns from data: a tree's split points, logistic regression's coefficients. **Hyperparameters** are the settings you pick before `fit` runs: `max_depth`, `n_estimators`, `C`. Tuning means searching for the hyperparameters with the best *cross-validated* score.

```mermaid caption="What a search's fit() does, whether it's a grid or random search"
flowchart TD
    S[Search space] --> G["Grid: every combination of the listed values"]
    S --> R["Random: n_iter draws from lists or distributions"]
    G --> CV["Cross-validate each setting on the shared folds"]
    R --> CV
    CV --> B["best_params_ = highest mean validation score"]
    B --> F["Refit that setting on all training rows: best_estimator_"]
```

## Grid search: try every combination

`GridSearchCV` takes a pipeline and a dictionary of values to try. Inside a pipeline, you name a hyperparameter as *step name*, two underscores, *parameter name*: `model__C` means "the `C` of the step called `model`." Notice the test set is split off first and never shown to the search.

```python run alt="Mean cross-validated ROC AUC against C on a log axis, with error bars. Scores are highest and tied near 0.996 at C = 0.1 and 1, slightly lower at 0.01, and fall to about 0.986 at C = 100." caption="A grid search is a validation curve that picks the winner for you"
from sklearn.model_selection import GridSearchCV, train_test_split

X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=0)

pipe = Pipeline([("scale", StandardScaler()),
                 ("model", LogisticRegression(max_iter=5000))])
grid = {"model__C": [0.01, 0.1, 1, 10, 100]}
search = GridSearchCV(pipe, grid, cv=cv, scoring="roc_auc")
search.fit(X_train, y_train)

means = search.cv_results_["mean_test_score"]
stds = search.cv_results_["std_test_score"]
print("best:", search.best_params_, f"CV AUC {search.best_score_:.4f}")

plt.figure(figsize=(7, 3))
plt.errorbar(grid["model__C"], means, yerr=stds, fmt="o-", capsize=4)
plt.xscale("log")
plt.xlabel("C (log scale)")
plt.ylabel("mean CV ROC AUC")
```

Three things happened. The search ran 5 settings × 5 folds = 25 fits. It picked the setting with the highest mean, breaking ties by taking the first one listed. Then, because `refit=True` by default, it retrained that setting on all of `X_train`, so `search` itself is now your tuned model, ready for `search.predict`. The error bars show that most of these settings are within one std of each other. The grid found a good region, not a magic number.

Here's the mistake almost everyone makes once:

```python run raises
GridSearchCV(pipe, {"C": [0.1, 1, 10]}, cv=cv).fit(X_train, y_train)
```

The pipeline has no `C`; its `model` step does. The message lists only the pipeline's own top-level settings (`memory`, `steps`, and so on). To see every name you can tune, including `model__C`, print `pipe.get_params().keys()`.

## Random search: sample instead of sweeping

Grids grow fast. Four hyperparameters with five values each is 625 settings, or 3,125 fits at five folds. `RandomizedSearchCV` draws a fixed number of settings, `n_iter`, from lists or probability distributions.

Here's the intuition for why that often works better. Usually only one or two hyperparameters really matter. A 3 × 3 grid tests just three distinct values of the important one, three times each. Nine random draws test nine distinct values of it:

```python run alt="Two square panels with the same 9-point budget over two hyperparameters. Left, a 3 by 3 grid whose points line up in only 3 columns along the important horizontal axis. Right, 9 random points spread across 9 different horizontal positions. Tick marks along the bottom of each panel show the distinct values tried." caption="Same budget, but random search tries 9 values of the parameter that matters instead of 3"
rng = np.random.default_rng(12)
grid_pts = np.array([(a, b) for a in (0.2, 0.5, 0.8) for b in (0.2, 0.5, 0.8)])
rand_pts = rng.uniform(0.05, 0.95, size=(9, 2))

fig, axes = plt.subplots(1, 2, figsize=(8, 3.6), sharey=True)
for ax, pts, title in [(axes[0], grid_pts, "grid: 3 distinct values"),
                       (axes[1], rand_pts, "random: 9 distinct values")]:
    ax.scatter(pts[:, 0], pts[:, 1], s=60)
    ax.plot(pts[:, 0], np.zeros(9), "|", color="C3", markersize=18)
    ax.set_xlim(0, 1)
    ax.set_ylim(-0.05, 1)
    ax.set_title(title)
    ax.set_xlabel("important hyperparameter")
axes[0].set_ylabel("unimportant hyperparameter")
```

Now let's use it for real on a random forest. `randint(50, 150)` draws whole numbers from 50 to 149; plain lists are sampled uniformly.

```python run
from scipy.stats import randint
from sklearn.model_selection import RandomizedSearchCV

forest_space = {
    "model__n_estimators": randint(50, 150),
    "model__max_depth": [None, 4, 8],
    "model__min_samples_leaf": randint(1, 8),
    "model__max_features": ["sqrt", 0.5],
}
forest_search = RandomizedSearchCV(
    Pipeline([("model", RandomForestClassifier(random_state=0))]),
    forest_space, n_iter=8, cv=cv, scoring="roc_auc", random_state=0)
forest_search.fit(X_train, y_train)
print("best:", forest_search.best_params_)
print(f"best CV AUC {forest_search.best_score_:.4f} after {8 * 5} fits + 1 refit")
```

For a hyperparameter that spans orders of magnitude, like `C`, sample with `scipy.stats.loguniform(1e-3, 1e2)` so that 0.001 to 0.01 gets as many draws as 10 to 100. Set `random_state` on the search so you can reproduce it.

## The winner's score is a little too good

Every search reports the best of many noisy scores, and the best of many noisy numbers is biased upward. You can see this with data where there is *nothing* to learn: random features and coin-flip labels. Any honest score should be 0.5.

```python run alt="Histogram of 40 cross-validated accuracies, one per tree setting, on coin-flip data. They spread from about 0.45 to 0.57 on both sides of a dashed line at the true 0.5. A red line marks the best setting's score, 0.567, at the far right." caption="Tuning on pure noise: the best of 40 settings still looks like skill"
rng = np.random.default_rng(0)
X_noise = rng.normal(size=(120, 10))
y_noise = rng.integers(0, 2, size=120)

noise_search = GridSearchCV(
    DecisionTreeClassifier(random_state=0),
    {"max_depth": [1, 2, 3, 4, 5, 6, 8, None], "min_samples_leaf": [1, 2, 5, 10, 20]},
    cv=StratifiedKFold(n_splits=5, shuffle=True, random_state=0))
noise_search.fit(X_noise, y_noise)

X_fresh = rng.normal(size=(2000, 10))
y_fresh = rng.integers(0, 2, size=2000)
print(f"best_score_ on noise: {noise_search.best_score_:.3f}")
print(f"same model on 2,000 fresh rows: {noise_search.score(X_fresh, y_fresh):.3f}")

plt.figure(figsize=(7, 2.8))
plt.hist(noise_search.cv_results_["mean_test_score"], bins=12, color="#9aa9c7", edgecolor="white")
plt.axvline(0.5, color="black", linestyle="--", label="truth: 0.5")
plt.axvline(noise_search.best_score_, color="C3", label="best_score_")
plt.xlabel("mean CV accuracy of each of the 40 settings")
plt.legend()
```

The best setting "scores" above 0.5 on labels that are pure chance, then falls back to about 0.5 on fresh rows. On real data the effect is smaller, but it's always there, and it grows with the number of settings you try. Two defenses:

-   **The test set, used once.** It played no part in the search, so its score is unbiased. That's the number to report.
-   **Nested cross-validation.** Put the entire search inside an outer CV loop. The inner folds tune; the outer folds score the tuned model on rows the search never saw.

```python run
inner = StratifiedKFold(n_splits=3, shuffle=True, random_state=1)
outer = StratifiedKFold(n_splits=5, shuffle=True, random_state=2)
tuned_logistic = GridSearchCV(pipe, grid, cv=inner, scoring="roc_auc")
nested = cross_val_score(tuned_logistic, X, y, cv=outer, scoring="roc_auc")
print(f"nested CV AUC: {nested.mean():.4f} ± {nested.std():.4f}")
print(f"test AUC of the grid search above (used once): {search.score(X_test, y_test):.4f}")
```

Nested CV estimates how well the *whole procedure* (search, then refit) works on new data. It doesn't hand you a single final model; it tells you how much to trust the one you'll build. It costs folds × settings × inner folds fits, so save it for small datasets and final comparisons.

:::warning
**Three ways tuning goes wrong.**
1. Tuning with the test set. If any search or comparison looks at `X_test`, its score is no longer an honest estimate.
2. A best value at the edge of the range. If the best `C` is the largest one you tried, the real best may be beyond it. Extend the range and search again.
3. Comparing models on different folds. Re-shuffling the folds alone can move a score by a point, which is often the whole "improvement."
:::

:::quiz
Q: After a grid search, `best_params_` is `{"model__C": 100}`, and 100 is the largest value in your grid. What should you do?
- [ ] Report C = 100 as the optimum
  You only know 100 beat the smaller values. Something larger might be better still.
- [x] Extend the grid past 100 and search again
  A best value at the edge of the range means the search may have stopped too early. Push the boundary until the best sits inside it.
- [ ] Switch to the test set to decide
  The test set must stay out of every choice, including this one.

Q: With a budget of 25 settings and four hyperparameters, of which only one really matters, why might random search beat a 5 × 5 × ... grid?
- [ ] Random search uses a smarter optimizer
  It doesn't. It just samples settings at random.
- [x] It tries many more distinct values of the hyperparameter that matters
  A grid repeats the same few values of each parameter across combinations; random draws spread across the whole range.
- [ ] Random search trains fewer models per setting
  Both use the same folds for each setting, so the per-setting cost is identical.

Q: Forest: 0.987 ± 0.010. Logistic: 0.995 ± 0.005. Same five folds, and logistic wins 4 of them. Which summary is fairest?
- [ ] Logistic is far better
  An 0.008 gap is about one forest std. "Far" overstates it.
- [x] Logistic is ahead consistently but narrowly; it's also simpler and faster
  Winning 4 of 5 paired folds is real evidence, and the size of the gap is small. Saying both is honest.
- [ ] They're identical, so the result is meaningless
  A consistent fold-by-fold edge is information, even when it's small.

Q: Your search tried 60 settings and `best_score_` is 0.91. The test set, used once, gives 0.88. What's the most likely explanation?
- [x] `best_score_` is the best of 60 noisy scores, so it runs high; 0.88 is the honest number
  Picking the maximum adds upward bias, and test-set noise adds a little more. Report 0.88.
- [ ] The test set must be corrupted
  A few points below the best CV score is expected after a big search.
- [ ] You should keep searching until the test score reaches 0.91
  That turns the test set into part of the search and destroys the honest estimate.
:::

:::takeaways
- Fair comparisons share one `cv` object, keep preprocessing in pipelines, fix the metric in advance, and include a baseline.
- With shared folds, compare models fold by fold; consistent wins are stronger evidence than a gap in means.
- In a pipeline, hyperparameters are named `step__param`; `pipe.get_params()` lists them.
- Grid search tries every combination; random search samples `n_iter` settings and usually covers the important hyperparameter better for the same cost.
- `best_score_` is optimistic because it's a maximum. Report the test score (used once) or nested CV instead.
:::
