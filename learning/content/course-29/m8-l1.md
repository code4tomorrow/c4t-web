Most machine learning projects end with a model. Yours ends with a **verdict**: a report that tells a reader whether a model is good enough to use, how sure you are, where it fails, and what it should never be used for. The model is part of the evidence. The reasoning is what you're graded on.

## The brief

Choose a public or bundled classification dataset and produce a notebook plus a short written report that includes:

1.  **A clear decision.** Who would use the model, and what action does a prediction trigger?
2.  **A baseline.** A `DummyClassifier` scored with the same folds and metrics as everything else.
3.  **At least two tuned models** from different families (for example, logistic regression and a random forest), each inside a leak-free `Pipeline` and tuned with `GridSearchCV` or `RandomizedSearchCV`.
4.  **Cross-validated metrics** reported as mean ± std, on shared folds, using metrics that suit your class balance.
5.  **A justified threshold**, chosen from out-of-fold training predictions using a stated rule: a recall target, a precision floor, a cost table, or best F1.
6.  **One held-out test evaluation**, done once, at the end.
7.  **Slice-based error analysis.** At least one feature bucketed into groups, with error counts and rates per group.
8.  **A written recommendation with limitations.** Use, don't use, or use with conditions, and what you didn't test.

You have three weeks: planning now, building in milestones next, then checking and presenting.

## Picking a dataset

A good capstone dataset has a few hundred rows or more, a target you can explain in one sentence, and at least one feature that makes a meaningful slice (size, age, region, amount). Run this quick scout on the bundled candidates to compare their sizes and class balance:

```python
import numpy as np
from sklearn.datasets import load_breast_cancer, load_digits, load_wine

candidates = {}

bc = load_breast_cancer()
candidates["breast cancer (malignant=1)"] = (bc.data, (bc.target == 0).astype(int))

wine = load_wine()
candidates["wine (3 cultivars)"] = (wine.data, wine.target)

digits = load_digits()
candidates["digits (is it a 9?)"] = (digits.data, (digits.target == 9).astype(int))

print(f"{'dataset':<28} {'rows':>5} {'feats':>5}  class counts")
for name, (X, y) in candidates.items():
    counts = np.bincount(y)
    smallest = counts.min() / counts.sum()
    print(f"{name:<28} {X.shape[0]:>5} {X.shape[1]:>5}  {counts.tolist()}  smallest {smallest:.1%}")
```

```text
dataset                       rows feats  class counts
breast cancer (malignant=1)    569    30  [357, 212]  smallest 37.3%
wine (3 cultivars)             178    13  [59, 71, 48]  smallest 27.0%
digits (is it a 9?)           1797    64  [1617, 180]  smallest 10.0%
```

Ideas, roughly from easier to harder:

-   **Breast cancer screening** (`load_breast_cancer`). Binary, mildly imbalanced, with natural slices by tumor size or texture. A strong default if you're unsure. Use a different slice and threshold rule than the class examples.
-   **"Is it a 9?" detector** (`load_digits`, target `== 9`). Turning ten classes into one-vs-rest gives you a real 10% imbalance. Slice by ink amount (the sum of pixel values) or by which digit a false alarm actually was.
-   **Wine cultivar classifier** (`load_wine`). Three classes, so you'll use macro F1 and per-class recall. It's small, which makes the ± std discussion interesting. For the threshold, describe how you'd handle low-confidence predictions (for example, "send to a human if the top probability is below 0.6").
-   **Synthetic rare-event detector** (`make_classification` with `weights=[0.97, 0.03]`). You control the imbalance exactly, but the features have no real meaning, so your slices and limitations must say so. Best for students who want to dig into threshold and cost analysis.
-   **Public OpenML datasets** via `sklearn.datasets.fetch_openml`, which needs an internet connection the first time. Examples: `"credit-g"` (good vs. bad credit, 30% bad) or `"diabetes"` (the Pima diabetes data, 35% positive). These have categorical features or messy values, so you'll use the `ColumnTransformer` and `SimpleImputer` skills from earlier weeks. Pass `as_frame=True` and check the target column's name and values before you do anything else.

:::warning
Avoid datasets where a feature *is* the answer in disguise, such as an ID that was assigned after diagnosis or a "follow-up date" that only exists for positive cases. If one feature gets near-perfect accuracy by itself, suspect leakage before you celebrate.
:::

## Write the plan before the code

Spend this session on a one-page plan. Fill in every line. A blank line now usually means a stuck afternoon later.

```text
CAPSTONE PLAN
Dataset and source:
Target (what does 1 mean?):
Who uses the model and what happens after a positive prediction?
Which mistake is worse, a false negative or a false positive? Why?
Primary metric (and why it fits the class balance):
Secondary metrics:
Threshold rule (recall >= __ / precision >= __ / cost FN:FP = __ / best F1):
Baseline:
Model family 1 + hyperparameters to search:
Model family 2 + hyperparameters to search:
CV scheme (folds, shuffle, random_state):
Test set size:
Slice feature(s) and why they might matter:
One risk I already suspect:
```

A few guidelines for the hardest lines:

-   **Primary metric.** For balanced data, accuracy or ROC AUC is fine for comparing models. For a 10% positive class, prefer average precision or F1, and always show recall. For multiclass, use macro F1.
-   **Threshold rule.** Tie it to the decision. "A specialist reviews every flag, so I want recall ≥ 0.98" is a rule. "0.3 looked good" is not.
-   **Slice features.** Pick something a real user would care about. A slice that reveals nothing is still a valid result: "error rates were similar across all three size groups" is a finding.

## Budget your compute

Count fits before you launch a search. Settings × folds + 1 refit, as in Week 5. A random forest with 300 trees on a few thousand rows is fine for 10–20 random-search iterations in Colab. A 500-setting grid is not. If a search takes more than a few minutes, lower `n_iter` or `n_estimators` while you develop, and save the larger run for the end.
