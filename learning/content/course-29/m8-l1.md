Most machine learning projects end with a model. Yours ends with a **verdict**: a report that tells a reader whether a model is good enough to use, how sure you are, where it fails, and what it must never be used for. The model is evidence. The reasoning is what you're graded on.

## The brief

Choose a public or bundled classification dataset and produce a notebook plus a one-page written report that includes:

1.  **A clear decision.** Who would use the model, and what action does a positive prediction trigger?
2.  **A baseline.** A `DummyClassifier` scored on the same folds and metric as everything else (Week 1).
3.  **At least two tuned models** from different families, each in a leak-free `Pipeline` (Week 2), tuned with `GridSearchCV` or `RandomizedSearchCV` (Week 5).
4.  **Cross-validated metrics** as mean ± std on shared folds (Week 4), using metrics that suit your class balance (Weeks 3 and 6).
5.  **A justified threshold**, chosen from out-of-fold training predictions with a stated rule (Week 6).
6.  **One held-out test evaluation**, done once, at the end.
7.  **Slice-based error analysis**: at least one feature bucketed into groups, with error counts and rates.
8.  **A written recommendation with limitations**: use, don't use, or use with conditions, and what you didn't test.

```mermaid caption="The capstone, end to end: everything before the test set happens on training data"

You have three sessions: plan today, build in milestones next week, then check, polish, and present.

## Choosing a dataset

A good capstone dataset has a few hundred rows or more, a target you can explain in one sentence, and at least one feature that makes a meaningful slice: size, age, region, amount. Scout the bundled candidates first. The number to watch is the share of the smallest class, because it decides your metric.

```python run alt="Horizontal bar chart of the smallest class's share for four candidate datasets: breast cancer about 37%, wine about 27%, digits 'is it a 9' about 10%, and the synthetic rare-event set about 3.5%." caption="Class balance decides your metric before anything else does"
import matplotlib.pyplot as plt
import numpy as np
from sklearn.datasets import load_breast_cancer, load_digits, load_wine, make_classification

bc, wine, digits = load_breast_cancer(), load_wine(), load_digits()
X_rare, y_rare = make_classification(n_samples=4000, weights=[0.97, 0.03], random_state=0)
candidates = {
    "breast cancer (malignant = 1)": (bc.data, (bc.target == 0).astype(int)),
    "wine (3 growers)": (wine.data, wine.target),
    "digits: is it a 9?": (digits.data, (digits.target == 9).astype(int)),
    "synthetic rare event": (X_rare, y_rare),
}
shares = {}
print(f"{'dataset':<30} {'rows':>5} {'feats':>5}  class counts")
for name, (X, y) in candidates.items():
    counts = np.bincount(y)
    shares[name] = counts.min() / counts.sum()
    print(f"{name:<30} {X.shape[0]:>5} {X.shape[1]:>5}  {counts.tolist()}")

plt.figure(figsize=(7, 2.6))
plt.barh(list(shares), list(shares.values()), color="#7f9cc9")
plt.gca().invert_yaxis()
plt.xlabel("share of the smallest class")
```

Project ideas, roughly from easier to harder:

-   **Breast tumor screening** (`load_breast_cancer`). Binary, mildly imbalanced, with natural slices by size or texture. A safe default, but use a different slice feature and threshold rule from the class examples.
-   **"Is it a 9?" detector** (`load_digits`, target `== 9`). Turning ten classes into one-versus-rest gives you a real 10% imbalance. Slice by total ink (the sum of the pixel values) or by which digit the false alarms really were.
-   **Wine grower classifier** (`load_wine`). Three classes, so you'll use macro F1 and per-class recall. It's small, which makes the ± std discussion interesting. Instead of a threshold, design a "send to a human" rule for low-confidence predictions, such as a top probability below 0.6.
-   **Synthetic rare-event detector** (`make_classification` with `weights=[0.97, 0.03]`). You control the imbalance exactly, so it's the best choice if you want to go deep on thresholds and costs. The features mean nothing, and your limitations section must say so.
-   **A real public dataset** from OpenML, loaded in Colab with `fetch_openml("credit-g", as_frame=True)` (good versus bad credit, 30% bad) or `fetch_openml("diabetes", version=1, as_frame=True)` (the Pima diabetes data, about 35% positive). These have text categories or odd values, so you'll use `ColumnTransformer`, `OneHotEncoder`, and `SimpleImputer`. Print the target's name and values before anything else; OpenML targets are often strings like `"good"` and `"bad"`.

:::warning
Watch for a feature that *is* the answer in disguise: an ID assigned after diagnosis, a "follow-up date" that only exists for positive cases, a column computed from the target. If one feature alone scores near-perfectly, suspect leakage before you celebrate. You'll run a formal check for this in the final week.
:::

## From use case to metric and threshold rule

Your primary metric and threshold rule should follow from the decision, not from whichever number looks best. Andrew Ng's advice is to pick one number to optimize so you can compare models quickly:

:::video sofffBNhVSo
What to watch for: why a single evaluation number speeds up decisions, and his example of averaging per-region errors, which is the same idea as macro F1.
:::

A quick guide:

| Situation | Primary metric for comparing models | Threshold rule |
| --- | --- | --- |
| Balanced binary, mistakes cost about the same | accuracy or ROC AUC | best F1 or 0.5 |
| Rare positive class, a human checks every flag | average precision | recall ≥ a target, best precision |
| Rare positive class, every flag is expensive | average precision | precision ≥ a floor, best recall |
| You can put a price on each mistake | average precision | minimize the cost table |
| Three or more classes | macro F1 | per-class review or a confidence cut-off |

## Budget your compute before you search

Every search costs settings × folds fits, plus one refit. Measure one fit and multiply, instead of discovering in class that a search takes forty minutes:

```python run
import time
from sklearn.ensemble import RandomForestClassifier

X, y = candidates["digits: is it a 9?"]
start = time.perf_counter()
RandomForestClassifier(n_estimators=200, random_state=0).fit(X, y)
one_fit = time.perf_counter() - start


def budget(settings, folds=5, seconds_per_fit=one_fit):
    fits = settings * folds + 1
    return f"{settings} settings: {fits} fits, about {fits * seconds_per_fit / 60:.1f} minutes"


print(f"one 200-tree forest on {len(y)} digits: {one_fit:.2f} s")
for settings in [10, 30, 100]:
    print(budget(settings))
```

The time you see depends on the computer, and Colab's free machines are usually slower than a laptop. While you're developing, keep `n_iter` and `n_estimators` small; raise them once for the final run.

## Write the plan before the code

Spend the rest of this session on a one-page plan. Fill in every line. A blank line today usually turns into a stuck afternoon next week.

```text
CAPSTONE PLAN
Dataset and source:
Target (what does 1 mean?):
Who uses the model, and what happens after a positive prediction?
Which mistake is worse, a false negative or a false positive? Why?
Primary metric (and why it fits the class balance):
Secondary metrics:
Threshold rule (recall >= __ / precision >= __ / cost FN:FP = __ / best F1):
Baseline:
Model family 1 + hyperparameters to search:
Model family 2 + hyperparameters to search:
CV scheme (folds, shuffle, random_state):
Test set size:
Slice feature(s) and why they might matter:
Compute budget (settings x folds x seconds per fit):
One risk I already suspect:
```

Three lines deserve extra care:

-   **Threshold rule.** Tie it to the decision. "A specialist reviews every flag, so recall must be at least 0.98" is a rule. "0.3 looked good" is not.
-   **Slice features.** Choose something a real user would care about. A slice that shows no difference is still a finding: "error rates were similar across all three size groups" tells the reader the model is even-handed on that feature.
-   **One risk I already suspect.** Writing down a doubt now (a small positive class, a feature that might leak, data from one source) gives you a head start on the limitations section.

:::quiz
Q: Which of these is a usable threshold rule for a capstone plan?
- [ ] "Use whatever threshold gives the best test-set F1"
  That chooses the threshold with the test set, which leaks.
- [x] "Every flag is reviewed by a nurse, so catch at least 95% of positives and maximize precision"
  It names the decision, the requirement, and what to optimize once the requirement is met.
- [ ] "0.3, because it looked good in a chart"
  A number without a reason can't be defended or reproduced.

Q: Your positive class is 4% of the rows. Which primary metric should you compare models with?
- [ ] Accuracy
  A model that never predicts positive already scores 96%.
- [x] Average precision, with recall reported alongside
  Average precision measures ranking of the rare class across thresholds, and its floor is the 4% positive rate, so it's hard to flatter.
- [ ] Training accuracy
  Training scores measure memorization, not performance on new data.

Q: One feature, `days_in_followup`, gets 0.99 ROC AUC on its own. What's your first move?
- [x] Ask whether that value exists at prediction time, because it may be recorded only after diagnosis
  A feature that's available only after the outcome is known leaks the answer, and the model would fail in real use.
- [ ] Celebrate and build the model on that feature
  A near-perfect single feature is far more often leakage than a breakthrough.
- [ ] Drop all the other features
  That doubles down on the suspicious feature instead of checking it.
:::

## What "done" looks like

Someone who has never seen your notebook can read your one-page report and answer three questions: should this model be used, under what conditions, and what could go wrong? If they can, you've done the job.
