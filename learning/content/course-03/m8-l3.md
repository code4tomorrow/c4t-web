Your app works when you use it. Unfortunately, that's the weakest test there is, because you know exactly what it expects. Hand it to a friend and within a minute they'll press Enter on an empty line, type `TWELVE`, or answer a yes-or-no question with `maybe`. This lesson is about finding those cracks before anyone else does, then presenting the result.

## Step 1: Build a test table

A test table lists what you'll type, what *should* happen, and what *did* happen. Fill in the "should happen" column before you run anything, or you'll be tempted to decide the program's behavior was correct after seeing it. Cover each of these kinds of input:

-   **Normal**: the things a user is supposed to type.
-   **Empty**: just pressing Enter.
-   **Wrong type**: a word where a number belongs, or a number where a word belongs.
-   **Messy formatting**: capitals, extra spaces, `$` signs.
-   **Boundaries**: the smallest and largest allowed values, and one step past each.
-   **Order and repetition**: doing something twice, or out of order.
-   **Leaving early**: quitting at the first prompt, in the middle, and at the end.

Here are the first rows for Escape the Lab from the last lesson:

| # | Kind | What I typed | What should happen | What happened | Pass? |
| --- | --- | --- | --- | --- | --- |
| 1 | Normal | `go north` in the lab | move to the hall and describe it | as expected | yes |
| 2 | Empty | Enter | "I don't understand that." | as expected | yes |
| 3 | Messy | `  GO   North ` | same as `go north` | as expected | yes |
| 4 | Missing part | `go` | "Go where? Try: go north" | as expected | yes |
| 5 | Wrong type | `four` at the keypad | digits hint, then ask again | as expected | yes |
| 6 | Repetition | `take` twice in the storeroom | the second time: "nothing here to take" | as expected | yes |
| 7 | Boundary | `99999999999` at the keypad | "Wrong code" | as expected | yes |
| 8 | Leaving early | `quit` as the first command | a goodbye message, no traceback | as expected | yes |

Aim for at least 12 rows, and make sure every `input()` in your program appears somewhere in the table. When a row fails, don't just fix it: keep the row, so you can check later changes haven't broken it again.

## Step 2: Let Python check your functions

Functions that take values and return a result can be tested automatically, which is much faster than typing the same inputs over and over. A tiny helper prints `PASS` or `FAIL` for each check. Here it's testing an early version of `split_command`, before the `.strip().lower()` cleanup was added:

```python run title="test_lab.py"
def split_command(text):
    words = text.split(" ")
    if len(words) == 1:
        return [words[0], ""]
    return [words[0], words[1]]


def check(label, actual, expected):
    if actual == expected:
        print("PASS", label)
    else:
        print("FAIL", label, "| expected", expected, "but got", actual)


check("normal", split_command("go north"), ["go", "north"])
check("one word", split_command("look"), ["look", ""])
check("capitals and spaces", split_command("  GO   North "), ["go", "north"])
check("empty line", split_command(""), ["", ""])
check("extra words", split_command("go north now"), ["go", "north"])
```

One failure, and the output says exactly what went wrong. `split(" ")` splits at *every* single space, so leading spaces produce empty strings. (The "empty line" test passed by luck, which is worth knowing too.) Switching to `text.strip().lower().split()`, which splits on any run of spaces and ignores spaces at the ends, makes all five pass. Keep `test_lab.py` next to your project and run it after every change.

Python also has a built-in one-line check, `assert`. It does nothing if the condition is `True` and stops the program with an `AssertionError` if it's `False`:

```python run raises title="test_percent.py"
def percent(part, whole):
    return round(part / whole * 100)

assert percent(1, 4) == 25
assert percent(1, 2) == 50
assert percent(2, 3) == 66
print("All percent tests passed")
```

The third check failed. But look closer: 2 out of 3 is 66.7%, which rounds to 67. The **test** was wrong, not the code. When a test fails, ask which one is mistaken before you change anything.

## Step 3: Throw nasty input at your validators

Your validation functions are the front door of your app, so test them hardest. The `input=` trick you've seen all course works for this too: feed a list of strange answers and watch what gets through.

```python run title="test_ask_number.py" input="|seven|  7 |-1|1e3|nan|250"
def ask_number(prompt, low, high):
    """Ask until the user types a number from low to high; return it as a float."""
    while True:
        text = input(prompt).strip()
        try:
            number = float(text)
        except ValueError:
            print("  Please type a number.")
            continue
        if low <= number <= high:
            return number
        print(f"  Please pick a number from {low} to {high}.")

print("Got", ask_number("Amount: ", 0, 500))
print("Got", ask_number("Amount: ", 0, 500))
```

Two surprises. `float()` understands `1e3` (scientific notation for 1000) and even `nan` ("not a number"). Here the range check happens to reject both, but if your range went up to 5000, `1e3` would sail through as 1000. That's not necessarily a bug, but now you *know*, and you can decide. Tests that teach you something about your own code are the most valuable kind.

## Step 4: Polish

Polish is what makes an app feel finished. Work down this list with your code open:

-   **Names.** Every variable and function name says what it holds or does. Rename `x`, `thing`, and `data2`.
-   **Docstrings.** Every function has one. If a function is longer than about 25 lines, it's probably doing two jobs; split it.
-   **Constants.** Fixed numbers and settings live at the top in capitals (`DOOR_CODE`, `ROUNDS`), not scattered through the code.
-   **Comments.** Explain *why*, not *what*. `# 21.0975 km is a half marathon` helps; `# set x to 5` doesn't.
-   **Messages.** Every hint tells the user what to type instead. Spelling and punctuation are consistent.
-   **Leftovers.** Delete debugging `print` lines and commented-out experiments.
-   **Fresh start.** Press **Stop** (or **Ctrl+F2**) to restart Thonny's Shell, then run with **F5**. This catches code that only worked because of a variable left over from an earlier run.

Here's the kind of change polish makes:

```diff
-def f(m, s):
-    return m * 60 + s
+def to_seconds(minutes, seconds):
+    """Combine minutes and seconds into a total number of seconds."""
+    return minutes * 60 + seconds
```

## Step 5: Write a README

A README is a short text file that tells someone what your app is and how to use it. Save this as `README.txt` next to your `.py` file and fill it in:

```text
PROJECT NAME
by Your Name

WHAT IT IS
One or two sentences: what it does and who it's for.

HOW TO RUN IT
Open project.py in Thonny and press F5 (or click Run).

HOW TO USE IT
The commands or menu choices, and what each one does.

EXAMPLE
Five to ten lines copied from a real session.

WHAT I'M PROUD OF
One feature or piece of code, and why.

A BUG I FIXED
What happened, what the error said, and how I found the cause.

WHAT I'D ADD NEXT
Two or three ideas.
```

## Step 6: Present it in two minutes

A good demo has a plan. Practice it once out loud with a timer.

| Time | What to show |
| --- | --- |
| 0:00–0:15 | What the app is and who it's for, in one or two sentences |
| 0:15–1:00 | A normal run of the main feature |
| 1:00–1:30 | Try to break it live: empty input, a word instead of a number, quitting early |
| 1:30–2:00 | One piece of code you're proud of, and one bug you fixed |

The "try to break it" part impresses people far more than a perfect run, because it shows you thought about real users.

## The rubric

Score yourself honestly before you hand in. Each row is worth up to 4 points, for 24 in total.

| Criterion | 4: Excellent | 3: Good | 2: Developing | 1: Beginning |
| --- | --- | --- | --- | --- |
| **It works** | Runs start to finish; no test input causes a traceback | Runs; one rare input crashes | Main feature works, but other parts crash | Doesn't run, or the main feature is missing |
| **Requirements** | All eight from the brief, each used where it makes sense | Seven of eight | Five or six | Four or fewer |
| **Validation and errors** | Every input is validated, with `try`/`except` wherever text becomes a number, and every hint is helpful | Most inputs validated; hints are clear | Some inputs validated | Little or no validation |
| **Code organization** | At least four functions with docstrings and return values; short main loop; clear names and constants | Functions used well, a few long or unclear spots | Some functions, but most code is in one block | One long block of code |
| **Testing** | A test table of 12+ rows covering every kind of input, plus automatic checks | 8 to 11 rows, most kinds covered | A few rows | No test evidence |
| **Communication** | Complete README; clear two-minute demo that explains a bug fix | README and demo with small gaps | README or demo missing parts | Neither |

## What to learn next

You can now write complete programs that take input, make decisions, repeat work, recover from bad input, and organize themselves into functions. Here's where those skills lead:

-   **Save data between runs.** Right now your high scores and budgets vanish when the program ends. Files fix that: `open()`, `write()`, and `read()` are a short step from what you know.
-   **Draw with code.** The `turtle` module comes with Python and turns loops and functions into drawings and simple games.
-   **Make real games.** Pygame Zero lets you write arcade-style games in plain Python. Install the `pgzero` package with Thonny's **Tools › Manage packages...**, then switch on **Run › Pygame Zero mode**.
-   **Model bigger things.** When your dictionaries start needing their own functions, you're ready for **classes**, Python's way of bundling data and the functions that work on it.

Q: Why fill in the "what should happen" column *before* running your tests?
- [x] So you judge the program against what you intended, not against whatever it happened to do
  Once you've seen the output, it's easy to convince yourself it was correct all along.
- [ ] Because Thonny needs the table to run the program
  Thonny doesn't read your test table; it's for you.
- [ ] It saves time
  It's about honest results, not speed.

Q: `assert percent(2, 3) == 66` fails with an `AssertionError`. What should you do first?
- [ ] Change `percent` until the assert passes
  That could break a function that was right all along.
- [x] Work out the correct answer by hand to see whether the test or the code is wrong
  2 out of 3 is 66.7%, which rounds to 67, so here the test needs fixing.
- [ ] Delete the assert
  A failing test is information; deleting it throws that away.

Q: Which test row is most likely to find a crash in a validated menu?
- [ ] Typing a correct menu choice
  That's the case you've already tried a dozen times.
- [x] Pressing Enter on an empty line, then typing the choice in capitals with spaces
  Empty and messy input are the cases beginners most often forget to handle.
- [ ] Running the program twice
  Running it again repeats the same behavior unless the inputs change.
:::

:::takeaways
- Test with normal, empty, wrong-type, messy, boundary, repeated, and early-exit inputs, and write the expected result first.
- Automatic checks (`check` helpers or `assert`) make retesting your functions instant.
- When a test fails, decide whether the code or the test is wrong before changing anything.
- Polish names, docstrings, constants, comments, and messages so a stranger can use and read your app.
- A README and a short demo that includes breaking the app on purpose show what you built and how well you built it.
:::
