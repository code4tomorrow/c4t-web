A phone game promises a bonus life when you reach 1000 points. A player scores exactly 1000:

```python run title="bonus_life.py"
score = 1000
if score > 1000:
    print("Bonus life!")
print("Score:", score)
```

No bonus life. The rule said *reach* 1000, but the code checks for *more than* 1000, and those disagree at exactly one number. Players at 999 and 1001 get the right result; only the player sitting on the line gets cheated. Most decision bugs look like this: one character wrong, at the edge. By the end of this page you'll know how to write the decision and how to catch the bug before a player does.

## Seven ways to do arithmetic

You know `+`, `-`, and `*`. Python has four more, and two of them come as a pair. Here they are with 23 students and vans that hold 7:

| Operator | Name | With 23 and 7 | What it's for |
| --- | --- | --- | --- |
| `/` | division | `3.2857…` | An exact answer, always a float |
| `//` | floor division | `3` | How many *whole* groups fit |
| `%` | remainder (modulo) | `2` | What's left over after the whole groups |
| `**` | power | `23 ** 2` is `529` | Squares, cubes, compound growth |

```python run title="vans.py"
students = 23
seats = 7
print(students / seats)
print(students // seats)
print(students % seats)
```

Here's the intuition for the pair: deal 23 students into vans of 7. You fill `23 // 7` = 3 vans and have `23 % 7` = 2 students standing on the curb. Every time you see "how many full ones, and how many left over" (eggs in cartons, minutes in an hour, items per page), reach for `//` and `%` together.

`%` has a second job you'll use constantly: `n % 2` is 0 when `n` is even and 1 when it's odd, and more generally `n % k == 0` means `n` divides exactly by `k`.

### Which operation happens first

Python follows the same order as math class: `**` first, then `*`, `/`, `//`, and `%`, then `+` and `-`. Operations at the same level go left to right. This catches people out when averaging:

```python run title="average.py"
quiz1 = 90
quiz2 = 80
print(quiz1 + quiz2 / 2)
print((quiz1 + quiz2) / 2)
```

The first line divides only `quiz2` by 2 and then adds 90, giving 130.0. Brackets force the addition to happen first. If you're ever unsure, add brackets: they never hurt, and they make your meaning obvious to the next reader.

## Comparisons answer True or False

A **comparison** asks a question about two values and the answer is always a `bool`:

| Operator | Asks | Example | Result |
| --- | --- | --- | --- |
| `==` | equal? | `5 == 5.0` | `True` |
| `!=` | not equal? | `"Owl" != "owl"` | `True` |
| `<`, `>` | less than, greater than | `999 > 1000` | `False` |
| `<=`, `>=` | less/greater than *or equal* | `1000 >= 1000` | `True` |

Two things to notice. Text comparison is exact, so `"Owl" == "owl"` is `False`; that's why Module 3 had you `.lower()` answers before checking them. And Python lets you chain comparisons the way you'd write them in math: `13 <= age <= 19` is `True` for teenagers.

The single `=` stores a value and the double `==` compares, and mixing them up is a mistake everyone makes once:

```python run raises
score = 1000
if score = 1000:
    print("Bonus life!")
```

Python even suggests the fix in the message.

## if: run some lines only when something is true

An `if` statement has a condition, a colon, and an **indented block** underneath. The block runs only when the condition is `True`. The first line that isn't indented runs either way. The vans need one extra van when there are leftovers:

```python run title="vans_needed.py"
students = 23
seats = 7
vans = students // seats
if students % seats > 0:
    vans += 1
print("Vans needed:", vans)
```

The indentation *is* the grammar: it's how Python knows which lines belong to the `if`. Use 4 spaces. Thonny adds them for you when you press Enter after a colon. Forget them and the program won't start:

```python run raises
uv = 9
if uv >= 8:
print("Very high")
```

## elif and else: pick exactly one path

The UV index tells you how strong the sun is. The World Health Organization's bands are 0 to 2 low, 3 to 5 moderate, 6 to 7 high, 8 to 10 very high, and 11 or more extreme. A chain of `if`, `elif` ("else if"), and `else` picks one message:

```python run title="uv_advice.py" input="9"
uv = int(input("UV index today: "))
if uv >= 11:
    print("Extreme: stay in the shade around midday.")
elif uv >= 8:
    print("Very high: sunscreen, hat, and shade.")
elif uv >= 6:
    print("High: sunscreen and a hat.")
elif uv >= 3:
    print("Moderate: sunscreen if you're out for long.")
else:
    print("Low: no special protection needed.")
```

Here's the precise rule. Python tests the conditions from the top down. The **first** one that's `True` gets its block run, and every branch below it is skipped, even ones that would also be true. If none is true, `else` runs. Step through it with a UV index of 9 and watch which lines get visited:

:::trace Python stops checking at the first true condition
```python input="9"
uv = int(input("UV index today: "))
if uv >= 11:
    print("Extreme")
elif uv >= 8:
    print("Very high")
elif uv >= 6:
    print("High")
elif uv >= 3:
    print("Moderate")
else:
    print("Low")
print("Done")
```
:::

Nine is also `>= 6` and `>= 3`, but those lines are never checked. That's why **order matters**. Put the checks the other way round and the program breaks:

```python run title="uv_wrong_order.py"
uv = 9
if uv >= 3:
    print("Moderate")
elif uv >= 8:
    print("Very high")
else:
    print("Low")
```

`9 >= 3` is true, so the first branch wins and "Very high" can never be reached by anyone. With `>=` chains, start from the highest cutoff and work down.

```mermaid caption="An elif chain: the first true condition wins, and the rest are skipped"
flowchart TD
    A["Read uv"] --> B{"uv >= 11?"}
    B -->|yes| X["Extreme"]
    B -->|no| C{"uv >= 8?"}
    C -->|yes| Y["Very high"]
    C -->|no| D{"uv >= 6?"}
    D -->|yes| Z["High"]
    D -->|no| E["...and so on, down to else"]
```

## and, or, not: combine conditions

Real rules often have several parts. A school study room is open every day except Sunday, from 8:00 until 21:00:

```python run title="study_room.py"
day = "Saturday"
hour = 19
if day != "Sunday" and 8 <= hour < 21:
    print("The study room is open.")
else:
    print("The study room is closed.")
```

-   `and` is `True` only when **both** sides are true.
-   `or` is `True` when **at least one** side is true.
-   `not` flips `True` to `False` and back, so `not is_member` means "isn't a member".

:::try
Change `hour` to `21`, then to `8`, then change `day` to `"Sunday"`. Predict each result before you run it. Is the room open at 21:00 exactly?
:::

Now the trap. This looks like it checks for the weekend:

```python run title="weekend_bug.py"
day = "Tuesday"
if day == "Saturday" or "Sunday":
    print("Weekend!")
```

It says Tuesday is the weekend. Python reads it as `(day == "Saturday") or ("Sunday")`. The left side is `False`, so Python looks at the right side on its own, and any non-empty string counts as true. The fix is to write the full comparison on both sides: `day == "Saturday" or day == "Sunday"`.

## Boundary testing: check the edges

Decision bugs hide at the cutoffs, because that's where `>` and `>=` disagree. So don't test random numbers: for each cutoff, test **just below it, exactly on it, and just above it**. For the bonus life, that's 999, 1000, and 1001, and the 1000 test catches the bug instantly.

For the UV program, the cutoffs are 3, 6, 8, and 11:

| Test | Expected | Why this one |
| --- | --- | --- |
| `2`, `3` | Low, Moderate | Either side of the first cutoff |
| `5`, `6` | Moderate, High | Either side of the second |
| `7`, `8` | High, Very high | Either side of the third |
| `10`, `11` | Very high, Extreme | Either side of the last |
| `0` | Low | The smallest real value |
| `-4` | ??? | Impossible input: what *should* happen? |

The last row matters too. The program says a UV index of -4 is "Low", which is wrong in a different way: the input is impossible. A careful program checks for impossible values first, and the build-along in the next lesson does exactly that.

:::warning
**Three mistakes to check for in every decision:**

1.  `=` where you meant `==`. Python stops with a syntax error, which at least makes it easy to find.
2.  A missing colon at the end of the `if` line, or a block that isn't indented.
3.  `x == "a" or "b"`. Write the comparison out in full on both sides of `or`.
:::

:::quiz
Q: A recipe makes 12 cookies per batch. How do you work out the cookies left over when you have dough for 50?
- [ ] `50 / 12`
  That gives 4.1666…, a float, which doesn't tell you how many cookies are left.
- [ ] `50 // 12`
  That gives 4, the number of full batches, not the leftovers.
- [x] `50 % 12`
  4 full batches use 48, leaving 2. `%` gives exactly that remainder.

Q: With `temp = 30`, what does this print? `if temp > 10:` → `print("Mild")`, `elif temp > 25:` → `print("Hot")`.
- [x] `Mild`
  `30 > 10` is true, so the first branch runs and the `elif` is never checked.
- [ ] `Hot`
  30 is above 25, but Python stops at the first true condition, and that came earlier.
- [ ] Both `Mild` and `Hot`
  An `if`/`elif` chain runs at most one branch.

Q: A rule says "free entry for under-5s". Which values best test `if age < 5:`?
- [ ] 1, 10, and 50
  These never get close to the cutoff, so they can't tell `<` from `<=`.
- [x] 4, 5, and 6
  Just below, exactly on, and just above the cutoff: 5 is the value that shows whether the rule is right.
- [ ] Only 5
  5 matters most, but checking the values beside it confirms the rest of the rule too.

Q: `fruit = "kiwi"`. What does `if fruit == "apple" or "pear":` do?
- [ ] Skips the block, because kiwi isn't apple or pear
  That's what it looks like it means, but Python reads `"pear"` as a separate condition.
- [x] Runs the block, because `"pear"` on its own counts as true
  A non-empty string is truthy, so the `or` is always true. Write `fruit == "apple" or fruit == "pear"`.
- [ ] Crashes with a `TypeError`
  It's valid Python, which is what makes the bug sneaky.
:::

:::takeaways
- `//` counts whole groups and `%` gives the leftover; together they split a number.
- `**` comes first, then `*`, `/`, `//`, `%`, then `+` and `-`; use brackets when in doubt.
- `==` compares and `=` stores. A comparison always produces `True` or `False`.
- In an `if`/`elif`/`else` chain, only the first true branch runs, so with `>=` order from the highest cutoff down.
- Write out both comparisons around `or`: `x == "a" or x == "b"`.
- Test every cutoff just below, exactly on, and just above, and try impossible input.
:::
