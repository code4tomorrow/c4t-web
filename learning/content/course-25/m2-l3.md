:::objectives
- Extend argument validation with `enum`, `minimum`, and `maximum`.
- Clip long tool output so the part that matters, usually the end, survives.
- Detect a stuck agent and enforce a token budget, each with its own named status.
- Trim a long history without separating a tool call from its result.
- Check a history against the message-order rules that real APIs enforce.
:::

Each exercise is one small function that your loop or registry calls. That keeps the code testable without a model and easy to wire into `harness/` once it works. Every solution runs on its own, so try each one in a scratch file before opening the hint.

## Warm-up: count the messages

A run starts with a system message and the task. The model then makes one tool call, then two tool calls in a single reply, then gives a final answer. How many messages are in the history at the end, and in what order? Write your answer down, then run this:

```python run
script = [
    {"tool_calls": [{"id": "a", "name": "list_files", "args": {}}]},
    {"tool_calls": [{"id": "b", "name": "read_file", "args": {"path": "x.txt"}},
                    {"id": "c", "name": "read_file", "args": {"path": "y.txt"}}]},
    {"tool_calls": [], "content": "Done."},
]
history = [{"role": "system"}, {"role": "user"}]
for reply in script:
    history.append({"role": "assistant", "tool_calls": reply["tool_calls"]})
    for call in reply["tool_calls"]:
        history.append({"role": "tool", "tool_call_id": call["id"]})
print(len(history), [m["role"] for m in history])
```

Eight: the two you started with, then `assistant, tool` for the first step, `assistant, tool, tool` for the second, and the final `assistant`. A reply with two calls is one assistant message followed by two results, not two separate turns. Exercise 6 depends on that.

### Exercise 1: Enums and ranges

Models often pass values that are the right type but still wrong: a mode that doesn't exist, a line count of 5000. Write `check_value(name, value, spec)` that returns a list of problems. It should keep the `bool` check from the build-along and also support `enum` (a list of allowed values), `minimum`, and `maximum`.

Sample output:

```text
mode='append': valid
mode='delete': ["'mode' must be one of ['read', 'append', 'overwrite'], got 'delete'"]
max_lines=50: valid
max_lines=0: ["'max_lines' must be at least 1, got 0"]
max_lines=5000: ["'max_lines' must be at most 200, got 5000"]
max_lines=True: ["'max_lines' should be integer, got bool"]
```

:::hint
Check the type first and return early if it's wrong, since comparing `"5" < 1` would raise `TypeError`. Then each extra rule is a separate `if` that appends its own message.
:::

:::solution
```python run
TYPES = {"string": str, "integer": int, "number": (int, float), "boolean": bool}

def check_value(name, value, spec):
    if isinstance(value, bool) and spec["type"] in ("integer", "number"):
        return [f"'{name}' should be {spec['type']}, got bool"]
    if not isinstance(value, TYPES[spec["type"]]):
        return [f"'{name}' should be {spec['type']}, got {type(value).__name__}"]
    problems = []
    if "enum" in spec and value not in spec["enum"]:
        problems.append(f"'{name}' must be one of {spec['enum']}, got {value!r}")
    if "minimum" in spec and value < spec["minimum"]:
        problems.append(f"'{name}' must be at least {spec['minimum']}, got {value}")
    if "maximum" in spec and value > spec["maximum"]:
        problems.append(f"'{name}' must be at most {spec['maximum']}, got {value}")
    return problems

mode = {"type": "string", "enum": ["read", "append", "overwrite"]}
lines = {"type": "integer", "minimum": 1, "maximum": 200}
for name, value, spec in [("mode", "append", mode), ("mode", "delete", mode),
                          ("max_lines", 50, lines), ("max_lines", 0, lines),
                          ("max_lines", 5000, lines), ("max_lines", True, lines)]:
    print(f"{name}={value!r}:", check_value(name, value, spec) or "valid")
```

The early returns mean a wrong type gives exactly one clear message, and range checks only run on values where `<` makes sense. Each message names the allowed values, so the model can correct itself in one step. To use it in `harness/tools.py`, call `check_value` from inside the loop in `check_args`.
:::

### Exercise 2: Clip long tool output

A test run can print thousands of lines, and all of them would land in the context. Write `clip(text, limit)` that returns the text unchanged when it fits, and otherwise keeps the first and last `limit // 2` characters with a marker in the middle saying how many characters were cut.

Sample output (the log has 199 `ok` lines and one error at the end):

```text
line 1: ok
line 2: ok
line 3: ok
line 4: ok
line 5: ok
line 
[... 2375 characters cut ...]
: ok
line 197: ok
line 198: ok
line 199: ok
ERROR: disk full
original: 2495 clipped: 151
True
```

:::hint
Slices do most of the work: `text[:n]` is the head and `text[-n:]` is the tail. Compute the number cut from the original length and the limit.
:::

:::solution
```python run
def clip(text, limit=200):
    """Keep the start and end of long text, and say how much was cut."""
    if len(text) <= limit:
        return text
    head, tail = text[: limit // 2], text[-(limit - limit // 2):]
    return f"{head}\n[... {len(text) - limit} characters cut ...]\n{tail}"

log = "\n".join(f"line {n}: ok" for n in range(1, 200)) + "\nERROR: disk full"
short = clip(log, 120)
print(short)
print("original:", len(log), "clipped:", len(short))
print(clip("tiny output") == "tiny output")
```

Keeping the tail matters more than it looks. Error messages, failing test names, and final summaries tend to come at the end of output, and a clip that kept only the head would have thrown away `ERROR: disk full`. The marker tells the model that something was cut, so it can ask for a specific part instead of assuming it saw everything. In the loop, clip `json.dumps(outcome)` before appending it.
:::

### Exercise 3: Detect a stuck agent

A model that calls `read_file("a.txt")` three times in a row isn't going to learn anything new from a fourth. Write `is_stuck(calls, repeats=3)` that returns `True` when the last `repeats` calls have the same tool name and the same arguments. Arguments that differ only in key order count as the same.

Sample output, for `[a, a]`, `[a, a, a]`, `[a, b, a]`, `[b, a, a, a]`, and three calls whose arguments only differ in order:

```text
False
True
False
True
True
```

:::hint
Turn each call into a string with `json.dumps(..., sort_keys=True)`. Then the last few calls are identical exactly when a set of those strings has one element.
:::

:::solution
```python run
import json

def is_stuck(calls, repeats=3):
    """True when the last `repeats` calls have the same tool and the same arguments."""
    if len(calls) < repeats:
        return False
    keys = {json.dumps([c["name"], c["args"]], sort_keys=True) for c in calls[-repeats:]}
    return len(keys) == 1

a = {"name": "read_file", "args": {"path": "a.txt"}}
b = {"name": "read_file", "args": {"path": "b.txt"}}
same_but_reordered = {"name": "search", "args": {"q": "x", "limit": 5}}
reordered = {"name": "search", "args": {"limit": 5, "q": "x"}}
print(is_stuck([a, a]))
print(is_stuck([a, a, a]))
print(is_stuck([a, b, a]))
print(is_stuck([b, a, a, a]))
print(is_stuck([same_but_reordered, reordered, same_but_reordered]))
```

`sort_keys=True` makes `{"q": "x", "limit": 5}` and `{"limit": 5, "q": "x"}` the same string, which matters because models don't keep key order consistent. In `run_agent`, keep a list of every call the model makes, check `is_stuck` after each step, and return `RunResult("stuck", ...)`. Choose `repeats` with care: an agent polling a slow job may legitimately repeat a call, so some harnesses instead count repeats of the same call *and* the same result.
:::

### Exercise 4: A token budget

Step limits cap the number of calls but not their size. Write `BudgetModel`, a wrapper with the same `complete` method as any model, that adds up `input_tokens + output_tokens` from every reply and raises `BudgetExceeded` before making a call once the total has reached `max_tokens`. Test it with a stand-in model whose prompt grows 400 tokens per call.

Sample output:

```text
call made, total used: 450
call made, total used: 1300
call made, total used: 2550
stopped: used 2550 of 2000 tokens
```

:::hint
Store `used` on the wrapper. Check it at the top of `complete`, before calling the inner model, then add the reply's usage afterwards.
:::

:::solution
```python run
class BudgetExceeded(Exception):
    pass


class BudgetModel:
    """Wraps a model and refuses to make a call once the token budget is spent."""

    def __init__(self, model, max_tokens):
        self.model, self.max_tokens, self.used = model, max_tokens, 0
        self.name = getattr(model, "name", "model")

    def complete(self, messages, tools=None):
        if self.used >= self.max_tokens:
            raise BudgetExceeded(f"used {self.used} of {self.max_tokens} tokens")
        reply = self.model.complete(messages, tools)
        self.used += reply["usage"]["input_tokens"] + reply["usage"]["output_tokens"]
        return reply


class Chatty:
    """A stand-in model whose prompt grows by 400 tokens per call."""
    name = "chatty"
    calls = 0

    def complete(self, messages, tools=None):
        self.calls += 1
        return {"role": "assistant", "content": "", "tool_calls": [],
                "usage": {"input_tokens": 400 * self.calls, "output_tokens": 50}}


model = BudgetModel(Chatty(), max_tokens=2000)
try:
    while True:
        model.complete([])
        print("call made, total used:", model.used)
except BudgetExceeded as exc:
    print("stopped:", exc)
```

Notice the overshoot: the budget was 2000 and the run used 2550, because the wrapper can't know how big a call will be until it's made. If you need a hard cap, estimate the next call's input from the messages before sending it, and refuse if `used` plus that estimate would go over. Because `BudgetModel` has the same interface as a model, the loop doesn't change: add `except BudgetExceeded` before the general `except` in `run_agent` and return status `budget`.
:::

### Exercise 5: Trim history without breaking pairs

Write `trim(messages, max_tokens)`. It always keeps the first two messages (system and task). It drops whole *turns* from the oldest end until the estimate fits, where a turn is one message plus any `tool` messages that follow it. If it dropped anything, it inserts a short user message saying how many messages were removed. Afterwards, every tool result must still have its call.

```mermaid caption="Trimming drops whole turns from the oldest end, so a call and its results leave together."
flowchart LR
    P["system + task (pinned)"] --> N["note: 6 removed"]
    N --> K["newest turn: call + result"]
    K --> F["latest feedback"]
    D["oldest turns: call + result, three times"] -.->|dropped| N
```

Sample output (roles abbreviated to their first letter):

```text
before: 618 tokens, ['s', 'u', 'a', 't', 'a', 't', 'a', 't', 'a', 't', 'u']
after:  206 tokens, ['s', 'u', 'u', 'a', 't', 'u']
[6 earlier messages removed to save space]
every result still has its call: True
```

:::hint
Write a helper that groups the messages after the task into lists: start a new group at every non-`tool` message, and add each `tool` message to the current group. Then pop groups from the front while the total is too big.
:::

:::solution
```python run
import json


def tokens(messages):
    return len(json.dumps(messages)) // 4


def turns(messages):
    """Group messages after the task into turns: an assistant message plus the tool results that follow it."""
    groups = []
    for message in messages:
        if message["role"] == "tool" and groups:
            groups[-1].append(message)
        else:
            groups.append([message])
    return groups


def trim(messages, max_tokens):
    pinned, rest = messages[:2], turns(messages[2:])
    dropped = 0
    while rest and tokens(pinned + [m for turn in rest for m in turn]) > max_tokens:
        dropped += len(rest.pop(0))
    note = [{"role": "user", "content": f"[{dropped} earlier messages removed to save space]"}] if dropped else []
    return pinned + note + [m for turn in rest for m in turn]


history = [{"role": "system", "content": "You are careful."}, {"role": "user", "content": "Summarize the logs."}]
for n in range(1, 5):
    history.append({"role": "assistant", "content": "", "tool_calls": [{"id": f"c{n}", "name": "read_file", "args": {"path": f"log{n}.txt"}}]})
    history.append({"role": "tool", "tool_call_id": f"c{n}", "content": "x" * 400})
history.append({"role": "user", "content": "Verification failed: summary missing log 4"})

print("before:", tokens(history), "tokens,", [m["role"][0] for m in history])
short = trim(history, 300)
print("after: ", tokens(short), "tokens,", [m["role"][0] for m in short])
print(short[2]["content"])
ids = [m["tool_call_id"] for m in short if m["role"] == "tool"]
calls = [c["id"] for m in short if m["role"] == "assistant" for c in m["tool_calls"]]
print("every result still has its call:", set(ids) <= set(calls))
```

Because whole groups leave together, there's no way to keep a result while dropping its call, and the final check proves it. The note tells the model that history is missing, so it won't assume it never read `log1.txt`. Better trimmers summarize dropped turns instead of discarding them ("read log1 to log3: all clean"), which costs one extra model call each time you trim.
:::

### Exercise 6: Check message order

The scripted model accepts any history, but real APIs reject one where a tool result has no matching call just before it, or where a call never gets a result. Write `order_problems(messages)` that returns a list of rule breaks, and test it on a correct history, one with a result missing, and one with an orphan result.

Sample output:

```text
good: ok
missing result: ["message 3: calls ['c2'] never got results"]
orphan result: ['message 1: result c1 has no open call']
```

:::hint
Walk the messages keeping a set of call ids still waiting for results. An assistant message replaces the set (and anything still waiting at that point is a problem). A tool message must remove an id that's in the set.
:::

:::solution
```python run
def order_problems(messages):
    """Check the rules APIs enforce: results follow their call, ids match, and no call goes unanswered."""
    problems, waiting = [], set()
    for number, message in enumerate(messages):
        if message["role"] == "tool":
            if message["tool_call_id"] not in waiting:
                problems.append(f"message {number}: result {message['tool_call_id']} has no open call")
            waiting.discard(message["tool_call_id"])
            continue
        if waiting:
            problems.append(f"message {number}: calls {sorted(waiting)} never got results")
        waiting = {c["id"] for c in message.get("tool_calls") or []}
    if waiting:
        problems.append(f"end: calls {sorted(waiting)} never got results")
    return problems


def call(id, path):
    return {"id": id, "name": "read_file", "args": {"path": path}}

good = [
    {"role": "user", "content": "Compare a.txt and b.txt"},
    {"role": "assistant", "content": "", "tool_calls": [call("c1", "a.txt"), call("c2", "b.txt")]},
    {"role": "tool", "tool_call_id": "c1", "content": "..."},
    {"role": "tool", "tool_call_id": "c2", "content": "..."},
    {"role": "assistant", "content": "They match.", "tool_calls": []},
]
missing = good[:3] + good[4:]
orphan = [good[0], good[2], good[4]]
for name, history in [("good", good), ("missing result", missing), ("orphan result", orphan)]:
    print(f"{name}:", order_problems(history) or "ok")
```

Put this in your tests, not your loop: run every scripted transcript through `order_problems` and assert it returns nothing. It catches the bug class the scripted model can't, so a harness that passes offline won't fail with HTTP 400 the first time it meets a real API.
:::

### Challenge: Four statuses, four runs

Write a compact `run(model, tools, task, max_steps, max_tokens, repeats)` with its own tiny scripted model that returns `done`, `stuck`, `budget`, or `max_steps`, along with the step count and tokens used. Then write four scripts, one that ends in each status. The point is the tests: each stop rule should have a run that proves it fires, and a run that proves it *doesn't* fire when it shouldn't.

Sample output:

```text
('done', 2, 86)
('stuck', 3, 1692)
('budget', 4, 3349)
('max_steps', 8, 7362)
```

:::hint
Check the stop rules in a fixed order after each step's tools have run: stuck first, then budget. For `max_steps`, script a model that alternates between two different calls, so neither the stuck rule nor a huge budget stops it early.
:::

:::solution
```python run
import itertools
import json

ids = itertools.count(1)


def call(name, **args):
    return {"content": "", "tool_calls": [{"id": f"c{next(ids)}", "name": name, "args": args}]}


def say(text):
    return {"content": text, "tool_calls": []}


class Scripted:
    def __init__(self, script):
        self.script = list(script)

    def complete(self, messages, tools=None):
        reply = self.script.pop(0)
        size = len(json.dumps(messages)) // 4
        return {**reply, "usage": {"input_tokens": size, "output_tokens": 10}}


def run(model, tools, task, max_steps=8, max_tokens=10_000, repeats=3):
    messages = [{"role": "user", "content": task}]
    used, recent = 0, []
    for step in range(1, max_steps + 1):
        reply = model.complete(messages)
        used += reply["usage"]["input_tokens"] + reply["usage"]["output_tokens"]
        messages.append({"role": "assistant", "content": reply["content"], "tool_calls": reply["tool_calls"]})
        if not reply["tool_calls"]:
            return "done", step, used
        for c in reply["tool_calls"]:
            recent.append(json.dumps([c["name"], c["args"]], sort_keys=True))
            result = tools[c["name"]](**c["args"])
            messages.append({"role": "tool", "tool_call_id": c["id"], "content": json.dumps(result)})
        if len(recent) >= repeats and len(set(recent[-repeats:])) == 1:
            return "stuck", step, used
        if used > max_tokens:
            return "budget", step, used
    return "max_steps", max_steps, used


tools = {"read_file": lambda path: "x" * 2000, "list_files": lambda: ["a.txt"]}
print(run(Scripted([call("list_files"), say("One file.")]), tools, "What files exist?"))
print(run(Scripted([call("read_file", path="a.txt")] * 9), tools, "Read a.txt"))
print(run(Scripted([call("read_file", path=f"{n}.txt") for n in range(9)]), tools, "Read everything", max_tokens=2000))
print(run(Scripted([call("list_files"), call("read_file", path="a.txt")] * 5), tools, "Loop", max_tokens=10**9))
```

The fourth run is the important one. It repeats the same pair of calls five times, which looks stuck to a person, but no single call repeats three times in a row, so `is_stuck` stays quiet and only the step limit ends it. That's a real gap. A stronger rule looks for any repeated *cycle* of calls, and an even simpler backstop is the step limit itself, which is why it's the one rule you never remove.
:::
