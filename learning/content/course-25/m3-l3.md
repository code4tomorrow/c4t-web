:::objectives
- Honor a server's `Retry-After` header, and give up when it asks for too long.
- Measure what full jitter does to the average and worst-case wait.
- Write a path check that survives `..`, symlinks, absolute paths, and look-alike folder names.
- Build a child environment from an allowlist, and refuse anything that looks like a secret.
- Make a side-effecting tool run at most once per idempotency key, even after a restart.
- Run a repair loop that feeds errors back to the model and stops after a fixed number of tries.
:::

Each exercise is a small function you could drop into `harness/retry.py`, `harness/sandbox.py`, or `harness/files.py`. The solutions are standalone, so run each one in a scratch file before you peek.

## Warm-up: the worst case

`with_retries` uses `attempts=4`, `base=0.5`, and `cap=8`. What's the longest it can spend waiting before it gives up? What if you raise `attempts` to 8? Work it out, then check:

```python run
attempts, base, cap = 4, 0.5, 8.0
ceilings = [min(cap, base * 2 ** n) for n in range(attempts - 1)]   # no wait after the last attempt
print("ceilings:", ceilings, " worst case:", sum(ceilings), "s")
attempts = 8
ceilings = [min(cap, base * 2 ** n) for n in range(attempts - 1)]
print("ceilings:", ceilings, " worst case:", sum(ceilings), "s")
```

Four attempts means three waits, not four, because there's nothing to wait for after the last one. With full jitter each wait is somewhere between zero and its ceiling, so 3.5 seconds is the worst case. At eight attempts the cap kicks in and the worst case jumps to 31.5 seconds, which is a long time for a person staring at a terminal. More attempts isn't free.

### Exercise 1: Honor Retry-After

When a server sends a 429 or 503, it may include a `Retry-After` header saying how many seconds to wait. Write `retry_delay(exc, attempt)` that returns the number of seconds to wait, or `None` if the error shouldn't be retried at all. Use the header when it's a whole number of seconds, give up if it asks for more than `longest` (30 seconds), and fall back to full jitter otherwise.

Sample output:

```text
429 Retry-After=3     attempt 0: wait 3.00s
503 Retry-After=None  attempt 2: wait 1.69s
429 Retry-After=300   attempt 0: don't retry
401 Retry-After=None  attempt 0: don't retry
503 Retry-After=soon  attempt 1: wait 0.76s
```

:::hint
`exc.headers.get("Retry-After")` returns the header or `None`. Check the status code first: a 401 with a `Retry-After` header still shouldn't be retried.
:::

:::solution
```python run
import io
import random
import urllib.error

RETRY_STATUS = {408, 429, 500, 502, 503, 504}


def retry_delay(exc, attempt, base=0.5, cap=8.0, longest=30.0, rng=random):
    """Seconds to wait before the next try, or None if this error shouldn't be retried."""
    if not isinstance(exc, urllib.error.HTTPError) or exc.code not in RETRY_STATUS:
        return None
    asked = exc.headers.get("Retry-After") if exc.headers else None
    if asked is not None and asked.strip().isdigit():
        wait = float(asked)
        return wait if wait <= longest else None    # the server wants longer than we'll wait
    return rng.uniform(0, min(cap, base * 2 ** attempt))


def http_error(code, retry_after=None):
    headers = {"Retry-After": retry_after} if retry_after else {}
    return urllib.error.HTTPError("https://api.example/v1", code, "error", headers, io.BytesIO(b""))


rng = random.Random(0)
for exc, attempt in [(http_error(429, "3"), 0), (http_error(503), 2), (http_error(429, "300"), 0),
                     (http_error(401), 0), (http_error(503, "soon"), 1)]:
    wait = retry_delay(exc, attempt, rng=rng)
    shown = "don't retry" if wait is None else f"wait {wait:.2f}s"
    print(f"{exc.code} Retry-After={exc.headers.get('Retry-After')!s:<5} attempt {attempt}: {shown}")
```

The server knows its own load better than your backoff formula does, so its number wins. Giving up on `Retry-After: 300` is a deliberate choice: a harness that silently sleeps five minutes looks frozen, and it's better to stop and report. `Retry-After` can also be an HTTP date instead of seconds; this version treats anything that isn't digits as "no header," which is safe but could be smarter.
:::

### Exercise 2: What full jitter does on average

Write `schedule(attempts)` that returns the list of waits for one retry sequence. Then generate 10,000 sequences for `attempts=6` with a seeded `random.Random`, and for each wait report its ceiling, its mean, its maximum, and whether every value stayed between zero and the ceiling. Finish with the mean and worst total.

Sample output:

```text
wait 1: ceiling  0.5  mean 0.25  max 0.50  all within bounds: True
wait 2: ceiling  1.0  mean 0.50  max 1.00  all within bounds: True
wait 3: ceiling  2.0  mean 1.00  max 2.00  all within bounds: True
wait 4: ceiling  4.0  mean 2.00  max 4.00  all within bounds: True
wait 5: ceiling  8.0  mean 3.99  max 8.00  all within bounds: True
total wait: mean 7.74s, worst seen 14.66s, worst possible 15.5s
```

:::hint
`statistics.mean` and `max` over `[run[n] for run in runs]` give the numbers for wait `n`. The worst possible total is the sum of the ceilings.
:::

:::solution
```python run
import random
import statistics


def schedule(attempts, base=0.5, cap=8.0, rng=random):
    return [rng.uniform(0, min(cap, base * 2 ** n)) for n in range(attempts - 1)]


rng = random.Random(42)
runs = [schedule(6, rng=rng) for _ in range(10_000)]
for n in range(5):
    ceiling = min(8.0, 0.5 * 2 ** n)
    waits = [run[n] for run in runs]
    inside = all(0 <= w <= ceiling for w in waits)
    print(f"wait {n + 1}: ceiling {ceiling:>4}  mean {statistics.mean(waits):.2f}  "
          f"max {max(waits):.2f}  all within bounds: {inside}")
totals = [sum(run) for run in runs]
print(f"total wait: mean {statistics.mean(totals):.2f}s, worst seen {max(totals):.2f}s, worst possible 15.5s")
```

Each mean is half its ceiling, because a uniform pick between 0 and `c` averages `c / 2`. So full jitter waits about half as long as plain exponential backoff on average, while spreading clients across the whole range. The worst case seen in 10,000 runs, 14.66 seconds, never reaches the possible 15.5, but it gets close. Plan your timeouts around the possible worst case, not the average.
:::

### Exercise 3: A path check with a classic bug

Here's a path check that looks reasonable: resolve the path, then check that the result starts with the workspace's path. Test it against a normal file, a `..` escape into a folder called `workspace-private`, a symlink inside the workspace that points into `workspace-private`, and an absolute path. Then write `safe_path` that refuses all three escapes.

Sample output:

```text
unsafe_path
  allowed  notes.txt
  allowed  ../workspace-private/keys.txt
  allowed  shortcut/keys.txt
  refused  /etc/hosts
safe_path
  allowed  notes.txt
  refused  ../workspace-private/keys.txt
  refused  shortcut/keys.txt
  refused  /etc/hosts
```

:::hint
Compare the strings `/tmp/x/workspace` and `/tmp/x/workspace-private/keys.txt`. Does the second start with the first? Now compare them as paths, part by part, which is what `Path.is_relative_to` does.
:::

:::solution
```python run
import os
import tempfile
from pathlib import Path


def unsafe_path(root, path):
    target = os.path.realpath(os.path.join(root, path))
    if not target.startswith(os.path.realpath(root)):        # the classic bug
        raise PermissionError(path)
    return target


def safe_path(root, path):
    root = Path(root).resolve()
    target = (root / path).resolve()                        # follows .. and symlinks
    if not target.is_relative_to(root):                     # compares whole path parts
        raise PermissionError(f"'{path}' is outside the workspace")
    return target


base = Path(tempfile.mkdtemp())
(base / "workspace").mkdir()
(base / "workspace-private").mkdir()
(base / "workspace-private" / "keys.txt").write_text("secret")
(base / "workspace" / "notes.txt").write_text("hello")
os.symlink(base / "workspace-private", base / "workspace" / "shortcut")

root = base / "workspace"
attempts = ["notes.txt", "../workspace-private/keys.txt", "shortcut/keys.txt", "/etc/hosts"]
for check in (unsafe_path, safe_path):
    print(check.__name__)
    for path in attempts:
        try:
            check(root, path)
            print(f"  allowed  {path}")
        except PermissionError:
            print(f"  refused  {path}")
```

`realpath` did follow the `..` and the symlink correctly. The bug is the comparison: `"/tmp/x/workspace-private/keys.txt".startswith("/tmp/x/workspace")` is `True`, because string prefixes don't respect folder boundaries. `is_relative_to` compares whole path components, so `workspace-private` never matches `workspace`. This is the check `harness/files.py` uses. On Windows, creating symlinks may need Developer Mode or administrator rights, so this test may only run on macOS and Linux.
:::

### Exercise 4: An allowlist with a guard

Write `child_env(parent, allow, extra)` that builds a child's environment from an allowlist of names plus extra values you set on purpose. Add a guard: if any resulting name contains `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, or `CREDENTIAL` (in any case), raise `ValueError` instead of returning it. Prove it with a child process that prints the names it can see.

Sample output (Python on macOS adds a couple of `LC_` and `__CF` variables of its own, which the probe hides):

```text
child sees: ['LANG', 'PATH', 'PYTHONIOENCODING']
mistake caught: refusing to pass secret-looking variables: LLM_API_KEY
```

:::hint
A dictionary comprehension builds the allowlisted part. A compiled regular expression with `re.IGNORECASE` makes the guard one line.
:::

:::solution
```python run
import os
import re
import subprocess
import sys

SECRET_NAME = re.compile(r"KEY|TOKEN|SECRET|PASSWORD|CREDENTIAL", re.IGNORECASE)


def child_env(parent, allow=("PATH", "LANG", "SYSTEMROOT"), extra=None):
    env = {name: parent[name] for name in allow if name in parent}
    env.update(extra or {})
    leaked = sorted(name for name in env if SECRET_NAME.search(name))
    if leaked:
        raise ValueError(f"refusing to pass secret-looking variables: {', '.join(leaked)}")
    return env


parent = dict(os.environ, LLM_API_KEY="sk-demo", GITHUB_TOKEN="ghp-demo", LANG="en_US.UTF-8")
env = child_env(parent, extra={"PYTHONIOENCODING": "utf-8"})
probe = "import os; print(sorted(k for k in os.environ if not k.startswith(('__CF', 'LC_'))))"
seen = subprocess.run([sys.executable, "-I", "-c", probe], env=env, capture_output=True, text=True, timeout=5)
print("child sees:", seen.stdout.strip())
try:
    child_env(parent, allow=("PATH", "LLM_API_KEY"))
except ValueError as exc:
    print("mistake caught:", exc)
```

The allowlist does the real work: `GITHUB_TOKEN` and `LLM_API_KEY` never got near the child because nobody listed them. The guard catches the other failure, a teammate adding a secret to `allow` to "make something work." Failing loudly is better than passing it through quietly. A name-based guard can't catch a secret stored under an innocent name like `CONFIG`, which is one more reason the allowlist should stay short.
:::

### Exercise 5: Once per key, even after a crash

Write `Once`, a wrapper around a side-effecting function. Calling `send(key, *args)` runs the function only the first time it sees `key` and returns the saved result on later calls. Save the ledger to a JSON file after each new key, so a new `Once` created from the same file (a harness that crashed and resumed) still remembers.

Sample output:

```text
message 1 sent
message 1 sent
message 2 sent
message 1 sent
inbox: ['Build is green', 'Deploy started']
```

:::hint
Load the ledger in `__init__` if the file exists. In `__call__`, check the key first; otherwise run the function, store the result, write the file, and return.
:::

:::solution
```python run
import json
import tempfile
from pathlib import Path


class Once:
    """Runs a side-effecting function at most once per idempotency key, even across restarts."""

    def __init__(self, fn, ledger_path):
        self.fn, self.path = fn, Path(ledger_path)
        self.done = json.loads(self.path.read_text()) if self.path.exists() else {}

    def __call__(self, key, *args):
        if key in self.done:
            return self.done[key]
        result = self.fn(*args)
        self.done[key] = result
        self.path.write_text(json.dumps(self.done))   # record it before reporting success
        return result


inbox = []

def send_message(text):
    inbox.append(text)
    return f"message {len(inbox)} sent"


ledger = Path(tempfile.mkdtemp()) / "ledger.json"
send = Once(send_message, ledger)
print(send("run1-step3-call_9", "Build is green"))
print(send("run1-step3-call_9", "Build is green"))      # a retry of the same call
print(send("run1-step5-call_12", "Deploy started"))     # a different action
restarted = Once(send_message, ledger)                   # the harness crashed and resumed
print(restarted("run1-step3-call_9", "Build is green"))
print("inbox:", inbox)
```

The keys combine the run, the step, and the tool call id, so a retry of the same call reuses its key and a different action gets a new one. There's still a gap: if the process dies after `fn` runs but before the ledger file is written, a resume will do it again. Closing that gap needs the effect and the record to be saved together, or a receiving service that deduplicates by key itself. Payment and messaging APIs that accept an idempotency key exist for exactly this reason.
:::

### Exercise 6: A bounded repair loop

Write `repair(attempts, check, max_tries=3)`. Each try, `attempts(feedback)` plays the model: it receives the last error line (or `None` the first time) and returns new code. Run the code plus the `check` assertions in a child process with a timeout, print one line per try, and return `("fixed", tries)` or `("gave up", max_tries)`. Test it with a model that fixes its bugs one at a time, and with one that writes an infinite loop every time.

```mermaid caption="The repair loop. The error is the model's next input, and the try counter is the harness's."
stateDiagram-v2
    [*] --> Write
    Write --> Run: code
    Run --> Fixed: checks pass
    Run --> Write: error fed back, tries left
    Run --> GaveUp: no tries left
    Fixed --> [*]
    GaveUp --> [*]
```

Sample output:

```text
try 1: NameError: name 'x' is not defined. Did you mean: 'xs'?
try 2: ZeroDivisionError: division by zero
try 3: passed
('fixed', 3)
try 1: timed out after 1s
try 2: timed out after 1s
try 3: timed out after 1s
('gave up', 3)
```

:::hint
Catch `subprocess.TimeoutExpired` and turn it into an error line like any other failure. The last line of stderr is usually the most useful single line of a traceback.
:::

:::solution
```python run
import subprocess
import sys
import tempfile


def run(code, timeout=1):
    """A compact stand-in for run_python: returns (ok, last line of the error)."""
    with tempfile.TemporaryDirectory() as work:
        try:
            done = subprocess.run([sys.executable, "-I", "-c", code], cwd=work, env={},
                                  stdin=subprocess.DEVNULL, capture_output=True, text=True,
                                  timeout=timeout)
        except subprocess.TimeoutExpired:
            return False, f"timed out after {timeout}s"
    lines = done.stderr.strip().splitlines()
    return done.returncode == 0, lines[-1] if lines else ""


def repair(attempts, check, max_tries=3):
    """attempts(feedback) plays the model: it gets the last error and returns new code."""
    feedback = None
    for number in range(1, max_tries + 1):
        code = attempts(feedback)
        ok, error = run(code + "\n" + check)
        print(f"try {number}: {'passed' if ok else error}")
        if ok:
            return "fixed", number
        feedback = error
    return "gave up", max_tries


versions = iter([
    "def mean(xs):\n    return sum(xs) / len(x)",          # typo
    "def mean(xs):\n    return sum(xs) / len(xs)",         # crashes on []
    "def mean(xs):\n    return sum(xs) / len(xs) if xs else 0.0",
])
check = "assert mean([2, 4]) == 3\nassert mean([]) == 0.0"
print(repair(lambda feedback: next(versions), check))

stubborn = iter(["while True:\n    pass"] * 3)
print(repair(lambda feedback: next(stubborn), check))
```

The first model needed all three tries: a typo, then a crash on the empty list, then a correct version. Each error line pointed at the next fix, which is how real models use tracebacks. The stubborn model shows why `max_tries` exists. Three timeouts cost three seconds here; without a limit, they'd cost forever. This is the same shape as `run_agent` with `verify`, shrunk to a single tool.
:::

### Challenge: Retries with a deadline

Retry counts don't map to wall-clock time, and the caller usually cares about time. Write `with_deadline(fn, deadline, clock, rng)` that retries `fn` on `TimeoutError` with full jitter, but refuses to *start* a wait that would end past the deadline, and raises a `TimeoutError` saying why. Use a fake clock with `time()` and `sleep()` so the test runs instantly, and make each failed call itself take 0.3 seconds of fake time.

Sample output:

```text
gave up at t=2.60s: next wait 2.42s, only 2.40s left
ok at t=1.56s
```

:::hint
Compute the time left as `deadline - (clock.time() - start)` just before each wait, and compare it with the wait you're about to take. Raise with `from exc` so the original error stays attached.
:::

:::solution
```python run
import random


class FakeClock:
    def __init__(self):
        self.now = 0.0

    def time(self):
        return self.now

    def sleep(self, seconds):
        self.now += seconds


def with_deadline(fn, deadline, clock, rng, base=0.5, cap=8.0):
    """Retry fn until it succeeds, but never start a wait that would end past the deadline."""
    start, attempt = clock.time(), 0
    while True:
        try:
            return fn()
        except TimeoutError as exc:
            wait = rng.uniform(0, min(cap, base * 2 ** attempt))
            left = deadline - (clock.time() - start)
            if wait >= left:
                raise TimeoutError(f"gave up at t={clock.time():.2f}s: next wait {wait:.2f}s, "
                                   f"only {left:.2f}s left") from exc
            clock.sleep(wait)
            attempt += 1


def always_busy():
    clock.sleep(0.3)            # each failed call itself takes 0.3 seconds
    raise TimeoutError("server busy")


clock = FakeClock()
try:
    with_deadline(always_busy, deadline=5.0, clock=clock, rng=random.Random(3))
except TimeoutError as exc:
    print(exc)

calls = iter([TimeoutError(), TimeoutError(), "ok"])

def busy_then_ok():
    clock.sleep(0.3)
    result = next(calls)
    if isinstance(result, Exception):
        raise result
    return result

clock = FakeClock()
print(with_deadline(busy_then_ok, deadline=5.0, clock=clock, rng=random.Random(3)), f"at t={clock.time():.2f}s")
```

The first run gave up at 2.6 seconds instead of sleeping past the 5-second deadline, and its message says exactly why, which is what you'd want in a trace. Counting the time the calls themselves take (0.3 seconds each) matters: on a slow API, the calls can use more of the deadline than the waits. The fake clock is the reusable idea. Any code that sleeps or reads the time should take its clock as a parameter, so tests can run in microseconds and get the same result every time.
:::
