Imagine a team that splits one coding agent into five, and reads this in the first run's log. The planner asked two workers to "improve error handling". One wrapped every call in `try/except` and returned `None`. The other made every function raise a custom exception. Both passed their own tests, the merge broke 14 others, and the run used about four times the tokens of the single agent it replaced.

Nothing in that story is a model failure. Each agent did a reasonable thing with what it was told. The failure was in the system around them: a vague handoff, overlapping work, no shared definition of done, and no check before merging. Multi-agent design is mostly about those seams.

## Routers: pick the right agent, or admit you can't

A **router** looks at a request and sends it to one specialized agent: a code agent with write access, a docs agent, a triage agent that only reads logs. Anthropic's "Building effective agents" lists routing as one of its basic workflow patterns. The design question is what happens when the router is wrong or unsure.

```mermaid caption="A router: rules first, then a classifier, then a person"
flowchart LR
    R[Request] --> K{Rule matches?}
    K -->|yes| T[Target agent]
    K -->|no| M[Classifier model]
    M --> C{"Known route and confident?"}
    C -->|yes| T
    C -->|no| H[Human queue]
```

Rules go first because they're free, fast, and predictable. The classifier handles the rest, and its answer is accepted only if the route exists and the confidence clears a threshold you tuned on labeled requests.

```python run
import json, re

ROUTES = {"code": "edits source files and runs tests",
          "docs": "writes and fixes documentation",
          "triage": "reads logs and explains failures; changes nothing"}

RULES = [  # cheap and predictable, so they go first
    (r"\b(readme|docstring|docs)\b", "docs"),
    (r"\b(traceback|stack trace|error log)\b", "triage"),
]

class ScriptedModel:
    """Module 1's scripted model, cut down: canned replies, in order."""
    def __init__(self, script):
        self.script = list(script)
    def complete(self, messages, tools=None):
        return self.script.pop(0)

def say(text):
    return {"role": "assistant", "content": text, "tool_calls": []}

def route(request, classifier, threshold=0.75):
    for pattern, target in RULES:
        if re.search(pattern, request, re.IGNORECASE):
            return target, "rule"
    prompt = f"Pick one route from {list(ROUTES)} for this request. Reply as JSON with route and confidence.\n\n{request}"
    try:
        choice = json.loads(classifier.complete([{"role": "user", "content": prompt}])["content"])
    except ValueError:
        return "human", "classifier reply was not JSON"
    if choice.get("route") in ROUTES and choice.get("confidence", 0) >= threshold:
        return choice["route"], f"model, confidence {choice['confidence']}"
    return "human", f"not routable: {choice}"

classifier = ScriptedModel([
    say('{"route": "code", "confidence": 0.93}'),
    say('{"route": "code", "confidence": 0.51}'),
    say('{"route": "deploy", "confidence": 0.99}'),
])
for request in ["Update the README install steps",
                "parse_date() returns None for ISO strings with a Z suffix; fix it",
                "Something is off with the dates, maybe",
                "Ship the release to production now"]:
    target, why = route(request, classifier)
    print(f"{target:7} <- {request[:44]:44} ({why})")
```

Look at the last line. The classifier was 99% confident in a route called `deploy`, which doesn't exist. A router that trusted the label would have crashed or, worse, matched it to something close. Confidence is the model's opinion; the list of routes is your policy. Check both.

## Planner, workers, reviewer

For tasks that need several steps, the common shape is the one Anthropic calls **orchestrator-workers**, plus a review loop. A **planner** breaks the request into subtasks with clear outputs. **Workers** each do one subtask with only the context and tools that subtask needs. A **reviewer** checks the combined result against acceptance criteria and either approves it or sends specific feedback back to one worker, a bounded number of times.

```mermaid caption="Planner, workers, and reviewer, with a bounded revision loop"
flowchart TD
    Q[Request] --> P[Planner]
    P -->|"plan: subtasks + owners"| O[Orchestrator]
    O --> W1[Worker: code]
    O --> W2[Worker: tests]
    W1 --> V[Reviewer]
    W2 --> V
    V -->|approve| D[Done]
    V -->|"revise (max 2)"| O
    V -->|"still failing"| H[Human]
```

Two rules make this work. Give each subtask an **owner** for every file it may touch, so two workers never edit the same thing (that's the opening story's bug). And make the reviewer **independent**: it didn't write the code, it runs the tests itself rather than trusting a worker's "tests pass", and it has read access only. A reviewer that can edit will "fix" things instead of reporting them, and then nobody reviews the reviewer.

## Handoffs are contracts, not chat

When one agent passes work to another, free text like "fix the date thing" loses everything the sender knew. A **handoff** should be a structured message that the receiver (or the orchestrator) can validate before any tokens are spent.

```python run
from dataclasses import dataclass

@dataclass
class Handoff:
    trace_id: str
    sender: str
    receiver: str
    task: str
    inputs: dict
    acceptance: list
    budget_tokens: int = 4000

    def problems(self):
        issues = []
        if len(self.task.split()) < 5:
            issues.append("task is too vague to act on")
        if not self.acceptance:
            issues.append("no acceptance criteria, so the receiver can't tell when it's done")
        if self.receiver == self.sender:
            issues.append("an agent can't hand work to itself")
        if not 0 < self.budget_tokens <= 20_000:
            issues.append(f"budget {self.budget_tokens} is outside 1..20000")
        return issues

good = Handoff("run-41", "planner", "code_worker",
               task="Make parse_date accept ISO strings that end in Z",
               inputs={"file": "dates.py", "function": "parse_date", "failing_test": "test_parse_z"},
               acceptance=["test_parse_z passes", "no other test changes state", "only dates.py is edited"])
vague = Handoff("run-41", "planner", "planner", task="fix it", inputs={}, acceptance=[], budget_tokens=0)
for h in (good, vague):
    print(h.receiver, "->", h.problems() or "ok")
```

The good handoff names the file, the function, the failing test, and three ways to tell when the job is done. The `trace_id` ties every message in a run together, so the traces from Module 4 can show the whole conversation across agents. The vague one fails four checks before a worker wastes a single call on it.

```mermaid caption="A handoff passes through the orchestrator, which validates it in both directions"
sequenceDiagram
    participant P as Planner
    participant O as Orchestrator
    participant W as Code worker
    P->>O: Handoff (JSON)
    O->>O: validate fields, owner, budget
    O->>W: task + only the inputs it needs
    W->>O: Result (diff, notes, tokens used)
    O->>O: check acceptance criteria
```

## Shared state or message passing?

Agents can coordinate in two ways. With **shared state** (often called a blackboard), every agent reads and writes one common store. With **message passing**, agents only see what's sent to them, and one orchestrator applies results. Shared state is convenient, and it's where lost updates come from:

```python run
class Board:
    """Shared state that every agent reads and writes."""
    def __init__(self):
        self.data, self.versions = {}, {}
    def read(self, key):
        return dict(self.data.get(key, {})), self.versions.get(key, 0)
    def write(self, key, value, expected_version=None):
        if expected_version is not None and self.versions.get(key, 0) != expected_version:
            return False
        self.data[key] = value
        self.versions[key] = self.versions.get(key, 0) + 1
        return True

for checked in (False, True):
    board = Board()
    board.write("config", {"retries": 1})
    a_conf, a_ver = board.read("config")       # worker A reads
    b_conf, b_ver = board.read("config")       # worker B reads the same version
    a_conf["timeout"] = 30
    b_conf["retries"] = 3
    print("A write ok:", board.write("config", a_conf, a_ver if checked else None))
    ok = board.write("config", b_conf, b_ver if checked else None)
    print("B write ok:", ok)
    if not ok:                                  # B re-reads and reapplies its change
        b_conf, b_ver = board.read("config")
        b_conf["retries"] = 3
        board.write("config", b_conf, b_ver)
    print("version check" if checked else "no check     ", "->", board.read("config")[0])
```

Without a version check, B's write silently erased A's `timeout`. With one (a compare-and-set), B's stale write is rejected, B re-reads, and both changes survive.

```mermaid caption="Two ways to coordinate: every agent touches one store, or one orchestrator applies results"
flowchart LR
    subgraph shared["Shared state"]
        A1[Agent A] <--> S[(Board)]
        B1[Agent B] <--> S
    end
    subgraph messages["Message passing"]
        A2[Agent A] -->|result| O2[Orchestrator]
        B2[Agent B] -->|result| O2
        O2 --> F[(Files)]
    end
```

Message passing has a security benefit too: each agent sees only what it's sent. On a shared board, a prompt injection that one agent reads from a web page can steer every agent that reads the board afterward. The tradeoff is the one Cognition's "Don't Build Multi-Agents" essay argues: agents that see too little make conflicting decisions. A good compromise is a single writer (the orchestrator), read-only shared context where it's needed, and handoffs that carry the decisions already made.

## When splitting helps, and when it only costs

Every model call re-sends its whole context, and contexts grow as an agent works, so input tokens grow roughly with the square of the number of steps. That one fact explains both sides of the argument:

```python run
def input_tokens(steps, briefing, growth):
    """Every call re-sends the whole context, which grows by `growth` each step."""
    return sum(briefing + i * growth for i in range(steps))

SECONDS_PER_STEP = 4
lead = input_tokens(8, 3000, 600)
plans = {
    "one agent, 30 steps": (input_tokens(30, 3000, 800), 30),
    "lead + 3 workers, small briefings": (lead + 3 * input_tokens(10, 2500, 800), 8 + 10),
    "lead + 3 workers, each re-reads all": (lead + 3 * input_tokens(10, 14000, 800), 8 + 10),
}
for name, (tokens, steps_on_critical_path) in plans.items():
    print(f"{name:38} {tokens:>9,} input tokens  {steps_on_critical_path * SECONDS_PER_STEP:>4} s")
```

When subtasks are truly independent and need small briefings, splitting is cheaper *and* faster, because workers run in parallel with short contexts. When every worker has to re-read the whole codebase to do its piece, the same split costs about 30% more than one agent. In practice teams also give multi-agent systems more work, not the same work: Anthropic reported that its multi-agent research system used about 15 times as many tokens as a chat, worth it for broad research questions but not for most coding tasks, which have fewer parallel pieces.

Reach for multiple agents when the work is **parallel** (many independent searches), when roles need **different permissions** (a reviewer that can't write), or when you want **independent verification**. Stay with one agent when the steps are tightly coupled, when every step needs the full context, or when the task is small enough that coordination is most of the cost.

:::warning
**Forwarding the whole transcript.** Giving each worker the planner's entire conversation "for context" feels safe, but it multiplies token cost and hands every worker every earlier mistake and every injected instruction. Send the handoff's fields and the files it names, and let workers ask for more through a tool.
:::

:::warning
**A review loop with no exit.** A reviewer that keeps finding something to change and a worker that keeps changing it will run until the budget dies. Cap revisions (two is common), require the reviewer's feedback to cite a failing acceptance check, and send the third failure to a person.
:::

:::quiz
Q: A classifier returns `{"route": "billing", "confidence": 0.97}`, but your routes are `code`, `docs`, and `triage`. What should the router do?
- [ ] Send it to the closest route by name
  Guessing a route the model didn't pick hides the error and sends work to an agent with the wrong tools.
- [x] Send it to a person, because the route isn't in the policy
  High confidence doesn't make an unknown route valid. The list of routes is your policy; a person can decide or add a route.
- [ ] Accept it, since 0.97 clears the threshold
  The threshold only applies to known routes.

Q: Two workers update the same shared config. Worker B's write is rejected by a version check. What's the right next step for B?
- [ ] Write again without the version, since B's change is valid
  That overwrites A's change, which is the lost update the check exists to stop.
- [x] Re-read the current version, reapply its change, and write with the new version
  This is compare-and-set: B merges its change onto the latest state, so neither update is lost.
- [ ] Stop the run, since conflicts mean the design is broken
  Occasional conflicts are normal with shared state; retrying on the latest version handles them.

Q: Which task benefits most from splitting into a planner and several workers?
- [ ] Renaming one function and updating its 12 call sites
  Every edit depends on the same decision, so splitting invites conflicting edits.
- [x] Checking 40 third-party packages for known vulnerabilities and summarizing them
  Each package check is independent and needs a small briefing, so workers can run in parallel with short contexts.
- [ ] Answering a one-line question about a config value
  The coordination would cost more than the whole task.
:::

:::takeaways
- Route with rules first, a classifier second, and a human queue when the route is unknown or the model is unsure.
- Planners split work, workers own disjoint pieces, and an independent read-only reviewer checks results against acceptance criteria with a revision cap.
- Handoffs are validated structured messages with a task, inputs, acceptance criteria, a budget, and a trace id.
- Shared state needs version checks; message passing with a single writer avoids lost updates and limits how far an injection spreads.
- Splitting helps when work is parallel and briefings are small; it costs more when every agent needs the full context.
:::
