Here's a way to leak an API key that has nothing to do with pasting it into a script. The key sits safely in an environment variable. You ask your agent to debug a config problem, and it runs a command that prints the environment. The output, key included, goes into the conversation, and the harness writes the conversation to a trace file. A week later you commit the traces folder so a friend can see a bug.

In this course, traces record everything the agent saw. So they need the same care as the key itself. This lesson sets up the habits that prevent that story, plus the testing routine and debugging moves you'll use in every module.

## The work cycle: change, test offline, commit

Every change to the harness follows the same three steps. Make the change. Run the tests, which use the scripted model and finish in about a second. Commit. Only then, if you want, try it against a real model. A failing live run is much easier to diagnose when you already know the code passes its offline tests.

The tests import the package, so this page needs `harness/model.py` from the last lesson. It's unchanged:

```python run title="harness/model.py"
"""The one interface every model in the harness speaks:

    reply = model.complete(messages, tools)

messages  a list of dicts such as {"role": "user", "content": "..."}
tools     a list of tool schemas (Module 2 builds these)
reply     {"role": "assistant", "content": "...",
           "tool_calls": [{"id": "...", "name": "...", "args": {...}}],
           "usage": {"input_tokens": 0, "output_tokens": 0}}
"""
import copy
import itertools
import json


def estimate_tokens(text):
    """About 4 characters per token in English. Rough, but fine for budgets."""
    return max(1, len(text) // 4)


_ids = itertools.count(1)


def say(text):
    """A scripted reply that is a final answer."""
    return {"role": "assistant", "content": text, "tool_calls": []}


def call(name, **args):
    """A scripted reply that asks for one tool call."""
    return {"role": "assistant", "content": "",
            "tool_calls": [{"id": f"call_{next(_ids)}", "name": name, "args": args}]}


class ScriptedModel:
    """Replies from a list you write in advance: offline, free, identical every run."""

    name = "scripted"

    def __init__(self, script):
        self.script = list(script)
        self.seen = []  # a copy of the messages it was shown, one list per call

    def complete(self, messages, tools=None):
        self.seen.append(copy.deepcopy(messages))
        if not self.script:
            raise RuntimeError("ScriptedModel ran out of replies")
        reply = self.script.pop(0)
        if callable(reply):  # a reply can be a function of what the model was shown
            reply = reply(messages)
        shown = json.dumps(messages) + json.dumps(tools or [])
        written = reply["content"] + json.dumps(reply["tool_calls"])
        usage = {"input_tokens": estimate_tokens(shown), "output_tokens": estimate_tokens(written)}
        return {**reply, "usage": usage}
```

Now the tests. Each one pins down a promise the rest of the harness relies on. The file starts with `from harness.model import ScriptedModel, call, say`:

```python run title="tests/test_model.py"
import sys
import unittest


class ScriptedModelTests(unittest.TestCase):
    def test_replies_come_back_in_order(self):
        model = ScriptedModel([call("list_files"), say("done")])
        self.assertEqual(model.complete([], [])["tool_calls"][0]["name"], "list_files")
        self.assertEqual(model.complete([], [])["content"], "done")

    def test_running_out_is_an_error(self):
        with self.assertRaises(RuntimeError):
            ScriptedModel([]).complete([], [])

    def test_seen_is_a_snapshot(self):
        model = ScriptedModel([say("ok")])
        history = [{"role": "user", "content": "hi"}]
        model.complete(history, [])
        history.append({"role": "user", "content": "added after the call"})
        self.assertEqual(len(model.seen[0]), 1)

    def test_every_reply_reports_usage(self):
        reply = ScriptedModel([say("ok")]).complete([{"role": "user", "content": "hi"}], [])
        self.assertGreater(reply["usage"]["input_tokens"], 0)
        self.assertGreater(reply["usage"]["output_tokens"], 0)

    def test_script_entries_are_left_alone(self):
        entry = say("ok")
        ScriptedModel([entry]).complete([], [])
        self.assertNotIn("usage", entry)


suite = unittest.defaultTestLoader.loadTestsFromTestCase(ScriptedModelTests)
unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)
```

The last two lines are only for this page. On disk, delete them. From the `harness-lab` folder, `python -m unittest` searches `tests/` for files named `test*.py` and runs every method whose name starts with `test`. That search only finds folders with an `__init__.py`, which is why you created `tests/__init__.py` in Lesson 1.

Look at `test_seen_is_a_snapshot`. If `complete` stored `messages` itself instead of a deep copy, appending to `history` after the call would also change `model.seen[0]`, and your record of what the model was shown would quietly become wrong. That bug is easy to write and invisible in normal runs, which is exactly the kind of thing a test is for.

What to watch for: how a `unittest.TestCase` is laid out, `assertEqual` and `assertRaises`, and the rule that test methods must start with `test`. Every test file in this course uses that pattern.

## Git: commit the code and the eval cases, not the runs

Make the project a repository, and tell Git what never to track before your first commit. Create `.gitignore` in `harness-lab`:

```text title=".gitignore"
.venv/
__pycache__/
.env
traces/
```

Then make the first commit:

```bash
git init
git add .
git commit -m "Set up harness project with scripted model and tests"
```

Each line in `.gitignore` has a reason. `.venv/` is hundreds of files you can recreate with one command. `.env` is where people tend to keep keys. And `traces/` holds raw records of every run, including every file the agent read and every command output it saw. In Module 4 you'll turn selected traces into eval cases in `evals/`, after reviewing them, and *those* you do commit.

If a key ever reaches a commit, revoke it at the provider right away and make a new one. Deleting the commit isn't enough, because clones and caches may already have it. GitHub scans public repositories for known key formats and can block a push that contains one, but treat that as a seatbelt, not a plan.

## Your key is visible to every process you start

The harness reads `LLM_API_KEY` from the environment so the key never sits in a file. But environment variables are inherited: every program the harness starts gets a copy. Predict what the child process prints:

```python run
import os
import subprocess
import sys

os.environ["LLM_API_KEY"] = "sk-demo-not-a-real-key"
child = subprocess.run([sys.executable, "-c", "import os; print(os.environ.get('LLM_API_KEY'))"],
                       capture_output=True, text=True)
print("the child process sees:", child.stdout.strip())
```

The child printed the key. Any code your agent writes and runs, any test command, any script it calls, can read every secret in your environment by default. Module 3's sandbox fixes this by starting child processes with an allowlisted environment that contains nothing secret.

## Where your data goes

Tool results are part of the prompt. When your agent reads a file, the file's contents are sent to the model on the next call. So the question "where does my data go?" has a different answer for each model option:

| Option | Where prompts and tool results go | Cost | Use it for |
| --- | --- | --- | --- |
| Scripted model | Nowhere: they stay in your Python process | Free | Every test and every cell on these pages |
| Ollama | Your own computer; Ollama listens on `127.0.0.1:11434` by default | Free, uses your CPU or GPU | Seeing real model behavior offline |
| Hosted provider | The provider's servers, under their data policy | Paid per token | Larger models and comparisons |

With a hosted model, never point the agent at folders holding personal data, school records, or anyone else's information. Read your provider's data-use policy before you send anything you wouldn't post publicly.

## Safety rules for the harness

These hold for the whole course, and later modules add machinery to enforce them:

1. **File tools stay inside `workspace/`.** The tools you write in Module 2 refuse any path that resolves outside it.
2. **Generated code runs only through the sandbox.** Module 3 builds it. When you run code you haven't read, run the sandbox inside a container or virtual machine as well.
3. **No tools that touch real accounts.** No email, no payments, no access to your real GitHub during this course. Module 7 adds human approval for risky actions.
4. **Every run is bounded.** Step limits, timeouts, and token budgets, so a confused model can't loop forever or spend without limit.
5. **The scripted model is the default.** A real model is something you switch on with a flag, like `--live`.

## Accessibility

Everything the harness produces is plain text. Traces are JSON lines you can read in any editor, search with `grep`, or hear with a screen reader, and every diagram on these pages has a caption and matching code. Nothing in the course is timed, which matters because a local model on a laptop CPU can take half a minute per reply.

If you use VS Code, it detects most screen readers and switches to a **Screen Reader Optimized** mode for the editor and terminal. **Accessibility Help** (Alt+F1 on Windows, Option+F1 on macOS, Shift+Alt+F1 on Linux) explains the shortcuts for whatever you're focused on, and **Accessible View** (Alt+F2, Option+F2, or Shift+Alt+F2) lets you read the terminal's whole output, which helps with long tracebacks. Ctrl+= or Cmd+= zooms the whole window.

## When you're stuck: the errors this course produces

Start with the last line of the traceback: it names the exception and usually the cause. Then look at what the model was shown, `model.seen[-1]`, before you change any code. And reproduce the problem with a scripted model before you touch the real one, because a bug you can trigger every time is half fixed.

| Error | What it means | Fix |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'harness'` | You ran a script from inside `harness/` or `tests/`, so Python can't see the package | Run from `harness-lab`: `python check_setup.py`, `python -m unittest` |
| `RuntimeError: ScriptedModel ran out of replies` | The harness called the model more times than the script expected | Usually a loop that didn't stop; print `len(model.seen)` and the last messages |
| `URLError: <urlopen error [Errno 61] Connection refused>` | Nothing is listening on port 11434 (the number is 111 on Linux, and Windows says `WinError 10061`) | Start the Ollama app, or run `ollama serve` |
| `HTTPError: HTTP Error 404: Not Found` | The model isn't pulled, or the base URL is missing `/v1` | Check `ollama list` and `LLM_BASE_URL` |
| `HTTPError: HTTP Error 401: Unauthorized` | A hosted provider rejected the key | Check `LLM_API_KEY` is set in *this* terminal |
| `HTTPError: HTTP Error 400: Bad Request` | The provider rejected the request itself | Read the response body, as shown below |

`urllib` puts only the status line in the exception message. The explanation, such as a model that doesn't support tools or a malformed message, is in the response body. You read it from the exception itself, since an `HTTPError` doubles as the response. Here's that move with a made-up error, so it runs offline:

```python run
import io
import urllib.error

body = b'{"error": {"message": "this model does not support tools"}}'
exc = urllib.error.HTTPError("http://localhost:11434/v1/chat/completions", 400, "Bad Request", {}, io.BytesIO(body))
print("message:", exc)
print("body:   ", exc.read().decode("utf-8"))
```

The first line is all you'd see in a traceback; the second tells you what to change. When a real call fails, wrap it in `try`, catch `urllib.error.HTTPError as exc`, and print `exc.read().decode()`.

:::quiz
Q: Which of these should be committed to Git?
- [ ] `traces/` from yesterday's runs
  Raw traces contain everything the agent saw, which can include secrets and personal data.
- [x] `evals/tasks-v1.jsonl`, after you've reviewed it
  Reviewed eval cases are the frozen test set the project depends on, so they belong in version control.
- [ ] `.venv/`, so classmates get the same Python
  It's machine-specific and recreated with one command; commit the instructions, not the folder.

Q: Your agent runs `python -m pytest` in a child process with Python's default settings. Can that test code read `LLM_API_KEY`?
- [x] Yes, because child processes inherit the parent's environment by default
  That's what the demo showed. The sandbox in Module 3 passes an allowlisted environment instead.
- [ ] No, because the key was set in a different program
  The harness process is the parent; every child gets a copy of its environment.
- [ ] Only if the test code imports the harness
  Reading an environment variable needs only `os.environ`; nothing from the harness.

Q: You `cd tests` and run `python test_model.py`. It fails with `ModuleNotFoundError: No module named 'harness'`. Why?
- [ ] The `harness` folder is missing `__init__.py`
  That would break imports from the project root too, and those work.
- [x] Python looks for imports starting from the script's folder, which is `tests/`, and the package isn't there
  Run `python -m unittest` from `harness-lab`, so the project root is where Python looks.
:::

:::takeaways
- Change, run the offline tests, commit; only then try a real model.
- `python -m unittest`, run from the project root, finds every `test*.py` file in `tests/`.
- `.gitignore` keeps `.venv/`, `.env`, and raw `traces/` out of Git; reviewed eval cases go in.
- Child processes inherit your environment, keys included, until the sandbox removes them.
- With a hosted model, every file the agent reads is sent to the provider.
:::
