Here's an agent loop in about twenty lines. On the happy path it works. A list of replies stands in for the model, and this time the model makes a typo in an argument name, which real models do:

```python run raises
def read_file(path):
    return {"notes.txt": "Deadline: June 3"}[path]

TOOLS = {"read_file": read_file}
replies = [
    {"content": "", "tool_calls": [{"id": "c1", "name": "read_file", "args": {"paht": "notes.txt"}}]},
    {"content": "The deadline is June 3.", "tool_calls": []},
]

def naive_agent(task):
    messages = [{"role": "user", "content": task}]
    while True:
        reply = replies.pop(0)              # stands in for model.complete(messages, tools)
        messages.append(reply)
        if not reply["tool_calls"]:
            return reply["content"]
        for call in reply["tool_calls"]:
            result = TOOLS[call["name"]](**call["args"])
            messages.append({"role": "tool", "tool_call_id": call["id"], "content": str(result)})

print(naive_agent("When is the deadline?"))
```

One wrong letter, and the whole run dies with a `TypeError`. The conversation so far is gone too. Three more crashes hide in those lines. An unknown tool name raises `KeyError`. A tool that fails for any reason (a missing file, say) takes the run down with it. And `while True` never ends if the model keeps asking for tools. A model would have fixed its own typo in one more step if it had been told what went wrong. A **runtime** is this loop plus the rules that turn every one of those failures into information instead of a crash.

## One turn of the loop

The model never runs anything. It reads the history and replies with either tool calls or a final answer. The harness does everything else: it checks and runs the calls, appends the results, and decides when to stop.

```mermaid caption="One task, two model calls. The harness owns every arrow that touches a tool."
sequenceDiagram
    participant H as Harness
    participant M as Model
    participant T as Tool registry
    H->>M: complete(history, tool schemas)
    M-->>H: tool call read_file with path notes.txt
    H->>T: validate, then dispatch
    T-->>H: ok result with the file text
    H->>H: append the call and the result to history
    H->>M: complete(longer history, tool schemas)
    M-->>H: final answer, no tool calls
    H->>H: verify, then stop
```

Those steps have names, and you'll see them in the code you write next lesson:

- **Plan.** The model call. Its reply is the plan for the next step: some actions, or "I'm done."
- **Act.** The harness runs the requested tools, after checking that each call is allowed and well formed. The model proposes; the harness decides.
- **Observe.** Each result goes back into the history as a `tool` message. It's the only way the model learns what happened.
- **Verify.** Before accepting "done," the harness checks the world itself: do the tests pass, does the file exist? Models regularly report success they didn't achieve.

Each model call is stateless. The model remembers nothing between calls; the history list *is* the agent's memory, and the harness sends all of it every time.

## Tools are contracts

A tool, from the model's side, is three things: a name, a description of when to use it, and a JSON Schema describing its arguments. The model sees only these, so a vague description makes a confused agent.

```json
{
  "name": "read_file",
  "description": "Read a UTF-8 text file from the workspace. Use list_files first if unsure of the name.",
  "parameters": {
    "type": "object",
    "properties": {"path": {"type": "string", "description": "Path relative to the workspace"}},
    "required": ["path"],
    "additionalProperties": false
  }
}
```

The schema is a promise the model makes, and nothing forces it to keep that promise. Some providers can constrain output to match a schema, but small local models often can't, and even constrained output can name a file that doesn't exist. So the harness checks every call before running it. Here's a first attempt at a checker. Read the four results and find the one that's wrong:

```python run
schema = {"required": ["path", "max_lines"],
          "properties": {"path": {"type": "string"}, "max_lines": {"type": "integer"}}}
TYPES = {"string": str, "integer": int}

def problems(args):
    found = [f"missing '{name}'" for name in schema["required"] if name not in args]
    for name, value in args.items():
        spec = schema["properties"].get(name)
        if spec is None:
            found.append(f"unknown argument '{name}'")
        elif not isinstance(value, TYPES[spec["type"]]):
            found.append(f"'{name}' should be {spec['type']}")
    return found

for args in [{"path": "a.txt", "max_lines": 5},
             {"paht": "a.txt", "max_lines": 5},
             {"path": 42, "max_lines": "5"},
             {"path": "a.txt", "max_lines": True}]:
    print(args, "->", problems(args) or "valid")
```

The typo is caught twice over: `path` is missing and `paht` is unknown. The last line is the bug. JSON `true` becomes Python `True`, and in Python `bool` is a subclass of `int`, so `isinstance(True, int)` is `True`. The checker you build next lesson tests for `bool` first.

## Errors are observations

When a call fails, the harness doesn't raise. It returns a result the model can read, in one consistent shape:

```json
{"ok": true, "result": "Deadline: June 3"}
{"ok": false, "error": {"type": "bad_arguments", "message": "missing required argument 'path'; unknown argument 'paht'"}}
```

The `message` is effectively a prompt, so write it for the model. "No file named 'notes.md'; call list_files to see what exists" gets a better next step than `KeyError: 'notes.md'`. Models recover from clear errors remarkably often: they fix the argument, try another file, or explain why they can't continue.

Not every exception should go back to the model, though. Sort failures into three kinds:

| Failure | Example | What the harness does |
| --- | --- | --- |
| The call was bad or the tool failed | Wrong argument type, missing file | Return `ok: false` to the model and keep going |
| The model API failed | Timeout, rate limit, server error | Retry if it's temporary (Module 3), otherwise stop with `model_error` |
| The harness itself has a bug | `KeyError` inside your own loop code | Crash, so a test catches it |

Catching your own bugs and showing them to the model would hide them, and the model can't fix your code anyway.

## Stop rules: every run must end

A runtime needs a reason to stop for every way a run can go. Here are the states one run can move through:

```mermaid caption="A run's states. Every path ends, and each ending has a name you can count."
stateDiagram-v2
    [*] --> Asking
    Asking --> Acting: tool calls
    Acting --> Asking: results appended
    Asking --> Verifying: no tool calls
    Verifying --> Done: check passes
    Verifying --> Asking: check fails
    Asking --> Stopped: step limit or budget
    Asking --> Failed: model call fails
    Done --> [*]
    Stopped --> [*]
    Failed --> [*]
```

The **step limit** is the one you can't skip. A model that keeps calling tools, or keeps failing verification, would otherwise run until your money or patience ran out. Asking the model to stop doesn't count as a limit; the harness has to count. Step through a loop whose model never stops asking for tools, and watch the counter and the history:

:::trace Watch the step limit end a run that would never finish
```python
replies = ["tool call", "tool call", "tool call", "tool call", "tool call"]
history = ["task"]
max_steps = 3
status = "running"
for step in range(1, max_steps + 1):
    reply = replies[step - 1]
    history.append(reply)
    if reply != "tool call":
        status = "done"
        break
    history.append("result")
else:
    status = "max_steps"
print(status, len(history))
```
:::

The `for ... else` runs its `else` branch only when the loop finishes without `break`, which is exactly "used every step and never finished." The status is a named outcome, `max_steps`, not just an empty answer, so in Module 4 you can count how often it happens. Two more rules you'll write in the practice set: **stuck**, for the same call with the same arguments several times in a row, and **budget**, for a cap on total tokens.

## The history grows, and every call sends all of it

Each step adds at least two messages, the call and its result, and each model call sends the entire history again. Suppose the system prompt, task, and tool schemas take 300 tokens, and each step adds a 50-token call and a 500-token file. Ollama's default context window is 4,096 tokens:

```python run
base, per_step, window = 300, 550, 4096
total = 0
for step in range(1, 21):
    sent = base + per_step * (step - 1)
    total += sent
    if step in (1, 2, 7, 8, 20):
        note = "  past the window" if sent > window else ""
        print(f"step {step:2}: sends {sent:5,} tokens, {total:7,} sent so far{note}")
```

By step 8 the history no longer fits, so a local model with default settings stops seeing all of it. The running total grows with roughly the square of the step count: twenty steps send 110,500 tokens, more than six times what eight steps sent, for two and a half times the steps. On a hosted model you pay for every one of those tokens. Context management is part of the runtime's job:

- **Clip big tool results.** Keep the head and tail of a long output and say how much was cut. The model can always ask for a specific part.
- **Pin what matters, drop what's old.** Keep the system prompt and the task, and drop or summarize the oldest turns.
- **Keep each call with its result.** If you drop an assistant message that made a tool call but keep its result, OpenAI-style APIs reject the request.
- **Put long-term memory in files.** Notes the agent writes to the workspace survive any trimming, and it reads them back when it needs them. History is working memory; files are the notebook; traces are the record for *you*, not the model.

What to watch for: the split between the model and the harness around it, and how each turn of the loop puts tool results back into the context. Notice how much of an agent's behavior comes from the harness rather than the model.
:::

:::warning
**Appending a tool result without the call that asked for it.** The history must contain the assistant message with `tool_calls` *before* the `tool` messages that answer it, with matching ids. Skip the assistant message and OpenAI-style APIs answer with HTTP 400. The scripted model won't complain, so test the message order yourself.
:::

:::warning
**Trusting "done."** A model that writes "I fixed the bug and all tests pass" may never have run the tests. Treat a final answer as a claim, and let a `verify` check decide whether the run really succeeded. A failed check goes back to the model as feedback, and the loop continues.
:::

:::quiz
Q: A model asks for a tool on every single reply. The harness has `max_steps=5`. How many times is the model called, and what's the status?
- [ ] 6 calls, status `done`
  The model never gives a final answer, so the run can't be `done`.
- [x] 5 calls, status `max_steps`
  One model call per step, and the limit ends the run with a named status instead of an answer.
- [ ] It runs until the model gives up
  A model that always wants tools never gives up; that's why the harness counts.

Q: The first checker said `{"path": "a.txt", "max_lines": True}` was valid. Why?
- [ ] JSON has no boolean type
  It does (`true` and `false`), and Python decodes it to `True`.
- [x] `bool` is a subclass of `int` in Python, so `isinstance(True, int)` is `True`
  Check for `bool` before checking for `int` or `number`.
- [ ] The checker skips arguments that are present
  It checks every argument; the type test itself is what passes.

Q: While running a tool call, `read_file` raises `FileNotFoundError`. In the same run, your own loop code raises `KeyError` because of a typo in the harness. What should happen to each?
- [x] Return the `FileNotFoundError` to the model as `ok: false`; let the `KeyError` crash so your tests catch it
  The first is information the model can act on. The second is your bug, and hiding it from yourself helps no one.
- [ ] Return both to the model
  The model can't fix your harness code, and the bug would stay hidden.
- [ ] Crash on both
  Crashing on a missing file throws away a run the model could have finished.

Q: To save context, a trimmer drops an old assistant message that called `read_file` but keeps the `tool` message with its result. What happens on the next call?
- [ ] Nothing; the model just sees less history
  The API checks message order, so it's not just a smaller prompt.
- [x] OpenAI-style APIs reject the request, because a tool result must follow the call it answers
  Trim calls and results together, as a pair.
:::

:::takeaways
- The model only proposes. The harness validates, runs, records, verifies, and stops.
- Each step goes plan (model call), act (dispatch), observe (append results), and on a final answer, verify.
- Validate every tool call against its schema, and check `bool` before `int`.
- Tool failures go back to the model as structured `ok: false` results with messages written for the model; harness bugs should crash.
- Every run ends with a named status: `done`, `max_steps`, `stuck`, `budget`, or `model_error`.
- Every call re-sends the whole history, so clip results, trim old turns in pairs, and keep long-term memory in files.
:::
