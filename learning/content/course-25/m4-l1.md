A run ends with status `done` and the answer "Fixed the bug; all tests pass." The tests don't pass. What happened?

Maybe the agent never ran the tests. Maybe it ran them, misread the output, and stopped. Maybe the tests passed, and then a later "tidying" edit broke the file again. Each of those needs a different fix (a better tool description, a verify step, a stop rule), and the final answer can't tell them apart. Only a record of every step can.

The same goes for scores. If "7 of 10 tasks" on Friday and "9 of 10" on Monday came from task files that someone edited in between, the two numbers measure different things. This module gives you two habits: record every observation and action as it happens, and freeze the tasks you grade against.

## What a trace records

A **trace** is the full, ordered record of one run: every model call, every tool call and its result, every verification, and how the run ended. It's written as events, one per thing that happened, and every event carries the run id, the step number, and its type:

| Event | Extra fields | Answers the question |
| --- | --- | --- |
| `start` | task, model name, tool names, step limit | What was the agent asked, with which setup? |
| `model` | latency in ms, input and output tokens, content, tool calls | What did the model decide, and what did it cost? |
| `tool` | call id, tool, arguments, `ok`, result or error, latency | What did the harness do, and what came back? |
| `verify` | `ok`, the problem found | Did the harness's own check agree with the model? |
| `end` | status, final answer | How did the run finish? |

Here are the first lines of a trace from the next lesson (the latencies change slightly every run):

```text
{"run": "deadline", "step": 0, "type": "start", "task": "When is the project deadline?", "model": "scripted", "tools": ["list_files", "read_file", "write_file"], "max_steps": 6}
{"run": "deadline", "step": 1, "type": "model", "ms": 0.04, "content": "", "tool_calls": [{"id": "call_1", "name": "list_files", "args": {}}], "input_tokens": 243, "output_tokens": 13}
{"run": "deadline", "step": 1, "type": "tool", "ms": 0.13, "call_id": "call_1", "tool": "list_files", "args": {}, "ok": true, "result": ["notes.txt"]}
{"run": "deadline", "step": 2, "type": "model", "ms": 0.03, "content": "", "tool_calls": [{"id": "call_2", "name": "read_file", "args": {"path": "notes.txt"}}], "input_tokens": 300, "output_tokens": 17}
{"run": "deadline", "step": 2, "type": "tool", "ms": 0.09, "call_id": "call_2", "tool": "read_file", "args": {"path": "notes.txt"}, "ok": true, "result": "Project: weather bot\nDeadline: June 3\nOwner: Priya\n"}
```

Two rules make a trace trustworthy. Record events **as they happen**, not as a summary at the end, because the runs you most need to understand are the ones that crashed before the end. And record **what the model was shown and what it did**, not your interpretation of it. "The agent seemed confused" isn't evidence; three identical `read_file` calls are.

## Why JSON Lines

**JSON Lines** (JSONL) puts one complete JSON object on each line of a file. The harness opens the file in append mode, writes a line, and moves on. Compare it with the obvious alternative, one JSON array written at the end, when the process dies partway through writing:

```python run
import json

events = [{"run": "r1", "step": 1, "type": "model", "tool_calls": [{"name": "read_file"}]},
          {"run": "r1", "step": 1, "type": "tool", "tool": "read_file", "ok": True},
          {"run": "r1", "step": 2, "type": "model", "tool_calls": []}]
as_array = json.dumps(events)
as_lines = "".join(json.dumps(event) + "\n" for event in events)

crashed_array, crashed_lines = as_array[:-25], as_lines[:-25]   # the process dies mid-write

try:
    json.loads(crashed_array)
except json.JSONDecodeError as exc:
    print("one JSON array:", "nothing readable,", exc.msg)

kept = []
for line in crashed_lines.splitlines():
    try:
        kept.append(json.loads(line))
    except json.JSONDecodeError:
        break
print("JSON Lines:    ", len(kept), "of", len(events), "events recovered")
```

The array lost everything, because a JSON document is only valid once its closing `]` is written. The JSONL file lost only the line being written. It has other advantages too: you can append without rewriting the file, read a huge trace one line at a time, `grep` it for `"ok": false`, and concatenate traces from many runs into one file.

Reading a trace is a loop over events. Step through this one and watch the counters change, then predict the three numbers it prints:

:::trace Summarize a trace one event at a time
```python
events = [
    {"step": 1, "type": "model", "input_tokens": 120, "output_tokens": 15},
    {"step": 1, "type": "tool", "tool": "read_file", "ok": False},
    {"step": 2, "type": "model", "input_tokens": 190, "output_tokens": 15},
    {"step": 2, "type": "tool", "tool": "read_file", "ok": True},
    {"step": 3, "type": "model", "input_tokens": 260, "output_tokens": 12},
    {"step": 3, "type": "end", "status": "done"},
]
tokens = 0
errors = 0
for event in events:
    if event["type"] == "model":
        tokens += event["input_tokens"] + event["output_tokens"]
    elif event["type"] == "tool" and not event["ok"]:
        errors += 1
print(tokens, errors, events[-1]["step"])
```
:::

612 tokens, one tool error, three steps. Notice the input tokens grow each step (120, 190, 260): the history from Module 2, re-sent every call, is visible right there in the trace.

## Replay: rerun a recorded run for free

The model is the expensive, slow, random part of a run. A trace contains every reply it gave, so you can rerun the run with a **replay model** that returns those replies in order instead of calling anything. The tools still run for real. If the world hasn't changed, the replay matches the recording exactly. If it has, the first place they differ tells you what changed:

```python run
def run(replies, files, log):
    """A tiny agent: each reply either reads a file or answers."""
    for step, reply in enumerate(replies, start=1):
        log.append({"step": step, "type": "model", "reply": reply})
        if "read" in reply:
            log.append({"step": step, "type": "tool", "path": reply["read"],
                        "result": files.get(reply["read"], "no such file")})


recorded = []
run([{"read": "notes.txt"}, {"answer": "June 3"}], {"notes.txt": "Deadline: June 3"}, recorded)

replies = [event["reply"] for event in recorded if event["type"] == "model"]   # no model needed
replayed = []
run(replies, {"notes.txt": "Deadline: June 10"}, replayed)                     # but the file changed

for old, new in zip(recorded, replayed):
    if old != new:
        print(f"diverged at step {old['step']}: {old['result']!r} became {new['result']!r}")
        break
print("replayed answer:", replayed[-1]["reply"]["answer"])
```

The divergence points straight at the changed file. Notice the replayed answer is still "June 3", now wrong, because a recording can't react to new information. Replay answers "what changed between these runs?" and "does my harness change alter behavior on recorded runs?" It doesn't answer "what would the model do now?" That still needs a live run.

Replay is also how you turn a surprising real run into a permanent test. A replayed trace is a script, so the bug you saw once with a real model becomes a `ScriptedModel` test that fails the same way every time until you fix it.

## From traces to eval cases

An **eval case** is one task frozen in place: the exact prompt, the exact starting files, and the checks that decide whether a run passed. Traces are where good cases come from. Read your traces and pick the failures, the near misses, and a few representative successes, then write down what a correct run must do.

```json
{"id": "deadline", "task": "When is the project deadline?",
 "files": {"notes.txt": "Project: weather bot\nDeadline: June 3\nOwner: Priya\n"},
 "expect": {"answer_contains": ["June 3"], "must_call": ["read_file"], "max_steps": 4},
 "source_run": "deadline"}
```

The set of cases is a dataset, and it gets the same discipline as code. Save the cases in a stable order, and record a **version**: a hash of the file's exact bytes. Change one character and the version changes:

```python run
import hashlib
import json


def version(cases):
    text = "".join(json.dumps(case, sort_keys=True) + "\n" for case in sorted(cases, key=lambda c: c["id"]))
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]


cases = [{"id": "deadline", "task": "When is the project deadline?",
          "files": {"notes.txt": "Deadline: June 3\n"},
          "expect": {"answer_contains": ["June 3"], "must_call": ["read_file"]}}]
print("v1:", version(cases))
cases[0]["files"]["notes.txt"] = "Deadline: June 3 \n"      # one extra space
print("after a one-character edit:", version(cases))
```

Every score you report carries the version it was measured on. Two scores are comparable only if their versions match. When a case needs fixing, don't edit it in place: write a new file (`tasks-v2.jsonl`), and rerun anything you want to compare against it.

## Graders: deterministic first, a judge when you must

A **grader** turns one run into pass or fail. **Deterministic graders** are code: the same run always gets the same grade, for free. They check things like whether the answer contains a phrase, whether the tests pass, whether a file has the right contents, which tools were called, and how many steps it took. Use them whenever the success condition can be written as code.

Deterministic doesn't mean correct, though. Here's the obvious check for "the answer says June 3," applied to four answers:

```python run
import re


def contains(answer, expected):
    return expected.lower() in answer.lower()


def whole_phrase(answer, expected):
    return re.search(rf"\b{re.escape(expected)}\b", answer, re.IGNORECASE) is not None


answers = ["The deadline is June 3.", "It's due June 30.", "Due june 3, 5 pm.",
           "I found no deadline, so it isn't June 3."]
for answer in answers:
    print(f"{answer:<42} contains: {contains(answer, 'June 3')!s:<5}  whole phrase: {whole_phrase(answer, 'June 3')}")
```

Plain `in` passes "June 30," which is wrong. A word-boundary regex fixes that, but both pass the last answer, which says the opposite. Test your graders on wrong answers, not just right ones. And when meaning matters more than wording, there are two good moves: ask the agent for a structured answer (`{"deadline": "2026-06-03"}`) that code can check exactly, or use a model.

A **model-based grader**, or judge, is a model call with a rubric: "Pass only if the answer states the deadline from the notes; fail if it hedges or contradicts them." Judges can grade explanations, summaries, and tone, which code can't. They also cost a model call per grade, can be wrong, and can be swayed by how an answer is written. Treat a judge as part of the eval set: version its prompt and model along with the cases, demand a strict JSON verdict, count a reply you can't parse as a grader error rather than a pass, and check its verdicts against a sample graded by people before you trust its numbers. :::warning
**Writing secrets into traces.** A trace records every tool result, so if the agent prints the environment or reads a config file, your key is now in `traces/`. Redact known secret patterns in the tracer itself, before anything is written, and keep `traces/` out of Git (Module 1's `.gitignore` already does).
:::

:::warning
**Editing eval cases in place.** Fixing a typo in a task's prompt changes the task. If you edit `tasks-v1.jsonl` and rerun, the new score and last week's aren't comparable, and nothing tells you so. Make a new version file, and print the version next to every score.
:::

:::quiz
Q: The harness crashes halfway through run 37 of 50. Which trace format still lets you see what run 37 did up to the crash?
- [x] JSON Lines, appended one event at a time as things happen
  Every line written before the crash is a complete JSON object, so only the line in progress is lost.
- [ ] One JSON array per run, written when the run ends
  The run never ended, so nothing was written.
- [ ] One JSON array per run, rewritten after every event
  That technically works, but rewriting the whole file each step gets slow, and a crash mid-rewrite can still corrupt it.

Q: You replay a trace from last week, and it diverges at step 2: `read_file("config.json")` returns different text. What have you learned?
- [ ] The model has changed since last week
  A replay doesn't call the model at all; it returns the recorded replies.
- [x] `config.json` changed since the recording, and that's the first point where the two runs saw different things
  Replay holds the model constant, so a divergence in a tool result points at the world, not the model.
- [ ] The replay is broken and should be rerun
  Divergence is the information replay is designed to give you.

Q: A grader checks `"42" in answer`. Which answer does it wrongly pass?
- [ ] "The answer is 42."
  That one is right, and it passes.
- [x] "It's 420, not 42."
  It contains "42" twice and is still wrong. Test graders on near-miss wrong answers.
- [ ] "Forty-two."
  This is right but fails the check, which is the opposite mistake.

Q: Two scores are printed: "8/10 (tasks a3f1c09e27d4)" and "9/10 (tasks 5b8e2d4c1f07)". What can you conclude?
- [ ] The agent improved by one task
  The versions differ, so the task sets differ.
- [x] Nothing yet; they were measured on different task sets and need to be rerun on the same version
  The version hash exists so that you notice this before drawing a conclusion.
:::

:::takeaways
- A trace records every model call, tool call, verification, and ending as it happens, with tokens and latency.
- JSON Lines survives crashes, appends cheaply, and is easy to stream and search.
- Replay returns recorded model replies so a run reproduces for free; the first divergence shows what changed in the world.
- Eval cases freeze the prompt, the starting files, and the checks; the dataset's hash goes next to every score.
- Prefer deterministic graders and test them on wrong answers; use a versioned, strict judge only where code can't decide.
:::
