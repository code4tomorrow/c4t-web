By the end of this lesson, two very different objects will answer the same method call. One is twenty lines of Python reading from a list. The other sends HTTP requests to a language model. The loop you build in Module 2 won't be able to tell them apart, and that's the whole design:

```mermaid caption="Two models, one method. The loop only ever calls complete()."
classDiagram
    class Model {
        name
        complete(messages, tools) reply
    }
    class ScriptedModel {
        script
        seen
    }
    class ChatAPIModel {
        url
        api_key
    }
    Model <|.. ScriptedModel
    Model <|.. ChatAPIModel
```

Python doesn't need a base class for this. Any object with a `name` and a `complete` method fits, which is called duck typing. The diagram's `Model` box is the contract, not a class you'll write.

One convention for the whole course: a code cell titled `harness/something.py` is a complete file. Save it at that path in `harness-lab`. The cells on each page share their names like a notebook, so later cells can use earlier ones. On disk, files reach each other with `import` lines, and each step tells you which ones to add.

## Step 1: Decide what a reply looks like

Providers disagree about tool calls. Ollama's native API sends arguments as a JSON object with no call id; the OpenAI-style API sends them as a JSON *string* with an id. If those formats leak into your loop, every provider change means a loop change. So the harness has its own format, and each real client translates at the edge.

A reply is a plain dictionary that doubles as the assistant message you append to the history, plus a `usage` entry for token counts:

```json
{
  "role": "assistant",
  "content": "",
  "tool_calls": [{"id": "call_1", "name": "read_file", "args": {"path": "notes.txt"}}],
  "usage": {"input_tokens": 120, "output_tokens": 14}
}
```

Plain dictionaries are easy to compare in tests and drop straight into JSON traces in Module 4. Here's the file:

```python run title="harness/model.py"
"""The one interface every model in the harness speaks:

    reply = model.complete(messages, tools)

messages  a list of dicts such as {"role": "user", "content": "..."}
tools     a list of tool schemas (Module 2 builds these)
reply     {"role": "assistant", "content": "...",
           "tool_calls": [{"id": "...", "name": "...", "args": {...}}],
           "usage": {"input_tokens": 0, "output_tokens": 0}}
"""
import copy
import itertools
import json


def estimate_tokens(text):
    """About 4 characters per token in English. Rough, but fine for budgets."""
    return max(1, len(text) // 4)


_ids = itertools.count(1)


def say(text):
    """A scripted reply that is a final answer."""
    return {"role": "assistant", "content": text, "tool_calls": []}


def call(name, **args):
    """A scripted reply that asks for one tool call."""
    return {"role": "assistant", "content": "",
            "tool_calls": [{"id": f"call_{next(_ids)}", "name": name, "args": args}]}


class ScriptedModel:
    """Replies from a list you write in advance: offline, free, identical every run."""

    name = "scripted"

    def __init__(self, script):
        self.script = list(script)
        self.seen = []  # a copy of the messages it was shown, one list per call

    def complete(self, messages, tools=None):
        self.seen.append(copy.deepcopy(messages))
        if not self.script:
            raise RuntimeError("ScriptedModel ran out of replies")
        reply = self.script.pop(0)
        if callable(reply):  # a reply can be a function of what the model was shown
            reply = reply(messages)
        shown = json.dumps(messages) + json.dumps(tools or [])
        written = reply["content"] + json.dumps(reply["tool_calls"])
        usage = {"input_tokens": estimate_tokens(shown), "output_tokens": estimate_tokens(written)}
        return {**reply, "usage": usage}
```

Three details matter later. `seen` stores a deep copy, so if the loop changes the history afterwards, your record of what the model was shown stays true. The token estimate counts the tool schemas too, because real providers bill for them as input. And `{**reply, "usage": usage}` builds a new dictionary instead of editing the scripted one.

## Step 2: Talk to the scripted model

A script is a list. `call(...)` makes a reply that asks for a tool, and `say(...)` makes a final answer:

```python run
model = ScriptedModel([
    call("read_file", path="notes.txt"),
    say("The deadline is June 3."),
])
history = [{"role": "user", "content": "When is the deadline?"}]

first = model.complete(history, tools=[])
print("first reply: ", first["tool_calls"], first["usage"])
second = model.complete(history, tools=[])
print("second reply:", repr(second["content"]))
print("calls made:  ", len(model.seen))
```

The model returned its replies in order and ignored what it was asked; a script doesn't read. That's enough for most tests. When a test needs a reply that depends on the conversation, use a function instead, and it receives the messages:

```python run
echo = ScriptedModel([lambda messages: say("You said: " + messages[-1]["content"])])
print(echo.complete([{"role": "user", "content": "ping"}])["content"])
```

Module 3 uses this to script a model that reads an error message and writes a fix.

What happens when the harness asks for more replies than you wrote? Predict, then look:

```python run raises
model = ScriptedModel([say("only one reply")])
model.complete([], [])
model.complete([], [])
```

A crash is the behavior you want. In a test, running out of replies means the harness called the model more often than you expected, which usually points to a loop that didn't stop. Returning an empty string instead would hide that bug.

## Step 3: Write the real client

`harness/chat_api.py` speaks the OpenAI chat-completions format, which Ollama serves under `http://localhost:11434/v1` and many hosted providers serve too. It has three parts: `to_wire` translates outgoing messages, `from_wire` translates the reply, and `ChatAPIModel` does the HTTP. The file needs no imports from the rest of the harness.

```python run title="harness/chat_api.py"
"""A real model behind the same interface: any OpenAI-compatible chat endpoint."""
import json
import os
import urllib.request


def to_wire(message):
    """Translate one harness message into the chat-completions format."""
    if message["role"] == "assistant" and message.get("tool_calls"):
        return {"role": "assistant", "content": message.get("content") or "",
                "tool_calls": [{"id": c["id"], "type": "function",
                                "function": {"name": c["name"], "arguments": json.dumps(c["args"])}}
                               for c in message["tool_calls"]]}
    if message["role"] == "tool":
        return {"role": "tool", "tool_call_id": message["tool_call_id"], "content": message["content"]}
    return {"role": message["role"], "content": message.get("content") or ""}


def from_wire(data):
    """Translate a chat-completions reply into a harness reply."""
    message = data["choices"][0]["message"]
    calls = []
    for number, raw in enumerate(message.get("tool_calls") or []):
        args = raw["function"].get("arguments") or "{}"
        if isinstance(args, str):  # the OpenAI format sends arguments as a JSON string
            args = json.loads(args)
        calls.append({"id": raw.get("id") or f"call_{number}", "name": raw["function"]["name"], "args": args})
    usage = data.get("usage") or {}
    return {"role": "assistant", "content": message.get("content") or "", "tool_calls": calls,
            "usage": {"input_tokens": usage.get("prompt_tokens", 0),
                      "output_tokens": usage.get("completion_tokens", 0)}}


class ChatAPIModel:
    """Ollama on this computer by default; any OpenAI-compatible provider otherwise."""

    def __init__(self, model=None, base_url=None, api_key=None, timeout=120):
        self.name = model or os.environ.get("LLM_MODEL", "qwen2.5:3b")
        base = base_url or os.environ.get("LLM_BASE_URL", "http://localhost:11434/v1")
        self.url = base.rstrip("/") + "/chat/completions"
        self.api_key = api_key or os.environ.get("LLM_API_KEY", "ollama")
        self.timeout = timeout

    def complete(self, messages, tools=None):
        body = {"model": self.name, "messages": [to_wire(m) for m in messages], "temperature": 0}
        if tools:
            body["tools"] = [{"type": "function", "function": schema} for schema in tools]
        request = urllib.request.Request(
            self.url, data=json.dumps(body).encode("utf-8"),
            headers={"Content-Type": "application/json", "Authorization": f"Bearer {self.api_key}"})
        with urllib.request.urlopen(request, timeout=self.timeout) as response:
            return from_wire(json.load(response))
```

Things to notice:

- **Defaults point at Ollama.** With no environment variables set, it calls `qwen2.5:3b` on your own machine. Ollama ignores the API key, but the header still needs a value.
- **`temperature: 0`** makes replies far less random. It doesn't make them identical every run, which is one more reason tests use the scripted model.
- **Missing ids get invented.** The harness pairs each tool result with the call that asked for it by id, so a call without one would break that pairing.
- **`timeout=120`** stops a stalled request from hanging the harness forever. A small model on a laptop CPU can take tens of seconds per reply, so the limit is generous.

## Step 4: Test the translation without a network

The HTTP part is five lines of standard library. The translation is where the bugs live, and it's pure functions, so you can test it with a reply copied from the API docs. This one asks for a tool call:

```python run
recorded = {
    "choices": [{"message": {
        "role": "assistant", "content": None,
        "tool_calls": [{"id": "call_abc", "type": "function",
                        "function": {"name": "read_file", "arguments": "{\"path\": \"notes.txt\"}"}}],
    }}],
    "usage": {"prompt_tokens": 91, "completion_tokens": 18},
}
reply = from_wire(recorded)
print(reply)
print(json.dumps(to_wire(reply)["tool_calls"][0]["function"]))
```

The arguments arrived as a string (`"{\"path\": ...}"`) and came out as a real dictionary. `content` was `None`, which many APIs send when the model only calls tools, and it became an empty string so later code can treat content as text without checking. Going back out, `to_wire` turns the dictionary back into a string. The `usage` key didn't leave the harness, since providers don't expect it.

## Step 5: The setup check

`check_setup.py` lives in the project root and starts with `from harness.model import ScriptedModel, call, say` and `from harness.chat_api import ChatAPIModel`. It prints one line per check: `ok`, `warn` for something that works but should be fixed, or `FAIL`.

```python run title="check_setup.py"
import sys

ADD_TOOL = {"name": "add", "description": "Add two integers.",
            "parameters": {"type": "object", "required": ["a", "b"],
                           "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}}}}


def report(level, label):
    print(f"[{level}] {label}")
    return level != "FAIL"


def live_checks():
    model = ChatAPIModel()
    try:
        reply = model.complete([{"role": "user", "content": "Reply with the single word: ready"}])
        yield report("ok", f"live model {model.name} answered: {reply['content'].strip()[:40]}")
        reply = model.complete([{"role": "user", "content": "Use the add tool to add 2 and 3."}], [ADD_TOOL])
        calls = reply["tool_calls"]
        if calls and calls[0]["name"] == "add":
            yield report("ok", f"live model can call tools: add({calls[0]['args']})")
        else:
            yield report("warn", "live model answered without calling the tool; try a model tagged tools")
    except Exception as exc:
        yield report("FAIL", f"live model {model.name}: {type(exc).__name__}: {exc}")


def main(live):
    results = [report("ok" if sys.version_info >= (3, 10) else "FAIL",
                      f"Python 3.10 or newer (found {sys.version.split()[0]})")]
    in_venv = sys.prefix != sys.base_prefix
    results.append(report("ok" if in_venv else "warn",
                          "inside a virtual environment" if in_venv else "not inside a virtual environment"))
    model = ScriptedModel([call("read_file", path="notes.txt"), say("done")])
    first, second = model.complete([], []), model.complete([], [])
    results.append(report("ok" if first["tool_calls"][0]["name"] == "read_file" and second["content"] == "done"
                          else "FAIL", "scripted model replies in order"))
    if live:
        results.extend(live_checks())
    print("Ready for the course" if all(results) else "Fix the FAIL lines and run it again")


main(live="--live" in sys.argv)
```

The page runs this outside any virtual environment, so you see a `warn` on that line. On your machine, with `.venv` active, it should say `ok`. Run it from the `harness-lab` folder:

```bash
python check_setup.py
python check_setup.py --live
```

The second command adds the two live checks. A working local setup looks something like this (your version numbers and the model's wording will differ):

```text
[ok] Python 3.10 or newer (found 3.12.7)
[ok] inside a virtual environment
[ok] scripted model replies in order
[ok] live model qwen2.5:3b answered: Ready
[ok] live model can call tools: add({'a': 2, 'b': 3})
Ready for the course
```

The second live check is the one that matters for this course: it proves the model returns real tool calls through your client, not just text. If you see `Connection refused`, Ollama isn't running; `HTTP Error 404` usually means the model isn't pulled. Lesson 3 has the full list of fixes.

:::quiz
Q: Why does `from_wire` invent an id like `call_0` when a tool call arrives without one?
- [ ] Providers reject replies without ids
  The id problem is on the harness side: it's the reply that's missing one.
- [x] The harness pairs each tool result with its call by id, so every call needs one
  Without an id, a tool result can't say which call it answers, and two calls in one reply would be ambiguous.
- [ ] To make the reply shorter
  An invented id adds text; it doesn't remove any.

Q: A test scripts two replies, but the harness under test calls `complete` three times. What should happen?
- [x] `ScriptedModel` raises `RuntimeError`, and the test fails
  The extra call is a bug in the harness, usually a loop that didn't stop, and a loud failure points straight at it.
- [ ] The model returns an empty reply so the run can finish
  That hides the bug: the run would end "successfully" with no answer.
- [ ] The script starts again from the first reply
  Repeating the script would make an endless loop look normal.

Q: Why is the reply format the harness's own, not the OpenAI format the client already receives?
- [ ] The OpenAI format can't represent tool calls
  It can; the client translates its tool calls in both directions.
- [x] So the loop doesn't change when you switch providers; only the translating client does
  Providers differ in details like arguments-as-string and missing ids. Keeping those differences at the edge keeps the loop simple.
:::

:::takeaways
- Every model implements `complete(messages, tools)` and returns a plain-dictionary reply with `content`, `tool_calls`, and `usage`.
- `ScriptedModel` makes the harness testable: fixed replies, a record of what it was shown, and a loud failure when it runs out.
- `ChatAPIModel` keeps provider details at the edge; its translation functions are pure, so you test them with recorded replies.
- `check_setup.py --live` proves the real model can make tool calls through your client, which is what the rest of the course needs.
:::

## Ideas to extend it

- Write `RecordingModel`, a wrapper that passes calls through to a real model and saves every reply to a JSON file. A saved list of replies is a script, so you can rerun a real conversation offline.
- Add a second adapter for Ollama's native `/api/chat` endpoint, whose tool-call arguments are objects and which has no call ids.
- Make `ChatAPIModel` read the response body when an `HTTPError` arrives and include it in the error message; providers explain most failures there.
