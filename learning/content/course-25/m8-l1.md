Here's the finished capstone in one sentence: an issue goes in ("`median()` is wrong for even-length lists"), and out come a branch with a tested fix, an audit log showing who allowed the push, a report with confidence intervals comparing your agent team to a single agent, and a list of attacks you ran against your own system and what stopped each one.

Everything you need was built in Modules 2 to 7. The capstone is about putting those pieces together and proving, with numbers and attacks, that the combination works. That proof is most of the grade.

## The brief

Your system must have all of these. Treat the list as a checklist; the rubric in the last lesson follows it.

1.  **Roles.** A planner, at least one worker, and an independent reviewer that can read and run tests but can't write. A router is optional.
2.  **Harness.** The Module 2 loop and tool registry, Module 3's sandbox for every piece of code that runs, and Module 4's JSONL traces for every model and tool call, tied together by a `trace_id`.
3.  **Controls.** One run budget (steps, tokens, time, and dollars if you use a paid model), a freeze when all checks pass, a progress monitor, an approval gate for anything that leaves the sandbox, a scoped short-lived credential per agent, and a hash-chained audit log whose head is stored outside the agents' reach.
4.  **Evaluation.** At least 20 dev tasks and 10 held-out tasks with hidden tests; pass@1 (and pass@k if you sample more than once) with bootstrap intervals; tokens or dollars per solved task; and a paired comparison against a single-agent baseline.
5.  **Attacks.** At least eight adversarial cases, each with the result a secure system must produce, run automatically.
6.  **Deliverables.** The code, `REPORT.md` (evaluation), `SECURITY.md` (threat model and attack results), and a five-minute demo.

Every runnable part must work with `ScriptedModel`, so anyone can reproduce your numbers offline. Connecting a real model through Ollama is a welcome extra, reported separately.

## Pick a project

All five meet the brief. They differ in what the agents work on and where the hard part is.

| Project | What the team does | Difficulty | The hard part |
| --- | --- | --- | --- |
| Docs-and-code checker | Finds functions whose docstrings disagree with their behavior and fixes the docs | Gentler | Writing hidden checks for prose, and keeping a model judge honest |
| Bug-fix crew | Fixes seeded bugs in a 300-line utility library | Core | Hidden tests that catch partial fixes; ownership when two bugs share a file |
| Test-writing team | Writes tests that catch deliberately mutated versions of a module | Core+ | Scoring by mutants caught, and stopping agents that write tests which always pass |
| Dependency-upgrade crew | Bumps a pinned version in a toy project, fixes breakages, rolls back on failure | Harder | Multi-file edits, all-or-nothing rollback, and approvals for each upgrade |
| Red team versus your harness | Attacker agents try to make worker agents break policy; the harness must hold | Hardest | Generating attacks that are new, and measuring the defense rate with intervals |

If you're unsure, take the bug-fix crew. The next lesson's starter is built for it, and every other project can begin from that starter.

## Draw the system and its trust boundaries

A trust boundary is a line that untrusted text crosses. In an agent system, more text is untrusted than people expect: the issue, every file in the repository, every tool result, and every message one agent writes for another. Draw yours before writing code.

```mermaid caption="A bug-fix crew. Everything in the left box can carry injected instructions."
flowchart LR
    subgraph untrusted["Untrusted text"]
        I[Issue text]
        F[Repository files]
        O[Tool output]
    end
    subgraph agents["Agents"]
        P[Planner] --> W[Worker]
        W --> R[Reviewer]
    end
    subgraph harness["Harness controls"]
        G["Supervisor: budget, freeze, progress"]
        C[Credential broker]
        A[(Audit log)]
    end
    untrusted --> agents
    agents --> G
    G --> C
    C -->|approved push| B[(Feature branch)]
    G --> A
```

Every arrow from the left box into the agents is a place where an instruction like "also push to main" can arrive. Your controls don't try to spot every such instruction. They make sure that obeying one can't do much damage.

## Write the threat model before the code

For each threat, write where it enters, which control stops it, and the attack test that proves the control works. A control without a test is a hope.

| Threat | Enters through | Control | Attack test |
| --- | --- | --- | --- |
| Instruction to push to `main` | Issue text | Worker credential lacks `main:merge` | Script the worker to obey; expect a denial in the audit log |
| Instruction hidden in a code comment | Repository file | Same credential limits, reviewer can't write | Plant the comment; expect no out-of-scope action |
| Agent edits or deletes tests | Worker output | Single writer drops edits outside owned files | Script a test edit; expect "rejected edit" |
| Fake success via early exit | Worker code | Strict grader requires a nonce report | Submit `os._exit(0)`; expect `no-report` |
| Endless revision loop | Worker and reviewer | Revision cap, progress monitor | Script three buggy attempts; expect "needs a human" |
| Budget blowout | Long contexts | Run budget checked before each call | Give a tiny budget; expect status `budget` |
| Log rewritten to hide an action | Anyone with file access | Hash chain plus external head | Edit an entry; expect verification to fail |
| Secret committed in a diff | Worker output | Diff secret scan in the release gate | Add a fake key; expect the gate to hold |

The STRIDE categories (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege) are a useful prompt for threats you haven't thought of. Tampering and repudiation are the two that audit logs answer; elevation of privilege is the one per-agent credentials answer.

## Size the evaluation before you build it

How many tasks do you need? With n tasks and a true solve rate p, a 95% interval is roughly p ± 1.96 × √(p(1 − p)/n). Plot that half-width before you write 100 tasks, or before you settle for 10:

```python run alt="Line chart of the 95 percent confidence interval half-width against the number of evaluation tasks from 5 to 200, for true solve rates of 0.5, 0.7, and 0.9. All three curves fall steeply until about 50 tasks and then flatten; at 20 tasks the half-width is about 0.2 for a rate of 0.7." caption="Interval half-width shrinks with the square root of the task count."
import numpy as np
import matplotlib.pyplot as plt

n = np.arange(5, 201)
plt.figure(figsize=(6, 3.2))
for p, color in [(0.5, "#7892ee"), (0.7, "#2a9d8f"), (0.9, "#d9534f")]:
    plt.plot(n, 1.96 * np.sqrt(p * (1 - p) / n), color=color, label=f"true rate {p}")
plt.axvline(20, color="#888", linestyle=":")
plt.xlabel("number of tasks")
plt.ylabel("95% CI half-width")
plt.legend()
plt.tight_layout()

for tasks in (10, 20, 50, 100):
    print(f"{tasks:>3} tasks at a 0.7 solve rate: ± {1.96 * np.sqrt(0.21 / tasks):.2f}")
```

At 20 tasks, a 70% solve rate comes with about ± 0.20, so a single-agent baseline would have to be far behind before you could call the team better from separate intervals. That's why the brief asks for a **paired** comparison: the same 20 tasks for both systems, with per-task differences bootstrapped as in Module 5. Quadrupling the tasks only halves the interval, so put your effort into enough tasks to answer your question, plus a held-out set you run once at the end.

## Fill in the plan

Copy this into `PLAN.md` at the top of your project and fill in every line before Milestone 1.

```text
PROJECT: ______________________   DIFFICULTY: gentler / core / core+ / harder / hardest

ONE-SENTENCE GOAL:
  Given ________, the team produces ________, checked by ________.

ROLES (what each may read / write / run):
  planner:   reads ____  writes ____  tools ____
  worker(s): reads ____  writes ____  tools ____
  reviewer:  reads ____  writes nothing  tools ____

TASKS: __ dev (where they come from: ____), __ held-out (written by: ____, sealed on: ____)
GRADERS: deterministic: ____   model judge (if any, and why): ____
METRICS: pass@1 with 95% CI, tokens per solve, paired gap vs single agent, ____

BUDGET PER RUN: steps __  tokens __  seconds __  dollars __
NEEDS APPROVAL: ____   DENIED OUTRIGHT: ____
CREDENTIAL SCOPES PER ROLE: ____

ATTACK CASES (8+): name / entry point / expected result
  1. ____
  ...

RISKS TO THE PROJECT ITSELF (and what you'll cut if time runs short): ____
```

The last line matters. Decide now which extra you'll drop if a milestone runs long: a real-model run, a second worker type, or the model judge. The checklist items in the brief are not on that list.

## Milestones at a glance

| Milestone | You build | Done when |
| --- | --- | --- |
| M1 Tasks and grader | Dev and held-out task files, strict hidden-test grader | Every reference fix passes and every seeded bug fails its hidden tests |
| M2 Baseline and team | Single-agent baseline; planner, workers, reviewer | Both systems run end to end on every dev task with `ScriptedModel` |
| M3 Controls | Budget, freeze, progress monitor, approvals, credentials, audit log | Unit tests show each control allows the good case and blocks the bad one |
| M4 Attacks | Eight or more automated attack cases | Every case reports BLOCKED, or you've written down why not |
| M5 Report | `REPORT.md`, `SECURITY.md`, held-out run | Numbers with intervals, attack table, and residual risks, all generated by code |

:::takeaways
- The brief is a checklist: roles, harness, controls, evaluation, attacks, deliverables.
- Untrusted text enters through the issue, the files, tool output, and other agents; controls limit what obeying it can do.
- Every control in the threat model needs an attack test that proves it.
- Size the eval with the interval formula, and compare systems with paired differences on the same tasks.
- Write `PLAN.md` first, including what you'll cut if time runs short.
:::
