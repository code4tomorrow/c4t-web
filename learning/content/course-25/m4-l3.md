- Answer questions about runs by computing over trace events: error rates, percentiles, and totals.
- Redact secrets from events before they reach disk, without damaging the fields you need.
- Turn a bad real run into a regression test that replays it offline.

- Grade the order of tool calls, and measure how far a judge agrees with people beyond chance.

Every exercise here works on plain lists and dictionaries shaped like the events from `harness/tracing.py`, so the solutions run without the rest of the harness. Once one works, it's a few lines to point it at `read_trace("traces/...")` instead.

## Warm-up: read a trace by eye

Here are eight events from one run. Before running anything, answer three questions: how many steps did it take, how many tool calls failed, and did it finish?

```python run
import json

trace = """{"run": "r7", "step": 0, "type": "start", "task": "Fix the failing test"}
{"run": "r7", "step": 1, "type": "model", "input_tokens": 410, "output_tokens": 20}
{"run": "r7", "step": 1, "type": "tool", "tool": "run_tests", "ok": true}
{"run": "r7", "step": 2, "type": "model", "input_tokens": 980, "output_tokens": 60}
{"run": "r7", "step": 2, "type": "tool", "tool": "write_file", "ok": false}
{"run": "r7", "step": 2, "type": "tool", "tool": "read_file", "ok": true}
{"run": "r7", "step": 3, "type": "model", "input_tokens": 1460, "output_tokens": 25}
{"run": "r7", "step": 3, "type": "end", "status": "done", "answer": "Fixed."}"""

events = [json.loads(line) for line in trace.splitlines()]
tools = [e for e in events if e["type"] == "tool"]
print("steps:", events[-1]["step"], "| tool calls:", len(tools),
      "| tool errors:", sum(not e["ok"] for e in tools), "| status:", events[-1]["status"])
```

Three steps, one failed tool call, done. Step 2 made two tool calls in one reply, which is why there are three tool events but only two steps with tools. Notice that the run's status is `done` even though a write failed. A status says how the run *ended*, not whether everything inside it went well, which is why traces matter.

### Exercise 1: Which tool fails most?

Given tool events from many runs, print each tool's number of calls, number of errors, and error rate, sorted from the worst rate to the best.

Sample output:

```text
run_tests     6 calls   2 errors    33%
read_file    10 calls   3 errors    30%
write_file    4 calls   0 errors     0%
list_files    5 calls   0 errors     0%
```

:::hint
Two `Counter`s, one for calls and one for errors, keyed by tool name. `not event["ok"]` is `True` or `False`, and adding a bool to a counter adds 1 or 0.
:::

:::solution
```python run
from collections import Counter

log = {"read_file": "ok ok fail ok ok fail ok ok fail ok", "write_file": "ok ok ok ok",
       "run_tests": "ok fail ok ok fail ok", "list_files": "ok ok ok ok ok"}
events = [{"type": "tool", "tool": tool, "ok": word == "ok"}
          for tool, words in log.items() for word in words.split()]

calls, errors = Counter(), Counter()
for event in events:
    if event["type"] == "tool":
        calls[event["tool"]] += 1
        errors[event["tool"]] += not event["ok"]

for tool in sorted(calls, key=lambda t: errors[t] / calls[t], reverse=True):
    print(f"{tool:<11} {calls[tool]:>3} calls  {errors[tool]:>2} errors  {errors[tool] / calls[tool]:>5.0%}")
```

`read_file` has the most errors (3), but `run_tests` fails at a higher rate (33%). Sorting by rate, not count, points at the tool that's least reliable per call. With only six calls, though, one more failure would move `run_tests` from 33% to 43%, so treat small counts as hints, not conclusions. In a real project, the next step is to open the failing events and read their error messages: a high `read_file` error rate usually means the model guesses file names, which a better tool description fixes.
:::

### Exercise 2: Redact before you write

Write `redact(value)` that returns a copy of an event with secrets replaced by `[REDACTED]`. Replace any string that looks like an API key (`sk-` or `ghp_` followed by a run of letters and digits), and any string value whose key name contains `key`, `token`, `secret`, or `password`. It has to walk nested dictionaries and lists.

Sample output:

```text
{
 "run": "r9",
 "step": 4,
 "type": "tool",
 "tool": "read_file",
 "args": {
  "path": ".env"
 },
 "ok": true,
 "result": "LLM_API_KEY=[REDACTED]\nDEBUG=1\nGITHUB=[REDACTED]",
 "headers": {
  "Authorization": "Bearer [REDACTED]",
  "api_key": "[REDACTED]"
 }
}
```

:::hint
Recursion handles the nesting: a dictionary maps `redact` over its values (passing the key name down), a list maps it over its items, and a string is where the replacing happens. Everything else comes back unchanged.
:::

:::solution
```python run
import json
import re

SECRET_TEXT = re.compile(r"\b(sk-[A-Za-z0-9_-]{8,}|ghp_[A-Za-z0-9]{20,})")
SECRET_NAME = re.compile(r"key|token|secret|password", re.IGNORECASE)


def redact(value, name=""):
    """Return a copy of value with secret-looking strings replaced."""
    if isinstance(value, dict):
        return {k: redact(v, k) for k, v in value.items()}
    if isinstance(value, list):
        return [redact(v, name) for v in value]
    if isinstance(value, str):
        if SECRET_NAME.search(name):
            return "[REDACTED]"
        return SECRET_TEXT.sub("[REDACTED]", value)
    return value


event = {"run": "r9", "step": 4, "type": "tool", "tool": "read_file", "args": {"path": ".env"}, "ok": True,
         "result": "LLM_API_KEY=sk-live-4f9a8b7c6d5e\nDEBUG=1\nGITHUB=ghp_abcdefghijklmnopqrstuvwx",
         "headers": {"Authorization": "Bearer sk-live-4f9a8b7c6d5e", "api_key": "anything at all"}}
print(json.dumps(redact(event), indent=1))
```

Both rules earned their place: the pattern caught keys inside the `.env` text and the `Authorization` header, and the name rule caught `api_key`, whose value doesn't look like a key at all. Only strings are replaced, which matters: a trace's `input_tokens` field contains "token" in its name, but it's a number, so it survives. To use this, call `redact` inside `Tracer.event` on the record before `json.dumps`, so nothing unredacted is ever written. Pattern lists always miss something, so keep traces out of Git anyway.
:::

### Exercise 3: Latency that tells the truth

Forty model-call latencies, in milliseconds, include one call that stalled for 24 seconds. Print the count, mean, median (p50), 95th percentile (p95), and maximum. Then print the mean and median again without the stall.

Sample output:

```text
calls 40  mean 1,261 ms  p50 648 ms  p95 1,141 ms  max 24,000 ms
without the stall: mean 678 ms  p50 648 ms
```

:::hint
`statistics.quantiles(data, n=100, method="inclusive")` returns 99 cut points; the 50th and 95th (indexes 49 and 94) are p50 and p95.
:::

:::solution
```python run
import random
import statistics

rng = random.Random(5)
latencies = [round(rng.lognormvariate(6.5, 0.35)) for _ in range(39)] + [24_000]   # ms; one call stalled

cuts = statistics.quantiles(latencies, n=100, method="inclusive")
p50, p95 = cuts[49], cuts[94]
print(f"calls {len(latencies)}  mean {statistics.mean(latencies):,.0f} ms  "
      f"p50 {p50:,.0f} ms  p95 {p95:,.0f} ms  max {max(latencies):,} ms")
without = latencies[:-1]
print(f"without the stall: mean {statistics.mean(without):,.0f} ms  p50 {statistics.median(without):,.0f} ms")
```

One stalled call nearly doubled the mean, from 678 to 1,261 ms, and left the median exactly where it was. The mean describes neither a typical call nor the worst one. Report the median for "usually," p95 for "almost always," and the maximum for "worst seen." Here the stall sits above p95, since it's 1 call in 40, so the maximum is the only number that shows it. That's an argument for timeouts on model calls too.
:::

### Exercise 4: A regression test from a bad run

A real model emptied `calc.py` by writing an empty string, then said "Done!" You've added a guard that refuses empty writes. Turn the trace into a test that proves the guard holds: write `script_from_trace(events)` that returns the model's replies in order, replay their writes against the original files with and without the guard, and add a `unittest` that fails if the file gets emptied.

Sample output:

```text
old harness: {'calc.py': ''}
new harness: {'calc.py': 'def add(a, b):\n    return a - b\n'}
test_run_r12_cannot_empty_a_file (__main__.RegressionTests.test_run_r12_cannot_empty_a_file) ... ok

----------------------------------------------------------------------
Ran 1 test in 0.000s

OK
```

:::hint
The `model` events already contain `content` and `tool_calls`, which is everything a reply needs. A list comprehension with `if e["type"] == "model"` builds the script.
:::

:::solution
```python run
import sys
import unittest

recorded = [   # trace r12 from a real model, trimmed: it emptied calc.py and declared victory
    {"step": 0, "type": "start", "task": "Fix calc.py"},
    {"step": 1, "type": "model", "content": "", "tool_calls": [
        {"id": "a1", "name": "read_file", "args": {"path": "calc.py"}}]},
    {"step": 1, "type": "tool", "tool": "read_file", "ok": True, "result": "def add(a, b):\n    return a - b\n"},
    {"step": 2, "type": "model", "content": "", "tool_calls": [
        {"id": "a2", "name": "write_file", "args": {"path": "calc.py", "content": ""}}]},
    {"step": 2, "type": "tool", "tool": "write_file", "ok": True, "result": "wrote 0 characters to calc.py"},
    {"step": 3, "type": "model", "content": "Done!", "tool_calls": []},
    {"step": 3, "type": "end", "status": "done", "answer": "Done!"},
]


def script_from_trace(events):
    """The model's side of a run, as replies a ScriptedModel can play back."""
    return [{"role": "assistant", "content": e["content"], "tool_calls": e["tool_calls"]}
            for e in events if e["type"] == "model"]


def replay_writes(script, files, allow_write):
    """A stand-in for run_agent: apply the script's writes that the guard allows."""
    for reply in script:
        for c in reply["tool_calls"]:
            if c["name"] == "write_file" and allow_write(c["args"]):
                files[c["args"]["path"]] = c["args"]["content"]
    return files


def no_empty_writes(args):          # the fix this test protects
    return bool(args["content"].strip())


START = {"calc.py": "def add(a, b):\n    return a - b\n"}
print("old harness:", replay_writes(script_from_trace(recorded), dict(START), lambda args: True))
print("new harness:", replay_writes(script_from_trace(recorded), dict(START), no_empty_writes))


class RegressionTests(unittest.TestCase):
    def test_run_r12_cannot_empty_a_file(self):
        files = replay_writes(script_from_trace(recorded), dict(START), no_empty_writes)
        self.assertEqual(files["calc.py"], START["calc.py"])


unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(
    unittest.defaultTestLoader.loadTestsFromTestCase(RegressionTests))
```

The script is exactly what a `ScriptedModel` takes, so in your project the test can call the real `run_agent` with `ScriptedModel(script_from_trace(read_trace("traces/r12.jsonl")))`. The run you saw once, with a real model, is now a test that fails the same way every time the guard is missing. Name tests after the trace they came from (`r12` here) so the next person can find the original run.
:::

### Exercise 5: A held-out split that never reshuffles

Keep about 20% of eval cases as a held-out set that you don't look at while improving the agent. Write `held_out(case_id)` that decides from the id alone, gives the same answer on every machine and every run, and doesn't move existing cases when new ones are added. Then show why Python's built-in `hash()` can't do this.

Sample output:

```text
held out 7 of 40: task-001, task-013, task-024, task-028, task-034, task-036, task-039
built-in hash() bucket with PYTHONHASHSEED=1: 10
built-in hash() bucket with PYTHONHASHSEED=2: 72
```

:::hint
`hashlib.sha256(text.encode()).hexdigest()` is the same everywhere. Turn it into a number with `int(..., 16)` and take `% 100` to get a bucket from 0 to 99.
:::

:::solution
```python run
import hashlib
import os
import subprocess
import sys


def held_out(case_id, percent=20):
    """Same answer on every machine, every run: hash the id, keep the bottom `percent` of 100 buckets."""
    bucket = int(hashlib.sha256(case_id.encode("utf-8")).hexdigest(), 16) % 100
    return bucket < percent


ids = [f"task-{n:03}" for n in range(1, 41)]
test = [i for i in ids if held_out(i)]
print(f"held out {len(test)} of {len(ids)}:", ", ".join(test))

probe = "print(hash('task-001') % 100)"
for seed in ("1", "2"):
    out = subprocess.run([sys.executable, "-c", probe], env={**os.environ, "PYTHONHASHSEED": seed},
                         capture_output=True, text=True).stdout.strip()
    print(f"built-in hash() bucket with PYTHONHASHSEED={seed}: {out}")
```

Seven of forty is close to 20% but not exact, because each id lands in a bucket independently; that's the price of a split that never needs to be recomputed. Adding `task-041` can't move any existing case between sets. Python's `hash()` on strings is randomized per process (so that attackers can't craft inputs that collide), which is why the same id landed in bucket 10 under one seed and 72 under another. A split built on it would quietly reshuffle every time you ran it.
:::

### Exercise 6: Grade the order of tool calls

For a bug fix, a good run reads the file, writes a fix, and runs the tests, in that order, though it may make other calls in between. Write `follows(called, expected, forbidden)` that checks the expected calls appear in order, and that no forbidden tool (here, `write_tests`) was ever used. Return whether it passed and which forbidden tools appeared.

Sample output:

```text
textbook     pass  
extra looks  pass  
tests first  FAIL  
edits tests  FAIL  used write_tests
never tests  FAIL  
```

:::hint
There's a neat idiom for "is `expected` a subsequence of `called`": make one iterator over `called`, and for each expected step, search forward with `any(c == step for c in iterator)`. Each search continues where the last one stopped.
:::

:::solution
```python run
def follows(called, expected, forbidden=()):
    """expected must appear in order (other calls may come between); forbidden must never appear."""
    remaining = iter(called)
    in_order = all(any(c == step for c in remaining) for step in expected)
    banned = sorted(set(called) & set(forbidden))
    return in_order and not banned, banned


expected = ["read_file", "write_file", "run_tests"]
runs = {
    "textbook": ["read_file", "write_file", "run_tests"],
    "extra looks": ["list_files", "read_file", "read_file", "write_file", "run_tests"],
    "tests first": ["run_tests", "read_file", "write_file"],
    "edits tests": ["read_file", "write_file", "write_tests", "run_tests"],
    "never tests": ["read_file", "write_file"],
}
for name, called in runs.items():
    ok, banned = follows(called, expected, forbidden=["write_tests"])
    print(f"{name:<12} {'pass' if ok else 'FAIL'}  {'used ' + ', '.join(banned) if banned else ''}")
```

Because all the searches share one iterator, `tests first` fails: after finding `run_tests` at the start, nothing is left to find it again after `write_file`. `extra looks` passes, since looking around is fine. The `edits tests` run is the one to worry about: it called the tests *after* editing them, so its passing tests prove nothing. Forbidding tools that change the grader's evidence is the start of Module 5's work on agents that game their graders.
:::

### Challenge: Does the judge agree with people?

Twenty answers were graded by people and by the judge. Compute the raw agreement, the agreement you'd expect by chance from each grader's pass rate, and **Cohen's kappa**, which measures agreement beyond chance:

```text
kappa = (observed - expected) / (1 - expected)
```

List which answers the judge got wrong, in each direction. Then compute the same numbers for a "judge" that passes everything.

Sample output:

```text
raw agreement 0.70   expected by chance 0.58   Cohen's kappa 0.29
judge passed answers people failed: [12, 13, 14, 15, 16, 17]
judge failed answers people passed: []
a judge that always says pass: agreement 0.60, kappa 0.00
```

:::hint
The chance agreement is the probability that both say pass plus the probability that both say fail, if they each picked independently at their own rates: `(a.count("P")/n) * (b.count("P")/n) + (a.count("F")/n) * (b.count("F")/n)`.
:::

:::solution
```python run
human = "PPPPPPPPPPPPFFFFFFFF"       # 12 passes, 8 fails, graded by people
judge = "PPPPPPPPPPPPPPPPPPFF"       # the judge, on the same 20 answers


def agreement(a, b, labels=("P", "F")):
    n = len(a)
    observed = sum(x == y for x, y in zip(a, b)) / n
    expected = sum((a.count(label) / n) * (b.count(label) / n) for label in labels)   # agreement by luck
    kappa = (observed - expected) / (1 - expected)
    return observed, expected, kappa


observed, expected, kappa = agreement(human, judge)
print(f"raw agreement {observed:.2f}   expected by chance {expected:.2f}   Cohen's kappa {kappa:.2f}")
missed = [i for i, (h, j) in enumerate(zip(human, judge)) if h == "F" and j == "P"]
too_harsh = [i for i, (h, j) in enumerate(zip(human, judge)) if h == "P" and j == "F"]
print("judge passed answers people failed:", missed)
print("judge failed answers people passed:", too_harsh)

always_pass = "P" * 20
print("a judge that always says pass: agreement {:.2f}, kappa {:.2f}".format(*agreement(human, always_pass)[::2]))
```

70% agreement sounds decent until you see that a judge that never reads anything gets 60%. Kappa removes the agreement that two graders would reach by luck, given how often each says pass: 0 means no better than chance, 1 means perfect. This judge's 0.29 is weak, and the error list says why: it passed six answers people failed and never failed one they passed, so it's lenient, and a lenient judge inflates scores. Fix the rubric (spell out what makes an answer fail), rerun on the same twenty, and only trust the judge's numbers once kappa is high. Many teams look for 0.6 or more, but the bar depends on what a wrong grade costs you.
:::
