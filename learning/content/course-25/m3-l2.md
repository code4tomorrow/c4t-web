In Module 2, `verify` checked whether `calc.py` *contained* `a + b`, which a wrong fix could pass. This lesson replaces that with the real check: run the tests. Running code is what the sandbox is for, so you'll build it first, then attack it, then hand the agent a tool that uses it. Here's the path one piece of code takes through `run_python`:

```mermaid caption="run_python. Every exit path kills the process group and returns the same dictionary."
flowchart TD
    A["write main.py and job files into a new temp folder"] --> B["start Python: -I, clean env, no stdin, own session"]
```

## Step 1: Limits the child sets on itself

Some limits can't be set from outside a process; the process has to set them on itself. `preexec_fn` is a function that `subprocess` runs inside the child after it's created and before Python starts, which is the moment to set them. Here's the top of `harness/sandbox.py`:

```python run title="harness/sandbox.py (part 1 of 2)"
"""Run model-written Python in a child process with limits.

This stops accidents (hangs, floods of output, leaked secrets). It is not a
security boundary: the child can still read any file your user account can.
"""
import os
import signal
import subprocess
import sys
import tempfile
import time
from pathlib import Path

KEEP_ENV = ("PATH", "SYSTEMROOT", "LANG")  # Windows needs SYSTEMROOT to start Python
POSIX = os.name == "posix"


def _set_limits(file_bytes, cpu_seconds):
    def apply():  # runs inside the child just before Python starts (POSIX only)
        import resource
        resource.setrlimit(resource.RLIMIT_FSIZE, (file_bytes, file_bytes))
        resource.setrlimit(resource.RLIMIT_CPU, (cpu_seconds, cpu_seconds))
    return apply


def _head(stream, limit):
    stream.seek(0)
    data = stream.read(limit + 1)
    return data[:limit].decode("utf-8", errors="replace"), len(data) > limit


def _tail(stream, limit):  # the end of stderr is where the error message is
    size = stream.seek(0, os.SEEK_END)
    stream.seek(max(0, size - limit))
    return stream.read().decode("utf-8", errors="replace"), size > limit
```

`RLIMIT_FSIZE` caps the size of any file the child writes, at 1 MB by default. That includes the files its output goes to, which is how the output cap is enforced: past the limit, Python raises `OSError` instead of filling your disk. `RLIMIT_CPU` caps CPU seconds, a second line of defense behind the wall-clock timeout. Both soft and hard limits are set to the same value, and an unprivileged process can't raise its own hard limit, so the code can't undo them.

`_head` and `_tail` read at most `limit` bytes from the start or end of an output file. Normal output reads best from the start. Tracebacks and test summaries are at the end, so stderr keeps its tail.

:::note
Python's docs warn that `preexec_fn` isn't safe in a program that uses threads, because the child can deadlock before it starts. The harness is single-threaded. If yours grows threads, set the limits in a small wrapper script that the child runs first instead.
:::

## Step 2: run_python

The rest of the file is one function:

```python run title="harness/sandbox.py (part 2 of 2)"
def run_python(code, files=None, timeout=5, max_output=2000, max_file_bytes=1_000_000):
    started = time.perf_counter()
    with tempfile.TemporaryDirectory(prefix="sandbox-") as work, \
            tempfile.TemporaryFile() as out, tempfile.TemporaryFile() as err:
        for name, text in {**(files or {}), "main.py": code}.items():
            (Path(work) / name).write_text(text, encoding="utf-8")
        env = {key: os.environ[key] for key in KEEP_ENV if key in os.environ}
        env["HOME"] = env["TMPDIR"] = work
        child = subprocess.Popen(
            [sys.executable, "-I", "main.py"], cwd=work, env=env,
            stdin=subprocess.DEVNULL, stdout=out, stderr=err,
            start_new_session=POSIX,
            preexec_fn=_set_limits(max_file_bytes, timeout + 1) if POSIX else None,
        )
        try:
            child.wait(timeout=timeout)
            timed_out = False
        except subprocess.TimeoutExpired:
            timed_out = True
        if POSIX:  # kill the whole process group: the child and anything it started
            try:
                os.killpg(child.pid, signal.SIGKILL)
            except (ProcessLookupError, PermissionError):
                pass  # the group is already gone
        else:
            child.kill()
        exit_code = child.wait()
        stdout, cut_out = _head(out, max_output)
        stderr, cut_err = _tail(err, max_output)
        for folder in sorted({os.path.realpath(work), work}, key=len, reverse=True):
            stderr = stderr.replace(folder + os.sep, "")  # "main.py" reads better than a temp path
    return {"exit_code": exit_code, "timed_out": timed_out, "stdout": stdout, "stderr": stderr,
            "truncated": cut_out or cut_err, "seconds": round(time.perf_counter() - started, 2)}

print(run_python("print(2 + 2)"))
```

The last line is only for this page. Things to notice:

- **Output goes to temporary files outside the job folder**, not to pipes. A pipe fills up and blocks the child if nobody reads it, and the child can't overwrite a file it can't see.
- **The process group is killed on every exit**, even a clean one, so a worker the code started in the background can't outlive the job.
- **`HOME` and `TMPDIR` point at the job folder**, so code that writes to `~` or to the temp directory writes somewhere that gets deleted.
- **Temporary paths are stripped from stderr.** `File "main.py", line 1` is shorter and means more to the model than a full temp path. On macOS, the temp folder has two names (`/var/...` and `/private/var/...`), so the longer one is replaced first.
- **The result is a plain dictionary**, so it can be a tool result and, in Module 4, a trace entry without any conversion.

## Step 3: Attack it

Here's hostile code, one line per attack. Before you run it, predict each row's `exit` and `timed_out`:

```python run
os.environ["LLM_API_KEY"] = "sk-demo-not-a-real-key"
cases = [
    ("prints 4", "print(2 + 2)"),
    ("infinite loop", "while True:\n    pass"),
    ("waits for input", "n = input('number? ')"),
    ("floods output", "while True:\n    print('spam' * 50)"),
    ("reads the key", "import os\nprint(os.environ.get('LLM_API_KEY'))"),
    ("crashes", "print(1 / 0)"),
]
for label, code in cases:
    r = run_python(code, timeout=1)
    last = (r["stderr"].strip().splitlines() or [""])[-1]
    print(f"{label:<16} exit={r['exit_code']:>3} timed_out={r['timed_out']!s:<5} truncated={r['truncated']!s:<5} "
          f"{r['seconds']:>4}s  stdout={r['stdout'][:12]!r:<15} {last}")
```

Read the rows:

- **The infinite loop** hit the one-second limit and was killed. Exit code `-9` means "killed by signal 9" (`SIGKILL`) on macOS and Linux.
- **`input()`** failed instantly with `EOFError`, because stdin is closed, instead of hanging.
- **The flood** stopped itself when its output file reached 1 MB. `OSError: [Errno 27] File too large` is the file-size limit, and `truncated=True` says the harness kept only part of the output.
- **The key** printed `None`, because the child's environment never had it.
- **The crash** came back as data: exit code 1 and the last line of the traceback, ready to show the model.

The sandbox has done its job when bad code turns into a row like these, never a frozen harness or a full disk. Reading your files and using the network still aren't blocked, as the Notes showed; for that, run the whole harness in a container.

## Step 4: A narrow tool for the agent

You could register `run_python` as a tool and let the model run anything. It's better to give the model the narrowest tool that does the job. Here, the job is "run the project's tests," so that's the tool. It copies the workspace's top-level `.py` files into the sandbox and runs `unittest` discovery there. It starts with `from harness.sandbox import run_python`:

```python run title="harness/test_tool.py"
"""The agent's one way to execute code: run the workspace's tests inside the sandbox."""

TEST_RUNNER = """import sys, unittest
suite = unittest.defaultTestLoader.discover(".", pattern="test*.py")
result = unittest.TextTestRunner(verbosity=1).run(suite)
sys.exit(0 if result.wasSuccessful() else 1)
"""


def run_tests_in(root, timeout=10):
    files = {path.name: path.read_text(encoding="utf-8") for path in Path(root).glob("*.py")}
    outcome = run_python(TEST_RUNNER, files=files, timeout=timeout)
    return {"passed": outcome["exit_code"] == 0, **outcome}


def add_test_tool(registry, root):
    @registry.tool("run_tests", "Run the workspace's unittest tests in a sandbox. "
                   "Returns passed, exit_code, timed_out, and the test output in stderr.", {})
    def run_tests():
        return run_tests_in(root)
```

There's a subtlety in `-I`. Isolated mode leaves the job folder off `sys.path`, so a plain `import calc` from `main.py` would fail. `unittest` discovery adds the folder it searches to `sys.path` itself, which is why the tests can import `calc` anyway. Give it a buggy workspace:

```python run
Path("workspace").mkdir(exist_ok=True)
Path("workspace/calc.py").write_text("def add(a, b):\n    return a - b\n")
Path("workspace/test_calc.py").write_text('''import unittest
from calc import add


class AddTests(unittest.TestCase):
    def test_small_numbers(self):
        self.assertEqual(add(2, 3), 5)

    def test_negative_numbers(self):
        self.assertEqual(add(-2, -3), -5)
''')
outcome = run_tests_in("workspace")
print("passed:", outcome["passed"], " exit code:", outcome["exit_code"])
for line in outcome["stderr"].splitlines():
    if line.startswith(("FAIL:", "AssertionError", "FAILED")):
        print(line)
```

Both tests failed, and the output says exactly how: `-1 != 5` and `1 != -5`. Those lines are filtered out of the full output here to keep the page short; the model gets all of it, up to the output cap.

## Step 5: Retry what's temporary

Model calls fail too: rate limits, overloaded servers, dropped connections. `harness/retry.py` retries those and lets everything else through on the first try. It needs no imports from the rest of the harness:

```python run title="harness/retry.py"
"""Retry transient failures with capped exponential backoff and full jitter."""
import random
import time
import urllib.error

RETRY_STATUS = {408, 429, 500, 502, 503, 504}


class TransientError(Exception):
    """A failure that may succeed if you wait and try again."""


def is_transient(exc):
    if isinstance(exc, urllib.error.HTTPError):  # check first: it is also a URLError
        return exc.code in RETRY_STATUS
    return isinstance(exc, (TransientError, urllib.error.URLError, TimeoutError, ConnectionError))


def with_retries(fn, attempts=4, base=0.5, cap=8.0, retry_if=is_transient,
                 sleep=time.sleep, rng=None):
    rng = rng or random.Random()
    for attempt in range(attempts):
        try:
            return fn()
        except Exception as exc:
            if attempt == attempts - 1 or not retry_if(exc):
                raise
            sleep(rng.uniform(0, min(cap, base * 2 ** attempt)))


class RetryingModel:
    """Wraps any model so the loop never sees a failure that one more try would fix."""

    def __init__(self, model, **options):
        self.model, self.options = model, options
        self.name = getattr(model, "name", "model")

    def complete(self, messages, tools=None):
        return with_retries(lambda: self.model.complete(messages, tools), **self.options)
```

`HTTPError` is a subclass of `URLError`, so it's checked first. Otherwise a 401 would match the `URLError` line and be retried forever. Passing `sleep` and `rng` in makes the function testable: a test can record the waits instead of sleeping through them.

```python run
import io

def http_error(code):
    return urllib.error.HTTPError("https://api.example/v1", code, "error", {}, io.BytesIO(b""))

for exc in [http_error(429), http_error(503), http_error(401), http_error(400),
            urllib.error.URLError("connection refused"), ValueError("bad JSON from our own code")]:
    print(f"{type(exc).__name__:<10} {str(exc)[:34]:<36} retry: {is_transient(exc)}")

waits = []
attempts = iter([TransientError("503"), TransientError("503"), "ok"])

def flaky():
    result = next(attempts)
    if isinstance(result, Exception):
        raise result
    return result

print(with_retries(flaky, sleep=waits.append, rng=random.Random(1)), [round(w, 2) for w in waits])
```

Two failures, two short random waits under 0.5 and 1 second, then success. A `ValueError` from your own code is never retried: it's a bug, and it should surface.

## Step 6: The rest of the harness

The final program uses the files from Modules 1 and 2. They're unchanged; skip past them if you have them open. First `harness/model.py`:

```python run title="harness/model.py"
"""The one interface every model in the harness speaks:

    reply = model.complete(messages, tools)

messages  a list of dicts such as {"role": "user", "content": "..."}
tools     a list of tool schemas (Module 2 builds these)
reply     {"role": "assistant", "content": "...",
           "tool_calls": [{"id": "...", "name": "...", "args": {...}}],
           "usage": {"input_tokens": 0, "output_tokens": 0}}
"""
import copy
import itertools
import json


def estimate_tokens(text):
    """About 4 characters per token in English. Rough, but fine for budgets."""
    return max(1, len(text) // 4)


_ids = itertools.count(1)


def say(text):
    """A scripted reply that is a final answer."""
    return {"role": "assistant", "content": text, "tool_calls": []}


def call(name, **args):
    """A scripted reply that asks for one tool call."""
    return {"role": "assistant", "content": "",
            "tool_calls": [{"id": f"call_{next(_ids)}", "name": name, "args": args}]}


class ScriptedModel:
    """Replies from a list you write in advance: offline, free, identical every run."""

    name = "scripted"

    def __init__(self, script):
        self.script = list(script)
        self.seen = []  # a copy of the messages it was shown, one list per call

    def complete(self, messages, tools=None):
        self.seen.append(copy.deepcopy(messages))
        if not self.script:
            raise RuntimeError("ScriptedModel ran out of replies")
        reply = self.script.pop(0)
        if callable(reply):  # a reply can be a function of what the model was shown
            reply = reply(messages)
        shown = json.dumps(messages) + json.dumps(tools or [])
        written = reply["content"] + json.dumps(reply["tool_calls"])
        usage = {"input_tokens": estimate_tokens(shown), "output_tokens": estimate_tokens(written)}
        return {**reply, "usage": usage}
```

Then `harness/tools.py`:

```python run title="harness/tools.py"
"""Tools the model may call: a schema it can read, a validator, and a dispatcher that never raises."""
from dataclasses import dataclass

TYPES = {"string": str, "integer": int, "number": (int, float),
         "boolean": bool, "array": list, "object": dict}


@dataclass
class Tool:
    name: str
    description: str
    params: dict      # {"path": {"type": "string", "description": "..."}}
    required: list
    fn: object        # the Python function to run

    def schema(self):
        return {"name": self.name, "description": self.description,
                "parameters": {"type": "object", "properties": self.params,
                               "required": self.required, "additionalProperties": False}}


def check_args(tool, args):
    """List what's wrong with args. An empty list means they are valid."""
    if not isinstance(args, dict):
        return ["arguments must be a JSON object"]
    problems = [f"missing required argument '{name}'" for name in tool.required if name not in args]
    for name, value in args.items():
        spec = tool.params.get(name)
        if spec is None:
            problems.append(f"unknown argument '{name}'")
            continue
        bool_as_number = isinstance(value, bool) and spec["type"] in ("integer", "number")
        if bool_as_number or not isinstance(value, TYPES[spec["type"]]):
            problems.append(f"'{name}' should be {spec['type']}, got {type(value).__name__}")
    return problems


def error(kind, message):
    return {"ok": False, "error": {"type": kind, "message": message}}


class ToolRegistry:
    def __init__(self):
        self.tools = {}

    def tool(self, name, description, params, required=None):
        """Decorator that registers a Python function as a tool."""
        def register(fn):
            needed = list(params) if required is None else required
            self.tools[name] = Tool(name, description, params, needed, fn)
            return fn
        return register

    def schemas(self):
        return [tool.schema() for tool in self.tools.values()]

    def dispatch(self, call):
        """Run one tool call. Every outcome, good or bad, comes back as a dict."""
        tool = self.tools.get(call["name"])
        if tool is None:
            return error("unknown_tool", f"no tool named '{call['name']}'; available: {', '.join(self.tools)}")
        problems = check_args(tool, call["args"])
        if problems:
            return error("bad_arguments", "; ".join(problems))
        try:
            return {"ok": True, "result": tool.fn(**call["args"])}
        except Exception as exc:  # the tool itself failed: report it, don't crash the run
            return error(type(exc).__name__, str(exc))
```

Then `harness/files.py`:

```python run title="harness/files.py"
"""File tools that only ever touch one workspace folder."""
from pathlib import Path


def add_file_tools(registry, root):
    root = Path(root).resolve()

    def inside(path):
        target = (root / path).resolve()
        if not target.is_relative_to(root):
            raise PermissionError(f"'{path}' is outside the workspace")
        return target

    @registry.tool("list_files", "List every file in the workspace.", {})
    def list_files():
        return sorted(p.relative_to(root).as_posix() for p in root.rglob("*") if p.is_file())

    @registry.tool("read_file", "Read a UTF-8 text file from the workspace.",
                   {"path": {"type": "string", "description": "Path relative to the workspace"}})
    def read_file(path):
        target = inside(path)
        if not target.is_file():
            raise FileNotFoundError(f"no file named '{path}'; call list_files to see what exists")
        return target.read_text(encoding="utf-8")

    @registry.tool("write_file", "Create or replace a UTF-8 text file in the workspace.",
                   {"path": {"type": "string"}, "content": {"type": "string"}})
    def write_file(path, content):
        target = inside(path)
        target.parent.mkdir(parents=True, exist_ok=True)
        target.write_text(content, encoding="utf-8")
        return f"wrote {len(content)} characters to {path}"
```

And `harness/loop.py`:

```python run title="harness/loop.py"
"""The runtime loop: ask the model, run the tools it asks for, stop when a rule says so."""
import json
from dataclasses import dataclass


@dataclass
class RunResult:
    status: str      # "done", "max_steps", or "model_error"
    answer: str
    steps: int
    messages: list


SYSTEM = ("You are a careful coding assistant. Use the tools to inspect and change files in "
          "the workspace. When the task is finished, reply with a short summary and no tool calls.")


def run_agent(model, registry, task, system=SYSTEM, max_steps=8, verify=None):
    messages = [{"role": "system", "content": system}, {"role": "user", "content": task}]
    for step in range(1, max_steps + 1):
        try:
            reply = model.complete(messages, registry.schemas())               # plan
        except Exception as exc:
            return RunResult("model_error", f"{type(exc).__name__}: {exc}", step, messages)
        messages.append({"role": "assistant", "content": reply["content"],
                         "tool_calls": reply["tool_calls"]})
        if reply["tool_calls"]:
            for call in reply["tool_calls"]:                                   # act
                outcome = registry.dispatch(call)
                messages.append({"role": "tool", "tool_call_id": call["id"],  # observe
                                 "name": call["name"], "content": json.dumps(outcome)})
            continue
        problem = verify() if verify else None                                 # verify
        if problem is None:
            return RunResult("done", reply["content"], step, messages)
        messages.append({"role": "user", "content": f"Verification failed: {problem}"})
    return RunResult("max_steps", "", max_steps, messages)
```

## The finished program

`run_fix_task.py` gives the agent the file tools and `run_tests`, wraps the model in `RetryingModel`, and makes the tests the `verify` step. To exercise the retries offline, `Overloaded` makes the scripted model fail with a 503 on its first two calls, the way a busy provider might. The fifth scripted reply is a function: it reads the latest test result and decides what to do, like a model reading its own failure. It uses the workspace from Step 4, and on disk it also imports from `harness.model`, `harness.tools`, `harness.files`, `harness.loop`, `harness.test_tool`, `harness.retry`, and `harness.chat_api`.

```python run title="run_fix_task.py"
import json
import sys
import time
from pathlib import Path

GOOD = "def add(a, b):\n    return a + b\n"


def tests_pass():
    outcome = run_tests_in("workspace")
    return None if outcome["passed"] else "the tests still fail:\n" + outcome["stderr"][-400:]


def fix_if_failing(messages):
    outcome = json.loads(messages[-1]["content"])["result"]
    if outcome["passed"]:
        return say("Tests pass.")
    return call("write_file", path="calc.py", content=GOOD)


class Overloaded:
    """Makes a model fail with HTTP 503 for its first few calls."""

    def __init__(self, model, failures):
        self.model, self.failures, self.name = model, failures, model.name

    def complete(self, messages, tools=None):
        if self.failures:
            self.failures -= 1
            raise TransientError("HTTP 503: model server overloaded")
        return self.model.complete(messages, tools)


def scripted_fixer():
    return ScriptedModel([
        call("run_tests"),
        call("read_file", path="calc.py"),
        call("write_file", path="calc.py", content="def add(a, b):\n    return abs(a) + abs(b)\n"),
        call("run_tests"),
        fix_if_failing,
        say("add() subtracted instead of adding. Fixed it, and both tests pass."),
    ])


def main(live=False):
    Path("workspace/calc.py").write_text("def add(a, b):\n    return a - b\n")
    registry = ToolRegistry()
    add_file_tools(registry, "workspace")
    add_test_tool(registry, "workspace")
    waits = []
    model = ChatAPIModel() if live else Overloaded(scripted_fixer(), failures=2)
    model = RetryingModel(model, sleep=waits.append if not live else time.sleep)
    result = run_agent(model, registry, "The tests in test_calc.py fail. Fix calc.py.",
                       verify=tests_pass, max_steps=10)
    for message in result.messages[1:]:
        if message["role"] == "tool":
            print(f"  tool   <- {message['content'][:80]}")
        elif message.get("tool_calls"):
            print("  model  -> " + ", ".join(f"{c['name']}({c['args']})"[:80] for c in message["tool_calls"]))
        else:
            print(f"  {'model' if message['role'] == 'assistant' else message['role']:<6} :  {message['content']}")
    print(f"status={result.status} steps={result.steps} retried model calls={len(waits)}")
    print("tests pass now:", run_tests_in("workspace")["passed"])


main(live="--live" in sys.argv)
```

Follow the run. The first test run failed both tests. The model's first fix, `abs(a) + abs(b)`, passes `add(2, 3)` but not the negative case, and the second test run said so. The scripted function read that result and wrote the real fix. The final claim was then checked by `verify`, which ran the tests itself instead of trusting the model's word. Meanwhile two 503s were retried without the loop ever seeing them.

With `--live`, your real model gets the same tools and the same verification. Small local models often skip running the tests, and `verify` is what catches that.

  Fewer capabilities mean fewer ways for a confused or manipulated model to do damage, and the sandbox still contains whatever the tests do.
- [ ] `run_python` can't run tests
  It can; `run_tests` is built on it. The question is what the model should be allowed to ask for.
- [ ] Tools can't return dictionaries
  `run_tests` returns a dictionary too.

Q: The model calls `run_tests`, sees `passed: true`, and says it's done. Why does `verify` run the tests again?
- [ ] The first run might have been slow
  Speed has nothing to do with whether the claim is true.
- [x] Changes after that test run, or a claim made without running tests at all, would slip through; verify checks the final state itself
  The harness trusts only what it checked itself, at the moment it decides the run is done.
- [ ] Running tests twice makes them more reliable
  Rerunning only helps with flaky tests; here it's about who does the checking.

Q: Why does `run_python` keep the head of stdout but the tail of stderr?
- [ ] stderr is always longer
  Either can be longer; it depends on the code.
- [x] Tracebacks and test summaries end with the most useful lines, while normal output usually starts with them
  The last line of a traceback names the error, and `FAILED (failures=2)` comes at the very end.
:::

:::takeaways
- `run_python` runs code in a temporary folder with a timeout, file and CPU limits, closed input, an allowlisted environment, and process-group cleanup, and always returns the same dictionary.
- Hostile code becomes a result row: killed at the timeout, `EOFError` on input, `File too large` on a flood, no secrets in the environment.
- Give the model the narrowest tool that does the job; here, `run_tests`.
- `RetryingModel` retries 408, 429, 5xx, and connection failures with jittered backoff, and passes everything else through on the first try.
- Using the tests as `verify` means `done` requires passing tests, checked by the harness.
:::

## Ideas to extend it

- Add a `max_memory` option that sets `RLIMIT_AS` on Linux (macOS doesn't enforce it), and test it with code that builds a huge list.
- Let `run_tests` take an optional `pattern` argument, such as `test_calc.py`, so the agent can run one file while it works and the whole suite at the end.
- Write a `run_in_container` function with the same signature and return value as `run_python` that runs the Docker command from the Notes, and pick between them with a setting.
