Last year, someone on the student council made a slick chart showing which school bus was late most often. It got the principal's attention. This year nobody can rebuild it: the spreadsheet had rows deleted by hand, a filter was clicked on and never noted, and the "late" cutoff isn't written down anywhere.

You're going to build the replacement, a notebook that goes from the raw arrival log to a finished report with one Run all. Here's the shape of what you'll produce:

```mermaid caption="The finished report, top to bottom, and the notebook sections that produce each part"
flowchart TD
    S["Executive summary: 3 findings + limits"] --- D["Dashboard: 3 charts in one figure"]
    D --- T["Summary table by route"]
    T --- L["Cleaning log and data checks"]
    P["Parameters cell"] -.-> L
    P -.-> T
    P -.-> D
    P -.-> S
```

## Step 1: A parameters cell at the top

Every choice that someone might reasonably question goes here: the seed, the definition of "late," the routes, and the file names. In Colab, the `# @param` comments turn into form fields beside the code, so a reader can change the late cutoff with a text box and rerun.

```python run
import numpy as np
import pandas as pd
import matplotlib
import matplotlib.pyplot as plt

SEED = 7  # @param {type:"integer"}
LATE_AFTER_MIN = 5  # @param {type:"integer"}
RAW_FILE = "bus_arrivals_raw.csv"
ROUTES = ["Route 3", "Route 7", "Route 12"]
VALID_DELAY = (-15, 90)

BLUE, ORANGE, AQUA, INK, MUTED = "#2a78d6", "#eb6834", "#1baf7a", "#0b0b0b", "#52514e"
ROUTE_COLORS = {"Route 3": BLUE, "Route 7": ORANGE, "Route 12": AQUA}
plt.rcParams.update({"axes.spines.top": False, "axes.spines.right": False})
print(f"pandas {pd.__version__}, numpy {np.__version__}, matplotlib {matplotlib.__version__}")
```

`ROUTE_COLORS` is a parameter too. Deciding once that Route 7 is orange means it's orange in every chart, and readers learn the code after the first one.

## Step 2: Get the raw file

In real life, the transportation office would email you `bus_arrivals_raw.csv` and you'd upload it to Colab's file panel. Here, a simulation writes one with the same problems real GPS logs have: some trips recorded twice, and a few impossible delays from GPS glitches. Treat this cell as "the office sent the file," and never edit the CSV by hand.

```python run
rng = np.random.default_rng(SEED)
days = pd.bdate_range("2026-09-08", periods=60)
rainy = rng.random(len(days)) < 0.25
rows = []
for i, (day, rain) in enumerate(zip(days, rainy)):
    for route in ROUTES:
        if route == "Route 3":
            delay = rng.normal(1.5, 2.5) + (2 if rain else 0)
        elif route == "Route 7":
            delay = rng.normal(8, 4) - (5 if i >= 30 else 0) + (2 if rain else 0)
        else:
            delay = rng.normal(2, 2.5) + (9 if rain else 0)
        rows.append((day.date().isoformat(), route, "rain" if rain else "dry", round(delay, 1)))

log = pd.DataFrame(rows, columns=["date", "route", "weather", "delay_min"])
repeats = log.sample(6, random_state=SEED)
glitches = log.sample(3, random_state=SEED + 1).assign(delay_min=[-45.0, 240.0, 999.0])
log = pd.concat([log, repeats, glitches]).sample(frac=1, random_state=SEED)
log.to_csv(RAW_FILE, index=False)
print(f"Wrote {len(log)} rows to {RAW_FILE}")
```

(Spoiler, since you can read the simulation: Route 7 got a new schedule on day 31, and Route 12's route floods when it rains. Your analysis should find both without being told.)

## Step 3: Clean in code, and log every step

Each cleaning step records how many rows it removed. That log goes into the report, so a reader can see exactly what happened to the data between the file and the charts.

```python run
raw = pd.read_csv(RAW_FILE, parse_dates=["date"])
cleaning_log = [("rows in raw file", len(raw))]

clean = raw.drop_duplicates()
cleaning_log.append(("exact duplicate rows removed", len(raw) - len(clean)))

in_range = clean["delay_min"].between(*VALID_DELAY)
cleaning_log.append((f"delays outside {VALID_DELAY} min removed", int((~in_range).sum())))
clean = clean[in_range].copy()
cleaning_log.append(("rows kept", len(clean)))

clean["late"] = clean["delay_min"] > LATE_AFTER_MIN
clean["week"] = (clean["date"] - clean["date"].min()).dt.days // 7 + 1

assert not clean.duplicated(["date", "route"]).any(), "a route has two arrivals on the same day"
assert set(clean["route"]) == set(ROUTES), "unexpected or missing route names"
for step_name, count in cleaning_log:
    print(f"{step_name:<40}{count:>5}")
```

The two assertions encode facts about buses: each route arrives once per school day, and only three routes exist. If next month's file breaks either one, the notebook stops here instead of drawing a confident chart from bad rows. Notice that the cleaning never touches `raw`; it builds `clean` from it, so rerunning the cell is always safe.

## Step 4: One summary table answers "which bus, and when?"

```python run
summary = clean.groupby("route").agg(
    trips=("delay_min", "size"),
    median_delay=("delay_min", "median"),
    pct_late=("late", "mean"),
).reindex(ROUTES)
summary["pct_late"] = summary["pct_late"] * 100

by_weather = clean.pivot_table(index="route", columns="weather", values="late", aggfunc="mean").reindex(ROUTES) * 100
route7 = clean[clean["route"] == "Route 7"]
change_day = days[30]
before = route7.loc[route7["date"] < change_day, "late"].mean() * 100
after = route7.loc[route7["date"] >= change_day, "late"].mean() * 100

print(summary.round(1))
print("\n% late by weather\n", by_weather.round(1))
print(f"\nRoute 7 late before {change_day.date()}: {before:.0f}%, after: {after:.0f}%")
print("Rainy days in the data:", int(rainy.sum()))
```

Three findings jump out: Route 7 is late most often overall but improved sharply partway through; Route 12 is fine on dry days and almost always late in the rain; Route 3 is reliable. Each finding is a different *kind* of question, so each gets a different chart.

## Step 5: One chart per question

| Question | Kind of question | Chart |
| --- | --- | --- |
| How spread out are each route's delays? | Distribution | Strip plot with medians |
| Did Route 7 get better? | Change over time | Line of weekly % late |
| Does rain matter, and for which route? | Comparing amounts across groups | Grouped bars, from zero |

Rather than three separate figures, build them as functions that draw onto an axis you pass in. That way the same code can draw a chart on its own or as a panel of a dashboard.

```python run alt="Line chart of Route 7's weekly percent of trips late over 12 weeks. Before a dotted line marking the schedule change between weeks 6 and 7, weekly values range from 60 to 100 percent, averaging 80. After it, they range from 0 to 60 percent, averaging 30. Dashed lines mark the two averages." caption="Route 7 before and after its schedule change"
def draw_spread(ax):
    for row, route in enumerate(ROUTES):
        delays = clean.loc[clean["route"] == route, "delay_min"]
        jitter = np.random.default_rng(row).uniform(-0.18, 0.18, len(delays))
        ax.scatter(delays, row + jitter, s=12, color=ROUTE_COLORS[route], alpha=0.6)
        ax.plot(delays.median(), row, marker="|", markersize=22, markeredgewidth=3, color=INK)
    ax.axvline(LATE_AFTER_MIN, color=MUTED, linestyle="--", linewidth=1)
    ax.set_yticks(range(len(ROUTES)), ROUTES)
    ax.set_xlabel("Delay (minutes, black tick = median)")
    ax.set_title("Route 7 runs latest", loc="left")


def draw_weekly(ax):
    weekly = clean[clean["route"] == "Route 7"].groupby("week")["late"].mean() * 100
    change_at = (change_day - clean["date"].min()).days // 7 + 0.5
    ax.plot(weekly.index, weekly.values, color=ROUTE_COLORS["Route 7"], linewidth=2, marker="o")
    ax.hlines(before, weekly.index.min(), change_at, color=INK, linestyle="--", linewidth=1)
    ax.hlines(after, change_at, weekly.index.max(), color=INK, linestyle="--", linewidth=1)
    ax.axvline(change_at, color=MUTED, linestyle=":", linewidth=1)
    ax.annotate("schedule change", (change_at, 104), xytext=(4, 0), textcoords="offset points", va="top", color=INK)
    ax.set_ylim(0, 105)
    ax.set_xlabel("Week of the semester")
    ax.set_ylabel("Route 7 trips late (%)")
    ax.set_title(f"Route 7 fell from {before:.0f}% to {after:.0f}% late", loc="left")


def draw_weather(ax):
    x = np.arange(len(ROUTES))
    for offset, weather, alpha in [(-0.2, "dry", 0.45), (0.2, "rain", 1.0)]:
        bars = ax.bar(x + offset, by_weather[weather], width=0.38, alpha=alpha,
                      color=[ROUTE_COLORS[r] for r in ROUTES])
        ax.bar_label(bars, labels=[weather] * len(ROUTES), padding=2, color=INK, fontsize=8)
    ax.set_xticks(x, ROUTES)
    ax.set_ylim(0, 110)
    ax.set_ylabel("Trips late (%)")
    ax.set_title("Rain makes Route 12 late", loc="left")


fig, ax = plt.subplots(figsize=(7, 3.6))
draw_weekly(ax)
```

The drawn chart is the weekly one, on its own. Look at how the titles are written: each states the finding, and the Route 7 numbers are filled in from `before` and `after`. In the weather chart, every bar is labeled "dry" or "rain" directly, so it doesn't rely on the lighter shade alone.

:::tip
Five trips per week makes the weekly line jumpy: one late bus moves a point by 20 percentage points. That's honest, but say so in the report, and don't read meaning into a single week's spike.
:::

## Step 6: Assemble the dashboard and export it

A **dashboard** here is just one figure with several panels and a title that tells the reader what the whole thing means. The three functions draw onto three axes:

```python run alt="Dashboard with three panels. Left: delays per route as dots, with Route 7's dots furthest right and medians marked, plus a dashed line at the 5-minute late cutoff. Middle: Route 7's weekly percent of trips late, between 60 and 100 percent before a dotted line marking its schedule change and between 0 and 60 percent after, with dashed lines at the before and after averages of 80 and 30 percent. Right: percent of trips late on dry and rainy days by route, where Route 12 jumps from near 0 on dry days to near 100 on rainy days." caption="The whole report in one figure"
dashboard, axes = plt.subplots(1, 3, figsize=(15, 4.2), width_ratios=[1.1, 1.3, 1])
draw_spread(axes[0])
draw_weekly(axes[1])
draw_weather(axes[2])
dashboard.suptitle(
    f"School bus arrivals, {clean['date'].min():%b %d} to {clean['date'].max():%b %d}, {len(clean)} trips "
    f"(late = more than {LATE_AFTER_MIN} min)", x=0.01, ha="left", fontsize=13)
dashboard.tight_layout()
```

To export it from Colab, add these lines at the end of that same cell. Saving in the cell that draws the figure avoids saving a blank or half-finished one, and numbered, descriptive file names keep the report's figures in order:

```python
import os
from google.colab import files

os.makedirs("figures", exist_ok=True)
dashboard.savefig("figures/fig1_bus_dashboard.png", dpi=200, bbox_inches="tight")

## Step 7: Write the executive summary from the numbers

An **executive summary** is the paragraph a busy reader reads instead of everything else: the main findings, how big they are, and the main limits. Building it with f-strings means every number in it comes from the same variables as the charts, so the text can't drift out of sync with the data.

```python run
worst = summary["pct_late"].idxmax()
best = summary["pct_late"].idxmin()
step_rows = dict(cleaning_log)

executive_summary = f"""EXECUTIVE SUMMARY: school bus arrivals, {clean['date'].min():%B %d} to {clean['date'].max():%B %d}

1. {worst} was late most often: {summary.loc[worst, 'pct_late']:.0f}% of trips arrived more than {LATE_AFTER_MIN} minutes late.
   After its schedule changed on {change_day:%B %d}, its late share fell from {before:.0f}% to {after:.0f}%.
2. Route 12 is reliable on dry days ({by_weather.loc['Route 12', 'dry']:.0f}% late) but was late on
   {by_weather.loc['Route 12', 'rain']:.0f}% of rainy days ({int(rainy.sum())} rainy days in the data).
3. {best} was the most reliable route ({summary.loc[best, 'pct_late']:.0f}% late, median delay {summary.loc[best, 'median_delay']:.1f} min).

Limits: one semester, {len(clean)} trips after removing {step_rows['exact duplicate rows removed']} duplicates and
{step_rows[f'delays outside {VALID_DELAY} min removed']} GPS glitches. The Route 7 improvement is a before/after comparison,
so other changes at the same time (such as roadwork ending) could explain part of it.
"Late" means more than {LATE_AFTER_MIN} minutes; change LATE_AFTER_MIN and rerun to test other cutoffs."""
print(executive_summary)
```

Try it: set `LATE_AFTER_MIN = 3`, choose **Runtime › Run all**, and every number in the summary, the chart titles, and the dashboard changes together. That's the whole point of the parameters cell. Note that the limits section is part of the summary, not a footnote. A reader who only reads this paragraph still learns what the data can't tell them.

## Step 8: Lock the published numbers

Once the report is shared, add one last cell that checks the headline numbers haven't changed. If someone edits a cleaning rule later and the numbers shift, this cell fails and tells them the published report no longer matches the notebook. (If you tried other cutoffs in Step 7, set `LATE_AFTER_MIN` back to 5 first.)

```python run
published = {"Route 7 % late": 55.0, "Route 12 % late in rain": 100.0, "trips analyzed": 180}
current = {
    "Route 7 % late": float(round(summary.loc["Route 7", "pct_late"], 1)),
    "Route 12 % late in rain": float(round(by_weather.loc["Route 12", "rain"], 1)),
    "trips analyzed": len(clean),
}
for name, value in published.items():
    assert current[name] == value, f"{name} changed: published {value}, now {current[name]}"
print("Report numbers match the published version:", current)
```

Then do the final test from the Notes: **Runtime › Restart session and run all**. The report should rebuild itself, end to end, with no errors and the same numbers.

## The finished notebook

Your finished notebook is Steps 1 to 8 in order, each under its own text-cell heading, so Colab's table of contents doubles as the report's outline:

| Text-cell heading | Code it holds |
| --- | --- |
| Question and setup | Step 1: parameters, colors, versions |
| Raw data | Step 2: load the file (never edited by hand) |
| Cleaning | Step 3: cleaning log and assertions |
| Results | Step 4: summary tables |
| Charts and dashboard | Steps 5 and 6: drawing functions, dashboard, export |
| Executive summary | Step 7: the generated summary |
| Checks | Step 8: locked numbers |

To prove the pipeline depends on nothing hidden, here is its core as one standalone cell. Paste it into a brand-new notebook and it reproduces the published headline numbers:

```python run
import numpy as np
import pandas as pd

SEED, LATE_AFTER_MIN, VALID_DELAY = 7, 5, (-15, 90)
ROUTES = ["Route 3", "Route 7", "Route 12"]
SETTINGS = {"Route 3": (1.5, 2.5, 2), "Route 7": (8, 4, 2), "Route 12": (2, 2.5, 9)}

rng = np.random.default_rng(SEED)
days = pd.bdate_range("2026-09-08", periods=60)
rainy = rng.random(len(days)) < 0.25
rows = []
for i, (day, rain) in enumerate(zip(days, rainy)):
    for route in ROUTES:
        mean, spread, rain_extra = SETTINGS[route]
        delay = rng.normal(mean, spread) - (5 if route == "Route 7" and i >= 30 else 0) + (rain_extra if rain else 0)
        rows.append((day.date().isoformat(), route, "rain" if rain else "dry", round(delay, 1)))
log = pd.DataFrame(rows, columns=["date", "route", "weather", "delay_min"])
log = pd.concat([log, log.sample(6, random_state=SEED),
                 log.sample(3, random_state=SEED + 1).assign(delay_min=[-45.0, 240.0, 999.0])])

clean = log.drop_duplicates()
clean = clean[clean["delay_min"].between(*VALID_DELAY)].copy()
clean["late"] = clean["delay_min"] > LATE_AFTER_MIN
assert not clean.duplicated(["date", "route"]).any()

pct_late = (clean.groupby("route")["late"].mean() * 100).reindex(ROUTES).round(1)
rain_late = clean[clean["weather"] == "rain"].groupby("route")["late"].mean() * 100
print(pct_late.to_string())
assert pct_late["Route 7"] == 55.0 and round(rain_late["Route 12"], 1) == 100.0 and len(clean) == 180
print("Matches the published report.")
```

The random calls happen in exactly the same order as in Step 2, which is why the numbers match. If you reorder the loop (all of Route 3's days first, say), the seed produces different delays and the final assertion fails. With seeds, the order of random calls is part of the recipe.

:::quiz
Q: Why does the executive summary use f-strings like `{before:.0f}%` instead of typing "80%"?
- [ ] f-strings run faster than typed text
  Speed isn't the issue; a summary prints in an instant either way.
- [x] The numbers come from the same variables as the charts, so the text updates when the data or parameters change
  A typed "80%" stays 80% even after a cleaning rule changes. A computed one can't disagree with the analysis.
- [ ] Colab can't display typed numbers in text cells
  Text cells can hold any text. The risk is that typed numbers go stale.

Q: Why are the three charts written as functions that take an `ax` argument?
- [x] The same drawing code can make a standalone chart or a panel in the dashboard
  `draw_weekly(ax)` doesn't care which axis it gets, so there's one version of each chart to keep correct.
- [ ] matplotlib requires every chart to be drawn by a function
  You can draw directly with `plt.plot`. Functions just avoid copying code between the single charts and the dashboard.
- [ ] Functions make the charts use less memory
  Memory use is the same. The benefit is avoiding duplicate code.

Q: A teammate changes `VALID_DELAY` to `(-15, 60)` and the "lock the published numbers" cell fails. What does that tell you?
- [ ] The notebook has a bug and the assertion should be deleted
  The assertion did its job: it caught a change that affects published results.
- [x] The new cleaning rule changed a headline number, so the report would need to be updated and the change explained
  That's the purpose of the check. Either revert the change, or update the report and say why the numbers moved.
- [ ] Assertions only work after Restart session and run all
  Assertions run whenever their cell runs.
:::
