Maya's notebook says the school's average reading time is 31.4 minutes a day, and her chart is already in the student newspaper. Her editor opens the notebook, chooses **Run all**, and gets this:

```python run raises
print(f"Average reading time: {reading_clean['minutes'].mean():.1f} minutes")
```

Two days ago Maya renamed the cell that created `reading_clean`, then deleted the old version. Her own session still had `reading_clean` in memory, so everything kept working for her. Nobody else can produce that 31.4, including Maya after her runtime resets. A result that only exists in one person's session isn't really a result.

## Notebook memory outlives your cells

A notebook is two things that can drift apart: the cells you see on the page, and the **runtime's memory**, which holds every variable any cell has ever created. Running a cell changes memory. Editing or deleting a cell doesn't. Three habits make them drift:

- **Deleting or renaming a cell** whose variables are still in memory (Maya's problem).
- **Running cells out of order**, such as cell 5, then cell 2, then cell 5 again. The bracketed counter beside each cell shows the order cells last ran, and the page doesn't show what memory looked like in between.
- **Running a cell twice when it changes something in place.** Watch what happens when the "apply discount" cell gets run a second time to double-check its output:

:::trace A cell that changes its input, run twice
```python
prices = [10.0, 20.0, 30.0]
# Cell 2: apply the 10% member discount
prices = [round(p * 0.9, 2) for p in prices]
# ...you run Cell 2 again to see the output
prices = [round(p * 0.9, 2) for p in prices]
print(prices)
```
:::

The discount was applied twice, and nothing on the page says so. The fix is a rule: **never overwrite your raw data; derive new names from it.** `member_prices = [round(p * 0.9, 2) for p in prices]` gives the same answer on the first run and the fiftieth. In pandas, that means `clean = raw[...].copy()` and new columns on `clean`, rather than editing `raw`.

## Seeds make randomness repeatable

Random sampling, shuffling, and simulated data all draw from a **random number generator**. Give the generator a **seed** (any whole number) and it produces the same sequence every time:

```python run
import sys
import numpy as np
import pandas as pd
import matplotlib.pyplot as plt

first = np.random.default_rng(2024).integers(1, 7, size=10)
again = np.random.default_rng(2024).integers(1, 7, size=10)
other = np.random.default_rng(2025).integers(1, 7, size=10)
print("seed 2024:      ", first)
print("seed 2024 again:", again)
print("seed 2025:      ", other)
print("identical?", (first == again).all())

students = pd.DataFrame({"name": ["Ana", "Ben", "Cy", "Dee", "Eli", "Fay", "Gus", "Hal"]})
print(students.sample(3, random_state=0)["name"].tolist(), students.sample(3, random_state=0)["name"].tolist())
```

Without a seed, `np.random.default_rng()` starts from fresh randomness every run, and `df.sample(3)` picks different rows every time. Seed every source of randomness you use: `np.random.default_rng(seed)` for NumPy, `random_state=` for `DataFrame.sample` and scikit-learn.

A seed makes a result **repeatable**, not **right**. Here, 20 classmates each draw a random sample of 40 students from the same school of 1,000 and report the average. Each uses a different seed:

```python run alt="Dot plot of 20 sample averages of daily reading minutes, one per seed, scattered between about 26 and 36 minutes. A dashed vertical line marks the true school average near 30 minutes. One dot, seed 11, is highlighted in orange at the far right, about 35.6 minutes." caption="Every dot is a correct, reproducible analysis, and they disagree"
BLUE, ORANGE, INK, MUTED = "#2a78d6", "#eb6834", "#0b0b0b", "#52514e"
plt.rcParams.update({"axes.spines.top": False, "axes.spines.right": False})

school = pd.DataFrame({"minutes": np.random.default_rng(99).gamma(3, 10, 1000).round()})
truth = school["minutes"].mean()
estimates = pd.Series({seed: school.sample(40, random_state=seed)["minutes"].mean() for seed in range(20)})

fig, ax = plt.subplots(figsize=(7, 2.6))
ax.scatter(estimates, np.zeros(len(estimates)), s=60, color=BLUE, alpha=0.6)
ax.scatter(estimates[11], 0, s=90, color=ORANGE, zorder=3)
ax.annotate(f"seed 11: {estimates[11]:.1f}", (estimates[11], 0), xytext=(0, 12), textcoords="offset points", ha="center", color=INK)
ax.axvline(truth, color=INK, linestyle="--", linewidth=1)
ax.annotate(f"true average {truth:.1f}", (truth, 0), xytext=(4, -24), textcoords="offset points", color=INK)
ax.set_yticks([])
ax.spines["left"].set_visible(False)
ax.set_xlabel("Sample average, minutes of reading per day")
print(f"Lowest estimate {estimates.min():.1f}, highest {estimates.max():.1f}, truth {truth:.1f}")
```

Anyone who reruns seed 11 gets exactly the same answer, and it's still more than five minutes too high. The seed picked one sample out of many possible ones. Report how much results vary (rerun with several seeds, or give a range), and never try seeds until one gives the answer you hoped for.

:::warning
**Seed shopping.** Running with seed 1, 2, 3… and keeping the one where your effect looks biggest is a quiet form of cheating, and the seed in your notebook makes it look reproducible. Choose the seed before you look at results, write it in your setup cell, and leave it alone.
:::

## The test: Restart session and run all

The only way to prove a notebook doesn't depend on hidden state is to wipe memory and run it top to bottom. In Colab, use **Runtime › Restart session and run all** (some older guides call it Restart runtime, or Restart and run all). Or do it in two steps: **Runtime › Restart session**, then **Runtime › Run all**.

Do this before you share a notebook, before you copy a number into a report, and whenever something seems off. If it passes, three things are true:

1. Every cell runs without an error, in page order.
2. The counters beside the cells go 1, 2, 3, … from top to bottom.
3. The numbers and charts match what you reported.

If a cell fails, that's good news: you found the hidden state before your reader did. Recreate whatever the failing cell needs in an earlier cell, then restart and run all again.

## Write the setup and the checks into the notebook

Restart-and-run-all proves the notebook runs. Two more habits help a reader trust *what* it ran on.

**Record versions and parameters in the first cell.** Library updates occasionally change defaults, so print what you used, and put every choice someone might want to change (seed, file name, cutoff values) in one place:

```python run
import matplotlib

SEED = 2024
DATA_FILE = "reading_log.csv"
MIN_MINUTES, MAX_MINUTES = 0, 600

print("Python", sys.version.split()[0])
for library in (np, pd, matplotlib):
    print(f"{library.__name__:<11}{library.__version__}")
```

Your Colab output will show different version numbers; that's exactly why it's worth printing them.

**Turn assumptions into assertions.** An `assert` stops the notebook with a message if something you believed about the data stops being true:

```python run
raw = pd.DataFrame({
    "student_id": [101, 102, 103, 104, 105],
    "minutes": [35, 20, 0, 45, 25],
})
assert raw["student_id"].is_unique, "duplicate student IDs"
assert raw["minutes"].between(MIN_MINUTES, MAX_MINUTES).all(), "minutes outside the allowed range"
print("All checks passed for", len(raw), "rows")
```

Now suppose next month's file arrives with a typo: someone entered 4500 minutes instead of 45. The notebook refuses to continue, and points straight at the problem:

```python run raises
next_month = pd.DataFrame({"student_id": [101, 102, 103], "minutes": [30, 4500, 25]})
assert next_month["minutes"].between(MIN_MINUTES, MAX_MINUTES).all(), "minutes outside the allowed range"
```

Without that line, the 4500 would quietly push the average up by about 1,500 minutes and land in a chart. An `AssertionError` at the top of the notebook is far better than a wrong number at the bottom.

## The shape of a reproducible notebook

Put all of this together and most analysis notebooks follow the same order. Each step only uses variables created in the steps before it:

```mermaid caption="Top to bottom, each section depends only on the ones above it"
flowchart TD
    A["Title, question, and date"] --> B["Setup: imports, seed, parameters, versions"]
    B --> C["Load raw data, never edited by hand"]
    C --> D["Clean in code, with assertions"]
    D --> E["Analyze: summaries and comparisons"]
    E --> F["Charts, each with a clear title"]
    F --> G["Findings and limitations"]
```

Use text cells with headings for each section. Colab builds a clickable **Table of contents** in the left sidebar from those headings, so a reader can jump straight to the findings. And if a step happened outside the notebook (you fixed a typo in a spreadsheet, or filtered rows by clicking), it isn't reproducible. Move it into code.

:::quiz
Q: Your notebook runs perfectly for you, but a teammate gets `NameError: name 'clean' is not defined` on Run all. What's the most likely cause?
- [ ] Your teammate's copy of pandas is broken
  A broken library gives an `ImportError` or `AttributeError`, not a missing variable name.
- [x] The cell that created `clean` was deleted or renamed, but `clean` still lives in your session's memory
  Your memory kept the old variable; a fresh runtime never creates it. Restart session and run all would have shown you the same error.
- [ ] `clean` is a reserved word in Python
  It isn't. Any variable name that was never assigned gives this error.

Q: A cell contains `df["price"] = df["price"] * 1.08` to add 8% tax. You run it three times while fixing a chart below it. What happened to the prices?
- [ ] Nothing; pandas notices the column was already taxed
  pandas has no idea what the column means. Each run multiplies the current values again.
- [x] They were multiplied by 1.08 three times, about 26% higher than the original
  1.08 × 1.08 × 1.08 ≈ 1.26. Writing `df["price_with_tax"] = df["price"] * 1.08` instead would be safe to rerun.
- [ ] Python raises an error on the second run
  Reassigning a column is always allowed, which is exactly why the bug is silent.

Q: Seed 42 shows a big difference between two groups; seeds 1 through 10 show small or none. What should you report?
- [ ] The seed 42 result, since it's fully reproducible
  Reproducible doesn't mean representative. Picking the seed after seeing results misleads readers.
- [x] The range of results across seeds, chosen before looking, and that the difference isn't consistent
  How much the result moves between seeds is part of the finding.
- [ ] Nothing, because random results can't be trusted
  Random sampling is fine; you just have to report the variation honestly.
:::

:::takeaways
- The runtime's memory, not the page, is what code actually uses. Deleted cells and out-of-order runs leave hidden state behind.
- Never overwrite raw data. Derive new variables so every cell is safe to rerun.
- Seed every random step, choose the seed up front, and report how much results vary.
- Use Runtime › Restart session and run all before sharing anything.
- Put versions, parameters, and assertions near the top so readers know what ran and what was checked.
:::
