Here's a notebook cell that takes 10% off three lunch prices. Run it once and the prices look right:

```python run
import pandas as pd

prices = pd.Series([4.00, 2.50, 3.25], index=["pizza", "fruit cup", "wrap"])
print(prices)
```

```python run
prices = prices * 0.9      # apply the 10% discount
print(prices.round(3))
```

Now suppose you click that second cell again, maybe because you edited a comment. Here's the same code, run a second time:

```python run
prices = prices * 0.9      # apply the 10% discount
print(prices.round(3))
```

Pizza now costs 3.24, a 19% discount. Nothing in the code changed. What changed is the runtime's memory: the second run started from the already-discounted prices. If you saved the notebook now and sent it to a friend, their run would show 3.60, and neither of you would know why your numbers disagree.

## The page you see is not the memory the code uses

A notebook has two separate things in it. The **page** is the cells and outputs you see. The **runtime's memory** holds every variable that currently exists. They only match if you ran every cell exactly once, from top to bottom.

```mermaid caption="Running cells out of order makes the page and the memory disagree"
flowchart TD
    A["Cell 1: load prices"] --> M[("Runtime memory")]
    B["Cell 2: prices = prices * 0.9"] --> M
    B2["Cell 2 again"] --> M
    C["Cell deleted from the page"] -.->|"its variables stay"| M
    M --> D["What the next cell actually sees"]
```

Three things give the mismatch away:

-   **The `[n]` numbers beside cells.** On a clean run they go 1, 2, 3 from the top. A notebook showing `[7]`, `[3]`, `[12]` was run out of order.
-   **Deleted cells.** Deleting a cell removes it from the page, but whatever it created stays in memory until the runtime restarts. Your notebook can depend on a cell that no longer exists.
-   **Cells that overwrite their own input**, like `prices = prices * 0.9`. Each run changes the answer.

The fix for that last one is to give the result a new name. This cell reloads the original prices and stores the discount separately, so it prints the same thing however many times you run it:

```python run
prices = pd.Series([4.00, 2.50, 3.25], index=["pizza", "fruit cup", "wrap"])
sale_prices = prices * 0.9   # prices itself never changes
print(sale_prices.round(3))
```

## The clean-restart test

There's one reliable way to know your notebook works: wipe the memory and run everything from the top. In Colab, open **Runtime › Restart session and run all**. (Older tutorials call it "Restart runtime"; the idea is the same.) Colab clears every variable, then runs each cell in order.

If it finishes without errors and the outputs match what you expected, the notebook is **reproducible**: anyone who opens it gets the same results. If a cell fails, you've found a hidden dependency, like a variable from a deleted cell or a file that was uploaded by hand. Fix it now, while you still remember what you did.

Do this before you share a notebook, before you submit any project in this course, and whenever results look "weird". In JupyterLab the same command is **Kernel › Restart Kernel and Run All Cells**.

:::warning
A restart doesn't delete files in `/content` the way a runtime shutdown does, but **Runtime › Disconnect and delete runtime** does. If your notebook reads an uploaded file, the cleanest test is to disconnect, reconnect, and run all. If it breaks, load the file from Drive instead (the previous lesson shows how).
:::

## Lay out a notebook so it reads top to bottom

A good analysis notebook reads like a short report. Use the same skeleton every time and you'll never hunt for where something happens:

1.  **A title text cell:** the question you're answering, where the data came from, and the date.
2.  **One imports cell:** every `import` in one place, at the top.
3.  **One load cell:** read the data. Every later cell works from this.
4.  **One step per section:** a text cell with a `##` heading ("Remove duplicate responses"), then the code cells for that step.
5.  **A results section:** the final tables and charts, with a sentence or two on what they show.

Name files so they sort sensibly in Drive: `m2-survey-first-look.ipynb` beats `Untitled7.ipynb`. When you open a notebook from someone else's link, it's read-only for you, so use **File › Save a copy in Drive** before editing. To keep a copy on your own computer, use **File › Download › Download .ipynb**.

:::tip
The Table of contents icon in the left sidebar builds a clickable outline from your `#` and `##` headings. If the outline looks messy, the notebook is messy.
:::

## Getting unstuck: read the error from the bottom

pandas errors can be 40 lines long, but almost all of that is pandas' own code. The line that matters is the **last** one. Here's the most common error in this whole course:

```python run raises
survey = pd.DataFrame({"grade": [9, 10, 11], "rating ": [4, 5, 3]})
print(survey["rating"].mean())
```

Skip to the bottom: `KeyError: 'rating'`. A `KeyError` means "there's no column with that exact name." When the name looks right, print the real column names:

```python run
print(survey.columns.tolist())
```

There it is: `'rating '` has a trailing space, which often happens when a CSV header was typed by hand. You can rename it, or clean every name at once with `survey.columns = survey.columns.str.strip()`.

When you're stuck, work through this list in order:

1.  **Read the last line of the error.** Name the error type and the value it complains about.
2.  **Check what you actually have.** `print(df.columns.tolist())`, `df.dtypes`, `df.shape`, `type(x)`. Most bugs are a gap between what you think a variable holds and what it holds.
3.  **Read the docs for the function.** In Colab, run `pd.read_csv?` in a cell to see its documentation, or `help(pd.read_csv)` anywhere.
4.  **Search the last line of the error**, in quotes, along with "pandas".
5.  **Make it smaller.** Copy the failing line into a new cell with a three-row DataFrame. If it works there, the problem is in your data, not your code.

:::note
Colab has built-in AI features (Google says they require an account aged 18 or older). If you use any AI helper, ask it to *explain* the error rather than rewrite your notebook, then make the fix yourself and check the output. You're here to learn to see what's wrong.
:::

## Share notebooks without leaking data

When you share a Colab notebook, the person gets the whole page: code, text, **and every output**. If a cell printed `df.head()` on a file of classmates' names and emails, those names and emails are in the shared notebook even after you delete the file. Before sharing:

-   Use **Edit › Clear all outputs** if outputs might contain personal data, or don't print raw rows of sensitive files at all.
-   Never paste passwords or API keys into cells.
-   Use only data you have permission to use. The datasets in this course are made up or come bundled with the libraries, so they're safe to share.

:::quiz
Q: A cell contains `scores = scores + 5`. You run it three times by accident. What happened to `scores`?
- [ ] It went up by 5, because the cell is the same each time
  The code is the same, but each run starts from the value the previous run left in memory.
- [x] It went up by 15
  Each run adds 5 to the current value. Writing `curved = scores + 5` would avoid the problem.
- [ ] Colab blocked the second and third runs
  Colab never stops you from rerunning a cell.

Q: Your notebook works when you run cells one by one, but **Restart session and run all** fails with `NameError: name 'clean' is not defined`. What's the most likely cause?
- [x] `clean` was created by a cell you later deleted or edited
  Memory kept the old variable, so step-by-step runs worked. A fresh start exposes the missing step.
- [ ] Restart session and run all skips some cells
  It runs every code cell in order; that's what makes it a fair test.
- [ ] `NameError` means a library is missing
  A missing library gives `ModuleNotFoundError`. `NameError` means a variable or function doesn't exist yet.

Q: `df["Price"]` raises `KeyError: 'Price'`, but the CSV clearly has a price column. What should you run first?
- [ ] `pip install pandas` again
  The library works fine; the error is about a column name.
- [x] `print(df.columns.tolist())`
  It shows the exact names, including case and stray spaces, such as `'price'` or `'Price '`.
- [ ] `df.dropna()`
  Missing values don't cause a `KeyError`.
:::

:::takeaways
- The page and the runtime's memory are different things; out-of-order runs and deleted cells make them disagree.
- Don't let a cell overwrite its own input; give results new names.
- **Restart session and run all** is the test for a working notebook. Run it before you share or submit.
- Read errors from the last line up, then check what your variables really hold.
- Shared notebooks include outputs, so clear them or avoid printing personal data.
:::
