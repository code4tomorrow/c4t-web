Suppose your school's robotics club wants software that reads handwritten scores off judges' sheets, and someone asks you which model to use. "k-NN, it got 98%" is an answer. It isn't a recommendation. A recommendation says 98% of *what*, measured *how*, compared with *which* alternatives, and what goes wrong in the other 2%.

The capstone asks you to produce exactly that: a comparison of classical models on one dataset that a skeptical reader can check and can't easily poke holes in. Everything you need, you've already practiced in Modules 2 to 7. This module puts it in one notebook.

## The brief

Build one Colab notebook that compares at least three models on one dataset and ends with a recommendation. It must include:

1. **A documented dataset.** One that ships with scikit-learn, one you generate in the notebook, or a small CSV you're allowed to use, with a data card (below).
2. **A protected test set.** Split it off first, and score it once, at the end.
3. **Preprocessing inside pipelines**, so no fold or test row ever leaks into a scaler or encoder.
4. **A baseline** (`DummyClassifier` or `DummyRegressor`) and **at least three real models** from the ones you've learned: k-NN, linear or logistic regression, and decision trees. Two versions of one model type with meaningfully different settings can count as two.
5. **A cross-validated comparison** on the same folds, with **at least two metrics** chosen before you look at results.
6. **A fit diagnosis**: at least one training-versus-validation curve, and a paragraph on where your models underfit or overfit.
7. **Error analysis**: look at the specific examples your final model gets wrong and describe any pattern.
8. **A recommendation** of one model, with the evidence for it, its limits, and what you'd try next.

Each requirement blocks one way of fooling yourself. The test set stops you from grading your own homework. Pipelines stop leaks. The baseline stops you from celebrating 90% accuracy on a dataset that's 90% one class. Cross-validation stops one lucky split from picking the winner. Error analysis stops a single number from hiding what the model can't do.

## Pick a project

| Project | Dataset | Task | What makes it interesting |
| --- | --- | --- | --- |
| **Iris species** (starter) | `load_iris` | 3-class classification | Every model scores above 90%, so the challenge is arguing honestly when results are tied. |
| **Handwritten digits** (middle) | `load_digits` | 10-class classification | A 10×10 confusion matrix and real images of the digits each model misreads. Lesson 2 builds this one as the worked example. |
| **Signal hidden in noise** (middle) | `make_friedman1` | Regression | Only 5 of the 10 features matter, and you know the true formula. Can any model find the useful ones? |
| **Rare-event detector** (harder) | `make_classification` with `weights=[0.97]`, or your own simulation like the icy roads | Imbalanced classification | Accuracy is useless, so you'll need precision and recall, a threshold chosen on validation data, and a story for what each mistake costs. |
| **Your own small CSV** (stretch) | A file you upload to Colab | Your choice | Real, messy data, but you must document where it came from and that you're allowed to use it. No personal information about real people. |

If you can't decide, take the digits. The worked example in the next lesson gives you a path to follow, and you can make it your own in the error analysis.

Here's a first look at four of the options. Run it and notice the class balance in each:

```python run alt="Three bar charts of class counts: iris has three equal bars of 50; digits has ten nearly equal bars around 180; the rare-event dataset has one tall bar near 1,930 and one tiny bar near 70" caption="Balanced, balanced, and very much not balanced."
import numpy as np
import matplotlib.pyplot as plt
from sklearn.datasets import load_iris, load_digits, make_friedman1, make_classification

iris_y = load_iris().target
digits_y = load_digits().target
_, rare_y = make_classification(n_samples=2000, n_features=6, n_informative=4, n_redundant=0,
                                weights=[0.97], random_state=0)
friedman_X, friedman_y = make_friedman1(n_samples=500, n_features=10, noise=1.0, random_state=0)

fig, axes = plt.subplots(1, 3, figsize=(12, 3))
for ax, (name, labels) in zip(axes, [("iris", iris_y), ("digits", digits_y), ("rare event", rare_y)]):
    counts = np.bincount(labels)
    ax.bar(range(len(counts)), counts, color="#7892ee")
    ax.set_title(f"{name}: {len(labels)} rows")
    ax.set_xlabel("class")
plt.show()

print(f"friedman1: {friedman_X.shape[0]} rows, {friedman_X.shape[1]} features, "
      f"target from {friedman_y.min():.1f} to {friedman_y.max():.1f}")
```

The rare-event set has about 70 positives in 2,000 rows. A model that never predicts the positive class scores above 96% accuracy there, which is exactly why that project needs different metrics.

## Write a data card first

A **data card** is a short description of a dataset that someone else could use to decide whether to trust your results. Write it in a Colab text cell at the top of your notebook, before any modeling code. Fill in every line, even when the answer is "unknown".

```text
DATA CARD
Name and source:     (e.g. scikit-learn load_digits, from the UCI handwritten digits data)
One row is:          (e.g. one handwritten digit, scanned and shrunk to 8x8 pixels)
Rows and columns:    (e.g. 1,797 rows, 64 pixel columns, values 0-16)
Target:              (name, type, and the possible values)
Class balance:       (counts per class, or the range and average for a number target)
Features:            (what they measure and their units)
Known issues:        (noise, imbalance, simulated data, missing values, small size)
Who is affected by mistakes, and how:
```

That last line matters even for toy data. "A misread 7 changes a judge's score" makes you think about which errors to analyze, and it will shape your recommendation.

## Make the plan before you train anything

The fastest way to fool yourself is to try things until a number looks good and then decide that number is the one that matters. Writing the plan first takes away that temptation. Copy this into a second text cell:

```text
PLAN
Question:            Which model should we use to predict ___ from ___?
Task type:           classification / regression
Positive class:      (if any, and why it's the one we care about)
Main metric:         ___ because ___
Second metric:       ___ because ___
Baseline:            DummyClassifier(strategy="most_frequent") / DummyRegressor()
Models (3+):         1. ___  2. ___  3. ___
Setting to tune:     (e.g. max_depth for the tree, k for k-NN)
Split:               test_size=___, stratify=___, random_state=___
Folds:               StratifiedKFold / KFold, n_splits=5, shuffle=True, random_state=___
What would change my mind:  (e.g. "if the tree is within one std of the best, I'll prefer it for readability")
```

The last line is the most useful one. Deciding in advance how you'll break a near-tie means the results can't talk you into whatever you hoped for.

:::quiz
Q: Halfway through, you notice the test-set accuracy of your tree is higher than its cross-validation score, so you switch your recommendation to the tree. What's wrong?
- [ ] Nothing; the test set is the most realistic score you have
  It's realistic only until you use it to make a choice. After that, it's just another validation score.
- [x] The test set has now influenced the choice, so its score is no longer a fair preview
  The plan says the test set is scored once, after the decision. Choose with cross-validation, then confirm.
- [ ] Trees should never be recommended
  Trees are fine. The problem is how the choice was made.

Q: For the rare-event project, which plan line most needs changing from the digits plan?
- [ ] The number of folds
  Five folds work for both, as long as they're stratified.
- [x] The metrics: accuracy should be replaced with recall and precision (or F1)
  With 3% positives, accuracy rewards a model that never finds a single positive.
- [ ] The baseline should be removed
  The baseline matters even more here, because it shows how high accuracy can be with zero skill.
:::

:::takeaways
- The brief's eight requirements each block a specific way of fooling yourself.
- Pick a project by what makes it interesting, not by which one will get the highest score.
- A data card and a written plan come before any modeling code.
- Decide in advance how you'll break near-ties, so results can't change your rules.
:::
