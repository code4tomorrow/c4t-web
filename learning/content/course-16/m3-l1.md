Train a 1-nearest-neighbor model on the breast tissue samples from the last practice, then ask it about the very samples it trained on:

```python run
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.neighbors import KNeighborsClassifier

X, y = load_breast_cancer(return_X_y=True)
X_train, X_test, y_train, y_test = train_test_split(X, y, random_state=0, stratify=y)

memorizer = KNeighborsClassifier(n_neighbors=1).fit(X_train, y_train)
print("accuracy on training rows:", memorizer.score(X_train, y_train))
print("accuracy on test rows:    ", round(memorizer.score(X_test, y_test), 3))
```

100% on the training rows. That isn't skill. Ask a 1-nearest-neighbor model about a sample it has stored, and the nearest sample is that same sample, so it copies the answer. On the rows it never saw, the score falls to about 92%, and that's the number that tells you how it will do in a clinic. `score` here means **accuracy**: the fraction of predictions that are correct.

## Why a model can't grade its own homework

A model's score on its own training rows measures memory. What you care about is **generalization**: how well it does on new examples. The only way to estimate that is to hide some labeled rows before training, then score the model on them once at the end. Those hidden rows are the **test set**; the rest are the **training set**.

Think of it like a practice exam. If a teacher hands out the exact questions the day before, a perfect score tells you nothing about what the students learned. The test set is the set of questions nobody has seen.

## Splitting with `train_test_split`

Why not just take the last 30 rows as the test set? Because datasets are often sorted. The iris table lists all 50 setosa first, then versicolor, then virginica:

```python run
from sklearn.datasets import load_iris

X_iris, y_iris = load_iris(return_X_y=True)
print("first 10 targets:", y_iris[:10])
print("last 30 targets: ", y_iris[-30:])
```

A test set made of the last 30 rows would contain only virginica, and a model that had never seen enough virginica during training would be tested on nothing else. `train_test_split` shuffles the rows before cutting, so both parts get a fair mix:

```python run
import numpy as np

X_train, X_test, y_train, y_test = train_test_split(X_iris, y_iris, test_size=0.2, random_state=0)
print("train:", X_train.shape, " test:", X_test.shape)
print("species in test set:", np.bincount(y_test))
```

It returns **four** things, always in this order: training features, test features, training targets, test targets. `test_size=0.2` keeps 20% for testing (you can also give a count, like `test_size=30`). `random_state=0` fixes the shuffle so you get the same split every run; any whole number works, and changing it gives a different, equally fair split. Notice the species counts in this test set: 11, 13, and 6. Fair, but not even, which leads to the next problem.

Here's what happens inside, on six rows. Step through it and watch the list get shuffled, then cut:

:::trace Shuffle first, then cut
```python
import random

rows = ["A", "B", "C", "D", "E", "F"]
random.seed(2)
random.shuffle(rows)
cut = int(len(rows) * 0.67)
train = rows[:cut]
test = rows[cut:]
print("train:", train)
print("test: ", test)
```
:::

## Keep the class mix with `stratify`

Shuffling is fair on average, but a single shuffle can be unlucky, especially when one class is rare. Here are 100 made-up examples where only 10 belong to class 1. Watch how many of them land in a 20-row test set for six different shuffles:

```python run
from sklearn.datasets import make_classification

X_rare, y_rare = make_classification(n_samples=100, weights=[0.9, 0.1], flip_y=0, random_state=0)
print("class-1 examples overall:", y_rare.sum(), "of", len(y_rare))

for seed in range(6):
    plain = train_test_split(X_rare, y_rare, test_size=20, random_state=seed)[3]
    strat = train_test_split(X_rare, y_rare, test_size=20, random_state=seed, stratify=y_rare)[3]
    print(f"seed {seed}: plain split has {plain.sum()} in test, stratified has {strat.sum()}")
```

Without stratifying, the test set got anywhere from 1 to 3 of the rare cases, so judging the model on them is partly luck. With `stratify=y_rare`, the split keeps each class's share the same in both parts, so the test set always holds exactly 10% of class 1, which is 2 of 20. For classification, pass `stratify=y` unless you have a reason not to.

## The test set is sacred

Hiding the test rows only works if they stay hidden from *every* decision, not just from `fit`. Three rules:

1. **Split first**, before you scale, encode, choose features, or look closely at patterns.
2. **Never fit anything on the test rows.** Not the model, not a scaler, not an encoder.
3. **Score on the test set at the end**, not after every small change. If you keep adjusting until the test score goes up, you've slowly trained on it by hand. Later modules show how to compare options without touching it.

## Why k-NN needs features on the same scale

k-nearest neighbors decides which samples are "near" by measuring distance, and distance adds up the differences in every feature. Look at how differently spread out the 30 breast tissue features are:

```python run alt="Horizontal bar chart of the standard deviation of each of the 30 breast cancer features on a logarithmic axis. Values range from about 0.003 for fractal dimension error up to about 570 for worst area." caption="The widest feature is spread out about 200,000 times more than the narrowest (note the log scale)."
import matplotlib.pyplot as plt
import pandas as pd

cancer = load_breast_cancer(as_frame=True)
spread = cancer.data.std().sort_values()

plt.figure(figsize=(7, 7))
plt.barh(spread.index, spread.values, color="#5b7bd5")
plt.xscale("log")
plt.xlabel("standard deviation (log scale)")
plt.title("How spread out each feature is")
plt.tight_layout()
```

Take two samples whose `mean area` differs by 100 and whose `mean smoothness` differs by 0.02. Squared and added (the way distance is computed), area contributes 10,000 and smoothness contributes 0.0004. Smoothness might be the more useful clue, but k-NN can barely see it. The model is effectively using only the handful of features with big numbers.

The fix is to put every feature on the same footing. **Standardizing** subtracts each feature's mean and divides by its standard deviation:

```text
z = (x - mean) / standard deviation
```

After that, every feature has mean 0 and standard deviation 1, and a value of 2 means "two standard deviations above average", whatever the original unit was. scikit-learn's `StandardScaler` does exactly this. Compare k-NN on raw and scaled features:

```python run
from sklearn.preprocessing import StandardScaler

X_train, X_test, y_train, y_test = train_test_split(X, y, random_state=0, stratify=y)

raw = KNeighborsClassifier().fit(X_train, y_train)
print("raw features:   ", round(raw.score(X_test, y_test), 3))

scaler = StandardScaler()
scaler.fit(X_train)
X_train_scaled = scaler.transform(X_train)
X_test_scaled = scaler.transform(X_test)

scaled = KNeighborsClassifier().fit(X_train_scaled, y_train)
print("scaled features:", round(scaled.score(X_test_scaled, y_test), 3))
```

Same model, same data, same split, and the test accuracy rises from about 92% to 95% just by changing units. Models based on distance (k-NN) or on gradual steps (Module 4's gradient descent) need scaling. Decision trees, which ask one feature at a time "is it bigger than this?", don't care about units at all.

## Fit the scaler on training rows only

Look at the code again. `scaler.fit(X_train)` learns the mean and standard deviation from **training rows only**, then `transform` applies those same numbers to both sets. That order isn't fussiness. If the scaler learned from all rows, the test set's values would shape how training data gets scaled: a little information about the "unseen" rows would leak into training, and the test score would no longer be an honest preview.

```mermaid caption="Leak-free order: everything learns from training rows only"
flowchart TD
    A["All labeled rows"] --> B["train_test_split"]
    B --> C["Training rows"]
    B --> D["Test rows (locked away)"]
    C --> E["scaler.fit: learn mean and std"]
    E --> F["transform training rows"]
    E --> G["transform test rows"]
    D --> G
    F --> H["model.fit"]
    H --> I["model.score on transformed test rows"]
    G --> I
```

Keeping track of `fit` and `transform` by hand gets error-prone. A **pipeline** chains the steps so that `fit` runs them in the right order on training data, and `score` or `predict` reuses what was learned:

```python run
from sklearn.pipeline import make_pipeline

knn_scaled = make_pipeline(StandardScaler(), KNeighborsClassifier())
knn_scaled.fit(X_train, y_train)
print("pipeline:", round(knn_scaled.score(X_test, y_test), 3))
```

Same score as the manual version, with no way to accidentally fit the scaler on test rows.

## Turning categories into numbers: one-hot encoding

Models need numbers, but plenty of useful columns hold words. Here's a tiny bike-share log where each trip starts at one of three stations:

```python run
trips = pd.DataFrame({
    "station": ["campus", "harbor", "north", "campus", "north", "harbor"],
    "km": [2.1, 5.4, 3.3, 1.8, 4.0, 6.2],
})
print(pd.get_dummies(trips, columns=["station"], dtype=int))
```

Why not just number the stations 0, 1, 2? Because a model would read those as quantities: "north" would be twice "harbor", and "campus" would be closer to "harbor" than to "north". None of that means anything. **One-hot encoding** gives each category its own 0-or-1 column instead, so every station is equally different from every other. `pd.get_dummies` does it in one line, which is handy for exploring.

For a model, use scikit-learn's `OneHotEncoder`. It learns the categories during `fit` (on training rows, like the scaler) and then encodes any later data with exactly the same columns, even data with a category it never saw:

```python run
from sklearn.preprocessing import OneHotEncoder

encoder = OneHotEncoder(handle_unknown="ignore", sparse_output=False)
encoder.fit(trips[["station"]])
print(encoder.get_feature_names_out())

new_trips = pd.DataFrame({"station": ["harbor", "airport"]})
print(encoder.transform(new_trips))
```

`harbor` becomes `[0, 1, 0]`. `airport` wasn't in the training data, so with `handle_unknown="ignore"` it becomes all zeros instead of crashing. `sparse_output=False` returns a normal array you can print; without it you get a memory-saving format that prints less readably.

:::warning
**Calling `fit_transform` on the test set.** `scaler.fit_transform(X_test)` re-learns the mean and standard deviation from the test rows, so training and test data end up scaled by different rulers, and the test rows' own statistics leak in. Fit once on training data; on test data, only ever call `transform`.

**Scaling before splitting.** `StandardScaler().fit_transform(X)` followed by `train_test_split` lets the test rows shape the scaling. On a big, well-behaved dataset the score may barely change, which makes this bug easy to miss; with smaller data or other preprocessing steps the damage gets bigger. Split first, every time.
:::

:::quiz
Q: A model scores 100% on its training rows and 71% on its test rows. Which number should you report as its expected accuracy on new data?
- [ ] 100%, because that's the model at its best
  Training rows measure memory, not how the model does on examples it hasn't seen.
- [x] 71%, because the test rows played the role of new data
  That's the honest estimate. The gap between the two numbers is also a warning sign you'll study in Module 7.
- [ ] The average, about 85%
  Averaging mixes an honest number with a dishonest one, which isn't a meaningful estimate.

Q: Which code scales the data without leaking test information?
- [ ] `X = StandardScaler().fit_transform(X)`, then `train_test_split(X, y)`
  The scaler learned from every row, including the future test rows.
- [x] Split first, then `scaler.fit(X_train)` and `scaler.transform` on both sets
  The scaler's mean and standard deviation come only from training rows.
- [ ] Split first, then `fit_transform` on the training set and `fit_transform` on the test set
  The second `fit_transform` re-learns from the test rows, so the two sets are scaled differently.

Q: You're classifying a rare condition that appears in 5% of rows. Why use `stratify=y`?
- [ ] It makes the condition more common in the training set
  It keeps the proportion the same; it doesn't change it.
- [x] It guarantees the test set has the same 5% share, so the score isn't skewed by an unlucky shuffle
  Without it, a small test set might get almost none of the rare cases.
- [ ] It's needed to make `train_test_split` shuffle
  `train_test_split` shuffles by default. `stratify` controls the class mix.

Q: A column `size` holds "small", "medium", or "large". Is one-hot encoding the only sensible choice?
- [ ] Yes, text must always be one-hot encoded
  One-hot is the safe default for categories with no order, but these have one.
- [x] No; because sizes have a natural order, numbering them 0, 1, 2 can also make sense
  For ordered categories, the numbers' order means something real. For unordered ones like stations, it doesn't.
- [ ] No; scikit-learn models accept text columns directly
  Most scikit-learn models need numbers, so text has to be encoded first.
:::

:::takeaways
- Split before anything else, and judge the model on the test rows, once, at the end.
- `train_test_split` returns training features, test features, training targets, test targets, in that order. Add `stratify=y` for classification.
- k-NN measures distance, so features with big numbers drown out the rest. `StandardScaler` gives every feature mean 0 and standard deviation 1.
- Preprocessing steps learn from training rows only: `fit` on train, `transform` on both. A pipeline enforces this for you.
- One-hot encoding turns a category into 0-or-1 columns; `OneHotEncoder(handle_unknown="ignore")` copes with categories it hasn't seen.
:::
