Saturday, 18:40, heavy rain. Model 1.2.0 of the late-delivery service has been on a 10% canary for 40 minutes. Overall numbers look fine. Then a support lead posts in the team channel: rainy-day customers in the canary group are getting "on time" and then waiting an hour. Three engineers reply within a minute. One says "should we roll back?", one says "I think Priya owns the canary," and one starts reading the model code. Meanwhile the autoscaler has doubled the instance count, because 1.2.0 is slower, and nobody set a limit.

Nothing in that story needed new technology. It needed three decisions made in advance: **what evidence triggers a rollback**, **how much the service may spend**, and **who is in charge when it goes wrong**. That's this module.

## A canary decision is a comparison, made by code

A canary is only as good as the rule that ends it. Three habits make the rule trustworthy:

- **Compare with the baseline over the same minutes**, not with yesterday. Rain, dinner rush, and a marketing email all hit both groups equally, so they cancel out.
- **Wait for enough traffic.** With 150 canary requests, two errors is 1.3% or 0% depending on luck. Set a minimum, and say WAIT until you have it.
- **Check the slices that matter**, not just the total. The canary above was fine overall and broken for rain.

For rates such as errors or missed warnings, a **two-proportion z-test** asks whether the canary's rate is higher than the baseline's by more than chance would explain. Here's the whole decision:

```python run
import numpy as np
from scipy import stats

def worse_than_baseline(bad_c, n_c, bad_b, n_b, alpha=0.01):
    """One-sided test: is the canary's rate of bad outcomes higher than the baseline's?"""
    p_c, p_b = bad_c / n_c, bad_b / n_b
    pooled = (bad_c + bad_b) / (n_c + n_b)
    se = np.sqrt(pooled * (1 - pooled) * (1 / n_c + 1 / n_b))
    p_value = stats.norm.sf((p_c - p_b) / se) if se > 0 else 1.0
    return p_value < alpha, p_c, p_b

def canary_decision(baseline, canary, min_requests=1000, max_p99_ratio=1.25):
    if canary["requests"] < min_requests:
        return "WAIT", [f"only {canary['requests']} canary requests (need {min_requests})"]
    problems = []
    worse, p_c, p_b = worse_than_baseline(canary["errors"], canary["requests"],
                                          baseline["errors"], baseline["requests"])
    if worse:
        problems.append(f"5xx rate {p_c:.2%} vs {p_b:.2%}")
    if canary["p99_ms"] > max_p99_ratio * baseline["p99_ms"]:
        problems.append(f"p99 {canary['p99_ms']} ms vs {baseline['p99_ms']} ms")
    for name, (missed_c, late_c) in canary["slices"].items():
        missed_b, late_b = baseline["slices"][name]
        worse, p_c, p_b = worse_than_baseline(missed_c, late_c, missed_b, late_b)
        if worse:
            problems.append(f"{name}: missed {p_c:.0%} of late orders vs {p_b:.0%}")
    return ("ROLLBACK", problems) if problems else ("PROMOTE", [])

# slices: (late orders the model failed to warn about, late orders with known outcomes)
baseline = {"requests": 13_500, "errors": 40, "p99_ms": 48,
            "slices": {"rainy": (250, 610), "dry": (610, 1020)}}
scenarios = {
    "after 5 minutes": {"requests": 150, "errors": 0, "p99_ms": 51, "slices": {"rainy": (5, 9), "dry": (14, 23)}},
    "Saturday 18:40": {"requests": 1_500, "errors": 5, "p99_ms": 57, "slices": {"rainy": (48, 70), "dry": (66, 112)}},
    "a healthy canary": {"requests": 1_500, "errors": 5, "p99_ms": 50, "slices": {"rainy": (27, 68), "dry": (69, 115)}},
}
for label, canary in scenarios.items():
    verdict, reasons = canary_decision(baseline, canary)
    print(f"{label:17} {verdict:9} {'; '.join(reasons)}")
```

The Saturday canary had normal errors and slightly higher latency, both within limits. Only the rainy slice tripped: it missed 69% of late rainy orders against the baseline's 41%, a gap the test says is very unlikely to be luck. The healthy canary's rainy number differs from the baseline's too, but by an amount chance explains easily, so it passes. Run this function every few minutes during a canary and let its verdict, not a debate in the team channel, move the release forward or back.

## Rollback is a pointer move, and some things don't move back

There are two different rollbacks, depending on where the release is.

**During a canary**, the champion alias still points at 1.1.0. Rolling back means setting the canary's traffic share to 0. Nothing in the registry changes, and it takes effect as fast as the router reloads its config.

**After full promotion**, `champion` points at 1.2.0, so rollback moves it back, exactly as your Module 4 `rollback()` does: append a move to `aliases.json`, then restart the service so its lifespan loads the alias again. If the bad change was in the *code* rather than the model, roll back the deploy instead: Render's dashboard and API can redeploy a previous successful deploy, reusing its stored build so nothing is rebuilt.

```python run
import json

aliases = {"current": {"champion": "1.1.0"},
           "history": [{"alias": "champion", "from": "1.0.0", "to": "1.1.0", "reason": "retrained Jan+Feb"}]}
router = {"stable": "1.1.0", "canary": "1.2.0", "canary_percent": 10}

def act_on(verdict, reasons):
    if verdict == "ROLLBACK" and router["canary_percent"] > 0:
        router["canary_percent"] = 0                      # canary rollback: routing only
        return f"canary off ({'; '.join(reasons)})"
    return "no change"

print(act_on(*canary_decision(baseline, scenarios["Saturday 18:40"])))
print("router:", router)
print("champion alias untouched:", aliases["current"]["champion"])
```

Rollback has limits, and a runbook should name them before anyone needs it:

- **Effects already in the world stay there.** Customers who were told "on time" during the bad window were still told it. Support may need a list of affected orders, which your prediction log provides.
- **Data and schema changes may not reverse.** If 1.2.0 needed a new column and the database migration has run, the old version must still work with the new schema. Make migrations backward compatible ("expand, then contract") so rollback stays possible.
- **Caches remember.** If predictions are cached without the model version in the key, the old model can keep serving the new model's answers. Next lesson's cache includes the version for exactly this reason.

When rollback is impossible, you **roll forward**: ship a fix as a new version through the same gates, as fast as they allow.

## What a prediction costs, and a limit autoscaling can't cross

Cost per prediction is instance price divided by throughput. If one instance costs `c` dollars per hour and serves `r` requests per second at your latency target, a thousand predictions cost `1000 * c / (3600 * r)` dollars. That makes the three levers obvious: a cheaper instance, more requests per instance (do less work, batch work, or make the model faster), or fewer requests (cache repeats).

```python run
def monthly_cost(peak_rps, per_instance_rps, price_per_hour, min_instances=1, max_instances=None):
    needed = max(min_instances, int(np.ceil(peak_rps / per_instance_rps)))
    capped = min(needed, max_instances) if max_instances else needed
    return capped, needed, capped * price_per_hour * 24 * 30

PRICE = 0.10   # dollars per instance-hour: an illustrative number, not a real quote
for label, per_instance in [("1.1.0", 120), ("1.2.0 (slower)", 55)]:
    capped, needed, cost = monthly_cost(peak_rps=400, per_instance_rps=per_instance,
                                        price_per_hour=PRICE, max_instances=6)
    cost_per_1k = 1000 * PRICE / (3600 * per_instance)
    print(f"{label:15} needs {needed} instances, capped at {capped}: ${cost:,.0f}/month, "
          f"${cost_per_1k:.5f} per 1,000 predictions")
```

The slower model needs eight instances at peak, twice as many, and the cap holds it at six. A **cost boundary** like that cap turns "the bill doubled" into a deliberate trade-off: at the cap, latency rises instead of spending, and the latency alert tells a human to decide whether 1.2.0 is worth the money. Without a cap, the autoscaler makes that decision silently. Next lesson measures real speedups that move `per_instance_rps`.

## When it breaks: roles, severity, and the runbook

Google's SRE book describes incident response with a few separate roles, because one person can't fix, coordinate, and communicate at once. The **incident commander** (IC) runs the incident: assigns work, makes the call on mitigation, and decides when it's over. The **operations lead** makes changes to the system, and only that person does. The **communications lead** updates support, stakeholders, and the status page on a schedule. In a small team one person may hold two roles, but every role has exactly one name next to it, said out loud: "I'm IC."

Severity decides how loud the response is. Write the levels for *your* service:

| Severity | Late-delivery example | Response |
| --- | --- | --- |
| SEV1 | `/predict` failing for most requests, or every customer told "on time" | Page on-call now; IC assigned within 5 minutes |
| SEV2 | One slice badly wrong (rain, one city), or p99 far over the SLO | Page on-call; fix or roll back within the hour |
| SEV3 | Drift ticket, a slow dashboard, one flaky test | Next working day |

The first rule of incident response is **mitigate first, investigate second**. Rolling back takes minutes; finding the cause can take days, and customers are hurt the whole time. A **runbook** turns that rule into steps someone can follow at 3 a.m. with no context:

```text
RUNBOOK: late-rate gap PAGE (actual late rate far above predicted)
Owner: ML platform on-call     Dashboard: late-delivery / outcomes

1. Declare: post "Investigating late-rate gap, I'm IC" in #incidents. Start a timeline.
2. Check what changed in the last 24 hours:
   - registry/late-delivery/aliases.json history (did champion move?)
   - Render deploys page (new code?)
   - any canary currently running?
3. If a release in the last 24 hours lines up with the start of the gap:
   - canary running: set canary_percent to 0
   - fully promoted: rollback("late-delivery", "champion", reason="INC-<n> late-rate gap")
     then restart the service and confirm /health shows the old model_version
4. If nothing changed (likely concept drift: weather, road closures, courier shortage):
   - turn on the general "deliveries are slower than usual" banner
   - open a SEV3 ticket to retrain with recent outcomes; do NOT retrain under pressure
5. Confirm recovery: late-rate gap under 0.10 for 30 minutes.
6. Close: hand the timeline to the postmortem owner within 24 hours.
```

## Blameless postmortems: fix the system, not the person

After the incident comes the **postmortem**: a written account of what happened, its impact, why it happened, and what will change. "Blameless" means it asks *why the system let this happen*, never *who messed up*. People who fear blame hide details, and hidden details are how incidents repeat. "Priya didn't roll back" is a blame statement. "No rule said who could roll back a canary, and no automated check watched slices" is a systems finding you can fix.

```text
POSTMORTEM: INC-112, rainy-order warnings missing in the 1.2.0 canary   (SEV2)
Status: action items open     Owner: Sam Ortiz     Date: 2026-11-21

SUMMARY
For 50 minutes, customers in the 10% canary group got "on time" for rainy-day
orders that were then late. Overall metrics stayed normal, so no alert fired.

IMPACT
About 1,900 orders went through the canary. It missed 69% of warnings on late
rainy orders against the champion's 41%: roughly 25 customers who would have been
warned were not. 41 support contacts. No data loss.

TIMELINE (all times local)
17:48  1.2.0 canary starts at 10% (CI and promotion gates passed)
18:05  Heavy rain begins across the main city
18:40  Support lead reports complaints in #team; discussion, no owner
18:52  On-call engineer declares SEV2, becomes IC; operations lead assigned
18:55  Canary set to 0%; complaints stop within 15 minutes
20:10  Cause confirmed (see below)

ROOT CAUSE AND CONTRIBUTING FACTORS
- 1.2.0's training data came from a dry 20-day stretch; only 4% of rows had rain,
  versus 25% normally, and the model learned a much weaker rain effect.
- The promotion gate compared overall AUC on the holdout, which is mostly dry.
- The canary rule checked errors and latency only, not slices.
- No one was named as canary owner, so the rollback waited 12 minutes for a decision.

WHAT WENT WELL
- The canary limited impact to 10% of customers.
- Rolling back was a single routing change and took effect immediately.

ACTION ITEMS
[ ] Add per-slice checks (rain, distance, city) to the canary decision   owner: Sam   due: 11-28
[ ] Add a training-data check: rain share within 15-35% of rows          owner: Lee   due: 11-28
[ ] The person who starts a canary is its owner until it finishes        owner: Priya due: 11-24
[ ] Cap autoscaling at 6 instances; alert at the cap                     owner: Lee   due: 11-24
```

Every action item has one owner and a date, and each one removes a contributing factor rather than reminding people to "be more careful." That's the test of a useful postmortem: if the same conditions happened again, would the system now catch it?

:::warning
**Three ways incident response goes wrong.**

1. **Debugging before mitigating.** The engineer who started reading model code at 18:40 was doing useful work at the wrong time. Roll back or switch off the canary first; read the code with customers safe.
2. **Rollback that's never been tried.** A procedure nobody has run fails when it matters (a missing permission, a cache with no version in the key). Rehearse it: run a rollback drill against staging on a calm afternoon.
3. **Action items like "be more careful".** They change nothing. A useful item changes a gate, a check, an alert, a default, or an owner.
:::

:::quiz
Q: A canary has served 150 requests with 2 errors (1.3%); the baseline has 0.3% errors. What should an automated canary rule say?
- [ ] ROLLBACK, because 1.3% is more than four times 0.3%
  Two errors in 150 requests can easily happen by chance. Acting on it would roll back good releases regularly.
- [x] WAIT until the canary has enough requests to judge
  With a minimum sample size and a significance test, two errors in 150 isn't evidence yet. Keep the canary small until it is.
- [ ] PROMOTE, because the absolute difference is only 1 percentage point
  Small samples can hide a real problem as easily as they can fake one. Not enough evidence means neither promote nor roll back.

Q: 1.2.0 was promoted to champion an hour ago, and its predictions turn out to be wrong for one city. Which rollback fits?
- [ ] Set the canary percentage to 0
  There's no canary anymore: 1.2.0 is the champion and gets all traffic.
- [x] Move the `champion` alias back to 1.1.0 and restart the service
  After promotion, the alias is what decides which model serves. Moving it back and reloading restores 1.1.0 without retraining or rebuilding.
- [ ] Retrain 1.2.0 on more data from that city and deploy it immediately
  That's a roll forward under pressure, skipping the gates. Mitigate with the known-good version first.

Q: Which postmortem action item is most likely to prevent a repeat?
- [ ] "Engineers should double-check rain performance before promoting"
  It depends on someone remembering under time pressure, which is what failed the first time.
- [x] "Add a rain-slice check to the canary decision, owner Sam, due 11-28"
  It changes the system so the same conditions are caught automatically, and it has an owner and a date.
- [ ] "Priya should own canaries in future"
  It names a person to blame rather than a rule. The fix is "whoever starts a canary owns it," which works for anyone.

Q: Autoscaling has no maximum, and 1.2.0 needs twice as many instances. What does adding a cap of 6 change?
- [ ] Nothing, because the autoscaler still adds instances as needed
  The cap stops it at 6, which is the point.
- [x] At the cap, latency rises instead of cost, and an alert asks a human to decide
  The cost boundary turns a silent budget overrun into a visible trade-off someone has to own.
- [ ] Requests over capacity are automatically routed to the old model
  A cap doesn't route anything. It limits instances; what happens at the limit is up to your alerts and runbook.
:::

:::takeaways
- Let code end a canary: compare with the baseline over the same window, require a minimum sample, test rates for significance, and check key slices.
- Canary rollback is a routing change; post-promotion rollback moves the registry alias back and reloads. Neither undoes effects already in the world.
- Cost per prediction is instance price over throughput. Cap autoscaling so a slower model raises latency and an alert, not just the bill.
- In an incident, name an IC, an operations lead, and a communications lead; mitigate first, investigate second; follow a runbook.
- A blameless postmortem finds the system conditions that allowed the incident, and every action item has one owner and a due date.
:::
