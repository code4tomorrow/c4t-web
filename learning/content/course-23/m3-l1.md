Two delivery companies, two mistakes. The first scores tomorrow's two million scheduled orders by sending each one to its prediction API, one HTTP request at a time, every night. The job takes most of the night and the API runs at full tilt for it. The second company computes its late-delivery warnings in a nightly batch, so when a customer adds a third pizza to the cart at 6 p.m. in the rain, the warning they see was computed from a different, drier order the night before.

Both companies have a fine model. They picked the wrong **serving mode**: the way predictions get from the model to whoever needs them.

## Four ways to deliver a prediction

- **Batch.** Score many rows on a schedule, store the results, and look them up later. Tomorrow's scheduled orders can be scored at 2 a.m., because everything the model needs is known in advance.
- **Online** (also called real-time, or request/response). A client sends one request and waits for the answer. The checkout page asks "will this order be late?" the moment the cart changes.
- **Streaming.** A consumer reads events from a stream (Apache Kafka is the common open-source choice) as they happen and writes predictions to another stream, usually within seconds. Each GPS ping from a driver updates that order's arrival estimate, and nobody is waiting on a request.
- **Edge.** The model runs on the user's device: a phone, a browser, a car. There's no network round trip, it works offline, and the data never leaves the device. A driver's app that flags risky routes in a tunnel needs this.

| Mode | When it computes | Input freshness | What the user waits for | What you operate |
| --- | --- | --- | --- | --- |
| Batch | On a schedule | As of the last run | A lookup (fast) | A scheduled job and a results table |
| Online | On each request | Live | The model, every time | An always-reachable API |
| Streaming | On each event | Seconds old | Nothing; results are pushed | A consumer and a message broker |
| Edge | On the device | Live, local | The device's own CPU | Model files shipped inside an app |

Many real systems mix them. A common pattern serves batch scores when they're fresh and falls back to the online API when they aren't; you'll build that in the practice lesson.

What to watch for: "model-in-database" is batch prediction, and its trade-offs (simple and fast to serve, but predictions go stale and only cover inputs you know ahead of time) are the ones in the table above. The talk then moves to model-as-a-service, which is online serving.

## Latency and throughput are different numbers

**Latency** is how long one prediction takes. **Throughput** is how many predictions you finish per second. They pull in different directions, and you can see it with the course model. This cell trains it and builds 200,000 orders to score:

```python run
import time
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

def make_orders(n=2000, seed=23):
    rng = np.random.default_rng(seed)
    distance_km = rng.gamma(shape=2.0, scale=2.0, size=n).round(2)
    items = rng.integers(1, 9, size=n)
    hour = rng.integers(10, 23, size=n)
    raining = (rng.random(n) < 0.25).astype(int)
    rush = (hour >= 17) & (hour <= 19)
    logit = -4.0 + 0.45 * distance_km + 0.15 * items + 1.2 * raining + 0.9 * rush
    late = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return pd.DataFrame({"distance_km": distance_km, "items": items,
                         "hour": hour, "raining": raining, "late": late})

FEATURES = ["distance_km", "items", "hour", "raining"]
history = make_orders()
model = Pipeline([
    ("prep", ColumnTransformer([
        ("scale", StandardScaler(), ["distance_km", "items"]),
        ("hour", OneHotEncoder(handle_unknown="ignore"), ["hour"]),
    ], remainder="passthrough")),
    ("clf", LogisticRegression(max_iter=1000)),
]).fit(history[FEATURES], history["late"])

tomorrow = make_orders(n=200_000, seed=7)[FEATURES]
print(f"{len(tomorrow):,} orders to score")
```

Now score 300 of them one at a time, the way an online API does, and then all 200,000 in a single call:

```python run
latencies_ms = []
for i in range(300):
    row = tomorrow.iloc[[i]]
    start = time.perf_counter()
    model.predict_proba(row)
    latencies_ms.append((time.perf_counter() - start) * 1000)
latencies_ms = np.array(latencies_ms)

p50, p95, p99 = np.percentile(latencies_ms, [50, 95, 99])
print(f"one row at a time:  mean {latencies_ms.mean():.2f} ms | p50 {p50:.2f} | p95 {p95:.2f} | p99 {p99:.2f} | max {latencies_ms.max():.2f}")

start = time.perf_counter()
model.predict_proba(tomorrow)
bulk_s = time.perf_counter() - start
print(f"200,000 rows in one call: {bulk_s:.2f} s total, {bulk_s / len(tomorrow) * 1e6:.2f} µs per row")
print(f"per-row cost, one at a time vs bulk: about {p50 / 1000 / (bulk_s / len(tomorrow)):,.0f}x")
```

Two things to see. First, the bulk call is thousands of times cheaper *per row*. Almost all of a single prediction is fixed overhead: building a DataFrame, checking columns, running each pipeline step. Bulk scoring pays it once. A real API adds HTTP parsing, JSON, and a network round trip on top, which makes the gap bigger still. That's the first company's mistake in numbers.

Second, look at the spread of the single-row latencies. The **p50** (median) is what a typical request sees. The **p99** is the latency that 1 in 100 requests exceeds, and it sits well above the median even in this tiny loop, because of garbage collection, other programs on the machine, and cache misses. Service-level objectives are written in percentiles ("p95 under 100 ms") because a page that makes several calls hits the slow tail far more often than 1% of the time.

:::warning
**Averages hide the tail.** A mean of 8 ms can sit on top of a p99 of 40 ms, and a handful of very slow requests barely moves the mean. Always report p50, p95, and p99 together, measured over enough requests (hundreds at least) that the p99 means something.
:::

## How many requests are in flight? Little's law

When requests arrive faster than one worker can finish them, they queue. Step through this tiny simulation: a request arrives every 20 ms, and each prediction takes 30 ms.

:::trace Watch the wait grow when arrivals outpace the worker
```python
arrivals_ms = [0, 20, 40, 60, 80]
service_ms = 30
worker_free_at = 0
for arrive in arrivals_ms:
    start = max(arrive, worker_free_at)
    wait = start - arrive
    worker_free_at = start + service_ms
    print(f"arrives {arrive:3} ms, waits {wait:2} ms")
```
:::

Every request waits 10 ms longer than the one before, forever. The worker is asked for 30 ms of work every 20 ms, which is 150% utilization, so the queue never drains. Real services fall over this way: latency climbs, clients time out and retry, and the retries add more load.

**Little's law** makes this precise. In a steady system, the average number of requests in flight equals the arrival rate times the average time each one spends inside:

**L = λ × W** (requests in flight = arrivals per second × seconds per request)

At 200 requests per second with 40 ms per request, there are on average 200 × 0.040 = 8 requests in progress at once. If one instance handles 4 at a time and you want headroom (say, run at 60% of capacity so bursts don't cause queues), you need ⌈8 / (4 × 0.6)⌉ = 4 instances:

```python run
import math

def instances_needed(requests_per_s, seconds_per_request, concurrency_per_instance, target_utilization=0.6):
    in_flight = requests_per_s * seconds_per_request           # Little's law: L = λW
    return in_flight, math.ceil(in_flight / (concurrency_per_instance * target_utilization))

for rate, latency in [(20, 0.040), (200, 0.040), (200, 0.080), (2000, 0.040)]:
    in_flight, n = instances_needed(rate, latency, concurrency_per_instance=4)
    print(f"{rate:5} req/s at {latency * 1000:3.0f} ms -> {in_flight:5.1f} in flight -> {n:3} instances")
```

Notice the third row: doubling latency nearly doubles the instances you need, even with the same traffic. Making each prediction faster is often cheaper than buying more servers.

## What each mode costs

Cloud providers bill in three main shapes, and each mode matches one:

- **Always-on instances** bill for every hour they exist, busy or idle. Online APIs with steady traffic usually live here.
- **Scale-to-zero** platforms (often called serverless) bill only while handling requests, but the first request after an idle period pays a **cold start** while a container boots and loads the model.
- **Scheduled jobs** bill only while they run. Batch scoring lives here.

The prices below are made-up round numbers to show the shape of the comparison; real prices vary by provider and change often, so check the pricing page before deciding anything.

```python run
HOURS_PER_MONTH = 730
instance_per_hour = 0.05           # illustrative price for one small always-on instance
job_per_hour = 0.10                # illustrative price for a bigger machine that runs only while the job runs

always_on_api = 2 * HOURS_PER_MONTH * instance_per_hour          # two instances for redundancy
nightly_batch = 30 * (15 / 60) * job_per_hour                    # 15-minute job, every night
print(f"online API, 2 instances always on: ${always_on_api:6.2f} / month")
print(f"nightly batch job, 15 min a night: ${nightly_batch:6.2f} / month")
```

The batch job is about a hundred times cheaper, *if* the predictions can be computed in advance. That condition is the whole decision.

## Free places to run each mode

These are the free options that fit this course's Docker service and scripts. Free tiers change, so treat the details as "true when this was written" and check each provider's page.

- **Online API: Render's free web services.** Render builds a web service from your Dockerfile (choose **Docker** as the language) and offers a Free instance type: 0.1 CPU and 512 MB of RAM, 750 free instance hours per workspace each month, and an ephemeral filesystem. A free service spins down after 15 minutes without traffic, and the next request waits about a minute while it starts again. Fine for a demo; not for a checkout page.
- **Batch jobs: scheduled GitHub Actions workflows.** A workflow with `on: schedule` runs on a cron expression in UTC, at most every 5 minutes, and only on the default branch. Standard GitHub-hosted runners are free for public repositories; private repositories get a monthly allowance. Scheduled runs can start late when GitHub is busy (the top of every hour is the busiest time), and in public repositories they're disabled after 60 days without repository activity.
- **Hugging Face Spaces.** Spaces host ML demos, and the free CPU Basic hardware provides 2 vCPUs and 16 GB of RAM. At the time of writing, though, creating a Docker or Gradio Space on that hardware requires a paid PRO account; free accounts can create static Spaces and up to two Gradio Spaces on ZeroGPU. For this course's Docker service, that makes Render the free choice.
- **Edge.** There's no host to pay for: the model ships inside the app. scikit-learn models are usually converted to a portable format such as ONNX first, so the device doesn't need Python.
- **Streaming** needs a message broker running all the time. You can run Kafka locally in Docker to learn it, but there's no free always-on option worth recommending, so this course treats streaming as a design choice you should recognize rather than one you deploy.

:::warning
**A free tier's cold start is part of your latency.** If your p99 target is 200 ms and the service sleeps after 15 minutes idle, the first user after a quiet period waits about a minute. Measure the cold start along with the warm latency, and say which one your numbers describe.
:::

## Choosing, as a flowchart

```mermaid caption="Start from when the prediction is needed, not from the technology"
flowchart TD
    A[Who needs the prediction, and when?] --> B{"Are all inputs known before it's needed?"}
    B -->|yes| C["Batch: score on a schedule, store results"]
    B -->|no| D{"Must it work offline or on the device?"}
    D -->|yes| E["Edge: ship the model to the device"]
    D -->|no| F{"Triggered by a request, or by a stream of events?"}
    F -->|"a user or service asks"| G[Online API]
    F -->|"events arrive continuously"| H[Streaming consumer]
```

The first question does most of the work. If the inputs are known ahead of time, batch is almost always simpler and cheaper, and the only thing to check is that results won't be too stale by the time they're used.

:::quiz
Q: A bank re-scores every customer's churn risk once a week for its marketing team. Which mode fits?
- [x] Batch
  The inputs are known in advance and nobody is waiting on an answer, so a weekly job is the cheapest and simplest option.
- [ ] Online
  An always-on API would sit idle all week and then be hammered with millions of calls. That's the first company's mistake.
- [ ] Edge
  Marketing reads results in a central system; there's no device that needs the model.

Q: Your API's mean latency is 12 ms, and the p99 is 450 ms. What does that tell you?
- [ ] The service is fast; the p99 is an outlier you can ignore
  1 in 100 requests takes nearly half a second, and pages that make several calls hit that tail much more often than 1% of the time.
- [x] Most requests are fast, but a slow tail exists and needs investigating
  A big gap between p50 and p99 usually points at something intermittent: garbage collection, a cold cache, a noisy neighbour, or queueing under bursts.
- [ ] The mean is wrong; it must be at least 450 ms
  A few slow requests barely move the mean, which is exactly why the mean hides them.

Q: Traffic stays at 100 requests per second, but a new model raises latency from 50 ms to 150 ms. By Little's law, what happens to requests in flight?
- [ ] Nothing, because traffic didn't change
  Requests in flight depends on traffic *and* time in the system.
- [x] They triple, from 5 to 15
  L = λW: 100 × 0.05 = 5 before, 100 × 0.15 = 15 after. Without more capacity, queues build.
- [ ] They drop, because slower requests are processed in larger batches
  Nothing here batches requests; each still waits for its own turn.

Q: A demo runs on a free host that sleeps after 15 idle minutes. A reviewer opens it after lunch, and the first request takes 60 seconds. What happened?
- [ ] The model is too large for the free tier
  The next requests are fast, so the model fits; only the first one was slow.
- [x] A cold start: the service had spun down, and the first request waited for it to boot
  Scale-to-zero saves money while idle and charges you in latency on the first request back.
:::

:::takeaways
- Batch scores ahead of time, online answers each request, streaming reacts to events, and edge runs on the device.
- Bulk scoring is far cheaper per row than single requests, because most of a single prediction is overhead.
- Report latency as p50, p95, and p99; the mean hides the slow tail.
- Little's law, L = λW, turns traffic and latency into the concurrency you must provision.
- Free hosting today: Render for a sleeping online API, GitHub Actions for scheduled batch jobs; Hugging Face Docker Spaces now need a paid plan.
:::
