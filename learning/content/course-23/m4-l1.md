The incident report has one line under "model":

```text
Model in production at time of incident: late-delivery (latest)
```

Which one is that? "latest" was retrained four times last month. Nobody can say which training data it saw, which commit of `train.py` built it, what its test score was, or which version it replaced, so nobody can say whether rolling back would help. The team spends the first two hours of the incident reconstructing history instead of fixing anything.

The cure is boring and completely effective. Every model gets a version that never changes meaning, and every version gets a written record of where it came from.

## What it takes to name a model exactly

A trained model is the output of a function with five inputs. Change any one, and you can get a different model:

```mermaid caption="A model version is pinned only when every input that produced it is pinned"
flowchart LR
    D["Training data (SHA-256 of the file)"] --> T[train.py run]
    C["Code (git commit)"] --> T
    P["Config (params, seed, split)"] --> T
    E["Environment (Python + library versions)"] --> T
    T --> A["Artifact model.joblib (SHA-256)"]
    A --> R["Registry record: late-delivery 1.0.0"]
```

The **registry record** is where all six identifiers get written down together, along with the metrics. Code already has a version system (Git). Environments are pinned by `requirements.txt` and the Docker base image. Data and artifacts are the gaps this lesson fills, and the tool for both is the same: a content hash.

## Fingerprint the data with a content hash

SHA-256 reads a file's bytes and produces a 64-character hex string. The same bytes always give the same string. Any change, however small, gives a completely different string, and nobody knows how to find two different files with the same one. That makes the hash a fingerprint: store 64 characters, and you can later prove whether a file is *exactly* the one you trained on.

```python run
import hashlib
import json
from pathlib import Path

import numpy as np
import pandas as pd

def make_orders(n=2000, seed=23):
    rng = np.random.default_rng(seed)
    distance_km = rng.gamma(shape=2.0, scale=2.0, size=n).round(2)
    items = rng.integers(1, 9, size=n)
    hour = rng.integers(10, 23, size=n)
    raining = (rng.random(n) < 0.25).astype(int)
    rush = (hour >= 17) & (hour <= 19)
    logit = -4.0 + 0.45 * distance_km + 0.15 * items + 1.2 * raining + 0.9 * rush
    late = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return pd.DataFrame({"distance_km": distance_km, "items": items,
                         "hour": hour, "raining": raining, "late": late})

def sha256_file(path):
    with open(path, "rb") as f:
        return hashlib.file_digest(f, "sha256").hexdigest()

Path("data").mkdir(exist_ok=True)
orders = make_orders()
orders.to_csv("data/orders.csv", index=False)

edited = orders.copy()
edited.loc[0, "late"] = 1 - edited.loc[0, "late"]           # flip one label out of 2,000
edited.to_csv("data/orders_edited.csv", index=False)

orders.sample(frac=1, random_state=1).to_csv("data/orders_shuffled.csv", index=False)

for name in ["orders.csv", "orders_edited.csv", "orders_shuffled.csv"]:
    print(f"{name:20} {sha256_file('data/' + name)}")
```

Flipping one label out of 2,000 changed every character of the hash, which is exactly what you want from a fingerprint. Shuffling the rows changed it too, even though the *set* of rows is identical, because the file's bytes are in a different order. `hashlib.file_digest` (Python 3.11 and newer) reads the file in pieces, so it works on files far bigger than memory.

:::warning
**The hash covers bytes, not meaning.** Opening the CSV in a spreadsheet and saving it again can change number formatting or line endings, and the hash changes even though no value did. That's a feature for reproducibility: it tells you the file isn't the one you trained on. If you need "same rows regardless of format or order", compute a canonical fingerprint from the parsed data instead; the practice lesson builds one.
:::

## Same inputs, same bytes

Now hash the model. Train it twice from the same file, and once from the shuffled file:

```python run
import joblib
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import roc_auc_score
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

FEATURES = ["distance_km", "items", "hour", "raining"]

def train(frame):
    prep = ColumnTransformer([
        ("scale", StandardScaler(), ["distance_km", "items"]),
        ("hour", OneHotEncoder(handle_unknown="ignore"), ["hour"]),
    ], remainder="passthrough")
    return Pipeline([("prep", prep), ("clf", LogisticRegression(max_iter=1000))]).fit(frame[FEATURES], frame["late"])

def save_and_hash(model, path):
    joblib.dump(model, path)
    return sha256_file(path)

Path("models").mkdir(exist_ok=True)
model_a = train(pd.read_csv("data/orders.csv"))
hash_a = save_and_hash(model_a, "models/run_a.joblib")
hash_b = save_and_hash(train(pd.read_csv("data/orders.csv")), "models/run_b.joblib")
model_c = train(pd.read_csv("data/orders_shuffled.csv"))
hash_c = save_and_hash(model_c, "models/run_c.joblib")

print("run A, orders.csv        ", hash_a[:16])
print("run B, orders.csv again  ", hash_b[:16])
print("run C, shuffled rows     ", hash_c[:16])
gap = np.abs(model_a.predict_proba(orders[FEATURES]) - model_c.predict_proba(orders[FEATURES])).max()
print(f"largest prediction gap between A and C: {gap:.1e}")
```

Runs A and B produced byte-identical files. That's a strong, cheap reproducibility test: if retraining from the recorded inputs doesn't reproduce the recorded artifact hash, some input wasn't pinned (an unseeded split, a different library version, data that changed underneath you).

Run C is a different file. The solver added up the same numbers in a different order, and floating-point arithmetic isn't perfectly associative, so the coefficients differ in their last digits. The predictions agree to many decimal places, so for most purposes A and C are the same model. But "the same model" is a judgment; "the same bytes" is a fact, and facts are what an incident review needs.

## Version numbers people can reason about

A hash identifies an artifact, but nobody wants to say "roll back to `d3a9be76`". People need names that also carry *meaning*. **Semantic versioning** (MAJOR.MINOR.PATCH) was invented for software libraries, where it describes API compatibility. For models, you have to define what the parts mean, and the most useful convention ties them to the service contract:

| Bump | When | Example |
| --- | --- | --- |
| MAJOR (`2.0.0`) | The request or response contract changes; clients must change | Adding a required `restaurant_id` feature, or switching distance to miles |
| MINOR (`1.1.0`) | Same contract, different predictions | Retrained on new data, new hyperparameters, a different algorithm, a new threshold |
| PATCH (`1.0.1`) | Predictions identical for every input | Fixing a typo in the metadata, repackaging the same weights |

Two rules make versions trustworthy. A version is **immutable**: once `1.1.0` is registered, its artifact never changes, and a fix becomes `1.1.1` or `1.2.0`. And a deployment refers to a version through an **alias**, a movable label such as `champion` (serving now) or `challenger` (being evaluated). Promoting a model moves the alias; rolling back moves it back. The versions underneath never change, so the history stays true.

"latest" fails both rules. It isn't a version (it moves), and it isn't a deliberate alias (it moves whenever anyone trains anything). Docker image tags have the same problem: `late-delivery:latest` can point at a different image tomorrow. Every image also has an immutable **digest** (`sha256:...`, shown by `docker images --digests`), and `docker pull late-delivery@sha256:...` always gets exactly that image.

## A registry is a table of records

A **model registry** stores, for every version, the artifact plus a record of where it came from, and keeps track of which version each alias points at. The record is the part that answers the incident review's questions. Here is the one for the model you just trained:

```python run
import platform
import subprocess
from datetime import datetime, timezone

import sklearn

def git_commit():
    """Current commit, marked -dirty if there are uncommitted changes."""
    try:
        commit = subprocess.run(["git", "rev-parse", "--short", "HEAD"],
                                capture_output=True, text=True, check=True).stdout.strip()
        dirty = subprocess.run(["git", "status", "--porcelain"], capture_output=True, text=True).stdout.strip()
        return commit + ("-dirty" if dirty else "")
    except (subprocess.CalledProcessError, FileNotFoundError):
        return "unknown"

holdout = make_orders(n=1000, seed=99)          # a fixed evaluation set every version is scored on
record = {
    "name": "late-delivery",
    "version": "1.0.0",
    "created_at": datetime.now(timezone.utc).isoformat(timespec="seconds"),
    "artifact": {"file": "models/run_a.joblib", "sha256": hash_a},
    "training_data": {"file": "data/orders.csv", "sha256": sha256_file("data/orders.csv"), "rows": len(orders)},
    "code": {"git_commit": git_commit()},
    "params": {"estimator": "LogisticRegression", "max_iter": 1000},
    "environment": {"python": platform.python_version(), "scikit-learn": sklearn.__version__,
                    "numpy": np.__version__, "pandas": pd.__version__},
    "schema": {"features": FEATURES, "output": "late_probability in [0, 1]", "threshold": 0.5},
    "metrics": {"holdout_roc_auc": round(roc_auc_score(holdout["late"], model_a.predict_proba(holdout[FEATURES])[:, 1]), 4)},
    "parent": None,
}
print(json.dumps(record, indent=2))
```

Every question from the incident report now has an answer in one file: which data (the hash), which code (the commit), what configuration, which environment, how good it was, and what it replaced (`parent`). On this page the code isn't in a Git repository, so the commit reads `unknown`, and the runner uses Python 3.13; in your project you'll see a real commit and `3.12.x`. The `-dirty` suffix matters: it marks a model trained from code with uncommitted changes, which no commit can reproduce.

The registry itself can be as simple as a folder of these files, which is what you'll build next lesson. Larger teams use a registry service.

## The same ideas in MLflow

MLflow is a widely used open-source platform with two parts that matter here. **Tracking** records each training run's parameters, metrics, input datasets, and artifacts. The **model registry** turns a logged model into a named, versioned entry with aliases and tags. It isn't installed on this page, so the code below is shown rather than run; it follows the current MLflow 3 API. Install it in your dev environment only (`python -m pip install mlflow`); the serving image doesn't need it.

```py title="train_mlflow.py"
import mlflow
from mlflow import MlflowClient
from mlflow.models import infer_signature

mlflow.set_tracking_uri("sqlite:///mlflow.db")     # the model registry needs a database-backed store
mlflow.set_experiment("late-delivery")

orders = pd.read_csv("data/orders.csv")
with mlflow.start_run(run_name="retrain-1.1.0"):
    model = train(orders)
    proba = model.predict_proba(holdout[FEATURES])[:, 1]
    mlflow.log_params({"estimator": "LogisticRegression", "max_iter": 1000})
    mlflow.log_metrics({"holdout_roc_auc": roc_auc_score(holdout["late"], proba)})
    mlflow.log_input(mlflow.data.from_pandas(orders, source="data/orders.csv", name="orders", targets="late"),
                     context="training")
    mlflow.set_tags({"data_sha256": sha256_file("data/orders.csv"), "git_commit": git_commit()})
    info = mlflow.sklearn.log_model(
        sk_model=model,
        name="model",
        signature=infer_signature(holdout[FEATURES], proba),
        input_example=holdout[FEATURES].head(3),
        registered_model_name="late-delivery",
    )

client = MlflowClient()
version = info.registered_model_version              # MLflow numbers versions 1, 2, 3, ...
client.set_model_version_tag("late-delivery", str(version), "semver", "1.1.0")
client.set_registered_model_alias("late-delivery", "champion", version)

champion = mlflow.sklearn.load_model("models:/late-delivery@champion")
```

To browse runs and registered models, start the tracking server and open http://localhost:5000:

```bash
mlflow server --backend-store-uri sqlite:///mlflow.db --port 5000
```

Each idea from this lesson has an MLflow counterpart. Runs record params, metrics, tags, and datasets; `log_input` stores a dataset with a digest that MLflow computes for you. `registered_model_name` creates the next version of a named model. MLflow numbers versions with plain integers, so the semantic version goes in a tag. Aliases work as described above, and `models:/late-delivery@champion` always loads whichever version the alias points to. MLflow once used fixed "stages" (Staging, Production) for this; stages have been deprecated since MLflow 2.9 in favour of aliases and tags.

What to watch for: registering a model from a run, browsing its versions in the MLflow UI, and loading a registered model by name. If the video moves a model between stages such as Staging and Production, the current equivalent is setting an alias such as `champion`.
:::

## Model cards: the record written for people

A registry record is for machines and incident reviews. A **model card**, an idea from a 2019 paper by Mitchell and colleagues, is the short document for people deciding whether to use the model: what it's for, what it isn't for, what data it learned from, how it performs (including on important subgroups), and its known limitations. A card for this model would include lines like these:

```text
Intended use: rank today's orders by risk of arriving late, to plan driver capacity.
Not for: judging individual drivers or restaurants; the model has no driver features.
Training data: 2,000 synthetic orders, 10:00-22:59, sha256 b0efa125...; 30% late.
Holdout ROC AUC: 0.81 overall. Not yet measured by city or by weather.
Known limits: never saw orders before 10:00; hours outside 10-22 get no hour signal.
```

The best cards are generated from the registry record plus a few hand-written sentences, so the numbers can't drift from the truth. You'll generate one next lesson.

:::quiz
Q: You open `data/orders.csv` in a spreadsheet and click Save without changing any values. You hash it again. What happens?
- [ ] Same hash, because no values changed
  The hash sees bytes, not values. Saving can change number formatting, quoting, or line endings.
- [x] Very likely a different hash, because the saved bytes changed
  That's the hash doing its job: the file is no longer byte-for-byte the one recorded. If you must edit data by hand, re-record its hash and treat it as new data.
- [ ] An error, because spreadsheets can't save CSV files
  They can; that's exactly why this mistake is common.

Q: You change the decision threshold from 0.5 to 0.4 without retraining. Under this lesson's convention, which version bump is it?
- [ ] PATCH, because the model weights didn't change
  PATCH is for changes that leave every output identical. The `late` field now flips for some orders.
- [x] MINOR, because the contract is the same but outputs change
  Clients still send and receive the same fields, but some answers differ, so it's a new behaviour under the same contract.
- [ ] MAJOR, because predictions change
  MAJOR is reserved for contract changes that force clients to change their code.

Q: The serving config says `alias: champion`. You promote 1.2.0, and an hour later you need to roll back. What changes?
- [x] The `champion` alias moves back to the previous version; no artifact is rebuilt or edited
  Versions are immutable, so rollback is just pointing the alias at a version that already exists and was already tested.
- [ ] 1.2.0's artifact is overwritten with the old weights
  That would make "1.2.0" mean two different things, which destroys the history the registry exists to keep.
- [ ] You retrain the previous model from scratch
  Unnecessary and risky: the previous artifact is still in the registry, byte for byte.

Q: Retraining from a record's exact data file, commit, and environment gives a different artifact hash. What does that tell you?
- [ ] Nothing; model hashes are random
  For this pipeline, two runs from identical inputs gave byte-identical files.
- [x] Some input that matters wasn't recorded or pinned
  Typical culprits: an unseeded random split, a library version that differs, or code with uncommitted changes (a `-dirty` commit).
- [ ] SHA-256 is unreliable for binary files
  SHA-256 treats every file as bytes; it's exactly as reliable for `.joblib` as for `.csv`.
:::

:::takeaways
- A model is pinned by five inputs (data, code, config, environment) plus its artifact; record all of them.
- SHA-256 fingerprints exact bytes: any edit, reorder, or re-save changes it.
- Retraining from identical recorded inputs should reproduce the artifact hash; if it doesn't, something wasn't pinned.
- Versions are immutable and carry meaning (MAJOR = contract, MINOR = behaviour, PATCH = nothing observable); aliases like `champion` move.
- MLflow provides the same pieces: runs, registered model versions, tags, and aliases loaded with `models:/name@alias`.
:::
