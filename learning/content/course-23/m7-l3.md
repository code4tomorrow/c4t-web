Setup: the champion, a test for "is the canary's rate worse," and the registry helpers in the shape of your Module 4 `aliases.json`. Run it first.

```python run
import hashlib
import json
from collections import OrderedDict
from datetime import datetime

import numpy as np
import pandas as pd
from scipy import stats
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

def make_orders(n=2000, seed=23):
    rng = np.random.default_rng(seed)
    distance_km = rng.gamma(shape=2.0, scale=2.0, size=n).round(2)
    items = rng.integers(1, 9, size=n)
    hour = rng.integers(10, 23, size=n)
    raining = (rng.random(n) < 0.25).astype(int)
    rush = (hour >= 17) & (hour <= 19)
    logit = -4.0 + 0.45 * distance_km + 0.15 * items + 1.2 * raining + 0.9 * rush
    late = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return pd.DataFrame({"distance_km": distance_km, "items": items,
                         "hour": hour, "raining": raining, "late": late})

FEATURES = ["distance_km", "items", "hour", "raining"]

def build():
    prep = ColumnTransformer([("scale", StandardScaler(), ["distance_km", "items"]),
                              ("hour", OneHotEncoder(handle_unknown="ignore"), ["hour"])],
                             remainder="passthrough")
    return Pipeline([("prep", prep), ("clf", LogisticRegression(max_iter=1000))])

def worse_than_baseline(bad_c, n_c, bad_b, n_b):
    """One-sided two-proportion z-test. Returns (canary rate, baseline rate, p-value)."""
    p_c, p_b = bad_c / n_c, bad_b / n_b
    pooled = (bad_c + bad_b) / (n_c + n_b)
    se = np.sqrt(pooled * (1 - pooled) * (1 / n_c + 1 / n_b))
    return p_c, p_b, (stats.norm.sf((p_c - p_b) / se) if se > 0 else 1.0)

champion = build().fit(make_orders()[FEATURES], make_orders()["late"])
print("ready")
```

## Warm-up: promote, wait, or roll back?

The baseline has 0.3% errors, p99 of 48 ms, and misses 40% of late rainy orders. For each canary readout, decide:

1. 2,000 requests, 0.35% errors, p99 50 ms, misses 42% of 60 late rainy orders.
2. 90 requests, 1 error, p99 49 ms, no rainy outcomes yet.
3. 2,500 requests, 0.3% errors, p99 95 ms, misses 39% of 75 late rainy orders.

:::solution
1. **Promote**: every difference is small and within what chance produces at these sample sizes.
2. **Wait**: 90 requests can't tell 0.3% from 1.1%, and there are no outcomes to judge the slice.
3. **Roll back**: errors and the rain slice are fine, but p99 almost doubled. Latency is part of correctness for an interactive service, and the slower model would also need more instances.
:::

### Exercise 1: Which slice did the canary break?

The canary model was trained while the weather feed was down, so most rainy orders in its training data were recorded as dry. It serves 10% of 6,000 orders, chosen by hashing the order ID. Using each arm's warnings and the true outcomes, compute the share of late orders that got *no* warning (the miss rate) on five slices for canary and baseline, test each with `worse_than_baseline`, and report which slices are significantly worse at p < 0.01.

```python run
outage = make_orders(2000, seed=30)
rng = np.random.default_rng(4)
outage.loc[(outage.raining == 1) & (rng.random(len(outage)) < 0.8), "raining"] = 0
canary_model = build().fit(outage[FEATURES], outage["late"])

traffic = make_orders(6000, seed=31)
traffic["arm"] = ["canary" if int(hashlib.sha256(f"ord-{i}".encode()).hexdigest(), 16) % 100 < 10 else "baseline"
                  for i in range(len(traffic))]
scores = np.where(traffic.arm == "canary", canary_model.predict_proba(traffic[FEATURES])[:, 1],
                  champion.predict_proba(traffic[FEATURES])[:, 1])
traffic["warned"] = scores >= 0.5
print(traffic.arm.value_counts().to_dict())
```

Sample output:

```text
slice        canary miss  baseline miss  late (c/b)   p-value
all                 0.55           0.50    171/1657     0.091
rainy               0.61           0.37     66/607    8.0e-05  WORSE
...
```

:::hint
For each slice mask `m`, the canary's late orders are `(traffic.arm == "canary") & m & (traffic.late == 1)`. The miss count is how many of those have `warned == False`. Do the same for the baseline and pass all four counts to `worse_than_baseline`.
:::

:::solution
```python run
slices = {"all": np.ones(len(traffic), dtype=bool), "rainy": traffic.raining == 1, "dry": traffic.raining == 0,
          "rush": traffic.hour.between(17, 19), "over 6 km": traffic.distance_km > 6}
late = traffic.late == 1
print(f"{'slice':10}{'canary miss':>13}{'baseline miss':>15}{'late (c/b)':>12}{'p-value':>10}")
for name, m in slices.items():
    c = (traffic.arm == "canary") & m & late
    b = (traffic.arm == "baseline") & m & late
    p_c, p_b, p = worse_than_baseline((~traffic.warned[c]).sum(), c.sum(), (~traffic.warned[b]).sum(), b.sum())
    print(f"{name:10}{p_c:13.2f}{p_b:15.2f}{f'{c.sum()}/{b.sum()}':>12}{p:10.1e}  {'WORSE' if p < 0.01 else ''}")
```

Only the rainy slice is significantly worse, and the overall number isn't (p ≈ 0.09), which is why a canary that checks only totals would have been promoted. The canary's rain coefficient is much weaker because most rainy training rows said "dry." Notice that the canary arm has only 66 late rainy orders: slice checks need enough canary traffic, so a rainy-slice check might keep a canary at 10% for longer on a dry day, and that's the right call.
:::

### Exercise 2: The peeking problem

The rollback rule runs every 5 minutes for an hour (12 checks, 150 canary requests each) and rolls back the first time p < 0.05. Simulate 500 *healthy* canaries (same 0.3% error rate as the baseline) and count how often the rule rolls back anyway. Then try two fixes: require 1,000 canary requests before any check counts, and divide alpha by the number of checks (a Bonferroni correction).

:::hint
For each trial, draw the baseline's errors once with `rng.binomial(20000, 0.003)`, and the canary's cumulative errors with `np.cumsum(rng.binomial(150, 0.003, 12))`. At check `k` the canary has served `150 * (k + 1)` requests. Stop at the first check with p below alpha.
:::

:::solution
```python run
def false_rollbacks(alpha, min_requests=0, checks=12, per_check=150, trials=500, seed=0):
    rng = np.random.default_rng(seed)
    rolled_back = 0
    for _ in range(trials):
        base_errors = rng.binomial(20_000, 0.003)
        errors = np.cumsum(rng.binomial(per_check, 0.003, checks))
        served = per_check * np.arange(1, checks + 1)
        for e, n in zip(errors, served):
            if n >= min_requests and worse_than_baseline(e, n, base_errors, 20_000)[2] < alpha:
                rolled_back += 1
                break
    return rolled_back / trials

print(f"one check at the end, alpha 0.05:   {false_rollbacks(0.05, checks=1, per_check=1800):.1%}")
print(f"12 checks, alpha 0.05:              {false_rollbacks(0.05):.1%}")
print(f"12 checks, alpha 0.05, min 1,000:   {false_rollbacks(0.05, min_requests=1000):.1%}")
print(f"12 checks, alpha 0.05/12, min 1,000: {false_rollbacks(0.05 / 12, min_requests=1000):.1%}")
```

Every check is another chance for noise to cross the line, so checking a dozen times turns a 5% false-alarm rate into a much larger one. The early checks are the worst offenders: with 150 requests, a single error looks like a rate twice the baseline's, and the normal approximation behind the z-test is poor at such small counts. A minimum sample removes those checks, and dividing alpha by the number of checks keeps the total false-rollback rate near the level you chose. False rollbacks aren't free: each one throws away a good release and trains people to distrust the automation. (Sequential tests designed for repeated looks exist; for most teams, a minimum sample plus a stricter alpha is enough.)
:::

### Exercise 3: Roll back to the last *good* version

1.2.0 caused INC-112, and the hotfix 1.2.1 turned out to be bad too. A naive rollback from 1.2.1 would move `champion` to its previous target, 1.2.0, which is also bad. Write `rollback_to_last_good(aliases, records, bad)` that walks the alias history backward, picks the most recent earlier champion that isn't in `bad` and has the same feature list as the current one, appends a history entry, and refuses if no such version exists.

```python run
records = {v: {"version": v, "schema": {"features": FEATURES}} for v in ["1.0.0", "1.1.0", "1.2.0", "1.2.1"]}
aliases = {"current": {"champion": "1.2.1"}, "history": [
    {"alias": "champion", "from": None, "to": "1.0.0", "reason": "first production model"},
    {"alias": "champion", "from": "1.0.0", "to": "1.1.0", "reason": "retrained Jan+Feb"},
    {"alias": "champion", "from": "1.1.0", "to": "1.2.0", "reason": "canary passed"},
    {"alias": "champion", "from": "1.2.0", "to": "1.2.1", "reason": "hotfix for INC-112"},
]}
bad = {"1.2.0", "1.2.1"}
print("naive rollback would pick:", aliases["history"][-1]["from"])
```

:::hint
Collect the `to` values of the champion's history in reverse order, skip the current version and anything in `bad`, and check `records[v]["schema"]["features"]` against the current record's. Record the move the same way `set_alias` does, with `from`, `to`, and a reason.
:::

:::solution
```python run
def rollback_to_last_good(aliases, records, bad, reason, alias="champion"):
    current = aliases["current"][alias]
    wanted = records[current]["schema"]["features"]
    seen = []
    for move in reversed(aliases["history"]):
        version = move["to"]
        if move["alias"] != alias or version == current or version in seen:
            continue
        seen.append(version)
        if version in bad:
            continue
        if records[version]["schema"]["features"] != wanted:
            raise ValueError(f"{version} expects different features; roll forward instead")
        aliases["history"].append({"alias": alias, "from": current, "to": version,
                                   "reason": f"rollback: {reason}"})
        aliases["current"][alias] = version
        return version
    raise ValueError(f"no known-good earlier version of {alias}; roll forward")

print("champion is now", rollback_to_last_good(aliases, records, bad, reason="INC-112 hotfix also bad"))
print(json.dumps(aliases["history"][-1]))
```

The function skips 1.2.0 because it's marked bad and lands on 1.1.0, the last version that was champion and is still trusted. Keeping a `bad` list in the registry (as a tag on each record, for example) makes this automatic, and the schema check refuses to roll back across a feature change, where the old model would receive inputs it can't handle. Then, as in Module 4, restart the service and confirm `/health` reports 1.1.0.
:::

### Exercise 4: A cache whose entries expire

The `lru_cache` from the build never forgets an answer while it's in the cache. Write `TTLCache(maxsize, ttl_seconds)` with `get(key, now)` and `put(key, value, now)`, where entries older than the TTL count as misses, and least recently used entries are evicted when full. Use an `OrderedDict`. Test it on two customers' polling streams, each polled every 30 seconds for five minutes.

```python run
stream = [(t, ("ord-1", 6.5, 3, 18, False)) for t in range(0, 300, 30)]
stream += [(t, ("ord-2", 2.0, 1, 12, False)) for t in range(15, 300, 30)]
stream.sort()
print(len(stream), "requests;", stream[:3])
```

:::hint
Store `(value, stored_at)` in the `OrderedDict`. On `get`, if the key is missing or `now - stored_at > ttl`, it's a miss; on a hit, call `move_to_end(key)`. On `put`, call `popitem(last=False)` while the dict is over `maxsize`.
:::

:::solution
```python run
class TTLCache:
    def __init__(self, maxsize, ttl_seconds):
        self.maxsize, self.ttl = maxsize, ttl_seconds
        self.data = OrderedDict()
        self.hits = self.misses = 0

    def get(self, key, now):
        entry = self.data.get(key)
        if entry is None or now - entry[1] > self.ttl:
            self.misses += 1
            return None
        self.data.move_to_end(key)
        self.hits += 1
        return entry[0]

    def put(self, key, value, now):
        self.data[key] = (value, now)
        self.data.move_to_end(key)
        while len(self.data) > self.maxsize:
            self.data.popitem(last=False)

for ttl in [10_000, 60]:
    cache = TTLCache(maxsize=100, ttl_seconds=ttl)
    for now, key in stream:
        if cache.get(key, now) is None:
            cache.put(key, f"score computed at {now}s", now)
    print(f"ttl {ttl:>6}s: hits {cache.hits}, misses {cache.misses}, ord-1 answer: {cache.data[stream[0][1]][0]}")
```

With an effectively infinite TTL, ord-1's score is computed once and reused for five minutes. With a 60-second TTL it's recomputed every couple of polls, so a change, such as the model version moving or rain starting at the restaurant, can be stale for at most a minute. The TTL is a product decision about how stale an answer may be, traded against hit rate.
:::

### Exercise 5: Keep a month under budget

Traffic follows a daily curve, peaking at dinner. The team targets 70% utilization per instance (headroom for bursts) and caps autoscaling at 3 instances. Using the per-instance throughputs measured in the build, compute for each variant: instances needed per hour, the monthly cost with the cap, and how many hours a day the cap binds (traffic the capped fleet can't serve at the target).

```python run
hourly_rps = np.array([20, 10, 8, 8, 10, 30, 60, 90, 120, 150, 260, 420,
                       480, 300, 200, 220, 380, 900, 1400, 1300, 800, 400, 150, 60])
variants = {"pipeline": 500, "pipeline + cache": 1600, "compiled scorer": 3200}   # req/s per instance
PRICE, CAP, UTILIZATION = 0.10, 3, 0.7
print("peak", hourly_rps.max(), "req/s at", hourly_rps.argmax(), ":00")
```

:::hint
Instances needed in an hour is `ceil(rps / (capacity * utilization))`, at least 1. Apply `np.minimum(needed, CAP)`, sum the instance-hours over the day, and multiply by 30 days and the price.
:::

:::solution
```python run
print(f"{'variant':18}{'peak need':>10}{'$/month':>9}{'hours capped':>14}")
for name, capacity in variants.items():
    needed = np.maximum(1, np.ceil(hourly_rps / (capacity * UTILIZATION))).astype(int)
    used = np.minimum(needed, CAP)
    cost = used.sum() * 30 * PRICE
    print(f"{name:18}{needed.max():10}{cost:9.0f}{int((needed > CAP).sum()):14}")
```

With the original pipeline, the dinner peak needs more instances than the cap allows, so for two hours a day the service runs hot: latency rises and the alert from Module 6 fires. The cache and the compiled scorer each bring the peak under the cap, and cut the monthly bill because quiet hours drop to a single instance. A cap doesn't save money by itself. It makes the shortfall visible, so the fix is a deliberate choice: optimize, raise the cap, or accept slower dinners.
:::

### Exercise 6: From a raw timeline to postmortem numbers

Compute three standard durations from this event log: **time to detect** (impact start to the first alert or report), **time to mitigate** (impact start to the mitigation that stopped the harm), and **impact duration** (impact start to confirmed recovery). Then write the TIMELINE section of the postmortem.

```python run
events = [
    ("17:48", "deploy", "1.2.0 canary starts at 10%"),
    ("18:05", "impact_start", "heavy rain begins; canary starts missing rainy warnings"),
    ("18:40", "report", "support lead reports complaints in #team"),
    ("18:52", "declared", "SEV2 declared, IC assigned"),
    ("18:55", "mitigation", "canary set to 0%"),
    ("19:10", "recovered", "no new complaints; late-rate gap normal for 15 minutes"),
]
print(len(events), "events")
```

:::hint
Parse times with `datetime.strptime(t, "%H:%M")` and subtract them; `.total_seconds() / 60` gives minutes. Look events up by their type with a dict comprehension.
:::

:::solution
```python run
at = {kind: datetime.strptime(t, "%H:%M") for t, kind, _ in events}
minutes = lambda a, b: int((at[b] - at[a]).total_seconds() // 60)
print(f"time to detect:   {minutes('impact_start', 'report')} min")
print(f"detect to declare: {minutes('report', 'declared')} min")
print(f"time to mitigate: {minutes('impact_start', 'mitigation')} min")
print(f"impact duration:  {minutes('impact_start', 'recovered')} min")
print("\nTIMELINE")
for t, kind, text in events:
    print(f"{t}  {text}")
```

Thirty-five minutes to detect is the headline finding, and it points straight at the missing slice check: a human noticed before any machine did. The twelve minutes between the report and the declaration point at the missing owner. Mitigation itself took three minutes once someone was in charge, which shows that the rollback mechanism was fine and the decision was the bottleneck. Good postmortems turn each gap like this into an action item with an owner.
:::

### Challenge: An error-budget policy

A smaller regional deployment of the service handles about 26 million requests a month, with an SLO of 99.5% successful requests per 30 days. This month had three incidents. Compute the share of the error budget each one consumed and the total, then apply the team's policy: above 100% consumed, freeze model releases except fixes; above 50%, canaries must use 5% steps and need two reviewers; otherwise, normal releases.

:::solution
```python run
monthly_requests = 26_000_000
budget = 0.005 * monthly_requests                     # failed requests the SLO allows
incidents = [("INC-108 bad deploy", 15, 200, 0.30),   # name, minutes, req/s during it, error rate
             ("INC-110 cold starts", 90, 250, 0.04),
             ("INC-112 rain canary", 50, 90, 0.00)]
used = 0.0
for name, minutes, rps, error_rate in incidents:
    failed = minutes * 60 * rps * error_rate
    used += failed / budget
    print(f"{name:22}{failed:9,.0f} failed requests  {failed / budget:6.1%} of budget")
print(f"total budget used: {used:.1%}")
policy = ("freeze releases except fixes" if used > 1 else
          "5% canary steps and two reviewers" if used > 0.5 else "normal releases")
print("policy:", policy)
```

INC-112 used none of the budget, because every request succeeded: the model just gave wrong answers. Availability SLOs can't see model quality, so an ML service needs a quality objective too, such as "the late-rate gap stays under 0.10 for 99% of hours," with its own budget and policy. The error-budget idea turns reliability into an agreed rule for when to slow down, instead of a negotiation after every incident.
:::
