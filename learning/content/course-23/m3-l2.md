- Write a batch scorer that reads in chunks, validates columns, and replaces its output file atomically.
- Stamp every stored prediction with the model version and the time it was computed.
- Benchmark an API's latency percentiles and draw them as a histogram.
- Compare batch and online throughput on the same model and the same machine.
- Schedule the batch job with a GitHub Actions cron workflow, and deploy the API to Render's free tier.
:::

The late-delivery model has two customers. The operations team wants a risk score for every one of tomorrow's 50,000 scheduled orders by 7 a.m., so they can add drivers on the worst routes. The checkout page wants a score for one cart, right now. Same model file, two serving modes. By the end of this lesson you'll have both, measured:

```text
batch:  50,000 orders scored in under a second, every row stamped with model 1.0.0
online: one order per request, milliseconds each, with p50, p95, and p99 measured
```

The exact numbers depend on your machine. The shape doesn't: batch wins on throughput by a wide margin, and only online can answer a cart that didn't exist last night.

## Step 1: Start from Module 2's artifacts

If you finished Module 2, `models/model.joblib` and `models/model.json` already exist in your project. This cell recreates them on this page so the rest of the lesson has something to load.

```python run
import json
import time
from pathlib import Path

import joblib
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

def make_orders(n=2000, seed=23):
    rng = np.random.default_rng(seed)
    distance_km = rng.gamma(shape=2.0, scale=2.0, size=n).round(2)
    items = rng.integers(1, 9, size=n)
    hour = rng.integers(10, 23, size=n)
    raining = (rng.random(n) < 0.25).astype(int)
    rush = (hour >= 17) & (hour <= 19)
    logit = -4.0 + 0.45 * distance_km + 0.15 * items + 1.2 * raining + 0.9 * rush
    late = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return pd.DataFrame({"distance_km": distance_km, "items": items,
                         "hour": hour, "raining": raining, "late": late})

FEATURES = ["distance_km", "items", "hour", "raining"]
history = make_orders()
model = Pipeline([
    ("prep", ColumnTransformer([
        ("scale", StandardScaler(), ["distance_km", "items"]),
        ("hour", OneHotEncoder(handle_unknown="ignore"), ["hour"]),
    ], remainder="passthrough")),
    ("clf", LogisticRegression(max_iter=1000)),
]).fit(history[FEATURES], history["late"])

Path("models").mkdir(exist_ok=True)
joblib.dump(model, "models/model.joblib")
Path("models/model.json").write_text(json.dumps(
    {"name": "late-delivery", "version": "1.0.0", "features": FEATURES, "threshold": 0.5}))
print("models/ ready")
```

## Step 2: Make tomorrow's scheduled orders

In production this file would come from a database query run just before scoring. Here a script generates 50,000 orders with an ID, the day they're scheduled for, and the four features. `raining` is tomorrow's forecast, which is the catch with batch scoring: forecasts change, and a score computed at 2 a.m. can't know that.

```python run title="make_scheduled_orders.py"
"""Write data/scheduled_orders.csv: tomorrow's scheduled orders (demo data)."""
from pathlib import Path

import numpy as np
import pandas as pd

def make_scheduled(n=50_000, seed=7, day="2026-11-17"):
    rng = np.random.default_rng(seed)
    return pd.DataFrame({
        "order_id": [f"ord-{i:06d}" for i in range(n)],
        "scheduled_for": day,
        "distance_km": rng.gamma(2.0, 2.0, n).round(2),
        "items": rng.integers(1, 9, n),
        "hour": rng.integers(10, 23, n),
        "raining": (rng.random(n) < 0.25).astype(int),     # from the weather forecast
    })

if __name__ == "__main__":
    Path("data").mkdir(exist_ok=True)
    scheduled = make_scheduled()
    scheduled.to_csv("data/scheduled_orders.csv", index=False)
    print(f"wrote data/scheduled_orders.csv: {len(scheduled):,} orders")
```

## Step 3: Write the batch scorer

The scorer has four habits worth copying into any batch job:

1. It reads the input in **chunks**, so memory stays flat whether the file has fifty thousand rows or fifty million.
2. It **checks the columns** before scoring and fails with a message that names what's missing.
3. It writes every row with the **model version** and the **time it was scored**, so anyone reading a prediction can tell where it came from and how old it is.
4. It writes to a temporary file and **renames** it at the end. A crash halfway leaves yesterday's complete file in place instead of half of today's.

```python run title="score_batch.py"
"""Score scheduled orders in chunks. Run: python score_batch.py"""
import json
import time
from datetime import datetime, timezone
from pathlib import Path

import joblib
import pandas as pd

def score_file(input_path, model_dir="models", out_dir="predictions", chunk_rows=10_000):
    model = joblib.load(Path(model_dir) / "model.joblib")
    meta = json.loads((Path(model_dir) / "model.json").read_text())
    scored_at = datetime.now(timezone.utc).isoformat(timespec="seconds")

    out_dir = Path(out_dir)
    out_dir.mkdir(exist_ok=True)
    out_path = out_dir / f"{Path(input_path).stem}_scored.csv"
    tmp_path = out_path.with_name(out_path.name + ".tmp")

    rows, start = 0, time.perf_counter()
    with open(tmp_path, "w", newline="") as out:
        for i, chunk in enumerate(pd.read_csv(input_path, chunksize=chunk_rows)):
            missing = set(meta["features"]) - set(chunk.columns)
            if missing:
                raise ValueError(f"{input_path} is missing columns {sorted(missing)}")
            probability = model.predict_proba(chunk[meta["features"]])[:, 1]
            pd.DataFrame({
                "order_id": chunk["order_id"],
                "late_probability": probability.round(4),
                "late": (probability >= meta["threshold"]).astype(int),
                "model_version": meta["version"],
                "scored_at": scored_at,
            }).to_csv(out, header=(i == 0), index=False)
            rows += len(chunk)
    tmp_path.replace(out_path)          # atomic on the same disk: readers see old or new, never half
    return out_path, rows, time.perf_counter() - start

if __name__ == "__main__":
    out_path, rows, seconds = score_file("data/scheduled_orders.csv")
    print(f"scored {rows:,} rows in {seconds:.2f} s ({rows / seconds:,.0f} rows/s) -> {out_path}")
```

Look at what landed on disk, and at what the operations team actually needs from it:

```python run
predictions = pd.read_csv("predictions/scheduled_orders_scored.csv")
print(predictions.head(3).to_string(index=False))
print(f"\n{predictions['late'].sum():,} of {len(predictions):,} orders flagged as likely late")
```

Running the script twice produces the same file name with the same rows (only `scored_at` changes), so a job that's retried after a failure doesn't create duplicates. That property, being safe to rerun, matters more for scheduled jobs than speed does.

## Step 4: Benchmark the online API

Now the other path. Here is the Module 2 service, trimmed to `/predict`:

```python run title="app/main.py"
from contextlib import asynccontextmanager
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, ConfigDict, Field

class Order(BaseModel):
    model_config = ConfigDict(extra="forbid")
    distance_km: float = Field(gt=0, le=50)
    items: int = Field(ge=1, le=50)
    hour: int = Field(ge=0, le=23)
    raining: bool

state = {}

@asynccontextmanager
async def lifespan(app):
    state["model"] = joblib.load("models/model.joblib")
    state["meta"] = json.loads(Path("models/model.json").read_text())
    yield
    state.clear()

app = FastAPI(lifespan=lifespan)

@app.post("/predict")
def predict(order: Order):
    row = pd.DataFrame([order.model_dump()], columns=state["meta"]["features"])
    probability = float(state["model"].predict_proba(row)[0, 1])
    return {"late_probability": round(probability, 3), "model_version": state["meta"]["version"]}
```

The benchmark sends 300 different orders, one after another, and times each full request: JSON encoding, validation, the DataFrame, the model, and the response. A few warm-up requests come first so one-time setup costs don't pollute the numbers.

```python run alt="Histogram of 300 API request latencies. Most requests fall in a tall, narrow peak a few milliseconds wide, with a thin tail stretching to the right. Three vertical lines mark p50, p95, and p99, with p99 noticeably right of the peak." caption="Latency per request through the API. The tail, not the peak, is what users complain about."
import matplotlib.pyplot as plt

sample = pd.read_csv("data/scheduled_orders.csv", nrows=300)
bodies = [{"distance_km": float(r.distance_km), "items": int(r.items), "hour": int(r.hour),
           "raining": bool(r.raining)} for r in sample.itertuples()]

latencies_ms = []
with TestClient(app) as client:
    for body in bodies[:10]:
        client.post("/predict", json=body)                       # warm-up
    for body in bodies:
        start = time.perf_counter()
        response = client.post("/predict", json=body)
        latencies_ms.append((time.perf_counter() - start) * 1000)
        assert response.status_code == 200
latencies_ms = np.array(latencies_ms)
p50, p95, p99 = np.percentile(latencies_ms, [50, 95, 99])

fig, ax = plt.subplots(figsize=(7, 3))
ax.hist(latencies_ms, bins=40, color="#2a78d6")
for value, label, style in [(p50, "p50", "-"), (p95, "p95", "--"), (p99, "p99", ":")]:
    ax.axvline(value, color="#222222", linestyle=style, label=f"{label} = {value:.1f} ms")
ax.set_xlabel("latency per request (ms)")
ax.set_ylabel("requests")
ax.legend(frameon=False)
ax.spines[["top", "right"]].set_visible(False)
plt.tight_layout()
plt.show()
print(f"p50 {p50:.1f} ms | p95 {p95:.1f} ms | p99 {p99:.1f} ms | max {latencies_ms.max():.1f} ms")
```

This measures the service's own processing time on your machine. A real client also pays for the network, which adds anywhere from under a millisecond (same data center) to hundreds (another continent). When you report latency, say which one you measured.

## Step 5: Put the two modes side by side

```python run
_, batch_rows, batch_seconds = score_file("data/scheduled_orders.csv")
online_rows_per_s = 1000 / latencies_ms.mean()          # one client, one request at a time

print(f"{'mode':8} {'rows/s':>12}  {'time for 50,000 orders':>24}")
print(f"{'batch':8} {batch_rows / batch_seconds:12,.0f}  {batch_seconds:21.1f} s")
print(f"{'online':8} {online_rows_per_s:12,.0f}  {50_000 / online_rows_per_s:21.1f} s")
```

The online path could go faster with more workers and parallel clients, but each request still pays the full fixed overhead. The batch path pays it once per 10,000-row chunk. Use batch for what can be scored ahead of time, and keep the API for what can't.

## Step 6: Schedule the batch job with GitHub Actions

Save this as `.github/workflows/nightly-batch.yml`. It runs every night at 07:30 UTC (cron times are always UTC unless you set a time zone), and `workflow_dispatch` adds a **Run workflow** button on the repository's **Actions** tab so you can test it without waiting until tonight.

```yaml title=".github/workflows/nightly-batch.yml"
name: nightly-batch-scoring

on:
  schedule:
    - cron: "30 7 * * *"      # minute hour day-of-month month day-of-week, in UTC
  workflow_dispatch:

jobs:
  score:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements.txt
      - run: python make_scheduled_orders.py
      - run: python score_batch.py
      - uses: actions/upload-artifact@v7
        with:
          name: late-risk-predictions
          path: predictions/
          retention-days: 7
```

The steps mirror what you ran by hand: get the code, install the same Python and the same pinned libraries, make the input, score it, and keep the output as a downloadable artifact on the run's summary page. In a real system the last step would write to a database or a storage bucket instead, using a secret stored in the repository's **Settings › Secrets and variables › Actions**.

:::warning
**Scheduled workflows run late sometimes, and stop silently in quiet public repositories.** GitHub may delay `schedule` runs when Actions is busy, especially at the top of the hour, which is why this one runs at :30. Scheduled workflows also run only on the default branch, and in a public repository they're disabled after 60 days without activity. If the 7 a.m. deadline is real, have the job record when it finished and alert when it hasn't.
:::

## Step 7: Deploy the online API to Render's free tier

Render sets a `PORT` environment variable (10000 by default) and expects your server to listen on it, on `0.0.0.0`. Change the last line of the Module 2 Dockerfile so the port comes from the environment, with 8000 as the fallback for local runs:

```dockerfile
CMD ["sh", "-c", "exec uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]
```

The exec form `["sh", "-c", ...]` is needed because only a shell expands `${PORT:-8000}`. The word `exec` then replaces the shell with uvicorn, so the stop signal from the platform reaches uvicorn directly and it shuts down cleanly. Build and run locally once to check nothing broke (`docker build -t late-delivery:1.0.0 .` and `docker run --rm -p 8000:8000 late-delivery:1.0.0`), then push to GitHub with `models/` committed.

Then, in the Render Dashboard:

1. Click **New › Web Service** and connect your GitHub account, then choose the `late-delivery` repository.
2. Set **Language** to **Docker**. Render finds the `Dockerfile` in the repository root.
3. Where the form asks for a plan (Render calls it the instance type or compute plan), choose **Free**.
4. Under **Advanced**, set the health check path to `/health`.
5. Click **Create Web Service** and watch the build log. When it finishes, the service has a public URL ending in `onrender.com`.

Measure the cold start and the warm latency separately with curl's timing output (`-w` prints the status code and total time):

```bash
curl -s -o /dev/null -w "%{http_code} in %{time_total}s\n" https://YOUR-SERVICE.onrender.com/health
curl -s -o /dev/null -w "%{http_code} in %{time_total}s\n" https://YOUR-SERVICE.onrender.com/health
```

```text
200 in 48.913s
200 in 0.187s
```

Those two lines are an example of the pattern you'll see after the service has been idle for 15 minutes: the first request waits for the container to start, and the next one is fast. The warm number includes the round trip over the internet, so it's far above the in-process latency from Step 4.

:::quiz
Q: Why does `score_batch.py` write to `*.tmp` and rename the file at the end?
- [ ] Renaming is faster than writing
  Speed isn't the point; the rename happens once, at the end.
- [x] So a crash or a reader in the middle never sees a half-written file
  A rename on the same disk swaps the old file for the new one in a single step. Until it happens, readers see the complete previous file.
- [ ] pandas can only append to files ending in `.tmp`
  pandas appends to any open file handle; the extension doesn't matter.

Q: An analyst finds an odd risk score in the predictions file a week from now. Which columns let them trace it?
- [ ] `order_id` alone
  It says which order, but not which model scored it or when.
- [x] `model_version` and `scored_at`
  Together they say exactly which artifact produced the number and how stale its inputs (like the rain forecast) might have been.
- [ ] `late`
  That's the decision, not where it came from.

Q: The Render service's first request after lunch took 49 seconds, and the next took 0.19 seconds. Which number belongs in your write-up?
- [ ] Only the warm number, since cold starts are rare
  They happen after every 15 idle minutes on the free tier, so a low-traffic service hits them constantly.
- [ ] Only the cold number, since it's the worst case
  It's real, but reporting only it hides how the service behaves once it's running.
- [x] Both, each labelled
  Cold and warm latency describe different user experiences, and the free tier's spin-down makes the cold one common.
:::

:::takeaways
- A batch job should chunk its input, check columns, stamp each row with model version and time, and replace its output atomically.
- Benchmark the API end to end with warm-up requests, and report p50, p95, and p99.
- Batch beats online on throughput by orders of magnitude because it pays the fixed overhead once per chunk.
- A GitHub Actions `schedule` with `workflow_dispatch` runs the batch job for free; expect occasional delays.
- On Render, listen on `0.0.0.0:$PORT`, use a `/health` check, and measure cold and warm latency separately.
:::
