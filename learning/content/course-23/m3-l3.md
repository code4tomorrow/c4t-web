## Warm-up: name the mode

For each workload, pick batch, online, streaming, or edge, and say which requirement decided it.

1. A streaming service recommends tomorrow's homepage rows for each of 40 million users.
2. A card payment must be approved or declined within 300 ms while the customer waits.
3. A factory camera checks every part on a conveyor belt; the factory's internet link drops several times a day.
4. Each driver's GPS ping (one every 5 seconds) should update that order's arrival estimate on the customer's screen.
5. A school district predicts next semester's enrolment per school, once a term.
6. A note-taking app suggests tags while you type, and must work on a plane.

:::solution
1. **Batch.** Every input (each user's history up to tonight) is known in advance, and nobody waits on the answer. Scoring 40 million users online would cost far more for the same result.
2. **Online.** The input (this transaction) didn't exist until now, and someone is waiting with a hard deadline.
3. **Edge.** It must keep working without the network, and sending video for every part off-site would be slow and expensive.
4. **Streaming.** Predictions are triggered by a continuous flow of events, not by anyone asking.
5. **Batch.** Once a term, inputs known ahead of time: the simplest possible case.
6. **Edge.** "Works on a plane" means the model must run on the device.
:::

## Setup

Run this once. It trains the course model and defines the order generator the exercises use.

```python run
import json
import math
import time
from datetime import datetime, timedelta, timezone
from pathlib import Path

import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

FEATURES = ["distance_km", "items", "hour", "raining"]

def make_orders(n, seed):
    rng = np.random.default_rng(seed)
    frame = pd.DataFrame({
        "order_id": [f"ord-{seed}-{i:06d}" for i in range(n)],
        "distance_km": rng.gamma(2.0, 2.0, n).round(2),
        "items": rng.integers(1, 9, n),
        "hour": rng.integers(10, 23, n),
        "raining": (rng.random(n) < 0.25).astype(int),
    })
    rush = frame["hour"].between(17, 19)
    logit = -4.0 + 0.45 * frame["distance_km"] + 0.15 * frame["items"] + 1.2 * frame["raining"] + 0.9 * rush
    frame["late"] = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return frame

history = make_orders(2000, seed=23)
model = Pipeline([
    ("prep", ColumnTransformer([
        ("scale", StandardScaler(), ["distance_km", "items"]),
        ("hour", OneHotEncoder(handle_unknown="ignore"), ["hour"]),
    ], remainder="passthrough")),
    ("clf", LogisticRegression(max_iter=1000)),
]).fit(history[FEATURES], history["late"])
print("model ready")
```

### Exercise 1: Does the service meet its objective?

The team's objective is **p95 ≤ 50 ms and p99 ≤ 150 ms**. Here are 1,000 measured request latencies. Compute the mean, p50, p95, and p99, and decide whether the objective is met. Then explain why the mean alone would have misled you.

```python run
rng = np.random.default_rng(3)
latencies = np.concatenate([rng.lognormal(np.log(20), 0.3, 980), rng.uniform(150, 400, 20)])
rng.shuffle(latencies)
print(f"{len(latencies)} latencies loaded")
```

```text
mean 26.2 ms | p50 20.4 | p95 34.6 | p99 253.4
p95 <= 50:  pass
p99 <= 150: FAIL
```

:::hint
`np.percentile(values, [50, 95, 99])` returns all three at once. Check each half of the objective separately.
:::

:::solution
```python run
p50, p95, p99 = np.percentile(latencies, [50, 95, 99])
print(f"mean {latencies.mean():.1f} ms | p50 {p50:.1f} | p95 {p95:.1f} | p99 {p99:.1f}")
print(f"p95 <= 50:  {'pass' if p95 <= 50 else 'FAIL'}")
print(f"p99 <= 150: {'pass' if p99 <= 150 else 'FAIL'}")
```

Two percent of requests take 150 to 400 ms. That's enough to blow the p99 completely, but it adds only about 5 ms to the mean, which still looks healthy at 26 ms. The slow 2% are usually a specific cause worth hunting: a cold cache, a garbage-collection pause, or one slow dependency.
:::

### Exercise 2: How many instances?

Peak traffic is 120 requests per second, the mean time per request is 50 ms, and each instance can work on 4 requests at once. The team keeps instances at or below 60% busy. How many instances are needed at peak? Marketing plans a promotion that could triple traffic for an hour: how many then?

```text
peak:         6.0 in flight -> 3 instances
promotion:   18.0 in flight -> 8 instances
```

:::hint
Little's law uses the *mean* time in the system: L = λ × W. Then divide by the usable concurrency per instance (4 × 0.6) and round **up**, because you can't run 2.5 instances.
:::

:::solution
```python run
def instances_for(rate_per_s, mean_seconds, concurrency=4, utilization=0.6):
    in_flight = rate_per_s * mean_seconds
    return in_flight, math.ceil(in_flight / (concurrency * utilization))

for label, rate in [("peak", 120), ("promotion", 360)]:
    in_flight, n = instances_for(rate, 0.050)
    print(f"{label + ':':12} {in_flight:4.1f} in flight -> {n} instances")
```

Two cautions. Little's law describes averages, so bursts within a second need the headroom you built in with the 60% target. And if latency rises under load (it usually does, as queues form), W grows too, so size from latency measured *at* the target load, not at idle.
:::

### Exercise 3: Pick a micro-batch size

Some online services collect requests for a few milliseconds and score them together (micro-batching). Measure how long `predict_proba` takes for batches of 1, 4, 16, 64, 256, and 1,024 rows. Print the total time and the cost per row for each. Then set a latency budget of **twice the single-row time** (a request may wait at most about one extra request's worth of time for its batch) and choose the largest batch that fits.

```text
batch    1:   4.10 ms total,  4100.0 µs/row
batch    4:   4.05 ms total,  1012.5 µs/row
...
batch 1024:   4.90 ms total,     4.8 µs/row
budget (2 x one row): 8.20 ms
largest batch within budget: 1024
```

Your timings will differ; the pattern of nearly flat total time with falling cost per row is what to look for.

:::hint
Time each size several times (say 20) and take the median, so one slow run doesn't decide the answer. Use `make_orders(1024, seed=1)[FEATURES]` and slice it with `.iloc[:size]`.
:::

:::solution
```python run
pool = make_orders(1024, seed=1)[FEATURES]
results = {}
for size in [1, 4, 16, 64, 256, 1024]:
    batch = pool.iloc[:size]
    runs = []
    for _ in range(20):
        start = time.perf_counter()
        model.predict_proba(batch)
        runs.append((time.perf_counter() - start) * 1000)
    results[size] = float(np.median(runs))
    print(f"batch {size:4}: {results[size]:6.2f} ms total, {results[size] * 1000 / size:7.1f} µs/row")

budget_ms = 2 * results[1]
within = [size for size, ms in results.items() if ms <= budget_ms]
print(f"budget (2 x one row): {budget_ms:.2f} ms")
print("largest batch within budget:", max(within))
```

The total time grows far more slowly than the batch size, so the cost per row falls by hundreds of times between 1 row and 1,024. That's the fixed overhead again. (On a busy machine the timings jump around; the falling cost per row shows through anyway.) Micro-batching spends a little latency, the wait to fill the batch, to buy a lot of throughput. If your budget were tighter than a single row's time, no batch size would help, and you'd need a faster model or faster hardware.
:::

### Exercise 4: Make the batch job resumable

A nightly job scoring 60,000 orders in 6 chunks crashes on chunk 3. Rerunning from scratch wastes the work already done, and appending to a half-written file creates duplicates. Write `score_in_parts(frame, out_dir, chunk_rows, fail_at=None)` that writes each chunk to its own file (`part-00000.csv`, `part-00001.csv`, ...), **skips parts that already exist**, and raises when it reaches the chunk number `fail_at`. Run it once with `fail_at=3`, then again without it, and finally combine the parts.

```text
run 1: wrote part 0
run 1: wrote part 1
run 1: wrote part 2
run 1 crashed: simulated crash on part 3
run 2: skipped part 0 (already done)
...
run 2: wrote part 5
combined: 60,000 rows, 60,000 unique order IDs
```

:::hint
Write each part to a temporary name and rename it only when complete, so a crash mid-part never leaves a file that looks finished. The existence check then means "this part is done".
:::

:::solution
```python run
def score_in_parts(frame, out_dir, chunk_rows, fail_at=None, run="run"):
    out_dir = Path(out_dir)
    out_dir.mkdir(exist_ok=True)
    for part, start in enumerate(range(0, len(frame), chunk_rows)):
        final = out_dir / f"part-{part:05d}.csv"
        if final.exists():
            print(f"{run}: skipped part {part} (already done)")
            continue
        if part == fail_at:
            raise RuntimeError(f"simulated crash on part {part}")
        chunk = frame.iloc[start:start + chunk_rows]
        scored = pd.DataFrame({"order_id": chunk["order_id"],
                               "late_probability": model.predict_proba(chunk[FEATURES])[:, 1].round(4)})
        temporary = final.with_name(final.name + ".tmp")
        scored.to_csv(temporary, index=False)
        temporary.replace(final)
        print(f"{run}: wrote part {part}")

tonight = make_orders(60_000, seed=8)
try:
    score_in_parts(tonight, "parts", 10_000, fail_at=3, run="run 1")
except RuntimeError as error:
    print("run 1 crashed:", error)
score_in_parts(tonight, "parts", 10_000, run="run 2")

combined = pd.concat(pd.read_csv(path) for path in sorted(Path("parts").glob("part-*.csv")))
print(f"combined: {len(combined):,} rows, {combined['order_id'].nunique():,} unique order IDs")
```

The second run does only the remaining half. This works because chunk boundaries are deterministic (same input, same `chunk_rows`, same parts) and each part is all-or-nothing. If the input could change between runs, you'd also record a hash of it and start over when it differs, which is Module 4's topic.
:::

### Exercise 5: Where do always-on and pay-per-request break even?

Use these **made-up** prices: an always-on instance costs $0.05 per hour (730 hours a month); a scale-to-zero platform charges $2.00 per million requests and nothing while idle. At how many requests per month do they cost the same? What's that as an average rate per second? Print the monthly cost of each option at 1, 10, and 50 million requests.

```text
break-even: 18,250,000 requests/month (about 7.0 requests/s on average)
   1,000,000 requests: always-on $ 36.50 | per-request $  2.00
  10,000,000 requests: always-on $ 36.50 | per-request $ 20.00
  50,000,000 requests: always-on $ 36.50 | per-request $100.00
```

:::hint
The always-on cost doesn't depend on traffic. Set the two monthly costs equal and solve for the number of requests. A 30-day month has 30 × 24 × 3600 seconds.
:::

:::solution
```python run
always_on = 0.05 * 730
per_request = 2.00 / 1_000_000
break_even = always_on / per_request
print(f"break-even: {break_even:,.0f} requests/month (about {break_even / (30 * 24 * 3600):.1f} requests/s on average)")
for monthly in [1_000_000, 10_000_000, 50_000_000]:
    print(f"{monthly:12,} requests: always-on ${always_on:6.2f} | per-request ${monthly * per_request:6.2f}")
```

Below about 7 requests per second on average, scale-to-zero is cheaper with these prices; above it, always-on wins. Cost isn't the whole answer, though: scale-to-zero buys its savings with cold starts, so a low-traffic service with a strict p99 might pay for always-on (or a minimum of one warm instance) anyway.
:::

### Exercise 6: Serve batch scores when fresh, online when not

Combine the two modes. Write `get_risk(order, batch_table, now)` that returns the stored batch score if one exists for the order, is less than 12 hours old, and was computed with the same `raining` value the order has now. Otherwise it scores the order online. Return the probability and which path answered.

```text
fresh, same weather   -> batch   0.1844
rain started since    -> online  0.1563
scored 20 hours ago   -> online  0.0754
not in the batch      -> online  0.0603
```

:::hint
Store `raining` and `scored_at` in each batch row, so you can compare them at lookup time. A `dict` keyed by `order_id` is a fine stand-in for a database table.
:::

:::solution
```python run
now = datetime(2026, 11, 17, 18, 0, tzinfo=timezone.utc)
scheduled = make_orders(3, seed=7)
probabilities = model.predict_proba(scheduled[FEATURES])[:, 1]
batch_table = {
    row.order_id: {"late_probability": round(float(p), 4), "raining": int(row.raining),
                   "scored_at": now - timedelta(hours=hours_old)}
    for row, p, hours_old in zip(scheduled.itertuples(), probabilities, [4, 4, 20])
}

def get_risk(order, batch_table, now, max_age=timedelta(hours=12)):
    stored = batch_table.get(order["order_id"])
    if stored and now - stored["scored_at"] < max_age and stored["raining"] == order["raining"]:
        return "batch", stored["late_probability"]
    row = pd.DataFrame([{name: order[name] for name in FEATURES}])
    return "online", round(float(model.predict_proba(row)[0, 1]), 4)

first, second, third = scheduled.to_dict("records")
cases = {
    "fresh, same weather": first,
    "rain started since":  {**second, "raining": 1 - second["raining"]},
    "scored 20 hours ago": third,
    "not in the batch":    {"order_id": "ord-new", "distance_km": 2.0, "items": 2, "hour": 12, "raining": 0},
}
for label, order in cases.items():
    path, probability = get_risk(order, batch_table, now)
    print(f"{label:21} -> {path:7} {probability}")
```

What matters is which path answers each case. This hybrid gets batch's low cost for the common case and online's freshness for the rest. The key design choice is the **staleness rule**: here, age plus the one input known to change (weather). Pick rules from inputs that actually move, and record which path answered each request so you can see how often the fallback fires.
:::

### Challenge: Turn the decision flowchart into tested code

Write `choose_mode(workload)` for a dictionary with three keys: `inputs_known_in_advance`, `must_work_offline`, and `trigger` (`"request"` or `"event"`). It should return `"batch"`, `"edge"`, `"online"`, or `"streaming"` following the flowchart from the Notes lesson. Then write unit tests for at least four workloads from the warm-up and run them so the results print.

```text
test_card_payment_is_online ... ok
test_factory_camera_is_edge ... ok
test_gps_pings_are_streaming ... ok
test_homepage_rows_are_batch ... ok
...
OK
```

:::hint
Check the conditions in the same order as the flowchart; the order matters when more than one is true. `unittest.TextTestRunner(stream=sys.stdout, verbosity=2)` prints each test's name and result.
:::

:::solution
```python run
import sys
import unittest

def choose_mode(workload):
    if workload["inputs_known_in_advance"]:
        return "batch"
    if workload["must_work_offline"]:
        return "edge"
    return "online" if workload["trigger"] == "request" else "streaming"

class ChooseModeTests(unittest.TestCase):
    def test_homepage_rows_are_batch(self):
        self.assertEqual(choose_mode({"inputs_known_in_advance": True, "must_work_offline": False, "trigger": "request"}), "batch")

    def test_card_payment_is_online(self):
        self.assertEqual(choose_mode({"inputs_known_in_advance": False, "must_work_offline": False, "trigger": "request"}), "online")

    def test_factory_camera_is_edge(self):
        self.assertEqual(choose_mode({"inputs_known_in_advance": False, "must_work_offline": True, "trigger": "event"}), "edge")

    def test_gps_pings_are_streaming(self):
        self.assertEqual(choose_mode({"inputs_known_in_advance": False, "must_work_offline": False, "trigger": "event"}), "streaming")

    def test_known_inputs_beat_offline_requirement(self):
        # Enrolment forecasts could run offline too, but batch is the simpler answer.
        self.assertEqual(choose_mode({"inputs_known_in_advance": True, "must_work_offline": True, "trigger": "event"}), "batch")

suite = unittest.defaultTestLoader.loadTestsFromTestCase(ChooseModeTests)
unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)
```

The last test pins down a decision the flowchart makes implicitly: when inputs are known in advance, batch wins even if offline operation is also possible. Writing that as a test means nobody can reorder the `if` statements later without noticing.
:::
