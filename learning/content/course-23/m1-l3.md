A first push to GitHub that takes twenty minutes is a classic. The culprit is almost always `.venv`: thousands of files of other people's libraries, compiled for one operating system, useless to anyone who clones the repository. GitHub also blocks any single file over 100 MB, so a large model file can make the push fail outright. Both problems are prevented by one small file, written before the first commit.

## The layout every module adds to

Each module fills in part of this tree. You don't need all of it today, but creating it now means later lessons can say "put this in `app/`" without explanation.

```text
late-delivery/
├── app/               the FastAPI service (Module 2)
│   └── main.py
├── data/              generated training data (rebuilt by make_data.py)
├── models/            the trained model and its metadata (Module 2)
├── registry/          version records for every model (Module 4)
├── tests/             pytest tests for the service
├── .github/workflows/ CI/CD pipelines (Module 5)
├── make_data.py       creates data/orders.csv
├── train.py           trains and saves the model
├── Dockerfile         builds the service image (Module 2)
├── .dockerignore
├── .gitignore
├── requirements.txt
└── requirements-dev.txt
```

The rule behind it: code that *serves* predictions lives in `app/`, code that *produces* the model lives at the top level, and outputs (`data/`, `models/`, `registry/`) live in their own folders so they're easy to ignore, copy into an image, or hash.

This script creates the folders and starter files. It never overwrites a file that already exists, so it's safe to run again. Save it as `scaffold.py` in the project folder and run `python scaffold.py`.

```python run title="scaffold.py"
"""Create the late-delivery project skeleton. Safe to re-run."""
from pathlib import Path

FOLDERS = ["app", "data", "models", "registry", "tests", ".github/workflows"]

GITIGNORE = """\
# Python environments and caches
.venv/
__pycache__/
*.pyc
.pytest_cache/

# Secrets and local settings: never commit these
.env

# Experiment tracking files (Module 4)
mlruns/
mlflow.db

# Generated data: rebuild it with python make_data.py
data/*.csv
"""

FILES = {
    ".gitignore": GITIGNORE,
    "app/__init__.py": "",
    "README.md": "# late-delivery\n\nPredicts whether a food delivery will arrive late.\n",
}

for folder in FOLDERS:
    path = Path(folder)
    existed = path.exists()
    path.mkdir(parents=True, exist_ok=True)
    print(f"{'kept   ' if existed else 'created'} {folder}/")

for name, text in FILES.items():
    path = Path(name)
    if path.exists():
        print(f"kept    {name} (already exists)")
    else:
        path.write_text(text)
        print(f"created {name}")
```

`exist_ok=True` makes `mkdir` quietly succeed if the folder is already there, and the `if path.exists()` check protects files you've edited. Scripts that are safe to run twice are called *idempotent*, and you'll want that property in every setup and deployment script in this course: a pipeline that fails halfway should be safe to simply run again.

## What goes in Git

The `.gitignore` above encodes three decisions:

- **Environments and caches stay out.** `.venv` can be rebuilt from `requirements.txt` in a minute, and it only works on the machine that made it.
- **Secrets stay out, always.** API keys go in a `.env` file or the hosting platform's secret settings. A key pushed to a public repository should be treated as leaked even if you delete it a minute later, because the old commit still contains it.
- **Generated data stays out.** `make_data.py` uses a fixed random seed, so it rebuilds the same `data/orders.csv` every time.

The model file is a judgment call. This course's model is a few kilobytes, so committing `models/` is fine for now and lets a hosting service build your image straight from the repository. Once artifacts reach megabytes, they belong in a registry with a recorded hash, which is exactly what Module 4 builds.

## A commit rhythm that keeps history useful

Commit whenever one thing works: the scaffold, then the training script, then the API. Each commit is a point you can return to. Run `git status` before every commit; it's the cheapest bug check there is.

```bash
git init                 # skip this in a Codespace or a cloned repo
git status
git add .
git commit -m "Scaffold project layout and .gitignore"
```

```text
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	README.md
	app/
	requirements-dev.txt
	requirements.txt
	scaffold.py
```

Read that list before running `git add .`. If `.venv/` appears in it, your `.gitignore` isn't working (check that it's in the project root and spelled with the leading dot). Empty folders such as `data/` don't appear at all, because Git tracks files, not folders. Write commit messages that finish the sentence "This commit will…": "Add /health endpoint", not "stuff" or "fix".

## Keep Docker from eating your disk

Every image you build stays on disk until you remove it, and Module 2 builds a lot of them. These commands show what's there and clean it up.

```bash
docker ps              # running containers
docker ps -a           # all containers, including stopped ones
docker stop <id>       # stop a running container (the first 3-4 characters of the ID are enough)
docker images          # images on this machine
docker system df       # disk used by images, containers, and the build cache
docker container prune # remove all stopped containers
docker image prune     # remove dangling images (old untagged builds)
```

Both `prune` commands ask for confirmation first. Neither touches running containers or tagged images you're still using.

## Debug by asking "where did it fail?"

Most errors in this course come from one of three places, and each has its own first move.

```mermaid caption="The first thing to check depends on where the failure appeared"
flowchart TD
    A[Something failed] --> B{Where did it show up?}
    B -->|Python traceback| C[Read the last line first]
    B -->|HTTP status code| D{Which code?}
    B -->|A docker command| E["docker ps -a, then docker logs <id>"]
    D -->|422| F[Read detail: which field failed validation]
    D -->|500| G[Read the traceback in the server terminal]
    D -->|No response| H[Is a server listening on that port?]
```

**A Python traceback is read from the bottom.** The last line names the exception and the message; the lines above it show the chain of calls that led there, most recent last. Here's one you'll see if you start the API before training a model:

```python run raises
import joblib

model = joblib.load("models/model.joblib")
```

The last line says everything: the file `models/model.joblib` doesn't exist *relative to where you ran the command*. Either the model hasn't been trained yet, or you ran the program from the wrong folder. Run `python train.py` from the project root, then try again.

These are the messages you're most likely to meet, with their usual causes:

| What you see | What it usually means | Fix |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'fastapi'` | The venv isn't active | Activate it; check for `(.venv)` in the prompt |
| `[Errno 48] Address already in use` (macOS), `[Errno 98]` (Linux), `[WinError 10048]` (Windows) | Another server already holds port 8000 | Stop it with Ctrl+C in its terminal, or start with `--port 8001` |
| Status `422` from the API | The request body failed validation | Read `detail` in the response: it names the field and the rule |
| `curl: (7) Failed to connect to localhost port 8000` | Nothing is listening there | Start the server, or publish the container's port with `-p 8000:8000` |
| `Bind for 0.0.0.0:8000 failed: port is already allocated` | An older container still holds the port | `docker ps`, then `docker stop` it |

:::warning
A server running in the background is the most common invisible cause of "it's still showing the old version". If your change doesn't appear, check `docker ps` and your other terminal windows for a server you started earlier.
:::

## Asking for help so people can answer

When you're stuck for more than 20 minutes, ask, and include enough for someone to reproduce the problem without your computer:

```text
What I ran:      uvicorn app.main:app --reload   (from late-delivery/)
What I expected: the server to start
What happened:   (paste the full traceback, not a screenshot)
Versions:        output of python check_setup.py
What I tried:    reinstalled requirements; same error
```

Writing this down solves a surprising share of problems before you send it.

:::quiz
Q: `git status` lists `.venv/` under "Untracked files". What should you do before `git add .`?
- [ ] Nothing; GitHub ignores virtual environments automatically
  GitHub stores whatever you push. It has no idea which folders are environments.
- [x] Fix `.gitignore` (it must be in the project root, named exactly `.gitignore`) until `.venv/` disappears from the list
  Untracked files that match an ignore pattern aren't listed, so `.venv/` showing up means the pattern isn't being applied.
- [ ] Delete `.venv` and commit without one
  You need the venv to work; it just shouldn't be committed.

Q: Your API returns status 500 for every prediction. Where is the most useful information?
- [ ] In the 500 response body
  The server deliberately returns only "Internal Server Error", so attackers learn nothing about your code. That also means it tells you nothing.
- [x] In the terminal (or `docker logs`) where the server is running
  The full traceback is written to the server's log. The last line names the real exception.
- [ ] In the browser's address bar
  The URL shows what you asked for, not why the server failed.
:::

:::takeaways
- Serving code goes in `app/`, model-making code at the top level, and outputs in their own folders.
- Ignore `.venv`, caches, secrets, and data you can regenerate; commit small model files for now.
- Run `git status` before every commit, and commit each time one thing works.
- Read tracebacks from the bottom, read `detail` on a 422, and read the server's log on a 500.
:::
