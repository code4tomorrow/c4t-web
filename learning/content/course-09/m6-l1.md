Load this counter, press A five times quickly, and watch the number.

```makecode
let presses = 0
basic.forever(function () {
    if (input.buttonIsPressed(Button.A)) {
        presses += 1
    }
    basic.showNumber(presses)
    basic.pause(1000)
})
```

You pressed five times. The board probably shows 1, maybe 2. Nothing is broken in the hardware. The program is only *looking* at the button for an instant in every pass of the loop, and the rest of each pass is spent scrolling a number and pausing. A quick tap that starts and ends during the pause never happens, as far as this code knows.

## Polling: checking over and over

Code that keeps asking "is it happening yet?" is **polling**. It's like checking your phone every hour for a message: fine for a letter that sits there until you look, useless for a doorbell that rings for half a second.

Polling works when two things are true: you check often, and the thing you're checking lasts longer than the gap between checks. A tap on a button lasts roughly a tenth of a second. The loop above checks about once every second and a bit. The numbers don't line up, so presses fall through the gaps.

```mermaid caption="Polling only sees a press that happens while it is looking"
sequenceDiagram
    participant You
    participant Code as forever loop
    You->>Code: tap A (during pause)
    Note over Code: pausing, never sees it
    Code->>Code: check button: not pressed
    You->>Code: tap A (during scroll)
    Note over Code: scrolling, never sees it
    Code->>Code: check button: not pressed
```

## Events: let the micro:bit tell you

The fix is to stop asking and let the board tell you. An **event handler** is a block of code you hand to the micro:bit in advance: "when A is pressed, run this." Here is the same counter, written with events:

```makecode
let presses = 0
input.onButtonPressed(Button.A, function () {
    presses += 1
})
basic.forever(function () {
    basic.showNumber(presses)
})
```

Five quick presses now give 5. The display may lag while a number scrolls, but the count is right, and the next pass of the loop catches up.

What changed? Behind the scenes MakeCode runs a small scheduler. According to MakeCode's own explanation of the micro:bit as a reactive system, it checks the buttons and other inputs every 6 milliseconds, far faster than any tap, and lines up your handler to run for each press it finds. You still have polling, but it's fast polling done by the system, so your code doesn't have to.

## Short handlers, one loop that draws

The scheduler can only run one piece of your code at a time. Handlers and the `forever` loop take turns, and they hand over control whenever they pause or finish (a `forever` loop also pauses briefly at the end of each pass). That has two practical consequences:

- **Keep handlers short.** A handler that scrolls a long message makes the device feel laggy while it runs. Change a variable and get out.
- **Draw in one place.** If two handlers both write to the LEDs, their images can overwrite each other halfway through. Let handlers update variables and let one `forever` loop decide what the screen shows.

The event version of the counter already follows both rules: the handler adds one, the loop draws.

## States: what is the device doing right now?

A kitchen timer has a problem a counter doesn't. Pressing B should *start* the timer when it's idle, *pause* it while it's running, and *resume* it when paused. The same event needs a different reaction depending on what the device is currently doing.

That "currently doing" is called the **state**. List every state the device can be in, then list which events move it from one state to another. Those moves are **transitions**. A state diagram puts both on one picture:

```mermaid caption="States of a kitchen timer and the events that move between them"
stateDiagram-v2
    [*] --> Idle
    Idle --> Running: B pressed
    Running --> Paused: B pressed
    Paused --> Running: B pressed
    Running --> Ringing: time is up
    Ringing --> Idle: A pressed
```

Each box is a state; each arrow is labelled with the event that causes it. An event with no arrow out of the current state does nothing. Pressing A while running, for example, has no arrow, so it's ignored.

In code, the state is one variable, and each handler checks it before acting:

```makecode
let state = "IDLE"
input.onButtonPressed(Button.B, function () {
    if (state == "IDLE") {
        state = "RUNNING"
    } else if (state == "RUNNING") {
        state = "PAUSED"
    } else if (state == "PAUSED") {
        state = "RUNNING"
    }
})
input.onButtonPressed(Button.A, function () {
    if (state == "RINGING") {
        state = "IDLE"
    }
})
```

Here's the same machine as a short Python model, fed a list of events instead of real buttons. Step through it and watch `state` change only when the event matches an arrow in the diagram.

:::trace Feed events to the timer's state machine
```python
state = "IDLE"
events = ["A", "B", "B", "A", "B", "timeup", "A"]
for event in events:
    if state == "IDLE" and event == "B":
        state = "RUNNING"
    elif state == "RUNNING" and event == "B":
        state = "PAUSED"
    elif state == "PAUSED" and event == "B":
        state = "RUNNING"
    elif state == "RUNNING" and event == "timeup":
        state = "RINGING"
    elif state == "RINGING" and event == "A":
        state = "IDLE"
    print(event, "->", state)
```
:::

The first `A` arrives while the timer is idle, so the state stays `IDLE`. The second `A` arrives while paused and is ignored too. Only events that match an arrow do anything.

## Measuring time without freezing

The timer still needs to know when time is up. The tempting way is `basic.pause(60000)`. But a paused loop can't update the display, can't notice the B button changed the state to paused, and can't stop early. It's the polling problem again, in a new costume.

Instead, write down *when* something started and keep comparing with the clock. `control.millis()` gives the milliseconds since the board started:

```makecode
let start = control.millis()
input.onButtonPressed(Button.A, function () {
    start = control.millis()
})
basic.forever(function () {
    let elapsed = control.millis() - start
    if (elapsed >= 10000) {
        basic.showIcon(IconNames.Yes)
    } else {
        led.plotBarGraph(elapsed, 10000)
    }
})
```

The bar graph fills over ten seconds and then shows a tick. Press A at any moment and it starts again at once, because nothing is ever stuck in a pause. "Remember the start, compare with now" is the pattern behind every timer, alarm, and timeout you'll write.

## Mistakes that break state machines

:::warning
**`if` where you meant `else if`.** This looks like a pause button:

```makecode
input.onButtonPressed(Button.B, function () {
    if (state == "RUNNING") {
        state = "PAUSED"
    }
    if (state == "PAUSED") {
        state = "RUNNING"
    }
})
```

Press B while running: the first `if` sets `PAUSED`, then the second `if` sees `PAUSED` and sets it straight back. The timer never pauses. Fix: chain the checks with `else if`, so one press makes at most one transition.
:::

:::warning
**A typo in a state name.** `if (state == "RUNING")` is never true and MakeCode won't warn you, because any text is a valid string. Fix: copy and paste state names, or in JavaScript use numbered states with named variables such as `let RUNNING = 1`.
:::

:::quiz
Q: The polling counter at the top of this lesson shows 2 after five fast presses. Why?
- [ ] The micro:bit can only count two presses per second
  The hardware can register far more than that; the code just isn't looking.
- [x] The loop checks the button for an instant each pass and spends the rest pausing and scrolling, so most taps happen while it isn't looking
  Polling catches a tap only if the tap overlaps the moment of the check.
- [ ] `presses += 1` only adds one per second
  It adds one every time it runs; the problem is how rarely it runs.

Q: The timer is in the `Running` state. According to the state diagram, what does pressing A do?
- [ ] Goes back to `Idle`
  That arrow starts from `Ringing`, not `Running`.
- [x] Nothing, because no arrow labelled with A leaves `Running`
  Events without a matching transition from the current state are ignored.
- [ ] Moves to `Paused`
  Pausing is triggered by B, not A.

Q: You want an LED to turn on ten minutes after a button press, while the board keeps responding to other buttons. Which approach fits?
- [ ] `basic.pause(600000)` in the button handler, then turn the LED on
  While that handler waits, you can't cancel it or show progress, and it ties up its slot for ten minutes.
- [x] Store `control.millis()` when the button is pressed, and in a `forever` loop check whether 600000 ms have passed
  Comparing with a saved start time never blocks, so everything else keeps working.
- [ ] Poll the button faster
  The problem is waiting, not detecting the press.
:::

:::takeaways
- Polling asks "is it happening?" over and over and misses anything shorter than the gap between checks.
- Event handlers run when something happens; MakeCode's scheduler watches the inputs for you every few milliseconds.
- Handlers change variables; one `forever` loop draws. Keep handlers short.
- A state machine lists what the device can be doing and which events move it on. In code it's a `state` variable checked with `if`/`else if`.
- For timing, save a start time with `control.millis()` and compare, rather than pausing.
:::
