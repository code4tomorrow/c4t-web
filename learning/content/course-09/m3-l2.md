---
title: Build a fair reaction-time game
summary: Build a pocket game that waits a random time, flashes the screen, and measures how fast you press A in milliseconds, with false-start detection and a best-time record.
---

:::objectives
- Organize a game as a set of states held in one variable.
- Use **pick random** to make a wait that players can't predict.
- Measure a time interval with **running time (ms)**.
- Spot and fix two fairness bugs: guessing the timing, and a "go" signal that isn't ready when it appears.
- Keep a best score that survives between rounds.
:::

Ask a friend to press a button "as soon as the screen lights up". If the screen always lights two seconds after they start, they'll stop watching and start counting, and their times will be impossibly fast. A reaction game is only fair if the player can't predict the signal, can't win by pressing early, and is timed from the exact moment the signal appears. Each of those becomes a step in this build.

## What we're building

The game moves between a few **states**. Each state has its own picture, so the player always knows what's going on, and each press of A means something different depending on the state.

```mermaid caption="The game's states. Every arrow is caused by a press of A or by the random wait ending."
stateDiagram-v2
    [*] --> idle
    idle --> waiting: press A
    waiting --> go: random wait ends
    waiting --> idle: press A too soon, show X
    go --> idle: press A, show the time
```

| State | What the screen shows | What pressing A does |
| --- | --- | --- |
| idle | an arrow pointing at A | starts a round |
| waiting | one dot in the center | false start: shows an X |
| go | every LED lit | stops the clock and shows your time |

```text
A typical round on the simulator:
  arrow ... press A ... dot (2.7 s) ... FULL SCREEN ... press A ... 348 ... arrow
```

## Step 1: A state variable and the idle screen

Start a project called `c4t-m3-reaction`.

```makecode
let state = "idle"
basic.showArrow(ArrowNames.West)
```

Make a variable `state` in **Variables** and set it to the text `"idle"` in **on start** (use the text block from **Text** under **Advanced**, or just type the word in JavaScript). Then add **show arrow** pointing West, at the A button. Using words like `"idle"` instead of numbers costs nothing and makes every `if` you write later read like a sentence.

## Step 2: Start a round, then wait a random time

```makecode
let state = "idle"
basic.showArrow(ArrowNames.West)
input.onButtonPressed(Button.A, function () {
    if (state == "idle") {
        state = "waiting"
        basic.clearScreen()
        led.plot(2, 2)
    }
})
basic.forever(function () {
    if (state == "waiting") {
        basic.pause(randint(1000, 4000))
        if (state == "waiting") {
            state = "go"
            basic.showLeds(`
                # # # # #
                # # # # #
                # # # # #
                # # # # #
                # # # # #
                `)
        }
    }
})
```

The button handler only starts the round: it sets the state, clears the screen, and plots a calm center dot. The waiting happens in **forever**, which checks the state, pauses for a random 1 to 4 seconds, and lights the whole screen.

Why put the pause in forever instead of in the A handler? Because of how presses queue. If the A handler were busy pausing, a second press of A during the wait would sit in line until the pause ended, then run instantly, and the player would get a "reaction time" of almost zero. Keeping the handler short means every press is handled the moment it happens.

The second `if (state == "waiting")` after the pause isn't a typo. A lot can happen in four seconds. In Step 4, an early press will change the state, and this check makes sure the screen doesn't light up for a round that's already over.

## Step 3: Measure the reaction

**Input › running time (ms)** tells you how many milliseconds have passed since the board started. Read it once when the signal appears and once when the player presses; the difference is the reaction time.

```makecode
let goTime = 0
basic.forever(function () {
    if (state == "waiting") {
        basic.pause(randint(1000, 4000))
        if (state == "waiting") {
            goTime = input.runningTime()
            state = "go"
            basic.showLeds(`
                # # # # #
                # # # # #
                # # # # #
                # # # # #
                # # # # #
                `)
        }
    }
})
```

And in the A handler, a new branch:

```makecode
if (state == "go") {
    let reaction = input.runningTime() - goTime
    state = "idle"
    basic.showNumber(reaction)
    basic.showArrow(ArrowNames.West)
}
```

The **order** of the three lines before show leds is the second fairness fix. **show leds** lights the screen and then holds for 400 ms before the next block runs. If `state = "go"` came *after* show leds, a quick player who pressed within those 400 ms would still find the state at `"waiting"` and be told they'd jumped the gun. Recording the time and switching the state first means the game is ready the instant the screen lights.

## Step 4: Catch false starts

```makecode
if (state == "waiting") {
    state = "idle"
    basic.showIcon(IconNames.No)
    basic.showArrow(ArrowNames.West)
}
```

A press during the wait ends the round with an X. Setting the state back to `"idle"` is what the second check in forever was for: when its pause ends, it sees the round is over and doesn't light the screen.

## Step 5: Remember the best time

```makecode
let best = 0
input.onButtonPressed(Button.B, function () {
    if (state == "idle") {
        basic.showNumber(best)
        basic.showArrow(ArrowNames.West)
    }
})
```

In the go branch, after working out `reaction`, add:

```makecode
if (best == 0 || reaction < best) {
    best = reaction
}
```

`best` starts at 0, which here means "no rounds yet". The `||` (an **or** block from **Logic**) lets the first real time become the best automatically. B only works when the game is idle, so it can't clutter the screen during a round.

## The finished program

```makecode title="c4t-m3-reaction"
let reaction = 0
let state = "idle"
let goTime = 0
let best = 0
basic.showArrow(ArrowNames.West)
input.onButtonPressed(Button.A, function () {
    if (state == "idle") {
        state = "waiting"
        basic.clearScreen()
        led.plot(2, 2)
    } else if (state == "waiting") {
        state = "idle"
        basic.showIcon(IconNames.No)
        basic.showArrow(ArrowNames.West)
    } else if (state == "go") {
        reaction = input.runningTime() - goTime
        state = "idle"
        if (best == 0 || reaction < best) {
            best = reaction
        }
        basic.showNumber(reaction)
        basic.showArrow(ArrowNames.West)
    }
})
input.onButtonPressed(Button.B, function () {
    if (state == "idle") {
        basic.showNumber(best)
        basic.showArrow(ArrowNames.West)
    }
})
basic.forever(function () {
    if (state == "waiting") {
        basic.pause(randint(1000, 4000))
        if (state == "waiting") {
            goTime = input.runningTime()
            state = "go"
            basic.showLeds(`
                # # # # #
                # # # # #
                # # # # #
                # # # # #
                # # # # #
                `)
        }
    }
})
```

In blocks, every variable belongs to the whole program, so the finished version declares `reaction` at the top with the others. It's still only set in the go branch.

## Step 6: Test that it's fair

| Test | Expected result |
| --- | --- |
| Play five normal rounds | Each wait feels different; times are a few hundred ms |
| Press A during the dot | X, then the arrow; the screen never lights for that round |
| Press A the moment the screen lights | A time is shown, never an X |
| Press B before playing | 0 (no best yet) |
| Play three rounds, then press B | The smallest of your three times |

In the simulator your times include the mouse and the browser, so expect a few hundred milliseconds. On a real board with your thumb resting on the button, times usually come out a little faster and more consistent.

:::tip
**on button pressed** runs when you *release* the button, so every time includes how long your thumb stayed down. Tap, don't hold, and everyone's times stay comparable. For timing from the moment the button goes down, the **on event** block in **Control** (under **Advanced**) can listen for `MICROBIT_BUTTON_EVT_DOWN` from button A instead.
:::

:::quiz
Q: Why does the game wait a *random* 1 to 4 seconds instead of exactly 2 seconds?
- [ ] Random waits use less battery
  The wait length makes no difference to power use.
- [x] A fixed wait lets players count and press on time without reacting
  If the signal is predictable, the game measures counting, not reaction.
- [ ] MakeCode can't pause for exactly 2 seconds
  `basic.pause(2000)` would work fine; it would just be unfair.

Q: What goes wrong if `state = "go"` is moved to *after* the show leds block?
- [ ] Nothing; the screen and the state change together
  Show leds holds for 400 ms before the next line runs.
- [x] A player who presses within 400 ms of the flash gets an X
  During the hold the state is still `"waiting"`, so a correct fast press counts as a false start.
- [ ] The reaction time is always 0
  The time is still measured from `goTime`; the problem is the wrong state.

Q: Why is the random pause in **forever** instead of inside the A handler?
- [ ] Handlers can't use pick random
  They can; pick random works anywhere.
- [x] A press during a busy A handler waits in line, so an early press would be handled late and look like a reaction
  Keeping the A handler short means each press is judged at the moment it happens.
- [ ] Forever loops pause more accurately
  The pause is equally accurate in either place.
:::

:::takeaways
- Name your game's states and keep the current one in a single variable; each input then does one clear thing per state.
- An unpredictable wait, a false-start rule, and an instant "go" state are what make a reaction game fair.
- Time an interval by subtracting two readings of **running time (ms)**.
- Put long waits in forever and keep button handlers short, so presses are judged when they happen.
- A best score can start at a value that means "none yet", like 0.
:::

## Ideas to extend it

- **Two players.** A and B both wait for the flash; the first press wins, and a press during the wait loses. (This is the practice lesson's challenge.)
- **Sound the start.** Play a short tone at the flash and see whether times get faster with sound than with light.
- **Average of five.** Add up five rounds and show the average, which is a fairer score than a single lucky round.
- **Hunt a sneaky bug.** False-start and then press A again straight away: the forever loop is still in its *old* pause, so the new round's wait is whatever was left of it. Fix it with a round counter that forever checks after its pause.
