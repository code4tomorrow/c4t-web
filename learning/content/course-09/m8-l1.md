A teacher asks the class to vote by raising hands. Twenty-eight hands go up, she counts twenty-seven, and nobody can check. Now picture the same vote on micro:bits: everyone presses A or B, every vote is counted exactly once, a voter whose vote didn't get through sees a cross and can try again, and every poll is saved to a CSV for later. That's a connected invention: several devices, each with a job, talking by radio to do something one device couldn't.

Your capstone is a network like that. You can build it entirely in the MakeCode simulator, which shows two boards whenever you use radio, or on real micro:bits if you have them. This lesson is all planning. It feels slower than coding, but networks are where unplanned projects fall apart: two boards that disagree about what a message means fail silently, and you lose an afternoon finding out why.

## The brief

Your network must do all of these. The right-hand column is how you'll prove it when you present.

| Requirement | How you'll show it |
| --- | --- |
| At least two roles that talk by radio on a group you chose | Demo with two simulated (or real) boards |
| Inputs handled with events, not polling | Point to the event blocks in your code |
| At least one state machine with three or more states | A state diagram that matches the code |
| Records data (data logger or serial) and you analyse it | A CSV plus a chart or summary in Python or a spreadsheet |
| Visible feedback when a message is lost or a device goes quiet | Demo the failure on purpose |
| Tested, with safety notes and design documentation | Your test table and README |

## Six project ideas, from gentle to ambitious

Pick one, or invent your own that meets the brief. The stars are a rough guide to how much new thinking each needs beyond this course.

| Idea | Difficulty | Roles | Data it records |
| --- | --- | --- | --- |
| Hot potato tournament | ★ | player, scoreboard | who exploded, after how long |
| Classroom voting system | ★★ | teacher, voter | votes per poll |
| Relay race timer | ★★ | start gate, finish gate | lap times |
| Climate network with alerts | ★★ | station, hub | readings per station |
| Quiet-zone sound monitor | ★★★ | zone sensor, desk display | sound levels per zone |
| Plant care network | ★★★ | plant sensor, gardener's badge | soil moisture over days |

**Hot potato tournament.** Extend the challenge from the event-driven practice: a third role, the scoreboard, hears every `BOOM` and keeps score across rounds, logging each round's fuse length and loser.

**Classroom voting system.** A teacher board opens and closes polls; voter boards send A or B. The hard parts are counting each voter once and telling a voter when their vote didn't arrive. The next lesson builds this one step by step as the worked example, so it's the safest choice if you want a guide.

**Relay race timer.** The start gate sends `GO` when a button is pressed; the finish gate measures time from hearing `GO` until a runner breaks the "beam" (a button, or a tilt of the board). Each board's clock starts at a different moment, so the finish gate must time everything with its own `control.millis()`.

**Climate network with alerts.** Build on the sensor network from Module 7: per-station "last heard" times, a temperature threshold, and an alert the hub sends back to the station that's too warm.

**Quiet-zone sound monitor.** Stations in different parts of a library send `input.soundLevel()` (micro:bit V2, 0 to 255). The display board shows which zone is loudest. You'll need averages, because a single cough shouldn't trigger the "too loud" warning.

**Plant care network.** Needs real hardware: two nails in a plant pot, wired with crocodile clips to pin 1 and 3V, read with `pins.analogReadPin(AnalogPin.P1)` (wetter soil conducts better and reads higher). The sensor board reports moisture every ten minutes; the gardener's badge lights up when a plant is dry. Add `pins.digitalWritePin(DigitalPin.P0, 1)` on the badge to switch on an external LED. In the simulator you can still build it, because the simulated board lets you change the pin's reading.

## Design the messages first

Before any code, write down every message your devices will send. This table is your **protocol**: the agreement every board has to follow. Here is the voting system's:

| Message | Kind | From → to | Meaning |
| --- | --- | --- | --- |
| `OPEN` | string | teacher → voters | a poll has started; voting allowed |
| `CLOSED` | string | teacher → voters | the poll has ended |
| `A` = voter id | value | voter → teacher | a vote for A from this voter |
| `B` = voter id | value | voter → teacher | a vote for B from this voter |
| `ack` = voter id | value | teacher → voters | receipt: this voter's vote was counted |

Check your table against what you already know about micro:bit radio. Every label fits in 8 characters, every string in 19. Each kind of message has one receive block per board, so the table tells you what goes in each `if`. And every message that matters has a reply, because the sender can't otherwise know it arrived.

## Draw the states for each role

Each role gets its own state diagram. The voter's is the interesting one:

```mermaid caption="Voter states, including what happens when a receipt never comes"
stateDiagram-v2
    [*] --> Waiting
    Waiting --> Voting: hears OPEN
    Voting --> Sent: presses A or B
    Sent --> Done: ack with my id
    Sent --> Sent: no ack after 1 s, resend
    Sent --> Failed: 3 tries, no ack
    Failed --> Sent: presses A or B again
    Done --> Waiting: hears CLOSED
    Voting --> Waiting: hears CLOSED
```

Drawing it exposed questions you'd otherwise meet as bugs: What if a voter presses B after voting A? (No arrow from `Done`, so nothing happens.) What if `CLOSED` arrives while a vote is still being resent? (Add an arrow from `Sent` to `Waiting`.) Answer each question on the diagram, then code what you drew.

## Plan the data

Decide what question your data will answer, then what to record. For the voting system: "How do class opinions change over a week of polls, and how many voters take part?" That needs one row per poll with the poll number, the two totals, and the number of voters. Write the column names down now and use exactly those names in `setColumnTitles`.

## Safety plan

Even a simulator-only project gets a safety section, because someone may build your design on real boards. Include the points that apply:

- Handle micro:bits by their edges, and power them only from the USB cable or the battery pack meant for them.
- Use batteries of the same type and age in a pack, and never let crocodile clips or wires touch both ends of a battery.
- Keep boards and battery packs away from water and plant pots' drip trays; a sensor in soil is fine, a board in a puddle isn't.
- Never connect a micro:bit to mains electricity or to anything plugged into the wall other than a computer's USB port.
- For devices worn or carried while moving (relay race), secure cables so nobody trips.
- Radio messages are readable by anyone on the same group, so don't send names or anything private.

## Milestones

Big projects fail in the middle, when nothing works and you can't tell which part is broken. Milestones stop that: each one adds a small piece, and you test it before moving on. The next lesson follows these five for the voting system.

| Milestone | Done when |
| --- | --- |
| M1: Roles and screens | Each board can take its role and shows a distinct screen |
| M2: First message | One message from the protocol travels and changes the other board's state |
| M3: Core job | The main feature works end to end in the simulator |
| M4: Failure feedback | Lost messages and silent devices produce a visible warning |
| M5: Data out | Data is logged or streamed, exported as CSV, and charted |

:::quiz
Q: In the voting protocol, why does each vote carry the voter's id as its value?
- [ ] The radio needs an id to know where to deliver the message
  Radio messages have no address; every board in the group hears them.
- [x] So the teacher can count each voter only once, and send an `ack` that only that voter will accept
  If a receipt is lost and the voter resends, the id lets the teacher spot the repeat instead of counting it twice.
- [ ] Because a value message must contain a number between 1 and 30000
  A value can be any number; the id is a design choice, not a rule of the radio.

Q: While drawing the voter's state diagram you realise there's no arrow out of `Sent` for "hears CLOSED". What should you do?
- [x] Decide what should happen (probably go to `Waiting`) and add the arrow before writing code
  Every missing arrow is a question about behaviour. Answering it on paper is much cheaper than finding it as a bug.
- [ ] Nothing, because voters will never be in `Sent` when the poll closes
  A slow voter can be mid-retry when the teacher closes the poll.
- [ ] Remove the `Sent` state
  Without `Sent`, the voter has no way to know whether to resend.
:::

:::takeaways
- The capstone needs roles, radio, events, states, data, failure feedback, testing, safety, and documentation.
- Write the protocol table first: every message, its kind, who sends it, and what it means.
- Draw a state diagram per role; every missing arrow is a question to answer before coding.
- Plan the data from the question backwards, and fix column names now.
- Split the build into milestones you can test one at a time.
:::
