The quickest step counter is one block: **on shake → change steps by 1**. Put it in your pocket, walk 20 steps, and it might say 9. Shake it in your hand for two seconds and it says 4. The shake gesture detects *shaking*, a fast back-and-forth swing, and walking isn't that. A real step counter has to look at the force itself and decide, reading by reading, what counts as one step.

That's the problem this build solves. You'll finish with a wearable gadget that has two modes: a step counter, and a compass arrow that always points north, the start of a navigation aid.

## Step 1: Look at the signal first

Before writing any counting code, look at what a step looks like to the accelerometer. Start a project called `c4t-m4-step-counter`:

```makecode
basic.forever(function () {
    serial.writeValue("strength", input.acceleration(Dimension.Strength))
})
```

**strength** combines all three axes into one size of force, so it doesn't matter which way the board is facing in your pocket. Download this, hold the board, walk across the room, and click **Show data** under the simulator (or **Show data Device** when the board is connected by WebUSB). Each step makes a spike. Here's a model of 10 steps, shaped like a real recording:

```python run alt="Model acceleration strength over 6 seconds of walking. The line sits near 1000 mg with jitter, and has 10 sharp spikes reaching between about 1450 and 1750 mg, each followed by a small dip. Dashed lines mark 1400 mg and 1100 mg." caption="Ten model steps. Each spike rises above 1400; between steps the signal drops back below 1100."
import numpy as np
import matplotlib.pyplot as plt

rng = np.random.default_rng(11)
t = np.arange(0, 6, 0.02)  # one reading every 20 ms
strength = np.full_like(t, 1000.0)
for s in 0.45 + 0.55 * np.arange(10):
    strength += rng.uniform(480, 720) * np.exp(-((t - s) / 0.06) ** 2)
    strength -= 200 * np.exp(-((t - s - 0.16) / 0.06) ** 2)
strength += rng.normal(0, 60, t.size)

plt.figure(figsize=(7, 3.2))
plt.plot(t, strength, color="#00798c", linewidth=1.2)
plt.axhline(1400, color="#d1495b", linestyle="--", label="1400: count a step")
plt.axhline(1100, color="#e09f3e", linestyle="--", label="1100: get ready again")
plt.xlabel("time (s)")
plt.ylabel("strength (mg)")
plt.legend(loc="upper right", fontsize=8)
plt.grid(alpha=0.3)
plt.tight_layout()
```

Two things stand out. Each step is a spike well above the resting value of about 1000. And the line is fuzzy: even the tops of the spikes wobble up and down.

## Step 2: The obvious rule, and why it fails

The obvious rule is "add a step whenever strength is over 1400". Before putting it on the board, test it on the data, along with a slightly smarter version that only counts the moment the line *crosses* 1400 going up:

```python run
over = int(np.sum(strength > 1400))

crossings = 0
was_above = False
for reading in strength:
    if reading > 1400 and not was_above:
        crossings += 1
    was_above = reading > 1400

print("real steps:                 10")
print("readings above 1400:       ", over)
print("upward crossings of 1400:  ", crossings)
```

Counting readings is hopeless: each spike stays above the line for several readings in a row, so one step counts three or four times. Counting crossings is much closer, but still wrong. When the top of a spike wobbles across 1400 (above, a hair below, above again), that one step crosses twice.

## Step 3: Count once, then wait to be ready again

The fix uses two lines instead of one, and a variable called `armed` that remembers whether the counter is ready for the next step:

- When `armed` is true and strength goes **above 1400**, count a step and set `armed` to false.
- Only when strength falls **below 1100** does `armed` become true again.

Wobbles at the top of a spike can cross 1400 as often as they like; the counter isn't armed, so they're ignored. The gap between 1100 and 1400 is the same margin the night light used in the notes. Step through the rule on twelve readings:

:::trace Watch `armed` block the wobbles at the top of each spike
```python
readings = [1020, 1350, 1520, 1380, 1530, 1200, 1050, 1010, 1460, 1610, 1390, 1030]
steps = 0
armed = True
for r in readings:
    if armed and r > 1400:
        steps = steps + 1
        armed = False
    elif r < 1100:
        armed = True
print("steps:", steps)
```
:::

The first spike dips to 1380 and climbs to 1530 again, which a single-line counter would count twice. Here it counts once, because `armed` stays false until the reading of 1050. Now test the rule on the full walk:

```python run
steps = 0
armed = True
for reading in strength:
    if armed and reading > 1400:
        steps += 1
        armed = False
    elif reading < 1100:
        armed = True
print("steps counted with the reset margin:", steps)
```

Ten for ten. Testing on data first meant you found and fixed the double-counting without walking a single step.

## Step 4: Put the sensing loop on the board

```makecode
let steps = 0
let armed = true
basic.forever(function () {
    let strength = input.acceleration(Dimension.Strength)
    if (armed && strength > 1400) {
        steps += 1
        armed = false
    } else if (strength < 1100) {
        armed = true
    }
})
```

This is the same rule, line for line. The **and** block comes from **Logic**, and `true` and `false` are the **true** and **false** blocks from **Logic** too. There's no pause: forever already rests 20 ms between passes, so it takes about 50 readings a second, the same rate as the data above. And there's no show block. That's deliberate.

## Step 5: A separate display loop

```makecode
let mode = "steps"
basic.forever(function () {
    if (mode == "steps") {
        basic.showNumber(steps)
    }
})
```

Add a **second** forever block for the display. Showing a two-digit count scrolls for over a second. If that scroll lived in the sensing loop, every step you took during it would be missed: the busy-loop problem from the buttons module, now with footsteps. With two loops, the sensing loop keeps reading while the display loop scrolls.

To test in the simulator, you need to push the strength above 1400. Over most of the simulator board it stays at 1023, however you tilt it. Move the pointer right into a **corner** of the board, where the simulated force rises well above 1400, then back to the middle. Each trip should add exactly one step. On a real board, walk 20 steps and compare. If it undercounts, try 1300; if it counts while you stand still, try 1500.

## Step 6: An arrow that always points north

**compass heading** tells you which way the board's top edge points. To point *at* north, turn that around. If the top edge faces east (90), north is 90 degrees to your left. In general, north is `(360 - heading) % 360` degrees clockwise from the top edge.

The micro:bit has eight arrows, numbered 0 to 7 clockwise from straight up: North, North East, East, South East, South, South West, West, North West. Divide the angle by 45 and round to get the nearest arrow:

| Top edge faces | heading | 360 - heading | arrow number | arrow shown |
| --- | --- | --- | --- | --- |
| north | 0 | 0 | 0 | up |
| east | 90 | 270 | 6 | left |
| south | 180 | 180 | 4 | down |
| north-west | 315 | 45 | 1 | up and right |

Add the compass branch to the display loop:

```makecode
basic.forever(function () {
    if (mode == "steps") {
        basic.showNumber(steps)
    } else {
        let toNorth = (360 - input.compassHeading()) % 360
        basic.showArrow(Math.round(toNorth / 45) % 8)
    }
})
```

The final `% 8` handles one edge case: an angle like 350 rounds to arrow 8, which doesn't exist, and `8 % 8` turns it back into 0, straight up. In the simulator, drag the compass needle around the logo and watch the arrow swing the opposite way, always toward north. On a real board, the first time compass mode runs, the screen asks you to **TILT TO FILL SCREEN**; finish the calibration before trusting the arrow.

## Step 7: Buttons to switch modes and reset

```makecode
input.onButtonPressed(Button.B, function () {
    if (mode == "steps") {
        mode = "compass"
    } else {
        mode = "steps"
    }
    led.stopAnimation()
})
input.onButtonPressed(Button.AB, function () {
    steps = 0
    led.stopAnimation()
})
```

Same pattern as the badge: handlers change a variable, **stop animation** makes the change show at once, and only the display loop draws.

## The finished program

```makecode title="c4t-m4-step-counter"
let steps = 0
let armed = true
let mode = "steps"
basic.forever(function () {
    let strength = input.acceleration(Dimension.Strength)
    if (armed && strength > 1400) {
        steps += 1
        armed = false
    } else if (strength < 1100) {
        armed = true
    }
})
basic.forever(function () {
    if (mode == "steps") {
        basic.showNumber(steps)
    } else {
        let toNorth = (360 - input.compassHeading()) % 360
        basic.showArrow(Math.round(toNorth / 45) % 8)
    }
})
input.onButtonPressed(Button.B, function () {
    if (mode == "steps") {
        mode = "compass"
    } else {
        mode = "steps"
    }
    led.stopAnimation()
})
input.onButtonPressed(Button.AB, function () {
    steps = 0
    led.stopAnimation()
})
```

Test it like the badge: in steps mode, three corner trips should give 3; B should switch to an arrow; dragging the needle should move the arrow; A+B should bring the count back to 0. For a walk, clip the battery pack and board together so the wires can't snag, and keep the board away from keys and coins in your pocket.

:::quiz
Q: Why are sensing and display in two separate forever loops?
- [ ] MakeCode only allows one show block per loop
  A loop can hold as many show blocks as you like.
- [x] So the display's scrolling never stops the readings, and no steps are missed
  While one loop scrolls a number, the other keeps reading about 50 times a second.
- [ ] Two loops make the board read the sensor twice as often
  The sensing loop reads at the same rate either way; the point is that nothing interrupts it.

Q: You remove the `else if (strength < 1100)` part and instead set `armed = true` whenever strength is below 1400. What happens?
- [ ] It counts exactly the same
  With one line, a wobble just below 1400 re-arms the counter mid-step.
- [x] It goes back to double-counting steps whose tops wobble across 1400
  That's the single-line crossing counter from Step 2, which counted 12 instead of 10.
- [ ] It never counts any steps
  It still counts; it just counts some steps twice.

Q: You face south, so the heading is 180. Which arrow does compass mode show?
- [ ] Up
  Up would mean north is straight ahead, but you're facing away from it.
- [x] Down
  `(360 - 180) % 360` is 180, arrow 4, which points down: north is behind you.
- [ ] Left
  Left is for facing east, when north is on your left.
:::

:::takeaways
- Plot a sensor's signal before writing code that interprets it.
- Two thresholds and an `armed` flag count each spike once, even when its top wobbles.
- Test a counting rule on recorded or modelled data before trusting it on the board.
- Put sensing and display in separate forever loops so slow drawing can't cause missed readings.
- To point at north, use `(360 - heading) % 360` and divide by 45 to pick one of the eight arrows.
:::

## Ideas to extend it
