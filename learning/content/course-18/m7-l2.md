A conservation group wants cameras on a forest trail to count deer, foxes, and a rare wildcat. The cameras run on two AA batteries, have a weak radio link to a base station, and someone can only reach them to change batteries a few times a year. The images will also include hikers, who never agreed to be photographed.

The camera uses the small image model you budgeted in module 5: about 300 ms per 96×96 image on a 64 MHz chip. It classifies each photo as **animal**, **person**, or **empty**. The question now is how to run it. Four designs are on the table:

| Design | When it takes a photo | What it sends |
| --- | --- | --- |
| **A. Timer** | Every 10 seconds, all day | A label for each animal photo |
| **B. Motion, labels** | When a motion (PIR) sensor triggers | A label and timestamp for each animal photo |
| **C. Motion, cloud** | When motion triggers | Every photo, classified at the base station |
| **D. Motion, summary** | When motion triggers | One message a day with counts per class |

You'll build a calculator that gives each design a battery life and a privacy profile, and finish with a recommendation.

## Step 1: Put every state into numbers

Each state has a current and a duration. These are planning figures, not measurements: the chip's sleep current is from the nRF52840 product brief, and the rest are typical values for parts of this kind. Replace them with readings from a USB power meter or a current profiler once you have hardware.

```python run
import numpy as np
import matplotlib.pyplot as plt

USABLE_MAH = 2500 * 0.8          # 2 x AA in series, keeping 20% in reserve
SLEEP_MA = {                     # always on, 24 hours a day
    "chip asleep (RTC running)": 0.003,
    "PIR motion sensor waiting": 0.050,
    "voltage regulator": 0.010,
}
STEPS = {                        # (current mA, seconds) each time it happens
    "capture photo": (25.0, 0.4),
    "run model": (5.0, 0.3),
    "send label": (30.0, 0.2),
    "send photo": (30.0, 4.0),
    "send daily summary": (30.0, 0.3),
}
ANIMAL_SHARE = 0.3               # of motion triggers, 30% are animals

def mah(step, times=1):
    ma, seconds = STEPS[step]
    return ma * seconds / 3600 * times      # mA x hours = mAh

sleep_per_day = sum(SLEEP_MA.values()) * 24
print(f"sleep alone: {sleep_per_day:.2f} mAh per day")
for step in STEPS:
    print(f"{step:20} {mah(step) * 1000:7.2f} µAh each")
```

Look at the sizes. One photo costs about 2.8 µAh, and one inference about 0.4 µAh. A day of sleeping costs about 1,500 µAh. Whether the camera's active work matters at all depends on how many times a day it happens.

## Step 2: Charge per day for each design

Write one function that returns a design's daily charge, split by category, for a given number of motion triggers per day.

```python run
def daily_mah(design, triggers):
    animals = triggers * ANIMAL_SHARE
    parts = {"sleep": sleep_per_day, "camera": 0.0, "model": 0.0, "radio": 0.0}
    if design == "A":                        # timer: 8,640 photos a day regardless of motion
        photos = 24 * 3600 / 10
        parts["camera"] = mah("capture photo", photos)
        parts["model"] = mah("run model", photos)
        parts["radio"] = mah("send label", animals)
    elif design == "B":
        parts["camera"] = mah("capture photo", triggers)
        parts["model"] = mah("run model", triggers)
        parts["radio"] = mah("send label", animals)
    elif design == "C":
        parts["camera"] = mah("capture photo", triggers)
        parts["radio"] = mah("send photo", triggers)
    elif design == "D":
        parts["camera"] = mah("capture photo", triggers)
        parts["model"] = mah("run model", triggers)
        parts["radio"] = mah("send daily summary")
    return parts

print(f"{'design':8} {'mAh/day':>8} {'battery life':>14}")
for d in "ABCD":
    total = sum(daily_mah(d, 50).values())
    print(f"{d:8} {total:8.2f} {USABLE_MAH / total:9.0f} days")
```

At 50 triggers a day, the timer design lasts a little over two months. The motion-triggered designs last years on paper, because the camera sleeps nearly all the time. Treat any figure past a couple of years with suspicion: alkaline cells slowly self-discharge and lose capacity in the cold, so real life will be shorter. The ranking is what's reliable.

## Step 3: How busy is the trail?

Fifty triggers is a guess. A trail in summer with wind in the bushes might fire the PIR 500 times a day. Sweep it:

```python run alt="Log-scale chart of battery life in days against motion triggers per day, from 5 to 1,000. Design A is flat at about 70 days. Designs B and D are nearly identical, starting near 1,300 days and falling to about 400 days at 1,000 triggers. Design C falls fastest, from about 1,100 days to under 100 days." caption="Battery life against trail activity for the four designs"
triggers = np.logspace(np.log10(5), 3, 40)
colors = {"A": "#d64545", "B": "#2a78d6", "C": "#7a5cd6", "D": "#1baf7a"}
names = {"A": "A. timer", "B": "B. motion, labels", "C": "C. motion, cloud", "D": "D. motion, summary"}

plt.figure(figsize=(7.5, 4))
for d in "ABCD":
    life = [USABLE_MAH / sum(daily_mah(d, t).values()) for t in triggers]
    plt.plot(triggers, life, color=colors[d], linewidth=2.2 if d != "B" else 3,
             linestyle="--" if d == "D" else "-", label=names[d])
plt.xscale("log"); plt.yscale("log")
plt.axhline(365, color="#999", linestyle=":")
plt.text(6, 390, "1 year", color="#666")
plt.xlabel("Motion triggers per day")
plt.ylabel("Battery life (days)")
plt.legend(frameon=False, loc="lower left")
plt.grid(alpha=0.25, which="both")
plt.tight_layout()

for t in [10, 100, 1000]:
    print(f"{t:5} triggers/day: " + "  ".join(f"{d} {USABLE_MAH / sum(daily_mah(d, t).values()):5.0f} d" for d in "ABCD"))
```

Three things stand out. Design A doesn't care about trail activity, because it photographs every 10 seconds anyway, and it's the worst by far. Design C falls fastest, because every trigger means 4 seconds of radio. And B and D sit almost on top of each other: sending a 0.2-second label for each animal costs very little compared with sleeping all day.

That last point matters. D doesn't win on battery. If you pick it, you pick it for another reason.

## Step 4: Where the charge goes

A bar per design, split by category, shows which state to attack first.

```python run alt="Horizontal bars showing each design's daily charge split into shares. Design A, 29 mAh per day, is 82% camera and 12% model. Design C, 3.3 mAh, is half radio and nearly half sleep. Designs B and D, about 1.7 mAh, are about 90% sleep." caption="Share of each design's daily charge at 50 triggers per day, with the total at the end of each bar"
parts_colors = {"sleep": "#9aa5b1", "camera": "#2a78d6", "model": "#7a5cd6", "radio": "#eb6834"}
fig, ax = plt.subplots(figsize=(7.5, 3))
for i, d in enumerate("ABCD"):
    parts = daily_mah(d, 50)
    total = sum(parts.values())
    left = 0
    for part, value in parts.items():
        ax.barh(names[d], value / total * 100, left=left, color=parts_colors[part], label=part if i == 0 else None)
        left += value / total * 100
    ax.text(101, i, f"{total:.1f} mAh/day", va="center", fontsize=9)
ax.set_xlim(0, 125)
ax.set_xlabel("Share of daily charge (%)")
ax.invert_yaxis()
ax.legend(frameon=False, ncol=4, loc="upper right", bbox_to_anchor=(1, 1.25))
plt.tight_layout()

for d in "ABCD":
    parts = daily_mah(d, 50)
    biggest = max(parts, key=parts.get)
    print(f"{names[d]:20} biggest cost: {biggest} ({parts[biggest] / sum(parts.values()):.0%})")
```

The biggest cost tells you what to optimize. For A, it's the camera: fix it by not taking photos nobody needs. For C, it's the radio. For B and D, it's sleep, and most of that is the PIR sensor's 50 µA. A lower-power PIR would extend B and D more than any change to the model. Speeding up inference would change nothing you could measure.

## Step 5: What each design sends, and what that reveals

Battery life can't separate B from D. Privacy can. Build the actual messages each design would send for one day of events, and measure them.

```python run
import json

rng = np.random.default_rng(4)
day_events = []                       # what the camera saw today
for _ in range(50):
    hour = rng.choice([5, 6, 7, 12, 14, 18, 19, 20])
    label = rng.choice(["animal", "person", "empty"], p=[0.3, 0.2, 0.5])
    species = rng.choice(["deer", "fox", "wildcat"], p=[0.6, 0.3, 0.1]) if label == "animal" else ""
    day_events.append({"time": f"2026-06-14T{hour:02d}:{rng.integers(60):02d}", "label": label, "species": species})

def messages(design):
    if design in ("A", "B"):
        return [json.dumps({"cam": 7, "t": e["time"], "species": e["species"]})
                for e in day_events if e["label"] == "animal"]
    if design == "C":
        return [f"<{4000}-byte photo taken {e['time']}>" for e in day_events]
    if design == "D":
        counts = {}
        for e in day_events:
            if e["label"] == "animal":
                counts[e["species"]] = counts.get(e["species"], 0) + 1
        return [json.dumps({"cam": 7, "day": "2026-06-14", "counts": counts})]

for d in "BCD":
    msgs = messages(d)
    size = sum(4000 if m.startswith("<") else len(m) for m in msgs)
    print(f"{names[d]}: {len(msgs)} message(s), {size:,} bytes")
    print("   e.g.", msgs[0])
```

Now read each one as an outsider would:

-   **C** sends every photo, including about ten a day of hikers' faces, to a base station and probably a cloud server. That's the largest privacy harm and the largest radio cost.
-   **B** sends no images, but every message carries a time and a species. A record that the wildcat passes camera 7 at dawn most days is exactly what a poacher would want.
-   **D** sends one line per day: counts per species. People are dropped on the device and never counted, and no time of day leaves the camera.

Notice that "no images leave the device" was true for B and still wasn't enough. The label and the timestamp were the sensitive part.

## The finished calculator

Here's the planning tool as one script. Change the numbers at the top as you measure your hardware, and add designs as you think of them.

```python run title="trail_camera_plan.py"
USABLE_MAH = 2500 * 0.8
SLEEP_MA = 0.003 + 0.050 + 0.010           # chip + PIR + regulator
STEPS = {"photo": (25.0, 0.4), "model": (5.0, 0.3), "label": (30.0, 0.2),
         "upload": (30.0, 4.0), "summary": (30.0, 0.3)}
ANIMAL_SHARE = 0.3

def mah(step, n=1):
    ma, s = STEPS[step]
    return ma * s / 3600 * n

DESIGNS = {     # (photos per day as a function of triggers, model runs, radio charge, what leaves)
    "A. timer":           (lambda t: 8640, lambda t: 8640, lambda t: mah("label", t * ANIMAL_SHARE), "species + time per animal"),
    "B. motion, labels":  (lambda t: t, lambda t: t, lambda t: mah("label", t * ANIMAL_SHARE), "species + time per animal"),
    "C. motion, cloud":   (lambda t: t, lambda t: 0, lambda t: mah("upload", t), "every photo, including people"),
    "D. motion, summary": (lambda t: t, lambda t: t, lambda t: mah("summary"), "daily counts per species"),
}

for triggers in [50, 500]:
    print(f"--- {triggers} motion triggers per day ---")
    for name, (photos, runs, radio, leaves) in DESIGNS.items():
        per_day = SLEEP_MA * 24 + mah("photo", photos(triggers)) + mah("model", runs(triggers)) + radio(triggers)
        print(f"{name:20} {USABLE_MAH / per_day:6.0f} days   sends: {leaves}")
```

At 500 triggers a day, D still lasts years on paper, C drops to a few months, and A never makes it past ten weeks. **D is the recommendation**: tied for the best battery life, and the only design whose output is safe to publish.

:::quiz
Q: Design B and design D last almost the same time. Why?
- [ ] Both send the same number of bytes
  B sends a message per animal and D one per day, so their byte counts differ a lot.
- [x] Sleep current dominates both, and a short label message costs little next to a day of sleeping
  About 1.5 mAh a day goes to sleep; 15 labels at about 1.7 µAh each add only about 2 percent.
- [ ] The model doesn't run in either design
  Both run the model on every trigger; it's just cheap at 0.4 µAh per run.

Q: You want B to last longer. Which change helps most?
- [ ] Halve the inference time
  The model uses about 1% of B's daily charge; halving it is invisible.
- [x] Replace the 50 µA PIR sensor with a 5 µA one
  The PIR is most of the sleep current, and sleep is most of B's budget.
- [ ] Send labels in batches of five
  Radio is a small slice of B's budget, so batching saves little energy (though it does help privacy).

Q: Design B sends no images. What is its main privacy risk?
- [x] Timestamps and species reveal when a rare animal reliably visits the camera
  The label plus time is what makes the data useful to someone with bad intentions.
- [ ] It might send photos of hikers
  B only sends labels; it never transmits images.
- [ ] Its battery could run out
  That's a reliability problem, not a privacy risk.
:::

:::takeaways
- Write each design as states with current and duration, then compute charge per day; that one function answers most power questions.
- Sweep the uncertain input (here, triggers per day) instead of trusting one guess.
- Optimize the biggest slice. For motion-triggered devices that's usually sleep current, not the model.
- Designs that tie on battery can differ sharply on privacy. Build the real messages and read them like an outsider.
- On-device inference makes it possible to drop sensitive classes, such as people, before anything is stored or sent.
:::
