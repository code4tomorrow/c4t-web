- Say what lives in flash and what lives in RAM while a model runs.
- Count a layer's parameters and turn them into bytes for float32 and int8.
- Find the peak activation memory of a chain of layers, the number that decides whether a model fits in RAM.
- Count multiply-accumulates (MACs) and turn them into a first latency estimate.
- Check that estimate against the deadline your sensor window sets.

Here is a layer with 320 parameters: a 3×3 convolution that turns a 96×96 grayscale image into 32 feature maps. Quantized to int8, its weights take well under a kilobyte. The Arduino Nano 33 BLE Sense has 1 MB of flash, so the weights fit more than two thousand times over.

The layer still can't run on that board. Its output is 96 × 96 × 32 = 294,912 numbers. At one byte each that's 288 KB, and the board's nRF52840 chip has 256 KB of RAM in total, for everything.

A model on a microcontroller can fail in three separate ways: too big for flash, too big for RAM, or too slow for its deadline. Each limit is counted differently, and a design that does well on one often does badly on another. You'll count all three by hand, then check the counts with PyTorch.

## Flash holds what the model knows; RAM holds what it's working on

A laptop and a microcontroller differ by a factor you can't picture until you write it down:

| | Typical laptop | nRF52840 (Nano 33 BLE Sense) |
| --- | --- | --- |
| Processor | about 3 GHz, 8 or more cores | 64 MHz Arm Cortex-M4 with a floating-point unit, 1 core |
| Long-term storage | 512 GB SSD | 1 MB flash |
| Working memory | 16 GB RAM | 256 KB RAM |

16 GB divided by 256 KB is 65,536. Your laptop has as much working memory as sixty-five thousand of these chips.

**Flash** keeps its contents with the power off and is slow to write, so firmware treats it as read-only while running. It holds the program, the Edge Impulse SDK, the signal-processing (DSP) code, and the model's weights, stored as constant arrays. **RAM** is fast to read and write and is wiped when power drops. It holds everything that changes: the sensor window being filled, the DSP features, each layer's outputs (called **activations**), the call stack, and buffers for Bluetooth and serial.

```mermaid caption="What sits in flash and what sits in RAM during one inference"

    end

```

TensorFlow Lite for Microcontrollers (now called LiteRT for Microcontrollers) asks you to reserve one block of RAM for the model's inputs, outputs, and activations, called the **tensor arena**, and model setup fails if the block is too small. Edge Impulse sizes that block for you, and it shows estimated RAM, flash, and inference time in the **On-device performance** panel after training, for the target board you chose on the Dashboard. Those estimates are good, but you'll design better models if you can predict them.

## Parameters: count them, then multiply by bytes

A parameter is one number the model learned. Count them layer by layer:

-   **Dense layer**: every output connects to every input, plus one bias per output: `n_in × n_out + n_out`.
-   **2-D convolution**: one k×k filter for each pair of input and output channels, plus one bias per output channel: `k × k × c_in × c_out + c_out`.

The image size is missing from the convolution formula. A filter slides across the image and reuses the same weights at every position, so a 96×96 input and a 960×960 input need the same weights.

```python run
import torch
from torch import nn

def dense_params(n_in, n_out):
    return n_in * n_out + n_out           # a weight per connection, a bias per output

def conv2d_params(k, c_in, c_out):
    return k * k * c_in * c_out + c_out   # a k x k filter per channel pair, a bias per output

layers = {
    "Dense 375 -> 20": (dense_params(375, 20), nn.Linear(375, 20)),
    "Conv2d 3x3, 1 -> 32": (conv2d_params(3, 1, 32), nn.Conv2d(1, 32, 3, padding=1)),
    "Conv2d 3x3, 32 -> 64": (conv2d_params(3, 32, 64), nn.Conv2d(32, 64, 3, padding=1)),
}

print(f"{'layer':22} {'by hand':>8} {'PyTorch':>8} {'int8':>9} {'float32':>9}")
for name, (by_hand, layer) in layers.items():
    by_torch = sum(p.numel() for p in layer.parameters())
    print(f"{name:22} {by_hand:8,} {by_torch:8,} {by_hand/1024:7.1f} KB {by_hand*4/1024:7.1f} KB")
```

The hand counts match PyTorch's `numel()` totals exactly. Now look at the first row. A dense layer fed a raw 2-second accelerometer window (125 samples × 3 axes = 375 values) has 23 times more parameters than the convolution that reads a whole image. Dense layers on wide inputs are where flash goes.

To turn parameters into bytes, multiply by 4 for float32 or by 1 for int8. That's the 4× saving from quantization you met in the last module. Int8 models usually keep their biases as 32-bit integers, which adds a little, so treat "1 byte per parameter" as a slight underestimate.

## Activations: the RAM that weight counts ignore

While a layer runs, it reads its whole input and writes its whole output, so both have to be in RAM at the same moment. Once the layer finishes, its input is no longer needed and that space can be reused by a later layer. A runtime that plans memory this way needs roughly the **largest input-plus-output pair** in the model, not the sum of every activation.

Step through the search for that pair. The sizes are each layer's output in KB, starting with the input image:

:::trace Find the largest pair of tensors alive at once
```python
sizes_kb = [9, 288, 72, 144, 36, 36]   # input, then each layer's output
peak = 0
for i in range(1, len(sizes_kb)):
    live = sizes_kb[i - 1] + sizes_kb[i]   # this layer's input and output
    if live > peak:
        peak = live
print("peak KB:", peak)
```
:::

`peak` jumps to 297, then to 360, and never moves again. The second layer is the problem: it reads the 288 KB feature map and writes a 72 KB one, and both exist at once.

Those numbers came from a real model. PyTorch can report every layer's input and output size with a **forward hook**, a function that runs each time a layer produces output. ReLU and Flatten are skipped because microcontroller runtimes apply ReLU in place and treat Flatten as a relabeling, with no new memory.

```python run alt="Bar chart of RAM needed at each layer of a small image model. The first max-pool layer needs 360 KB and the first convolution 297 KB, both above a dashed line at 256 KB. The second convolution needs 216 KB and later layers much less." caption="Input plus output at each layer, int8, against the nRF52840's 256 KB of RAM"
import matplotlib.pyplot as plt

image_model = nn.Sequential(
    nn.Conv2d(1, 32, 3, padding=1), nn.ReLU(),    # 96x96x1 in, 96x96x32 out
    nn.MaxPool2d(2),                               # 48x48x32
    nn.Conv2d(32, 64, 3, padding=1), nn.ReLU(),   # 48x48x64
    nn.MaxPool2d(2),                               # 24x24x64
    nn.Conv2d(64, 64, 3, padding=1), nn.ReLU(),   # 24x24x64
    nn.AdaptiveAvgPool2d(1), nn.Flatten(),         # 64 numbers
    nn.Linear(64, 2),                              # person / no person
)

def layer_sizes(model, input_shape):
    rows = []
    def record(layer, inputs, output):
        rows.append((type(layer).__name__, inputs[0].numel(), output.numel()))
    hooks = [m.register_forward_hook(record) for m in model
             if not isinstance(m, (nn.ReLU, nn.Flatten))]
    with torch.no_grad():
        model(torch.zeros(1, *input_shape))
    for h in hooks:
        h.remove()
    return rows

rows = layer_sizes(image_model, (1, 96, 96))
names = [f"{i+1}. {name}" for i, (name, _, _) in enumerate(rows)]
live_kb = [(n_in + n_out) / 1024 for _, n_in, n_out in rows]   # 1 byte each in int8

params = sum(p.numel() for p in image_model.parameters())
print(f"parameters: {params:,}  (about {params/1024:.0f} KB of flash in int8)")
print(f"peak activations: {max(live_kb):.0f} KB of RAM in int8")

plt.figure(figsize=(7.5, 3.8))
colors = ["#d64545" if kb > 256 else "#2a78d6" for kb in live_kb]
plt.barh(names[::-1], live_kb[::-1], color=colors[::-1])
plt.axvline(256, color="#333", linestyle="--", linewidth=1.2)
plt.text(258, 0.2, "256 KB: all of the chip's RAM", fontsize=9)
plt.xlabel("Input + output of the layer (KB, int8)")
plt.title("The weights take 55 KB of flash. The activations don't fit in RAM.")
plt.tight_layout()
```

Flash says yes (about 55 KB of 1 MB) and RAM says no (360 KB of 256 KB). This is the most common way a TinyML model fails, and it's invisible if you only look at model size.

The fix is to shrink the early feature maps, because they're the biggest. Giving the first convolution `stride=2` makes it step two pixels at a time, so it outputs 48×48 instead of 96×96. Then the first max-pool isn't needed:

```python run
smaller = nn.Sequential(
    nn.Conv2d(1, 32, 3, stride=2, padding=1), nn.ReLU(),   # 48x48x32 straight away
    nn.Conv2d(32, 64, 3, padding=1), nn.ReLU(),
    nn.MaxPool2d(2),
    nn.Conv2d(64, 64, 3, padding=1), nn.ReLU(),
    nn.AdaptiveAvgPool2d(1), nn.Flatten(),
    nn.Linear(64, 2),
)
rows = layer_sizes(smaller, (1, 96, 96))
peak_kb = max(n_in + n_out for _, n_in, n_out in rows) / 1024
print(f"parameters: {sum(p.numel() for p in smaller.parameters()):,}")
print(f"peak activations: {peak_kb:.0f} KB")
```

The parameter count is exactly the same, because stride doesn't change the filters. The peak drops to 216 KB, which fits on paper. On a real board it's still tight: the sensor buffer, the stack, and the Bluetooth stack all need RAM too, which is why the next lesson builds a full budget table.

## MACs: counting the work

Nearly all of a neural network's arithmetic is **multiply-accumulate**: multiply a weight by an input value and add the result to a running sum. Counting MACs is counting work.

-   **Dense**: each weight is used once, so `n_in × n_out` MACs.
-   **Convolution**: each weight is used once at every output position, so `h_out × w_out × k × k × c_in × c_out` MACs.

Here convolutions flip around. Few parameters, but every one is reused thousands of times. To turn MACs into time, you need a clock speed and a cycles-per-MAC figure. With optimized int8 kernels such as Arm's CMSIS-NN, a Cortex-M4 manages very roughly one MAC every one or two clock cycles. Treat that as a planning number to replace with a measurement later.

```python run
def count_macs(model, input_shape):
    macs = []
    def record(layer, inputs, output):
        if isinstance(layer, nn.Conv2d):
            k = layer.kernel_size[0] * layer.kernel_size[1]
            positions = output.shape[2] * output.shape[3]
            macs.append(positions * k * layer.in_channels * layer.out_channels)
        elif isinstance(layer, nn.Linear):
            macs.append(layer.in_features * layer.out_features)
    hooks = [m.register_forward_hook(record) for m in model]
    with torch.no_grad():
        model(torch.zeros(1, *input_shape))
    for h in hooks:
        h.remove()
    return macs

narrow = nn.Sequential(                                       # stride 2 AND half the channels
    nn.Conv2d(1, 16, 3, stride=2, padding=1), nn.ReLU(),
    nn.Conv2d(16, 32, 3, padding=1), nn.ReLU(),
    nn.MaxPool2d(2),
    nn.Conv2d(32, 32, 3, padding=1), nn.ReLU(),
    nn.AdaptiveAvgPool2d(1), nn.Flatten(),
    nn.Linear(32, 2),
)

CLOCK_HZ = 64_000_000
for name, model in [("original", image_model), ("stride-2 first layer", smaller), ("stride 2, half width", narrow)]:
    per_layer = count_macs(model, (1, 96, 96))
    total = sum(per_layer)
    fast = total * 1 / CLOCK_HZ * 1000
    slow = total * 2 / CLOCK_HZ * 1000
    print(f"{name:21} {total/1e6:5.1f} M MACs  ->  about {fast:4.0f} to {slow:4.0f} ms at 64 MHz")
    print(f"{'':21} per layer (M): {[round(m / 1e6, 1) for m in per_layer]}")
```

The original model needs about 66 million MACs, a second or two per image at 64 MHz. The stride-2 fix that rescued RAM barely changes that, and the per-layer list shows why: it only shrank the first layer's work, and most of the work is in the second convolution (32 channels in, 64 out, at 48×48). Memory and speed are separate problems with separate fixes.

Halving every layer's channels cuts the MACs about 4×, because a convolution's work grows with `c_in × c_out`. That version lands around 250 to 500 ms. It wouldn't keep up with live video, but a camera trap that checks one photo each time motion wakes it could live with half a second.

## The deadline comes from the sensor window

Every TinyML system has a clock it can't argue with: the sensor. If a gesture detector makes a new prediction every 250 ms, then the DSP and the model together must finish in under 250 ms, every time. If they take longer, new windows arrive before the old ones are done. The device either drops windows (and misses gestures) or falls further behind with each prediction.

```python run alt="Timeline of eight predictions for two models with a new window every 250 ms. The 40 ms model finishes each prediction long before the next window arrives. The 310 ms model starts each prediction later than the last, and its lag grows from 310 ms to 730 ms." caption="Windows arrive every 250 ms. Processing that takes longer than that falls further behind every time."
hop_ms = 250
plt.figure(figsize=(7.5, 2.8))
for row, (label, work_ms) in enumerate([("310 ms per prediction", 310), ("40 ms per prediction", 40)]):
    free_at = 0
    lags = []
    for k in range(8):
        arrives = k * hop_ms
        start = max(arrives, free_at)           # wait if still busy with the last window
        free_at = start + work_ms
        lags.append(free_at - arrives)
        plt.broken_barh([(start, work_ms)], (row - 0.35, 0.7),
                        color="#d64545" if work_ms > hop_ms else "#1baf7a", edgecolor="white")
    print(f"{label}: lag after each window (ms) = {lags}")
for k in range(9):
    plt.axvline(k * hop_ms, color="#999", linewidth=0.6, linestyle=":")
plt.yticks([0, 1], ["310 ms model", "40 ms model"])
plt.xlabel("Time (ms); dotted lines mark new windows")
plt.tight_layout()
```

The green model is idle most of the time, which you'll be glad of in the power module: idle time is time the chip can sleep. The red model's lag grows by 60 ms with every window, without limit. "Usually fast enough" doesn't count; the worst case has to fit.

:::warning
**Three counting mistakes that sink a TinyML design**

1.  **Counting weights and calling it "model size".** Flash is only one of three limits. A 55 KB model above needed 360 KB of RAM. Always compute peak activations too.
2.  **Mixing float32 and int8 numbers.** An Edge Impulse estimate for the int8 model and a PyTorch count of float32 bytes differ by 4×. Write the data type next to every number in your budget.
3.  **Timing on your laptop and assuming the board is similar.** A laptop core runs at roughly 50 times the clock rate and does more work per cycle. A model that takes 0.5 ms in Colab can take tens or hundreds of milliseconds on a Cortex-M4. Estimate from MACs, then measure on the device.
:::

:::quiz
Q: A 3×3 convolution with 16 input and 16 output channels runs on a 48×48 input. You switch to a 96×96 input. What happens?
- [ ] Parameters and activation memory both go up 4×
  The weights don't depend on image size, so the parameter count can't change.
- [x] Parameters stay the same; the output activation goes up 4×
  The same 3×3×16×16 filters slide over a larger image, and the output has four times as many positions.
- [ ] Nothing changes, because convolutions reuse weights
  The weights are reused, but every output position still needs its own slot in RAM.

Q: A model's int8 weights take 140 KB and its largest input-plus-output pair is 310 KB. Which limit does it break on an nRF52840 (1 MB flash, 256 KB RAM)?
- [ ] Flash
  140 KB of weights is well under 1 MB, even with room for the program.
- [x] RAM
  310 KB of activations alive at once is more than the chip's 256 KB, before the stack and buffers are counted.
- [ ] Neither; the total is 450 KB, which is under 1 MB
  Weights and activations live in different memories with different limits. Adding them together hides the RAM problem.

Q: A gesture model needs 12.8 million MACs per prediction. At 64 MHz and 1.5 cycles per MAC, can it make a new prediction every 250 ms?
- [ ] Yes, with about 200 ms to spare
  12.8 million × 1.5 cycles is 19.2 million cycles, and at 64 million cycles per second that's 300 ms, not 50.
- [x] No, it needs about 300 ms
  19.2 million cycles ÷ 64 million per second = 0.3 s, which is over the 250 ms hop, before any DSP time.
- [ ] You can't tell without knowing the parameter count
  The work per prediction comes from MACs; parameter count tells you about flash, not time.

Q: Which change cuts peak activation memory without changing the number of parameters?
- [ ] Removing the last dense layer
  That removes parameters, and the last layer's tiny output isn't where the peak is.
- [ ] Halving the number of filters in the last convolution
  That changes the parameter count, and late feature maps are already small.
- [x] Adding `stride=2` to the first convolution
  The filters are identical, but the first feature map shrinks to a quarter of its size, and that's where the peak was.
:::

:::takeaways
- Flash holds code and weights; RAM holds the sensor window, features, activations, stack, and buffers.
- Parameters: `n_in × n_out + n_out` for dense layers, `k × k × c_in × c_out + c_out` for convolutions. Multiply by 1 byte for int8 or 4 for float32.
- Peak RAM for a chain of layers is roughly the largest input-plus-output pair, and it's usually in the first layers of an image model.
- MACs measure work. Divide MACs × cycles-per-MAC by the clock rate to estimate latency, then confirm on the device.
- The sensor window's hop sets a hard deadline for DSP plus inference, and the worst case has to fit.
:::
