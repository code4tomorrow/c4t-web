:::objectives
- Create a Colab notebook that saves to your Google Drive, and connect the notebook to Drive so files you write survive a restart.
- Build a project folder where raw data, code, and results each have one obvious home.
- Record your Python and library versions in `environment.json` and pin them in `requirements.txt`.
- Detect, months later, whether your environment has drifted from the one that produced a result.
:::

In October you train a model on your science fair data and it scores 0.91. In January a judge asks you to rerun it with one extra feature. Before you change anything, you rerun the old version to have a starting point, and it scores 0.84.

Which number is real? You can only answer if you know four things about the October run: which data file it read, which code it ran, which library versions it used, and which random seed it started from. Most student projects can't answer any of the four, and the published literature isn't much better. This module sets up all four on the first day, so every result you produce in this course can be traced and rerun.

## What you need

- **A Google account.** A personal one is the reliable choice. Some school accounts block Colab or Drive access for apps, and you only find out when a cell fails.
- **A browser** on any computer. Chromebooks work fine.
- **No installs.** Colab runs Python on a Google virtual machine. It normally ships with NumPy, pandas, SciPy, statsmodels, scikit-learn, and matplotlib, which are the six libraries this course uses. The version cell below confirms that for your machine.

If you'd rather use Jupyter on your own computer, the optional section near the end covers it.

## Create the notebook and connect it to Drive

1.  Open [colab.research.google.com](https://colab.research.google.com/) and sign in.
2.  Choose **File › New notebook in Drive**.
3.  Click the name at the top left (something like `Untitled3.ipynb`) and rename it `00-setup.ipynb`.
4.  Run a first cell with **Shift+Enter** to connect to a runtime.

The notebook file itself lives in your Drive's **Colab Notebooks** folder. Files your code writes are a different story. By default they land on the virtual machine's disk under `/content`, and that disk is erased whenever Colab recycles your runtime. A result saved there is gone by tomorrow. Connect Drive so your project folder is permanent:

```python
from google.colab import drive
drive.mount("/content/drive")
```

Colab asks you to approve access in a pop-up. Afterwards, your Drive appears at `/content/drive/MyDrive`, and you can also browse it from the folder icon in the left sidebar (the same panel has a **Mount Drive** button that does this for you).

## Lay out the project so raw data stays raw

A research project produces three kinds of files: data you were given or measured, code you wrote, and things the code produced. The most useful rule in computational research is to keep them apart and never edit the first kind by hand. If you fix a typo directly in your raw spreadsheet, nobody (including you in three months) can tell which values were measured and which were corrected.

```mermaid caption="Data flows one way: raw files are read, never overwritten"
flowchart LR
    R["data/raw (read-only)"] --> C["notebooks/ and src/"]
    C --> P["data/processed"]
    P --> C
    C --> O["results/ (figures, runs)"]
```

This cell builds that layout. In Colab, point `PROJECT` at your Drive (the comment shows how); here it's a relative path so the cell runs anywhere.

```python run title="make_project.py"
from pathlib import Path

PROJECT = Path("leaf-nitrogen-study")   # Colab: Path("/content/drive/MyDrive/leaf-nitrogen-study")

FOLDERS = ["data/raw", "data/processed", "notebooks", "src", "results/figures", "results/runs"]
for folder in FOLDERS:
    (PROJECT / folder).mkdir(parents=True, exist_ok=True)

readme = PROJECT / "README.md"
if not readme.exists():
    readme.write_text(
        "# Leaf nitrogen study\n\n"
        "Question: (one sentence, written before any modeling)\n\n"
        "data/raw is never edited. Every file in data/processed and results\n"
        "is produced by code in notebooks/ or src/.\n"
    )

for path in sorted(PROJECT.rglob("*")):
    depth = len(path.relative_to(PROJECT).parts) - 1
    print("    " * depth + path.name + ("/" if path.is_dir() else ""))
```

`exist_ok=True` makes the cell safe to rerun: running it a second time changes nothing instead of crashing on folders that already exist. The README check works the same way, so rerunning never overwrites notes you've added. `results/runs` will hold one small record per experiment, which you'll start writing in the next lesson.

## Record the versions that produced your results

Library updates change results. Default hyperparameters change between releases, random number streams get reworked, and a deprecated argument starts raising an error. To rerun an old result you need the versions it ran on, so write them down at the start of every project.

```python run title="record_environment.py"
import json
import platform
import sys
from importlib.metadata import version

PACKAGES = ["numpy", "pandas", "scipy", "statsmodels", "scikit-learn", "matplotlib"]

env = {"python": sys.version.split()[0], "os": platform.system()}
for name in PACKAGES:
    env[name] = version(name)

for key, value in env.items():
    print(f"{key:<14}{value}")

(PROJECT / "results" / "environment.json").write_text(json.dumps(env, indent=2))
```

That output came from the machine that built this page. Colab will print `Linux` for the operating system and may show different version numbers; that's expected. What matters is that the numbers are written into the project next to the results they produced.

`importlib.metadata.version` reads the installed package's version without importing it, and it uses the name you'd type after `pip install`, which is why the list says `scikit-learn` rather than `sklearn`.

## Pin the versions in requirements.txt

`environment.json` is a record for humans. `requirements.txt` is the same information in the format `pip` reads, so someone else can rebuild your environment with one command.

```python run title="pin_requirements.py"
pins = "".join(f"{name}=={env[name]}\n" for name in PACKAGES)
(PROJECT / "requirements.txt").write_text(pins)
print(pins)
```

The `==` is the point. A line that says `scikit-learn` installs whatever is newest on the day someone runs it, which might be three releases after yours. A line that says `scikit-learn==1.8.0` installs the version you actually used. In Colab, someone rebuilding your environment would run this in a cell, then choose **Runtime › Restart session** so the newly installed versions are the ones Python loads:

```text
%pip install -r /content/drive/MyDrive/leaf-nitrogen-study/requirements.txt
```

## Check for drift when you come back

When you reopen a project weeks later, compare the current environment with the record before trusting any rerun. This cell is worth keeping at the top of every analysis notebook.

```python run title="check_drift.py"
recorded = json.loads((PROJECT / "results" / "environment.json").read_text())
current = {"python": sys.version.split()[0], **{name: version(name) for name in PACKAGES}}

drift = {name: (recorded[name], now) for name, now in current.items() if recorded.get(name) != now}
if drift:
    for name, (then, now) in drift.items():
        print(f"{name}: recorded {then}, running {now}")
else:
    print("Environment matches results/environment.json")
```

Here it matches because the record was written a minute ago. On a fresh Colab runtime next semester it may not, and then you'll know that a changed score could come from the libraries rather than your code.

## Optional: Jupyter on your own computer

A local setup has no session limits and works offline. Make a virtual environment inside the project folder so its packages stay separate from everything else on your computer.

:::tabs
@tab Windows
Install Python 3.10 or newer from [python.org/downloads](https://www.python.org/downloads/), ticking **Add python.exe to PATH** in the installer. Then open PowerShell in your project folder:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install numpy pandas scipy statsmodels scikit-learn matplotlib jupyterlab
jupyter lab
```

If PowerShell says running scripts is disabled, run `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` once, then activate again.
@tab macOS
Install Python 3.10 or newer from [python.org/downloads](https://www.python.org/downloads/). Then open Terminal in your project folder:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install numpy pandas scipy statsmodels scikit-learn matplotlib jupyterlab
jupyter lab
```
@tab Chromebook or Linux
On a Chromebook, Colab is the simplest route. With the Linux development environment turned on, or on any Linux computer:

```bash
sudo apt install python3-venv
python3 -m venv .venv
source .venv/bin/activate
python -m pip install numpy pandas scipy statsmodels scikit-learn matplotlib jupyterlab
jupyter lab
```
:::

Once a project has a `requirements.txt`, replace the long install line with `python -m pip install -r requirements.txt`, which installs exactly the pinned versions.

## Problems people hit on day one

**`drive.mount` fails or the pop-up says access is blocked.** Your school account doesn't allow Drive access for Colab. Switch to a personal Google account from the profile picture at the top right and create the notebook there.

**`FileNotFoundError` for a file you saved yesterday.** Either the file was written under `/content` instead of your Drive (so it was erased with the runtime), or Drive isn't mounted in the current session. Run the mount cell first, then check the path starts with `/content/drive/MyDrive`.

**`ModuleNotFoundError: No module named 'statsmodels'` on your own computer.** The virtual environment isn't active in that terminal, so Jupyter is using a different Python. Activate it (your prompt starts with `(.venv)`), then start `jupyter lab` again.

**`PackageNotFoundError: scikit-learn` from the version cell.** The package isn't installed in this environment at all. Install it, and in Colab restart the session afterwards.

:::quiz
Q: Your notebook saves a results table to `/content/results.csv`. The next morning the file is gone, but the notebook is still in Drive. What happened?
- [x] The file was on the runtime's temporary disk, which was erased when the runtime was recycled
  The notebook lives in Drive, but `/content` belongs to the virtual machine. Save under `/content/drive/MyDrive` after mounting.
- [ ] Colab deletes CSV files older than one day
  There's no such rule; everything on the runtime's disk goes when the machine does, whatever the file type.
- [ ] The notebook didn't autosave
  The notebook saved fine. The CSV was never in Drive in the first place.

Q: Why pin `scikit-learn==1.8.0` instead of writing just `scikit-learn` in `requirements.txt`?
- [ ] Unpinned lines are a syntax error
  `pip` accepts a bare name; it just installs the newest release.
- [x] A bare name installs whatever release is newest on the day of the install, which may behave differently from yours
  Pinning reproduces the environment that produced your numbers, not today's.
- [ ] Pinning makes installation faster
  Speed is about the same. The benefit is that everyone gets the same version.

Q: You find a typo in a value in `data/raw/plants.csv`. What's the reproducible fix?
- [ ] Correct the value in the raw file and save it
  Then nobody can tell measured values from corrected ones, and the original is lost.
- [x] Leave the raw file alone and fix the value in code that writes a cleaned copy to `data/processed`
  The correction is now documented, repeatable, and reversible, and the raw measurement survives.
- [ ] Delete the row so the typo can't cause trouble
  Silently dropping data changes the results and hides a decision a reader should see.
:::

:::takeaways
- Mount Drive and keep the project under `/content/drive/MyDrive`; files under `/content` alone are erased with the runtime.
- Separate `data/raw` (never edited), code, `data/processed`, and `results`, so every derived file can be regenerated.
- Write library versions to `environment.json` and pin them with `==` in `requirements.txt` on day one.
- Compare the current environment with the record before trusting a rerun of an old result.
:::
