Here is a tiny simulated experiment: 24 control plants, 24 fertilized plants, and the fertilizer adds about 2 cm of growth. The cell runs it twice and prints the estimated effect each time.

```python run title="no_seed.py"
import numpy as np

for attempt in range(2):
    rng = np.random.default_rng()            # no seed
    control = rng.normal(20, 2.5, size=24)
    fertilized = rng.normal(22, 2.5, size=24)
    print(f"attempt {attempt + 1}: effect = {fertilized.mean() - control.mean():.2f} cm")
```

Same code, two different answers, and if you run this page's code yourself you'll get two more. Neither number is wrong. They're both honest draws from the same process. The problem is that you can't write either one in a report, because nobody (you included) can regenerate it. A seed fixes that.

## How a seed replays the same "random" numbers

A random number generator is a deterministic machine. It holds a hidden state, and each draw transforms that state into a number and a new state. The seed sets the starting state, so the same seed always produces the same sequence. Step through this program and watch `first` and `second` fill up.

:::trace Reseeding replays the sequence
```python
import random

random.seed(7)
first = [random.randint(1, 6) for _ in range(3)]

random.seed(7)
second = [random.randint(1, 6) for _ in range(3)]

print(first, second, first == second)
```
:::

The second `random.seed(7)` rewinds the generator to the same starting state, so the second list is a copy of the first. For NumPy, use `rng = np.random.default_rng(seed)` and draw from `rng` everywhere. The older `np.random.seed(...)` sets one global generator that any library can silently advance, so a seed set at the top of a notebook doesn't protect a cell that runs after some other code has drawn from it.

## Step 1: Simulate a greenhouse experiment from a seed

Real experiments have structure, so this simulation does too. There are three greenhouse benches with slightly different light, 16 pots per bench, and the fertilizer is assigned at random *within* each bench (8 fertilized, 8 control), which keeps bench light from piling up in one group. The true fertilizer effect is built in as 2.0 cm.

```python run title="simulate.py"
import hashlib
import json
from pathlib import Path

import pandas as pd

PROJECT = Path("greenhouse-study")
for folder in ["data/raw", "results/runs"]:
    (PROJECT / folder).mkdir(parents=True, exist_ok=True)

BENCH_LIGHT = {"A": 0.0, "B": 1.5, "C": -1.0}   # cm of extra growth from each bench's light
TRUE_EFFECT = 2.0

def simulate_greenhouse(seed, pots_per_bench=16):
    rng = np.random.default_rng(seed)
    rows = []
    for bench, light in BENCH_LIGHT.items():
        groups = rng.permutation(["control", "nitrogen"] * (pots_per_bench // 2))
        for number, group in enumerate(groups, start=1):
            height = 20 + light + (TRUE_EFFECT if group == "nitrogen" else 0) + rng.normal(0, 2.5)
            rows.append({"pot": f"{bench}{number:02d}", "bench": bench,
                         "treatment": group, "height_cm": round(height, 1)})
    return pd.DataFrame(rows)

SEED = 42
plants = simulate_greenhouse(SEED)
raw_file = PROJECT / "data" / "raw" / "greenhouse.csv"
plants.to_csv(raw_file, index=False)
print(plants.head(4))
print(plants.shape)
```

Every random choice in the function, both the treatment shuffle and the measurement noise, comes from the one `rng` built from `seed`. That's what makes the whole dataset a function of a single integer.

## Step 2: Fingerprint the raw file

A file name tells you nothing about a file's contents. `greenhouse.csv` in March and `greenhouse.csv` in May may differ by one edited cell. A cryptographic hash such as SHA-256 turns the file's bytes into a 64-character fingerprint, and changing even one character changes the fingerprint completely.

```python run title="fingerprint.py"
def sha256_of(path):
    return hashlib.sha256(Path(path).read_bytes()).hexdigest()

data_hash = sha256_of(raw_file)
print("sha256:", data_hash[:16], "...")

edited = plants.copy()
edited.loc[0, "height_cm"] += 0.1                 # one value, nudged by a millimeter
edited.to_csv(PROJECT / "edited.csv", index=False)
print("edited:", sha256_of(PROJECT / "edited.csv")[:16], "...")
```

Store the hash with every result. If a rerun reads a file with a different hash, you know the data changed before you start hunting for bugs in the code.

## Step 3: Estimate the effect and plot the data

Look at the data before you model it. Each dot is one pot.

```python run alt="Strip chart of plant height by bench, with control and nitrogen pots side by side; nitrogen pots sit slightly higher on every bench and bench B is tallest overall" caption="Plant height by bench and treatment (seed 42)"
import matplotlib.pyplot as plt

fig, ax = plt.subplots(figsize=(6.5, 3.6))
for offset, (group, color, marker) in zip([-0.15, 0.15], [("control", "#7892ee", "o"), ("nitrogen", "#e0803a", "s")]):
    for position, bench in enumerate(BENCH_LIGHT):
        heights = plants.query("bench == @bench and treatment == @group")["height_cm"]
        jitter = np.linspace(-0.06, 0.06, len(heights))
        ax.scatter(position + offset + jitter, heights, color=color, marker=marker, s=22,
                   label=group if position == 0 else None)
ax.set_xticks(range(3), [f"bench {b}" for b in BENCH_LIGHT])
ax.set_ylabel("height after 4 weeks (cm)")
ax.legend(frameon=False)
```

Now estimate the fertilizer effect while accounting for the benches. `C(bench)` tells statsmodels to treat bench as a category, so each bench gets its own baseline height and the treatment effect is estimated within benches.

```python run title="estimate.py"
import statsmodels.formula.api as smf

fit = smf.ols("height_cm ~ treatment + C(bench)", data=plants).fit()
effect = fit.params["treatment[T.nitrogen]"]
low, high = fit.conf_int().loc["treatment[T.nitrogen]"]
print(f"fertilizer effect: {effect:.2f} cm  (95% CI {low:.2f} to {high:.2f})")
```

We built a true effect of 2.0 cm into the simulation, and the estimate from seed 42 is about half that. That isn't a bug. With 24 pots per group and 2.5 cm of plant-to-plant noise, an estimate this far off happens, and the confidence interval is wide enough to say so. Notice that 2.0 sits inside the interval.

## Step 4: Write a run record

A run record is a small JSON file holding everything needed to regenerate and recognize a result.

```python run title="record.py"
from importlib.metadata import version

def run_record(seed, data_hash, effect, low, high):
    return {
        "seed": seed,
        "data_file": str(raw_file),
        "data_sha256": data_hash,
        "versions": {name: version(name) for name in ["numpy", "pandas", "statsmodels"]},
        "model": "ols: height_cm ~ treatment + C(bench)",
        "effect_cm": round(effect, 4),
        "ci95_cm": [round(low, 4), round(high, 4)],
    }

record = run_record(SEED, data_hash, effect, low, high)
(PROJECT / "results" / "runs" / "run-001.json").write_text(json.dumps(record, indent=2))
print(json.dumps(record, indent=2))
```

## Step 5: Prove the whole run repeats

The real test is to rebuild everything from the seed (data, hash, fit, record) and compare it with the saved record.

```python run title="rerun.py"
def run_experiment(seed):
    data = simulate_greenhouse(seed)
    data.to_csv(raw_file, index=False)
    result = smf.ols("height_cm ~ treatment + C(bench)", data=data).fit()
    lo, hi = result.conf_int().loc["treatment[T.nitrogen]"]
    return run_record(seed, sha256_of(raw_file), result.params["treatment[T.nitrogen]"], lo, hi)

saved = json.loads((PROJECT / "results" / "runs" / "run-001.json").read_text())
rerun = run_experiment(42)
print("rerun matches run-001:", rerun == saved)

estimates = [run_experiment(seed)["effect_cm"] for seed in range(20)]
print("20 other seeds:", np.round(estimates, 2))
print(f"spread (sd) of the estimate: {np.std(estimates):.2f} cm")
plants.to_csv(raw_file, index=False)      # put the seed-42 data back
```

`rerun == saved` compares every key and value, including the data hash, so `True` means the data and the result are the same down to the fourth decimal. The second part is just as useful. Running the identical experiment with 20 other seeds shows how much the estimate moves from sampling noise alone, about 0.6 cm here. Keep that idea in mind: a difference between two models or two conditions that is smaller than the seed-to-seed spread isn't evidence of anything yet.

## Smoke test: every library in one cell

The last check confirms that SciPy and scikit-learn work too, using the same data.

```python run title="smoke_test.py"
from scipy import stats
from sklearn.linear_model import LinearRegression
from sklearn.model_selection import KFold, cross_val_score

t_stat, p_value = stats.ttest_ind(
    plants.query("treatment == 'nitrogen'")["height_cm"],
    plants.query("treatment == 'control'")["height_cm"],
)
print(f"scipy        t = {t_stat:.2f}, p = {p_value:.3f}")

X = pd.get_dummies(plants[["bench", "treatment"]], drop_first=True).astype(float)
cv = KFold(n_splits=5, shuffle=True, random_state=SEED)
scores = cross_val_score(LinearRegression(), X, plants["height_cm"], cv=cv, scoring="r2")
print(f"scikit-learn cross-validated R^2 = {scores.mean():.2f}")
print("Toolkit works")
```

The low R² is the honest answer, not a failure: bench and treatment explain only a small part of the plant-to-plant variation, which is mostly noise. If you see `Toolkit works`, your setup is ready.

## When the rerun doesn't match

**`rerun matches run-001: False` after editing nothing.** Something drew random numbers outside `rng`. Look for `np.random.normal(...)`, `random.random()`, or a scikit-learn object without `random_state`; each one uses a different, unseeded generator.

**The hash changes but the numbers look identical.** The bytes differ even if the values don't. A different pandas version can format floats differently, and opening and resaving a CSV in a spreadsheet program can change line endings or quoting. That's exactly why raw files are written once and never resaved by hand.

**The record compares as `False` because of a timestamp.** If you add the time a run started (useful), leave that key out when you compare records.

:::video WAdrXVnOTIM
A two-minute explanation from Data School. What to watch for: `random_state` in scikit-learn is the same idea as the seed in this lesson, one integer that makes a split or model repeatable.
:::

:::quiz
Q: You call `np.random.seed(0)` in the first cell, then run cells out of order and get a different result than yesterday. Why?
- [x] `np.random.seed` sets one global generator, and whatever ran before your cell advanced it
  The seed fixes the start of the sequence, not where your cell lands in it. A local `rng = np.random.default_rng(0)` passed to your code avoids this.
- [ ] Seeds expire when a runtime restarts
  A seed is just an integer; it doesn't expire. The generator's position in its sequence is what changed.
- [ ] NumPy ignores seeds on Colab
  Seeds work the same on every machine.

Q: The seed-42 run estimated an effect of about 1 cm, but the simulation's true effect is 2 cm. What's the right conclusion?
- [ ] The code has a bug, because the estimate should equal 2.0
  With 24 pots per group and 2.5 cm of noise, estimates vary by roughly 0.6 cm between seeds, so 1 cm is unlucky but plausible.
- [x] It's sampling variation, and the confidence interval, which contains 2.0, says so
  One dataset gives one estimate. The interval and the 20-seed spread both show how far off a single run can be.
- [ ] Rerun with different seeds and report the one closest to 2.0
  Picking the seed that gives the answer you want is cherry-picking, and in real research you don't know the true value.

Q: Two run records have identical results but different `data_sha256` values. What does that tell you?
- [ ] Nothing; hashes are random
  SHA-256 is deterministic: the same bytes always give the same hash.
- [x] The raw files' bytes differ, so treat them as different data until you find out why
  Maybe it's only formatting, maybe it's an edited value. The hash tells you to check before trusting either result.
- [ ] One of the hashes was computed wrong
  The function is the same each time; different hashes mean different input bytes.
:::

:::takeaways
- A seed sets a generator's starting state; create one `rng = np.random.default_rng(seed)` and draw everything from it.
- Fingerprint raw data with SHA-256 so you can tell when a file has changed.
- Save a run record (seed, data hash, versions, model, results) next to every result.
- Prove reproducibility by rebuilding from the seed and comparing with the record, and measure how much results move between seeds.
:::
