In February you dropped 31 plants from your dataset because their labels were smudged. In April your mentor asks why the sample size in your poster is 31 smaller than the number in your proposal. If the reason lives only in your memory, the honest answer is "I think there was a reason." Research is full of small decisions like that one, and a project is only as trustworthy as its record of them.

## Keep a research log next to the code

A research log is a plain text file in the project folder with one dated entry per working session. Each entry answers four questions: what you did, why, what happened, and what's next. It takes two minutes at the end of a session and saves hours when you write the report.

```python run title="log.py"
from datetime import date
from pathlib import Path

PROJECT = Path("greenhouse-study")
PROJECT.mkdir(exist_ok=True)
LOG = PROJECT / "research_log.md"

def log(did, why, result, next_step, day=None):
    day = day or date.today().isoformat()
    entry = (f"\n## {day}\n- Did: {did}\n- Why: {why}\n"
             f"- Result: {result}\n- Next: {next_step}\n")
    with LOG.open("a") as handle:
        handle.write(entry)

log("Dropped 31 pots with unreadable labels (list in data/processed/dropped.csv)",
    "Treatment group can't be confirmed for those pots",
    "n went from 480 to 449; dropped pots are spread across all benches",
    "Check the dropped pots aren't mostly from one treatment",
    day="2026-02-12")
log("Refit OLS with bench as a category",
    "Bench B gets more light and was inflating the nitrogen group's mean",
    "Effect fell from 2.6 cm to 1.9 cm (95% CI 1.2 to 2.6)",
    "Ask mentor whether to add pot position as a covariate",
    day="2026-02-19")

print(LOG.read_text())
```

Notice what the second entry captures: a number changed, and the log says why it changed. That's the entry that answers your mentor's question in April. Keep negative results too. "Tried a random forest, no better than linear" is a finding, and it stops you from trying the same thing again in May.

## A notebook isn't finished until it survives Restart and run all

A notebook keeps variables in memory between cells, so the order you ran cells in, including cells you've since deleted, shapes what's in memory. A result can depend on a cell that no longer exists. Before you trust a number, put it in your log, or send the notebook to anyone, choose **Runtime › Restart session and run all**. If every cell runs top to bottom and produces the same numbers, the notebook is a real record. If it crashes halfway, you've found a hidden dependency while it's still cheap to fix.

A few habits make that test easy to pass:

- **Number notebooks by stage**: `01-audit.ipynb`, `02-baseline.ipynb`, `03-model.ipynb`. Each one reads files written by earlier stages instead of relying on variables from another notebook.
- **Put the drift check from Lesson 1 in the first cell**, and set `SEED` once near the top.
- **Move a function to `src/`** once you've copied it into a second notebook, so there's one version of it.

Colab also keeps history for you. **File › Revision history** lists saved versions of the notebook you can restore, and **File › Download › Download .ipynb** gives you a copy to keep with the project or put under version control.

## Protect the people (and places) in your data

If your project uses data about people, such as surveys, health measurements, or anything with names, ages, or locations, privacy rules apply before any code does. Science fairs that follow the ISEF rules require an Institutional Review Board (IRB) to review and approve student research with human participants *before* any recruitment or data collection. Projects that use only preexisting, publicly available datasets, with no interaction with people, are generally exempt from that preapproval. Check the [human participants rules](https://www.societyforscience.org/isef/international-rules/human-participants/) and your fair's own guidance early, because review takes weeks.

Even with approval, keep identifying details out of the files you analyze and share. This cell de-identifies a small survey table: it drops names, swaps student IDs for random codes, and coarsens birth dates to years.

```python run title="deidentify.py"
import numpy as np
import pandas as pd

survey = pd.DataFrame({
    "name": ["Ava Chen", "Leo Park", "Mia Ortiz"],
    "student_id": ["S1042", "S1187", "S1203"],
    "birth_date": ["2009-03-14", "2008-11-02", "2009-07-29"],
    "sleep_hours": [6.5, 8.0, 7.25],
    "reaction_ms": [312, 287, 301],
})

rng = np.random.default_rng()                     # unseeded on purpose: codes must not be reproducible
codes = [f"P{n:03d}" for n in rng.permutation(np.arange(1, len(survey) + 1))]
key = pd.DataFrame({"student_id": survey["student_id"], "code": codes})   # store apart from the data

shared = (survey.assign(participant=codes,
                        birth_year=survey["birth_date"].str[:4].astype(int))
                .drop(columns=["name", "student_id", "birth_date"]))
print(shared[["participant", "birth_year", "sleep_hours", "reaction_ms"]])
```

The key table that links codes back to students is the sensitive part. Keep it out of the project folder and out of anything you share or upload, and delete it when the study no longer needs it. This is also the one place in the course where a seed would be a mistake: anyone who knew the seed could regenerate the codes.

:::warning
Shared notebooks leak data in their outputs. A notebook whose last run printed `survey.head()` still contains those names after you delete the cell's code, because the output is saved in the file. Before sharing, choose **Edit › Clear all outputs**, then restart and run all on the de-identified data only. Don't paste private data into public forums or AI chat tools either.
:::

Locations can be sensitive too. Field biologists routinely blur or withhold the coordinates of rare species, because a precise location in a public dataset can lead collectors or poachers straight to them. Round coordinates or publish them at a coarse grid when that risk exists.

## Draw charts everyone can read

About one in twelve men has some form of color-vision deficiency, and red versus green is the pair most often confused. Two cheap fixes cover most cases: use a color-blind-safe palette, and make groups differ by marker shape or line style as well as color, so the chart still works printed in greyscale.

```python run alt="Line chart of mean plant height over four weeks for three treatments, each drawn in a color-blind-safe color with its own marker and line style and labelled at the end of its line" caption="Color plus shape plus a direct label: readable even in greyscale"
import matplotlib.pyplot as plt

weeks = np.arange(0, 5)
heights = {"control": [5.0, 8.1, 11.0, 13.6, 15.9],
           "low nitrogen": [5.0, 8.6, 12.0, 15.1, 17.8],
           "high nitrogen": [5.0, 9.0, 12.9, 16.4, 19.6]}

with plt.style.context("tableau-colorblind10"):
    fig, ax = plt.subplots(figsize=(6.5, 3.6))
    for (label, values), marker, style in zip(heights.items(), ["o", "s", "^"], ["-", "--", ":"]):
        ax.plot(weeks, values, marker=marker, linestyle=style, linewidth=2)
        ax.annotate(label, (weeks[-1], values[-1]), xytext=(6, 0), textcoords="offset points", va="center")
    ax.set_xlabel("week")
    ax.set_ylabel("mean height (cm)")
    ax.set_xlim(-0.2, 5.6)
    ax.spines[["top", "right"]].set_visible(False)
```

Labelling each line directly also removes the legend, so readers don't have to match colors across the chart. For your own comfort while working, Colab's settings (the gear icon at the top right) include a dark theme and a larger editor font size.

## Getting unstuck: read the last line, then shrink the problem

Here's an error you'll meet in some form this year. The CSV came from a spreadsheet, and the column clearly says `height_cm`.

```python run raises
import io

csv_text = "pot,bench,height_cm \nA01,A,22.2\nA02,A,23.9\nB01,B,24.1\n"
plants = pd.read_csv(io.StringIO(csv_text))
print(plants["height_cm"].mean())
```

Read a traceback from the bottom. The last line, `KeyError: 'height_cm'`, says pandas has no column with exactly that name; everything above it is pandas' internal route to that conclusion. When a name "obviously exists" but isn't found, print the exact names as a list, where the quotes make invisible characters such as spaces visible:

```python run
print(plants.columns.tolist())
plants.columns = plants.columns.str.strip()
print(round(plants["height_cm"].mean(), 2))
```

The spreadsheet left a trailing space in the header: `'height_cm '`. Stripping whitespace from every column name fixes it.

When you can't find the cause yourself, build a **minimal reproducible example** before asking anyone. Copy the failing line into a fresh cell, replace your dataset with three or four rows typed inline (like `csv_text` above), and delete everything that isn't needed to trigger the error. Half the time the bug becomes obvious while you shrink it. The other half, you have a ten-line example that a mentor or a forum can answer in minutes, and it contains none of your private data.

:::quiz
Q: Your notebook gives a clean result, but **Restart session and run all** crashes at cell 9 with a `NameError`. What does that tell you?
- [ ] Colab's restart is unreliable, so trust the earlier result
  The restart is the reliable part: it shows exactly what the notebook's code produces from scratch.
- [x] The result depended on a variable from a cell that was deleted, moved, or run out of order
  The notebook as written can't produce that result. Fix the dependency, then recheck the number.
- [ ] Cell 9 has a typo that only matters after a restart
  A typo would fail every time. Failing only after a restart points to hidden state.

Q: You share a de-identified table plus the notebook that made it. Which mistake can still expose participants?
- [x] The notebook's saved outputs still show `survey.head()` from before you de-identified
  Outputs are stored inside the `.ipynb` file. Clear all outputs and rerun on the de-identified data before sharing.
- [ ] Using random participant codes like `P002`
  Random codes with the key stored separately are the recommended approach.
- [ ] Keeping birth year instead of birth date
  Coarsening to year reduces identifiability; it's one of the standard steps.

Q: A `KeyError: 'temp_c'` appears, but you can see a `temp_c` column in the spreadsheet. What's the fastest first check?
- [ ] Reinstall pandas
  The library is fine; it's reporting a real mismatch in names.
- [x] Print `df.columns.tolist()` to see the exact names, including hidden spaces or different capitalization
  Quoted names reveal `'temp_c '` or `'Temp_C'` immediately.
- [ ] Rename the file and read it again
  The file name has nothing to do with the column names inside it.
:::

:::takeaways
- Keep a dated research log: what you did, why, the result, and what's next. Record decisions that change numbers.
- A notebook result counts only after **Restart session and run all** reproduces it.
- Data about people needs approval before collection at ISEF-affiliated fairs; share only de-identified data, with the key stored elsewhere, and clear outputs first.
- Make charts readable without color: safe palette, distinct markers or line styles, direct labels.
- Read tracebacks from the last line up, and shrink a stubborn bug to a few inline rows before asking for help.
:::
