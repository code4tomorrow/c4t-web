The capstone pulls every module together into one system. Someone asks a question about a set of documents. Your system finds the passages that matter, answers only from them, cites the chunk each claim came from, says "the documents don't say" when they don't, and refuses to ship until an evaluation says it's ready.

You'll build it in the next lesson and present it in the one after. This lesson is planning, and the planning includes code: by the end you'll have the two files that define success, the output schema and the evaluation set, before a single line of retrieval exists.

## What the finished system must do

Every project, whatever its documents, needs all of these:

| Part | Minimum for the capstone | Where you learned it |
| --- | --- | --- |
| Ingestion | Load your documents from files; scrub personal data before indexing | Module 2, Module 7 |
| Chunking | Split by structure, overlap long paragraphs, keep chunk ids | Module 6 |
| Retrieval | TF-IDF or embeddings, top-k with a score floor, measured with hit@k | Modules 3 and 6 |
| Grounded answers | A prompt with rules, numbered sources, and few-shot examples | Module 6 |
| Structured output | A strict Pydantic schema; reject anything that doesn't validate | Module 6 |
| Hallucination checks | Citations shown, quantities in the source, word-level support | Module 7 |
| Evaluation | At least 25 questions, at least a fifth unanswerable, with a launch gate | Module 7 |
| Context budget | A token estimate for every prompt, under your model's window | Module 5 |
| Limits | A written statement of what the system can't do and who shouldn't rely on it | This module |

```mermaid caption="The capstone pipeline; the dashed parts run offline before anyone asks a question"
flowchart LR
    F[Your files] -.-> I[Ingest and scrub]
    I -.-> C[Chunk]
    C -.-> X[(Index)]

## Five project ideas, from first build to stretch

Pick one, or adapt one to documents you care about. The difficulty comes mostly from the documents and the questions, not from the code, which is the same skeleton for all five.

| Level | Project | Documents | What makes it hard |
| --- | --- | --- | --- |
| Starter | **Syllabus helper** | The syllabi for two or three of your own classes | Little text, so the eval set is small; works without any LLM using the extractive stand-in |
| Core | **Club handbook bot** | A robotics, debate, or sports club's rules and FAQ, with permission | Questions that need two sections at once, like a rule plus its exception |
| Core | **Open-source docs helper** | The README and guides of a library you use (check the license) | Code blocks and API names chunk badly; exact names matter |
| Advanced | **Public rules explainer** | A city's published park, library, or transit fare rules | Lots of numbers, dates, and conditions; the quantity check earns its keep |
| Stretch | **Retrieval bake-off** | Any set above, 15 pages or more | Compare TF-IDF, embeddings, and hybrid retrieval, plus prompt-only versus RAG, with confidence intervals |

## Choose documents you're allowed to use

Your documents decide whether this project is safe to share. Use text that is public or that you wrote, and check three things before you load anything:

-   **No personal data.** No student records, grades, health information, addresses, phone numbers, or anyone's messages. A club roster is personal data; the club's rules are not.
-   **Permission and licensing.** Public government pages and openly licensed docs are fine for a class project. A paid textbook scanned to PDF is not.
-   **Where the text goes.** Anything you send to a hosted API leaves your computer. If you're unsure about a document, run a local model with Ollama, or use the extractive stand-in, which never sends text anywhere.

:::warning
"I'll scrub it later" is how personal data ends up in a demo. Module 7's harness caught a desk note with a patron's email address because the corpus contained it. Remove sensitive documents before indexing, and run the scrubber anyway as a second line of defense.
:::

  Five real questions they ask:  1. ____  2. ____  3. ____  4. ____  5. ____
  What happens if an answer is wrong?  ______________________

DOCUMENTS
  Source and license:            ______________________
  Number of files / pages:       ______________________
  Personal data present?         no / yes -> removed how: ______________

MODEL           provider: stand-in / Gemini / Ollama   context window: ___ tokens
OUTPUT SCHEMA   fields: answer, citations, answerable, ____________
CHECKS          citations shown / quantities / support threshold ___ / other: ____
EVAL SET        total questions: ___   unanswerable: ___   tags: number, negation, two-part, ...

```

The "what happens if an answer is wrong" line sets every threshold below it. A syllabus helper that gets a due date wrong costs a student a late penalty; that argues for a strict quantity check and 100% abstention on unanswerable questions.

## Write the contract before the pipeline

Two definitions come first, because everything else is measured against them. `QAResult` is what your system must return. `EvalCase` is one row of your evaluation set, and its validator refuses half-written cases: an answerable question needs both a gold answer and the chunk it comes from, and an unanswerable one needs neither.

```python run
import json
from typing import Optional

from pydantic import BaseModel, ConfigDict, Field, ValidationError, model_validator

class QAResult(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    answer: str = Field(description="One to three sentences, using only the sources.")
    citations: list[str] = Field(description="Ids of the sources used, such as S1.")
    answerable: bool = Field(description="False when the sources do not answer the question.")

class EvalCase(BaseModel):
    model_config = ConfigDict(extra="forbid")
    id: str
    question: str = Field(min_length=5)
    gold_answer: Optional[str] = None
    gold_chunks: list[str] = []
    tags: list[str] = []

    @model_validator(mode="after")
    def gold_matches_answerability(self):
        if (self.gold_answer is None) != (not self.gold_chunks):
            raise ValueError("answerable cases need gold_answer and gold_chunks; "
                             "unanswerable cases need neither")
        return self

print("QAResult fields:", list(QAResult.model_json_schema()["properties"]))
```

The `description` on each field isn't decoration. When you pass `QAResult` to an API's structured-output mode, the descriptions travel inside the JSON Schema, so they double as instructions to the model.

Store the eval set as **JSON Lines**: one JSON object per line, easy to add to and easy to review in a diff. Here are the first five cases for a robotics-club handbook, with one mistake planted in them:

```python run
EVAL_JSONL = """
{"id": "q01", "question": "When are build sessions held?", "gold_answer": "Tuesdays and Thursdays, 3:30 to 5:30", "gold_chunks": ["meetings#0"], "tags": ["schedule"]}
{"id": "q02", "question": "How many build hours do I need to travel to competitions?", "gold_answer": "20 build hours", "gold_chunks": ["travel#0"], "tags": ["number"]}
{"id": "q03", "question": "Can I take a battery home?", "gold_answer": "No, batteries stay in the lab", "gold_chunks": ["safety#1"], "tags": ["negation"]}
{"id": "q04", "question": "Who won last year's regional?", "tags": ["unanswerable"]}
{"id": "q05", "question": "What is the dress code?", "gold_answer": "closed-toe shoes", "tags": ["safety"]}
"""

cases, problems = [], []
for line in EVAL_JSONL.strip().splitlines():
    try:
        cases.append(EvalCase.model_validate_json(line))
    except ValidationError as err:
        problems.append(f"{json.loads(line)['id']}: {err.errors()[0]['msg']}")

unanswerable = sum(case.gold_answer is None for case in cases)
print(f"{len(cases)} valid cases, {unanswerable} unanswerable")
for problem in problems:
    print("REJECTED", problem)
tags = sorted({tag for case in cases for tag in case.tags})
print("tags covered:", tags)
```

Case q05 has an answer but no gold chunk, so it's rejected: without a gold chunk you can't measure retrieval, and you can't tell whether a correct-sounding answer came from the documents. Write 25 or more cases this way, from your plan's real questions, before you build anything. It's easier to write fair questions before you know which ones your system finds hard.

## Six milestones

| Milestone | Build | Done when |
| --- | --- | --- |
| 1. Ingest | Load files, scrub personal data, report what was removed | Every document loads; the scrub report is empty or explained |
| 2. Chunk | Structure-aware chunks with ids and overlap | Every chunk is under your word limit and makes sense read alone |
| 3. Retrieve | Index and `retrieve(question, k)` | hit@3 measured on your eval set, and the misses read and explained |
| 4. Answer | Prompt builder, schema, model call (stand-in first) | Every prompt fits the token budget; every reply is validated |
| 5. Check | Citation, quantity, and support checks; abstain on failure | Each check has at least one eval case that trips it |
| 6. Evaluate | Run the eval set, summarize, launch gate | A gate report you can explain line by line, plus a limits statement |

Build them in order, and run the eval set after milestones 3, 5, and 6. A system that's tested only at the end gives you one number and no idea which part to fix.

:::quiz
Q: Your club's shared drive has the rules handbook, the meeting schedule, and a spreadsheet of members with phone numbers. Which should go into the index?
- [x] The handbook and the schedule
  Rules and schedules answer the questions; the member list is personal data and has no place in a Q&A index.
- [ ] All three, with the scrubber removing phone numbers
  The scrubber is a backstop, not a plan; names and other details would remain.
- [ ] Only the member spreadsheet, since it's the most structured
  Structure doesn't make it appropriate, and members' details aren't what users should be asking about.

Q: Why write the evaluation set before building the retriever?
- [ ] Because the retriever needs the eval set to train
  TF-IDF and pretrained embeddings don't train on your eval set.
- [x] So the questions reflect what users ask, not what your system happens to handle well
  Questions written after you've seen the system tend to drift toward its strengths.
- [ ] Because Pydantic requires it
  Pydantic validates the cases; it doesn't care when you write them.
:::
