:::objectives
- Write an evaluation set with gold answers, gold sources, and questions the documents can't answer.
- Score each answer on several separate checks instead of one blended number.
- Compare a prompt-only system with a RAG system and read where each fails.
- Turn the results into a launch gate with explicit thresholds and a list of blocking failures.
:::

Two versions of the library help bot are on the table. One just asks a model; the other retrieves first. Someone tried each on a few questions and declared the RAG version "accurate." By the end of this page you'll have a harness that prints this instead:

```text
LAUNCH GATE (rag): FAIL
  - abstains when it should: 67%, need 100%
  - invented numbers in 1 answer(s) [5]
  - unsupported claims in 2 answer(s) [8, 9]
  - personal data in 1 answer(s) [9]
```

Every line names a check, a threshold, and the cases that broke it. That's what makes it actionable: three answers to fix, not a vague sense that the bot "needs work."

```mermaid caption="The harness scores every case on separate checks, then the gate compares totals with thresholds"
flowchart LR
    E[Eval set] --> S[score_case]

    G -->|all thresholds met| P[PASS]

## Step 3: The checks, one function each

Each check answers one yes-or-no question about one answer. Keeping them separate is the main design decision: a single blended score would hide *which* thing went wrong.

```python run
from sklearn.feature_extraction.text import ENGLISH_STOP_WORDS

def normalize(text):
    text = "".join(ch for ch in text.lower() if ch not in string.punctuation)
    text = re.sub(r"\b(a|an|the)\b", " ", text)
    return " ".join(text.split())

def token_f1(prediction, gold):
    pred, ref = normalize(prediction).split(), normalize(gold).split()
    common = sum((Counter(pred) & Counter(ref)).values())
    if common == 0:
        return 0.0
    precision, recall = common / len(pred), common / len(ref)
    return 2 * precision * recall / (precision + recall)

WORD_NUMBERS = {"one": "1", "two": "2", "three": "3", "four": "4", "five": "5",
                "six": "6", "seven": "7", "eight": "8", "nine": "9", "ten": "10"}

def numbers(text):
    found = set(re.findall(r"\d+(?:\.\d+)?", text))
    return found | {WORD_NUMBERS[w] for w in re.findall(r"[a-z]+", text.lower()) if w in WORD_NUMBERS}

def terms(text):
    out = []
    for word in re.findall(r"[a-z0-9]+", text.lower()):
        if word in ENGLISH_STOP_WORDS:
            continue
        for suffix in ("ing", "ed", "s"):
            if word.endswith(suffix) and len(word) - len(suffix) >= 3:
                word = word[: -len(suffix)]
                break
        out.append(word)
    return out

def support(answer, source_text):
    words, source_words = terms(answer), set(terms(source_text))
    return sum(w in source_words for w in words) / max(len(words), 1)

PERSONAL_DATA = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+|\b\d{3}-\d{4}\b")

print(numbers("Six hours per week, 2 per day"), round(support("Laptops are charged 15 dollars", CORPUS["fees#1"]), 2))
```

`numbers` also reads number words, so "six hours" counts as 6, and an answer can't dodge the check by spelling a number out. `PERSONAL_DATA` looks for email addresses and phone-number patterns; a real project would add names and ID numbers, or use a dedicated PII detector.

## Step 4: Score every case

`score_case` runs every check on one answer and returns a row. An answer with no citations has nothing to be grounded in, so any number it states counts as invented.

```python run
def score_case(case, output, min_support=0.75):
    answer, citations = output
    row = {"id": case["id"], "answerable": case["gold"] is not None, "abstained": answer is None}
    row["abstain_ok"] = row["abstained"] != row["answerable"]
    if answer is None:
        return {**row, "f1": 0.0, "cites_gold": False, "numbers_ok": True, "supported": True, "pii": False}
    cited = " ".join(CORPUS[c] for c in citations if c in CORPUS)
    return {**row,
            "f1": token_f1(answer, case["gold"]) if case["gold"] else 0.0,
            "cites_gold": case["source"] in citations,
            "numbers_ok": numbers(answer) <= numbers(cited),
            "supported": bool(cited) and support(answer, cited) >= min_support,
            "pii": bool(PERSONAL_DATA.search(answer))}

def score_system(outputs):
    return [score_case(case, outputs[case["id"]]) for case in EVAL]

print(" id  f1    gold-src  numbers  supported  abstain  pii")
for row in score_system(RAG):
    print(f"{row['id']:3d}  {row['f1']:.2f}  {str(row['cites_gold']):8s}  {str(row['numbers_ok']):7s}"
          f"  {str(row['supported']):9s}  {str(row['abstain_ok']):7s}  {row['pii']}")
```

Read row 5: F1 is 0.50, a middling score that looks like a so-so paraphrase. The number check says what really happened: the answer says 15 dollars and the source says 5. Row 8 passes the number check but fails support, because "drivers can also pick up returns" appears nowhere. Row 9 answered an unanswerable question and leaked a patron's email address in the process.

## Step 5: Summarize and compare

Each metric is averaged over the cases where it means something: answer quality over answerable questions, abstention over unanswerable ones, and grounding over every answer the system actually gave.

```python run
def summarize(rows):
    answerable = [r for r in rows if r["answerable"]]
    unanswerable = [r for r in rows if not r["answerable"]]
    answered = [r for r in rows if not r["abstained"]]
    mean = lambda items, key: sum(r[key] for r in items) / max(len(items), 1)
    return {
        "mean F1 (answerable)": mean(answerable, "f1"),
        "cites gold source": mean(answerable, "cites_gold"),
        "numbers grounded": mean(answered, "numbers_ok"),
        "claims supported": mean(answered, "supported"),
        "abstains when it should": mean(unanswerable, "abstained"),
        "answers when it should": 1 - mean(answerable, "abstained"),
        "no personal data": 1 - mean(answered, "pii"),
    }

results = {"prompt-only": summarize(score_system(PROMPT_ONLY)), "rag": summarize(score_system(RAG))}
print(f"{'metric':26s} {'prompt-only':>11s} {'rag':>6s}")
for metric in results["rag"]:
    print(f"{metric:26s} {results['prompt-only'][metric]:11.2f} {results['rag'][metric]:6.2f}")
```

```

RAG is better on five of the seven metrics, ties on one, and is worse only on privacy. That is the comparison "a few impressive demos" never made. Prompt-only's color-printing answer happens to be right, but with no citation there's no way to know that without checking by hand, so it counts as ungrounded. And prompt-only has a perfect privacy score only because it never read the desk note.

## Step 6: The launch gate

A **launch gate** writes down, before you look at results, what "good enough" means. Some thresholds are averages, but privacy and invented numbers get a hard zero: one leaked email is a failure, however good the average is.

```python run title="eval_harness.py"
THRESHOLDS = {
    "mean F1 (answerable)": 0.5,
    "cites gold source": 0.9,
    "abstains when it should": 1.0,
    "answers when it should": 0.9,
}
ZERO_TOLERANCE = {"numbers_ok": "invented numbers", "supported": "unsupported claims", "pii": "personal data"}

def launch_gate(name, outputs):
    rows = score_system(outputs)
    summary = summarize(rows)
    blockers = []
    for metric, minimum in THRESHOLDS.items():
        if summary[metric] < minimum:
            blockers.append(f"{metric}: {summary[metric]:.0%}, need {minimum:.0%}")
    for key, label in ZERO_TOLERANCE.items():
        bad = [r["id"] for r in rows if not r["abstained"] and (r[key] if key == "pii" else not r[key])]
        if bad:
            blockers.append(f"{label} in {len(bad)} answer(s) {bad}")
    print(f"LAUNCH GATE ({name}): {'FAIL' if blockers else 'PASS'}")
    for blocker in blockers:
        print("  -", blocker)

launch_gate("prompt-only", PROMPT_ONLY)
print()
launch_gate("rag", RAG)
```

Both fail, for very different reasons. Prompt-only fails nearly everything; it isn't close. RAG fails on three specific answers, and each maps to a fix you already know: case 5 needs a stricter number check before the reply is shown, case 8 needs the support check from the last lesson in the pipeline, and case 9 needs the desk note removed from the corpus and personal data scrubbed at ingestion. Fix those, add the cases that broke to the eval set, and rerun the gate.

:::quiz
Q: Why is "abstains when it should" averaged only over unanswerable questions?
- [x] On answerable questions, abstaining is a different mistake, and mixing the two would hide both
  Refusing a real question and answering an impossible one are opposite failures; each gets its own metric.
- [ ] Because abstaining on answerable questions is always fine
  It isn't: a bot that refuses everything is useless, which is why "answers when it should" exists.
- [ ] Because F1 can't be computed for unanswerable questions
  True, but that's about F1; abstention needs its own denominator for a different reason.

Q: A system scores 0.98 on "no personal data" across 500 answers. Should the gate pass that check?
- [ ] Yes, 98% is above any reasonable threshold
  98% of 500 is 10 answers that leaked someone's personal data.
- [x] No: personal data is zero-tolerance, so any leak blocks launch and must be fixed at the source
  Averages are right for quality; for harms like leaks, one case is one too many.
- [ ] Only if the leaks were in unanswerable questions
  Where the leak happened doesn't change who was exposed.

Q: Case 5 has an F1 of 0.50 and states 15 dollars instead of 5. What does this show about relying on F1 alone?
- [ ] F1 is broken and shouldn't be used
  F1 is useful for wording overlap; it just can't judge facts on its own.
- [x] F1 rewards shared words, so a wrong number in a well-worded answer still earns partial credit
  That's why the harness has a separate number check with zero tolerance.
- [ ] The gold answer was written badly
  "5 dollars per day" is a fine gold answer; the prediction is the problem.
:::

:::takeaways
- Write the eval set first, with gold answers, gold sources, and a solid share of unanswerable questions.
- Score each answer on separate checks so a failure tells you what to fix.
- Average each metric over the cases where it applies, and compare systems on the same set.
- Decide thresholds before you see results; make privacy leaks and invented facts zero-tolerance.
- A failing gate with case ids is a to-do list. Fix, add the failures as new eval cases, and rerun.
:::

## Ideas to extend it

-   Add a `latency_ms` and `tokens` field per output and gate on cost as well as quality.
-   Bootstrap the summary (resample the eval cases 1,000 times) to show how much each metric could move by luck.
-   Write a second gate that compares a new version with the current one and fails if any metric drops.
