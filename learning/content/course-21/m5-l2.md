:::objectives
- Estimate token counts with a simple tokenizer and know which direction it errs.
- Split a context window into a budget: instructions, question, document, and room for the answer.
- Show how keep-the-start and keep-the-end truncation each lose a different part of a document.
- Build a planner that pins required sections, ranks the rest by relevance, packs them to fit, and reports every section it dropped.
:::

A student asks the school's help bot: "Can a part-time student borrow a laptop over the summer?" The right answer needs two pieces of the lending policy: the definition of an *eligible student* near the top, and the summer rules near the bottom. The whole policy doesn't fit in the model's window, so something gets cut. If the cut happens wherever the tokens run out, the bot answers confidently from half the rules.

Here's what you'll build: a planner that takes the policy, the question, and a window size, and returns a prompt that fits plus a report like this one.

```text
window 512 = instructions 83 + document 325 + answer reserve 100 + unused 4
kept    : 1. Definitions (pinned), 2. Borrowing, 3. Loan periods and renewals, 8. Summer loans
dropped : 4. Late returns, 5. Damage and loss, 6. Acceptable use, 7. Privacy and monitoring, 9. Graduation and withdrawal
```

We'll pretend the model has a 512-token window (the limit of BERT-style models) so the numbers stay readable. Current chat models allow 128,000 tokens or more, but a stack of handbooks fills that just as surely, and the arithmetic doesn't change.

## Step 1: The document and the question

The policy is a dictionary of sections, title to text. Keeping the structure is the first decision: a section is a unit of meaning, while a random 300-token slice is not.

## Step 2: Estimate tokens

Exact counts need the model's own tokenizer, and every model family has a different one. For planning, an estimate is enough as long as you know which way it leans. This one splits text into words and punctuation marks, counts short words as one token, and charges long words about one token per four letters, because subword tokenizers break rare long words into pieces.

```python run
import math
import re

PIECE = re.compile(r"\w+|[^\w\s]")

def piece_tokens(piece):
    return 1 if len(piece) <= 6 else math.ceil(len(piece) / 4)

def estimate_tokens(text):
    return sum(piece_tokens(p) for p in PIECE.findall(text))

def format_section(title, body):
    return f"## {title}\n{body}\n"

for title, body in POLICY.items():
    print(f"{title:30s} {estimate_tokens(format_section(title, body)):4d} tokens")

document = "\n".join(format_section(t, b) for t, b in POLICY.items())
print(f"\nwhole document: {estimate_tokens(document)} tokens, {len(document) / 4:.0f} by the 4-characters rule")
```

The two estimates agree within a few percent. When I ran this policy through real tokenizers (OpenAI's `tiktoken` with the GPT-2 and `o200k_base` encodings), they counted between 523 and 544 tokens for the policy, where this estimator says about 630, so it runs roughly 15 to 20 percent high. That's the safe direction: a budget built on an overestimate leaves spare room instead of overflowing.

:::note
For exact numbers in Colab, load the tokenizer of the model you'll actually call, such as `AutoTokenizer.from_pretrained("gpt2")` from Hugging Face `transformers`, and count with `len(tokenizer(text)["input_ids"])`. Hosted APIs also report the true counts in each response's usage field.
:::

## Step 3: Split the window into a budget

The window has to hold everything at once, and the answer is part of it. Forget to reserve room for the answer and the model gets cut off mid-sentence, or the API refuses the request.

```python run
WINDOW = 512
RESERVED_FOR_ANSWER = 100
FORMATTING = 20          # labels, blank lines, "QUESTION:" and so on

instructions = estimate_tokens(SYSTEM) + estimate_tokens(QUESTION) + FORMATTING
doc_budget = WINDOW - RESERVED_FOR_ANSWER - instructions
print("instructions + question:", instructions)
print("room for the document  :", doc_budget, "of", estimate_tokens(document), "needed")
```

Only about half of the policy fits. Now the question is which half.

## Step 4: Watch truncation drop the wrong part

The simplest fix is to cut the text when the tokens run out. Tools do this in two directions: tokenizers usually keep the start, and chat apps usually keep the most recent text, which is the end. Predict before you run: which section does each one lose that our question needs?

```python run
def truncate(text, max_tokens, keep="start"):
    pieces = list(PIECE.finditer(text))
    if keep == "end":
        pieces.reverse()
    used = 0
    for match in pieces:
        used += piece_tokens(match.group())
        if used > max_tokens:
            return text[:match.start()] if keep == "start" else text[match.end():]
    return text

for keep in ["start", "end"]:
    kept = truncate(document, doc_budget, keep)
    whole = [t.split(".")[0] for t in POLICY if format_section(t, POLICY[t]) in kept]
    print(f"keep the {keep:5s}: complete sections {whole}")
    print(f"   cut point: ...{kept[-50:]!r}" if keep == "start" else f"   cut point: {kept[:50]!r}...")
```

Keeping the start loses section 8, so the model never sees the summer rule. Keeping the end loses section 1, so the model reads "students without approved eligibility" without knowing that part-time students need a counselor's approval. Both prompts look fine, both answers can sound sure of themselves, and both cuts land mid-section. Nothing raised an error.

## Step 5: Pin, rank, and pack

A better planner makes three decisions on purpose:

1.  **Pin** what every answer depends on. Definitions change the meaning of every other section, so they always go in.
2.  **Rank** the rest by how much they share with the question. Here that's a plain word overlap; in Module 6 you'll swap in TF-IDF retrieval.
3.  **Pack** whole sections, best first, until the budget is full, and record every section that didn't make it.

```python run
STOP = set("a an the can over of to for is are be in on at and or with do does "
           "i my me we you what how".split())

def content_words(text):
    words = re.findall(r"[a-z]+", text.lower())
    return {w.rstrip("s") for w in words if w not in STOP and len(w) > 2}

def relevance(title, body, question):
    return len(content_words(question) & content_words(title + " " + body))

def pack(sections, question, budget, pinned):
    chosen, used = list(pinned), 0
    for title in pinned:
        used += estimate_tokens(format_section(title, sections[title]))
    if used > budget:
        raise ValueError(f"pinned sections need {used} tokens; the budget is {budget}")
    rest = [t for t in sections if t not in pinned]
    ranked = sorted(rest, key=lambda t: relevance(t, sections[t], question), reverse=True)
    dropped = []
    for title in ranked:
        cost = estimate_tokens(format_section(title, sections[title]))
        if relevance(title, sections[title], question) > 0 and used + cost <= budget:
            chosen.append(title)
            used += cost
        else:
            dropped.append(title)
    order = list(sections)
    return sorted(chosen, key=order.index), sorted(dropped, key=order.index), used

for title, body in POLICY.items():
    print(f"{relevance(title, body, QUESTION)}  {title}")
chosen, dropped, used = pack(POLICY, QUESTION, doc_budget, pinned=["1. Definitions"])
print("\nkept:", chosen)
print("used:", used, "of", doc_budget)
```

The planner kept Definitions, Borrowing, Loan periods, and Summer loans: exactly the sections a person would read to answer this question. Two details matter. A section with zero overlap is dropped even if there's room, since unrelated text costs tokens and can distract the model. And if the pinned sections alone are too big, `pack` raises a `ValueError` instead of quietly cutting the definitions.

## Step 6: Build the prompt and check the bill

The chosen sections go back in their original order, so the excerpt reads like the policy. The prompt also tells the model what was left out, which gives it a fair way to say "that isn't in the excerpt."

```python run
def build_prompt(sections, chosen, dropped, question, system):
    excerpt = "\n".join(format_section(t, sections[t]) for t in chosen)
    omitted = ", ".join(t.split(".")[0] for t in dropped) or "none"
    return (f"{system}\n\nPOLICY EXCERPT (omitted sections: {omitted})\n\n"
            f"{excerpt}\nQUESTION: {question}\nANSWER:")

prompt = build_prompt(POLICY, chosen, dropped, QUESTION, SYSTEM)
total = estimate_tokens(prompt)
print(prompt[:420], "...\n")
print(f"prompt {total} + answer reserve {RESERVED_FOR_ANSWER} = {total + RESERVED_FOR_ANSWER} of {WINDOW}")
assert total + RESERVED_FOR_ANSWER <= WINDOW
```

The `assert` is the line that turns "probably fits" into "checked." The chart compares this plan with pasting everything:

## The finished planner

Here is the planner as one function. It reuses `estimate_tokens`, `format_section`, `pack`, and `build_prompt` from the steps above; to save it as a script, paste those functions and the Step 1 data above it.

```python run title="context_planner.py"
def plan_context(sections, question, system, window=512, reserve=100, pinned=()):
    fixed = estimate_tokens(system) + estimate_tokens(question) + FORMATTING
    budget = window - reserve - fixed
    chosen, dropped, used = pack(sections, question, budget, list(pinned))
    prompt = build_prompt(sections, chosen, dropped, question, system)
    prompt_tokens = estimate_tokens(prompt)
    if prompt_tokens + reserve > window:
        raise ValueError(f"prompt needs {prompt_tokens} + {reserve} tokens; window is {window}")
    report = (f"window {window} = instructions {prompt_tokens - used} + document {used}"
              f" + answer reserve {reserve} + unused {window - prompt_tokens - reserve}\n"
              f"kept    : {', '.join(t + (' (pinned)' if t in pinned else '') for t in chosen)}\n"
              f"dropped : {', '.join(dropped) or 'nothing'}")
    return prompt, report

prompt, report = plan_context(POLICY, QUESTION, SYSTEM, pinned=["1. Definitions"])
print(report)
print()
_, report = plan_context(POLICY, "How much does a laptop repair cost after damage?", SYSTEM,
                         pinned=["1. Definitions"])
print(report)
```

The second question swaps Summer loans out and Damage and loss in, from the same code. The planner works per question, which is the idea that retrieval-augmented generation scales up.

:::quiz
Q: Why does the planner reserve 100 tokens for the answer instead of giving all leftover space to the document?
- [ ] The estimator is too inaccurate to use all the space
  The estimate leans high already; the reserve is for a different reason.
- [x] The answer is generated inside the same window, so it needs room too
  Input and output share the context window; with no reserve the answer can be cut short or the request rejected.
- [ ] Models refuse prompts that fill more than 80% of the window
  There's no such rule; the limit is the total of input and output tokens.

Q: The policy grows, and Definitions alone now costs more than the document budget. What does `pack` do?
- [ ] Truncates Definitions to fit
  That would recreate the silent-loss problem the planner exists to stop.
- [ ] Skips Definitions and packs other sections
  Pinned sections are never skipped; the answers depend on them.
- [x] Raises a `ValueError` saying how many tokens the pinned sections need
  Failing loudly forces a human decision: a bigger window, shorter definitions, or splitting the task.

Q: Why does the prompt list the omitted section numbers?
- [x] So the model can tell the user the excerpt doesn't cover something, instead of guessing
  A model told what's missing has an honest way to say "not in the provided excerpt."
- [ ] So the model can fetch the omitted sections itself
  A plain chat model can't fetch anything; it only reads the prompt.
- [ ] To make the prompt longer and more detailed
  Extra tokens are a cost, not a benefit; the list is there for honesty about coverage.
:::

:::takeaways
- Estimate tokens with a method that leans high, and check it against a real tokenizer once.
- A context budget is window = instructions + question + document + answer reserve.
- Truncation cuts wherever tokens run out, often mid-section, with no warning; which end it keeps decides what you lose.
- Pin what every answer depends on, rank the rest against the question, pack whole sections, and report what you dropped.
- Fail loudly when the pinned content alone won't fit.
:::

## Ideas to extend it

-   Pack by value per token: divide relevance by cost so short, relevant sections beat long, slightly relevant ones.
-   Split oversized sections into paragraphs before packing, keeping the section title on each piece.
-   Add a "keep the last N chat turns" mode and check that a pinned rule survives a long conversation.
