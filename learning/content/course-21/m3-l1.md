A small online shop routes its support email with one rule: if the message contains *card*, send it to Billing. It works for a few days. Then "The app crashes when I open the gift card screen" lands in Billing, and so does "My birthday card arrived torn". Single keywords fail in both directions: they match words that mean something else here, and they miss messages that say the same thing in different words, like *money back* instead of *refund*.

This module replaces the keyword with two tools. **Similarity** finds past tickets that look like a new one. **Classification** learns a label from many examples instead of one word.

## Cosine similarity compares direction, not size

Two texts about the same thing use the same words in roughly the same proportions. A long complaint about a double charge and a short one point the same way in word-count space; the long one is just further out. So instead of measuring the distance between the two points, measure the angle between the vectors. That's **cosine similarity**:

cos(a, b) = (a · b) / (‖a‖ ‖b‖)

The dot product a · b adds up the products of matching counts, so it's large when both texts use the same words. Dividing by the two lengths removes the effect of text length. For count or TF-IDF vectors, which have no negative entries, the result runs from 0 (no words in common) to 1 (identical proportions).

```python run
import numpy as np
from sklearn.feature_extraction.text import CountVectorizer

def cosine(a, b):
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

texts = ["refund my card charge", "refund my card charge refund my card charge", "my parcel is late"]
X = CountVectorizer().fit_transform(texts).toarray()
print(X)
print("short vs doubled: cosine", round(cosine(X[0], X[1]), 3), " distance", round(np.linalg.norm(X[0] - X[1]), 3))
print("short vs parcel:  cosine", round(cosine(X[0], X[2]), 3), " distance", round(np.linalg.norm(X[0] - X[2]), 3))
```

The doubled text has cosine 1.0 with the original: same direction, same meaning. Straight-line distance puts it 2.0 away, nearly as far as the unrelated parcel message (2.449). Distance punishes length; cosine ignores it. The 0.25 between the card text and the parcel text comes entirely from the shared word *my*, which is why stop words and TF-IDF weighting matter for search.

## Search is ranking documents by similarity to the query

Here are 18 past tickets with the team's labels. To search them, fit a TF-IDF vectorizer on the tickets once, turn each query into a vector with the **same** vectorizer, and rank tickets by cosine similarity.

```python run
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

tickets = [
    ("refund my double charge", "billing"),
    ("charged twice for one order", "billing"),
    ("my card was billed the wrong amount", "billing"),
    ("the discount was not applied to my payment", "billing"),
    ("cancel the subscription payment", "billing"),
    ("invoice shows the wrong price", "billing"),
    ("parcel has not arrived", "shipping"),
    ("tracking says delivered but no package", "shipping"),
    ("the box arrived damaged", "shipping"),
    ("wrong item in my delivery", "shipping"),
    ("courier lost my parcel", "shipping"),
    ("change the delivery address", "shipping"),
    ("app crashes on startup", "technical"),
    ("checkout page will not load", "technical"),
    ("website shows an error when I search", "technical"),
    ("images do not load in the app", "technical"),
    ("the app logs me out", "technical"),
    ("search returns no results", "technical"),
]
texts = [text for text, label in tickets]
labels = [label for text, label in tickets]

vectorizer = TfidfVectorizer()
ticket_vectors = vectorizer.fit_transform(texts)

def search(query, k=3):
    scores = cosine_similarity(vectorizer.transform([query]), ticket_vectors)[0]
    print(repr(query))
    hits = [i for i in scores.argsort()[::-1][:k] if scores[i] > 0]
    for i in hits:
        print(f"   {scores[i]:.2f}  [{labels[i]}] {texts[i]}")
    if not hits:
        print("   no ticket shares a word with this query")

search("my parcel arrived damaged")
search("the app will not load")
search("money back please")
```

The first two queries work well, and their top matches all carry the right label, which hints at the next idea: a new ticket probably deserves the label of the tickets it most resembles. The third query shows the limit of word overlap. *money back* means *refund*, but no ticket shares a single word with it, so every score is 0. Fixing that takes vectors that place *refund* near *money back*: sentence embeddings from a transformer, which Module 6 compares with TF-IDF for retrieval.

## Naive Bayes: which class makes these words most likely?

**Multinomial naive Bayes** imagines that each class writes tickets by drawing words from its own bag. Billing's bag is full of *refund*, *charge*, and *invoice*; Shipping's has *parcel*, *late*, and *courier*. To label a new ticket, ask which bag was most likely to produce its words:

score(class) = log P(class) + Σ log P(word | class)

The probabilities come from counting words in each class's training tickets. Logs turn a product of many small probabilities into a sum, which avoids numbers too small for the computer to store. The "naive" part is treating each word as independent of the others, which is false (*double* and *charge* go together) but works well enough to have filtered spam for decades.

:::trace Watch naive Bayes add up the evidence for each class
```python
log_prior = {"billing": -1.10, "shipping": -1.10}
log_likelihood = {
    "billing": {"refund": -1.61, "late": -3.22, "parcel": -3.22},
    "shipping": {"refund": -3.00, "late": -1.90, "parcel": -1.39},
}
message = ["refund", "late", "parcel"]
scores = {}
for label in log_prior:
    score = log_prior[label]
    for word in message:
        score += log_likelihood[label][word]
    scores[label] = round(score, 2)
print(max(scores, key=scores.get), scores)
```
:::

*refund* pushes strongly toward billing (−1.61 against −3.00), but *late* and *parcel* push harder toward shipping, so shipping wins. A word that never appeared in a class's training tickets would get probability 0 and a log of minus infinity, vetoing that class outright. Naive Bayes avoids that with **smoothing**: `MultinomialNB(alpha=1.0)` adds one imaginary occurrence of every word to every class.

## Logistic regression: learn a weight for every word

**Logistic regression** takes the other route. It gives every word a weight for each class and adds up weight × TF-IDF value, plus a bias, to get a score per class. A softmax turns the scores into probabilities. Training adjusts the weights to make the correct labels as probable as possible, so the model learns which words matter instead of counting them.

Train both in pipelines and test them on seven tickets neither has seen:

```python run
from sklearn.linear_model import LogisticRegression
from sklearn.naive_bayes import MultinomialNB
from sklearn.pipeline import make_pipeline

test = [
    ("please refund the extra charge on my card", "billing"),
    ("my payment went through twice", "billing"),
    ("I was charged for a parcel that never arrived", "billing"),
    ("where is my parcel", "shipping"),
    ("package arrived crushed", "shipping"),
    ("the page crashes at checkout", "technical"),
    ("the app freezes when I pay", "technical"),
]
test_texts = [text for text, label in test]
test_labels = [label for text, label in test]

nb = make_pipeline(CountVectorizer(), MultinomialNB(alpha=1.0)).fit(texts, labels)
lr = make_pipeline(TfidfVectorizer(), LogisticRegression()).fit(texts, labels)

for name, model in [("naive Bayes", nb), ("logistic regression", lr)]:
    predicted = model.predict(test_texts)
    print(name)
    for text, truth, guess in zip(test_texts, test_labels, predicted):
        print(f"   {'ok   ' if truth == guess else 'WRONG'} {guess:10} {text}")
```

A pipeline bundles the vectorizer and the classifier, so `fit` learns the vocabulary from the training tickets only and `predict` reuses it, which rules out the fit-on-the-query mistake from Module 2. Both models miss the same ticket, and it's a fair miss: "charged for a parcel that never arrived" is a billing complaint about a shipping problem.

Logistic regression's weights tell you what it learned, and its probabilities tell you how sure it was:

```python run
vec, clf = lr[0], lr[-1]
words = vec.get_feature_names_out()
for k, label in enumerate(clf.classes_):
    top = clf.coef_[k].argsort()[::-1][:4]
    print(f"{label:10}", [words[i] for i in top])

probs = lr.predict_proba(["I was charged for a parcel that never arrived"])[0]
print({str(label): round(float(p), 2) for label, p in zip(clf.classes_, probs)})
```

The top words look sensible, apart from *was* sitting near the top for billing: with 18 training tickets, the model picks up accidents of phrasing as well as real signal. And it was nearly a coin flip between billing and shipping on the misclassified ticket. A low top probability is a useful signal: in the next lesson, low-confidence tickets go to a human.

## Evaluate on tickets the model never saw

Scoring a model on its own training tickets measures memory, not skill. Hold out a test set, predict it, and compare. **Accuracy** is the share correct. It hides *which* mistakes happen, so also read the **confusion matrix**, with one row per true label and one column per predicted label:

```python run
from sklearn.metrics import classification_report, confusion_matrix

predicted = lr.predict(test_texts)
classes = ["billing", "shipping", "technical"]
print(confusion_matrix(test_labels, predicted, labels=classes))
print(classification_report(test_labels, predicted, zero_division=0))
```

The diagonal counts correct answers. The 1 in row *billing*, column *shipping* is the misread ticket. From the matrix come two numbers per class:

- **Precision**: of the tickets predicted *shipping*, what share really were? 2 of 3, so 0.67.
- **Recall**: of the real *billing* tickets, what share were found? 2 of 3, so 0.67.

F1 is their harmonic mean. *Macro avg* averages the classes equally; *weighted avg* weights them by how many test tickets each has. With seven test tickets, one mistake moves accuracy by 14 points, so treat these numbers as rough. The Practice lesson uses cross-validation to get steadier ones.

:::warning
**Accuracy on unbalanced classes.** If 90 of 100 tickets are billing, a "model" that always says *billing* scores 90% accuracy and never finds a single shipping problem. Always compare against that baseline (scikit-learn's `DummyClassifier(strategy="most_frequent")` computes it), and read recall for the small classes.
:::

:::warning
**Letting the test set leak into training.** Calling `TfidfVectorizer().fit_transform(all_texts)` before splitting lets the test tickets shape the vocabulary and the idf weights. Worse is a duplicated ticket that lands on both sides of the split, which the model "predicts" by memory. Split first, keep the vectorizer inside a pipeline, and remove exact duplicates before splitting.
:::

:::quiz
Q: Ticket A is "refund my order" and ticket B is the same three words repeated five times. What is their cosine similarity on count vectors?
- [ ] 0.2, because B is five times longer
  Cosine divides by both lengths, so length cancels out.
- [x] 1.0
  B's vector is A's times five: same direction, so the angle is zero.
- [ ] It depends on the idf weights
  These are plain count vectors, and even with idf, scaling every count by 5 keeps the direction.

Q: In naive Bayes, the word *invoice* never appeared in any shipping ticket. Without smoothing, what happens when a new ticket contains *invoice*?
- [ ] Shipping's score goes up slightly
  An unseen word lowers a class's score; it never raises it.
- [x] P(invoice | shipping) is 0, so shipping's log score is minus infinity and shipping can't win
  One unseen word vetoes the class. `alpha=1.0` adds pseudo-counts to prevent this.
- [ ] The word is ignored
  scikit-learn ignores words missing from the whole vocabulary, but *invoice* is in it (from billing tickets).

Q: A classifier gets 95% accuracy on a test set where 95% of tickets are billing. What should you check before celebrating?
- [ ] The training accuracy
  Training accuracy says nothing about how the minority classes are handled.
- [x] Recall for the non-billing classes, compared with an always-billing baseline
  Always predicting billing scores 95% too. Per-class recall shows whether the model finds anything else.
- [ ] Whether the vectorizer used bigrams
  That's a modelling choice, not a check on whether the accuracy is meaningful.

Q: Why fit the vectorizer inside a pipeline instead of on all the tickets first?
- [x] So the vocabulary and idf weights come only from training tickets, and the test set stays unseen
  Otherwise the test set influences the features, and the score is optimistic.
- [ ] Pipelines run faster
  Speed isn't the reason; the order of fitting is.
- [ ] `LogisticRegression` refuses sparse matrices outside a pipeline
  It accepts sparse input either way.
:::

:::takeaways
- Cosine similarity compares the direction of two vectors, so it ignores text length. For count and TF-IDF vectors it runs from 0 to 1.
- Search = fit a vectorizer on the documents, `transform` the query, rank by cosine. Word-overlap search can't match synonyms.
- Naive Bayes adds log probabilities of each word under each class; smoothing stops unseen words from vetoing a class.
- Logistic regression learns a weight per word per class; its coefficients show what it learned, and `predict_proba` shows how sure it is.
- Evaluate on held-out text. Read the confusion matrix and per-class precision and recall, and compare accuracy against the most-frequent-class baseline.
:::
