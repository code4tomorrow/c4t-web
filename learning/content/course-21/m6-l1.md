You ask a model to answer from the lending policy and reply with JSON containing `answer`, `citations`, and `answerable`. This comes back:

```text
Sure! Here's the JSON you asked for:
{"Answer": "Yes, part-time students can borrow laptops all summer.", "citations": ["Student Handbook p. 14"]}
```

Count the failures. There's chatter before the JSON, so a parser chokes. The key is `Answer`, not `answer`. The `answerable` field is missing. The citation names a handbook page nobody retrieved. And the answer is wrong: part-time students need a counselor's approval. Every one of these has a fix you can write in code: a better prompt, a schema, retrieval, and a citation check.

## A prompt has parts, so build it like code

Chat models take a list of **messages**, each with a role. The `system` message holds rules that apply to the whole conversation. `user` messages carry the task and the data. `assistant` messages are the model's replies, and you can write some yourself to show the model examples.

A reliable prompt usually has the same pieces: what the model is for, the rules, the context it may use, examples, the output format, and finally the input. Building it with a function means every request follows the same template, and you can test and version that template like any other code.

```python run
import json

SOURCES = {
    "S1": "An eligible student is enrolled full-time. Part-time students are eligible "
          "only with written approval from a counselor.",
    "S2": "Eligible students taking summer classes can request a summer loan in May.",
    "S3": "Laptops and tablets are loaned for 14 days and can be renewed twice online.",
}

SYSTEM = (
    "You answer questions about the Riverside High device lending policy.\n"
    "Rules:\n"
    "- Use only the text inside <source> tags.\n"
    "- Cite the id of every source you used.\n"
    "- If the sources do not answer the question, set answerable to false.\n"
    "Reply with JSON only, with keys: answer (string), citations (list of source ids), "
    "answerable (true or false)."
)

def build_messages(question, sources, examples=()):
    context = "\n".join(f'<source id="{sid}">{text}</source>' for sid, text in sources.items())
    messages = [{"role": "system", "content": SYSTEM}]
    for example_input, example_reply in examples:
        messages.append({"role": "user", "content": example_input})
        messages.append({"role": "assistant", "content": example_reply})
    messages.append({"role": "user", "content": f"{context}\n\nQuestion: {question}"})
    return messages

question = "Can a part-time student borrow a laptop over the summer?"
for message in build_messages(question, SOURCES):
    print(f"[{message['role']}]\n{message['content']}\n")
```

The `<source id="...">` tags matter more than they look. They separate *your* instructions from *document* text, give each source an id the model can cite, and make it harder for a sentence inside a document to pass itself off as an instruction. Any clear delimiter works; XML-style tags are a common choice because models have seen many of them.

## Few-shot examples teach the format and the edge cases

A **zero-shot** prompt only describes what you want. A **few-shot** prompt also shows it: a handful of example inputs, each followed by the exact reply you'd want. Examples beat descriptions at pinning down format, and they're the best way to teach the case models get wrong most often, which here is admitting the sources don't say.

```python run
EXAMPLES = [
    ('<source id="S1">Calculators are loaned for the full semester.</source>\n\n'
     "Question: How long can I keep a calculator?",
     '{"answer": "For the full semester.", "citations": ["S1"], "answerable": true}'),
    ('<source id="S1">Late devices are charged 1 dollar per school day.</source>\n\n'
     "Question: Can I borrow a projector?",
     '{"answer": "The sources do not say.", "citations": [], "answerable": false}'),
]

messages = build_messages(question, SOURCES, EXAMPLES)
print(" -> ".join(m["role"] for m in messages))
```

Two examples, one answerable and one not. If both were answerable, you'd be quietly teaching the model that the answer is always yes. Keep examples short, make them cover different cases, and don't reuse the real question's sources in them, or the model may copy an example's answer.

## A schema is a contract you can check

A **JSON Schema** says exactly what valid output looks like: which keys, which types, which are required, and whether extra keys are allowed. First, though, the reply has to parse:

```python run raises
reply = '''Sure! Here's the JSON you asked for:
{"Answer": "Yes, part-time students can borrow laptops all summer.", "citations": ["Student Handbook p. 14"]}'''
json.loads(reply)
```

"Expecting value: line 1 column 1" means the parser hit `S` where JSON should start. Cutting from the first `{` to the last `}` gets past the chatter, and then the schema reports every remaining problem at once:

```python run
from jsonschema import Draft202012Validator

SCHEMA = {
    "type": "object",
    "properties": {
        "answer": {"type": "string", "minLength": 1},
        "citations": {"type": "array", "items": {"type": "string", "pattern": "^S[0-9]+$"}},
        "answerable": {"type": "boolean"},
    },
    "required": ["answer", "citations", "answerable"],
    "additionalProperties": False,
}

data = json.loads(reply[reply.find("{"): reply.rfind("}") + 1])
validator = Draft202012Validator(SCHEMA)
for error in validator.iter_errors(data):
    where = "/".join(map(str, error.path)) or "(top level)"
    print(f"{where}: {error.message}")
```

Four errors covering three failures: the wrong key name (reported twice, as a missing `answer` and an unexpected `Answer`), the missing `answerable`, and a citation that isn't a source id. The extraction handled the chatter. The wrong answer sails through. In Python code, **Pydantic** expresses the same contract as a class, and validation gives you a typed object you can use with attribute access:

```python run
from pydantic import BaseModel, ConfigDict, ValidationError

class GroundedAnswer(BaseModel):
    model_config = ConfigDict(extra="forbid")
    answer: str
    citations: list[str]
    answerable: bool

try:
    GroundedAnswer.model_validate(data)
except ValidationError as err:
    for problem in err.errors():
        print(problem["loc"], problem["msg"])

good = GroundedAnswer.model_validate_json(
    '{"answer": "Only with written approval from a counselor; approved students taking '
    'summer classes can request a summer loan in May.", "citations": ["S1", "S2"], '
    '"answerable": true}')
print(good.answerable, good.citations)
```

Many APIs can now enforce a schema while the model writes, called **structured outputs**: OpenAI's `response_format` with a JSON Schema, Gemini's response schema, and Ollama's `format` parameter. When it's supported, the reply always parses and has the right keys. Keep validating anyway: support for schema features varies by provider and model, and a perfectly shaped answer can still be false.

## Retrieval puts the facts in the prompt

A model only knows what was in its training data, which stops at a cutoff date and never included your school's policy. **Retrieval-augmented generation** fixes that at question time: find the passages most related to the question, put them in the prompt as numbered sources, and tell the model to answer only from them.

```mermaid caption="Retrieval-augmented generation, with checks before the answer reaches anyone"
flowchart LR
    D[Documents] --> C[Split into chunks]
    C --> I[(Index)]
    Q[Question] --> R[Retrieve top k chunks]
    I --> R
    R --> P["Prompt: rules + sources + question"]
    P --> M[Model]
    M --> V{"Valid JSON? Real citations?"}
    V -->|yes| A[Answer with sources]
    V -->|no| X[Retry or say it can't answer]
```

**Chunking** decides what the retriever can find. Split along the document's own structure (sections, then paragraphs) so each chunk is about one thing. Chunks that are too small lose context ("it must be returned within five days": *what* must?). Chunks that are too big mix topics, which blurs the match and spends your token budget. Many systems also let neighboring chunks **overlap** by a sentence or two so a fact that straddles a boundary survives whole. **Retrieval** can use the TF-IDF vectors you built in Module 2, dense embeddings, or both. Next lesson you'll build the TF-IDF version end to end.

## Citations you can verify

Retrieval gives you something prompting alone can't: a list of what the model was shown. That makes the invented-source failure checkable in one line.

```python run
def citation_problems(result, retrieved_ids):
    problems = []
    unknown = [c for c in result.citations if c not in retrieved_ids]
    if unknown:
        problems.append(f"cites sources that were never retrieved: {unknown}")
    if result.answerable and not result.citations:
        problems.append("claims an answer but cites nothing")
    return problems

invented = GroundedAnswer(answer="Yes, all summer.", citations=["S2", "S7"], answerable=True)
print("good    :", citation_problems(good, set(SOURCES)) or "ok")
print("invented:", citation_problems(invented, set(SOURCES)))
```

A real id doesn't prove the source *supports* the sentence, only that it exists. Module 7 adds that second check.

## Sending it to a real model

This cell runs in Colab, not on this page. It uses the `openai` Python package, which also talks to Google's Gemini API (free tier) and to Ollama on your own computer, because both offer OpenAI-compatible endpoints.

:::note
**One-time setup for Gemini.** Create a key at [Google AI Studio](https://aistudio.google.com/apikey). In Colab, open **Secrets** (the key icon), add a secret named `GEMINI_API_KEY`, and switch on **Notebook access**. **Using Ollama instead?** Install it from ollama.com, run `ollama pull llama3.2`, and create the client with `OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")` and `model="llama3.2"`. Model names change often, so check your provider's model list if one is rejected.
:::

```python
from google.colab import userdata
from openai import OpenAI

client = OpenAI(
    api_key=userdata.get("GEMINI_API_KEY"),
    base_url="https://generativelanguage.googleapis.com/v1beta/openai/",
)

completion = client.beta.chat.completions.parse(
    model="gemini-3.5-flash-lite",
    messages=build_messages(question, SOURCES, EXAMPLES),
    response_format=GroundedAnswer,      # the Pydantic class from above
)
result = completion.choices[0].message.parsed
print(result)
print(citation_problems(result, set(SOURCES)) or "citations ok")
```

`parse` turns the Pydantic class into a JSON Schema, sends it as the response format, and hands back a validated `GroundedAnswer`. Text you send to a hosted API leaves your computer, so use only non-sensitive documents with it.

:::warning
**Calling `json.loads` on the raw reply.** Models often wrap JSON in a sentence or in a Markdown code fence, and you get `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`. Use structured outputs when the API has them; otherwise extract from the first `{` to the last `}` and validate.

**Treating "valid" as "correct."** A schema checks shape. `{"answer": "Yes", "citations": ["S1"], "answerable": true}` passes every check on this page and is still the wrong answer to the summer question.
:::

:::quiz
Q: Your few-shot prompt has four examples, and all four are answerable questions with "yes" answers. What risk does that add?
- [ ] The prompt gets too long to fit
  Four short examples cost little; the problem is what they teach.
- [x] The model learns that the expected answer is "yes" and rarely sets `answerable` to false
  Examples teach patterns, including accidental ones. Cover the unanswerable case on purpose.
- [ ] The model will refuse to answer
  Nothing in these examples models a refusal; if anything they push the other way.

Q: Which problem in a reply would a JSON Schema with `"required"` and `"additionalProperties": false` catch?
- [x] The key is `Answer` instead of `answer`
  `answer` is reported missing and `Answer` is reported as an unexpected extra key.
- [ ] The answer contradicts source S1
  A schema checks structure and types, not whether the content is true.
- [ ] The citation `S2` exists but doesn't support the sentence
  `S2` matches the pattern; checking support needs a different test.

Q: The retriever returned S1, S2, and S3. The reply cites `["S2", "S9"]`. What should the system do?
- [ ] Accept it, since S2 is real
  One invented citation means you can't trust which claims came from where.
- [x] Flag it: S9 was never retrieved, so the model invented a source
  The model can only legitimately cite what it was shown; anything else is fabricated.
- [ ] Look for a document called S9 and add it to the sources
  Ids are labels you assigned in this prompt; S9 doesn't refer to anything.

Q: You split a policy into chunks of 15 words each. What is the most likely problem?
- [ ] Too many tokens per request
  Small chunks are cheap; the trouble is what each one means on its own.
- [x] Chunks lose context, like "it must be returned in five days" with no clue what "it" is
  Tiny chunks cut facts away from the words that make them meaningful.
- [ ] TF-IDF can't index short text
  TF-IDF works on short text; it just has less to match on.
:::

:::takeaways
- Build prompts with a function: system rules, delimited sources with ids, few-shot examples, then the question.
- Few-shot examples should cover different cases, including the one where the sources don't answer.
- Validate every reply against a schema (JSON Schema or Pydantic), even when the API enforces one.
- RAG retrieves relevant chunks at question time and puts them in the prompt; chunking by structure decides what can be found.
- Check that citations are a subset of what was retrieved. A schema-valid, well-cited answer can still be wrong, so test support next.
:::
