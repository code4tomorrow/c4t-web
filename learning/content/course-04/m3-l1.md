This report generator prints the right totals for every active team, and then gets the one thing you actually wanted wrong:

```python run title="league_report.py"
teams = [
    {"name": "Hawks", "active": True, "players": [
        {"name": "Ana", "games": 3, "points": 21},
        {"name": "Raj", "games": 0, "points": 0},
    ]},
    {"name": "Owls", "active": False, "players": [
        {"name": "Kim", "games": 2, "points": 9},
    ]},
    {"name": "Foxes", "active": True, "players": [
        {"name": "Tom", "games": 4, "points": 30},
        {"name": "Zoe", "games": 2, "points": 12},
    ]},
]


def report(teams):
    for team in teams:
        if team["active"]:
            total = 0
            for player in team["players"]:
                if player["games"] > 0:
                    total = total + player["points"]
            print(team["name"], total)


best = report(teams)
print("Best team:", best)
```

"Best team: None." Two separate things went wrong. The function **prints** its results instead of handing them back, so the caller receives nothing. And the logic that matters is buried four indents deep, which makes it hard to see where a "best team" calculation would even go. This lesson fixes both.

## Read nested code from the inside out

Deeply nested code is easiest to understand starting from the innermost line and working outward. In `report`:

-   The innermost `if` decides which **players** count: only those who played a game.
-   The player loop adds those players' points into `total`.
-   The `if team["active"]` decides which **teams** get a total at all.
-   The outer loop repeats all of that once per team.

Notice that `total = 0` sits inside the team loop, so every team starts from zero. Step through a smaller version and watch it reset. The players here are `(games, points)` tuples to keep the trace short:

:::trace Watch `total` reset for each team, and the Owls get skipped
```python
teams = [
    {"name": "Hawks", "active": True, "players": [(3, 21), (0, 0)]},
    {"name": "Owls", "active": False, "players": [(2, 9)]},
    {"name": "Foxes", "active": True, "players": [(4, 30), (2, 12)]},
]
for team in teams:
    if team["active"]:
        total = 0
        for games, points in team["players"]:
            if games > 0:
                total = total + points
        print(team["name"], total)
```
:::

For the Owls, the `if` is false, so the whole inner block is skipped and nothing prints. Every extra level of nesting is another condition you have to hold in your head while reading the lines below it.

## Guard clauses: deal with the exceptions first

A **guard clause** checks for a case you *don't* want to handle and gets out early. In a loop, `continue` skips to the next item. In a function, `return` leaves right away. The main work then sits at the left margin instead of at the bottom of a staircase.

Compare two versions of the same ticket-price rule:

```python run title="tickets.py"
def price_nested(age, is_member):
    if age >= 0:
        if age >= 5:
            if is_member:
                return 6
            else:
                return 10
        else:
            return 0
    else:
        return None


def price_guarded(age, is_member):
    if age < 0:
        return None
    if age < 5:
        return 0
    if is_member:
        return 6
    return 10


for age, member in [(-1, False), (3, False), (15, True), (15, False)]:
    print(age, member, price_nested(age, member), price_guarded(age, member))
```

Both give identical answers, but the guarded one reads like the rule you'd say out loud: "Negative ages are invalid. Under-fives are free. Members pay 6. Everyone else pays 10." Each special case is handled and forgotten, one line at a time.

The same idea flattens the team loop:

```python run title="guarded_loop.py"
teams = [
    {"name": "Hawks", "active": True, "players": [(3, 21), (0, 0)]},
    {"name": "Owls", "active": False, "players": [(2, 9)]},
]

for team in teams:
    if not team["active"]:
        continue
    total = 0
    for games, points in team["players"]:
        if games == 0:
            continue
        total = total + points
    print(team["name"], total)
```

To write a guard, flip the condition: `if team["active"]:` becomes `if not team["active"]: continue`.

## Return the answer, and let the caller decide what to print

`print` shows a value to a person, and then the value is gone. `return` hands the value back to the code that called the function, which can store it, compare it, sort by it, or print it. A function with no `return` statement still returns something: `None`. That's what `best` received in the opening example.

```python run title="print_vs_return.py"
def total_printed(points):
    print(sum(points))


def total_returned(points):
    return sum(points)


a = total_printed([21, 0])
b = total_returned([21, 0])
print("a is", a)
print("b is", b)
print("b doubled is", b * 2)
```

`total_printed` displays 21, but `a` is `None`, so `a * 2` would crash with `TypeError`. `b` is a real number you can keep working with. A useful rule: functions that **calculate** should return; only a few functions near the top of the program should **talk** to the user with `print` and `input`.

A function can return several values at once by returning a tuple, which the caller unpacks:

```python run title="min_max.py"
def lowest_and_highest(scores):
    return min(scores), max(scores)


low, high = lowest_and_highest([72, 95, 58, 88])
print(f"Range: {low} to {high}")
```

## Small functions with one job each

Now rebuild the report from small pieces. Each function has a name that says what it gives back, takes everything it needs as parameters, and returns its answer:

```python run title="league_report_v2.py"
teams = [
    {"name": "Hawks", "active": True, "players": [(3, 21), (0, 0)]},
    {"name": "Owls", "active": False, "players": [(2, 9)]},
    {"name": "Foxes", "active": True, "players": [(4, 30), (2, 12)]},
]


def team_total(team):
    return sum(points for games, points in team["players"] if games > 0)


def active_totals(teams):
    return {team["name"]: team_total(team) for team in teams if team["active"]}


def best_team(totals):
    name = max(totals, key=totals.get)
    return name, totals[name]


def format_row(name, total):
    return f"{name:<8}{total:>4}"


totals = active_totals(teams)
for name, total in totals.items():
    print(format_row(name, total))
name, total = best_team(totals)
print("Best team:", name, "with", total)

assert team_total(teams[0]) == 21
assert best_team({"A": 1, "B": 5}) == ("B", 5)
print("checks passed")
```

Look at what small functions buy you. `team_total` is one line you can check by eye. (The `sum(points for ... if ...)` inside it is a comprehension without the square brackets; it feeds each value straight into `sum` instead of building a list first.) Each piece can be tested on its own with `assert`, which does nothing when the claim is true and crashes loudly when it's false. And `best_team` was easy to add, because the totals now exist as a value instead of scrolling past on the screen.

## Where variables live: scope

A variable created inside a function is **local**: it exists only while that call is running, and the caller can't see it. A variable created at the top level of the file is **global**, and functions can read it. The trap is *assigning* to a global name inside a function:

```python run raises title="scope_bug.py"
count = 0


def add_point():
    count = count + 1


add_point()
```

Because `add_point` assigns to `count`, Python decides that `count` is local for the **whole** function. So when the right-hand side tries to read `count`, the local one doesn't exist yet. The fix is the same habit as before: pass values in and return results out.

```python run title="scope_fixed.py"
def add_point(count):
    return count + 1


count = 0
count = add_point(count)
count = add_point(count)
print(count)
```

Python does have a `global` statement that lets a function reassign a global, but code built on it is hard to test and hard to follow, because any function might be changing any variable. Parameters and return values keep each function's inputs and outputs in plain sight.

:::warning
**A `return` in the wrong place ends the loop early.** This checker is meant to report whether *any* score is failing:

```python
def has_failing(scores):
    for score in scores:
        if score < 60:
            return True
        else:
            return False
```

`has_failing([80, 45])` returns `False`, because the `else` returns on the very first score. A function can only conclude "none of them" after checking all of them, so the `return False` belongs **after** the loop, unindented.
:::

:::warning
**Reading a local from outside.** After `team_total(team)` runs, writing `print(total)` at the top level gives `NameError: name 'total' is not defined` if `total` was only created inside a function. Capture the result instead: `total = team_total(team)`.
:::

:::quiz
Q: What does this print? `def shout(word): print(word.upper())` then `x = shout("hi")` then `print(x)`
- [ ] `HI` then `HI`
  The function prints once, but it never returns the text, so `x` can't hold it.
- [x] `HI` then `None`
  Calling `shout` prints `HI`. With no `return`, the call's value is `None`, which is then printed.
- [ ] Just `None`
  The `print` inside the function still runs when it's called.

Q: Which line is a guard clause?
- [x] `if not scores: return 0` at the top of a function
  It handles a special case (an empty list) and leaves, so the rest of the function can assume there are scores.
- [ ] `total = total + score` inside a loop
  That's the main work, not a check that leaves early.
- [ ] `return total` at the end of a function
  Returning at the end is normal; a guard returns early on a special case.

Q: Why does `count = count + 1` inside a function crash with `UnboundLocalError` when `count` exists globally?
- [ ] Functions can't see global variables at all
  They can read them. The problem only starts when the function also assigns to the name.
- [x] Assigning to `count` makes it local for the whole function, so reading it first fails
  Python decides scope before the function runs. A local `count` has no value yet when the right side needs it.
- [ ] Integers can't be changed
  Rebinding a name to a new integer is fine; this is about which `count` the name refers to.

Q: A function `team_report(team)` calculates a total and prints a formatted line. What's the best way to split it?
- [ ] Keep it as one function and add a `return` after the `print`
  It still mixes calculating and displaying, so you can't reuse the total without printing.
- [x] `team_total(team)` returns the number; `format_row(name, total)` returns the line; the caller prints it
  Each piece has one job, can be tested with `assert`, and can be reused elsewhere.
- [ ] Make `total` a global so other functions can read it
  Globals hide where values come from. Return values make the data flow visible.
:::

:::takeaways
- Read nested code from the innermost line outward; each level adds a condition to keep in mind.
- Guard clauses (`continue`, early `return`) handle special cases first and keep the main path flat.
- `print` shows a value and loses it; `return` hands it back. No `return` means the call gives `None`.
- Functions that calculate should return; leave printing and input to a few functions at the top.
- Assigning to a name inside a function makes it local everywhere in that function. Pass values in and return them out.
:::
