:::objectives
- Locate a crash from its traceback and decide where the fix belongs.
- Find silent bugs (wrong output, no crash) with targeted `print(f"{x=}")` evidence.
- Swap debug prints for `logging` and control them with a level.
- Use a conditional breakpoint or an `assert` to find the first moment data goes wrong.
- Recognize two shared-object bugs: the mutable default argument and the shallow copy.
:::

Every exercise here contains a real bug. Before you open a hint, write one sentence: "I think the bug is ___ because ___." Then gather evidence for or against it. Being wrong is fine; guessing without testing is the habit to break.

## Warm-up: what does each print show?

Predict both lines before you look.

```python run
answer = "Yes\n"
count = 3.0
print(answer, count)
print(f"{answer=} {count=}")
```

The first `print` hides a newline: `3.0` lands on the next line and nothing says why. It also doesn't tell you whether `3.0` is a number or text. The second shows `'Yes\n'`, so `answer == "Yes"` would be `False`, and it confirms `count` is a float. Two bugs found before reading any other code.

### Exercise 1: The report that crashes in the middle

Read the traceback and answer three questions before fixing anything: which line raised the error, which piece of data caused it, and where the fix should go. Then make Period 2 print `Period 2: no scores yet` while the other periods still print their averages.

```python run raises title="class_report.py"
def average(scores):
    return sum(scores) / len(scores)


def class_report(classes):
    for name, scores in classes.items():
        print(f"{name}: {average(scores):.1f}")


class_report({"Period 1": [88, 92, 75], "Period 2": [], "Period 3": [90]})
```

:::hint
The lowest frame is inside `average`, but `average` has no way to print "no scores yet". Which function knows the period's name?
:::

:::solution
The error is raised on line 2 (`sum(scores) / len(scores)`), the data is Period 2's empty list, and `Period 1: 85.0` printed first, which proves the loop got one period in. Dividing by `len([])` is dividing by zero.

```python run title="class_report.py"
def average(scores):
    if not scores:
        return None
    return sum(scores) / len(scores)


def class_report(classes):
    for name, scores in classes.items():
        result = average(scores)
        if result is None:
            print(f"{name}: no scores yet")
        else:
            print(f"{name}: {result:.1f}")


class_report({"Period 1": [88, 92, 75], "Period 2": [], "Period 3": [90]})
```

`average` reports "there's no answer" by returning `None`, and `class_report`, which knows the name, decides what to print. The crash happened in one function, and the fix touched both.
:::

### Exercise 2: The best score that isn't

`best_score([97, 85, 90])` should return 97. It returns 90, and there's no error. Add one debug print inside the loop that shows which index and value it checks on each pass, read the evidence, then fix it.

```python
def best_score(scores):
    best = 0
    for i in range(1, len(scores)):
        if scores[i] > best:
            best = scores[i]
    return best


print(best_score([97, 85, 90]))
```

:::hint
Print `f"{i=} {scores[i]=} {best=}"` as the first line of the loop. How many passes do you see, and which index is missing?
:::

:::solution
```python run
def best_score(scores):
    best = 0
    for i in range(1, len(scores)):
        print(f"{i=} {scores[i]=} {best=}")
        if scores[i] > best:
            best = scores[i]
    return best


print(best_score([97, 85, 90]))
```

Only two passes, and index 0, the 97, is never checked. `range(1, len(scores))` starts at 1. The clean fix loops over the values directly, so there's no index to get wrong:

```python run
def best_score(scores):
    best = scores[0]
    for score in scores:
        if score > best:
            best = score
    return best


print(best_score([97, 85, 90]))
print(best_score([-4, -9]))
```

Starting `best` at `scores[0]` instead of 0 also fixes a second, hidden bug: with all-negative values, the old version would return 0, a number that isn't in the list. (In real code, `max(scores)` does all of this.)
:::

### Exercise 3: "No such item," but it's right there

A user types `Glue ` (with a capital G and a trailing space) and gets `No such item`. Use evidence to show exactly why, then fix it so capitalization and spaces don't matter.

```python run title="lookup.py" input="Glue "
stock = {"pen": 12, "glue": 3, "tape": 2}

name = input("Item: ")
if name in stock:
    print(name, "has", stock[name])
else:
    print("No such item")
```

:::hint
Print `repr(name)` or `f"{name=}"` right after the `input` line. Then compare it with the keys of `stock`.
:::

:::solution
```python run title="lookup.py" input="Glue "
stock = {"pen": 12, "glue": 3, "tape": 2}

raw = input("Item: ")
print(f"{raw=}")
name = raw.strip().lower()
print(f"{name=}")

if name in stock:
    print(name, "has", stock[name])
else:
    print("No such item")
```

`raw='Glue '` shows both problems at once: the capital G and the space. Dictionary keys must match exactly, so clean the input once, right where it enters the program. Delete the two debug prints when you're done.
:::

### Exercise 4: From print spam to logging

This function prints details on every call, and the output is drowning the useful line. Convert it to `logging`: the details become `DEBUG` messages, the low-stock alert becomes a `WARNING`, and the final summary stays a normal `print`. Run it once at `DEBUG` level and once at `WARNING` level.

```python
def sell(stock, name, amount):
    print("DEBUG: selling", amount, name)
    print("DEBUG: before:", stock[name])
    stock[name] -= amount
    print("DEBUG: after:", stock[name])
    if stock[name] < 5:
        print("LOW STOCK:", name, stock[name])


stock = {"pen": 12, "glue": 6}
sell(stock, "pen", 3)
sell(stock, "glue", 2)
print("Stock now:", stock)
```

:::hint
Call `logging.basicConfig(level=logging.DEBUG, format="%(levelname)s: %(message)s")` once at the top. To switch levels later in the same program, use `logging.getLogger().setLevel(logging.WARNING)`.
:::

:::solution
```python run
import logging
import sys

logging.basicConfig(stream=sys.stdout, level=logging.DEBUG,
                    format="%(levelname)s: %(message)s")


def sell(stock, name, amount):
    logging.debug(f"selling {amount} {name}, before: {stock[name]}")
    stock[name] -= amount
    logging.debug(f"after: {stock[name]}")
    if stock[name] < 5:
        logging.warning(f"low stock: {name} has {stock[name]}")


stock = {"pen": 12, "glue": 6}
print("--- level DEBUG ---")
sell(stock, "pen", 3)
sell(stock, "glue", 2)

logging.getLogger().setLevel(logging.WARNING)
print("--- level WARNING ---")
sell(stock, "pen", 3)
sell(stock, "glue", 1)
print("Stock now:", stock)
```

At `WARNING`, only the alerts remain, and the debug lines are still in the code for the next time you need them. `stream=sys.stdout` is only there so the log lines appear in order with the prints on this page; in your own terminal you can leave it out.
:::

### Exercise 5: Every new task has everyone's tags

Each new task should start with only the tag `"new"`. Instead, the tags pile up across tasks. Prove that the tasks are sharing one list, write a minimal reproduction of the cause, and fix it.

```python run title="tasks.py"
def make_task(title, tags=[]):
    tags.append("new")
    return {"title": title, "tags": tags}


a = make_task("Read chapter 3")
b = make_task("Lab report")
c = make_task("Practice scales", ["music"])
print(a["tags"], b["tags"], c["tags"])
```

:::hint
`a["tags"] is b["tags"]` asks whether two names point to the *same* list object, not just equal ones. When is the default `[]` created: each call, or once?
:::

:::solution
```python run
def make_task(title, tags=[]):
    tags.append("new")
    return {"title": title, "tags": tags}


a = make_task("Read chapter 3")
b = make_task("Lab report")
print(a["tags"] is b["tags"])

# Minimal reproduction: the default list is created once, when def runs.
def grow(items=[]):
    items.append(1)
    return items

print(grow(), grow(), grow())
```

`True` proves it: there is one list, shared by every call that relies on the default. Python evaluates `tags=[]` once, when the `def` line runs, not each time the function is called. The standard fix uses `None` as the default and makes a fresh list inside:

```python run
def make_task(title, tags=None):
    if tags is None:
        tags = []
    tags = tags + ["new"]
    return {"title": title, "tags": tags}


a = make_task("Read chapter 3")
b = make_task("Lab report")
c = make_task("Practice scales", ["music"])
print(a["tags"], b["tags"], c["tags"])
```

`tags + ["new"]` builds a new list, so even a list the caller passed in isn't changed behind their back.
:::

### Exercise 6: When did glue go negative?

This simulation runs 300 orders, and the month-end report shows glue at -15. A shelf can't hold negative glue, so some order took more than was there. Find the *first* order where glue went below zero, and what that order was.

```python run title="month.py"
import random


def simulate(seed, count):
    rng = random.Random(seed)
    stock = {"pen": 40, "glue": 25, "tape": 30}
    for number in range(1, count + 1):
        name = rng.choice(["pen", "glue", "tape"])
        change = rng.choice([-3, -2, -1, 1, 2, 3])
        stock[name] += change
    return stock


print(simulate(14, 300))
```

:::hint
In VS Code, right-click the margin next to `stock[name] += change`, choose **Add Conditional Breakpoint**, and use the expression `stock[name] + change < 0`. Debug the file, and when it pauses, read `number`, `name`, `change`, and `stock` in the Variables pane. No debugger handy? An `assert` after the update finds the same moment.
:::

:::solution
The debugger pauses once, with `number` = 104, `name` = `'glue'`, `change` = -2, and glue at 1. Here's the same answer found with an `assert`, which states the rule and stops the instant it breaks:

```python run raises title="month.py"
import random


def simulate(seed, count):
    rng = random.Random(seed)
    stock = {"pen": 40, "glue": 25, "tape": 30}
    for number in range(1, count + 1):
        name = rng.choice(["pen", "glue", "tape"])
        change = rng.choice([-3, -2, -1, 1, 2, 3])
        stock[name] += change
        assert stock[name] >= 0, f"order {number}: {name} {change:+d} left {stock[name]}"
    return stock


print(simulate(14, 300))
```

Without this, you'd see only the final -15 and have no idea when it started. The real fix belongs in the code that takes orders: reject or shorten any sale bigger than what's on the shelf.
:::

### Challenge: The undo button that doesn't undo

The program saves a snapshot before each change so the user can undo. After a sale and an undo, the pen count should be back to 12. It's 7. Find out why with evidence, try `dict(inventory)` as a fix and explain why it *still* fails, then fix it for real.

```python run title="undo.py"
inventory = {"pen": {"qty": 12}, "glue": {"qty": 3}}
history = []

history.append(inventory)          # save a snapshot
inventory["pen"]["qty"] -= 5       # sell 5 pens
inventory = history.pop()          # undo
print(inventory)
```

```mermaid caption="A shallow copy makes a new outer dict, but both still share the inner dicts"
flowchart LR
    A[inventory] --> O1[outer dict]
    B["snapshot = dict(inventory)"] --> O2[outer dict copy]
    O1 --> P["pen: qty 12"]
    O2 --> P
    O1 --> G["glue: qty 3"]
    O2 --> G
```

:::hint
Print `history[0] is inventory` right after saving the snapshot. Then try `history.append(dict(inventory))` and print `history[0]["pen"] is inventory["pen"]`. The `copy` module has a function that copies all the way down.
:::

:::solution
```python run
import copy

inventory = {"pen": {"qty": 12}, "glue": {"qty": 3}}

history = [inventory]
print("same object?", history[0] is inventory)

history = [dict(inventory)]
print("outer copied?", history[0] is not inventory)
print("inner shared?", history[0]["pen"] is inventory["pen"])

history = [copy.deepcopy(inventory)]
inventory["pen"]["qty"] -= 5
inventory = history.pop()
print(inventory)
```

`history.append(inventory)` doesn't copy anything; it stores a second reference to the same dictionary, so the "snapshot" changes along with the original. `dict(inventory)` makes a new outer dictionary, but its values are the *same* inner dictionaries (that's the diagram above), and the sale changes an inner one. `copy.deepcopy` copies every level, so the snapshot is truly separate. This is the same family of bug as Exercise 5: two names, one object, and a change through one name that shows up through the other.
:::
