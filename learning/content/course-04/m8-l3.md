Your tool works when *you* use it, because you know which commands exist and you type dates the right way. Then a friend tries it and, within a minute, types `python habits.py check Read --date tomorrow`. Testing is how you find out what happens next before they do. This lesson uses the habit tracker from Lesson 2, and every technique applies to your project.

## Start with a test plan

List what to test before writing any test code. Three kinds of cases catch most bugs: **normal** use, **edge** cases at the boundaries, and **bad input**.

| Area | Normal | Edge | Bad input |
| --- | --- | --- | --- |
| Streaks | three days in a row ending today | today not checked yet; crossing a month; no days at all | (not user input) |
| Habits | add a new name | same name with different capitals or spaces | blank name; 31 characters; duplicate |
| Check-ins | check in today | a past date | future date; same day twice; unknown habit; `--date 11/14` |
| Storage | save then load gives the same data | no file yet | damaged JSON; valid JSON of the wrong shape |
| Commands | data survives between runs | `list` with no habits | missing subcommand; unknown subcommand |

Every row in your Lesson 1 table for the hardest rule belongs in here. So does every bug you've already fixed: that's the regression-check habit from Module 6.

## Your first unittest tests

`assert` statements stop at the first failure. The `unittest` module, built into Python, runs every test, reports each one by name, and tells you exactly what was expected. Here's the logic and storage code from Lesson 2, condensed into one cell so the tests below have something real to test:

```python run
import json
import os
from datetime import date, timedelta


def load_data(path):
    try:
        with open(path, encoding="utf-8") as file:
            data = json.load(file)
    except FileNotFoundError:
        return {"habits": {}}
    except json.JSONDecodeError:
        raise ValueError(f"{path} is damaged; fix it or move it out of the way")
    if not isinstance(data, dict) or not isinstance(data.get("habits"), dict):
        raise ValueError(f"{path} doesn't look like a habits file")
    return data


def save_data(path, data):
    temp = path + ".tmp"
    with open(temp, "w", encoding="utf-8") as file:
        json.dump(data, file, indent=2)
    os.replace(temp, path)


def normalize(name):
    name = " ".join(name.split()).lower()
    if not name:
        raise ValueError("a habit needs a name")
    if len(name) > 30:
        raise ValueError("keep habit names to 30 characters or fewer")
    return name


def add_habit(data, name):
    key = normalize(name)
    if key in data["habits"]:
        raise ValueError(f"you already track '{key}'")
    data["habits"][key] = {"days": []}
    return key


def check_in(data, name, day, today):
    key = normalize(name)
    if key not in data["habits"]:
        raise ValueError(f"no habit called '{key}'")
    if day > today:
        raise ValueError("you can't check in for a day that hasn't happened yet")
    habit = data["habits"][key]
    if day.isoformat() in habit["days"]:
        raise ValueError(f"'{key}' is already checked in for {day.isoformat()}")
    habit["days"].append(day.isoformat())
    habit["days"].sort()
    return key


def current_streak(days, today):
    day = today if today in days else today - timedelta(days=1)
    streak = 0
    while day in days:
        streak += 1
        day -= timedelta(days=1)
    return streak


def longest_streak(days):
    best = 0
    for day in days:
        if day - timedelta(days=1) not in days:
            length = 1
            while day + timedelta(days=length) in days:
                length += 1
            best = max(best, length)
    return best


print("code under test is loaded")
```

A test is a method whose name starts with `test_`, inside a class that inherits from `unittest.TestCase`. Inside it, `self.assertEqual(actual, expected)` checks a result:

```python run
import sys
import unittest

TODAY = date(2026, 11, 15)


def nov(*numbers):
    return {date(2026, 11, n) for n in numbers}


class TestStreaks(unittest.TestCase):
    def test_no_days_means_no_streak(self):
        self.assertEqual(current_streak(set(), TODAY), 0)

    def test_streak_includes_today(self):
        self.assertEqual(current_streak(nov(13, 14, 15), TODAY), 3)

    def test_streak_survives_until_today_is_checked(self):
        self.assertEqual(current_streak(nov(13, 14), TODAY), 2)

    def test_gap_breaks_the_streak(self):
        self.assertEqual(current_streak(nov(10, 11, 13), TODAY), 0)

    def test_streak_crosses_a_month_boundary(self):
        across = {date(2026, 10, 31), date(2026, 11, 1)}
        self.assertEqual(current_streak(across, date(2026, 11, 1)), 2)

    def test_longest_streak_finds_the_best_run(self):
        self.assertEqual(longest_streak(nov(1, 2, 3, 7, 8)), 3)


def run(*cases):
    loader = unittest.defaultTestLoader
    suite = unittest.TestSuite(loader.loadTestsFromTestCase(case) for case in cases)
    unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)


run(TestStreaks)
```

Name each test after the behavior it checks, as a sentence: `test_streak_survives_until_today_is_checked` tells you what broke without opening the file. The little `run()` helper exists only for this page; in your project you'll run tests from the terminal, shown further down.

## Watch a test catch a bug

Tests earn their keep when someone "improves" the code later. Suppose you decide the grace rule is unnecessary and simplify `current_streak` to always count from today:

```python run
working_streak = current_streak


def current_streak(days, today):
    day = today
    streak = 0
    while day in days:
        streak += 1
        day -= timedelta(days=1)
    return streak


run(TestStreaks)
current_streak = working_streak
```

One test fails, by name, with the exact numbers: it expected 2 and got 0. Without the test, you'd find out when a user's 40-day streak showed 0 one morning. The last line puts the working version back for the tests below.

## Test errors and files without touching real data

`assertRaises` checks that bad input is *refused*. Used with `with`, the test passes only if the code inside raises that exception. For storage, `setUp` runs before every test and `tearDown` after it; here they create and delete a temporary folder, so tests never read or overwrite your real `habits.json`.

```python run
import tempfile


class TestHabits(unittest.TestCase):
    def setUp(self):
        self.data = {"habits": {}}
        add_habit(self.data, "Read")

    def test_names_ignore_case_and_spaces(self):
        self.assertEqual(normalize("  Read   20  Pages "), "read 20 pages")

    def test_duplicate_habit_is_rejected(self):
        with self.assertRaises(ValueError):
            add_habit(self.data, "READ")

    def test_double_check_in_is_rejected(self):
        check_in(self.data, "read", TODAY, TODAY)
        with self.assertRaises(ValueError):
            check_in(self.data, "Read", TODAY, TODAY)

    def test_future_check_in_is_rejected(self):
        with self.assertRaises(ValueError):
            check_in(self.data, "read", date(2026, 11, 16), TODAY)


class TestStorage(unittest.TestCase):
    def setUp(self):
        self.folder = tempfile.TemporaryDirectory()
        self.path = os.path.join(self.folder.name, "habits.json")

    def tearDown(self):
        self.folder.cleanup()

    def test_missing_file_gives_empty_tracker(self):
        self.assertEqual(load_data(self.path), {"habits": {}})

    def test_round_trip(self):
        data = {"habits": {"read": {"days": ["2026-11-15"]}}}
        save_data(self.path, data)
        self.assertEqual(load_data(self.path), data)

    def test_damaged_file_raises_instead_of_erasing(self):
        with open(self.path, "w") as file:
            file.write('{"habits": ')
        with self.assertRaises(ValueError):
            load_data(self.path)


run(TestHabits, TestStorage)
```

`setUp` gives each test a fresh tracker with one habit. Tests must not depend on each other: if `test_double_check_in_is_rejected` left a check-in behind for the next test, the order tests run in could change the results.

## Test whole commands through `main()`

Unit tests check pieces. A few **end-to-end** tests check that the pieces are wired together: call `main()` with a list of words, a temporary path, and a fixed `today`, and capture what it prints. In your project they go in `test_habits.py` next to the other tests, which import from your three modules:

```py title="test_habits.py (the command tests)"
import contextlib
import io
import os
import tempfile
import unittest
from datetime import date

from habits import main

TODAY = date(2026, 11, 15)


class TestCommands(unittest.TestCase):
    def setUp(self):
        self.folder = tempfile.TemporaryDirectory()
        self.path = os.path.join(self.folder.name, "habits.json")

    def tearDown(self):
        self.folder.cleanup()

    def run_main(self, *words):
        out, err = io.StringIO(), io.StringIO()
        with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):
            code = main(list(words), path=self.path, today=TODAY)
        return code, out.getvalue(), err.getvalue()

    def test_check_in_survives_between_runs(self):
        self.run_main("add", "Read")
        self.run_main("check", "read")
        code, out, _ = self.run_main("list")
        self.assertEqual(code, 0)
        self.assertIn("streak   1", out)

    def test_unknown_habit_exits_with_1(self):
        code, _, err = self.run_main("check", "guitar")
        self.assertEqual(code, 1)
        self.assertIn("no habit called 'guitar'", err)

    def test_bad_date_is_a_usage_error(self):
        with self.assertRaises(SystemExit) as caught:
            self.run_main("check", "read", "--date", "11/14")
        self.assertEqual(caught.exception.code, 2)


if __name__ == "__main__":
    unittest.main()
```

`redirect_stdout` and `redirect_stderr` catch the printed output in memory, so the test can check the message and the terminal stays clean. The first test is the capstone's main promise, written as code: data saved by one run is there for the next. With all four test classes in the file, run them from the project folder:

## Polish: the last 10% people notice first

Work through this list with fresh eyes, ideally the day after you finish the code.

- **Every message helps.** Each `error:` line says what went wrong *and* what to do. Read them all by triggering each one.
- **Help text is complete.** Run `-h` on the tool and on every subcommand. Every argument has a `help=` string, and defaults are mentioned.
- **No leftovers.** No debug `print`s, no commented-out code blocks, no unused imports, no `NotImplementedError` stubs.
- **Names tell the truth.** A function called `get_habit` doesn't also change data.
- **The README is current.** Every example in it runs, exactly as written, on a fresh folder.
- **The hallway test.** Give the tool and README to someone who hasn't seen it. Don't explain anything. Watch what they type first, and fix whatever confused them.

Here's the README for the finished habit tracker:

```markdown title="README.md"
# habits

Track daily habits and streaks from the terminal. Data is saved in
`habits.json` in the folder you run it from.

## Setup
Python 3.10 or newer. No packages to install.

## Usage
    python habits.py add "Read 20 pages"
    python habits.py check "read 20 pages"              # today
    python habits.py check stretch --date 2026-11-12    # a past day
    python habits.py list                               # streaks for every habit
    python habits.py history "read 20 pages" --days 30
    python habits.py remove stretch
Names ignore capital letters and extra spaces. A streak still counts
until the end of today, even if you haven't checked in yet.

## Files
- habits.py: commands and messages
- tracker.py: habits, check-ins, and streak rules (no printing)
- storage.py: loading and safely saving habits.json
- test_habits.py: run with `python -m unittest -v`

## Known limits
One person per habits.json. Days only, not times. No reminders.
```

## Present it in three minutes

A short demo shows what you built and how you think. Use this outline, and rehearse it once with a timer.

1.  **The problem (20 seconds).** Who is it for, and what did they do before it existed?
2.  **Live demo (90 seconds).** Run three or four commands that tell a story: add, use it a few times, show the result. Start from an empty data file so the audience sees it build up. Have the commands ready in a text file to paste.
3.  **Break it on purpose (30 seconds).** Type something wrong and show the helpful error. Then close the terminal, reopen it, and run `list` to show nothing was lost.
4.  **One thing you learned (30 seconds).** A bug you chased and the test that now guards it, or a design decision you'd make differently.
5.  **Next steps (10 seconds).** One feature you'd add with another week.

## Rubric

Score each row from 1 to 4. A 3 in every row is a strong, complete project.

| Criterion | 4: Excellent | 3: Solid | 2: Developing | 1: Beginning |
| --- | --- | --- | --- | --- |
| **Persistence** | data survives restarts; missing and damaged files handled; saves are crash-safe | data survives restarts; missing file handled | saves work, but a missing or damaged file crashes the tool | data is lost between runs |
| **Commands** | 5 or more subcommands, including update and search, all with help text | 4 subcommands, including update and search | 3 subcommands, or update or search is missing | 1 or 2 commands, or input via prompts only |
| **Validation and errors** | every bad input gets a clear, actionable message and the right exit code | bad input never shows a traceback | some bad input crashes with a traceback | no validation |
| **Design** | three modules; logic never prints or reads files; `today` and paths are parameters | three layers, with small slips | logic and printing mixed in places | one long script |
| **Data and collections** | data shape chosen for the commands, with reasons written down; 2 or more collections used well | sensible data shape; 2 collections used | works, but awkward shape or calculated values stored | data shape fights the program |
| **Tests** | 12 or more tests covering normal, edge, bad input, and whole commands; all pass | 8 or more passing tests, including edge cases | a few tests, or some failing | no tests |
| **README and presentation** | a stranger can install and use it from the README alone; demo is clear and timed | README covers the five questions; demo works | README missing setup or examples | no README |

## Reflect, then keep going

Write a short paragraph answering these, and keep it with your project: Which bug took longest to find, and what evidence finally cracked it? Which design decision from your plan held up, and which did you change? If you started over tomorrow, what would you do first?

When you're ready for more, each of these builds directly on what you made:

- **Better tests:** [pytest](https://docs.pytest.org/) runs your `unittest` tests unchanged and makes new ones shorter.
- **A real database:** the built-in [`sqlite3`](https://docs.python.org/3/library/sqlite3.html) module stores records in one file and lets you query them, a natural step up from JSON once you have thousands of records.
- **A nicer terminal:** third-party packages like Rich add colors and tables; list them in `requirements.txt` the way Module 5 showed.
- **A different interface:** keep `tracker.py` and `storage.py` exactly as they are and write a new interface layer, such as a window with the built-in `tkinter` module. If your layers are truly separate, the logic won't need a single change, which is the best test of your design there is.

:::quiz
Q: Why do the storage tests use `tempfile.TemporaryDirectory()` instead of the real `habits.json`?
- [ ] Temporary files are faster to write
  Speed isn't the reason.
- [x] So tests can't read or overwrite your real data, and each test starts from a clean, known state
  `setUp` makes a fresh folder and `tearDown` deletes it, every time.
- [ ] Because `unittest` can't open normal files
  It can; using your real data would make tests unsafe and unpredictable.

Q: After a refactor, one test fails: `AssertionError: 0 != 2` in `test_streak_survives_until_today_is_checked`. What's the best next step?
- [ ] Change the expected value to 0 so the test passes
  That deletes the requirement instead of keeping it.
- [x] Read the test's name and numbers, then check what the refactor changed about counting from yesterday
  The test names the rule that broke and shows the expected and actual values.
- [ ] Delete the test, since the other tests still pass
  Then the bug ships, and nothing will catch it next time.
:::

:::takeaways
- Plan tests in three kinds: normal, edge, and bad input; every past bug becomes a test.
- A `unittest` test is a `test_` method in a `TestCase` class; name it as a sentence about behavior.
- `assertRaises` proves bad input is refused; `setUp`/`tearDown` give every test a clean start.
- Test files in a temporary folder and pass a fixed `today`, so tests never touch real data or depend on the calendar.
- End-to-end tests call `main()` with a list of words and check the exit code and output.
- Polish with fresh eyes and a hallway test, then demo the story: problem, use, failure handled, lesson learned.
:::
