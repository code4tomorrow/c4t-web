:::objectives
- Test your app like a stranger would: every screen, every rotation, every bad input.
- Use plain-Java tests, Developer options, and the Monkey tool to find crashes before your audience does.
- Polish the details people notice first: text, spacing, feedback, dark mode, and accessibility.
- Write a bug note with a symptom, the evidence, the cause, and the fix.
- Plan a 2 to 3 minute demo and check your app against the rubric.
:::

Your app works when *you* use it, because you know exactly which buttons to press and in what order. Your audience doesn't. Someone will tap Save with an empty title, rotate in the middle of typing, or paste a paragraph into a number field. This last stretch is about using your app the way a stranger would, fixing what breaks, and then showing it off with confidence.

Treat testing as a loop, not a single pass:

```mermaid caption="The test loop: one change at a time, and re-test what you fixed"
flowchart LR
    A[Pick one test from your plan] --> B[Run it on a real phone]
    B --> C{Did anything break?}
    C -->|no| A
    C -->|yes| D["Read Logcat, or set a breakpoint"]
    D --> E[Fix one thing]
    E --> F[Write it in your bug log]
    F --> B
```

## Test like you're trying to break it

Run every test on a **real phone** if you can, not only the emulator. Touch targets, text sizes, and speed all feel different in your hand.

### Rotation, on every screen

Rotate on each screen, in each state: an empty list, a full list, halfway through typing, right after an error appears. After each rotation, ask: *did anything the user could see change?* The usual failures:

-   A counter, score, or toggle resets. Save it in `onSaveInstanceState`.
-   A `TextView` you set in code goes back to its XML text. Save the value and set it again in `onCreate`.
-   An `EditText` loses its text. It probably has no `android:id`, and views without ids don't save their state.

### Leave and come back

-   Press Home, open another app, then come back. Nothing should change.
-   Swipe the app away from recent apps and reopen it. Your saved data must be there.
-   Turn on **Don't keep activities** in **Developer options** (in Settings; the exact path varies by phone). Now Android destroys each screen as soon as you leave it, which imitates the system closing your app to free memory. Leave and return on every screen. Anything that lived only in a `ViewModel` will vanish; back it up with a Bundle. **Turn the setting off when you're done**, or other apps on the phone will act strangely.

### Odd input

Make a table of every input field and feed each one the worst things you can think of. Testing validation as plain Java first is fast, because you can try ten inputs in one run. Here's a validator for a "minutes" field in a workout log. Before you run it, pick out which inputs you think are accepted:

```java run title="EdgeCases.java"
public class EdgeCases {

    // Returns an error message, or null if the input is fine.
    static String checkMinutes(String text) {
        String trimmed = text.trim();
        if (trimmed.isEmpty()) {
            return "Enter how many minutes";
        }
        int minutes;
        try {
            minutes = Integer.parseInt(trimmed);
        } catch (NumberFormatException e) {
            return "Minutes must be a whole number";
        }
        if (minutes <= 0 || minutes > 600) {
            return "Pick between 1 and 600 minutes";
        }
        return null;
    }

    public static void main(String[] args) {
        String[] inputs = {"30", "", "   ", "abc", "2.5", "-5", "0", "99999999999", "600", " 45 "};
        for (String input : inputs) {
            String error = checkMinutes(input);
            System.out.println("\"" + input + "\" -> " + (error == null ? "OK" : error));
        }
    }
}
```

Look at `99999999999`. It *is* all digits, but it's too big to fit in an `int` (the largest is 2,147,483,647), so `parseInt` throws and the user gets "must be a whole number," which is a slightly confusing message. That's the kind of case nobody thinks of until a friend types it during your demo. In the app, use the method like this:

```java
String error = checkMinutes(minutesInput.getText().toString());
if (error != null) {
    minutesInput.setError(error);
    return;
}
```

Also try very long text (does it wrap, or push buttons off the screen?), emoji, and tapping **Save** twice very quickly.

### Empty and crowded lists

-   **Zero items:** a blank screen looks broken. Add a `TextView` such as "No habits yet. Tap Add to start." and switch it with `setVisibility(View.VISIBLE)` or `setVisibility(View.GONE)` depending on the list size.
-   **Fifty items:** add a lot and scroll fast. Check that no row shows another row's data (the recycling bug from Week 5) and that the Add button is still reachable.

### Random taps with Monkey

With the phone plugged in and USB debugging on, Android's built-in **Monkey** tool fires hundreds of random taps and swipes at your app. Run this in Android Studio's **Terminal** tab, with your own package name:

```bash
adb shell monkey -p com.example.capstone -v 500
```

If Monkey finds a crash, the stack trace appears in Logcat. Read it the way you practiced in Week 6: the last `Caused by:`, then the first line from your own package.

## Polish what people notice

You don't need fancy design, but these small things make an app feel finished:

-   **Real strings:** move hard-coded text into `strings.xml`. Android Studio's yellow warning highlights point to every one.
-   **Spacing:** the same padding (16dp or 24dp) on every screen. Put repeated numbers in `dimens.xml`.
-   **Feedback for every action:** rows use `?attr/selectableItemBackground`, and every tap produces a response, like a Toast, a new screen, or an updated count.
-   **Dark mode and large text:** switch both on in the phone's settings and check every screen. Use `sp` for text sizes so they scale.
-   **Accessibility:** give every `ImageView` and icon-only button an `android:contentDescription`, and keep touch targets at least 48dp tall.
-   **A name and an icon:** set `app_name` in `strings.xml`, and make an icon with **right-click res > New > Image Asset**.

## Write your bug note

Pick the bug that taught you the most. Keep it to four or five sentences that answer four questions:

1.  **Symptom:** what the user saw ("the app crashed when I saved an empty title").
2.  **Evidence:** how you investigated (the `Caused by:` line in Logcat, a breakpoint, a `Log.d` you added).
3.  **Cause:** the actual mistake in the code.
4.  **Fix:** what you changed, and how you checked that it stays fixed.

## Presenting in 2 to 3 minutes

Plan the demo as a short story, not a tour of every button:

1.  **The problem**, in one sentence: who the app is for and why they'd want it.
2.  **The happy path:** add an item, see it in the list, tap it to open the second screen.
3.  **The proof:** rotate the phone; close the app fully and reopen it to show saved data; type bad input to show it's handled.
4.  **The bug story:** your bug note, in about 30 seconds.
5.  **What's next:** one feature you'd add with more time.

Rehearse at least once with a timer; most first run-throughs take twice as long as planned. Have a few items already saved so you aren't typing them live, and charge your phone. If the demo device might fail you, make a backup screen recording the day before.

## Rubric

Go through this the day before you present. Each row has three levels; aim for the left column on every one.

| Area | Strong | Working | Not yet |
| --- | --- | --- | --- |
| Screens and navigation | Two or more Activities; Intents carry data with constant keys; Back always behaves | Two Activities connected by an Intent | One screen, or navigation crashes |
| Input and validation | Every field rejects empty and bad input with a clear `setError` message | Main field validated; some edge cases slip through | Bad input crashes the app |
| Rotation | Nothing visible changes on any screen, including a value saved with `onSaveInstanceState` or a `ViewModel` | Most screens survive; one value resets | Data is lost on rotation |
| RecyclerView list | Custom row layout, no recycling bugs, helpful empty-list message | Custom rows work; empty list is blank | No RecyclerView |
| Saved data | All user data survives being swiped away and a phone restart | Most data survives; one piece is lost | Nothing is saved |
| Quality | No crashes in rotation, odd input, or Monkey tests; text in `strings.xml`; readable in dark mode and large fonts | One or two rough edges | Crashes during normal use |
| Demo and bug note | Clear 2 to 3 minute story showing every requirement; bug note covers symptom, evidence, cause, and fix | Requirements shown; bug note missing a part | Demo or bug note missing |
| Project | Opens, syncs, and runs from a fresh copy; clear names throughout | Runs after small fixes | Doesn't build |

You started this course with an empty template. You're finishing with an app you designed, built, debugged, and can install on anyone's phone. Bring it to the final class and show people what you made.
