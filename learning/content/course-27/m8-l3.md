Your app works when *you* use it, because you know exactly which buttons to press and in what order. Your audience won't. This last stretch is about using your app the way a stranger would, fixing what breaks, and showing it off with confidence.

## Test like you're trying to break it

Run every test on a **real phone** if you can, not only the emulator. Touch targets, font sizes, and performance feel different in your hand.

### Rotation, on every screen

Rotate on each screen, in each state: an empty list, a full list, halfway through typing, right after an error appears. After each rotation, ask: *Did anything the user could see change?* Common failures:

-   A counter, score, or toggle resets. Save it in `onSaveInstanceState`.
-   A `TextView` you set in code goes back to its XML text. Save the value and set it again in `onCreate`.
-   An `EditText` loses its text. It probably has no `android:id`; views without ids don't save their state.

### Leave and come back

-   Press Home, open another app, come back. Nothing should change.
-   Swipe the app away from recent apps and reopen it. Your saved data must be there.
-   Turn on **Settings > System > Developer options > Don't keep activities** (the exact path varies by phone). Now Android destroys every screen as soon as you leave it, which imitates the system killing your app to save memory. Leave and return on each screen. If anything that relies on a `ViewModel` alone disappears, back it up with a Bundle. **Turn this setting off when you're done**, or other apps will act strangely.

### Odd input

Make a table of every field and feed it the worst things you can think of. Testing your validation as plain Java first is fast. For example, a "minutes" field in a workout log:

```java
public class EdgeCases {

    // Returns an error message, or null if the input is fine.
    static String checkMinutes(String text) {
        String trimmed = text.trim();
        if (trimmed.isEmpty()) {
            return "Enter how many minutes";
        }
        int minutes;
        try {
            minutes = Integer.parseInt(trimmed);
        } catch (NumberFormatException e) {
            return "Minutes must be a whole number";
        }
        if (minutes <= 0 || minutes > 600) {
            return "Pick between 1 and 600 minutes";
        }
        return null;
    }

    public static void main(String[] args) {
        String[] inputs = {"30", "", "   ", "abc", "2.5", "-5", "0", "99999999999", "600", " 45 "};
        for (String input : inputs) {
            String error = checkMinutes(input);
            System.out.println("\"" + input + "\" -> " + (error == null ? "OK" : error));
        }
    }
}
```

```text
"30" -> OK
"" -> Enter how many minutes
"   " -> Enter how many minutes
"abc" -> Minutes must be a whole number
"2.5" -> Minutes must be a whole number
"-5" -> Pick between 1 and 600 minutes
"0" -> Pick between 1 and 600 minutes
"99999999999" -> Minutes must be a whole number
"600" -> OK
" 45 " -> OK
```

Notice `99999999999`: it *is* digits, but it's too big for an `int`, so `parseInt` throws. That's the kind of case nobody thinks of until a friend types it in the demo. In the app, use the method like this:

```java
String error = checkMinutes(minutesInput.getText().toString());
if (error != null) {
    minutesInput.setError(error);
    return;
}
```

Also try very long text (does it wrap or push buttons off screen?), emoji, and tapping **Save** twice quickly.

### Empty and crowded lists

-   **Zero items:** a blank screen looks broken. Show a `TextView` like "No habits yet. Tap Add to start." and toggle it with `setVisibility(View.VISIBLE)` or `View.GONE` based on the list size.
-   **Fifty items:** add a lot and scroll fast. Check that rows don't show another row's data (the recycling bug from week 5) and that the Add button is still reachable.

### Random taps

With the phone plugged in and USB debugging on, Android's built-in Monkey tool fires random taps and swipes at your app:

```bash
adb shell monkey -p com.example.capstone -v 500
```

Use your own package name. If it finds a crash, the stack trace appears in Logcat; read it the way you practiced in week 6.

## Polish what people notice

You don't need fancy design, but these small things make an app feel finished:

-   **Real strings:** move hard-coded text into `strings.xml`. Android Studio's warning highlights point to every one.
-   **Spacing:** consistent padding (16dp or 24dp) on every screen, with `dimens.xml` if you're repeating numbers.
-   **Tap feedback:** rows use `?attr/selectableItemBackground`, and every action gives a response, like a Toast, a screen change, or an updated count.
-   **Readable in dark mode and large fonts:** switch both on in the phone's settings and check every screen. Use `sp` for text sizes so they scale.
-   **Accessibility:** give every `ImageView` and icon-only button an `android:contentDescription`, and keep touch targets at least 48dp tall.
-   **A name and icon:** set `app_name` in `strings.xml`, and make an icon with **right-click res > New > Image Asset**.

## Write your bug note

Pick the bug that taught you the most. Keep it to four or five sentences:

1.  **Symptom:** what the user saw ("the app crashed when I saved an empty title").
2.  **Evidence:** how you investigated (the `Caused by:` line in Logcat, a breakpoint, a `Log.d`).
3.  **Cause:** the actual mistake in the code.
4.  **Fix:** what you changed, and how you checked it stays fixed.

## Presenting (2 to 3 minutes)

Plan your demo as a short story, not a tour of every button:

1.  **The problem** (one sentence): who the app is for and why.
2.  **The happy path:** add an item, see it in the list, tap it to open the second screen.
3.  **The proof:** rotate the phone; close the app fully and reopen it to show saved data; type bad input to show it's handled.
4.  **The bug story:** your bug note, in about 30 seconds.
5.  **What's next:** one feature you'd add with more time.

Rehearse at least once with a timer. Have a few items already saved so you aren't typing them live, and charge your phone. If your demo device might fail, record a backup screen recording beforehand.

## Grading checklist

Go through this the day before you present. You should be able to say a confident yes to every line.

**Requirements**

-   Two or more Activities, with navigation between them through an Intent
-   At least one input field, validated so empty or bad input shows an error instead of crashing
-   Rotating on any screen keeps everything the user sees, including at least one value saved with `onSaveInstanceState` or a `ViewModel`
-   A `RecyclerView` list with a custom row layout
-   Data is still there after the app is swiped away and reopened

**Deliverables**

-   The project syncs, builds, and runs from a fresh copy with no errors
-   A 2 to 3 minute demo that shows every requirement
-   A written bug note: symptom, evidence, cause, fix

**Quality**

-   No crashes during rotation, odd input, or the Monkey test
-   An empty list shows a helpful message
-   User-facing text lives in `strings.xml`
-   Readable in dark mode and with a large font size
-   Code uses clear names, and keys for extras and SharedPreferences are constants

Congratulations on getting here. You started with an empty template and you're finishing with an app you designed, built, debugged, and can install on anyone's phone.
