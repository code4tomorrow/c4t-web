Swipe your app away from recent apps and open it again: everything the user typed is gone. A `Bundle` only survives rotation and short background trips, and a `ViewModel` doesn't even survive that long. This week covers the last three skills a real app needs: remembering data for good, finding out *why* something broke, and getting the app onto someone else's phone.

## SharedPreferences: a tiny saved dictionary

`SharedPreferences` stores key-value pairs in a private file inside your app's storage. It's perfect for settings, a high score, a username, or a short note. It is **not** meant for big data like hundreds of records or photos; those belong in a database or files.

### Opening the file

Inside an Activity:

```java
SharedPreferences prefs = getSharedPreferences("settings", MODE_PRIVATE);
```

-   `"settings"` is the file name. Use the same name everywhere you read or write.
-   `MODE_PRIVATE` means only your app can read it. It's the only mode you should use.

Import `android.content.SharedPreferences`.

### Writing

Changes go through an `Editor`. Chain the `put` calls and finish with `apply()`:

```java
prefs.edit()
        .putString("username", "Ana")
        .putInt("high_score", 1200)
        .putBoolean("sound_on", true)
        .apply();
```

`apply()` updates the in-memory copy right away and writes the file in the background, so it never freezes the screen. There's also `commit()`, which writes immediately and returns `true` or `false`, but it blocks the main thread while it works. Use `apply()` unless you truly need the result.

:::warning
Forgetting `apply()` is the number one SharedPreferences bug. `prefs.edit().putString("username", "Ana");` compiles and runs, but nothing is saved.
:::

### Reading

Every getter takes a key and a **default** that's returned when nothing is saved yet:

```java
String username = prefs.getString("username", "");
int highScore = prefs.getInt("high_score", 0);
boolean soundOn = prefs.getBoolean("sound_on", true);
```

The type has to match: saving with `putInt` and reading with `getString` throws a `ClassCastException`. Keep keys in constants (`private static final String KEY_USERNAME = "username";`) so a typo can't create a second, empty key.

A common pattern is to read in `onCreate` and write whenever the value changes, or in `onPause` so nothing is lost if the user leaves suddenly.

To wipe saved data while testing, go to the phone's **Settings > Apps > your app > Storage > Clear storage**, or just uninstall the app.

## Logcat: let your app talk to you

`System.out.println` technically works on Android, but the proper tool is `android.util.Log`:

```java
private static final String TAG = "ScoreKeeper";

Log.d(TAG, "Loaded high score: " + highScore);
Log.w(TAG, "Name was empty, using default");
Log.e(TAG, "Could not parse score", exception);
```

The letter is the **level**: `v` verbose, `d` debug, `i` info, `w` warning, `e` error. The **tag** labels where the message came from; the convention is one constant per class.

Open **View > Tool Windows > Logcat** while the app runs. Logcat shows messages from the whole phone, so filter it in the search bar:

-   `package:mine` shows only your app.
-   `tag:ScoreKeeper` shows only your tag.
-   `level:WARN` shows warnings and errors only.
-   Combine them: `package:mine level:ERROR`.

### Reading a crash

When an app crashes, Logcat prints a **stack trace** in red. Here is a typical one (your numbers will differ):

```text
FATAL EXCEPTION: main
Process: com.example.scorekeeper, PID: 8123
java.lang.RuntimeException: Unable to start activity ComponentInfo{com.example.scorekeeper/com.example.scorekeeper.MainActivity}: java.lang.NullPointerException: Attempt to invoke virtual method 'void android.widget.Button.setOnClickListener(android.view.View$OnClickListener)' on a null object reference
	at android.app.ActivityThread.performLaunchActivity(ActivityThread.java:3645)
	...
Caused by: java.lang.NullPointerException: Attempt to invoke virtual method 'void android.widget.Button.setOnClickListener(android.view.View$OnClickListener)' on a null object reference
	at com.example.scorekeeper.MainActivity.onCreate(MainActivity.java:34)
	at android.app.Activity.performCreate(Activity.java:8595)
```

How to read it:

1.  Find the **last** `Caused by:` line. That's the real problem: something was `null` and you called `setOnClickListener` on it.
2.  Below it, find the first line that mentions **your** package (`com.example.scorekeeper`). `MainActivity.java:34` is the exact line. It's a blue link in Logcat; click it.
3.  Ignore the `android.app...` lines. They're Android's own code that called yours.

Here the Button on line 34 was `null`, so the `findViewById` id was wrong or came from a different layout.

## Breakpoints: pause the app and look inside

Logs tell you what happened; a debugger lets you stop time and look around.

1.  Click in the gutter just right of a line number. A red dot appears: that's a **breakpoint**.
2.  Start the app with **Run > Debug 'app'** (the bug icon) instead of Run.
3.  When that line is about to run, the app freezes and Android Studio opens the **Debug** window.

Now you can:

-   Read the **Variables** pane to see every local variable and field right now.
-   **Step Over** (F8) runs the current line and stops on the next one.
-   **Step Into** (F7) goes inside the method being called on this line.
-   **Resume Program** runs until the next breakpoint.
-   Right-click a breakpoint to add a **condition** like `i == 5` so it only stops when that's true.

Use breakpoints when the app doesn't crash but gives the wrong answer. Stepping line by line and watching a variable change is often the fastest way to see where your logic goes off track.

## Building an APK

An **APK** is the installable file for an Android app. When you press Run, Android Studio builds one and installs it for you. To get the file itself:

**Build > Build Bundle(s) / APK(s) > Build APK(s)**

In some newer versions of Android Studio the same command is under **Build > Generate App Bundles or APKs > Generate APKs**. When it finishes, click **locate** in the popup. The file is at `app/build/outputs/apk/debug/app-debug.apk`.

### Debug vs release

-   **Debug** builds are signed automatically with a debug key Android Studio made for you. Great for sharing with friends and testing. They're larger and can be debugged.
-   **Release** builds are optimized and must be signed with **your own** key. The Play Store accepts only release builds (as an app bundle, `.aab`).

### Signing basics

Android refuses to install an unsigned APK. Signing proves that updates come from the same developer. To make a release build: **Build > Generate Signed Bundle / APK**, choose **APK**, then **Create new...** to make a **keystore** (a password-protected file holding your key). Choose the `release` variant, and the file appears in `app/release/`.

:::warning
Back up your keystore and its passwords, and never commit them to GitHub. If you lose the key, you can never publish an update to that app on the Play Store under the same listing.
:::

### Installing on a phone

Send the APK to the phone (USB, Google Drive, email), tap it, and allow **Install unknown apps** for the app you opened it with when Android asks. With the phone plugged in and USB debugging on, `adb install app-debug.apk` works too.
