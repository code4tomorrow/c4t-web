Type your name into last week's app, swipe the app away from recent apps, and open it again. Your name is gone. The Bundle from two weeks ago only covers rotation and short trips to the background, and a ViewModel doesn't last even that long. Here's the full scorecard:

| Where the value lives | Rotation | Android frees memory in the background | Swiped away from recents | Phone restarts |
| --- | --- | --- | --- | --- |
| A plain field | lost | lost | lost | lost |
| A `ViewModel` | kept | lost | lost | lost |
| The Bundle (`onSaveInstanceState`) | kept | kept | lost | lost |
| `SharedPreferences` | kept | kept | kept | kept |

Only the bottom row survives everything, because it's the only one written to storage. This week covers the last three things a real app needs: remembering data for good, finding out *why* something broke, and getting the app onto someone else's phone.

## SharedPreferences: a small saved dictionary

`SharedPreferences` stores key-value pairs in a private file inside your app's storage. Think of a labeled jar for each value: `"username"` holds `Ana`, `"high_score"` holds `1200`. It's the right tool for settings, a high score, a name, or one short note. It is **not** meant for hundreds of records or for photos; those belong in a database or in files.

### Open the file

Inside an Activity:

```java
SharedPreferences prefs = getSharedPreferences("settings", MODE_PRIVATE);
```

`"settings"` is the file name; use the same name everywhere you read or write. `MODE_PRIVATE` means only your app can read it, and it's the only mode you should use. Import `android.content.SharedPreferences`.

### Write, then apply

Changes go through an **Editor**. Chain the `put` calls and finish with `apply()`:

```java
prefs.edit()
        .putString("username", "Ana")
        .putInt("high_score", 1200)
        .putBoolean("sound_on", true)
        .apply();
```

`apply()` updates the in-memory copy right away and writes the file in the background, so the screen never freezes while it saves. There's also `commit()`, which writes immediately and returns `true` or `false`, but it makes the main thread wait for the disk. Use `apply()` unless you truly need that answer.

```mermaid caption="A value's trip into SharedPreferences and back out on the next launch"
flowchart LR
    A["prefs.edit()"] --> B["putString, putInt, ..."]
    B --> C["apply()"]
    C --> D["Memory copy: updated now"]
    C --> E[("File on the phone: written in the background")]
    E -->|"app opens again"| F["getString(key, default)"]
```

The file really is just XML. On an emulator you can usually open it with **View > Tool Windows > Device Explorer**, under `data/data/` followed by your package name and `shared_prefs/`. After the code above, `settings.xml` looks like this:

```xml
<?xml version='1.0' encoding='utf-8' standalone='yes' ?>
<map>
    <string name="username">Ana</string>
    <int name="high_score" value="1200" />
    <boolean name="sound_on" value="true" />
</map>
```

:::warning
Forgetting `apply()` is the number one SharedPreferences bug. `prefs.edit().putString("username", "Ana");` compiles and runs without a single error, and saves nothing. The Editor collected your change and was thrown away.
:::

### Read, with a default

Every getter takes a key and a **default**, which is what you get when nothing has been saved yet, like on the very first launch:

```java
String username = prefs.getString("username", "");
int highScore = prefs.getInt("high_score", 0);
boolean soundOn = prefs.getBoolean("sound_on", true);
```

The type must match what you saved. Save with `putInt` and read with `getString`, and you get a `ClassCastException`. Keep every key in a constant (`private static final String KEY_USERNAME = "username";`) so a typo can't quietly create a second, empty key.

A good default pattern: read in `onCreate`, and write whenever the value changes, or in `onPause` so nothing is lost if the user leaves suddenly. To wipe saved data while testing, open the phone's **Settings > Apps**, pick your app, then **Storage > Clear storage**, or simply uninstall it.

What to watch for: the save method and the load method as two separate pieces, and the default values passed to every getter. The video is in Java, like this course.

## Logcat: make your app talk to you

`System.out.println` does work on Android, but the proper tool is `android.util.Log`, which tags every message and gives it a level:

```java
private static final String TAG = "ScoreKeeper";

Log.d(TAG, "Loaded high score: " + highScore);
Log.w(TAG, "Name was empty, using default");
Log.e(TAG, "Could not parse score", exception);
```

The letter is the **level**: `v` verbose, `d` debug, `i` info, `w` warning, `e` error. The **tag** says where the message came from; one constant per class is the usual habit.

Open **View > Tool Windows > Logcat** while the app runs. Logcat shows messages from the *entire phone*, often hundreds per second, so you filter it in the search bar:

-   `package:mine` shows only your app.
-   `tag:ScoreKeeper` shows only your tag.
-   `level:WARN` shows warnings and worse.
-   They combine: `package:mine level:ERROR`.

### Reading a crash

When the app crashes, Logcat prints a **stack trace** in red. It looks scary, but you only need three lines of it. Here's a typical one (your numbers will differ):

```text
FATAL EXCEPTION: main
Process: com.example.scorekeeper, PID: 8123
java.lang.RuntimeException: Unable to start activity ComponentInfo{com.example.scorekeeper/com.example.scorekeeper.MainActivity}: java.lang.NullPointerException: Attempt to invoke virtual method 'void android.widget.Button.setOnClickListener(android.view.View$OnClickListener)' on a null object reference
	at android.app.ActivityThread.performLaunchActivity(ActivityThread.java:3645)
	...
Caused by: java.lang.NullPointerException: Attempt to invoke virtual method 'void android.widget.Button.setOnClickListener(android.view.View$OnClickListener)' on a null object reference
	at com.example.scorekeeper.MainActivity.onCreate(MainActivity.java:34)
	at android.app.Activity.performCreate(Activity.java:8595)
```

1.  Find the **last** `Caused by:` line. That's the real problem: something was `null`, and the code called `setOnClickListener` on it.
2.  Just below it, find the first line that names **your** package (`com.example.scorekeeper`). `MainActivity.java:34` is the exact file and line. In Logcat it's a blue link; click it.
3.  Skip the `android.app...` lines. That's Android's own code, which called yours.

So the Button on line 34 was `null`, which means its `findViewById` id was wrong or belongs to another layout. Three lines read, bug found.

## Breakpoints: freeze the app and look inside

Logs tell you what happened. A debugger lets you stop time and look around while it's happening.

1.  Click in the gutter just to the right of a line number. A red dot appears: that's a **breakpoint**.
2.  Start the app with **Run > Debug 'app'** (the bug icon) instead of Run.
3.  When that line is about to run, the app freezes and the **Debug** window opens.

While it's frozen you can:

-   Read the **Variables** pane: every local variable and field, with its value right now.
-   **Step Over** (F8): run this line and stop at the next one.
-   **Step Into** (F7): go inside the method this line calls.
-   **Resume Program**: run until the next breakpoint.
-   Right-click the red dot and add a **condition** like `i == 5`, so it only stops when that's true.

Reach for a breakpoint when the app doesn't crash but gives the wrong answer. There's no stack trace for a wrong answer. Watching a variable change one line at a time is often the fastest way to see exactly where your logic goes off course.

## Building an APK

An **APK** (Android Package) is the installable file for an Android app. Every time you press Run, Android Studio builds one and installs it for you. Here's what happens to your files on the way:

```mermaid caption="From your project files to an app installed on a phone"
flowchart LR
    A[Java code] --> D[Gradle build]
    B[XML layouts and resources] --> D
    C[Libraries such as AppCompat] --> D
    D --> E["Compiled code (.dex) and resources"]
    E --> F[Packaged into an APK]
    F --> G{Signed with which key?}
    G -->|debug key| H[app-debug.apk]
    G -->|your own keystore| I[app-release.apk]
    H --> J[Install on a phone]
    I --> J
```

To get the file itself, choose **Build > Generate App Bundles or APKs > Generate APKs**. Older versions of Android Studio call it **Build > Build Bundle(s) / APK(s) > Build APK(s)**; use whichever your menu shows. When it finishes, click **locate** in the popup. The file is `app/build/outputs/apk/debug/app-debug.apk`.

### Debug versus release, and why signing exists

Android refuses to install an APK that isn't **signed**. A signature is like a wax seal on a letter: it proves the file came from whoever holds the key, and that later updates came from the same person. If someone else built a fake "update" to your app, it wouldn't carry your seal, and the phone would refuse it.

-   **Debug** builds are signed automatically with a debug key Android Studio created for you. They're fine for testing and for sharing with friends.
-   **Release** builds are optimized and signed with **your own** key, stored in a password-protected file called a **keystore**. You make one with **Build > Generate Signed App Bundle or APK** (older versions: **Generate Signed Bundle / APK**). The Play Store only takes release builds, uploaded as an app bundle (`.aab`).

:::warning
Back up your keystore and both passwords, and never commit them to GitHub. Anyone with the key can sign apps as you, and if you lose it you can't sign updates to an app you've already shared.
:::

### Installing on a phone

Send the APK to the phone (USB cable, Google Drive, email), tap it, and allow **Install unknown apps** for whichever app opened it. With the phone plugged in and USB debugging on, `adb install app-debug.apk` works too.

:::note
Google is phasing in **developer verification**: apps installed on certified Android phones will need to come from verified developers, worldwide starting in 2027. A first phase began on September 30, 2026, for apps from certain stores in Brazil, Indonesia, Singapore, and Thailand. Installing with Android Studio or `adb` isn't affected. For sharing beyond that, students can use a free *limited distribution* account that covers up to 20 devices and needs no ID.
:::

:::quiz
Q: A settings screen runs `prefs.edit().putString("username", name);` when you tap Save. After reopening the app, the name is empty. Why?
- [x] The chain never calls `apply()`, so the change is never saved
  The Editor collected the change and was thrown away. Add `.apply()` at the end.
- [ ] SharedPreferences are wiped when the app closes
  Saved preferences survive closing the app and even restarting the phone.
- [ ] `putString` only works inside `onPause`
  You can save from anywhere, including a click listener.

Q: A crash's stack trace has a dozen `at ...` lines. Which one do you click first?
- [ ] The very first line of the trace
  That's often a wrapper exception from Android's code. The real cause is further down.
- [x] The first line under the last `Caused by:` that names your own package
  That's the exact line in your code where things went wrong.
- [ ] The last line of the whole trace
  The bottom lines are usually deep inside Android's code.

Q: Your average-score screen shows `50.0` when it should show `80.0`, and nothing crashes. What's the most direct way to find the bug?
- [ ] Read the stack trace in Logcat
  There's no stack trace, because nothing crashed.
- [x] Set a breakpoint in the loop and watch the variables change as you step
  You'll see exactly which value is skipped or wrong.
- [ ] Rebuild the APK
  Building again runs the same wrong code.

Q: A habit tracker must still show your streak after you swipe the app away and restart the phone. Where should the streak live?
- [ ] In a field of `MainActivity`
  Fields vanish as soon as the Activity is destroyed.
- [ ] In the Bundle from `onSaveInstanceState`
  The Bundle survives rotation and background kills, but not being swiped away.
- [x] In SharedPreferences
  It's written to storage, so it survives everything in the scorecard.
:::

:::takeaways
- Only stored data survives the app being swiped away; for small values, that's SharedPreferences.
- Write with `edit()`, `put...`, and `apply()`. Read with a getter and a default. Keep keys in constants.
- `Log.d(TAG, ...)` plus `package:mine` or `tag:` in Logcat shows what your app is doing.
- In a crash, read the last `Caused by:` and the first line from your own package below it.
- Breakpoints catch wrong answers that never crash.
- An APK must be signed: debug builds use Android Studio's key, release builds use your keystore.
:::
