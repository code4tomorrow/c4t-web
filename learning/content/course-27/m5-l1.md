Last week's layout had a perfect Button. Tap it now and nothing happens. No error, no crash, nothing. XML can describe a button, but it can't decide what a tap means. Deciding is Java's job, and right now your Java has no idea the button exists.

There's a stranger problem waiting further down. Build a score counter, tap it up to 7, turn the phone sideways, and the score is back to 0. Nothing in your code reset it. By the end of these notes you'll know exactly who did, and how to stop it.

## Give a view an id, then look it up

Think of the layout as a room full of objects and an id as a name tag. Java can only grab an object that wears a tag. You add the tag in XML with `android:id`; the `@+id/` part means "create this id if it doesn't exist yet."

```xml
<EditText
    android:id="@+id/name_input"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    android:hint="@string/name_hint"
    android:inputType="textPersonName" />

<Button
    android:id="@+id/greet_button"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:text="@string/greet" />

<TextView
    android:id="@+id/greeting_text"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content" />
```

When you build, Android Studio turns every id into a number in a generated class called `R`, so `@+id/greet_button` becomes `R.id.greet_button`. In `onCreate`, **after** `setContentView`, you ask for each view by that number:

```java
EditText nameInput = findViewById(R.id.name_input);
Button greetButton = findViewById(R.id.greet_button);
TextView greetingText = findViewById(R.id.greeting_text);
```

`findViewById` searches only the layout you handed to `setContentView`. Call it before that line, or pass an id that lives in a different layout file, and it quietly returns `null`. You won't find out until the next line tries to use the view and the app crashes.

:::warning
The crash looks like this in Logcat: `java.lang.NullPointerException: Attempt to invoke virtual method 'void android.widget.Button.setOnClickListener(android.view.View$OnClickListener)' on a null object reference`. It almost always means a misspelled id, an id from another layout, or `findViewById` called before `setContentView`.
:::

### Optional: View Binding

View Binding generates a class with one field per view, so you never type an id twice and can't get `null` for a missing view. Turn it on in `app/build.gradle.kts`, inside the `android { }` block, then click **Sync Now**:

```kotlin
buildFeatures {
    viewBinding = true
}
```

That file is Gradle configuration, not app code, so your app stays pure Java. For `activity_main.xml` you get a class named `ActivityMainBinding`, and `snake_case` ids become `camelCase` fields:

```java
ActivityMainBinding binding = ActivityMainBinding.inflate(getLayoutInflater());
setContentView(binding.getRoot());
binding.greetButton.setOnClickListener(v -> binding.greetingText.setText("Hi!"));
```

The course examples use `findViewById` because it shows every step, but either style is fine in your own projects.

## A click listener is a callback

You don't check the button in a loop asking "tapped yet? tapped yet?" Instead you hand Android a small piece of code and say "run this when it's tapped." That piece of code is a **listener**: an object with one method, `onClick(View v)`. A Java lambda writes it in one line:

```java
greetButton.setOnClickListener(v -> {
    String name = nameInput.getText().toString().trim();
    if (name.isEmpty()) {
        nameInput.setError("Type a name first");
        return;
    }
    greetingText.setText("Hello, " + name + "!");
    Toast.makeText(this, "Greeted " + name, Toast.LENGTH_SHORT).show();
});
```

Type `  Ana ` and tap, and the TextView reads `Hello, Ana!` while a small grey message pops up near the bottom. Leave the box empty and a red error icon appears on the field instead. Here's what each line is doing:

-   `getText()` returns an `Editable`, not a `String`, so you add `.toString()`.
-   `trim()` strips spaces from both ends, so a box with only spaces counts as empty.
-   `setError` puts the message on the field itself, right where the user is looking.
-   `Toast.makeText(context, text, duration)` **builds** a Toast, and `.show()` displays it. Leave off `.show()` and nothing appears, with no error to tell you why.

Inside a lambda, `this` still means the Activity, so `Toast.makeText(this, ...)` works. In an old-style anonymous class (`new View.OnClickListener() { ... }`), `this` would mean the listener, and you'd write `MainActivity.this` instead.

## Typed text is never a number until you parse it

`android:inputType="numberDecimal"` shows a number keyboard, but it can't stop a user from leaving the box empty or typing a lone `.`. You still get a `String`, and turning it into a `double` with `Double.parseDouble` throws a `NumberFormatException` when the text isn't a number. An exception that nobody catches crashes the app.

So wrap the parse in `try`/`catch`. Before you run this, guess which of the six inputs come back as `-1`:

```java run title="SafeParse.java"
public class SafeParse {

    // Returns the number in text, or -1 if text is not a valid number.
    static double parseOrMinusOne(String text) {
        try {
            return Double.parseDouble(text.trim());
        } catch (NumberFormatException e) {
            return -1;
        }
    }

    public static void main(String[] args) {
        String[] inputs = {"42.50", "  18 ", "", ".", "abc", "1e3"};
        for (String input : inputs) {
            System.out.println("\"" + input + "\" -> " + parseOrMinusOne(input));
        }
    }
}
```

The surprise is the last line: `1e3` is scientific notation for 1,000, and Java happily accepts it. The number keyboard won't let anyone type an `e`, but pasted text can sneak one in, which is why you check the parsed value too (a bill can't be negative). Returning `-1` works as a "this was bad" signal here because no real bill or percent is negative. In the app, you check for it and call `setError` instead of crashing.

This is plain Java, so it runs right here on the page. Testing logic outside Android first is a habit worth keeping: if the app shows a wrong number later, you'll know the math was fine and the bug is in the wiring.

## The Activity lifecycle: Android is in charge

Your Activity doesn't just "run." Android moves it through states as the user opens it, covers it with something else, leaves it, and comes back. At every change, Android calls one of your methods so you can react.

```mermaid caption="The lifecycle methods Android calls as a screen comes and goes"
stateDiagram-v2
    [*] --> Created: onCreate
    Created --> Started: onStart
    Started --> Resumed: onResume
    Resumed --> Paused: onPause
    Paused --> Resumed: onResume
    Paused --> Stopped: onStop
    Stopped --> Started: onRestart then onStart
    Stopped --> Destroyed: onDestroy
    Destroyed --> [*]
```

| Method | When Android calls it | What to do there |
| --- | --- | --- |
| `onCreate` | The Activity object was just created | `setContentView`, find views, attach listeners |
| `onStart` | It's about to become visible | Start things the user can see |
| `onResume` | It's in front and receiving taps | Resume animations, the camera, sensors |
| `onPause` | Something is partly covering it, or the user is leaving | Pause quick work, save a draft |
| `onStop` | It's no longer visible at all | Stop heavy work |
| `onDestroy` | It's being thrown away | Final cleanup |

The best way to believe this is to watch it. Override a method, log from it, and filter Logcat by your tag:

```java
private static final String TAG = "Lifecycle";

@Override
protected void onStart() {
    super.onStart();
    Log.d(TAG, "onStart");
}
```

Every override must call its `super` version. Skip it and Android throws a `SuperNotCalledException` the moment the method runs.

## Why rotation wipes your data

Here's the score counter mystery solved. When the phone rotates, Android **destroys your Activity and creates a brand-new one**, so the new one can load a landscape layout if you have one. Log all six methods and rotate once, and Logcat shows:

```text
onPause
onStop
onDestroy
onCreate
onStart
onResume
```

Your `int count` field lived in the old object, and the old object is gone. The new object starts with `count = 0`. Views are rebuilt from XML too, with one exception: a view that has an id saves some of its own state. An `EditText` with an id keeps its typed text. A `TextView` whose text you changed in code goes back to whatever the XML says.

### Save it in a Bundle before it's destroyed

Just before destroying the old Activity, Android calls `onSaveInstanceState` and hands you a `Bundle`, a small box of key-value pairs. Whatever you put in, Android passes to the new Activity's `onCreate`:

```mermaid caption="The Bundle carries your value from the old Activity to the new one"
sequenceDiagram
    participant User
    participant Android
    participant Old as Old MainActivity
    participant New as New MainActivity
    User->>Android: Rotates the phone
    Android->>Old: onPause, onStop
    Android->>Old: onSaveInstanceState(outState)
    Old-->>Android: Bundle holding count = 7
    Android->>Old: onDestroy
    Android->>New: onCreate(savedInstanceState)
    New->>New: count = getInt(KEY_COUNT, 0)
    Android->>New: onStart, onResume
```

```java
private static final String KEY_COUNT = "count";
private int count = 0;

@Override
protected void onSaveInstanceState(@NonNull Bundle outState) {
    super.onSaveInstanceState(outState);
    outState.putInt(KEY_COUNT, count);
}

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);
    if (savedInstanceState != null) {
        count = savedInstanceState.getInt(KEY_COUNT, 0);
    }
    // ...find views, then show count on screen...
}
```

`savedInstanceState` is `null` the first time the screen opens, and holds your Bundle after a rotation. Bundles have `putInt`, `putString`, `putDouble`, `putBoolean`, and matching getters. Keep what you store small: numbers and short strings, not long lists or images.

### Optional: a ViewModel

A `ViewModel` is an object Android keeps alive across rotation, so there's nothing to pack and unpack:

```java
import androidx.lifecycle.ViewModel;

public class CounterViewModel extends ViewModel {
    public int count = 0;
}
```

```java
CounterViewModel model = new ViewModelProvider(this).get(CounterViewModel.class);
model.count++;
```

`ViewModelProvider` comes from `androidx.lifecycle`, which the template's AppCompat library already brings in. The catch: a ViewModel survives rotation but **not** Android killing your app in the background to free memory, while a Bundle survives both. Larger apps often use both.

:::warning
Two bugs show up every week in this unit. First, `countText.setText(count)` with an `int` compiles, but Android treats the number as a string resource id and crashes with `android.content.res.Resources$NotFoundException: String resource ID #0x7`. Write `setText(String.valueOf(count))`. Second, restoring `count` in `onCreate` isn't enough on its own: you also have to put it back on screen, or the TextView keeps showing its XML text.
:::

:::quiz
Q: Tapping your new button crashes with a `NullPointerException` on the line `greetButton.setOnClickListener(...)`. What's the most likely cause?
- [ ] The Toast inside the listener is missing `.show()`
  A missing `.show()` just means no Toast appears; it never crashes, and the listener hasn't even run yet.
- [x] `findViewById` returned `null` because the id doesn't match a view in the layout passed to `setContentView`
  Right. The crash happens when you call a method on `greetButton`, so `greetButton` itself is `null`.
- [ ] The button's text isn't in `strings.xml`
  A missing string resource is a build error in the XML, not a crash at this line.

Q: Which input makes `parseOrMinusOne` return `-1`?
- [ ] `"  18 "`
  `trim()` removes the spaces first, so it parses as `18.0`.
- [ ] `"1e3"`
  That's scientific notation, and `Double.parseDouble` reads it as `1000.0`.
- [x] `"."`
  A lone decimal point isn't a number, so `parseDouble` throws and the `catch` returns `-1`.

Q: A counter shows `7`. It has no `onSaveInstanceState`. You rotate the phone. What does the screen show?
- [ ] `7`, because Android remembers what was on screen
  Android only restores views that save their own state, and a TextView changed in code doesn't.
- [x] The TextView's text from the XML, and `count` is back to `0`
  Rotation built a brand-new Activity, so the field starts at 0 and the TextView is rebuilt from XML.
- [ ] The app crashes
  Nothing here is `null`; the data is simply lost.

Q: The user presses Home, then reopens your app from recent apps a few seconds later. Which methods run when it comes back?
- [ ] `onCreate`, `onStart`, `onResume`
  `onCreate` only runs for a new Activity object. Pressing Home stopped yours but didn't destroy it.
- [x] `onRestart`, `onStart`, `onResume`
  The stopped Activity is brought back, so your fields are still there.
- [ ] Only `onResume`
  That's what happens when a dialog covering part of the screen goes away. After Home, the Activity was fully stopped.
:::

:::takeaways
- Java reaches a view through its `android:id`, using `findViewById` after `setContentView`.
- A click listener is code you hand to Android to run later; `setError` and `Toast` (with `.show()`) are how you answer the user.
- Typed text is a `String`. Parse it inside `try`/`catch` and check the result, or bad input crashes the app.
- Android, not your code, moves an Activity through `onCreate`, `onStart`, `onResume`, `onPause`, `onStop`, and `onDestroy`.
- Rotation destroys and rebuilds the Activity. Put values in the Bundle in `onSaveInstanceState` and read them back in `onCreate`.
:::
