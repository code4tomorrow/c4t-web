summary: Wire XML views to Java with findViewById, react to taps, read and safely parse user input, and keep your data when the phone rotates.

Up to now your layouts have been pretty pictures. You can place a Button perfectly, but tapping it does nothing, because nothing in Java knows it exists. This week you connect the two halves of an Android app: the XML that describes the screen and the Java that decides what happens.

## Step 1: Give views an id, then find them

Java can only reach a view that has an `android:id`. The `@+id/` part means "create this id if it doesn't exist yet."

```xml
<EditText
    android:id="@+id/name_input"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    android:hint="@string/name_hint"
    android:inputType="textPersonName" />

<Button
    android:id="@+id/greet_button"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:text="@string/greet" />

<TextView
    android:id="@+id/greeting_text"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content" />
```

Android Studio turns every id into a constant in the generated `R` class, so `@+id/greet_button` becomes `R.id.greet_button`. In `onCreate`, **after** `setContentView`, you look views up:

```java
EditText nameInput = findViewById(R.id.name_input);
Button greetButton = findViewById(R.id.greet_button);
TextView greetingText = findViewById(R.id.greeting_text);
```

`findViewById` searches the layout you just set. Call it before `setContentView` and it returns `null`, because there is no layout to search yet.

:::warning
A `NullPointerException` on a line like `greetButton.setOnClickListener(...)` almost always means the id is misspelled, belongs to a different layout file, or you called `findViewById` before `setContentView`.
:::

### Optional: View Binding

View Binding generates a class with one field per view, so you never type an id twice. Turn it on in `app/build.gradle.kts`, inside the `android { }` block, then click **Sync Now**:

```kotlin
buildFeatures {
    viewBinding = true
}
```

For `activity_main.xml` you get `ActivityMainBinding`, and ids written in `snake_case` become `camelCase` fields:

```java
ActivityMainBinding binding = ActivityMainBinding.inflate(getLayoutInflater());
setContentView(binding.getRoot());
binding.greetButton.setOnClickListener(v -> binding.greetingText.setText("Hi!"));
```

It is type-safe and can't return `null` for a missing view. This course uses `findViewById` in examples because it shows exactly what is going on, but either style is fine in your projects.

## Step 2: React to taps

A click listener is an object with one method, `onClick(View v)`, that Android calls when the view is tapped. Java lambdas make it short:

```java
greetButton.setOnClickListener(v -> {
    String name = nameInput.getText().toString().trim();
    if (name.isEmpty()) {
        nameInput.setError("Type a name first");
        return;
    }
    greetingText.setText("Hello, " + name + "!");
    Toast.makeText(this, "Greeted " + name, Toast.LENGTH_SHORT).show();
});
```

A few things to notice:

-   `getText()` returns an `Editable`, not a `String`. Add `.toString()`.
-   `trim()` removes stray spaces, so "   " counts as empty.
-   `setError` shows a small red message on the field itself. It's a better way to point at the problem than a popup.
-   `Toast.makeText(context, text, duration)` builds a short message at the bottom of the screen, and **`.show()`** actually displays it. Forgetting `.show()` is the classic Toast bug.

Inside a lambda, `this` still means the Activity, so `Toast.makeText(this, ...)` works. With an old-style anonymous class (`new View.OnClickListener() { ... }`) you'd need `MainActivity.this` instead.

## Step 3: Parse numbers without crashing

`android:inputType="numberDecimal"` shows a number keyboard, but the field can still be empty, or hold just ".". `Double.parseDouble("")` throws a `NumberFormatException`, and an uncaught exception crashes the app. Wrap the parse in `try`/`catch`:

```java
public class SafeParse {

    // Returns the number in text, or -1 if text is not a valid number.
    static double parseOrMinusOne(String text) {
        try {
            return Double.parseDouble(text.trim());
        } catch (NumberFormatException e) {
            return -1;
        }
    }

    public static void main(String[] args) {
        String[] inputs = {"42.50", "  18 ", "", ".", "abc"};
        for (String input : inputs) {
            System.out.println("\"" + input + "\" -> " + parseOrMinusOne(input));
        }
    }
}
```

```text
"42.50" -> 42.5
"  18 " -> 18.0
"" -> -1.0
"." -> -1.0
"abc" -> -1.0
```

That is plain Java, so you can test it with `javac` before you put it in an app. In the app, you check for `-1` and call `setError` instead of crashing.

## Step 4: The Activity lifecycle

An Activity doesn't just "run." Android moves it through states and calls a method each time:

-   `onCreate`: the Activity is created. Call `setContentView`, find views, set listeners.
-   `onStart`: it's becoming visible. Start things the user can see.
-   `onResume`: it's in front and receiving taps. Resume animations or sensors.
-   `onPause`: it's losing focus (a dialog or another app on top). Pause quick work.
-   `onStop`: it's no longer visible. Save drafts, stop heavy work.
-   `onDestroy`: it's being destroyed. Do final cleanup.

You can watch it happen by overriding the methods and logging:

```java
private static final String TAG = "Lifecycle";

@Override
protected void onStart() {
    super.onStart();
    Log.d(TAG, "onStart");
}
```

Always call `super` first in these methods, or the app throws a `SuperNotCalledException`.

### Rotation destroys your Activity

Here's the surprise: when the phone rotates, Android **destroys the Activity and creates a brand-new one** so it can load the landscape layout. If you log every method and rotate once, Logcat shows:

```text
onPause
onStop
onDestroy
onCreate
onStart
onResume
```

Every normal field (like `int count`) starts over in the new object. Views that have an id keep some of their own state; an `EditText` keeps its typed text. But a `TextView` you changed in code goes back to its XML text.

### Saving state with a Bundle

Before destroying the Activity, Android calls `onSaveInstanceState` and hands you a `Bundle`, a small key-value box. You put values in; the new Activity gets the same Bundle in `onCreate`:

```java
private static final String KEY_COUNT = "count";
private int count = 0;

@Override
protected void onSaveInstanceState(@NonNull Bundle outState) {
    super.onSaveInstanceState(outState);
    outState.putInt(KEY_COUNT, count);
}

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);
    if (savedInstanceState != null) {
        count = savedInstanceState.getInt(KEY_COUNT, 0);
    }
    // ...find views and show count...
}
```

`savedInstanceState` is `null` the first time the app opens and holds your data after a rotation. Bundles have `putInt`, `putString`, `putDouble`, `putBoolean`, and matching getters. Keep it small: numbers and short strings, not huge lists or images.

### Optional: ViewModel

A `ViewModel` is an object that Android keeps alive across rotation, so you don't have to pack and unpack a Bundle:

```java
import androidx.lifecycle.ViewModel;

public class CounterViewModel extends ViewModel {
    public int count = 0;
}
```

```java
CounterViewModel model = new ViewModelProvider(this).get(CounterViewModel.class);
model.count++;
```

`ViewModelProvider` comes from `androidx.lifecycle`, which the template's AppCompat library already pulls in. The catch is that a ViewModel survives rotation but **not** Android killing your app in the background, while a Bundle survives both. Bigger apps often use both.
