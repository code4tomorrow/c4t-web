A recycling plant has a machine that sorts aluminum cans from plastic bottles on a conveyor belt. It doesn't "see" a can the way you do. For each object it measures two numbers: how heavy it is, and how much light bounces off it. That's all it gets. A crushed can and a plastic bottle wrapped in foil look almost the same to it.

Every machine learning model works like this. It never sees the thing itself, only the numbers someone chose to measure about it. Choose well and the job is easy. Choose badly and no amount of training will help.

## Data is a table

Here's what the sorter's training data looks like:

| Weight (g) | Shininess (0–10) | See-through? | Label |
| --- | --- | --- | --- |
| 15 | 8 | no | Can |
| 21 | 3 | yes | Plastic |
| 14 | 7 | no | Can |
| 19 | 4 | yes | Plastic |
| 17 | 6 | no | Can |
| 16 | 5 | no | Plastic |

Three words describe every part of it:

-   **Example**: one row. One object that went past the sensors.
-   **Feature**: one column the model gets to look at. Weight, shininess, see-through.
-   **Label**: the column with the right answer, filled in by a person. It's the thing the model is learning to produce.

A model trained on rows like these is doing **supervised learning**: learning from examples where the answer is supplied. Clustering, from Module 2, is the unsupervised version: the same table with the label column missing.

The label isn't a fixed part of the data; it depends on your question. Give the same table a label column of "recycling value in cents", and you're training a regression model on identical features.

## The features decide what a model can notice

Look at the last row of the table: a dull, 16-gram piece of plastic. On weight alone, it sits right among the cans. Here's what happens across 40 objects when the model gets one feature, and then two:

```python run alt="Two panels. Left: cans and plastic bottles plotted along a weight axis only, heavily mixed together between 13 and 18 grams. Right: the same objects plotted by weight and shininess; cans sit in the upper area and bottles in the lower area, separated by a slightly tilted line, with blue shading above it and orange shading below." caption="Weight alone can't separate cans from bottles; add shininess and a line can"
import numpy as np
import matplotlib.pyplot as plt
from sklearn.linear_model import LogisticRegression

rng = np.random.default_rng(1)
BLUE, ORANGE = "#2a78d6", "#eb6834"
# 20 cans and 20 plastic bottles: weight in grams, shininess from 0 to 10
cans = np.column_stack([rng.normal(15, 2.5, 20), rng.normal(7.5, 1.0, 20)])
bottles = np.column_stack([rng.normal(18, 3.5, 20), rng.normal(4.0, 1.1, 20)])
X = np.vstack([cans, bottles])
y = np.array([0] * 20 + [1] * 20)

fig, (left, right) = plt.subplots(1, 2, figsize=(11, 4), gridspec_kw={"width_ratios": [1, 1.2]})

# Left: weight is the only feature
jitter = rng.uniform(-0.15, 0.15, 40)
left.scatter(cans[:, 0], 0.5 + jitter[:20], color=BLUE, marker="o", label="Can")
left.scatter(bottles[:, 0], 0.5 + jitter[20:], color=ORANGE, marker="^", label="Plastic bottle")
left.set_ylim(0, 1)
left.set_yticks([])
left.set_xlabel("Weight (g)")
left.set_title("One feature: weight only", loc="left")
left.legend(frameon=False, loc="upper left")

# Right: weight and shininess, with the boundary a model learned
model = LogisticRegression().fit(X, y)
gx, gy = np.meshgrid(np.linspace(8, 27, 300), np.linspace(0, 11, 300))
pred = model.predict(np.column_stack([gx.ravel(), gy.ravel()])).reshape(gx.shape)
right.contourf(gx, gy, pred, levels=[-0.5, 0.5, 1.5], colors=["#d6e6f8", "#fbe0d4"])
right.contour(gx, gy, pred, levels=[0.5], colors="#555555", linewidths=1.5)
right.scatter(*cans.T, color=BLUE, marker="o", label="Can")
right.scatter(*bottles.T, color=ORANGE, marker="^", label="Plastic bottle")
right.set_xlabel("Weight (g)")
right.set_ylabel("Shininess (0 to 10)")
right.set_title("Two features: weight and shininess", loc="left")
right.text(8.5, 10.2, "model says Can", color="#1d5aa3")
right.text(21, 0.5, "model says Plastic", color="#b4471c")

for ax in (left, right):
    ax.spines[["top", "right"]].set_visible(False)
fig.tight_layout()
print("Correct on its own training examples:", f"{model.score(X, y):.0%}")
```

**Left panel.** With only weight, the model has a single number line. Cans and bottles overlap between about 13 and 18 grams, so wherever you put a cut-off, many objects land on the wrong side. This is the loudness rule from the clap detector all over again.

**Right panel.** Add shininess and the two groups pull apart: cans high, bottles low. The model learned the gray line, called the **decision boundary**. Everything in the blue region gets called a can, everything in the orange region plastic. A new object is placed on this chart by its two measurements, and the color under it is the prediction.

Two things to notice. First, one can lands on the wrong side (a dull, dented one near weight 17, shininess 5). Even good features leave some overlap, which is why the printout says 98%, not 100%. Second, the model never chose to look at shininess. *We* chose to measure it. Picking features is a human decision, and it often matters more than anything the model does afterward.

## Training versus inference

A model has two separate lives, and keeping them apart clears up most confusion about how machine learning works:

```mermaid caption="Training needs labels; inference is the reason labels aren't available"
flowchart LR
    subgraph T [Training: happens once]
        A["Examples: features + labels"] --> B[Learning algorithm] --> C[Model]
    end
    subgraph I [Inference: happens every time]
        D["New object: features only"] --> E[Model] --> F[Predicted label]
    end
```

**Training** uses the full table, labels included, to produce the model. **Inference** is using the model: a new object arrives, its features are measured, and the model supplies the label. There's no label at inference time; if there were, you wouldn't need a model.

That leads to a rule worth memorizing: **every feature must be available at the moment of prediction.** A feature measured after the fact is useless, however well it predicts during training.

## Pictures and sounds are tables too

When you trained the thumbs model, where were the features? Every image is already a table of numbers. Here's an 8×8 scan of a handwritten digit that ships with the scikit-learn library, printed as numbers and then drawn:

```python run alt="An 8 by 8 grid of grey squares that forms a handwritten zero, shown next to the 64 numbers that describe it." caption="A tiny image: 64 features, one label"
import matplotlib.pyplot as plt
from sklearn.datasets import load_digits

digits = load_digits()
image = digits.images[0]          # an 8 x 8 scan of a handwritten digit
print("Label:", digits.target[0])
print("Features (0 = white, 16 = darkest):")
for row in image.astype(int):
    print(" ".join(f"{value:2d}" for value in row))

fig, ax = plt.subplots(figsize=(3, 3))
ax.imshow(image, cmap="Greys")
ax.set_xticks([])
ax.set_yticks([])
ax.set_title("The same 64 numbers, drawn", loc="left", fontsize=10)
```

You can see the zero in the numbers if you squint: a ring of high values around a middle of zeros. This one image is one row of a table with 64 feature columns, and its label is 0.

Teachable Machine's photos are 224×224 pixels in color, which is 224 × 224 × 3 = 150,528 numbers per example. Raw pixels make poor features, though: move your hand two centimeters and almost every number changes. So Teachable Machine first runs each picture through a network Google already trained on a huge collection of photos (it's called MobileNet), which turns the pixels into a much shorter list of more useful features, things closer to "edges here, a round shape there". Your classes are learned on top of those. This trick is called **transfer learning**, and it's why your model trained in under a minute on a hundred photos.

The consequence is important for the next lesson: in Teachable Machine you don't choose features. You only choose examples. Examples are your one steering wheel.

## Labels come from people, and people disagree

Somebody filled in the label column. Is a juice box paper or plastic? Is a can with a plastic label a can? If two people labeled the same objects differently, the model learns a blur of both opinions. Teams that label data write a **labeling rule** first ("anything with a metal body is a Can, whatever its label") and check that labelers agree. Module 5 returns to what happens when the people or examples behind a dataset are lopsided.

:::warning
**A feature that secretly contains the label.** Suppose the sorter's table had a column "which bin a worker put it in". It would predict perfectly in training, because it *is* the label written another way. At inference time there's no worker, so the column doesn't exist. If a feature seems too good to be true, ask whether it's the answer in disguise. This is called **leakage**.
:::

:::warning
**Features that look like numbers but carry no meaning.** A student ID or a row number is a number, but a model will happily find patterns in it (maybe IDs assigned later belong to younger students). That pattern won't hold for new data. Only use features that plausibly relate to the answer.
:::

:::quiz
Q: A model predicts whether a student will pass a course, using a table with columns: hours of sleep, homework done (%), attendance (%), and final exam score. What's wrong with this setup if predictions are needed in week 3?
- [ ] Hours of sleep isn't a number
  It is a number, and it could plausibly matter.
- [x] Final exam score doesn't exist in week 3, and it nearly gives away the answer
  Every feature must be available when the prediction is made. This one leaks the label and arrives too late.
- [ ] There aren't enough columns
  Four features can be plenty. The problem is which ones, not how many.

Q: On the right-hand chart, a new object weighs 24 g and has a shininess of 9. What does the model predict?
- [ ] Plastic, because it's heavy
  Weight alone would suggest that, but the model uses both features. At shininess 9 it's above the line.
- [x] Can, because that point falls in the blue region above the boundary
  Find 24 on the weight axis and 9 on the shininess axis: the region there is blue.
- [ ] It can't predict, because no training example looks like that
  A model always predicts; the boundary covers every point. Whether to trust a prediction far from the training data is a separate question.

Q: Same objects, same sensors, but now the label column is "recycling value in cents". What changed?
- [x] The task is now regression, because the label is a number on a scale
  The features are identical. Changing the question changes the label, and the label decides the task.
- [ ] Nothing, because the features are the same
  The features are the same, but the model is now learning to produce a different kind of answer.
- [ ] The task is now clustering
  There's still a label column filled in by people, so it's still supervised.

Q: In Teachable Machine, what's the main way you control which features your model relies on?
- [ ] Typing in the features you want
  Teachable Machine doesn't let you choose features. A pre-trained network computes them from each picture.
- [x] Choosing which examples go into each class
  The model leans on whatever reliably differs between your classes, so varied examples steer it toward what you care about.
- [ ] Renaming the classes
  The model never reads class names.
:::

:::takeaways
- A dataset is a table: each row is an example, the columns are features, and the label is the answer a person supplied.
- The features decide what a model can tell apart; picking them is a human choice that often matters most.
- A decision boundary divides the feature space; a new example gets the label of the region it lands in.
- Training uses features and labels; inference sees features only, so every feature must exist at prediction time.
- Images are tables of numbers too. Teachable Machine computes features for you, so your examples are how you steer it.
:::
