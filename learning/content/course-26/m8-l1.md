For six weeks you've built programs someone else designed. The capstone flips that around. **You** decide what to build, and you use everything from this course to make it work from start to finish.

In almost every class, the best projects don't come from the most ambitious ideas. They come from students who picked something they genuinely care about, like a quiz on their favorite game, a tool for their sport, or a joke generator for their little brother. Those students keep wanting to make their program better, so they test it more, fix more, and add more.

## The brief

Build a **text game, quiz, or tool of your choice** in Python that runs in IDLE.

### Your program must use

| Requirement | Looks like |
| --- | --- |
| Variables | `score = 0`, `name = input(...)` |
| User input | at least one `input()` the program reacts to |
| Conditions | `if` / `elif` / `else` that make a real decision |
| A loop | `for` or `while`, for example a game round or "play again?" |
| A list | storing questions, items, scores, rooms, or answers |
| At least two functions you define | with `def`, and at least one that takes a parameter or returns a value |

### What you hand in

1.  **A `.py` file that runs** from top to bottom without crashing on normal use.
2.  **A test table** showing at least 6 inputs you tried, including **unusual** ones (a blank answer, letters where a number goes, capital letters, a number that's too big), with what you expected and what actually happened.
3.  **One bug you found and fixed**, written up in a few sentences: what went wrong, the error message if there was one, and how you fixed it.
4.  **A short demo** of 2 to 4 minutes, where you run the program and walk through one piece of your code.

The last two lessons in this module walk you through building it in milestones and then testing and presenting it, so you won't face any of this alone.

## The smallest program that ticks every box

If that list looks like a lot, here's a program of about 30 lines that already meets every requirement. Yours will be bigger and much more *you*, but this proves the list is very doable. In this run, Jordan orders popcorn, lemonade, a menu item that doesn't exist, and more popcorn:

```python run title="snack_stand.py" input="Jordan|1|3|7|1|done"
# Snack Stand: a tiny program that meets every capstone requirement

snacks = ["popcorn", "pretzel", "lemonade"]    # list
prices = [3, 4, 2]


def show_menu():                                # function 1
    for i in range(len(snacks)):                # loop
        print(f"{i + 1}. {snacks[i]} ${prices[i]}")


def order_total(order):                         # function 2 (takes a parameter, returns a value)
    total = 0
    for number in order:
        total = total + prices[number - 1]
    return total


name = input("Name for the order: ")            # input + variable
order = []
show_menu()
pick = input("Item number (or done): ")
while pick != "done":                           # loop
    if pick == "1" or pick == "2" or pick == "3":   # condition
        order.append(int(pick))
    else:
        print("That's not on the menu.")
    pick = input("Item number (or done): ")

print(name + ", you ordered", len(order), "items.")
print(f"Your total is ${order_total(order)}")
```

Notice that `pick` is checked as *text* (`"1"`) before `int()` ever sees it. That's why typing `7`, or even `banana`, prints a friendly message instead of crashing. Also notice `prices[number - 1]`: the menu shows 1, 2, 3, but the list's indexes are 0, 1, 2. That's the same translation you did in the to-do list app.

## Pick a project

Choose one idea, mix two, or invent your own. The levels are a guide to how much work each one takes, not a grade. A polished Starter project beats an unfinished Stretch project every time.

| Level | Idea | What makes it interesting |
| --- | --- | --- |
| Starter | **Dice duel.** Two players take turns rolling with `random.randint(1, 6)`; first to 20 wins. | A `while` loop that stops at a target, and a running total for each player |
| Starter | **Grade calculator.** Enter scores, get the average, the letter grade, and what you need on the final. | A list of scores, a `letter_grade()` function, and input checking |
| Starter | **Rock, paper, scissors, best of 5.** The computer picks with `random.choice(["rock", "paper", "scissors"])`. | `if` / `elif` rules for who wins, and a score for each side |
| Solid | **Trivia quiz** on a topic you know cold: soccer, Minecraft, Marvel, a country, a book series. | Questions and answers in two lists, a score, and a percentage at the end |
| Solid | **Study flashcards** for a real class, which repeat the cards you missed. | Moving missed cards into a second list, then looping over that list again |
| Solid | **Budget tracker.** Add income and expenses, then see the balance and the biggest expense. | A menu loop like the to-do app, plus totals and a "biggest so far" |
| Stretch | **Word guess** (like Hangman). Show `_ _ a _`, track the letters guessed, and count wrong guesses. | Building the display string with a loop over the secret word |
| Stretch | **Choose-your-path adventure.** Each room is a function, and the player's inventory is a list. | Functions that call other functions, and decisions that depend on what's in the list |

`random.choice(some_list)` picks one item from a list at random. It lives in the same `random` module as `randint`, so it needs `import random` at the top of your file too.

:::tip
Scope your project so you could finish the basic version in about half the time you have. You can always add features once it works. A small program that runs beats a giant one that crashes, and it gives you something calm to demo.
:::

## Plan before you code

Spend 20 minutes on paper, or in a comment block at the top of your file. It'll save you hours of rewriting later. Copy this template and fill in every line:

```text
PROJECT PLAN
Name of my program:
One sentence: what does it do, and who is it for?

What the user types (inputs):
What the program shows (outputs):

My list(s) will hold:
My loop repeats:
Decisions my program makes (if/elif/else):

Functions (name - what it gets - what it gives back):
  1.
  2.
  3.

Must-have features (the basic version):
Nice-to-have features (only after the basic version works):
```

Planning in plain words before code has a name: **pseudocode**. You describe each step the way you'd explain it to a friend, then turn each step into Python later.

### Write out one run, step by step

Next, write down everything a person sees and types during one complete run of your program. This is the script your code has to follow. For a trivia quiz it might be:

```text
1. Program says welcome and explains the rules
2. Asks the player's name
3. Asks question 1 -> player answers -> "Correct!" or shows the right answer
4. Repeats step 3 for every question in the list
5. Shows the score and a message based on how well they did
6. Asks "Play again?" -> back to step 3, or says goodbye
```

Now draw it. Any step that points back to an earlier step is a loop, and every diamond is an `if`. Here's the quiz script above as a flowchart:

```mermaid caption="Arrows that point backwards are loops; diamonds are decisions"
flowchart TD
    A[Welcome and rules] --> B[Ask the player's name]
    B --> C[Ask the next question]
    C --> D{Answer right?}
    D -->|yes| E[Correct! Add a point]
    D -->|no| F[Show the right answer]
    E --> G{More questions?}
    F --> G
    G -->|yes| C
    G -->|no| H[Show score and message]
    H --> I{Play again?}
    I -->|yes| C
    I -->|no| J[Goodbye]
```

Two backwards arrows means two loops: a `for` over the questions, inside a `while` for playing again. You've just designed the structure of your program without writing a line of Python.

### Name your functions now

Good function names are verbs that say what the function does: `ask_question`, `show_menu`, `roll_dice`, `get_number`, `calculate_average`. If you can't name a function in two or three words, it's probably doing too many jobs, so split it in two. Look at your flowchart: a box you visit more than once, like "Ask the next question", is a strong candidate for a function.

## Planning mistakes to avoid

:::warning
**Too big.** "An RPG with 20 levels, shops, and a boss fight" won't fit. "One dungeon with 3 rooms and a key" will, and it can still be great.

**No list.** If your idea doesn't naturally need one, find a place it helps: past guesses, high scores, menu items, questions.

**Functions as an afterthought.** Plan at least two now. Squeezing them in at the end means rewriting code that already works.
:::

:::takeaways
- The capstone needs variables, input, conditions, a loop, a list, and at least two of your own functions.
- You hand in four things: the `.py` file, a test table, one bug write-up, and a short demo.
- Pick a project you care about, at a size you can finish in half your time.
- Plan on paper first: inputs, outputs, lists, loops, decisions, and function names.
- Write out one full run. Backwards arrows become loops, and repeated steps become functions.
:::
