Your program works when *you* use it, because you know exactly what to type. Your classmates don't. In your demo, someone will press Enter without typing anything, or type `YES` in capitals, or answer a number question with a word. This lesson is about finding those problems before your audience does, then showing what you built with confidence.

Testing isn't a single step at the end. It's a loop: try an input, check the result, fix what failed, and then re-run the earlier tests, because a fix in one place can break another.

```mermaid caption="The test-fix loop: every fix sends you back to re-run your tests"
flowchart TD
    A[Pick an input from your test table] --> B[Run from a fresh start]
    B --> C{Did it do what you expected?}
    C -->|yes| D[Mark it Pass and pick the next input]
    D --> A
    C -->|no| E[Find the cause and fix it]
    E --> F[Re-run all the earlier tests too]
    F --> A
```

## Step 1: Build a test table

A **test table** lists the inputs you tried, what you expected, and what actually happened. Aim for at least 6 rows, and make at least half of them **unusual** inputs: the kind a real person types by accident.

Unusual inputs worth trying in almost any program:

-   **Blank:** press Enter without typing anything.
-   **Different capitals:** `MARS`, `Mars`, `mArS`.
-   **Extra spaces:** ` y ` or `  milky way`.
-   **Wrong type:** a word where a number goes (`three`), or a decimal where a whole number goes (`2.5`).
-   **Out of range:** `0`, `-1`, `999`, or menu option `7` when there are only 3.
-   **The extremes:** everything right, everything wrong, an empty list.

Here's the real test table for the Space Trivia quiz from the last lesson:

| # | What I typed | Expected | What happened | Pass? |
| --- | --- | --- | --- | --- |
| 1 | All five answers spelled exactly right | 5/5, "Perfect!" | 5/5 (100%), "Perfect! Mission control is impressed." | Yes |
| 2 | All five answers wrong | 0/5, "Keep exploring" | 0/5 (0%), "Keep exploring and try again!" | Yes |
| 3 | `mercury` (lowercase) | Correct | Correct! | Yes |
| 4 | `  JUPITER  ` (capitals and spaces) | Correct | Correct! | Yes |
| 5 | Blank answer (just Enter) | Wrong, with no crash | "Not quite. The answer is Mercury" | Yes |
| 6 | `eight` instead of `8` | Should probably count | Marked wrong | No (known limit) |
| 7 | `milky  way` (two spaces in the middle) | Correct | Marked wrong | No (known limit) |
| 8 | `yes` at "Play again?" | Ask again | "Please type y or n." | Yes |
| 9 | ` N ` at "Play again?" | Quit | Quit and showed the best score | Yes |

Rows 6 and 7 fail, and that's fine to hand in. A test table isn't supposed to be all "Yes". Its job is to prove you **know** how your program behaves. For each "No", either fix it or write one sentence about why you left it. For example: "Answers must be typed as digits, so the welcome message now says so."

:::tip
Run each test from a fresh start (press F5 again), not halfway through an earlier run. Bugs that depend on what happened earlier in a run are real, but they're much harder to pin down. Start simple.
:::

## Step 2: Write up one bug you found and fixed

Every program has bugs along the way. Pick a real one, ideally one your test table caught, and write it up in this format:

```text
BUG REPORT
What I did:       Typed "mercury" (lowercase) for question 1.
What I expected:  "Correct!"
What happened:    "Not quite. The answer is Mercury" - marked wrong.
Error message:    None (it was a logic error).
Cause:            I compared reply == answers[i], and "mercury" is not
                  equal to "Mercury" because Python checks capital letters.
Fix:              Cleaned up the reply with .strip().lower() and compared
                  it with answer.lower(), so capitals and extra spaces
                  no longer matter.
```

Here's that bug for real. This is the M2 version from the last lesson, run with a lowercase `mercury`:

```python run title="space_trivia.py" input="mercury|8|Jupiter"
questions = [
    "What planet is closest to the Sun?",
    "How many planets are in our solar system?",
    "What is the largest planet?",
]
answers = ["Mercury", "8", "Jupiter"]

score = 0
for i in range(len(questions)):
    reply = input(questions[i] + " ")
    if reply == answers[i]:
        print("Correct!")
        score = score + 1
    else:
        print("Not quite. The answer is", answers[i])
print("Score:", score)
```

The player knew all three answers and still scored 2. No error message, just a wrong result: a classic logic error. The fix, from the finished program, cleans up both sides of the comparison:

```python
    reply = input("Q" + str(number) + ": " + question + " ").strip().lower()
    if reply == answer.lower():
```

### If your program crashes on bad input

Tools that ask for numbers often crash the first time someone types a word. Here's the first line of a grade calculator, given `three`:

```python run raises title="grades.py" input="three"
count = int(input("How many test scores? "))
```

That's a perfect bug for your write-up, and the fix is one you've already built: a helper like `get_whole_number` from the Week 6 pizza planner. It keeps asking until `text.isdigit()` is `True`, and only then calls `int()`.

## Step 3: Polish

Polish is what turns "it works" into "I'd show this to someone". Go through this list one item at a time:

-   **Header comment** at the top with the project name, your name, and one sentence on what it does.
-   **Clear names.** Rename `x`, `thing2`, and `a` to names like `score`, `guess`, and `item_price`. In IDLE, **Edit > Replace...** can rename every copy at once, but check each one.
-   **Every function** has a name that says what it does, and a one-line docstring if that isn't obvious.
-   **No leftover debugging prints** like `print("i is", i)`.
-   **Friendly messages.** Tell the user what to type (`(y/n)`, `1-3`, `or done`) and what went wrong when they slip up.
-   **Readable output.** Blank lines from `print()` between rounds or sections.
-   **No copy-paste code.** If the same four lines appear twice, they probably belong in a function.
-   **A final fresh run.** Close IDLE, reopen your file, and run it once more from the start.

## Step 4: Present it

Your demo is 2 to 4 minutes. Here's a structure that works:

1.  **The pitch (20 seconds).** What is it, and who is it for? "This is a space trivia quiz for my little brother, who's obsessed with planets."
2.  **A live run (1 to 2 minutes).** Play through once, and include one unusual input on purpose to show it's handled: "Watch what happens if I type YES instead of y."
3.  **One piece of code (1 minute).** Show a function you're proud of, and explain what it takes in and what it returns.
4.  **Your bug story (30 seconds).** What broke, how you found it, and how you fixed it.
5.  **What's next (10 seconds).** One feature you'd add with more time.

:::warning
Plan your demo inputs ahead of time and practice them once. If something crashes live, don't panic. Read the last line of the traceback out loud and explain what it means. Reading an error calmly is exactly the skill this course has been building, and it impresses people far more than a demo where nothing goes wrong.
:::

## Check your work against the rubric

Use this rubric to check your own project before you hand it in. Aim for the middle column in every row, and the right-hand column in at least one.

| Area | Not yet | Meets the brief | Goes further |
| --- | --- | --- | --- |
| **Runs** | Crashes on normal input | Runs start to finish from a fresh start | Also survives every unusual input in your table |
| **Requirements** | One or more missing | Variables, input, conditions, a loop, a list, and 2+ functions | Functions that take parameters *and* return values, used more than once |
| **Code quality** | Unclear names, copy-pasted blocks | Header comment, clear names, no debugging prints | Docstrings, constants, and a short, readable main program |
| **Testing** | Fewer than 6 rows, or only normal inputs | 6+ rows, at least half unusual, with expected vs. actual | Every "No" is either fixed or explained |
| **Bug write-up** | Missing, or "it didn't work" | What happened, the error (if any), the cause, and the fix | Explains how you tracked it down, such as which print or test found it |
| **Demo** | Code shown but not run | Pitch, live run, one function explained, bug story | Shows an unusual input being handled on purpose |

## Final checklist

**Requirements**

-   The program uses **variables** to store information that changes.
-   It uses **`input()`**, and its behavior depends on what the user types.
-   It has **`if` / `elif` / `else`** making real decisions.
-   It has at least one **loop** (`for` or `while`).
-   It uses at least one **list**.
-   It defines at least **two functions** with `def`, and at least one takes a parameter or returns a value.

**Deliverables**

-   A **`.py` file** that runs from a fresh start without crashing on normal input.
-   A **test table** with at least 6 rows, including unusual inputs, with expected and actual results.
-   **One bug write-up**: what happened, the error message (if any), the cause, and the fix.
-   A **demo** of 2 to 4 minutes: the pitch, a live run, one function explained, and your bug story.

You started this course by printing one line of text. Now you're handing in a complete program that takes input, makes decisions, repeats work, stores data, and is organized into functions, along with proof that you tested it. That's real programming.
