Your program works when *you* use it, because you know exactly what to type. Your classmates don't. In the demo, someone will press Enter without typing anything, or type `YES` in capitals, or answer a number question with a word. This lesson is about finding those problems before your audience does, then presenting what you built with confidence.

## Step 1: Build a test table

A **test table** lists inputs you tried, what you expected, and what actually happened. Aim for at least 6 rows, and make at least half of them **unusual** inputs, the kind a real user might type by accident.

Good unusual inputs to try in almost any program:

-   **Blank:** press Enter without typing.
-   **Different capitals:** `MARS`, `Mars`, `mArS`.
-   **Extra spaces:** ` y ` or `  milky way`.
-   **Wrong type:** a word where a number goes (`three`), or a decimal where a whole number goes (`2.5`).
-   **Out of range:** `0`, `-1`, `999`, or menu option `7` when there are only 3.
-   **The edges:** everything right, everything wrong, an empty list.

Here's the real test table for the Space Trivia quiz from the last lesson:

| # | What I typed | Expected | What happened | Pass? |
| --- | --- | --- | --- | --- |
| 1 | All five answers spelled exactly right | 5/5, "Perfect!" | 5/5 (100%), "Perfect! Mission control is impressed." | Yes |
| 2 | All five answers wrong | 0/5, "Keep exploring" | 0/5 (0%), "Keep exploring and try again!" | Yes |
| 3 | `mercury` (lowercase) | Correct | Correct! | Yes |
| 4 | `  JUPITER  ` (capitals and spaces) | Correct | Correct! | Yes |
| 5 | Blank answer (just Enter) | Wrong, with no crash | "Not quite. The answer is Mercury" | Yes |
| 6 | `eight` instead of `8` | Hmm, should probably count | Marked wrong | No (known limit) |
| 7 | `milky  way` (two spaces in the middle) | Correct | Marked wrong | No (known limit) |
| 8 | `yes` at "Play again?" | Ask again | "Please type y or n." | Yes |
| 9 | ` N ` at "Play again?" | Quit | Quit and showed the best score | Yes |

Rows 6 and 7 fail, and that's fine to hand in. A test table isn't supposed to be all "Yes". Its job is to show you **know** how your program behaves. For each "No", either fix it or write one sentence about why you left it. For example: "Answers must be spelled with digits. The welcome message could say so."

:::tip
Run your tests from a fresh start every time (F5), not halfway through an earlier run. Bugs that depend on what happened before are real, but they're much harder to track down.
:::

## Step 2: Write up one bug you found and fixed

Every program has bugs along the way. Pick a real one, ideally one your test table caught. Use this format:

```text
BUG REPORT
What I did:       Typed "mercury" (lowercase) for question 1.
What I expected:  "Correct!"
What happened:    "Not quite. The answer is Mercury" - marked wrong.
Error message:    None (it was a logic error).
Cause:            I compared reply == answers[i], and "mercury" is not
                  equal to "Mercury" because Python checks capital letters.
Fix:              Cleaned up the reply with .strip().lower() and compared
                  it with answer.lower(), so capitals and extra spaces
                  no longer matter.
```

Here's that bug in action. This is the M2 version from last lesson:

```text
What planet is closest to the Sun? mercury
Not quite. The answer is Mercury
How many planets are in our solar system? 8
Correct!
What is the largest planet? Jupiter
Correct!
Score: 2
```

The fix, from the finished program:

```python
    reply = input("Q" + str(number) + ": " + question + " ").strip().lower()
    if reply == answer.lower():
```

### If your program crashes on bad input

Tools that ask for numbers often crash the first time someone types a word:

```text
How many test scores? three
Traceback (most recent call last):
  File "/Users/you/grades.py", line 2, in <module>
    count = int(input("How many test scores? "))
ValueError: invalid literal for int() with base 10: 'three'
```

That's a perfect bug for your write-up. The fix is a helper function like `get_whole_number` from the Week 6 pizza planner. It keeps asking until `text.isdigit()` is `True`, and only then calls `int()`.

## Step 3: Polish

Polish is what turns "it works" into "I'd show this to someone". Go through this list:

-   **Header comment** at the top with the project name, your name, and one sentence on what it does.
-   **Clear names.** Rename `x`, `thing2`, and `a` to names like `score`, `guess`, and `item_price`.
-   **Every function** has a name that says what it does, and a one-line docstring or comment if it isn't obvious.
-   **Remove debugging prints** like `print("i is", i)`.
-   **Friendly messages.** Tell the user what to type (`(y/n)`, `1-3`, `or done`) and what went wrong when they make a mistake.
-   **Readable output.** Add blank lines with `print()` between rounds or sections.
-   **No copy-paste code.** If the same 4 lines appear twice, they probably belong in a function.
-   **A final fresh run.** Close IDLE, reopen your file, and run it once more from the start.

## Step 4: Present it

Your demo is 2–4 minutes. Here's a structure that works:

1.  **The pitch (20 seconds).** What is it and who is it for? "This is a space trivia quiz for my little brother, who's obsessed with planets."
2.  **Live run (1–2 minutes).** Play through once. Include one unusual input on purpose to show it's handled: "Watch what happens if I type YES instead of y."
3.  **One piece of code (1 minute).** Show a function you're proud of and explain what it takes in and what it returns.
4.  **Your bug story (30 seconds).** What broke, how you found it, and how you fixed it.
5.  **What's next (10 seconds).** One feature you'd add with more time.

:::warning
Plan your demo inputs ahead of time and practice them once. If something crashes live, don't panic. Read the last line of the traceback out loud and explain what it means. Reading an error calmly is exactly the skill this course is about, and teachers notice.
:::

## Final checklist

Go through this before you submit.

**Requirements**

-   The program uses **variables** to store information that changes.
-   It uses **`input()`**, and its behavior depends on what the user types.
-   It has **`if` / `elif` / `else`** making real decisions.
-   It has at least one **loop** (`for` or `while`).
-   It uses at least one **list**.
-   It defines at least **two functions** with `def`, and at least one takes a parameter or returns a value.

**Deliverables**

-   A **`.py` file** that runs from a fresh start without crashing on normal input.
-   A **test table** with at least 6 rows, including unusual inputs, with expected and actual results.
-   **One bug write-up**: what happened, the error message (if any), the cause, and the fix.
-   A **demo** of 2–4 minutes: the pitch, a live run, one function explained, and your bug story.

**Quality**

-   Header comment, clear variable and function names, and no leftover debugging prints.
-   Messages tell the user what to type and what went wrong.

You started this course by printing one line of text. Now you're handing in a complete program that takes input, makes decisions, repeats work, stores data, and is organized into functions. That's real programming. Be proud of it, and keep building.
