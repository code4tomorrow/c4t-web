You've switched on the GPU. Here is the error you're most likely to meet next, word for word as PyTorch prints it:

```text
RuntimeError: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu!
```

A GPU has its own memory, separate from the computer's main RAM. Every tensor lives in exactly one of those places, and PyTorch will not quietly copy data between them, because copying is slow and doing it by accident inside a training loop would wreck your speed without telling you. So the rule is simple: **everything that meets in one operation must already be on the same device.** This lesson gives you the handful of habits that make that automatic.


## One line picks the device

Start every notebook with this. Make a new cell in `dlcv-setup.ipynb` and run it:

```python run
import torch
import torch.nn as nn

device = "cuda" if torch.cuda.is_available() else "cpu"
print("device:", device)
```

This page was built on a machine without CUDA, so it prints `cpu`. In Colab with a T4 it prints `cuda`. From here on, write `device` everywhere instead of typing `"cuda"`, and the same notebook runs unchanged on a GPU runtime, a CPU runtime, or your laptop.

:::note
Recent PyTorch versions also have `torch.accelerator.current_accelerator()`, which picks whatever accelerator the machine has, including Apple's `mps`. This course uses the explicit CUDA check because Colab's GPUs are NVIDIA ones and the explicit line is easier to read.
:::

## Tensors: `.to()` hands you a copy

`.to()` converts a tensor to another device or dtype. For tensors it **returns a new tensor** and leaves the original alone. Predict what this prints before you run it:

```python run
x = torch.randn(4, 3)
print("start:          ", x.dtype)

x.to(torch.float64)          # converts a copy... and throws the copy away
print("after x.to(...):", x.dtype)

x = x.to(torch.float64)      # keep the converted copy
print("after x = ...:  ", x.dtype)
```

The middle line does real work and then discards it, so `x` is unchanged. Moving between devices behaves the same way: `x.to(device)` on a line by itself leaves `x` on the CPU, and the device error shows up later, far from the line that caused it. Always assign: `x = x.to(device)`.

You can also skip the copy by creating a tensor where it will be used: `torch.randn(4, 3, device=device)`.

## Models: `.to()` moves the parameters in place

Modules work differently. `model.to(device)` moves the model's weights in place and returns the same model, so assigning is optional. Here's a small network of the kind you'll build in Module 2, moved to the device along with a batch of 16 fake inputs:

```python run
model = nn.Sequential(nn.Linear(64, 32), nn.ReLU(), nn.Linear(32, 10))
model.to(device)                                   # moves every weight; no assignment needed

batch = torch.randn(16, 64).to(device)             # tensors still need the assignment
out = model(batch)

print("weights on:", next(model.parameters()).device)
print("output:    ", tuple(out.shape), "on", out.device)
```

`next(model.parameters())` grabs the first weight tensor, a quick way to ask where a model lives. The pattern you'll use in every training loop: move the model **once**, right after building it, then move **each batch** as it comes out of the data loader. Forget the second part and you get the error from the top of this lesson, naming `cuda:0` and `cpu`.

The device error has a CPU twin you can trigger right here: the model's weights are `float32`, so a `float64` batch can't meet them.

```python run raises
wrong = torch.randn(16, 64, dtype=torch.float64)
model(wrong.to(device))
```

Same idea, different attribute. Two tensors in one operation must agree on device **and** dtype. NumPy arrays are `float64` by default, so this one bites whenever you build tensors from NumPy; `.float()` fixes it.

## Coming back to the CPU: `.item()`, `.detach()`, `.cpu()`

NumPy and matplotlib can only read CPU memory, and they know nothing about gradients. That's why plotting a model's output often fails the first time:

```python run raises
out.numpy()
```

`out` came from a model whose weights are tracked for gradients (you'll see why in Module 3), so PyTorch refuses to hand it to NumPy as-is. On a GPU the same call fails for a second reason too:

```text
TypeError: can't convert cuda:0 device type tensor to numpy. Use Tensor.cpu() to copy the tensor to host memory first.
```

The full return trip is a chain, and the order is worth memorizing:

```python run
values = out.detach().cpu().numpy()      # stop tracking, copy to CPU, convert
print(type(values).__name__, values.shape)

loss = out.pow(2).mean()
print("loss as a Python number:", round(loss.item(), 4))
```

`.detach()` drops the gradient tracking, `.cpu()` copies to main memory (and does nothing if the tensor is already there), and `.numpy()` shares that memory with a NumPy array. For a single number, such as a loss, `.item()` does the whole trip and returns a plain Python float. You'll call `loss.item()` in every training loop in this course.

## Timing GPU code honestly

GPU calls are **asynchronous**: when Python reaches `a @ b`, it queues the work for the GPU and moves straight on. If you stop a timer right after, you measure how long it took to queue the job, not to do it. `torch.cuda.synchronize()` waits until the GPU has finished everything queued so far. Paste this into Colab and run it once on a CPU runtime and once on the T4:

```python
import time

import torch

device = "cuda" if torch.cuda.is_available() else "cpu"


def time_matmul(n, device, repeats=5):
    a = torch.randn(n, n, device=device)
    b = torch.randn(n, n, device=device)
    a @ b                              # warm-up: the first call pays one-time setup costs
    if device == "cuda":
        torch.cuda.synchronize()
    start = time.perf_counter()
    for _ in range(repeats):
        a @ b
    if device == "cuda":
        torch.cuda.synchronize()       # wait until the GPU has really finished
    return (time.perf_counter() - start) / repeats


for n in [512, 1024, 2048, 4096]:
    seconds = time_matmul(n, device)
    tflops = 2 * n**3 / seconds / 1e12
    print(f"n={n:5d}  {seconds * 1000:9.2f} ms  {tflops:6.2f} TFLOP/s")
```

Each row reports the time for one `n × n` multiplication and the speed it implies. On the T4, the speed should climb as `n` grows, because small matrices can't keep thousands of GPU cores busy. Write both sets of numbers down; you'll want them when you choose between CPU and GPU runs in Module 7.

:::try
Delete both `torch.cuda.synchronize()` lines and run it again on the T4. The times collapse to almost nothing and the "TFLOP/s" column climbs past anything the hardware can actually do. That impossible number is what an unsynchronized timer looks like.
:::

:::quiz
Q: A training loop has the line `xb.to(device)` on its own, followed by `pred = model(xb)`. The model was moved to `cuda`. What happens?
- [ ] It works, because `.to()` moves `xb` in place
  That's true for modules, not tensors. For a tensor, `.to()` returns a moved copy, and this line throws it away.
- [x] It fails with "Expected all tensors to be on the same device"
  `xb` is still on the CPU while the weights are on `cuda:0`. Writing `xb = xb.to(device)` fixes it.
- [ ] PyTorch copies `xb` to the GPU automatically, just more slowly
  PyTorch never copies between devices behind your back; it raises an error instead.

Q: Your timer says a 4096 × 4096 matrix multiply on the T4 took 0.03 ms, which works out to thousands of TFLOP/s. What's the most likely explanation?
- [ ] The T4 is much faster than NVIDIA's specification
  No chip beats its own peak rating by that much. The measurement is wrong, not the hardware.
- [x] The timer stopped before the GPU finished, because nothing called `torch.cuda.synchronize()`
  GPU work is queued asynchronously, so without a synchronize you timed the queueing. Synchronize before reading the clock.
- [ ] PyTorch cached the answer from the warm-up run
  PyTorch doesn't cache results of matrix multiplications; every call does the arithmetic again.

Q: You want to plot `preds`, a model output on the GPU. Which line works?
- [ ] `plt.plot(preds.numpy())`
  This fails twice over: `preds` is on the GPU and it's tracked for gradients.
- [ ] `plt.plot(preds.cpu())`
  Copying to the CPU is necessary but not enough; the tensor is still tracked for gradients, so the conversion to NumPy fails.
- [x] `plt.plot(preds.detach().cpu().numpy())`
  Stop tracking, copy to main memory, then convert. That's the full return trip.
:::
