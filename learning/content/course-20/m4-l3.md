## Warm-up: what should the first loss be?

An untrained classifier spreads its probability roughly evenly, so its cross-entropy starts near `−ln(1/C) = ln C` for `C` classes. Predict the starting loss for 2, 10, and 26 classes, then check:

```python run
import math

for classes in [2, 10, 26]:
    print(f"{classes:2d} classes: starting loss about {math.log(classes):.3f}")
```

If your 10-class model starts at 2.3, initialization is sane. If it starts at 15, the logits are huge, usually because inputs weren't scaled, and the first epochs will be spent undoing that.

## Setup: data and a training helper

Run this once. It splits the digits into training and validation sets and defines `train_run`, which trains a two-hidden-layer network with the settings you give it and returns per-epoch history.

```python run
import matplotlib.pyplot as plt
import torch
import torch.nn as nn
from sklearn.datasets import load_digits
from sklearn.model_selection import train_test_split
from torch.utils.data import DataLoader, TensorDataset

digits = load_digits()
X_all = torch.tensor(digits.data, dtype=torch.float32) / 16.0      # (1797, 64), already flat
y_all = torch.tensor(digits.target)
X_train, X_val, y_train, y_val = train_test_split(X_all, y_all, test_size=0.25, stratify=y_all, random_state=0)
loss_fn = nn.CrossEntropyLoss()


def make_mlp(width=64, dropout=0.0):
    return nn.Sequential(
        nn.Linear(64, width), nn.ReLU(), nn.Dropout(dropout),
        nn.Linear(width, width), nn.ReLU(), nn.Dropout(dropout),
        nn.Linear(width, 10),
    )


def train_run(lr, epochs=40, n_train=None, width=64, dropout=0.0, weight_decay=0.0, momentum=0.0, seed=0):
    torch.manual_seed(seed)
    xt, yt = (X_train, y_train) if n_train is None else (X_train[:n_train], y_train[:n_train])
    loader = DataLoader(TensorDataset(xt, yt), batch_size=32, shuffle=True)
    model = make_mlp(width, dropout)
    opt = torch.optim.SGD(model.parameters(), lr=lr, momentum=momentum, weight_decay=weight_decay)
    history = {"train_loss": [], "val_loss": [], "val_acc": []}
    for epoch in range(epochs):
        model.train()
        total, seen = 0.0, 0
        for xb, yb in loader:
            opt.zero_grad()
            loss = loss_fn(model(xb), yb)
            loss.backward()
            opt.step()
            total += loss.item() * len(yb)
            seen += len(yb)
        model.eval()
        with torch.no_grad():
            out = model(X_val)
        history["train_loss"].append(total / seen)
        history["val_loss"].append(loss_fn(out, y_val).item())
        history["val_acc"].append((out.argmax(dim=1) == y_val).float().mean().item())
    return history


print("train:", tuple(X_train.shape), "| val:", tuple(X_val.shape))
```

### Exercise 1: the honest epoch average

A loader produced three batches with these mean losses and sizes. Compute the naive average of the three numbers and the correct per-example average.

```python
batch_losses = [0.30, 0.28, 2.10]
batch_sizes = [64, 64, 3]
```

```text
naive mean of batch means: 0.893
per-example mean:          0.331
```

:::hint
The correct average gives every **example** equal weight. Each batch mean stands for `size` examples, so multiply before you add, then divide by the total number of examples.
:::

:::solution
```python run
batch_losses = [0.30, 0.28, 2.10]
batch_sizes = [64, 64, 3]

naive = sum(batch_losses) / len(batch_losses)
weighted = sum(loss * n for loss, n in zip(batch_losses, batch_sizes)) / sum(batch_sizes)
print(f"naive mean of batch means: {naive:.3f}")
print(f"per-example mean:          {weighted:.3f}")
```

The 3-example batch, probably a few odd digits left over at the end of an epoch, nearly triples the naive figure. Weighting it by its size gives those 3 examples the influence of 3 examples. If you set `drop_last=True` on the training loader, every batch is the same size and the two averages agree.
:::

### Exercise 2: accuracy that's only wrong sometimes

This accuracy function runs without complaint on a batch of 10, where every prediction is right, and reports 0.0. On a batch of 16 it crashes. Explain both results, then fix it.

```python run
def accuracy(logits, labels):
    return (logits.argmax(dim=0) == labels).float().mean().item()


torch.manual_seed(0)
logits10 = torch.randn(10, 10)
labels10 = logits10.argmax(dim=1)          # labels the model gets 100% right
print("batch of 10:", accuracy(logits10, labels10))
```

```python run raises
logits16 = torch.randn(16, 10)
accuracy(logits16, logits16.argmax(dim=1))
```

:::hint
`logits` has shape `(batch, classes)`. Which dimension does `argmax(dim=0)` collapse, and what shape is left? Why does that shape happen to match the labels when the batch size is 10?
:::

:::solution
`argmax(dim=0)` finds the highest-scoring **example** for each class, giving one number per class, shape `(10,)`. With a batch of 10 that matches the labels' shape by coincidence, so the comparison runs and returns a wrong answer. With 16 examples it's `(10,)` against `(16,)`, which can't broadcast. The class dimension is 1:

```python run
def accuracy(logits, labels):
    return (logits.argmax(dim=1) == labels).float().mean().item()


print("batch of 10:", accuracy(logits10, labels10))
print("batch of 16:", accuracy(logits16, logits16.argmax(dim=1)))
```

The crash was the lucky case. Batch size equal to the number of classes is rare, but when it happens this bug reports a believable, wrong accuracy with no error at all. Test metric code on a batch size that differs from every other dimension.
:::

### Exercise 3: two silent bugs

This loop trains, prints, and never errors. It also has two bugs. The prints give both away; find them and fix the loop.

```python run
torch.manual_seed(0)
model = nn.Sequential(nn.Linear(64, 64), nn.ReLU(), nn.Dropout(0.5), nn.Linear(64, 10))
optimizer = torch.optim.SGD(model.parameters(), lr=0.1)
train_loader = DataLoader(TensorDataset(X_train, y_train), batch_size=32, shuffle=True)


def validate(model):
    model.eval()
    with torch.no_grad():
        return loss_fn(model(X_val), y_val).item()


model.train()
for epoch in range(3):
    running = 0
    print(f"epoch {epoch}: dropout active = {model.training}")
    for xb, yb in train_loader:
        optimizer.zero_grad()
        loss = loss_fn(model(xb), yb)
        loss.backward()
        optimizer.step()
        running += loss
    print(f"   running is a {type(running).__name__}, tracked by autograd: {running.grad_fn is not None}")
    print(f"   val loss {validate(model):.3f}")
```

:::hint
Bug 1: what does `validate` leave the model in, and who switches it back? Bug 2: what kind of object does `running` become after the first `+= loss`, and what does it keep a reference to?
:::

:::solution
**Bug 1:** `validate` calls `model.eval()`, and nothing calls `model.train()` again, so dropout is off for epochs 1 and 2. **Bug 2:** `running += loss` turns `running` into a tensor that's part of the autograd graph, so every batch's graph stays in memory until the epoch ends. On a GPU with a large model, that's how you run out of memory halfway through an epoch. The fix moves `model.train()` inside the epoch loop and uses `.item()`:

```python run
torch.manual_seed(0)
model = nn.Sequential(nn.Linear(64, 64), nn.ReLU(), nn.Dropout(0.5), nn.Linear(64, 10))
optimizer = torch.optim.SGD(model.parameters(), lr=0.1)

for epoch in range(3):
    model.train()                       # every epoch, not once
    running, seen = 0.0, 0
    for xb, yb in train_loader:
        optimizer.zero_grad()
        loss = loss_fn(model(xb), yb)
        loss.backward()
        optimizer.step()
        running += loss.item() * len(yb)   # a plain float, weighted by batch size
        seen += len(yb)
    print(f"epoch {epoch}: dropout was active = {model.training} | train {running / seen:.3f} | val {validate(model):.3f}")
```

Putting `model.train()` at the top of each epoch means no helper function can leave the model in the wrong mode.
:::

### Exercise 4: predict the curves, then train

Using `train_run`, four runs are planned. Before running anything, sketch the training and validation loss curves you expect for each over 40 epochs:

- **A:** `lr=0.001`
- **B:** `lr=0.1`
- **C:** `lr=2.0`
- **D:** `lr=0.05, momentum=0.9`, but only `n_train=150` examples and a much wider network, `width=512`

Then run all four and plot them side by side.

:::hint
Think back to the learning-rate sweep in Module 3: where on that curve do 0.001 and 2.0 sit? For D, compare the number of weights with the number of training examples.
:::

:::solution
```python run alt="Four small line charts in a grid, each showing training and validation loss over 40 epochs. A, learning rate 0.001: both curves sit almost flat near 2.3, barely sloping down. B, learning rate 0.1: both fall together, ending near 0.03 and 0.12, though validation loss jumps up on a few epochs, once as high as 2.0, and recovers each time. C, learning rate 2.0: validation loss starts above the top of the chart, then both curves sit flat near 2.3 for the rest of training. D, 150 examples and width 512: training loss falls to nearly zero, while validation loss reaches its low point near 0.3 around epoch 18 and then creeps up to about 0.36." caption="A crawls, B learns, C breaks and stays broken, D memorizes."
runs = {
    "A: lr 0.001": train_run(lr=0.001),
    "B: lr 0.1": train_run(lr=0.1),
    "C: lr 2.0": train_run(lr=2.0),
    "D: 150 examples, width 512": train_run(lr=0.05, momentum=0.9, n_train=150, width=512),
}

fig, axes = plt.subplots(2, 2, figsize=(9, 5.6), sharex=True)
for ax, (name, h) in zip(axes.flat, runs.items()):
    ax.plot(h["train_loss"], color="#2a78d6", linewidth=2, label="train")
    ax.plot(h["val_loss"], color="#eb6834", linewidth=2, label="validation")
    ax.set_title(name, fontsize=10)
    ax.set_ylim(0, 2.6)
    ax.spines[["top", "right"]].set_visible(False)
    best = min(range(40), key=lambda e: h["val_loss"][e])
    print(f"{name:28s} final train {h['train_loss'][-1]:.3f}  final val {h['val_loss'][-1]:.3f}  best val {h['val_loss'][best]:.3f} at epoch {best + 1}")
axes[0, 0].legend(frameon=False)
for ax in axes[1]:
    ax.set_xlabel("epoch")
plt.tight_layout()
plt.show()
```

**A** is the crawl: correct direction, far too small steps, still near `ln 10` after 40 epochs. **B** is healthy: both curves fall together. The occasional validation spikes come from the last few batches of an epoch knocking the weights off course, with the next epoch recovering. Spikes on an otherwise good curve hint that the learning rate is near the top of its safe range, and Exercise 6 will agree. **C** is the interesting one. It doesn't produce `nan`; a few huge early steps push most ReLU units into the dead zone, and the network is left predicting roughly uniform probabilities, stuck at 2.3 forever. That's the "stuck at about 2.30" row of the field guide, caused by a learning rate rather than a bug in the code. **D** is overfitting: the training loss heads for zero, and the validation loss turns upward after its best epoch.
:::

### Exercise 5: early stopping

Write a class `EarlyStopper(patience)` with a method `step(val_loss)` that returns `True` when training should stop: when the validation loss hasn't set a new best for `patience` epochs in a row. It should also remember the best epoch. Test it on this sequence with `patience=3`:

```python
val_losses = [0.90, 0.70, 0.60, 0.62, 0.58, 0.59, 0.61, 0.60, 0.63, 0.64]
```

```text
stop after epoch 8 | best epoch 5 (loss 0.58)
```

:::hint
Keep three numbers: the best loss so far, the epoch it happened, and a counter of epochs since then. A new best resets the counter to 0; anything else adds 1.
:::

:::solution
```python run
class EarlyStopper:
    def __init__(self, patience):
        self.patience = patience
        self.best_loss = float("inf")
        self.best_epoch = 0
        self.epoch = 0
        self.bad_epochs = 0

    def step(self, val_loss):
        self.epoch += 1
        if val_loss < self.best_loss:
            self.best_loss, self.best_epoch, self.bad_epochs = val_loss, self.epoch, 0
        else:
            self.bad_epochs += 1
        return self.bad_epochs >= self.patience


val_losses = [0.90, 0.70, 0.60, 0.62, 0.58, 0.59, 0.61, 0.60, 0.63, 0.64]
stopper = EarlyStopper(patience=3)
for loss in val_losses:
    if stopper.step(loss):
        break
print(f"stop after epoch {stopper.epoch} | best epoch {stopper.best_epoch} (loss {stopper.best_loss})")
```

Epoch 4 (0.62) is worse than 0.60, but epoch 5 sets a new best and resets the counter, so a single bad epoch doesn't end training. Epochs 6, 7, and 8 all fail to beat 0.58, and it stops. In a real loop you'd save a `deepcopy` of the weights whenever `best_epoch` changes, and load them after stopping. Patience trades time for safety: validation loss is noisy, so a patience of 1 stops on the first unlucky epoch.
:::

### Exercise 6: a learning-rate range test

Instead of guessing a learning rate, measure. Train for 100 batches while multiplying the learning rate by a constant factor every batch, from `1e-4` up to `10`. Record a smoothed loss at each step and stop early if it climbs above 4 times the best so far. Plot loss against learning rate on a log axis.

:::hint
The factor is `(10 / 1e-4) ** (1 / 100)`. Set the rate each step with `for group in optimizer.param_groups: group["lr"] = lr`. For smoothing, keep `smooth = 0.8 * smooth + 0.2 * loss.item()`.
:::

:::solution
```python run alt="Line chart of smoothed training loss against learning rate on a log scale from 0.0001 to about 8. The loss stays flat near 2.3 from 0.0001 to about 0.3, dips to its lowest point, a little above 2.0, near a learning rate of 1.8, then becomes bumpy and shoots off the top of the chart. A dashed line at about 0.18 marks the suggested rate." caption="Flat, then falling, then exploding. A safe choice sits about ten times below the minimum."
import math

torch.manual_seed(0)
model = make_mlp()
optimizer = torch.optim.SGD(model.parameters(), lr=1e-4)
loader = DataLoader(TensorDataset(X_train, y_train), batch_size=32, shuffle=True)

lr, steps = 1e-4, 100
factor = (10 / lr) ** (1 / steps)
rates, smoothed = [], []
smooth, best = None, float("inf")
batches = iter(loader)
for step in range(steps):
    try:
        xb, yb = next(batches)
    except StopIteration:              # start a new pass if the data runs out
        batches = iter(loader)
        xb, yb = next(batches)
    for group in optimizer.param_groups:
        group["lr"] = lr
    optimizer.zero_grad()
    loss = loss_fn(model(xb), yb)
    loss.backward()
    optimizer.step()
    smooth = loss.item() if smooth is None else 0.8 * smooth + 0.2 * loss.item()
    rates.append(lr)
    smoothed.append(smooth)
    best = min(best, smooth)
    if smooth > 4 * best or math.isnan(smooth):
        break
    lr *= factor

lowest = min(range(len(smoothed)), key=smoothed.__getitem__)
suggested = rates[lowest] / 10
print(f"lowest loss at lr {rates[lowest]:.2f} | suggested lr {suggested:.2f} | stopped at lr {rates[-1]:.2f}")

fig, ax = plt.subplots(figsize=(6.4, 3))
ax.plot(rates, smoothed, color="#2a78d6", linewidth=2)
ax.axvline(suggested, color="#52514e", linestyle="--", linewidth=1)
ax.set_xscale("log")
ax.set_xlabel("learning rate (log scale)")
ax.set_ylabel("smoothed training loss")
ax.set_ylim(1.8, 3.6)
ax.spines[["top", "right"]].set_visible(False)
plt.show()
```

Below about 0.3 the steps are too small to move the loss in 100 batches. The loss reaches its lowest point near 1.8, then turns bumpy and explodes (the chart clips the final spike). The rule of thumb is to pick a rate about ten times smaller than the minimum, giving 0.18 here: just above run B in Exercise 4, which trained well with a few spikes, and about 11 times below run C, which broke. A range test costs about one-sixth of an epoch's worth of compute, far less than a sweep of full runs.
:::

### Challenge: beat the overfitter without more data

Run D from Exercise 4 overfit badly. Keep its data (150 examples), width (512), and optimizer settings, and improve its **best** validation loss using any mix of dropout, `weight_decay` (which shrinks every weight a little at each step), and early stopping with your `EarlyStopper`. Report the baseline and your version side by side: best validation loss, the accuracy at that epoch, and the epoch where early stopping would have ended training.

:::hint
Dropout makes memorizing individual examples harder; weight decay keeps weights small. Try `dropout=0.5` with `weight_decay=1e-3` for 60 epochs, then replay each run's validation losses through an `EarlyStopper(patience=8)`.
:::

:::solution
```python run
settings = dict(lr=0.05, momentum=0.9, n_train=150, width=512, epochs=60)
results = {
    "baseline": train_run(**settings),
    "dropout 0.5 + weight decay 1e-3": train_run(**settings, dropout=0.5, weight_decay=1e-3),
}

for name, h in results.items():
    stopper = EarlyStopper(patience=8)
    for val_loss in h["val_loss"]:
        if stopper.step(val_loss):
            break
    best = stopper.best_epoch - 1
    print(f"{name:32s} best val loss {h['val_loss'][best]:.3f} at epoch {best + 1:2d}, "
          f"accuracy {h['val_acc'][best]:.3f}, early stop after epoch {stopper.epoch}")
```

The regularized network reaches a lower best validation loss and a higher accuracy at that point. Early stopping helps both runs differently: for the baseline it ends training soon after the turn, while the regularized network keeps improving for longer because it's slower to memorize. The improvement is real but modest, which is the honest lesson: with 150 examples, regularization can only do so much. More data, or a model that bakes in what images look like (Module 5's convolutions), moves the needle further.
:::
