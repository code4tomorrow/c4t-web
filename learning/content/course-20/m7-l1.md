Two weeks ago a teammate posted "97.8% on the test set!" in the project chat. Today nobody can get above 95%. Was it a different seed? A different split? A learning rate someone changed and changed back? The notebook has been edited since, and the cell that printed 97.8% no longer exists.

Even if the number were reproducible, it would leave out two things a reader needs: what the run cost (time, GPU memory), and **who** the remaining 2.2% of errors land on. This lesson covers all three: recording runs, budgeting resources, and evaluating for real.

## What a run record needs

A result is reproducible when someone else can rerun it from your record alone. That takes six things:

| Record | Example | Why |
| --- | --- | --- |
| Config | learning rate, batch size, epochs, augmentation | Every choice that changes the result |
| Seeds | `seed=0` for weights, batch order, augmentation | Randomness is part of the run |
| Data | dataset version and the exact split (seed or index file) | A different split is a different experiment |
| Code | the git commit hash | The code changes more often than you think |
| Environment | torch and torchvision versions, GPU name | Defaults and kernels change between versions |
| Results | per-epoch metrics, final metrics, time, peak memory | The curve, not just the last number |

Start with seeds. Here's a tiny training run on the digits, run three times:

```python run
import csv
import json
import time
import torch
import torch.nn as nn
import torch.nn.functional as F
from sklearn.datasets import load_digits
from sklearn.model_selection import train_test_split

digits = load_digits()
X = torch.tensor(digits.images, dtype=torch.float32).unsqueeze(1) / 16
y = torch.tensor(digits.target)
X_train, X_val, y_train, y_val = train_test_split(X, y, test_size=0.25, random_state=0, stratify=y)

def run(config):
    torch.manual_seed(config["seed"])
    model = nn.Sequential(nn.Flatten(), nn.Linear(64, config["hidden"]), nn.ReLU(), nn.Linear(config["hidden"], 10))
    opt = torch.optim.SGD(model.parameters(), lr=config["lr"])
    rows = []
    for epoch in range(1, config["epochs"] + 1):
        for idx in torch.randperm(len(y_train)).split(config["batch_size"]):
            loss = F.cross_entropy(model(X_train[idx]), y_train[idx])
            opt.zero_grad()
            loss.backward()
            opt.step()
        with torch.no_grad():
            val_acc = (model(X_val).argmax(1) == y_val).float().mean().item()
        rows.append({"epoch": epoch, "last_batch_loss": round(loss.item(), 4), "val_acc": round(val_acc, 4)})
    return rows

base = {"seed": 0, "lr": 0.1, "hidden": 32, "batch_size": 32, "epochs": 3}
first, again, other = run(base), run(base), run({**base, "seed": 1})
print("same seed twice, identical:", first == again)
print("seed 0 final:", first[-1])
print("seed 1 final:", other[-1])
```

The same seed gives bit-for-bit the same numbers, and changing only the seed moves the result. That second fact matters as much as the first: if seed 1 scores lower than seed 0, a 0.5-point "improvement" from a new idea may just be noise. Run important comparisons with three or more seeds and report the spread.

:::note
On a GPU, the same seed can still give slightly different numbers, because some CUDA kernels add floating-point values in a nondeterministic order. `torch.use_deterministic_algorithms(True)` forces deterministic versions (and raises an error for operations that have none), and `torch.backends.cudnn.benchmark = False` stops cuDNN from picking different algorithms between runs. Both can cost speed.
:::

## Logging every run to one file

A CSV file with one row per epoch per run is a perfectly good experiment tracker. Each row carries the run's id and config, so you can filter and plot later; a JSON file next to it holds the environment.

```python run
import platform

def log_run(config, rows, path="runs.csv"):
    run_id = f"lr{config['lr']}_h{config['hidden']}_s{config['seed']}"
    fields = ["run_id", *config.keys(), *rows[0].keys()]
    with open(path, "a", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=fields)
        if f.tell() == 0:
            writer.writeheader()
        for row in rows:
            writer.writerow({"run_id": run_id, **config, **row})
    env = {"torch": torch.__version__, "python": platform.python_version(),
           "device": "cuda" if torch.cuda.is_available() else "cpu", "logged_at": time.strftime("%Y-%m-%d %H:%M")}
    with open(f"{run_id}.json", "w") as f:
        json.dump({"config": config, "env": env}, f, indent=1)
    return run_id

log_run(base, first)
log_run({**base, "seed": 1}, other)
print(open("runs.csv").read())
```

**TensorBoard** does the same job with live charts. In Colab, `SummaryWriter` writes event files under `runs/`, and the notebook commands `%load_ext tensorboard` and `%tensorboard --logdir runs` open the dashboard inside the notebook. Colab has TensorBoard installed; on a machine without it, the import below fails with an error until you install the `tensorboard` package.

```python
from torch.utils.tensorboard import SummaryWriter

writer = SummaryWriter(log_dir="runs/lr0.1_h32_s0")
for row in first:
    writer.add_scalar("loss/last_batch", row["last_batch_loss"], row["epoch"])
    writer.add_scalar("accuracy/val", row["val_acc"], row["epoch"])
writer.add_hparams({"lr": 0.1, "hidden": 32, "seed": 0}, {"hparam/val_acc": first[-1]["val_acc"]})
writer.close()
```

Pick one tool and use it for every run, including the ones that fail. The failed runs are what tell you which ideas you've already tried.

## Where GPU memory goes

During training with Adam in float32, GPU memory holds four things:

- **Weights:** 4 bytes per parameter.
- **Gradients:** another 4 bytes per parameter.
- **Adam's state:** two running averages per parameter, 8 more bytes.
- **Activations:** every layer's output, saved for the backward pass. This part grows with batch size and image size.

The first three are fixed: 16 bytes per parameter. The fourth is the one you control. You can estimate it on a CPU by adding up the size of every layer's output for one image:

```python run alt="Line chart of estimated training memory for ResNet-18 at 224 by 224 against batch size on a doubling scale from 8 to 512. The estimate climbs from about 0.4 GB at batch 8 to about 15.5 GB at batch 512, just above a dashed line marking the roughly 15 GB a Colab T4 has available." caption="A rough lower bound: real use adds the CUDA context and allocator overhead, so leave headroom"
import matplotlib.pyplot as plt
from torchvision import models

net = models.resnet18(weights=None)
params = sum(p.numel() for p in net.parameters())
fixed_gb = params * 16 / 1e9                         # weights + gradients + Adam state

saved = []
for module in net.modules():
    if not list(module.children()):                  # leaf layers only
        module.register_forward_hook(lambda m, i, out: saved.append(out.numel()))
net(torch.zeros(1, 3, 224, 224))
per_image_gb = sum(saved) * 4 / 1e9
print(f"fixed: {fixed_gb:.2f} GB   activations per image: {per_image_gb * 1000:.0f} MB")

batches = [8, 16, 32, 64, 128, 256, 512]
plt.figure(figsize=(6, 3))
plt.plot(batches, [fixed_gb + b * per_image_gb for b in batches], marker="o", color="#7892ee")
plt.axhline(15, ls="--", color="#d9534f")
plt.text(10, 15.3, "Colab T4: about 15 GB usable", color="#d9534f", fontsize=9)
plt.xscale("log", base=2)
plt.xticks(batches, [str(b) for b in batches])
plt.xlabel("batch size")
plt.ylabel("GB")
plt.gca().spines[["top", "right"]].set_visible(False)
plt.tight_layout()
plt.show()
```

For ResNet-18 the fixed part is under 0.2 GB; activations are nearly everything. Doubling the batch size doubles activation memory. Doubling the image's width and height multiplies it by four, because every feature map has four times as many pixels. When a batch doesn't fit, PyTorch stops with `torch.OutOfMemoryError: CUDA out of memory. Tried to allocate ...`. The usual fixes, in order: halve the batch size, turn on mixed precision, or keep the batch size and use **gradient accumulation** (call `backward()` on several small batches and `step()` once).

Measure instead of guessing once you're on the GPU. On a CPU runtime these calls raise an error, because there is no CUDA device:

```python
torch.cuda.reset_peak_memory_stats()
# ... run one full training step here ...
print(f"peak: {torch.cuda.max_memory_allocated() / 2**30:.2f} GiB")
print(torch.cuda.get_device_name(0))
```

## Mixed precision: half the bytes, with a safety net

**float16** stores a number in 2 bytes instead of float32's 4. That halves activation memory, and GPUs like the T4 have tensor cores that multiply float16 matrices much faster than float32 ones. The catch is range: float16 can't represent numbers smaller than about 6 × 10⁻⁸, and small gradients are often that small.

```python run
grad = torch.tensor(1e-8)
print("float16 directly:     ", grad.half().item())
scaled = (grad * 65536).half()                      # scale up before converting
print("scaled, then unscaled:", scaled.float().item() / 65536)
```

That's exactly what a **gradient scaler** does: multiply the loss by a large factor so gradients survive in float16, then divide them back before the optimizer step (and skip the step if anything overflowed). **Autocast** decides which operations run in float16 (matrix multiplications and convolutions) and which stay in float32 (sums, softmax, losses). In a training loop on a GPU it looks like the code below; without a CUDA device and the rest of the loop defined, it stops with an error.

```python
scaler = torch.amp.GradScaler("cuda")
for xb, yb in loader:
    xb, yb = xb.to("cuda"), yb.to("cuda")
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        loss = F.cross_entropy(model(xb), yb)
    optimizer.zero_grad()
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()
```

Newer GPUs also support **bfloat16**, which keeps float32's range with less precision and usually doesn't need a scaler. The T4 doesn't have fast bfloat16, so on free Colab use float16 with the scaler.

## One accuracy number hides who the errors land on

In 2018, Joy Buolamwini and Timnit Gebru tested three commercial gender-classification systems, from Microsoft, Face++, and IBM, on 1,270 photos of parliament members, labeled by gender and by skin type. Their paper, *Gender Shades*, reported overall error rates of 6.3%, 10.0%, and 12.1%. Then they split the errors by subgroup:

```python run alt="Grouped bar chart of error rates by subgroup for three systems. For Microsoft, Face++, and IBM, the darker-skinned female bars are tallest at 20.8, 34.5, and 34.7 percent, while the lighter-skinned male bars are near zero at 0.0, 0.8, and 0.3 percent." caption="Error rates by subgroup, from Table 4 of Buolamwini and Gebru (2018)"
groups = ["darker female", "darker male", "lighter female", "lighter male"]
error = {"Microsoft": [20.8, 6.0, 1.7, 0.0], "Face++": [34.5, 0.7, 9.8, 0.8], "IBM": [34.7, 12.0, 7.1, 0.3]}
colors = ["#7892ee", "#f0ad4e", "#5cb85c"]

fig, ax = plt.subplots(figsize=(7, 3.2))
for i, (name, values) in enumerate(error.items()):
    ax.bar([g + (i - 1) * 0.27 for g in range(4)], values, width=0.27, label=name, color=colors[i])
ax.set_xticks(range(4), groups)
ax.set_ylabel("error rate (%)")
ax.legend(frameon=False)
ax.spines[["top", "right"]].set_visible(False)
plt.tight_layout()
plt.show()
```

Every system did worst on darker-skinned women, with error rates up to 34.7%. For lighter-skinned men, no system's error rate was above 0.8%. Three lessons carry over to any vision model:

1. **Slice the test set.** Report results per class and per subgroup, not only overall. The overall numbers above look acceptable; the slices don't.
2. **Slice by combinations.** Microsoft's error on women overall was 10.7% and on darker-skinned people overall 12.9%, but on darker-skinned women it was 20.8%. Single-attribute slices can hide the worst-served group.
3. **Check what you trained and tested on.** The paper found that two widely used face benchmarks were 79.6% and 86.2% lighter-skinned. A benchmark that underrepresents a group can't reveal how badly a model serves it.

For your own models, the same practice applies with whatever metadata you have: camera type, lighting, location, image size, the kind of document or the hospital a scan came from. Two more tools complete the picture: a **confusion matrix**, which shows which classes get mistaken for which, and a **failure gallery**, a grid of the actual misclassified images with their true and predicted labels. You'll build both in the next lesson.

:::warning
**`total_loss += loss` leaks memory.** `loss` is a tensor that still holds its computation graph, so adding it to a running total keeps every batch's graph alive, and memory grows until the run dies with an out-of-memory error. Use `total_loss += loss.item()`, which copies out a plain Python number.
:::

:::warning
**Don't report your luckiest run.** Training ten seeds and quoting the best test score is selecting on the test set. Choose settings on validation data, then report the test result as a mean and spread across seeds.
:::

:::quiz
Q: A model has 25 million parameters and trains with Adam in float32. Roughly how much memory do weights, gradients, and optimizer state take, before activations?
- [ ] 100 MB
  That's only the weights (25 million × 4 bytes).
- [ ] 200 MB
  Weights plus gradients; Adam adds two more values per parameter.
- [x] 400 MB
  4 + 4 + 8 = 16 bytes per parameter, times 25 million.

Q: Batch size 256 runs out of GPU memory, but you want the training to behave like batch 256. What do you change?
- [ ] Lower the learning rate
  The learning rate doesn't change memory use.
- [x] Use batches of 64 and accumulate gradients over 4 of them before each optimizer step
  Activations scale with the micro-batch size, and the summed gradients act like one batch of 256.
- [ ] Train for more epochs
  More epochs reuse the same memory per step; it still won't fit.

Q: Why does float16 training use a gradient scaler?
- [ ] float16 can't represent negative numbers
  It can; it has a sign bit like float32.
- [x] Small gradients round to zero in float16, so the loss is scaled up first and the gradients scaled back down before the step
  The scaler moves gradients into float16's representable range and back.
- [ ] It makes the model converge in fewer epochs
  It's about not losing gradients, not about speed of convergence.

Q: A model's overall error is 6%. Error is 1% for one subgroup and 21% for another. What's the most useful next step?
- [ ] Report 6%, since it averages over everyone
  The average is the number that hides the problem.
- [x] Report both subgroup numbers with their sample sizes, and check how well the second group is represented in the training and test data
  Disaggregated results are the finding; representation is the first place to look for a cause.
- [ ] Remove the second subgroup from the test set as outliers
  That hides the failure instead of fixing it.
:::

:::takeaways
- A reproducible result comes with its config, seeds, data split, code version, environment, and per-epoch metrics.
- The same seed reproduces a CPU run exactly; compare ideas across several seeds, because seed-to-seed noise is real.
- Training memory is about 16 bytes per parameter with Adam, plus activations that grow with batch and image size.
- Mixed precision halves activation memory and speeds up matrix math; float16 needs autocast and a gradient scaler.
- Evaluate per class and per subgroup, including combinations of attributes; overall accuracy can hide large failures.
:::
