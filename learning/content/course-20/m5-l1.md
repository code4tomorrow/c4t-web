Here is a fully connected network, the kind you trained in Module 4, on the 8×8 handwritten digits. It does well on the test set. Then we slide every test image one pixel to the right and score it again. Nothing else changes.

```python run
import torch
import torch.nn as nn
import torch.nn.functional as F
from sklearn.datasets import load_digits
from sklearn.model_selection import train_test_split

torch.manual_seed(0)
digits = load_digits()
X = torch.tensor(digits.images, dtype=torch.float32).unsqueeze(1) / 16  # (1797, 1, 8, 8), values 0 to 1
y = torch.tensor(digits.target)
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.25, random_state=0, stratify=y
)

def shift_right(images, pixels=1):
    moved = torch.zeros_like(images)
    moved[..., pixels:] = images[..., :-pixels]
    return moved

mlp = nn.Sequential(nn.Flatten(), nn.Linear(64, 128), nn.ReLU(), nn.Linear(128, 10))
opt = torch.optim.Adam(mlp.parameters(), lr=1e-3)
for epoch in range(15):
    order = torch.randperm(len(X_train))
    for i in range(0, len(order), 64):
        batch = order[i:i + 64]
        loss = F.cross_entropy(mlp(X_train[batch]), y_train[batch])
        opt.zero_grad()
        loss.backward()
        opt.step()

with torch.no_grad():
    clean = (mlp(X_test).argmax(1) == y_test).float().mean()
    moved = (mlp(shift_right(X_test)).argmax(1) == y_test).float().mean()
print(f"test accuracy, original images:  {clean:.1%}")
print(f"test accuracy, shifted one pixel: {moved:.1%}")
```

To you, a 3 moved one pixel over is still a 3. To this network it's a different input. Its first layer has a separate weight for every pixel position, so "ink at row 2, column 5" and "ink at row 2, column 6" are unrelated facts. It learned where the ink usually sits, not what the strokes look like.

A convolutional network builds in a different assumption: a stroke means the same thing wherever it appears. The rest of this page is the machinery that makes that assumption work.

## A kernel is a small pattern you slide across the image

Here's the intuition. Hold a 3×3 stencil of numbers over the top-left corner of the image. Multiply each stencil number by the pixel under it and add the nine products. The sum says how well that patch matches the stencil. Slide one pixel right and repeat, row by row. The grid of sums is called a **feature map**, and the stencil is the **kernel** (or filter).

Now precisely. For an image `I`, a k×k kernel `K`, and a bias `b`:

```text
out[i, j] = b + sum over u = 0..k-1 and v = 0..k-1 of  I[i + u, j + v] * K[u, v]
```

Take a 5×5 image that is dark (0) on the left and bright (9) in its last two columns, and the kernel below, which subtracts the left column of the patch from the right column. At the window starting in column 1, each row of the patch is `0, 0, 9`, so each row contributes −1·0 + 0·0 + 1·9 = 9, and three rows give 27. Check it with PyTorch:

```python run
image = torch.tensor([[0., 0., 0., 9., 9.]] * 5).reshape(1, 1, 5, 5)   # (batch, channels, height, width)
kernel = torch.tensor([[-1., 0., 1.]] * 3).reshape(1, 1, 3, 3)          # (out_ch, in_ch, k, k)
print(F.conv2d(image, kernel))
```

The output is 3×3, not 5×5, because a 3-wide window fits in only three positions across five columns. Where the window sits on flat dark pixels the answer is 0; where it straddles the edge, it's 27.

:::note
Mathematicians flip the kernel before sliding it; that's "true" convolution. PyTorch and every other deep-learning library skip the flip (strictly, it's cross-correlation). Since the network learns its kernels, the flip makes no difference, and everyone calls it convolution anyway.
:::

Step through the same sliding window written as plain loops. Watch `total` build up for each position, then land in `row`:

:::trace Slide a 3×3 kernel over a 4×4 image
```python
image = [[0, 0, 0, 9],
         [0, 0, 9, 9],
         [0, 9, 9, 9],
         [9, 9, 9, 9]]
kernel = [-1, 0, 1]          # the same row used three times
out = []
for i in range(2):
    row = []
    for j in range(2):
        total = 0
        for u in range(3):
            a, b, c = image[i + u][j:j + 3]
            total += -a + c
        row.append(total)
    out.append(row)
print(out)
```
:::

## An edge detector on a picture

The same arithmetic finds edges in a real picture. Below, two kernels go into one `conv2d` call as two output channels, so we get two feature maps at once. The first is the Sobel kernel for left-to-right changes (vertical edges), and the second is the same kernel turned on its side.

```python run alt="Three panels. Left: a white square and a white disk on black. Middle: the vertical-edge map, red along left edges of both shapes, blue along right edges, white elsewhere. Right: the horizontal-edge map, red along top edges, blue along bottom edges." caption="The left panel is the input; the other two are feature maps from two hand-made kernels"
import matplotlib.pyplot as plt

pic = torch.zeros(24, 24)
pic[4:12, 3:11] = 1.0                                    # a square
rows, cols = torch.meshgrid(torch.arange(24), torch.arange(24), indexing="ij")
pic[(rows - 16) ** 2 + (cols - 16) ** 2 <= 25] = 1.0     # a disk

sobel_x = torch.tensor([[-1., 0., 1.], [-2., 0., 2.], [-1., 0., 1.]])
weights = torch.stack([sobel_x, sobel_x.T]).unsqueeze(1)  # shape (2, 1, 3, 3)
maps = F.conv2d(pic.reshape(1, 1, 24, 24), weights, padding=1)[0]
print("feature maps:", tuple(maps.shape))

fig, axes = plt.subplots(1, 3, figsize=(8, 2.9))
axes[0].imshow(pic, cmap="gray")
axes[0].set_title("input")
for ax, fmap, name in zip(axes[1:], maps, ["vertical edges", "horizontal edges"]):
    ax.imshow(fmap, cmap="RdBu_r", vmin=-4, vmax=4)
    ax.set_title(name)
for ax in axes:
    ax.axis("off")
plt.tight_layout()
plt.show()
```

Inside each shape and in the background the patch is flat, so the kernel's positive and negative halves cancel to 0. On a left edge the patch goes dark-to-bright and the response is positive (red). A right edge gives the same size response with the opposite sign (blue). A CNN's first layer learns kernels much like these on its own, because edges are the cheapest clue to what's in an image.

## Stride and padding set the output size

Two settings change how the window moves:

- **Padding** `p` adds `p` rows and columns of zeros around the border, so the window can be centered on edge pixels.
- **Stride** `s` is how many pixels the window jumps each move. Stride 2 skips every other position and roughly halves the height and width.

For an input of size `n` and a kernel of size `k`, the output size is

```text
out = floor((n + 2p - k) / s) + 1
```

For an 8×8 digit with a 3×3 kernel: no padding gives (8 − 3)/1 + 1 = 6. Padding 1 gives (8 + 2 − 3)/1 + 1 = 8, the same size as the input. Padding 1 with stride 2 gives ⌊7/2⌋ + 1 = 4. Check the formula against real layers:

```python run
def conv_out(n, k, s=1, p=0):
    return (n + 2 * p - k) // s + 1

x = torch.zeros(1, 1, 8, 8)
for k, s, p in [(3, 1, 0), (3, 1, 1), (3, 2, 1), (5, 1, 2), (2, 2, 0)]:
    layer = nn.Conv2d(1, 4, kernel_size=k, stride=s, padding=p)
    print(f"k={k} s={s} p={p}: formula {conv_out(8, k, s, p)}, PyTorch {tuple(layer(x).shape)}")
```

The rule of thumb: kernel 3 with padding 1 (or kernel 5 with padding 2) keeps the size, which PyTorch also lets you write as `padding="same"` when the stride is 1.

## One small detector, shared across every position

A layer like `nn.Conv2d(1, 16, kernel_size=3)` holds 16 kernels of shape 1×3×3 plus 16 biases: 16 × 9 + 16 = 160 numbers. With `C_in` input channels, each kernel spans all of them, so the count is `C_out × C_in × k × k + C_out`. A fully connected layer producing the same 16×8×8 output from an 8×8 input would need 64 × 1,024 + 1,024 = 66,560.

The saving comes from **weight sharing**: the same 3×3 kernel is used at every position. That has a useful side effect. Shift the input, and the feature map shifts by exactly the same amount. Run a random conv layer both ways:

```python run
conv = nn.Conv2d(1, 4, kernel_size=3, padding=1)
x = X_test[:1]
shift_then_conv = conv(shift_right(x))
conv_then_shift = shift_right(conv(x))
gap = (shift_then_conv - conv_then_shift)[..., 1:-1].abs().max()
print("largest difference away from the border:", gap.item())
```

The two orders agree (only the border columns, where zero padding meets the image, can differ). This property is called **translation equivariance**. It's why a stroke detector trained on digits near the center still fires on digits near the edge. Notice the word "equivariant", not "invariant": the feature map moves with the input. A layer that later reads that map position by position can still be fooled, which is where pooling and augmentation come in.

## Pooling keeps the strongest nearby response

`nn.MaxPool2d(2)` splits each feature map into 2×2 blocks and keeps the largest value in each. It has no weights, and it halves height and width.

```python run
fmap = torch.zeros(1, 1, 4, 4)
fmap[0, 0, 0, 0] = 5.0                   # a strong response in the top-left corner
nudged = torch.zeros(1, 1, 4, 4)
nudged[0, 0, 1, 1] = 5.0                 # the same response, one pixel down and right
pool = nn.MaxPool2d(2)
print(pool(fmap)[0, 0])
print(pool(nudged)[0, 0])
```

Both give the same 2×2 result: the pooled map recorded that there's a strong response in the top-left block and threw away exactly where in the block it was. That tolerance only covers moves inside a block. A move across a block boundary still changes the output, so pooling buys a little shift tolerance, not immunity.

## Augmentation: train on the changes you expect

If test images may be shifted, tilted, or dimmer, show the model shifted, tilted, and dimmer training images with the same labels. That's **data augmentation**: a random, label-preserving change applied every time a training image is loaded, so each epoch sees a slightly different version of each image. You never augment validation or test images; they should look like the real inputs.

`torchvision.transforms.v2` provides the transforms. `RandomAffine` shifts and rotates, `ColorJitter` changes brightness and contrast:

```python run alt="A strip of eight small framed grayscale digits. The first is the original 7; the other seven are the same 7 shifted by a pixel or so, slightly tilted, and some with washed-out contrast." caption="One training image and seven augmented versions the model might see in different epochs"
from torchvision.transforms import v2

augment = v2.Compose([
    v2.RandomAffine(degrees=15, translate=(0.2, 0.2)),
    v2.ColorJitter(contrast=0.5),
])
original = X_train[0]                        # shape (1, 8, 8)
versions = [original] + [augment(original) for _ in range(7)]

fig, axes = plt.subplots(1, 8, figsize=(8, 1.3))
for ax, img in zip(axes, versions):
    ax.imshow(img[0], cmap="gray_r", vmin=0, vmax=1)
    ax.set_xticks([])
    ax.set_yticks([])
axes[0].set_title("original", fontsize=9)
plt.show()
print("label for all eight:", y_train[0].item())
```

The test for any augmentation is simple: would a person still give the new image the same label? A small shift of a digit, yes. A horizontal flip of a cat photo, yes. A horizontal flip of a 2 or a 7, no: it becomes a mirror-image shape that isn't a digit, and you'd be training the model on false examples.

:::warning
**Conv layers expect four dimensions: (batch, channels, height, width).** The digits come as (N, 8, 8); forget the channel dimension and PyTorch reads your 64-image batch as one image with 64 channels:

```python run raises
nn.Conv2d(1, 16, kernel_size=3)(torch.zeros(64, 8, 8))
```

Fix it with `images.unsqueeze(1)`, which inserts the channel axis to make (N, 1, 8, 8).
:::

:::warning
**A v2 transform called on a whole batch tensor applies the same random change to every image in it.** All 64 digits shift by the same amount, which is far less variety than you wanted. Apply the transform to one image at a time, usually inside a `Dataset`'s `__getitem__`, as the next lesson does.
:::

:::quiz
Q: A batch of 32×32 color images goes through `nn.Conv2d(3, 16, kernel_size=5)` (stride 1, no padding). What is the shape of one output?
- [x] (16, 28, 28)
  (32 + 0 − 5)/1 + 1 = 28, and the number of channels becomes `out_channels`, 16.
- [ ] (16, 32, 32)
  The size would stay 32 only with padding 2 on each side.
- [ ] (3, 28, 28)
  The output has one channel per kernel, so 16, not the 3 input channels.

Q: How many trainable numbers does `nn.Conv2d(3, 16, kernel_size=5)` have?
- [ ] 400
  That's 16 × 5 × 5, which forgets that each kernel spans all 3 input channels, and forgets the biases.
- [ ] 1,200
  Right weights (16 × 3 × 5 × 5), but each of the 16 kernels also has a bias.
- [x] 1,216
  16 × 3 × 5 × 5 = 1,200 weights plus 16 biases.

Q: An 8×8 feature map goes through `nn.Conv2d(16, 32, kernel_size=3, stride=2, padding=1)`. What height and width come out?
- [ ] 8×8
  Padding 1 keeps the size only at stride 1.
- [x] 4×4
  ⌊(8 + 2 − 3)/2⌋ + 1 = ⌊3.5⌋ + 1 = 4.
- [ ] 3×3
  That's what you'd get with no padding: ⌊5/2⌋ + 1 = 3.

Q: You're training a classifier for photos of handwritten digits. Which augmentation teaches it something false?
- [ ] Shifting by up to one pixel
  A shifted 4 is still a 4, so this is safe and useful.
- [ ] Lowering the contrast a little
  A faded 4 is still a 4.
- [x] Flipping left to right
  A mirrored 2, 3, or 7 is not a digit at all, yet you'd label it as one.
:::

:::takeaways
- A convolution slides a small kernel across the image and records the sum of products at each position; the result is a feature map.
- Output size is ⌊(n + 2p − k)/s⌋ + 1. Kernel 3 with padding 1 keeps the size; stride 2 halves it.
- A conv layer has C_out × C_in × k × k + C_out parameters, far fewer than a dense layer, because one kernel is shared across every position.
- Shared weights make feature maps shift with the input; max pooling forgives small moves inside each block.
- Augment only the training data, and only with changes that keep the label true.
:::
