A training script runs for 60 epochs and finishes by printing:

```text
epoch 60  loss 0.0006
```

It looks like a triumph. It's nearly meaningless. That number is the loss on the **last batch** of the last epoch: here, the 8 images left over when 200 training digits are split into batches of 32. It says nothing about the other 192, and nothing at all about digits the model has never seen. By the end of this lesson you'll run that exact training setup and find that its loss on new digits got **worse** for the final 43 epochs while that printout kept shrinking.

Fixing this takes a loop that measures properly. First, the machinery that feeds it.

## A `Dataset` answers "give me example i"

PyTorch splits data handling in two. A **`Dataset`** knows how many examples there are and how to produce example number `i`. A **`DataLoader`** draws examples from it in shuffled batches. Here's a custom `Dataset` for the digits; for real image folders, `__getitem__` is where you'd open a file from disk.

```python run
import matplotlib.pyplot as plt
import torch
import torch.nn as nn
from sklearn.datasets import load_digits
from sklearn.model_selection import train_test_split
from torch.utils.data import DataLoader, Dataset


class DigitsDataset(Dataset):
    def __init__(self, images, labels):
        self.images = torch.tensor(images, dtype=torch.float32) / 16.0   # scale once, up front
        self.labels = torch.tensor(labels)

    def __len__(self):
        return len(self.labels)

    def __getitem__(self, i):
        return self.images[i].unsqueeze(0), self.labels[i]               # (1, 8, 8), label


digits = load_digits()
img_train, img_val, lab_train, lab_val = train_test_split(
    digits.images, digits.target, test_size=0.25, stratify=digits.target, random_state=0
)
train_ds, val_ds = DigitsDataset(img_train, lab_train), DigitsDataset(img_val, lab_val)
x0, y0 = train_ds[0]
print("train:", len(train_ds), "| val:", len(val_ds), "| one example:", tuple(x0.shape), "label", y0.item())
```

The two required methods are `__len__` and `__getitem__`. The **validation set** (25% of the digits, never trained on) is what tells you whether the model works on new data. When you only have tensors already in memory, `torch.utils.data.TensorDataset(X, y)` does the same job in one line.

## A `DataLoader` shuffles and batches

```python run
torch.manual_seed(0)
train_loader = DataLoader(train_ds, batch_size=64, shuffle=True)
val_loader = DataLoader(val_ds, batch_size=256)

xb, yb = next(iter(train_loader))
print("batch:", tuple(xb.shape), tuple(yb.shape))
sizes = [len(yb) for _, yb in train_loader]
print("batches per epoch:", len(train_loader), "| last three sizes:", sizes[-3:])
```

1,347 training images in batches of 64 gives 21 full batches and one batch of just 3. The loader stacks individual examples into a batch tensor, `(64, 1, 8, 8)`, so your model never sees one example at a time. Here's what the loader does with indices, in plain Python, over two epochs:

:::trace Shuffle, then slice into batches, every epoch
```python
import random

random.seed(1)
indices = list(range(10))
batch_size = 4
for epoch in range(2):
    random.shuffle(indices)
    for start in range(0, len(indices), batch_size):
        batch = indices[start:start + batch_size]
        print("epoch", epoch, "batch", batch)
```
:::

Each epoch visits every example exactly once in a new order, and the leftovers form a short final batch. Shuffling the training set stops the model from learning anything about the order of the data. The validation loader doesn't shuffle, because order can't affect a measurement.

## The five lines, wrapped in epochs

```mermaid caption="One epoch: a training pass that changes the weights, then a validation pass that only measures"
flowchart TD
    A["model.train()"] --> B{More training batches?}
    B -->|yes| C["zero_grad, forward, loss, backward, step"]
    C --> D["add loss × batch size to the total"]
    D --> B
    B -->|no| E["model.eval() and torch.no_grad()"]
    E --> F["loss and accuracy on every validation batch"]
    F --> G["log the train and validation averages"]
```

Two functions, reused for the rest of the course:

```python run
def train_one_epoch(model, loader, loss_fn, optimizer):
    model.train()
    total_loss, correct, seen, batch_losses = 0.0, 0, 0, []
    for xb, yb in loader:
        optimizer.zero_grad()
        logits = model(xb)
        loss = loss_fn(logits, yb)
        loss.backward()
        optimizer.step()
        total_loss += loss.item() * len(yb)          # weight by batch size
        correct += (logits.argmax(dim=1) == yb).sum().item()
        seen += len(yb)
        batch_losses.append(loss.item())
    return total_loss / seen, correct / seen, batch_losses


def evaluate(model, loader, loss_fn):
    model.eval()
    total_loss, correct, seen = 0.0, 0, 0
    with torch.no_grad():
        for xb, yb in loader:
            logits = model(xb)
            total_loss += loss_fn(logits, yb).item() * len(yb)
            correct += (logits.argmax(dim=1) == yb).sum().item()
            seen += len(yb)
    return total_loss / seen, correct / seen
```

Three details carry the honesty. `loss.item()` turns the loss into a plain number, so the running total doesn't hold on to the computation graph. Multiplying by `len(yb)` weights each batch by its size, so the 3-image batch counts as 3 images and not as a twenty-second of the epoch. And `argmax(dim=1)` picks a class per row.

## `train()` and `eval()`: same weights, different behavior

Some layers act differently while training. **Dropout** zeroes a random fraction of values during training, which forces the network not to depend on any single unit, and scales the survivors up to keep the average the same. At evaluation time it must do nothing. `model.train()` and `model.eval()` flip that behavior for every such layer in the model:

```python run
torch.manual_seed(0)
dropout = nn.Dropout(p=0.5)
ones = torch.ones(1, 8)

dropout.train()
print("train mode:", dropout(ones).tolist())
dropout.eval()
print("eval mode: ", dropout(ones).tolist())
```

In train mode about half the values become 0 and the rest become 2, so the expected value is still 1. In eval mode the input passes through unchanged. Batch normalization, a layer common in CNNs, also behaves differently in the two modes.

`torch.no_grad()` is a separate switch: it stops autograd from recording operations, which saves memory and time when you don't need gradients. `eval()` doesn't turn off gradients, and `no_grad()` doesn't turn off dropout. Validation needs both, which is why `evaluate` uses both.

## Run it: the curves behind that printout

Here's the setup from the opening: an oversized network (two hidden layers of 256 units, about 85,000 parameters) trained on only 200 digits. We record every batch's loss, the epoch averages, and the validation numbers.

```python run alt="Two line charts over 60 epochs. Left, loss: faint dots for individual batch losses scatter widely early on and shrink toward zero. The training epoch average falls smoothly to near zero. The validation loss falls to its lowest point, about 0.25, around epoch 17, then climbs steadily to about 0.33 by epoch 60. A dashed vertical line marks the best epoch. Right, accuracy: training accuracy reaches 1.0 within about 15 epochs; validation accuracy levels off around 0.93 to 0.94." caption="Training loss keeps falling; validation loss turns around at the dashed line. Everything after it is memorization."
torch.manual_seed(0)
small_train = torch.utils.data.Subset(train_ds, range(200))
small_loader = DataLoader(small_train, batch_size=32, shuffle=True)

model = nn.Sequential(
    nn.Flatten(),
    nn.Linear(64, 256), nn.ReLU(),
    nn.Linear(256, 256), nn.ReLU(),
    nn.Linear(256, 10),
)
loss_fn = nn.CrossEntropyLoss()
optimizer = torch.optim.SGD(model.parameters(), lr=0.05, momentum=0.9)

history = {"train_loss": [], "train_acc": [], "val_loss": [], "val_acc": [], "batches": []}
for epoch in range(60):
    tr_loss, tr_acc, batch_losses = train_one_epoch(model, small_loader, loss_fn, optimizer)
    va_loss, va_acc = evaluate(model, val_loader, loss_fn)
    for name, value in zip(["train_loss", "train_acc", "val_loss", "val_acc"], [tr_loss, tr_acc, va_loss, va_acc]):
        history[name].append(value)
    history["batches"].append(batch_losses)

best = min(range(60), key=lambda e: history["val_loss"][e])
print(f"last batch of epoch 60:   loss {history['batches'][-1][-1]:.4f}")
print(f"epoch 60 averages:        train {history['train_loss'][-1]:.4f}  val {history['val_loss'][-1]:.4f}")
print(f"best val loss at epoch {best + 1}: {history['val_loss'][best]:.4f} (val accuracy {history['val_acc'][best]:.3f})")

epochs = range(1, 61)
fig, (left, right) = plt.subplots(1, 2, figsize=(10, 3.6))
for e, losses in enumerate(history["batches"], start=1):
    left.scatter([e] * len(losses), losses, s=6, color="#b8b7b1")
left.plot(epochs, history["train_loss"], color="#2a78d6", linewidth=2, label="train (epoch average)")
left.plot(epochs, history["val_loss"], color="#eb6834", linewidth=2, label="validation")
left.set_ylim(0, 1.0)
left.set_ylabel("cross-entropy loss")
right.plot(epochs, history["train_acc"], color="#2a78d6", linewidth=2, label="train")
right.plot(epochs, history["val_acc"], color="#eb6834", linewidth=2, label="validation")
right.set_ylim(0.5, 1.02)
right.set_ylabel("accuracy")
for ax in (left, right):
    ax.axvline(best + 1, color="#52514e", linestyle="--", linewidth=1)
    ax.set_xlabel("epoch")
    ax.spines[["top", "right"]].set_visible(False)
    ax.legend(frameon=False)
plt.tight_layout()
plt.show()
```

Both panels cut off the first few epochs, where the loss starts near 2.3. The gray dots are single-batch losses, the kind of number the original script printed. Early on they scatter widely around the blue average, because a batch of 32 is a small, noisy sample. The real story is the gap between blue and orange. The training loss heads to zero: with 85,000 weights and 200 examples, the network can memorize every one. The validation loss bottoms out early and then rises, so the model gets worse on new digits even as it gets "better" on old ones. That's **overfitting**, and the dashed line marks the epoch you'd want to keep.

Notice that validation **accuracy** barely moves while validation loss climbs. The model is still right about as often, but it's becoming more and more confident about the digits it gets wrong, and cross-entropy charges heavily for confident mistakes. Loss curves often reveal trouble before accuracy does.

## A field guide to loss curves

| What you see | Likely cause | First thing to try |
| --- | --- | --- |
| Train and validation both falling, still falling at the end | Not done yet | Train longer |
| Both flat and high from the start | Learning rate far too small, or a bug that stops updates | Check `optimizer.step()` runs; raise the learning rate 10× |
| Loss stuck at about 2.30 with 10 classes | The model is guessing uniformly: `ln 10 = 2.30` | Check labels, inputs, and that gradients reach the weights |
| Spikes, then `nan` | Learning rate too large | Lower it 3 to 10×; check inputs for NaN |
| Train falls, validation turns upward | Overfitting | Keep the best epoch; add data, dropout, or weight decay |
| Validation better than train early on | Dropout is active only during training, and train is averaged over a changing epoch | Usually fine; compare after a few epochs |

## Bugs that hide in training loops

:::warning
**Forgetting to switch back to `model.train()`.** If `evaluate` calls `model.eval()` and the training loop never calls `model.train()`, dropout is off from the second epoch onward. Nothing crashes; the model just trains differently than you think. Putting `model.train()` as the first line of `train_one_epoch` makes this impossible.
:::

- **`total += loss` instead of `total += loss.item()`.** The tensor keeps a reference to its whole computation graph, so memory grows every batch until the GPU runs out.
- **Averaging batch means equally.** With a tiny last batch, `sum(batch_losses) / len(batch_losses)` gives that batch far too much weight. Weight by batch size.
- **Choosing epochs or settings by test accuracy.** Validation data is for decisions; the test set is touched once, at the very end.

:::quiz
Q: A training set of 1,000 images uses `batch_size=64`. How many batches are in one epoch, and how big is the last?
- [ ] 15 batches, all of 64; the extra 40 images are dropped
  A `DataLoader` keeps the leftovers by default. Only `drop_last=True` discards them.
- [x] 16 batches; the last has 40 images
  15 × 64 = 960, leaving a 16th batch of 40.
- [ ] 16 batches of 62 or 63, so they're even
  The loader doesn't rebalance; every batch is full except possibly the last.

Q: Your validation loop uses `with torch.no_grad():` but never calls `model.eval()`. The model has dropout. What's wrong with the validation numbers?
- [x] Dropout is still randomly zeroing units, so validation scores are noisy and lower than the model's true performance
  `no_grad` only stops gradient tracking. Dropout still drops units until `model.eval()` turns it off.
- [ ] Nothing: `no_grad` also switches dropout off
  The two switches are independent. You need both.
- [ ] The weights get updated by the validation data
  Nothing updates the weights without `optimizer.step()`. The problem is the dropout noise.

Q: Training loss falls steadily for 50 epochs. Validation loss falls until epoch 12, then rises. Which checkpoint should you keep?
- [ ] Epoch 50, since its training loss is lowest
  Training loss measures memorization as well as learning. After epoch 12, the extra drop is memorization.
- [x] Epoch 12, the lowest validation loss
  That's the model that does best on data it didn't train on, which is the job.
- [ ] Neither: rising validation loss means the code has a bug
  It's the normal signature of overfitting, not a bug.

Q: With 10 classes, the loss of an untrained model is 2.31 and stays at 2.30 for every epoch. What does that suggest?
- [ ] The learning rate is slightly too high
  A too-high rate makes the loss jump around or blow up, not sit perfectly still.
- [ ] The model has overfit
  Overfitting needs training loss to fall. Here nothing is learned at all.
- [x] The model is predicting all classes about equally and isn't learning, so check that gradients reach the weights and the optimizer steps
  `ln(10) ≈ 2.30` is the loss of a uniform guess. A flat line there points to a broken loop, not a hard problem.
:::

:::takeaways
- A `Dataset` returns example `i`; a `DataLoader` shuffles it into batches, and the last batch may be small.
- Every epoch: `model.train()` and update on training batches, then `model.eval()` with `torch.no_grad()` to measure validation.
- Log epoch averages weighted by batch size, for both training and validation. A last-batch loss is noise.
- Training loss falling while validation loss rises is overfitting; keep the epoch with the lowest validation loss.
:::
