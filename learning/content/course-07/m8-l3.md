Your app works: on your computer, with your data, when you click things in the order you expect. Testing is finding out what happens the rest of the time. The good news is that you designed for most of it already. Now you prove it.

## Check the rules automatically

The rules of your app live in `state.js` as pure functions, so you can check them in Node in a few seconds, as often as you like. You don't need a testing library: a `check` function that compares what you got with what you expected is enough. Here it is testing the starter's rules. The functions are copied in without `export` so the file runs on its own.

```javascript run title="check-state.js"
function isItem(item) {
  return typeof item?.id === "number" && typeof item.name === "string" && typeof item.done === "boolean";
}
function createInitialState(saved) {
  const items = Array.isArray(saved?.items) ? saved.items.filter(isItem) : [];
  const biggestId = Math.max(0, ...items.map((item) => item.id));
  return { items, nextId: biggestId + 1, formError: "", ideas: [], ideasStatus: "idle", ideasError: "" };
}
function addItem(state, rawName) {
  const name = rawName.trim();
  if (name === "") return { ...state, formError: "Type a name first." };
  if (name.length > 60) return { ...state, formError: "Keep it under 60 characters." };
  const taken = state.items.some((item) => item.name.toLowerCase() === name.toLowerCase());
  if (taken) return { ...state, formError: `"${name}" is already on your list.` };
  const item = { id: state.nextId, name, done: false };
  return { ...state, items: [...state.items, item], nextId: state.nextId + 1, formError: "" };
}
function toggleItem(state, id) {
  return { ...state, items: state.items.map((item) => (item.id === id ? { ...item, done: !item.done } : item)) };
}
function ideasLoaded(state, ideas) {
  const clean = Array.isArray(ideas) ? ideas.filter((idea) => typeof idea === "string") : [];
  return { ...state, ideasStatus: "ready", ideas: clean };
}

// ---- the checks ----
let passed = 0;
let failed = 0;
function check(name, actual, expected) {
  const ok = JSON.stringify(actual) === JSON.stringify(expected);
  if (ok) passed = passed + 1;
  else failed = failed + 1;
  console.log(ok ? `PASS  ${name}` : `FAIL  ${name}: expected ${JSON.stringify(expected)}, got ${JSON.stringify(actual)}`);
}

const empty = createInitialState(null);
check("first visit starts empty", empty.items, []);
check("damaged entries are dropped", createInitialState({ items: [{ id: 1, name: "ok", done: false }, { name: 5 }, null] }).items.length, 1);
check("a non-array is ignored", createInitialState({ items: "oops" }).items, []);
check("ids continue after the biggest saved id", createInitialState({ items: [{ id: 7, name: "a", done: true }] }).nextId, 8);

const one = addItem(empty, "  Read  ");
check("names are trimmed", one.items[0].name, "Read");
check("blank names are refused", addItem(one, "   ").formError, "Type a name first.");
check("duplicates are refused in any case", addItem(one, "READ").items.length, 1);
check("toggle flips only that item", toggleItem(addItem(one, "Write"), 1).items.map((i) => i.done), [true, false]);
check("the old state is untouched", one.items[0].done, false);
check("junk in a response is filtered out", ideasLoaded(empty, ["a", 7, null, "b"]).ideas, ["a", "b"]);
check("a non-array response gives no ideas", ideasLoaded(empty, { error: "x" }).ideas, []);

console.log(`\n${passed} passed, ${failed} failed`);
```

Write one check for every rule in your own `state.js`, especially the edge cases from your plan: empty input, a duplicate, a value out of range, damaged saved data, a response with missing fields. Run the file after every change. When a check fails, the name tells you which rule broke before you've even opened the browser.

## The test plan

Copy this table into `plan.txt` and add a **Result** column. Run every row on your finished app, write pass or fail, and fix each fail before moving on. Run the whole plan again after the fixes, because fixes break things too.

| # | Situation | How to make it happen | It passes when |
| --- | --- | --- | --- |
| 1 | First visit | **Application › Storage › Clear site data**, then refresh | A clean, friendly empty state; no red errors in the Console |
| 2 | Refresh in the middle | Do half the main task, then refresh | Everything the person would mind losing is still there |
| 3 | Damaged saved data | In **Local storage**, double-click your value, type `{oops`, refresh | The app starts fresh instead of crashing |
| 4 | Slow network | **Network** throttling: **Slow 4G** | The loading state is visible, and clicking twice doesn't send duplicates |
| 5 | No network | Throttling: **Offline** | A clear error message with a way to try again, which works once back online |
| 6 | Nothing found | Search for nonsense, or make your JSON file `[]` | An empty state that suggests what to do next |
| 7 | Server says no | Misspell the API path in `getJSON` for a moment | A specific message, not a crash or a blank space |
| 8 | Bad input | Try empty, very long, duplicate, and out-of-range values | A specific message for each, and nothing bad is saved |
| 9 | Impatient clicks | Click every button five times, fast | No duplicates, no errors, no stuck loading message |
| 10 | Keyboard only | Put the mouse away; use Tab, Shift+Tab, Enter, Space | The whole main task works; focus is always visible and never jumps to the top |
| 11 | Small screen | **Toggle device toolbar**, width 320 | No sideways scrolling; buttons are easy to tap |
| 12 | Zoomed in | Zoom the page to 200% (Ctrl and +, or Cmd and + on a Mac) | Everything is still readable and usable |
| 13 | Accessibility basics | Run a **Lighthouse** report with **Accessibility** ticked | Labels, alt text, contrast, and names pass; fix anything flagged |
| 14 | Clean Console | Watch the Console during all of the above | No red errors, and no leftover debugging logs |

Rows 3, 5, and 10 find the most bugs. They're also the ones most people skip.

## Polish: the details people notice

Polish is mostly words and focus. Go through this list once your test plan passes:

- **Empty states give a next step.** "No habits yet. Add your first one above." beats a blank box.
- **Error messages say what happened and what to do:** "Couldn't reach the weather service. Check your connection and try again."
- **Buttons describe their result.** "Add habit" and "Save city", not "Submit" and "OK".
- **Focus is always visible** (keep `:focus-visible` styles) and always lands somewhere sensible after an action.
- **Status messages are announced.** Loading, saved, and error messages go in an `aria-live="polite"` element that exists from the start.
- **Colour is never the only signal.** Pair red and green with words or symbols.
- **Motion is optional.** If you added animations, turn them off for people who've asked their system for less motion with `@media (prefers-reduced-motion: reduce)`.
- **The tab title names the app**, and a timer or count can go in it too.

## Write a README

A README is the first thing anyone reads about your project, including future you. Save this as `README.md` in your project folder and fill it in. The `#` lines are headings in Markdown, which GitHub displays nicely.

```text
# App name

One sentence: what it does and who it's for.

## How to run it
1. Download this folder and open it in VS Code.
2. Right-click index.html and choose "Open with Live Server".

## What it does
- (your must-have features)

## How it handles problems
- No internet connection:
- Bad input:
- Damaged saved data:

## What I'd add next
-

## Credits
- Data from (API name and link)
```

The "How it handles problems" section is where your app stands out. Most beginner projects don't have one, because most beginner projects don't handle problems.

## Present it in three minutes

Practise this once out loud with a timer. Three minutes goes quickly.

1. **The problem (20 seconds).** Who is it for, and what do they get done?
2. **The main task, live (60 seconds).** Do the thing the app is for, start to finish.
3. **Prove it's sturdy (40 seconds).** Refresh and show nothing was lost. Switch the Network panel to Offline and show the error and the retry. Type something invalid and show the message.
4. **Behind the scenes (40 seconds).** Show your state object, and tell the story of one bug: what went wrong, how you found it, how you fixed it.
5. **What's next (20 seconds).** The first thing on your NICE TO HAVE list.

## Put it online (optional)

GitHub Pages hosts static sites like yours for free. You'll need a GitHub account (GitHub requires users to be at least 13). Create a public repository and upload your project files with **Add file › Upload files**, keeping `index.html` at the top level. Then go to the repository's **Settings › Pages**, and under **Build and deployment** set **Source** to **Deploy from a branch**, choose your main branch and the root folder, and click **Save**. After a minute or two your app is live at `https://your-username.github.io/repository-name/`.

Everything on GitHub Pages is public, so check your files for anything personal before you upload. Each visitor's `localStorage` is their own, so their data stays in their browser.

## The rubric

Score your own app honestly before anyone else does. Each criterion has full marks and partial marks; anything less than partial scores zero for that row.

| Criterion | Points | Full marks | Partial marks (about half) |
| --- | --- | --- | --- |
| Main task works | 20 | Every must-have feature works from start to finish | The main task works with rough edges, or one must-have is missing |
| State and code organisation | 15 | One state object; `render()` draws from it; rules live in pure functions in their own module | State is mostly in one place, but some values are read from or stored in the page |
| Saved data | 10 | Survives refresh; first visit and damaged data both handled | Saves and restores, but fails test 1 or test 3 |
| Async data and its states | 15 | Loading, empty, success, and error all look intentional, and retry works | Success plus one or two of the other states |
| Validation and messages | 10 | Every bad input gets a specific message that says how to fix it | Some validation, or only generic messages |
| Accessibility and layout | 15 | Keyboard-only use works with visible focus; labels and alt text; usable at 320 px and 200% zoom | Mostly usable, with a few problem controls or sizes |
| Testing | 10 | Node checks for the rules, and the full test plan with results | A few checks, or a partly completed plan |
| README and demo | 5 | The README covers running it and handling problems; the demo fits three minutes | One of the two is missing or incomplete |

A total of 85 or more is excellent work, 70 to 84 is solid, and below 70 means there's a row or two worth another evening.

## Look back, then look ahead

Answer these in a few sentences each. They're for you, and they make the best material for your presentation:

1. Which bug took longest to find, and what finally revealed it?
2. Where did keeping state in one object save you trouble? Where did it feel awkward?
3. What would you design differently if you started again tomorrow?
4. Which test plan row found the most problems?

You now know the ideas that every front-end framework is built on: state, a render step, events that update state, async data with loading and error states, and modules. When you meet a framework such as React, Svelte, or Vue, you'll recognise `render()` and the state object straight away; the framework mostly does the redrawing for you. Good next steps are TypeScript (JavaScript with types, which catches many bugs before you run the code), a testing tool that grows out of your `check` function, and building a small back end of your own, so the API your app talks to is one you wrote.
