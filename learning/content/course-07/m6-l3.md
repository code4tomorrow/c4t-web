:::objectives
- Write promise-based helpers like `wait(ms)` and use them with `await` in loops.
- Convert `.then` chains to `async`/`await` with `try`/`catch`.
- Retry failed work, time sequential and parallel requests, and add a timeout.
- Fetch a real API with a loading state, and make sure only the latest request updates the page.
:::

Most of these run in Node with fake, delayed "servers", so you can test async logic without a network or rate limits. Exercise 5 and the challenge use a real API in the browser, served by Live Server.

## Warm-up: predict, then check

:::quiz
Q: What does this print? `async function f() { console.log("B"); await null; console.log("D"); } console.log("A"); f(); console.log("C");`
- [ ] A C B D
  An `async` function starts running straight away. It only steps aside when it reaches `await`.
- [x] A B C D
  `f()` prints `B` immediately, pauses at `await`, the script prints `C`, and then `f` resumes and prints `D`.
- [ ] A B D C
  `await` always pauses, even for a value that's already there, so `C` gets in first.

Q: What does `console.log(getAge())` show if `async function getAge() { return 15; }`?
- [ ] `15`
  An `async` function wraps whatever it returns in a promise.
- [x] A promise that is fulfilled with 15
  Chrome shows it as `Promise {<fulfilled>: 15}`. Use `await getAge()` (inside an `async` function) or `.then` to get the number.
- [ ] `undefined`
  The function does return something: a promise holding 15.
:::

### Exercise 1: Countdown with `await`

Write a `wait(ms)` function that returns a promise fulfilled after `ms` milliseconds. Then use it inside a `for` loop to print `3`, `2`, `1`, and `Go!`, 300 ms apart. No `setInterval` allowed.

:::hint
`new Promise((resolve) => setTimeout(resolve, ms))` is the whole of `wait`. The loop has to be inside an `async` function so it can `await wait(300)` on each pass.
:::

:::solution
```javascript run title="await-countdown.js"
function wait(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function countdown() {
  for (let n = 3; n >= 1; n--) {
    console.log(n);
    await wait(300);
  }
  console.log("Go!");
}

countdown();
```

Compare this with the `setInterval` liftoff from Module 5: no ids, no `clearInterval`, and the loop reads like the countdown sounds. `await` inside a loop is the natural way to do one slow thing after another.
:::

### Exercise 2: Untangle the `.then` chain

This works, but the nesting makes it hard to follow. Rewrite `showStudent` with `async`/`await` and `try`/`catch` so it prints exactly the same thing.

```javascript run title="then-chain.js"
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
const students = { 7: { name: "Maya", classId: "bio" } };
const classes = { bio: { name: "Biology", room: "B12" } };

async function getStudent(id) {
  await wait(100);
  if (!(id in students)) throw new Error(`No student with id ${id}`);
  return students[id];
}

async function getClass(classId) {
  await wait(100);
  return classes[classId];
}

function showStudent(id) {
  return getStudent(id)
    .then((student) =>
      getClass(student.classId).then((cls) => {
        console.log(`${student.name} is in ${cls.name}, room ${cls.room}`);
      })
    )
    .catch((error) => console.log("Error:", error.message));
}

showStudent(7).then(() => showStudent(99));
```

:::hint
Each `.then((x) => …)` becomes `const x = await …;`. The `.catch` becomes a `catch (error)` block around the whole body.
:::

:::solution
```javascript run title="async-version.js"
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
const students = { 7: { name: "Maya", classId: "bio" } };
const classes = { bio: { name: "Biology", room: "B12" } };

async function getStudent(id) {
  await wait(100);
  if (!(id in students)) throw new Error(`No student with id ${id}`);
  return students[id];
}

async function getClass(classId) {
  await wait(100);
  return classes[classId];
}

async function showStudent(id) {
  try {
    const student = await getStudent(id);
    const cls = await getClass(student.classId);
    console.log(`${student.name} is in ${cls.name}, room ${cls.room}`);
  } catch (error) {
    console.log("Error:", error.message);
  }
}

async function main() {
  await showStudent(7);
  await showStudent(99);
}
main();
```

Both `student` and `cls` are ordinary variables in one scope now, which is why the nesting disappears. The second `getClass` has to wait for the first result anyway (it needs `student.classId`), so awaiting them one after the other is right here.
:::

### Exercise 3: Try again before giving up

Servers sometimes fail for a moment. Write `withRetry(task, attempts)`, which calls the async function `task` and returns its result. If it throws, wait 200 ms and try again, up to `attempts` tries in total. If every try fails, throw the last error. Test it with this flaky fake, which fails twice and then works:

```javascript
let calls = 0;
async function flakyRequest() {
  calls = calls + 1;
  if (calls < 3) throw new Error("server busy");
  return "the data";
}
```

```text
attempt 1 failed: server busy
attempt 2 failed: server busy
got: the data
attempt 1 failed: server busy
attempt 2 failed: server busy
gave up: server busy
```

:::hint
Use a `for` loop with a `try`/`catch` inside. Write `return await task();`, not `return task();`. Without `await`, the rejected promise escapes the `try` before it has a chance to fail, and the `catch` never sees it.
:::

:::solution
```javascript run title="retry.js"
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function withRetry(task, attempts) {
  for (let i = 1; i <= attempts; i++) {
    try {
      return await task();
    } catch (error) {
      console.log(`attempt ${i} failed: ${error.message}`);
      if (i === attempts) throw error;
      await wait(200);
    }
  }
}

let calls = 0;
async function flakyRequest() {
  calls = calls + 1;
  if (calls < 3) throw new Error("server busy");
  return "the data";
}

async function main() {
  console.log("got:", await withRetry(flakyRequest, 4));

  calls = 0;
  try {
    await withRetry(flakyRequest, 2);
  } catch (error) {
    console.log("gave up:", error.message);
  }
}
main();
```

Only retry errors that might go away. A 404 will be a 404 every time, and a 403 from a rate limit gets worse if you hammer the server, so real code checks `error.status` before retrying.
:::

### Exercise 4: One by one, or all at once?

A dashboard needs weather, news, and scores. Each fake request takes 300 ms. Write `oneByOne()`, which awaits the three in turn, and `allAtOnce()`, which uses `Promise.all`. Time both with `Date.now()`, rounded to the nearest 100 ms.

```text
one by one: about 900 ms -> weather, news, scores
all at once: about 300 ms -> weather, news, scores
```

:::hint
Start the clock with `const start = Date.now()` before the work and subtract afterwards. `Math.round(ms / 100) * 100` rounds to the nearest 100. A small `time(label, fn)` helper keeps the measuring code in one place.
:::

:::solution
```javascript run title="timing.js"
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function fakeRequest(name) {
  await wait(300);
  return name;
}

async function oneByOne() {
  const a = await fakeRequest("weather");
  const b = await fakeRequest("news");
  const c = await fakeRequest("scores");
  return [a, b, c];
}

async function allAtOnce() {
  return Promise.all([fakeRequest("weather"), fakeRequest("news"), fakeRequest("scores")]);
}

async function time(label, fn) {
  const start = Date.now();
  const result = await fn();
  const ms = Math.round((Date.now() - start) / 100) * 100;
  console.log(`${label}: about ${ms} ms ->`, result.join(", "));
}

async function main() {
  await time("one by one", oneByOne);
  await time("all at once", allAtOnce);
}
main();
```

`Promise.all` gets all three requests going before waiting for any of them, and its results come back in the order you listed them, not the order they finished. Use it whenever requests don't need each other's answers.
:::

### Exercise 5: A random dog, for real

Use the free [Dog CEO API](https://dog.ceo/dog-api/) to make a **Show me a dog** button. Each click fetches `https://dog.ceo/api/breeds/image/random` and shows the photo. The answer looks like this:

```json
{
  "message": "https://images.dog.ceo/breeds/hound-english/n02089973_3860.jpg",
  "status": "success"
}
```

Requirements: disable the button and show "Fetching a dog…" while waiting; give the image useful `alt` text that names the breed (it's in the URL); and show a friendly message if anything fails, including an answer whose `status` isn't `"success"`.

:::hint
The breed is the fifth piece when you split the URL on `/` (index 4): `"hound-english"`. Test that function in Node before you touch the page. Check `response.ok` first, then `data.status`, and throw an error in either case so one `catch` handles everything.
:::

:::solution
The breed helper, tested on real URLs from the API:

```javascript run title="breed.js"
function breedFromUrl(url) {
  return url.split("/")[4].replace("-", " ");
}

console.log(breedFromUrl("https://images.dog.ceo/breeds/hound-english/n02089973_3860.jpg"));
console.log(breedFromUrl("https://images.dog.ceo/breeds/kelpie/n02105412_1530.jpg"));
```

The page:

```html title="index.html"
<button id="dog">Show me a dog</button>
<p id="status" aria-live="polite"></p>
<img id="photo" alt="" width="320" hidden />
<script src="script.js" defer></script>
```

```javascript title="script.js"
const button = document.querySelector("#dog");
const statusEl = document.querySelector("#status");
const photo = document.querySelector("#photo");

function breedFromUrl(url) {
  return url.split("/")[4].replace("-", " ");
}

button.addEventListener("click", async () => {
  button.disabled = true;
  statusEl.textContent = "Fetching a dog…";
  try {
    const response = await fetch("https://dog.ceo/api/breeds/image/random");
    if (!response.ok) throw new Error(`status ${response.status}`);
    const data = await response.json();
    if (data.status !== "success") throw new Error(data.message);

    photo.src = data.message;
    photo.alt = `A photo of a ${breedFromUrl(data.message)}`;
    photo.hidden = false;
    statusEl.textContent = "";
  } catch (error) {
    statusEl.textContent = `No dog this time (${error.message}). Try again.`;
  } finally {
    button.disabled = false;
  }
});
```

This API reports problems in two ways at once: an HTTP status and a `status` field in the JSON. Checking both costs one line. For a smoother look, clear the loading message in the image's `load` event instead, since the photo itself can take a moment to download after the JSON arrives.
:::

### Exercise 6: Only the latest search wins

A search box sends a request on every key press. The person types `o`, then `oc`, then `octo`. The requests take different amounts of time, and the slow `oc` request arrives **last**, so the screen shows results for `oc` even though the box says `octo`. Run this to see the bug, then fix `onType` so that only results for the most recent request are shown.

```javascript run title="stale-results.js"
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

// A fake search API where some queries happen to be slow.
async function search(query) {
  const delays = { o: 300, oc: 500, octo: 100 };
  await wait(delays[query]);
  return `results for "${query}"`;
}

let shown = null;

async function onType(query) {
  const results = await search(query);
  shown = results;
  console.log("showing", shown);
}

onType("o");
setTimeout(() => onType("oc"), 50);
setTimeout(() => onType("octo"), 100);
setTimeout(() => console.log("Final screen:", shown), 800);
```

```mermaid caption="Requests can finish in a different order from the one they started in"
sequenceDiagram
    participant UI as Search box
    participant API as Server
    UI->>API: search for o
    UI->>API: search for oc
    UI->>API: search for octo
    API-->>UI: octo results, after 100 ms
    API-->>UI: o results, after 300 ms
    API-->>UI: oc results, after 500 ms (overwrites the screen)
```

:::hint
Give each request a number. Keep a variable `latest` outside the function and increase it at the start of every call; save a copy in a local `mine`. When the results come back, show them only if `mine === latest`.
:::

:::solution
```javascript run title="latest-wins.js"
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function search(query) {
  const delays = { o: 300, oc: 500, octo: 100 };
  await wait(delays[query]);
  return `results for "${query}"`;
}

let shown = null;
let latest = 0;

async function onType(query) {
  latest = latest + 1;
  const mine = latest;
  const results = await search(query);
  if (mine !== latest) {
    console.log(`ignoring old ${results}`);
    return;
  }
  shown = results;
  console.log("showing", shown);
}

onType("o");
setTimeout(() => onType("oc"), 50);
setTimeout(() => onType("octo"), 100);
setTimeout(() => console.log("Final screen:", shown), 800);
```

Each call remembers its own `mine` (it's a local variable), while `latest` is shared. By the time the slow `oc` results arrive, `latest` is 3 and `mine` is 2, so they're thrown away. This is exactly the "dashboard shows stale data" bug that real apps ship with, and it only shows up when the network is uneven, so test with throttling on.
:::

### Challenge: Give up after 3 seconds

A request that hangs forever leaves your app stuck on "Loading…". Add a time limit to the GitHub viewer from the last lesson: if GitHub hasn't answered in 3 seconds, show "GitHub is taking too long. Try again."

First, build the idea in Node with `Promise.race`, which settles as soon as the first of its promises does. Write `withTimeout(promise, ms)` and test it with a fast (100 ms) and a slow (800 ms) fake, using a 500 ms limit.

```text
fast answer
Gave up after 500 ms
```

Then use the browser's built-in version. `AbortSignal.timeout(ms)` makes a signal that cancels the request itself, and `fetch` then rejects with an error named `"TimeoutError"`. To test it, use the Network panel's throttling menu, choose **Custom › Add…**, and create a profile with a latency of 4000 ms.

:::hint
For `withTimeout`, race the real promise against one that only ever rejects, after `ms` milliseconds. For the browser, pass `{ signal: AbortSignal.timeout(3000) }` as the second argument to `fetch`, and add an `if (error.name === "TimeoutError")` case to your message function.
:::

:::solution
```javascript run title="timeout.js"
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

function withTimeout(promise, ms) {
  const timer = new Promise((_, reject) => {
    setTimeout(() => reject(new Error(`Gave up after ${ms} ms`)), ms);
  });
  return Promise.race([promise, timer]);
}

async function main() {
  console.log(await withTimeout(wait(100).then(() => "fast answer"), 500));
  try {
    await withTimeout(wait(800).then(() => "slow answer"), 500);
  } catch (error) {
    console.log(error.message);
  }
}
main();
```

In the viewer, change one line of `getJSON` and add one check to `messageFor`:

```javascript title="script.js"
const response = await fetch(url, { signal: AbortSignal.timeout(3000) });
```

```javascript title="script.js"
if (error.name === "TimeoutError") return "GitHub is taking too long. Try again.";
```

Put the new check first in `messageFor`. `Promise.race` only stops *waiting*; the slow request carries on in the background. `AbortSignal.timeout` actually cancels it, which is why the browser version is better for `fetch`.
:::
