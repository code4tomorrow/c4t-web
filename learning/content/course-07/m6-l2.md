---
title: Build a GitHub profile viewer with fetch
summary: Build a page that looks up any GitHub user with the real GitHub API, shows their profile and recent repositories, and handles loading, not-found, rate-limit, and offline cases.
---

:::objectives
- Read an API's JSON before writing code against it.
- Write a `getJSON` helper that turns bad HTTP statuses into errors.
- Show a loading state, then the profile, or a message that tells the person what to do next.
- Build page content from API data with `textContent`, so text from strangers can't inject HTML.
- Run two requests at the same time with `Promise.all`.
:::

GitHub has a free public API. Ask it about any username and it answers with JSON, with no account or key needed. You'll build a page where someone types a username and gets back the person's avatar, name, bio, stats, and five recent repositories. Then you'll make it behave well when things go wrong, which is most of the work in any app that talks to a server.

Here's the finished viewer. This page can't reach the internet from its previews, so this copy answers from **sample data saved from the real API**: try `octocat`, any other name (not found), and `offline` (no connection). The version you build on Live Server talks to GitHub for real.

  };
  const SAMPLE_REPOS = [

    { name: "octocat.github.io", stargazers_count: 1209 },

    { name: "git-consortium", stargazers_count: 627 },

  // Stands in for fetch() in this preview only. It waits 800 ms, then answers like GitHub.
  function fakeFetch(url) {
    return new Promise((resolve, reject) => {
      setTimeout(() => {
        if (/\/users\/offline(\/|$)/.test(url)) return reject(new TypeError("Failed to fetch"));
        const found = /\/users\/octocat(\/|$)/.test(url);
        const body = url.includes("/repos") ? SAMPLE_REPOS : SAMPLE_USER;
        resolve({
          ok: found,
          status: found ? 200 : 404,
          json: async () => (found ? body : { message: "Not Found", status: "404" }),
        });

  // ---- The app ----
  const API = "https://api.github.com";
  const form = document.querySelector("#search");
  const input = document.querySelector("#username");

  const statusEl = document.querySelector("#status");
  const profileEl = document.querySelector("#profile");

  async function getJSON(url) {

    if (!response.ok) {
      const error = new Error(`Request failed with status ${response.status}`);
      error.status = response.status;
      throw error;

    return response.json();

      getJSON(`${API}/users/${name}`),

    return "Couldn't reach GitHub. Check your internet connection and try again.";

      link,

## Step 1: Look at the data before you write code

Open [https://api.github.com/users/octocat](https://api.github.com/users/octocat) in a new browser tab. You'll see the raw JSON that your code will receive. It has about 30 fields; these are the ones the viewer uses:

```json
{
  "login": "octocat",
  "name": "The Octocat",
  "avatar_url": "https://avatars.githubusercontent.com/u/583231?v=4",
  "html_url": "https://github.com/octocat",
  "bio": null,
  "public_repos": 8,
  "followers": 25143
}
```

Notice `"bio": null`. Plenty of users have no bio, and some have no `name` either, so the code must handle `null`. Now change the address to a username that can't exist, like `https://api.github.com/users/no-such-user-zz-404`. GitHub sends status 404 and this body:

```json
{
  "message": "Not Found",
  "documentation_url": "https://docs.github.com/rest",
  "status": "404"
}
```

Five minutes reading real responses saves an hour of guessing why something is `undefined`.

## Step 3: A `getJSON` helper that refuses bad answers

Last lesson showed that `fetch` happily fulfills its promise for a 404. You'll make several requests, so write the check once, in a helper. It throws an error that carries the status, so later code can decide what to tell the person.

```javascript title="script.js"
const API = "https://api.github.com";

async function getJSON(url) {
  const response = await fetch(url);
  if (!response.ok) {
    const error = new Error(`Request failed with status ${response.status}`);
    error.status = response.status;
    throw error;
  }
  return response.json();
}
```

You can test this without a network by swapping in a fake `fetch` for a moment. This Node program tries three fake answers: a success, a 404, and no connection at all.

```javascript run title="get-json-test.js"
async function getJSON(url) {
  const response = await fetch(url);
  if (!response.ok) {
    const error = new Error(`Request failed with status ${response.status}`);
    error.status = response.status;
    throw error;
  }
  return response.json();
}

// Replace fetch with a fake that answers based on the URL.
globalThis.fetch = async (url) => {
  if (url.endsWith("/offline")) throw new TypeError("Failed to fetch");
  if (url.endsWith("/octocat")) {
    return { ok: true, status: 200, json: async () => ({ name: "The Octocat" }) };
  }
  return { ok: false, status: 404, json: async () => ({ message: "Not Found" }) };
};

async function tryOne(url) {
  try {
    const data = await getJSON(url);
    console.log("OK:", data.name);
  } catch (error) {
    console.log(`${error.name}: ${error.message} (status: ${error.status})`);
  }
}

async function main() {
  await tryOne("https://api.github.com/users/octocat");
  await tryOne("https://api.github.com/users/nobody-zz-404");
  await tryOne("https://api.github.com/users/offline");
}
main();
```

The 404 now becomes a real error with `status: 404`. The offline case is a `TypeError` with no status at all, and that difference is exactly what Step 5 will use.

## Step 4: Show "Looking up…", then the profile

When the form is submitted, the handler stops the page from reloading, checks the input, switches on the loading state, and waits. Add these to `script.js`:

```javascript title="script.js"
const form = document.querySelector("#search");
const input = document.querySelector("#username");
const button = form.querySelector("button");
const statusEl = document.querySelector("#status");
const profileEl = document.querySelector("#profile");

function make(tag, text) {
  const el = document.createElement(tag);
  if (text !== undefined) el.textContent = text;
  return el;
}

function renderProfile(user, repos) {
  const avatar = make("img");
  avatar.src = user.avatar_url;
  avatar.alt = `${user.login}'s avatar`;
  avatar.width = 88;
  avatar.height = 88;

  const link = make("a", `@${user.login} on GitHub`);
  link.href = user.html_url;

  const list = make("ul");
  for (const repo of repos) {
    list.append(make("li", `${repo.name} (${repo.stargazers_count} stars)`));
  }
  if (repos.length === 0) list.append(make("li", "No public repositories yet."));

  profileEl.replaceChildren(
    avatar,
    make("h2", user.name ?? user.login),
    make("p", user.bio ?? "No bio yet."),
    make("p", `${user.public_repos} public repos · ${user.followers} followers`),
    link,
    make("h3", "Recently updated repositories"),
    list
  );
  profileEl.hidden = false;
}
```

`make` is a tiny helper so each element takes one line. `replaceChildren` swaps out everything inside the article in one go, so searching twice never stacks two profiles. `user.name ?? user.login` falls back to the username when `name` is `null`, and the same trick gives an empty bio a friendly default.

Every piece of text goes in through `textContent`, never `innerHTML`. Bios and repository names are typed by strangers. If someone's bio were `<img src=x onerror="alert('hacked')">`, `innerHTML` would turn it into a real element and run the code; `textContent` shows it as harmless characters.

## Step 5: Turn errors into messages people can act on

"Request failed with status 404" means nothing to most people. Each kind of failure deserves its own sentence that says what to do next. GitHub allows 60 requests an hour from one address without signing in, and after that it answers 403 or 429.

```javascript run title="messages.js"
function messageFor(error, username) {
  if (error.status === 404) return `There's no GitHub user called "${username}".`;
  if (error.status === 403 || error.status === 429) {
    return "GitHub allows 60 lookups an hour without signing in. Wait a while, then try again.";
  }
  if (error.status) return `GitHub had a problem (status ${error.status}). Try again in a minute.`;
  return "Couldn't reach GitHub. Check your internet connection and try again.";
}

function failWith(status) {
  const error = new Error("Request failed");
  error.status = status;
  return error;
}

console.log(messageFor(failWith(404), "octocatt"));
console.log(messageFor(failWith(403), "octocat"));
console.log(messageFor(failWith(500), "octocat"));
console.log(messageFor(new TypeError("Failed to fetch"), "octocat"));
```

The order of the checks matters. Specific statuses come first, then "any other status", and last the case with no status at all, which can only mean the request never got an answer.

## Step 6: Ask for the profile and the repositories at once

The repositories come from a second address, `/users/octocat/repos`. The two requests don't depend on each other, so there's no reason to wait for one before starting the other. `Promise.all` takes an array of promises and waits for all of them, giving back their results in the same order.

```javascript title="script.js"
async function loadProfile(username) {
  const name = encodeURIComponent(username);
  const [user, repos] = await Promise.all([
    getJSON(`${API}/users/${name}`),
    getJSON(`${API}/users/${name}/repos?sort=updated&per_page=5`),
  ]);
  return { user, repos };
}
```

If each request takes 300 ms, awaiting them one after the other takes about 600 ms; together they take about 300. If **either** one fails, `Promise.all` rejects straight away with that error, so the `catch` in the submit handler still works. `encodeURIComponent` makes sure odd input like spaces or `?` can't break the address. The query string `?sort=updated&per_page=5` asks GitHub for the five most recently updated repositories.

## Step 7: Break it on purpose with DevTools

1. Click **Fetch/XHR** to hide everything except your two API requests. Click one to see its status, headers, and the JSON under **Response**.
2. In the throttling drop-down (it says **No throttling**), pick **Slow 4G** and search again. Now you can actually read "Looking up octocat…" and see the button stay disabled.

:::quiz
Q: Why does `renderProfile` put the bio in with `textContent` instead of `innerHTML`?
- [ ] `textContent` is the only way to set text on a paragraph
  `innerHTML` can set text too. The difference is what happens to text that looks like HTML.
- [x] The bio is written by a stranger, and `innerHTML` would turn any tags in it into real, possibly harmful, elements
  `textContent` always shows characters as characters, so a bio containing `<img onerror=…>` is displayed, not run.
- [ ] `innerHTML` doesn't work with data from `fetch`
  It works with any string. That's exactly why it's risky with untrusted text.

Q: What does `Promise.all` buy you in `loadProfile`?
- [x] Both requests run at the same time, so the wait is about as long as the slower one
  Awaiting them one after another would add the two waits together.
- [ ] It retries a request that fails
  `Promise.all` never retries. If either request fails, the whole thing rejects with that error.
- [ ] It makes the requests skip GitHub's rate limit
  Each request still counts. Two requests per search means 30 searches an hour, not 60.

Q: Someone loses their Wi-Fi and searches. Which message do they see, and why?
- [ ] "There's no GitHub user called…", because nothing came back
  No response means no 404 either. `fetch` rejected before any status existed.
- [x] "Couldn't reach GitHub…", because the error has no `status`
  `fetch` rejects with a `TypeError` that has no `status` property, so every status check is skipped and the last line runs.
- [ ] "GitHub had a problem (status 0)"
  `error.status` is `undefined`, not 0, so `if (error.status)` is false.
:::

:::takeaways
- Read the real JSON first. It tells you the field names and which ones can be `null`.
- Put the `response.ok` check in one `getJSON` helper and attach the status to the error you throw.
- Disable the button and show a loading message while waiting; use `finally` to switch it back on.
- Give each failure (not found, rate limited, server trouble, offline) its own message that says what to do.
- Use `textContent` for anything that came from an API, and `Promise.all` for requests that don't depend on each other.
:::

## Ideas to extend it

- **Recent searches.** Save the last five usernames to `localStorage` and show them as buttons that search again when clicked.
- **Member since.** `new Date(user.created_at).getFullYear()` gives the year the account was made.
- **Requests left.** GitHub reports your remaining quota in a response header. Read it with `response.headers.get("x-ratelimit-remaining")` and show it in small print.
- **Compare two users.** Two inputs, two sets of requests, all four in one `Promise.all`, shown side by side.
- **Link the repositories.** Each repo object has an `html_url`. Make each list item a link that opens the repository.
