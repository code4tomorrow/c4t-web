:::objectives
- Keep everything that can change in one `state` object and redraw the page from it with `render()`.
- Store only the facts and calculate everything else.
- Throw errors when a function can't do its job, and catch them where you can show a helpful message.
- Guard against missing data with `?.` and `??`, and know why `??` is safer than `||` for defaults.
- Split a program into modules with `export` and `import`.
:::

A browser game shows **Score: 0** after you press Restart. You score one point and it says **Score: 4**. Try it: click **+1 point** three times, then **Restart**, then **+1 point** again.

```html preview height="130" title="score-bug.html"
<p>Score: <strong id="score">0</strong></p>
<button id="point">+1 point</button>
<button id="restart">Restart</button>
<script>
  let score = 0;
  const scoreEl = document.querySelector("#score");

  document.querySelector("#point").addEventListener("click", () => {
    score = score + 1;
    scoreEl.textContent = score;
  });

  document.querySelector("#restart").addEventListener("click", () => {
    scoreEl.textContent = 0; // resets the screen, but not the variable
  });
</script>
<style>
  body { font-family: system-ui, sans-serif; margin: 12px; font-size: 18px; }
  button { font-size: 16px; padding: 6px 14px; }
</style>
```

The score lives in two places: the variable `score` and the text on the page. Restart updated one and forgot the other, so they disagree. In a small demo you'd spot it at once. In an app with a score, a timer, a question number, and a high score, each stored in a variable *and* in the page, bugs like this are everywhere.

## One state object, one `render()` function

Think of a sports scoreboard. The official scorer keeps the real score on a sheet, and the big screen only displays what's on the sheet. Nobody climbs up and changes the screen by hand. If the screen is wrong, you fix the sheet and redraw.

You've already done part of this: the to-do list in Module 3 drew itself from an array with a `render` function. Here the idea becomes a rule for the whole app, in three parts:

1. Everything that can change lives in one object, `state`. That's the sheet.
2. One function, `render()`, updates the page to match `state`. That's the screen.
3. Event handlers never touch the page. They change `state`, then call `render()`.

```mermaid caption="Data flows one way: events change the state, and render() redraws the page from it"
flowchart LR
    A[Click, key press, or data arriving] --> B[Change state]
    B --> C["render()"]
    C --> D[The page]
    D -->|"person acts again"| A
```

Here's the same game following the rules. Restart replaces the whole state with a fresh one, so there's nothing left to forget.

```html preview height="150" title="score-fixed.html"
<p>Round <strong id="round"></strong> · Score <strong id="score"></strong></p>
<button id="point">+1 point</button>
<button id="next">Next round</button>
<button id="restart">Restart</button>
<script>
  function createInitialState() {
    return { score: 0, round: 1 };
  }

  let state = createInitialState();

  function render() {
    document.querySelector("#score").textContent = state.score;
    document.querySelector("#round").textContent = state.round;
  }

  document.querySelector("#point").addEventListener("click", () => {
    state.score = state.score + 1;
    render();
  });
  document.querySelector("#next").addEventListener("click", () => {
    state.round = state.round + 1;
    render();
  });
  document.querySelector("#restart").addEventListener("click", () => {
    state = createInitialState();
    render();
  });

  render();
</script>
<style>
  body { font-family: system-ui, sans-serif; margin: 12px; font-size: 18px; }
  button { font-size: 16px; padding: 6px 14px; }
</style>
```

Notice that the HTML doesn't even contain a starting score; the first `render()` fills it in. If you add a fifth thing to track later, you add it to `createInitialState` and `render`, and Restart handles it automatically.

## Store the facts, calculate everything else

If you store `total`, `done`, and `percent` next to a list of tasks, you have to remember to update all three every time a task changes. Miss one and they disagree, the same bug as before. Instead, store only the list and **derive** the rest whenever you need it.

```javascript run title="derived.js"
const tasks = [
  { title: "Read chapter 4", done: true },
  { title: "Math worksheet", done: false },
  { title: "Practice piano", done: true },
];

function summarize(tasks) {
  const done = tasks.filter((task) => task.done).length;
  return {
    total: tasks.length,
    done,
    left: tasks.length - done,
    percent: tasks.length === 0 ? 0 : Math.round((done / tasks.length) * 100),
  };
}

console.log(summarize(tasks));
tasks[1].done = true;
console.log(summarize(tasks));
```

Change one task and every number is right automatically, because none of them was stored. `render()` calls `summarize(state.tasks)` each time it runs.

There's a second trap hiding in "start fresh". Assigning an object to a new variable doesn't copy it; both names point at the **same** object. Predict what the first line prints.

```javascript run title="fresh-state.js"
const START = { score: 0, lives: 3 };

let state = START;     // not a copy: one object, two names
state.score = 40;
state.lives = 1;

state = START;         // "restart"
console.log("after restart:", state);

function createInitialState() {
  return { score: 0, lives: 3 };
}

state = createInitialState();
state.score = 40;
state = createInitialState();
console.log("with a function:", state);
```

Changing `state.score` changed `START` too, so "restarting" from it brought back the old score. A function like `createInitialState()` builds a brand-new object on every call, which is why the game above uses one.

## Throw errors on purpose, catch them where you can help

Some functions can't do their job with the input they're given. Returning a strange value (like `-1` or `undefined`) hides the problem until something breaks far away. Throwing an error stops right there and says exactly what went wrong.

```javascript run title="validate.js"
function parseQuestionCount(value) {
  const count = Number(value);
  if (!Number.isInteger(count) || count < 1 || count > 20) {
    throw new RangeError(`Pick a whole number from 1 to 20 (got "${value}")`);
  }
  return count;
}

for (const input of ["5", "0", "seven", "12.5"]) {
  try {
    console.log("OK:", parseQuestionCount(input));
  } catch (error) {
    console.log(`${error.name}: ${error.message}`);
  }
}
```

`throw` jumps straight out of the function, skipping the `return`, and lands in the nearest `catch`. `RangeError` is one of JavaScript's built-in error types; plain `Error` works too. The question is **where** to catch. Usually that's the event handler, the one place that knows how to show a message on the page. Functions deeper down just throw and let it travel up.

These are the errors you'll meet most often, and what they usually mean:

| Error | Usually means |
| --- | --- |
| `TypeError: Cannot read properties of undefined (reading 'name')` | You used `x.name`, but `x` was `undefined`: missing data, or a wrong index. |
| `ReferenceError: scroe is not defined` | A typo in a name, or a variable used outside the scope where it exists. |
| `SyntaxError: "[object Object]" is not valid JSON` | `JSON.parse` got text that isn't JSON. |

:::warning
An empty `catch {}` makes the error vanish without a trace. Only write one when you've decided what should happen instead, like the "storage is blocked, keep going without saving" case in Module 5. Otherwise, at least show a message or `console.error(error)`.
:::

## Guard against data you didn't create

Data from an API, from `localStorage`, or from a form can be missing pieces. Optional chaining, `?.`, stops and gives `undefined` instead of crashing when something along the path is `null` or `undefined`. The nullish operator, `??`, then supplies a default.

```javascript run title="defensive.js"
const answers = [
  { user: { name: "Ana", location: { city: "Lisbon" } } },
  { user: { name: "Ben" } },
  { user: null },
  {},
];

for (const data of answers) {
  const name = data.user?.name ?? "Anonymous";
  const city = data.user?.location?.city ?? "somewhere";
  console.log(`${name} from ${city}`);
}

const saved = { volume: 0, nickname: "" };
console.log("with ||:", saved.volume || 50, JSON.stringify(saved.nickname || "Player"));
console.log("with ??:", saved.volume ?? 50, JSON.stringify(saved.nickname ?? "Player"));
```

Without `?.`, the third object would crash with `TypeError: Cannot read properties of null (reading 'name')`. The last two lines show why `??` beats `||` for defaults: `||` replaces *every* falsy value, so a volume someone deliberately set to 0 jumps back to 50. `??` only replaces `null` and `undefined`.

A **guard clause** handles the bad case first and leaves early, so the rest of the function can assume good data:

```javascript title="script.js"
function renderQuestions(questions) {
  if (!Array.isArray(questions) || questions.length === 0) {
    showMessage("No questions yet. Add some to questions.js.");
    return;
  }
  // From here on, questions is a non-empty array.
}
```

## Split your code into modules

Once `script.js` passes a few hundred lines, finding things gets slow. **Modules** let each file hold one job and share only what it chooses. A file marks what it shares with `export`, and another file asks for it with `import`.

```javascript title="state.js"
export function createInitialState() {
  return { score: 0, round: 1 };
}

export function addPoint(state) {
  return { ...state, score: state.score + 1 };
}
```

```javascript title="main.js"
import { createInitialState, addPoint } from "./state.js";

let state = createInitialState();
const scoreEl = document.querySelector("#score");

function render() {
  scoreEl.textContent = state.score;
}

document.querySelector("#point").addEventListener("click", () => {
  state = addPoint(state);
  render();
});

render();
```

```html title="index.html"
<script type="module" src="main.js"></script>
```

`addPoint` returns a **new** object instead of changing the old one. A function that only takes values and returns values, never touching the page, is easy to test in Node, and you'll use that heavily in the next lesson. A few rules come with modules:

- **They need a server.** Double-click `index.html` so it opens as a `file://` address and the Console says `Access to script at 'file:///…/main.js' from origin 'null' has been blocked by CORS policy`. Open it with Live Server instead.
- **Write the path in full.** `"./state.js"`, with the `./` and the `.js`. Browsers don't guess.
- **Each module has its own scope.** Top-level variables are no longer global, so `onclick="addPoint()"` in your HTML can't find anything. Use `addEventListener`.
- **They wait for the page.** Module scripts are deferred automatically, so you don't need `defer`.

If you import a name a module doesn't export (a typo, or a missing `export`), the Console shows `SyntaxError: The requested module './state.js' does not provide an export named 'addPiont'`, and nothing in `main.js` runs.

:::quiz
Q: In the buggy score game, what's the best fix for Restart?
- [ ] Also set `score = 0` in the Restart handler
  It fixes this bug, but the next value you add (lives, a timer) can be forgotten the same way.
- [x] Keep the score only in a state object, rebuild it with `createInitialState()`, and call `render()`
  Restart then can't miss anything: every field gets its starting value and the page is redrawn from it.
- [ ] Reload the page with `location.reload()`
  That throws away everything, including things you wanted to keep, like a high score.

Q: Someone saved `volume: 0`. What does `const volume = saved.volume || 50;` give?
- [ ] `0`
  That's what `??` would give. `||` treats 0 as "missing" because 0 is falsy.
- [x] `50`
  `||` replaces any falsy value: 0, `""`, `false`, `null`, and `undefined`. Use `??` to keep a real 0.
- [ ] `undefined`
  The `||` operator always produces one side or the other, and here the right side is 50.

Q: Your page uses `<script type="module" src="main.js">`. You double-click `index.html` and nothing works. Why?
- [ ] Modules only work in Chrome
  Every current browser supports modules.
- [x] Module scripts aren't allowed from `file://` pages, so the browser blocks them
  The Console shows a CORS error. Serving the folder with Live Server gives the page an `http://` address, and the modules load.
- [ ] `main.js` needs `defer`
  Modules are deferred automatically; `defer` would change nothing.

Q: What does this print? `const initial = { score: 0 }; let state = initial; state.score = 5; state = initial; console.log(state.score);`
- [ ] `0`
  That would need `initial` to be a separate copy, but `state = initial` only made a second name for it.
- [x] `5`
  `state.score = 5` changed the one shared object, so `initial.score` is 5 as well.
- [ ] `undefined`
  The property exists; it just holds the changed value.
:::

:::takeaways
- Keep every changing value in one `state` object; events change `state`, and `render()` redraws the page from it.
- Store facts, not totals. Derive counts and percentages inside `render()`.
- Start over with a function that builds a new object; assigning an object never copies it.
- Throw an error when a function can't do its job, and catch it where you can tell the person what happened.
- Use `?.` for paths that might be missing and `??` for defaults that keep real zeros and empty strings.
- Modules (`export`, `import`, `type="module"`) need a server, full `./file.js` paths, and `addEventListener` instead of `onclick` attributes.
:::
