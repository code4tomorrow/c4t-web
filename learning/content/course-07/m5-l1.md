A habit-timer app gets this bug report: "I clicked Start twice and my 10-minute timer finished in 5 minutes. Then I refreshed the page and my 12-day streak was gone."

That is two bugs. Every click started another timer, and both counted down the same number. And the streak lived in a JavaScript variable, which is wiped every time the page reloads. This module fixes both, and next lesson you'll build a pomodoro timer that survives a refresh.

## `setTimeout` runs a function later, and doesn't wait for it

Think of an oven timer. You set it for 20 minutes and go chop vegetables. You don't stand frozen in front of the oven. `setTimeout` works the same way: you hand the browser a function and a delay, and your code carries on immediately.

Precisely: `setTimeout(callback, delay)` asks the browser to call `callback` once, after at least `delay` milliseconds. It returns an id, and `clearTimeout(id)` cancels the call if it hasn't happened yet.

Before you look at the output, predict the order of the three lines.

```javascript run title="pizza.js"
console.log("1. Order the pizza");

setTimeout(() => {
  console.log("3. Pizza arrives");
}, 300);

console.log("2. Set the table");

const reminder = setTimeout(() => {
  console.log("This never prints");
}, 200);
clearTimeout(reminder);
```

Line 2 prints before line 3 even though it comes later in the file. `setTimeout` only schedules the callback, so the script keeps going and finishes first. The second timer is cancelled before its 200 ms are up, so its message never appears. Even a delay of `0` wouldn't change the order; Module 6 explains why.

## `setInterval` repeats until you tell it to stop

`setInterval(callback, delay)` calls the function again and again, every `delay` milliseconds, forever. The only way to stop it is `clearInterval(id)`, using the id it gave you. Lose the id and you lose the off switch.

```javascript run title="ticks.js"
let ticks = 0;

const tickerId = setInterval(() => {
  ticks = ticks + 1;
  console.log("tick", ticks);

  if (ticks === 3) {
    clearInterval(tickerId);
    console.log("stopped after 3 ticks");
  }
}, 200);
```

The callback can stop its own interval because `tickerId` was saved in a variable it can see. Every countdown you write will have this "count, then stop yourself" shape.

## The double-start bug, and the two-line fix

Every call to `setInterval` creates a brand-new, independent timer. If a Start button calls it on every click, two clicks means two timers both adding to the same counter. Worse, the variable that held the first id now holds the second one, so Stop can only cancel one of them.

Click **Start** on the buggy timer three times, then click **Stop**. Then do the same on the fixed one.

```html preview height="250" title="double-start.html"
<div class="row">
  <section>
    <h3>Buggy timer</h3>
    <p class="time" id="bug-time">0</p>
    <button id="bug-start">Start</button>
    <button id="bug-stop">Stop</button>
    <p class="small">Intervals started: <span id="bug-count">0</span></p>
  </section>
  <section>
    <h3>Fixed timer</h3>
    <p class="time" id="fix-time">0</p>
    <button id="fix-start">Start</button>
    <button id="fix-stop">Stop</button>
    <p class="small">Running: <span id="fix-running">no</span></p>
  </section>
</div>
<script>
  // Buggy: each click on Start creates another interval.
  let bugSeconds = 0;
  let bugId = null;
  let bugStarted = 0;
  document.querySelector("#bug-start").addEventListener("click", () => {
    bugId = setInterval(() => {
      bugSeconds = bugSeconds + 1;
      document.querySelector("#bug-time").textContent = bugSeconds;
    }, 1000);
    bugStarted = bugStarted + 1;
    document.querySelector("#bug-count").textContent = bugStarted;
  });
  document.querySelector("#bug-stop").addEventListener("click", () => {
    clearInterval(bugId); // only stops the most recent one
  });

  // Fixed: refuse to start twice, and forget the id after stopping.
  let fixSeconds = 0;
  let fixId = null;
  document.querySelector("#fix-start").addEventListener("click", () => {
    if (fixId !== null) return;
    fixId = setInterval(() => {
      fixSeconds = fixSeconds + 1;
      document.querySelector("#fix-time").textContent = fixSeconds;
    }, 1000);
    document.querySelector("#fix-running").textContent = "yes";
  });
  document.querySelector("#fix-stop").addEventListener("click", () => {
    clearInterval(fixId);
    fixId = null;
    document.querySelector("#fix-running").textContent = "no";
  });
</script>
<style>
  body { font-family: system-ui, sans-serif; margin: 12px; }
  .row { display: flex; gap: 16px; flex-wrap: wrap; }
  section { flex: 1; min-width: 180px; border: 1px solid #ccd; border-radius: 10px; padding: 10px 14px; }
  h3 { margin: 0; font-size: 16px; }
  .time { font-size: 40px; margin: 6px 0; font-variant-numeric: tabular-nums; }
  button { font-size: 15px; padding: 6px 14px; }
  .small { font-size: 13px; color: #555; }
</style>
```

The buggy timer speeds up with each click, and Stop only slows it down by one interval. The fix is two lines. `if (fixId !== null) return;` means "a timer is already running, so do nothing", and `fixId = null;` after `clearInterval` means "there's no timer now, so Start is allowed again". Forget the second line and Start stops working after the first Stop.

## Ticks arrive late, so trust the clock

Time an egg by counting "one Mississippi, two Mississippi" while answering the phone and you'll lose count; a clock won't. Timers have the same problem: a delay is a minimum, not a promise. If the page is busy, the next tick waits. In a background tab, browsers slow timers down on purpose to save battery; Firefox waits at least a second between runs, and Chrome can drop to about once a minute for a tab that has been hidden for more than five minutes.

This program pretends the page is busy for 250 ms during the second tick. Compare the counted time with the real time.

```javascript run title="drift.js"
const startedAt = Date.now();
let ticks = 0;

const id = setInterval(() => {
  ticks = ticks + 1;
  const counted = ticks * 100;
  const real = Date.now() - startedAt;
  console.log(`tick ${ticks}: counted ${counted} ms, clock says ${real} ms`);

  if (ticks === 2) {
    // Pretend the page is busy drawing something.
    const busyUntil = Date.now() + 250;
    while (Date.now() < busyUntil) {}
  }
  if (ticks === 5) clearInterval(id);
}, 100);
```

After the busy moment, "counted" falls behind and never catches up. A countdown that subtracts 1 second per tick would show the wrong time. The fix is to remember **when** the countdown ends, using `Date.now()` (milliseconds since 1 January 1970), and work out the time left on every tick. The interval then only decides how often to redraw.

```html preview height="170" title="countdown.html"
<p id="time">10</p>
<button id="start">Start a 10-second countdown</button>
<script>
  const display = document.querySelector("#time");
  let timerId = null;

  document.querySelector("#start").addEventListener("click", () => {
    if (timerId !== null) return;
    const endAt = Date.now() + 10 * 1000;

    timerId = setInterval(() => {
      const msLeft = Math.max(0, endAt - Date.now());
      display.textContent = Math.ceil(msLeft / 1000);
      if (msLeft === 0) {
        clearInterval(timerId);
        timerId = null;
        display.textContent = "Done!";
      }
    }, 250);
  });
</script>
<style>
  body { font-family: system-ui, sans-serif; margin: 12px; }
  #time { font-size: 48px; margin: 0 0 8px; font-variant-numeric: tabular-nums; }
  button { font-size: 15px; padding: 8px 14px; }
</style>
```

Redrawing four times a second costs almost nothing and means the display never skips a number. `Math.ceil` rounds 9.4 seconds up to 10, so the display reaches 0 exactly when time runs out.

:::

## `localStorage` keeps strings after a refresh

Everything in your JavaScript variables disappears when the page reloads. `localStorage` is a small notebook the browser keeps for each website. It survives refreshes and restarts, each site gets its own (about 5 MiB), and it has one strict rule: **it only stores strings**.

```javascript title="script.js"
localStorage.setItem("streak", "12");      // save
localStorage.getItem("streak");            // "12"
localStorage.getItem("not-saved-yet");     // null
localStorage.removeItem("streak");         // delete one key
```

To see it, open DevTools on a Live Server page, go to **Application › Storage › Local storage**, and click your site's address (in Firefox, use the **Storage** tab). You can read, edit, and delete keys there.

Node doesn't have `localStorage`, so this program builds a stand-in that follows the same rule: whatever you save is turned into a string with `String()`. Predict both lines before you look.

```javascript run title="only-strings.js"
// A stand-in for localStorage that copies its one big rule.
const storage = {
  data: {},
  setItem(key, value) {
    this.data[key] = String(value);
  },
  getItem(key) {
    return key in this.data ? this.data[key] : null;
  },
};

storage.setItem("streak", 12);
console.log(storage.getItem("streak") + 1);

storage.setItem("settings", { minutes: 25, sound: true });
console.log(storage.getItem("settings"));
```

The number 12 came back as the text `"12"`, so `+ 1` glued on a character and gave `121`. The object became the useless text `[object Object]`, and its data is gone. The real `localStorage` behaves exactly like this.

## JSON turns objects into text and back

JSON (JavaScript Object Notation) is a text format that looks almost exactly like a JavaScript object. `JSON.stringify(value)` turns an object or array into a JSON string, and `JSON.parse(text)` turns it back.

```javascript run title="json.js"
const settings = { minutes: 25, sound: true, tags: ["math", "focus"] };

const text = JSON.stringify(settings);
console.log(text);
console.log(typeof text);

const back = JSON.parse(text);
console.log(back.minutes + 5, back.tags[0]);

try {
  JSON.parse("[object Object]");
} catch (error) {
  console.log(error.name + ": " + error.message);
}
```

The round trip keeps numbers as numbers and arrays as arrays. The last part shows what happens when the saved text isn't valid JSON: `JSON.parse` throws a `SyntaxError`. Real apps hit this when an old version saved something broken or someone edited the value in DevTools. So a good `load` function expects three cases: nothing saved yet, good data, and damaged data.

```javascript title="script.js"
const KEY = "habit-timer";
const DEFAULTS = { streak: 0, minutes: 25 };

function save(state) {
  localStorage.setItem(KEY, JSON.stringify(state));
}

function load() {
  const text = localStorage.getItem(KEY);
  if (text === null) return { ...DEFAULTS };    // first visit
  try {
    return { ...DEFAULTS, ...JSON.parse(text) };  // fill in any missing fields
  } catch {
    return { ...DEFAULTS };                       // damaged data
  }
}
```

`{ ...DEFAULTS, ...saved }` copies the defaults, then lets the saved values overwrite them. If you add a new setting next month, people with older saved data still get a sensible value for it.

:::warning
**Three classic mistakes.**

1. **Saving an object directly.** `localStorage.setItem("todos", todos)` stores `"[object Object]"` (or, for an array, its items joined by commas). Later, `JSON.parse` throws `SyntaxError: "[object Object]" is not valid JSON`. Always wrap the value in `JSON.stringify`.
2. **Forgetting the first visit.** `getItem` returns `null` when nothing is saved, and `JSON.parse(null)` returns `null`, so `load().streak` crashes with `TypeError: Cannot read properties of null (reading 'streak')`. Check for `null` and return defaults.
3. **Not clearing the id.** After `clearInterval(timerId)`, set `timerId = null`, or your "already running?" check will block Start forever.
:::

:::note
Some lesson previews on this site run in a locked-down frame where `localStorage` is switched off, and touching it throws a `SecurityError`. Your own pages on Live Server don't have that limit. Also, never keep passwords or private data in `localStorage`: any script running on your page can read it.
:::

:::quiz
Q: What does this print? `console.log("A"); setTimeout(() => console.log("B"), 0); console.log("C");`
- [ ] A B C
  A delay of 0 doesn't run the callback right away. It still waits until the current script has finished.
- [x] A C B
  `setTimeout` only schedules `B`. The script finishes first (`A`, then `C`), and then the callback runs.
- [ ] B A C
  Nothing can jump ahead of code that is already running, and `B` was scheduled after `A` printed.

Q: You run `localStorage.setItem("count", 9)` and later `localStorage.getItem("count") + 1`. What do you get?
- [ ] `10`
  That would need a number, but `localStorage` handed back the string `"9"`.
- [x] `"91"`
  The value was stored as text. A string plus a number joins them, so you get `"91"`. Use `Number(...)` to convert first.
- [ ] `NaN`
  `NaN` comes from failed maths, like `Number("abc")`. Here JavaScript joined the strings instead.

Q: In the buggy timer you click Start three times, then Stop once. What happens?
- [ ] The timer stops
  Stop only cancels the id stored last. The other two intervals have no variable pointing at them any more.
- [x] It keeps counting, two steps per second instead of three
  Three intervals were running; Stop cancelled one, so two are still adding to the same counter.
- [ ] It counts down instead of up
  Nothing in the code subtracts. The leftover intervals keep adding.

Q: Why does the countdown store `endAt` instead of subtracting one second on every tick?
- [x] Ticks can arrive late, and the clock is always right
  A busy page or a background tab delays ticks. Working out `endAt - Date.now()` gives the true time left no matter how many ticks were missed.
- [ ] `setInterval` can't run code every second
  It can, it just doesn't guarantee exact timing. That's the problem `endAt` solves.
- [ ] Subtraction is slower than `Date.now()`
  Both are instant. The issue is accuracy, not speed.
:::

:::takeaways
- `setTimeout` and `setInterval` schedule work and return immediately; your code keeps running.
- Keep the id from `setInterval`, guard Start with `if (timerId !== null) return;`, and set the id back to `null` after `clearInterval`.
- For countdowns, save the end time and compute `endAt - Date.now()` each tick; never count ticks.
- `localStorage` stores strings only. Use `JSON.stringify` to save objects and `JSON.parse` to load them.
- A safe `load()` handles three cases: nothing saved (`null`), good data, and damaged data (`try`/`catch`).
:::
