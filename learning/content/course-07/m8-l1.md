Here's a good test for a finished app. Someone you've never met opens it on a phone over a slow connection. They use it for a minute, refresh halfway through, and lose their signal for a moment. They still get what they came for, and nothing on the screen ever says `undefined`.

Your capstone is an app that passes that test. You've built every piece already: a timer that survives a refresh, a profile viewer that handles a 404, a quiz whose state can't disagree with itself. Now you'll put them together in something of your own. The first step happens away from the keyboard, because an hour of planning saves days of rewriting.

## What your app must do

| Requirement | What it means in practice | Where you learned it |
| --- | --- | --- |
| Data in arrays and objects | The app's information is modelled as data, not scattered through the HTML. | Module 2 |
| The page is drawn from state | One `state` object; `render()` updates the page from it. | Modules 3 and 7 |
| Mouse and keyboard events | Every action works with a click **and** with Tab and Enter. | Module 4 |
| Validated input | Bad input gets a specific message that says how to fix it. | Module 4 |
| Saved state | The important data survives a refresh, a first visit, and damaged saved data. | Module 5 |
| At least one async operation | `fetch` from a public API, or from a JSON file in your own project folder. | Module 6 |
| Every state of the data | Loading, empty, success, and error each look intentional. | Modules 6 and 7 |
| Responsive layout | Usable from a 320-pixel-wide phone up to a laptop. | Your CSS |

A timer is welcome but not required. If your idea needs one, reuse the `endAt` pattern from the pomodoro build.

## Five project ideas

Each idea has a core you should finish and a stretch goal for later. The stars are a rough guide to how much work it is.

**1. Habit tracker** (★, a solid first capstone). A list of habits like "read 20 minutes" or "drink water", each with a check box for today and a streak count. Habits and their completed days are saved. The async part: a "suggestions" panel loads ideas from a `habits.json` file in your project with `fetch("./habits.json")`, with loading and error states. *Stretch:* a seven-day grid for each habit drawn with CSS.

**2. Quiz show** (★★). Grow the quiz from Module 7 into a real game: questions in `questions.json`, grouped by category, with a 15-second timer per question and the best score saved for each category. *Stretch:* a review screen that shows every question with your answer and the right one.

**3. Dog breed explorer** (★★). Fill a drop-down with every breed from `https://dog.ceo/api/breeds/list/all`, then show a random photo of the chosen breed from `https://dog.ceo/api/breed/beagle/images/random` (with `beagle` replaced by the breed). A heart button saves favourite photos, and a Favourites view shows them even offline (the image addresses are saved; the pictures need a connection). *Stretch:* compare two breeds side by side.

**4. Weather dashboard** (★★★). Save a list of places with a name, latitude, and longitude, and show the current temperature and wind for each from the free [Open-Meteo](https://open-meteo.com/en/docs) API, for example `https://api.open-meteo.com/v1/forecast?latitude=40.71&longitude=-74.01&current=temperature_2m,wind_speed_10m`. Validate the coordinates (latitude from -90 to 90, longitude from -180 to 180), add a °C/°F switch that's saved (`&temperature_unit=fahrenheit`), and show "Updated 12 minutes ago" so stale data is obvious. *Stretch:* an hourly forecast for the next 12 hours.

**5. Reading list with book search** (★★★). Search the [Open Library](https://openlibrary.org/dev/docs/api/search) catalogue with `https://openlibrary.org/search.json?q=hatchet&limit=10&fields=title,author_name,first_publish_year,cover_i`, add results to your own list, and mark each book as "want to read", "reading", or "finished", with filters. Search-as-you-type needs the debounce from Module 5 and the "latest request wins" fix from Module 6. *Stretch:* covers from `https://covers.openlibrary.org/b/id/` followed by the `cover_i` number and `-M.jpg`.

**Your own idea** is welcome if it meets every requirement in the table. Run it past the checklist at the end of this lesson first.

:::note
All three APIs above are free, need no key, and allow requests from a page on Live Server. Be a polite guest anyway: never send a request on every key press without debouncing, and cache answers you already have. And never put a secret API key in front-end code. Anyone can read your JavaScript in DevTools, so a key in it isn't secret.
:::

## Check the API before you commit to it

Ten minutes now can save you from building on something that won't work. For any API you plan to use:

1. **Open the address in a browser tab.** You should see JSON. Save one real response in your notes; you'll need the exact field names.
2. **Call it from your page.** In a `script.js` served by Live Server, `fetch` it and `console.log` the result. If the Console says the request was **blocked by CORS policy**, that API doesn't allow requests from other websites' pages, and no JavaScript on your side can fix it. Pick another one.
3. **Try a bad request.** Misspell a breed or search for nonsense. Note the status code and what the body looks like, because your error state will need it.
4. **Read the limits.** Look for "rate limit" in the docs, and plan for what your app shows when you hit it.

If you choose a local JSON file instead, write it by hand with five to ten realistic entries, and include one entry with a missing field so you can test your defensive code.

## Write a one-page plan

Copy this template into a file called `plan.txt` in your project folder and fill in every line. Short answers are fine; blank ones aren't.

```text
PROJECT:
WHO IT'S FOR, AND WHAT THEY GET DONE WITH IT:

MUST HAVE (the app is pointless without these):
-
NICE TO HAVE (only after every must-have works):
-

STATE (every field, with an example value):
DERIVED (things render() works out instead of storing):
SAVED (which fields go in localStorage, under which key):

DATA SOURCE (URL or JSON file, plus one real example response):

SCREENS AND STATES (for each screen: loading / empty / success / error):

EVENTS (each thing the person can do -> the update function it calls):

RISKS (what could go wrong, and the backup plan):
```

The most important lines are STATE and SAVED. If you can write the state object now, with real example values, you understand your app. If you can't, you're not ready to code it yet, and that's useful to know now rather than halfway through the build.

## A worked example: the habit tracker

Here's the plan's heart for idea 1, written as the actual starting state:

```javascript title="state.js"
export function createInitialState() {
  return {
    habits: [
      // { id: 1, name: "Read 20 minutes", doneDays: ["2026-11-14", "2026-11-15"] }
    ],
    nextId: 1,
    suggestions: [],             // loaded from habits.json
    suggestionsStatus: "idle",   // "idle" | "loading" | "ready" | "error"
    formError: "",               // message under the "new habit" field
  };
}
```

**Derived, not stored:** whether a habit is done today (`doneDays` includes today's date key), each habit's streak (the `currentStreak` function from the Module 5 challenge), and the count of habits done today. **Saved:** `habits` and `nextId`, under the key `habit-tracker`, loaded with the defensive pattern from Module 7. `suggestions` isn't saved, because it can be loaded again.

Then the screens. Writing down all four states for every piece of data is the step most people skip, and it's where most "it works on my machine" bugs come from.

| Part of the page | Loading | Empty | Success | Error |
| --- | --- | --- | --- | --- |
| Habit list | (none; it's local) | "No habits yet. Add your first one above." | The list, with streaks | Saved data damaged: start fresh and say so once |
| Suggestions panel | "Loading ideas…" | "No suggestions right now." | Clickable idea chips | "Couldn't load ideas." plus a Try again button |
| New habit form | | | The habit appears in the list | "Give the habit a name" or "You already track that" |

And the shape of the code, which next lesson's starter follows:

```mermaid caption="Every capstone has the same skeleton: data in, state in the middle, the page out"
flowchart LR
    API["api.js: fetch + checks"] --> MAIN["main.js: events"]
    STORE["storage.js: load + save"] --> MAIN
    STATE["state.js: update functions"] --> MAIN
    MAIN --> RENDER["render.js: state to page"]
    RENDER --> PAGE[The page]
    PAGE -->|"clicks and typing"| MAIN
```

## Cut it down to something you can finish

Look at your MUST HAVE list and be honest. A small app that handles every case beats a big one that breaks when the network is slow. A good rule: if your must-have list has more than five items, move the last ones to NICE TO HAVE. You can always add them after the rubric is satisfied.

Next lesson splits the build into six milestones, each ending with something that works. Estimate how long each will take you, then add half again. Things always take longer than planned, and that's normal, not a sign you're doing it wrong.

:::takeaways
- The capstone must model data, render from one state object, handle mouse and keyboard, validate input, save state, do at least one async operation, show loading, empty, success, and error states, and work on a phone.
- Choose an idea by honest size. A finished ★ app beats an unfinished ★★★ one.
- Check an API in a browser tab and from a Live Server page (watch for CORS errors) before you build on it.
- Write the state object with real example values before writing any other code.
- List all four data states for every part of the page.
:::

## Before you move on

Your plan is ready when you can answer yes to all of these:

- [ ] The STATE section is a real object with example values.
- [ ] You know which fields are saved, and under what key.
- [ ] You've seen a real response from your data source, and a real error response.
- [ ] Every screen has its loading, empty, success, and error states written down.
- [ ] Your must-have list has five items or fewer.
