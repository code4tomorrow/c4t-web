title: Settle a settings conflict in VS Code and record the decision
summary: Build a small Quiz Night repo, create a real conflict between two teammates' settings, resolve it in VS Code's merge editor so both intentions survive, and document the choice.
---

:::objectives
- Create a merge conflict on purpose and recognize it from Git's output.
- Resolve it in VS Code's merge editor by writing a result neither side had.
- Finish the merge and clean up the merged branch.
- Record the decision in a decision record, the README, and a CHANGELOG.
:::

Here is the history you'll have at the end of this lesson. Two teammates changed the same game setting in opposite directions, and the merge commit keeps both of their goals:

```text
* 20c573b Record why hard mode has its own settings
*   d736dc8 Merge hard-mode: keep 60 s default, add a hard_mode block
|\  
| * 0e2db9c Make hard mode faster with more questions
* | eefef48 Give players more time to read each question
|/  
* 81f85a8 Start Quiz Night with a README and settings
```

Along with it come four files: `settings.json`, a README that explains every setting, a CHANGELOG, and `docs/decisions/0001-hard-mode-gets-its-own-settings.md`. Your commit IDs will be different from these; everything else should match.

## Step 1: Make the practice repo

Open VS Code, then open its terminal with **Terminal › New Terminal**. Make a folder and turn it into a repository:

```bash
mkdir quiz-night
cd quiz-night
git init
```

Use **File › Open Folder…** to open `quiz-night` in VS Code, and create two files in it.

```markdown title="README.md"
# Quiz Night

A small quiz game for our club's Friday meetings.

## Settings

Edit `settings.json` to change how the game plays.
```

```json title="settings.json"
{
  "title": "Friday Quiz Night",
  "time_limit_seconds": 30,
  "questions_per_round": 10,
  "theme": "light"
}
```

Commit both:

```bash
git add .
git commit -m "Start Quiz Night with a README and settings"
```

```text
[main (root-commit) 81f85a8] Start Quiz Night with a README and settings
 2 files changed, 13 insertions(+)
 create mode 100644 README.md
 create mode 100644 settings.json
```

## Step 2: Play two teammates

You'll play both people. Maya wants a hard mode: less time and more questions. On a new branch, change `time_limit_seconds` to `15` and `questions_per_round` to `20`, then commit:

```bash
git switch -c hard-mode
git commit -am "Make hard mode faster with more questions"
```

```text
Switched to a new branch 'hard-mode'
[hard-mode 0e2db9c] Make hard mode faster with more questions
 1 file changed, 2 insertions(+), 2 deletions(-)
```

Leo noticed that slower readers run out of time. Back on `main`, change `time_limit_seconds` from `30` to `60` and commit:

```bash
git switch main
git commit -am "Give players more time to read each question"
git log --oneline --graph --all
```

```text
Switched to branch 'main'
[main eefef48] Give players more time to read each question
 1 file changed, 1 insertion(+), 1 deletion(-)
* 0e2db9c Make hard mode faster with more questions
| * eefef48 Give players more time to read each question
|/  
* 81f85a8 Start Quiz Night with a README and settings
```

On a real team, Leo's commit would reach `main` through a merged pull request and you'd get it with `git pull`. The conflict that follows is identical either way.

## Step 3: Merge and meet the conflict

Still on `main`, merge Maya's branch:

```bash
git merge hard-mode
```

```text
Auto-merging settings.json
CONFLICT (content): Merge conflict in settings.json
Automatic merge failed; fix conflicts and then commit the result.
```

Predict before you look: which lines will be inside the markers? Both branches edited line 3, and Maya also edited line 4, right next to it. Git treats touching changes as one block, so both lines end up in the conflict:

```json title="settings.json (during the merge)"
{
  "title": "Friday Quiz Night",
<<<<<<< HEAD
  "time_limit_seconds": 60,
  "questions_per_round": 10,
=======
  "time_limit_seconds": 15,
  "questions_per_round": 20,
>>>>>>> hard-mode
  "theme": "light"
}
```

## Step 4: Resolve it in the merge editor

Open the Source Control view (Ctrl+Shift+G, or ⌃⇧G on a Mac). `settings.json` is listed under **Merge Changes**. Click it to open the file, then click the **Resolve in Merge Editor** button in the editor.

The merge editor has three parts:

- **Incoming** (top left): Maya's version from `hard-mode`.
- **Current** (top right): Leo's version, already on `main`.
- **Result** (bottom): what the file will say when you finish. You can type in it.

Each side has its own controls to accept it into the Result. Before you click anything, ask what each one would do:

| Choice | What the game does | Who loses |
| --- | --- | --- |
| Accept Current | Every round is 60 s, 10 questions | Maya: hard mode is gone |
| Accept Incoming | Every round is 15 s, 20 questions | Leo: slow readers time out again |
| Accept both | Two `time_limit_seconds` keys in one object | Everyone: most JSON readers silently keep the last one, 15 |

None of them keeps both goals, because one number can't be 60 and 15 at once. The fix is a change in shape: keep Leo's values as the default and give hard mode its own block. Type this into the Result pane so the whole file reads:

```json title="settings.json (resolved)"
{
  "title": "Friday Quiz Night",
  "time_limit_seconds": 60,
  "questions_per_round": 10,
  "hard_mode": {
    "time_limit_seconds": 15,
    "questions_per_round": 20
  },
  "theme": "light"
}
```

Check the commas: every line inside an object ends with one except the last. Then click **Complete Merge**. VS Code saves the file and stages it, which is the same as running `git add settings.json`.

:::tip
Stuck halfway? Open the Command Palette (Ctrl+Shift+P, or ⇧⌘P on a Mac) and run **Git: Abort Merge**, or type `git merge --abort` in the terminal. Both put the files back as they were before Step 3.
:::

## Step 5: Commit the merge

Back in the terminal, confirm Git agrees the conflict is settled:

```bash
git status
```

```text
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   settings.json

```

Commit with a message that says how you resolved it, so the history explains itself:

```bash
git commit -m "Merge hard-mode: keep 60 s default, add a hard_mode block"
git branch -d hard-mode
```

```text
[main d736dc8] Merge hard-mode: keep 60 s default, add a hard_mode block
Deleted branch hard-mode (was 0e2db9c).
```

`git branch -d` only deletes a branch whose work is already merged, so it's safe here. Maya's commit `0e2db9c` is still in history; only the label went away.

## Step 6: Write the decision record

In six months someone will open `settings.json`, see two time limits, and wonder why. Make a folder `docs/decisions` and add this file:

```markdown title="docs/decisions/0001-hard-mode-gets-its-own-settings.md"
# 1. Hard mode gets its own settings

Date: 2026-11-15
Status: Accepted

## Context

Two changes to `settings.json` collided in a merge. One raised the time
limit to 60 seconds so players can read long questions. The other cut it
to 15 seconds and raised the round to 20 questions to make a harder game.
Both help different players, and one number can't hold both.

## Decision

Keep 60 seconds and 10 questions as the default. Add a `hard_mode` block
with 15 seconds and 20 questions, used when a player picks hard mode.

## Consequences

- New players get the slower, friendlier default.
- The game code must read `hard_mode` when hard mode is on.
- Anyone who changes timing must say which mode they mean.
```

Context, Decision, and Consequences are the three parts of the classic format. Consequences is the part people skip, and it's the most useful: here it tells the next programmer about work that still needs doing.

## Step 7: Update the README and start a CHANGELOG

Replace the Settings section of `README.md` so a newcomer can understand every setting without opening the JSON:

```markdown title="README.md"
# Quiz Night

A small quiz game for our club's Friday meetings.

## Settings

Edit `settings.json` to change how the game plays.

| Setting | Default | What it does |
| --- | --- | --- |
| `time_limit_seconds` | `60` | Seconds to answer each question |
| `questions_per_round` | `10` | Questions in one round |
| `hard_mode` | 15 s, 20 questions | Replaces the two settings above when a player picks hard mode |
| `theme` | `"light"` | `"light"` or `"dark"` |

Why hard mode has its own block: see
[decision 0001](docs/decisions/0001-hard-mode-gets-its-own-settings.md).
```

Then create `CHANGELOG.md`. Nothing has been released yet, so both changes go under Unreleased:

```markdown title="CHANGELOG.md"
# Changelog

Every notable change to Quiz Night is listed here, newest first.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- A `hard_mode` block in `settings.json`: 15 seconds and 20 questions.

### Changed

- The default time limit is 60 seconds instead of 30.
```

Commit the three documents together, since they describe one decision:

```bash
git status --short
git add .
git commit -m "Record why hard mode has its own settings"
```

```text
 M README.md
?? CHANGELOG.md
?? docs/
[main 20c573b] Record why hard mode has its own settings
 3 files changed, 46 insertions(+)
 create mode 100644 CHANGELOG.md
 create mode 100644 docs/decisions/0001-hard-mode-gets-its-own-settings.md
```

:::quiz
Q: Why didn't any of the merge editor's accept buttons give the right answer in Step 4?
- [ ] The merge editor can't handle JSON files
  It handles any text file. The problem was the content, not the file type.
- [x] Each button keeps one person's number, and the game needed both numbers in different places
  Resolving well meant changing the file's shape, which only you could decide.
- [ ] Accept Both would have deleted the theme setting
  The theme line was outside the conflict, so every choice kept it.

Q: Why does the merge commit's message say "keep 60 s default, add a hard_mode block" instead of the default "Merge branch 'hard-mode'"?
- [x] It tells anyone reading the log how the conflict was settled, without opening the files
  The default message only says that a merge happened, not what was decided.
- [ ] Git rejects merge commits that use the default message
  Git accepts the default message; it's just less useful.
- [ ] A custom message makes the merge commit smaller
  The message length has no effect on what the commit stores.

Q: Which file should tell the next programmer that the game code still has to read `hard_mode`?
- [ ] The CHANGELOG
  The CHANGELOG lists what users will notice per version, not follow-up work for developers.
- [x] The decision record's Consequences section
  Consequences lists what the decision makes necessary, so it's where that note belongs.
- [ ] The merge commit's message
  Commit messages stay short; the reasoning and follow-ups belong in a document people can find.
:::

:::takeaways
- Start resolving by asking what each side was trying to achieve, not which button to press.
- When one value can't satisfy both goals, change the file's shape so each goal gets its own place.
- **Complete Merge** stages the file. You still commit the merge yourself.
- Write the resolution into the merge commit's message, and the reasons into a decision record.
- Update the README and CHANGELOG in the same commit series as the change they describe.
:::

## Extend it

- Turn on the zdiff3 style for this repo only with `git config merge.conflictStyle zdiff3`, then redo the conflict in a copy of the folder and compare the markers.
- Push the repo to GitHub and open an issue titled "Game code must read hard_mode", linking to decision 0001.
- Make the conflict again in a fresh copy, but this time run `git rebase main` on `hard-mode`. Notice which side the markers call `HEAD`.
