## Warm-up: read a version number

Python's version `3.12.4` has three parts. Which number is the patch? What would the next minor release be called?

:::solution
The patch is `4`. The next minor release is `3.13.0`: minor goes up by one and patch resets to `0`.
:::

### Exercise 1: Pick the next version

Quiz Night is at `2.3.1`. For each change on its own, what is the next version?

1. Fix a crash when `settings.json` has no `theme`.
2. Add a `projector` option.
3. Remove the old `colour` spelling that was still accepted alongside `color`.
4. Correct a spelling mistake in the README.
5. Three bug fixes and one new option, released together.

:::hint
Ask "could this break someone's existing settings file?" first, then "does it add anything?"
:::

:::solution
1. `2.3.2`: a fix that breaks nothing.
2. `2.4.0`: a new feature; old settings still work.
3. `3.0.0`: settings files that say `colour` stop working, so it's breaking.
4. No new version is needed for a docs-only change. If you do publish one, it's a patch.
5. `2.4.0`: the biggest kind of change in the batch decides. Fixes ride along with the feature.
:::

### Exercise 2: Write `bump()`

Write `bump(version, part)`, where `part` is `"major"`, `"minor"`, or `"patch"`. It returns the next version as a string. Test it on `1.4.7` with all three parts, and on `0.9.9` with `"minor"`.

:::hint
`version.split(".")` gives three strings. Convert them with `int`, and remember that bumping a number resets everything to its right.
:::

:::solution
```python run title="bump.py"
def bump(version, part):
    major, minor, patch = (int(n) for n in version.split("."))
    if part == "major":
        return f"{major + 1}.0.0"
    if part == "minor":
        return f"{major}.{minor + 1}.0"
    if part == "patch":
        return f"{major}.{minor}.{patch + 1}"
    raise ValueError(f"part must be major, minor, or patch, not {part!r}")


tests = [
    ("1.4.7", "patch", "1.4.8"),
    ("1.4.7", "minor", "1.5.0"),
    ("1.4.7", "major", "2.0.0"),
    ("0.9.9", "minor", "0.10.0"),
]
for version, part, expected in tests:
    result = bump(version, part)
    status = "ok" if result == expected else "WRONG"
    print(f"bump({version!r}, {part!r}) -> {result}  {status}")
```

The last test is the one people get wrong on paper: after 0.9.9 comes 0.10.0, not 1.0.0. Going to 1.0.0 is a decision, not arithmetic. Raising `ValueError` for a typo like `"mnior"` is better than quietly returning the old version.
:::

### Exercise 3: Sort release tags

`git tag` lists tags alphabetically, so `v1.10.0` appears before `v1.2.0`. Write code that sorts these tags by version and prints the newest: `["v1.10.0", "v1.2.0", "v2.0.0", "v1.9.3", "v1.2.10"]`.

:::hint
Strip the `v`, split on dots, and turn the parts into a tuple of numbers. Tuples compare item by item.
:::

:::solution
```python run title="sort_tags.py"
tags = ["v1.10.0", "v1.2.0", "v2.0.0", "v1.9.3", "v1.2.10"]


def version_key(tag):
    return tuple(int(n) for n in tag.removeprefix("v").split("."))


print(sorted(tags, key=version_key))
print("newest:", max(tags, key=version_key))
```

Git can do this too: `git tag --sort=version:refname` sorts tags by version instead of alphabetically.
:::

### Exercise 4: Match the license

Which license fits each author?

1. A robotics club wants anyone, including companies, to reuse their code with as few rules as possible.
2. A student wants anyone who shares an improved version of her game to share its source as well.
3. A teacher is sharing a folder of quiz questions and hand-drawn diagrams and wants credit.

:::hint
Only one of these is software.
:::

:::solution
1. **MIT**: keep the notice, and that's nearly all. (Apache-2.0 also works if they want the patent grant.)
2. **GPL-3.0**: its copyleft condition makes distributed modified versions stay open.
3. **CC BY 4.0**: questions and drawings aren't software, and CC BY requires credit. Creative Commons advises against its licenses for code, so if the folder later gains code, license that part separately.
:::

### Exercise 5: Turn a log into a CHANGELOG entry

These commits landed after `v1.1.0`:

```bash
git log --oneline v1.1.0..HEAD
```

```text
df308dc Fix a typo in a history question
830addf Rename questions_per_round to round_size
cbb83ea Update the README screenshot
5fbf42f Add a high-contrast theme for projectors
6bdb4da Fix the timer showing -1 at the end of a round
```

Write the CHANGELOG section for the next release, including its version number. Users read this, not developers.

:::hint
`v1.1.0..HEAD` means "commits after v1.1.0 up to now." One of these breaks existing settings files. One isn't worth mentioning to users.
:::

:::solution
```markdown title="CHANGELOG.md"
## [2.0.0] - 2026-12-01

### Changed

- **Breaking:** `questions_per_round` is now called `round_size`.
  Rename it in your `settings.json`, including inside `hard_mode`.

### Added

- A high-contrast theme for projectors.

### Fixed

- The timer no longer shows -1 at the end of a round.
- A typo in one of the history questions.
```

The rename forces `2.0.0`, and it goes first, with instructions, because it's the change that can hurt someone. The README screenshot is left out: it doesn't change what users get. A CHANGELOG is a summary for people, not a copy of `git log`.
:::

### Exercise 6: Move a tag that landed on the wrong commit

In your copy of `quiz-night`, you tag `v1.1.0` and only then commit the CHANGELOG update. The tag now points at the commit before the release commit. Move it, then prove that release tags are annotated by comparing one with a quick lightweight tag.

:::hint
Delete the tag locally with `git tag -d`, then create it again while `HEAD` is on the right commit. `git cat-file -t` prints what kind of object a name points to.
:::

:::solution
```bash
git log --oneline --decorate -3
```

```text
576ccd0 (HEAD -> main) Prepare release 1.1.0
297bcaa (tag: v1.1.0) Add a categories list to settings
ba7a5f1 (tag: v1.0.0) Prepare release 1.0.0
```

```bash
git tag -d v1.1.0
git tag -a v1.1.0 -m "Quiz Night 1.1.0"
git log --oneline --decorate -3
```

```text
Deleted tag 'v1.1.0' (was 8dd1f20)
576ccd0 (HEAD -> main, tag: v1.1.0) Prepare release 1.1.0
297bcaa Add a categories list to settings
ba7a5f1 (tag: v1.0.0) Prepare release 1.0.0
```

Now compare the two kinds of tag:

```bash
git tag v1.1.0-quick
git cat-file -t v1.1.0
git cat-file -t v1.1.0-quick
```

```text
tag
commit
```

The annotated tag is its own object with a tagger, date, and message. The lightweight one is just a name pointing straight at a commit. Delete the experiment with `git tag -d v1.1.0-quick`.

If you had already pushed the wrong tag, you would also need `git push origin --delete v1.1.0` before pushing the fixed one, and anyone who fetched it would still have the old version. Fixing a tag before you push is cheap; afterward it's awkward, which is why checking `git log --oneline --decorate` before pushing is a good habit.
:::

### Challenge: sort pre-releases correctly

Projects often publish test versions like `1.0.0-beta.2` before `1.0.0`. Semver's rules say a pre-release comes **before** its release, and pre-release parts compare one by one: numbers compare as numbers, words compare alphabetically, numbers rank below words, and fewer parts rank lower if all earlier parts match. Write `semver_key(version)` so this list sorts into the official order, ending with `1.0.0`:

`["1.0.0", "1.0.0-rc.1", "1.0.0-beta.11", "1.0.0-beta.2", "1.0.0-beta", "1.0.0-alpha.beta", "1.0.0-alpha.1", "1.0.0-alpha"]`

:::hint
Split on the first `-` with `partition`. Give a plain release an extra `1` at position 3 and a pre-release a `0`, so releases win. For each pre-release part, `(0, number)` or `(1, word)` makes numbers rank below words.
:::

:::solution
```python run title="semver_sort.py"
def semver_key(version):
    core, _, pre = version.removeprefix("v").partition("-")
    numbers = tuple(int(n) for n in core.split("."))
    if not pre:
        return numbers + (1,)
    parts = tuple((0, int(p)) if p.isdigit() else (1, p) for p in pre.split("."))
    return numbers + (0,) + parts


mixed = ["1.0.0", "1.0.0-rc.1", "1.0.0-beta.11", "1.0.0-beta.2",
         "1.0.0-beta", "1.0.0-alpha.beta", "1.0.0-alpha.1", "1.0.0-alpha"]
for version in sorted(mixed, key=semver_key):
    print(version)
```

This matches the example order in section 11 of the semver spec. `beta.2` sorts before `beta.11` because `2` and `11` are compared as numbers, and `alpha` before `alpha.1` because it has fewer parts.
:::
