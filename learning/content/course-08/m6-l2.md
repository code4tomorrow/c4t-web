You'll continue the `quiz-night` repo from the previous module. By the end, its history carries two release tags:

```text
d03a388 (HEAD -> main, tag: v1.1.0) Prepare release 1.1.0
297bcaa Add a categories list to settings
ba7a5f1 (tag: v1.0.0) Prepare release 1.0.0
20c573b Record why hard mode has its own settings
```

On GitHub, the repo's **Releases** page will list "Quiz Night 1.1.0" and "Quiz Night 1.0.0", each with notes and source downloads. If you skipped Module 5, any small repo with a README works; adjust the file names as you go.

## Step 1: Add the MIT license

Quiz Night is a club project, and you'd like other clubs to reuse it freely, so MIT fits. Create a file named exactly `LICENSE` (no extension) in the repo's top folder. Copy the text from [choosealicense.com's MIT page](https://choosealicense.com/licenses/mit/) and fill in the year and your name:

```text title="LICENSE"
MIT License

Copyright (c) 2026 Your Name

Permission is hereby granted, free of charge, to any person obtaining a copy
of this software and associated documentation files (the "Software"), to deal
in the Software without restriction, including without limitation the rights
to use, copy, modify, merge, publish, distribute, sublicense, and/or sell
copies of the Software, and to permit persons to whom the Software is
furnished to do so, subject to the following conditions:

The above copyright notice and this permission notice shall be included in all
copies or substantial portions of the Software.

THE SOFTWARE IS PROVIDED "AS IS", WITHOUT WARRANTY OF ANY KIND, EXPRESS OR
IMPLIED, INCLUDING BUT NOT LIMITED TO THE WARRANTIES OF MERCHANTABILITY,
FITNESS FOR A PARTICULAR PURPOSE AND NONINFRINGEMENT. IN NO EVENT SHALL THE
AUTHORS OR COPYRIGHT HOLDERS BE LIABLE FOR ANY CLAIM, DAMAGES OR OTHER
LIABILITY, WHETHER IN AN ACTION OF CONTRACT, TORT OR OTHERWISE, ARISING FROM,
OUT OF OR IN CONNECTION WITH THE SOFTWARE OR THE USE OR OTHER DEALINGS IN THE
SOFTWARE.
```

Don't edit anything except the year and name. GitHub recognizes a license by comparing the file with the standard text, and a reworded license is a new one that nobody has checked.

## Step 2: Say so in the README

Visitors read the README before anything else. Add a section at the bottom:

```markdown title="README.md (new section at the end)"
## License

Quiz Night is released under the [MIT License](LICENSE). You may use,
change, and share it, as long as you keep the copyright notice.
```

## Step 3: Turn Unreleased into 1.0.0

Open `CHANGELOG.md`. Its Unreleased section says the default time limit "changed" from 30 to 60, but nobody outside your team ever had a version with 30. Users of 1.0.0 only care what's in it, so describe everything as Added:

```markdown title="CHANGELOG.md"
# Changelog

Every notable change to Quiz Night is listed here, newest first.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and version numbers follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

## [1.0.0] - 2026-11-15

### Added

- `settings.json` with a title, a 60-second time limit, 10 questions
  per round, and a light or dark theme.
- A `hard_mode` block in `settings.json`: 15 seconds and 20 questions.
- A decision record explaining why hard mode has its own settings.
- The MIT License.

[Unreleased]: https://github.com/YOUR-USERNAME/quiz-night/compare/v1.0.0...HEAD
[1.0.0]: https://github.com/YOUR-USERNAME/quiz-night/releases/tag/v1.0.0
```

Three details matter. The empty Unreleased heading stays on top, ready for the next change. The date uses the `YYYY-MM-DD` form, which sorts correctly and reads the same in every country. The links at the bottom make each heading clickable on GitHub; replace `YOUR-USERNAME` with yours.

## Step 4: Commit, then tag

Commit first, so the tag points at a commit that already contains the finished CHANGELOG:

```bash
git status --short
git add .
git commit -m "Prepare release 1.0.0"
```

```text
 M CHANGELOG.md
 M README.md
?? LICENSE
[main ba7a5f1] Prepare release 1.0.0
 3 files changed, 36 insertions(+), 4 deletions(-)
 create mode 100644 LICENSE
```

Now create an annotated tag and look at what it stores:

```bash
git tag -a v1.0.0 -m "Quiz Night 1.0.0"
git tag
git show v1.0.0 --no-patch
```

```text
v1.0.0
tag v1.0.0
Tagger: Learner <learner@example.com>
Date:   Sun Nov 15 23:00:02 2026 -0500

Quiz Night 1.0.0

commit ba7a5f1411dea47fdce122d06321dc6bcbc6eb88
Author: Learner <learner@example.com>
Date:   Sun Nov 15 22:59:51 2026 -0500

    Prepare release 1.0.0
```

The top part is the tag itself: who tagged, when, and the message. Below it is the commit the tag points to. `--no-patch` hides the line-by-line changes, which would otherwise fill the screen.

## Step 5: Push the commit and the tag

If the repo isn't on GitHub yet, create an **empty** repository named `quiz-night` there (no README, license, or .gitignore, since you already have them), then connect it:

```bash
git remote add origin https://github.com/YOUR-USERNAME/quiz-night.git
git push -u origin main
```

Push the tag separately. Plain `git push` sends branches and leaves tags behind:

```bash
git push origin v1.0.0
```

The output ends with a line containing `[new tag]` and `v1.0.0 -> v1.0.0`. Refresh the repo page: the sidebar now shows **MIT license**, and the tag count near the branch menu reads 1.

## Step 6: Publish the GitHub Release

1. On the repo's main page, click **Releases** on the right side.
2. Click **Draft a new release**.
3. Open **Choose a tag** and pick `v1.0.0`.
4. In **Release title**, type `Quiz Night 1.0.0`.
5. In the description, paste the Added list from your 1.0.0 CHANGELOG section.
6. Click **Publish release**.

GitHub adds **Source code (zip)** and **Source code (tar.gz)** downloads on its own. There's also a **Generate release notes** button that drafts notes from merged pull requests. It shines on projects where every change arrives through a pull request; Quiz Night's changes so far were committed directly, so your CHANGELOG text is the better description here.

## Step 7: Ship 1.1.0 the same way

New feature: club leaders want to choose question topics. Add a line to `settings.json`:

```json title="settings.json (new line)"
  "categories": ["general", "science", "history"],
```

Add a row for it to the README's settings table, and put the change under Unreleased in the CHANGELOG:

```markdown title="CHANGELOG.md (top part)"
## [Unreleased]

### Added

- A `categories` list in `settings.json` for choosing question topics.
```

Commit, then ask Git where you are relative to the last release:

```bash
git add .
git commit -m "Add a categories list to settings"
git describe --tags
```

```text
[main 297bcaa] Add a categories list to settings
 3 files changed, 6 insertions(+)
v1.0.0-1-g297bcaa
```

Read `v1.0.0-1-g297bcaa` as "one commit after v1.0.0, at commit 297bcaa" (the `g` stands for Git). It's a handy way to name a build that falls between releases.

Is this release 1.0.1, 1.1.0, or 2.0.0? It adds a feature and every old settings file still works, so it's **minor**: 1.1.0. Move the Added list under a new `## [1.1.0] - 2026-11-15` heading, leave Unreleased empty above it, update the links at the bottom, and release:

```bash
git commit -am "Prepare release 1.1.0"
git tag -a v1.1.0 -m "Quiz Night 1.1.0"
git log --oneline --decorate -4
git describe --tags
```

```text
[main d03a388] Prepare release 1.1.0
 1 file changed, 4 insertions(+), 1 deletion(-)
d03a388 (HEAD -> main, tag: v1.1.0) Prepare release 1.1.0
297bcaa Add a categories list to settings
ba7a5f1 (tag: v1.0.0) Prepare release 1.0.0
20c573b Record why hard mode has its own settings
v1.1.0
```

Now `git describe` prints just `v1.1.0`, because you're exactly on the tag. Push with `git push` and `git push origin v1.1.0`, then repeat Step 6 for `v1.1.0`.

```markdown title="CHANGELOG.md"
# Changelog

Every notable change to Quiz Night is listed here, newest first.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and version numbers follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

## [1.1.0] - 2026-11-15

### Added

- A `categories` list in `settings.json` for choosing question topics.

## [1.0.0] - 2026-11-15

### Added

- `settings.json` with a title, a 60-second time limit, 10 questions
  per round, and a light or dark theme.
- A `hard_mode` block in `settings.json`: 15 seconds and 20 questions.
- A decision record explaining why hard mode has its own settings.
- The MIT License.

[Unreleased]: https://github.com/YOUR-USERNAME/quiz-night/compare/v1.1.0...HEAD
```

:::quiz
Q: Why did you commit the CHANGELOG update before running `git tag`?
- [x] A tag points at one commit, so the release commit has to contain the finished CHANGELOG
  Tagging first would label a commit whose CHANGELOG still says Unreleased.
- [ ] Git refuses to tag while there are uncommitted changes
  Git tags happily with a messy folder; the tag just ignores those changes.
- [ ] Annotated tags copy the CHANGELOG into the tag message
  The tag stores only the message you type with `-m`.

Q: The categories feature became 1.1.0. Which change would have made it 2.0.0 instead?
- [ ] Adding a second new setting in the same release
  More features are still minor, as long as nothing breaks.
- [x] Requiring every settings file to have a `categories` list, so old files fail
  Breaking existing settings files is exactly what a major bump warns about.
- [ ] Fixing a typo in the README at the same time
  A docs fix doesn't break anything.

Q: Why replace the 1.0.0 entry's "Changed: 60 instead of 30" with an Added item?
- [x] No released version ever had 30, so for users it isn't a change
  A CHANGELOG describes differences between releases, not every step of development.
- [ ] Keep a Changelog doesn't allow a Changed heading
  Changed is one of its standard headings; it just didn't apply here.
- [ ] GitHub Releases only show Added items
  Release notes show whatever you write.
:::

:::takeaways
- A license is a file named `LICENSE` with the exact license text, plus your year and name.
- Release in this order: update the CHANGELOG, commit, tag, push the branch, push the tag, publish.
- Annotated tags record who released what and when; push each one by name.
- `git describe --tags` shows how far you are from the last release.
- Decide the version number by asking "can this break anyone?" before "how big is it?"
:::
