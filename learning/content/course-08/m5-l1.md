Maya and Leo improve the same quiz game on the same afternoon. On her branch, Maya adds a music category. On `main`, Leo adds sports. Both edits land on the same lines of `settings.json`, so when you merge Maya's branch, Git prints this and stops:

```text
Auto-merging settings.json
CONFLICT (content): Merge conflict in settings.json
Automatic merge failed; fix conflicts and then commit the result.
```

Nothing is broken and nothing is lost: both versions are safe in commits. Git is asking a question it can't answer for you. What should these lines say now?

## Git compares three versions, not two

Picture two friends who each get a photocopy of the same essay. If one fixes paragraph 1 and the other fixes paragraph 4, anyone could combine the copies. If both rewrite paragraph 2, a person has to read both and decide.

Git works the same way. When you run `git merge`, it finds the **merge base**, the newest commit both branches share. Then it walks through each file and asks who changed each region since the base:

- Nobody changed it: keep it.
- Only one branch changed it: take that branch's version.
- Both changed the same lines, or lines right next to each other: stop and ask a human.

```mermaid caption="Both branches changed settings.json after the shared commit"
gitGraph
    commit id: "Add settings"
    branch add-music
    checkout add-music
    commit id: "Add music"
    checkout main
    commit id: "Add sports"
    merge add-music id: "Merge (conflict)"
```

The "right next to each other" part surprises people, because Git compares lines, not JSON keys. When I changed the title on one branch and the time limit on the very next line on another, Git reported a conflict. Changing the time limit and the theme, two lines apart, merged on its own:

```text
Auto-merging settings.json
Merge made by the 'ort' strategy.
 settings.json | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

## Reading the conflict markers

After a failed merge, `git status` lists the files that need you:

```bash
git status
```

```text
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   settings.json

no changes added to commit (use "git add" and/or "git commit -a")
```

"Both modified" means both branches changed this file in overlapping places. Open it and Git has written both versions into the file, fenced off with markers:

```json title="settings.json"
{
  "title": "Friday Quiz Night",
  "time_limit_seconds": 30,
  "categories": [
    "science",
    "history",
<<<<<<< HEAD
    "sports"
=======
    "music"
>>>>>>> add-music
  ]
}
```

Read it from top to bottom:

- `<<<<<<< HEAD` starts the version from **your current branch**, the one you were on when you typed `git merge` (here `main`). VS Code labels this the *Current Change*.
- `=======` separates the two versions.
- `>>>>>>> add-music` ends the version from **the branch coming in**. VS Code calls it the *Incoming Change*.
- Everything outside the markers merged cleanly. Leave it alone.

Notice `"history",` above the markers. Both branches added the same comma there, so Git counted it as agreed.

:::tip
To also see what the lines said at the merge base, merge with the `zdiff3` style: `git -c merge.conflictStyle=zdiff3 merge add-music`. A middle section starting with `|||||||` shows the original lines, which makes it easier to see what each person meant.
:::

## Resolving means deciding what the file should say

Resolving is three steps: edit the file until it is right, mark it resolved with `git add`, then commit.

Here both new categories belong in the game, so delete the three marker lines and keep both entries. That looks finished, but `"sports"` now needs a comma because another item follows it. Keeping both sides by deleting markers often breaks the syntax, so check the result. If you have Python installed, it can test a JSON file (type `python` instead of `python3` on Windows):

```bash
python3 -m json.tool settings.json
```

```text
Expecting ',' delimiter: line 8 column 5 (char 127)
```

Add the comma after `"sports"` and the same command prints the file back with no error. Then finish the merge:

```bash
git diff --check
git add settings.json
git commit -m "Merge add-music: keep both new categories"
git log --oneline --graph
```

```text
[main 22ce1d4] Merge add-music: keep both new categories
*   22ce1d4 Merge add-music: keep both new categories
|\  
| * 9463ec3 Add a music category
* | 5b06fe8 Add a sports category
|/  
* a3e12c8 Add settings
```

`git diff --check` printed nothing, which is what you want. Had a marker survived, it would print lines like `settings.json:7: leftover conflict marker`. The merge commit at the top has two parents, so the graph shows two lines joining.

Changed your mind halfway through? `git merge --abort` puts every file back exactly as it was before you typed `git merge`.

## The same fix in VS Code

VS Code colors each conflict and puts four links above it: **Accept Current Change**, **Accept Incoming Change**, **Accept Both Changes**, and **Compare Changes**. For more room, click **Resolve in Merge Editor**, which shows the incoming version, the current version, and an editable **Result**. **Complete Merge** stages the file. The next lesson walks through it click by click.

The buttons pick text. They don't check meaning: **Accept Both Changes** on this file gives the same missing comma.

## Merge or rebase: two ways to catch up with main

Your branch has fallen behind `main`, and there are two ways to catch up.

- `git merge main`, run on your branch, adds a merge commit that ties the histories together. Nothing that exists changes.
- `git rebase main` lifts your commits off and replays them on top of the newest `main`, as if you had started today. History becomes one straight line.

Here is a real rebase of a branch with two commits:

```bash
git log --oneline --graph --all
git rebase main
git log --oneline --graph --all
```

```text
* 109210b Add a second science question
* 5d4c230 Add a science question
| * d054493 Explain how to run the quiz
|/  
* e46cad9 Start quiz
Successfully rebased and updated refs/heads/add-science.
* 0788046 Add a second science question
* 0e01462 Add a science question
* d054493 Explain how to run the quiz
* e46cad9 Start quiz
```

Compare the IDs: `5d4c230` became `0e01462`. Rebase makes **new** commits with the same changes. That's harmless for commits only you have, but a teammate who already pulled the old ones now has a history that disagrees with yours. So rebase only commits you haven't shared, and merge when in doubt. Conflicts can stop a rebase too; you fix them the same way and run `git rebase --continue`.

## Stash: a pocket for half-finished work

You're halfway through an edit when a teammate needs a quick fix on `main`, and Git refuses to switch branches:

```text
error: Your local changes to the following files would be overwritten by checkout:
	questions.txt
Please commit your changes or stash them before you switch branches.
Aborting
```

`git stash` saves your uncommitted changes and gives you a clean folder. `git stash pop` brings them back and removes them from the stash.

```bash
git stash
git stash list
```

```text
Saved working directory and index state WIP on add-science: 0788046 Add a second science question
stash@{0}: WIP on add-science: 0788046 Add a second science question
```

Switch, fix, switch back, and run `git stash pop`. New files Git doesn't track yet stay behind unless you add `-u`. A stash is for minutes or hours; for anything longer, commit to a branch.

## Write down what you decided, and why

A merge commit records what the file says now, not why. Three documents serve three readers:

- **README.md**, for newcomers: what the project is, how to run it, what each setting does. Update it in the same pull request that changes the behavior.
- **CHANGELOG.md**, for users: notable changes per version under headings like Added, Changed, and Fixed, with an Unreleased section on top.
- A **decision record**, for future teammates: one short numbered file per significant choice, often in `docs/decisions/`. When a later choice replaces it, write a new record and mark the old one superseded.

```markdown title="docs/decisions/0002-keep-categories-sorted.md"
# 2. Keep categories in alphabetical order

Status: Accepted

## Context
Two branches added categories at the end of the list and conflicted.

## Decision
New categories go in alphabetical order, one per line.

## Consequences
Easier to scan; reviewers check the order in every pull request.
```

:::warning
**Three classic conflict mistakes.**
1. Committing with markers still in the file. Git won't stop you. Run `git diff --check` before `git add`.
2. Clicking **Accept Current Change** just to make the conflict go away. That silently throws out a teammate's work. If you can't tell what their change was for, ask them.
3. Rebasing a branch other people use. Their copies keep the old commits and the next pull mixes old with new. Merge instead.
:::

:::quiz
Q: Branch A changes line 2 of `settings.json`. Branch B changes line 9 and nothing else. What happens when you merge B into A?
- [x] Git merges it automatically
  Only one branch touched each region, so Git takes each change from the side that made it.
- [ ] Git reports a conflict because both branches changed the same file
  Conflicts are about overlapping or adjacent lines, not whole files.
- [ ] Git keeps only branch A's version of the file
  Git never drops a change just because it came from the incoming branch.

Q: You are on `main` and run `git merge add-music`. Which version sits between `<<<<<<< HEAD` and `=======`?
- [x] The version from `main`
  `HEAD` is the branch you are on when you start the merge, so its lines come first.
- [ ] The version from `add-music`
  The incoming branch's lines come after `=======` and end at `>>>>>>> add-music`.
- [ ] The version from the merge base
  The base only appears in a `|||||||` section, and only with the diff3 or zdiff3 style turned on.

Q: After resolving, `git diff --check` prints `settings.json:7: leftover conflict marker`. What should you do next?
- [ ] Run `git add settings.json` and commit, since the merge is nearly done
  That would commit a broken file with a marker in it.
- [x] Open the file, remove the marker on line 7, and run the check again
  The check is telling you exactly which line still has a marker. Fix it before staging.
- [ ] Run `git merge --abort` and start over
  Aborting works, but it throws away the resolving you already did for one stray line.

Q: You pushed your branch `team-size` yesterday and a classmate added a commit on top of it. Now `main` has moved ahead. What is the safest way to catch up?
- [ ] `git rebase main`, so history stays in a straight line
  Rebase rewrites commits your classmate already has, and your histories split.
- [x] `git merge main` while on `team-size`
  Merging adds one new commit and leaves every shared commit exactly as it was.
- [ ] `git stash`, then switch to `main`
  Stash parks uncommitted edits. It doesn't bring a branch up to date.
:::

:::takeaways
- Git compares both branches with their merge base and stops only when both changed the same or neighboring lines.
- `<<<<<<< HEAD` to `=======` is your current branch; `=======` to `>>>>>>>` is the incoming one.
- Resolve, run `git diff --check`, then `git add` and `git commit`. `git merge --abort` is always a way out.
- Rebase replays your commits as new ones, so use it only on commits you haven't shared.
- `git stash` parks uncommitted work briefly; `-u` includes new files.
- README explains the project, CHANGELOG lists changes per version, a decision record explains why.
:::
