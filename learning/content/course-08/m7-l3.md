Use your `quiz-night` repo for the workflow exercises. Each change goes on its own branch with a pull request, so you see every check's result on GitHub.

## Warm-up: when does this run?

```yaml
on:
  pull_request:
    branches: [main]
  workflow_dispatch:
```

When does a workflow with this `on:` block start?

:::solution
On pull requests that target `main`, and whenever someone starts it by hand: `workflow_dispatch` adds a **Run workflow** button to the workflow's page in the **Actions** tab. It does **not** run on plain pushes, not even pushes to `main`.
:::

### Exercise 1: Fix the broken workflow

This workflow has three bugs. Find them before reading the hint.

```yaml title=".github/workflows/tests.yml (broken)"
name: Tests
on: [push, pull_request]
jobs:
  unittest:
    runs-on: ubuntu-latest
    steps:
      - name: Set up Python
        uses: actions/setup-python@v7
        with:
        python-version: "3.13"
      - name: Run the tests
        uses: python -m unittest -v
```

:::hint
One step is missing entirely. One line is at the wrong depth. One keyword is wrong for running a shell command.
:::

:::solution
1. There's no `actions/checkout` step, so the runner has no files and unittest finds no tests.
2. `python-version` is at the same depth as `with:`, so YAML reads `with:` as empty and `python-version` as a stray key on the step. GitHub rejects the file as invalid.
3. `uses:` is for ready-made actions. A shell command needs `run:`.

```yaml title=".github/workflows/tests.yml (fixed)"
name: Tests
on: [push, pull_request]
jobs:
  unittest:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the code
        uses: actions/checkout@v7
      - name: Set up Python
        uses: actions/setup-python@v7
        with:
          python-version: "3.13"
      - name: Run the tests
        run: python -m unittest -v
```

`on: [push, pull_request]` is a valid short form. It runs on pushes to every branch, so a pull request's branch gets checked twice: once for the push and once for the pull request. Limiting `push` to `main`, as in the build-along, avoids the duplicate.
:::

### Exercise 2: Test on three Python versions

Club members run Quiz Night on Python 3.11, 3.12, and 3.13. Change the workflow so the tests run on all three, and add a step that checks `settings.json` is valid JSON before the tests run, so a broken file gets its own clear failure.

:::hint
Add `strategy:` with a `matrix:` under the job, then refer to the value as `${{ matrix.python-version }}`. For the JSON step, `python -m json.tool settings.json` exits with an error code when the file is invalid.
:::

:::solution
```yaml title=".github/workflows/tests.yml"
name: Tests

on:
  push:
    branches: [main]
  pull_request:

jobs:
  unittest:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.11", "3.12", "3.13"]
    steps:
      - name: Check out the code
        uses: actions/checkout@v7

      - name: Set up Python ${{ matrix.python-version }}
        uses: actions/setup-python@v7
        with:
          python-version: ${{ matrix.python-version }}

      - name: Check that settings.json is valid JSON
        run: python -m json.tool settings.json

      - name: Run the tests
        run: python -m unittest -v
```

GitHub now runs three copies of the job at the same time, one per version, and the pull request shows three checks with the version in each name. Put the versions in quotes: unquoted, YAML reads `3.10` as the number 3.1.

If you required `unittest` in branch protection, update the rule: the old check name no longer appears, and the three new names do.
:::

### Exercise 3: Set up a fork's remotes

Fork GitHub's practice repo [octocat/Spoon-Knife](https://github.com/octocat/Spoon-Knife) with the **Fork** button, clone **your fork**, add the original as `upstream`, and sync your `main` with it.

:::hint
After cloning, `origin` already points at your fork. You add `upstream` yourself.
:::

:::solution
```bash
git clone https://github.com/YOUR-USERNAME/Spoon-Knife.git
cd Spoon-Knife
git remote add upstream https://github.com/octocat/Spoon-Knife.git
git remote -v
git fetch upstream
git merge upstream/main
```

```text
origin	https://github.com/YOUR-USERNAME/Spoon-Knife.git (fetch)
origin	https://github.com/YOUR-USERNAME/Spoon-Knife.git (push)
upstream	https://github.com/octocat/Spoon-Knife.git (fetch)
upstream	https://github.com/octocat/Spoon-Knife.git (push)
From https://github.com/octocat/Spoon-Knife
 * [new branch]      change-the-title -> upstream/change-the-title
 * [new branch]      main             -> upstream/main
 * [new branch]      test-branch      -> upstream/test-branch
Already up to date.
```

"Already up to date" is expected for a fresh fork. On an active project, run the last two commands before starting each new branch, so you build on the newest code and meet fewer conflicts later.
:::

### Exercise 4: Read a key from the environment

Write Python that reads `QUIZ_API_KEY` from the environment. If it's missing, print a helpful message instead of crashing. If it's there, print only its last four characters, so the key never appears in full in a log.

:::hint
`os.environ.get(name)` returns `None` when the variable isn't set.
:::

:::solution
```python run title="key_check.py"
import os

key = os.environ.get("QUIZ_API_KEY")
if key is None:
    print("QUIZ_API_KEY is not set. Put it in .env or in your environment.")
else:
    print("Key loaded, ending in", key[-4:])
```

It isn't set on this page, so you see the friendly message. On your computer, the popular `python-dotenv` package can load `.env` into the environment for you. In a workflow, pass a repository secret into the same variable:

```yaml
      - name: Fetch new questions
        run: python fetch_questions.py
        env:
          QUIZ_API_KEY: ${{ secrets.QUIZ_API_KEY }}
```

The code doesn't change between your laptop and GitHub. Only where the value comes from does.
:::

### Exercise 5: A key leaked. Put the response in order

You pushed `config.py` with a real key in it to a public repo an hour ago. Put these in order and cross out the one that doesn't help:

- A. Move the key into `.env`, add `.env` to `.gitignore`, and read it with `os.environ`.
- B. Revoke the key at the service and create a new one.
- C. Tell the project owner or your teacher what happened.
- D. Make the repository private and consider the problem solved.
- E. Decide whether to scrub the old key from history.

:::hint
What can someone do with the key right now, while you're still editing files?
:::

:::solution
**B, A, C, E.** Revoking comes first, because until then anyone who copied the key can use it. Then fix the code so the new key never lands in Git. Then tell the owner, who may need to check for misuse. History cleanup comes last and is optional once the old key is dead.

**D doesn't help.** Copies made while the repo was public still exist, and the key still works until you revoke it.
:::

:::video iyw-qZF_vF8 start=3:02
What to watch for: a security company leaks a decoy key on purpose, then checks who used it after 5 minutes, 15 minutes, and an hour. It's the reason revoking the key came first in Exercise 5.
:::

### Exercise 6: Spot the unsafe workflow

A classmate's workflow prints debugging info. What's wrong, and how do you fix it?

```yaml
      - name: Debug
        run: echo "Using key sk-live-4f9a2b7c1d"
```

:::hint
Where does this text live, and who can read it?
:::

:::solution
The key is typed straight into the workflow file, so it's in the repo's history for anyone to read, and it's printed in every run's log. Revoke that key, store a new one as a repository secret, pass it in with `env:` as in Exercise 4, and never `echo` it. GitHub masks registered secrets in logs, but it can't mask a value it was never told is secret.
:::

### Challenge: write CONTRIBUTING.md

Write a `CONTRIBUTING.md` for Quiz Night that a classmate who has never seen the repo could follow from fork to merged pull request. Include: how to set up and run the tests, how to name branches, what a good pull request contains, and one rule about secrets.

:::hint
Write it as numbered steps. A newcomer should never have to guess the next command.
:::

:::solution
```markdown title="CONTRIBUTING.md"
# Contributing to Quiz Night

Thanks for helping! Small, focused pull requests are the easiest to review.

## Before you start

1. Find an issue, or open one describing the change you have in mind.
2. Comment that you'd like to work on it and wait for a reply.

## Set up

1. Fork this repo and clone your fork.
2. Add the original as upstream:
   `git remote add upstream https://github.com/OWNER/quiz-night.git`
3. Run the tests: `python -m unittest -v` (or `py -m unittest -v` on Windows).

## Make your change

1. Sync first: `git fetch upstream` then `git merge upstream/main`.
2. Branch with a short name: `fix/timer-rounding` or `docs/run-tests`.
3. Add or update a test when you change behavior.
4. Add a line under Unreleased in CHANGELOG.md if users will notice.

## Open a pull request

- Say which issue it fixes ("Fixes #12") and how you tested it.
- Keep it to one change. Unrelated fixes get their own pull request.
- The Tests check must be green before review.

## Never commit secrets

Keys and passwords go in `.env`, which is ignored. If you commit one by
accident, tell a maintainer right away so it can be revoked.
```

GitHub links to this file when someone opens an issue or a pull request, so put the most important rules near the top.
:::
