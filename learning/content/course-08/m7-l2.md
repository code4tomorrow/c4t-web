By the end of this lesson, every pull request to Quiz Night shows a check named **Tests / unittest (pull_request)**. The pull request below went red when someone made hard mode slower, and green again after the fix, without anyone running a test by hand:

```text

5067c32 Try a slower hard mode
48a5efd Add tests and a workflow that runs them
```

Python on your own computer is optional. The tests run on GitHub either way; having Python locally just lets you see failures before you push.

## Step 1: Start a branch

Open your `quiz-night` repo in VS Code, make sure `main` is up to date, and branch:

```bash
git switch -c add-tests
```

```text

```

## Step 2: Add the code to test

Quiz Night needs two small jobs done in code: read the rules for a round, and score answers. Create `quiz.py`:

```python title="quiz.py"
"""Quiz Night: read the settings and score a round."""
import json


def load_settings(path="settings.json"):
    with open(path, encoding="utf-8") as file:
        return json.load(file)


def round_rules(settings, hard=False):
    """Return (seconds per question, questions per round) for one mode."""
    source = settings["hard_mode"] if hard else settings
    return source["time_limit_seconds"], source["questions_per_round"]


def score(answers, key):
    """Count answers that match the key, ignoring case and extra spaces."""
    return sum(
        1
        for given, correct in zip(answers, key)
        if given.strip().lower() == correct.strip().lower()
    )
```

`round_rules` is the code that decision 0001 said had to exist: it reads `hard_mode` when hard mode is on.

## Step 3: Write tests for the bugs you've already had

Good first tests target mistakes that really happened. Create `test_quiz.py` next to `quiz.py`:

```py title="test_quiz.py"
import unittest

from quiz import load_settings, round_rules, score


class SettingsTests(unittest.TestCase):
    def setUp(self):
        # Fails with a clear error if settings.json is not valid JSON.
        self.settings = load_settings()

    def test_time_limits_are_positive(self):
        for hard in (False, True):
            seconds, count = round_rules(self.settings, hard)
            self.assertGreater(seconds, 0)
            self.assertGreater(count, 0)

    def test_hard_mode_is_faster(self):
        normal_seconds, _ = round_rules(self.settings)
        hard_seconds, _ = round_rules(self.settings, hard=True)
        self.assertLess(hard_seconds, normal_seconds)


class ScoreTests(unittest.TestCase):
    def test_counts_matching_answers(self):
        self.assertEqual(score(["Paris", "4"], ["Paris", "5"]), 1)

    def test_ignores_case_and_spaces(self):
        self.assertEqual(score(["  paris "], ["Paris"]), 1)


if __name__ == "__main__":
    unittest.main()
```

`setUp` runs before each settings test, so a missing comma like the one in Module 5 makes every settings test error out. `test_hard_mode_is_faster` pins down the whole reason hard mode exists. If you have Python, run the tests from the project folder (use `py` instead of `python` on Windows if `python` isn't found):

```bash
python -m unittest -v
```

```text

test_ignores_case_and_spaces (test_quiz.ScoreTests.test_ignores_case_and_spaces) ... ok
test_hard_mode_is_faster (test_quiz.SettingsTests.test_hard_mode_is_faster) ... ok
test_time_limits_are_positive (test_quiz.SettingsTests.test_time_limits_are_positive) ... ok

OK
```

## Step 4: Add the workflow

Create the folders `.github/workflows/` (the dot and the final `s` both matter) and this file inside:

```yaml title=".github/workflows/tests.yml"
name: Tests

on:
  push:
    branches: [main]
  pull_request:

jobs:
  unittest:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the code
        uses: actions/checkout@v7

      - name: Set up Python
        uses: actions/setup-python@v7
        with:
          python-version: "3.13"

      - name: Run the tests
        run: python -m unittest -v
```

The last line is the same command you ran in Step 3. A workflow is your own routine, written down so a machine can repeat it every time.

## Step 5: Ignore secrets before they exist

Quiz Night may one day fetch questions from an online service that needs a key. Decide now where that key will live: in a `.env` file that Git never sees. Create `.gitignore`:

```bash title=".gitignore"
# Secrets and personal settings: never commit these
.env

# Files Python creates when it runs
__pycache__/
*.pyc
```

Now test the rule. Create a `.env` file containing the line `QUIZ_API_KEY=not-a-real-key`, then:

```bash
git status --short
git check-ignore -v .env
```

```text
?? .github/
?? .gitignore
?? quiz.py
?? test_quiz.py
.gitignore:2:.env	.env
```

`.env` isn't listed by `git status`, and `check-ignore` names the exact rule that hides it: line 2 of `.gitignore`. A real key would sit safely in that file on your computer only.

## Step 7: Break it on purpose

A check you've never seen fail is a check you can't trust. On the same branch, change the `hard_mode` time limit in `settings.json` from `15` to `90`. Predict which test fails, then run them:

```bash
git commit -am "Try a slower hard mode"
python -m unittest
```

```text
[add-tests 5067c32] Try a slower hard mode
 1 file changed, 1 insertion(+), 1 deletion(-)
..F.
======================================================================
FAIL: test_hard_mode_is_faster (test_quiz.SettingsTests.test_hard_mode_is_faster)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "/private/tmp/quiz-night/test_quiz.py", line 20, in test_hard_mode_is_faster
    self.assertLess(hard_seconds, normal_seconds)
    ~~~~~~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
AssertionError: 90 not less than 60

----------------------------------------------------------------------
Ran 4 tests in 0.005s

FAILED (failures=1)
```

Each dot is a passing test and `F` is a failure. The message names the test and the values: 90 is not less than 60. Your file path will be your own folder. Now `git push`, and the pull request's check turns into a red X with the same message in its log.

Undo the change with `git revert`, which adds a new commit that reverses the last one. It's the safe undo for commits you've already pushed, because it doesn't rewrite anything:

```bash
git revert --no-edit HEAD
python -m unittest
```

```text
[add-tests e14e940] Revert "Try a slower hard mode"
 Date: Sun Nov 15 23:27:54 2026 -0500
 1 file changed, 1 insertion(+), 1 deletion(-)
....
----------------------------------------------------------------------
Ran 4 tests in 0.007s

OK
```

Push again and the check goes green.

## Step 8: Make the check a rule

1. In the repo, open **Settings › Branches** and click **Add classic branch protection rule**.
2. In **Branch name pattern**, type `main`.
3. Tick **Require a pull request before merging**. If you work alone, untick **Require approvals** underneath it, since you can't approve your own pull request.
4. Tick **Require status checks to pass before merging**, type `unittest` in the search box, and select it.
5. Click **Create**.

Back on your pull request, the merge box now lists `unittest` as required. Merge the pull request. Because the workflow also runs on pushes to `main`, the **Actions** tab shows one more run, this time for `main` itself.

:::quiz
Q: Why push a deliberately broken commit in Step 7?
- [x] To prove the check really fails when it should, before relying on it
  A check that can't go red protects nothing. Seeing it fail once builds trust in the green.
- [ ] Because GitHub only allows branch protection after a failed run
  A check needs to have run once, but it doesn't have to have failed.
- [ ] To make the commit history longer
  The revert keeps history honest, but length was never the goal.

Q: Why fix the slower hard mode with `git revert` instead of deleting the commit?
- [ ] `git revert` is faster to type
  Speed isn't the reason. Both fixes take one command.
- [x] The bad commit was already pushed, and revert undoes it without rewriting shared history
  Deleting a pushed commit would mean force-pushing over history others may have.
- [ ] Deleted commits are still checked by GitHub Actions
  Actions runs on whatever you push; that isn't why you'd choose revert.

Q: You're the only person on the repo and ticked **Require approvals**. What happens to your pull requests?
- [ ] They merge as usual, since you own the repo
  Rules apply to your PRs too, though admins can bypass unless that's blocked.
- [x] They wait for an approving review that you can't give yourself
  Authors can't approve their own pull requests, so a solo project needs this unticked or a second person.
- [ ] GitHub approves them automatically after the checks pass
  Passing checks and approvals are separate requirements.
:::

:::takeaways
- Write your first tests for bugs that already happened.
- Add `.env` to `.gitignore` before the file exists, and check the rule with `git check-ignore -v`.
- A workflow repeats your own local command on a clean machine for every push and pull request.
- Watch a check fail once on purpose, so you know it works.
- `git revert` undoes a pushed commit safely; branch protection makes the passing check required.
:::

## Extend it

- Test on several Python versions by adding a `strategy:` with `matrix: python-version: ["3.11", "3.12", "3.13"]` and using `${{ matrix.python-version }}` in the setup step.
- Add a status badge: in the **Actions** tab, open the Tests workflow, use the **...** menu to pick **Create status badge**, and paste the Markdown at the top of your README.
- Add a test that fails if `categories` is empty, then open a pull request that empties it and watch the check catch it.
