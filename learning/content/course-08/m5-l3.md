---
title: "Practice: conflicts, aborts, stashes, and rebases"
summary: Six exercises and a challenge on reading conflict markers, backing out safely, stashing new files, resolving a conflict mid-rebase, handling a deleted file, and writing a decision record.
---

:::objectives
- Predict whether a merge will conflict before running it.
- Resolve conflicts in text files, during a rebase, and when one side deleted the file.
- Use `git merge --abort` and `git stash -u` to get out of the way safely.
- Write a decision record that a teammate could act on.
:::

Do each exercise in a throwaway folder (`mkdir practice-5 && cd practice-5 && git init`) so mistakes cost nothing. The outputs below are real; your commit IDs will differ.

## Warm-up: conflict or clean?

For each pair of changes to the same file, predict whether `git merge` stops.

1. Branch A edits line 2. Branch B edits line 8.
2. Branch A edits line 4. Branch B edits line 5.
3. Both branches add the identical line in the same place.
4. Branch A edits `README.md`. Branch B edits `settings.json`.

:::solution
1. Clean: the changes are far apart, so Git takes each one.
2. Conflict: changes on neighboring lines count as touching.
3. Clean: when both sides made exactly the same change, there is nothing to choose.
4. Clean: different files never conflict with each other's content.
:::

### Exercise 1: Read the markers

You're on `main` and merged a branch called `fix-run-command`. The README now says:

```markdown title="README.md"
# Quiz Night

Run the game with:

<<<<<<< HEAD
    py quiz.py
=======
    python3 quiz.py
>>>>>>> fix-run-command
```

Which command came from `main`? Write a resolved README that keeps both, since `py` works on Windows and `python3` on macOS and Linux.

:::hint
`HEAD` is the branch you were on when you started the merge.
:::

:::solution
`py quiz.py` came from `main`, the current branch; `python3 quiz.py` came in from `fix-run-command`. One good resolution:

```markdown title="README.md"
# Quiz Night

Run the game with `py quiz.py` on Windows,
or `python3 quiz.py` on macOS and Linux.
```

Then `git diff --check`, `git add README.md`, and `git commit`. The best resolutions often say more than either side did alone.
:::

### Exercise 2: Back out of a merge you didn't mean to start

You merged the wrong branch and the conflict is in a file you've never seen. Undo the merge so your folder is exactly as it was, and prove it with `git status`.

:::hint
You don't need to touch the conflicted file at all.
:::

:::solution
```bash
git merge --abort
git status
```

```text
On branch main
nothing to commit, working tree clean
```

`--abort` only works while the merge is still in progress. Once you've committed a merge, undoing it is a different, bigger job, so check which branch you're merging before you press Enter.
:::

### Exercise 3: Stash a brand-new file too

On a branch `music-round`, change `settings.json` and create a new file `music.txt` without committing either. Run `git stash`, then `git status --short`. What stayed behind? Fix it so both changes are stashed, with a message you'll recognize later.

:::hint
Look at the `??` line. Untracked files need an extra flag.
:::

:::solution
```bash
git status --short
git stash
git status --short
```

```text
 M settings.json
?? music.txt
Saved working directory and index state WIP on music-round: ba269ca Start
?? music.txt
```

Plain `git stash` took the tracked change and left the untracked `music.txt` behind. Bring everything back with `git stash pop`, then stash again with `-u` and a message:

```bash
git stash -u -m "music round, half done"
git status --short
git stash list
```

```text
Saved working directory and index state On music-round: music round, half done
stash@{0}: On music-round: music round, half done
```

The empty line after `git status --short` means the folder is clean. `git stash pop` brings back both files.
:::

What to watch for: each stash command he runs and what the working folder looks like before and after it. Then compare with your own output from Exercise 3.
:::

### Exercise 4: Resolve a conflict in the middle of a rebase

Make a README with the line `Teams of up to 4 players.` and commit it on `main`. On a branch `team-size`, change it to `Teams of 2 to 4 players.` and commit. Back on `main`, change it to `Teams of up to 5 players.` and commit. Now switch to `team-size` and run `git rebase main`. Resolve so both rules survive, and finish the rebase.

```mermaid caption="After the rebase, your commit sits on top of main's newest commit with a new ID"
gitGraph
    commit id: "Add rules"
    commit id: "Up to 5 players"
    branch team-size
    checkout team-size
    commit id: "2 to 5 players"
```

:::hint
During a rebase the labels flip. `HEAD` is the branch you are replaying onto (`main`), and the other side is your own commit.
:::

:::solution
```bash
git rebase main
```

```text
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
error: could not apply 9dcc804... Require at least 2 players per team
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
hint: Disable this message with "git config advice.mergeConflict false"
Could not apply 9dcc804... Require at least 2 players per team
```

The README shows `main`'s line under `HEAD` and your commit under its ID:

```text
<<<<<<< HEAD
Teams of up to 5 players.
=======
Teams of 2 to 4 players.
>>>>>>> 9dcc804 (Require at least 2 players per team)
```

Both rules fit in one sentence: `Teams of 2 to 5 players.` Write that, remove the markers, then:

```bash
git add README.md
git rebase --continue
git log --oneline --graph --all
```

```text
[detached HEAD 4d1eb7d] Require at least 2 players per team
 1 file changed, 1 insertion(+), 1 deletion(-)
Successfully rebased and updated refs/heads/team-size.
* 4d1eb7d Require at least 2 players per team
* 3d1b528 Allow teams of 5
* ef0e620 Add rules
```

Git may open your editor to confirm the commit message; save and close it. "Detached HEAD" is normal mid-rebase, and the last line tells you the branch is back on track.
:::

### Exercise 5: One side deleted the file

On a branch `tidy-up`, someone ran `git rm old-questions.txt` because it looked unused. Meanwhile on `main`, you added a question to that same file. Merge `tidy-up` into `main`. Read the message, then decide: does the file stay or go?

:::hint
There are no markers this time. Git needs you to either `git add` the file (keep it) or `git rm` it (delete it).
:::

:::solution
```bash
git merge tidy-up
git status
```

```text
CONFLICT (modify/delete): old-questions.txt deleted in tidy-up and modified in HEAD.  Version HEAD of old-questions.txt left in tree.
Automatic merge failed; fix conflicts and then commit the result.
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add/rm <file>..." as appropriate to mark resolution)
	deleted by them: old-questions.txt

no changes added to commit (use "git add" and/or "git commit -a")
```

Your new question shows the file is not dead after all, so keep it with `git add old-questions.txt` and commit. If the game really doesn't read it, move your question to the file it does use, then `git rm old-questions.txt` and commit. Either is fine; what matters is that you decided on purpose and said why in the commit message.
:::

### Exercise 6: Write the decision record

Two pull requests clashed in `settings.json`. One switched the default `theme` to `"dark"` because the club meets in a dim room. The other kept `"light"` because the projector washes out dark colors. The team agreed: keep `"light"` as the default and add a `"projector"` setting that switches to a high-contrast light theme. Write `docs/decisions/0002-...md`.

:::hint
Use the three headings from the build-along. Consequences should name at least one piece of follow-up work.
:::

:::solution
```markdown title="docs/decisions/0002-light-theme-with-projector-option.md"
# 2. Light theme by default, with a projector option

Date: 2026-11-20
Status: Accepted

## Context

One change made dark the default for a dim meeting room. Another kept
light because the projector washes out dark colors. Both problems are real.

## Decision

Keep "light" as the default theme. Add "projector": true, which switches
to a high-contrast light theme.

## Consequences

- The game needs a high-contrast theme before the option does anything.
- The README settings table gets a new row for "projector".
- If the club changes rooms, revisit this record.
```
:::

### Challenge: the conflict Git didn't report

On `main`, `settings.json` has `"time_limit_seconds": 60`. Branch `rename-key` renames that key to `"seconds_per_question"`. Meanwhile `main` gains a new `hard_mode` block near the bottom of the file that uses `"time_limit_seconds": 15`. Merge `rename-key`. Did Git complain? Is the result correct? Find the problem with one command, fix it, and write a CHANGELOG entry for the rename.

:::hint
Try `git grep -n "seconds"` after the merge.
:::

:::solution
The merge is clean, because the two edits are several lines apart:

```text
Auto-merging settings.json
Merge made by the 'ort' strategy.
 settings.json | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

But the file now uses two names for the same idea:

```bash
git grep -n "seconds"
```

```text
settings.json:3:  "seconds_per_question": 60,
settings.json:8:    "time_limit_seconds": 15,
```

Rename the key inside `hard_mode` too, commit, and add this under Unreleased in the CHANGELOG:

```markdown title="CHANGELOG.md"
### Changed

- Renamed `time_limit_seconds` to `seconds_per_question`, including in
  `hard_mode`. Update any custom settings files.
```

Git only notices clashing lines, not clashing meaning. Catching this kind of mistake is a job for automated tests, which Module 7 sets up.
:::
