Git's error messages look alarming, but most of them tell you exactly what to type next. Look at what Git prints when you ask about a folder that isn't a repository yet, and when you forget to stage a file:

```text
fatal: not a git repository (or any of the parent directories): .git
```

```text
nothing added to commit but untracked files present (use "git add" to track)
```

The first says Git looked in this folder *and every folder above it* for a hidden `.git` folder and found none. The second ends with the fix in parentheses. Reading the whole message, slowly, solves more problems than searching online.

## One folder per project, all inside `git-course`

You made `~/git-course` in the last lesson. Every project in this course gets its own folder inside it, and each of those folders becomes its own repository:

```text
git-course/
├── Spoon-Knife/     (cloned in Module 1)
├── recipes/         (Module 2 examples)
├── club-site/       (built in Modules 2 to 4)
└── practice/        (throwaway experiments)
```

A repository is just a folder with a hidden `.git` folder inside it. That `.git` folder *is* the history; delete it and the files stay but the history is gone. To check which repository you're in, ask Git for its top folder:

```bash
cd ~/git-course/Spoon-Knife
git rev-parse --show-toplevel
```

```text
/Users/sam/git-course/Spoon-Knife
```

Run the same command somewhere that isn't a repository and you get the `not a git repository` error from above. That's useful too: it means you're not about to commit into the wrong project.

:::warning
**Never run `git init` in your home folder, Desktop, or Documents.** Git would treat every file in it as part of one giant project, and `git status` would list thousands of files. If it happens, the fix is to delete only the hidden `.git` folder at the top of that folder (for your home folder: `rm -rf ~/.git`). Your files stay; only the accidental tracking goes away. Check with your instructor before deleting anything if you're unsure.
:::

Also keep `git-course` **outside** OneDrive, iCloud Drive, Google Drive, and Dropbox. Sync apps copy files while Git is writing to `.git`, which can leave a repository in a broken state. Once you push to GitHub in Module 3, you'll have an off-computer copy anyway.

## A tour of VS Code's Source Control view

Open a repository folder with **File > Open Folder…**, then click the branching icon in the left bar (or press **Ctrl+Shift+G**). You'll see:

| In VS Code | What it means | Same as |
| --- | --- | --- |
| **Changes** list | Files you've changed but not staged | `git status` |
| Letter **U**, **M**, or **D** | Untracked (new), Modified, Deleted | `git status` |
| **+** next to a file (**Stage Changes**) | Put this file in the next commit | `git add file` |
| **−** in **Staged Changes** | Take it back out | `git restore --staged file` |
| Message box and **Commit** button | Save a snapshot with that message | `git commit -m "…"` |
| Curved arrow (**Discard Changes**) | Throw away your edits to that file | `git restore file` |
| Branch name in the bottom-left status bar | Which branch you're on; click to switch | `git switch` |
| Colored bars beside line numbers | Green: added, blue: changed, red marker: deleted lines | `git diff` |

This course teaches each idea with terminal commands first and then shows the button. The commands are worth learning because every Git tool, website, and tutorial uses the same words. Once you know what `git add` does, the **+** button stops being mysterious.

## Privacy and safety rules for this course

Anything in a public repository can be read, copied, and archived by anyone. Git also remembers every version, so deleting a file in a later commit doesn't remove it from history. Four rules keep you safe:

1.  **Never commit secrets.** No passwords, API keys, access tokens, or `.env` files. If one slips into a commit that's been pushed, treat it as public: change the password or delete the key on the site that issued it *first*, then clean up the repository.
2.  **Keep personal details out.** Your noreply email is already set. Don't put your address, phone number, school schedule, or photos of yourself in READMEs or commit messages.
3.  **Make practice repositories private** if you'd rather nobody sees them. Private repositories are free on GitHub, and you can make one public later.
4.  **Don't paste commands you don't understand,** especially ones with `--force`, `rm -rf`, or `sudo`. Ask what a command does before you run it, whether the suggestion came from a forum or an AI tool.

On GitHub, be the collaborator you'd want: comment on the work, not the person. If someone is rude or harassing, use the **…** menu on their comment to report it, and tell your instructor.

## Accessibility settings worth knowing

-   **Zoom VS Code** with **Ctrl+=** and **Ctrl+-** (**Cmd** on a Mac), or pick a **High Contrast** theme with **Ctrl+K Ctrl+T**.
-   **Screen readers:** VS Code switches to *Screen Reader Optimized* mode when it detects one. In a diff, press **F7** to open the **Accessible Diff Viewer**, which reads changes line by line. **Alt+F1** (Option+F1 on Mac) opens accessibility help for whatever you're focused on.
-   **Red and green are hard to tell apart?** Git's colors are settings. These two lines make removed lines magenta and added lines blue:

```bash
git config --global color.diff.old magenta
git config --global color.diff.new blue
```

-   **On GitHub**, press **?** on most pages to list keyboard shortcuts. **Settings > Accessibility** lets you underline links and stop animated images from playing.

## A routine for getting unstuck

When something goes wrong, work through these in order:

1.  **Run `git status`** and read every line, including the hints in parentheses. It tells you the branch, what's staged, and what Git expects next.
2.  **Read the last line of the error.** Lines starting with `fatal:` or `error:` name the actual problem.
3.  **Check the command's options** with `-h`. For example, `git restore -h` starts like this:

```text
usage: git restore [<options>] [--source=<branch>] <file>...

    -s, --[no-]source <tree-ish>
                          which tree-ish to checkout from
    -S, --[no-]staged     restore the index
    -W, --[no-]worktree   restore the working tree (default)
```

4.  **Ask for help with three things:** the exact command you ran, the full output (copy it as text, not a blurry photo), and what you expected to happen.

### Screens that look frozen

-   **`git log` fills the screen and shows `:` or `(END)` at the bottom.** You're in a pager that lets you scroll. Use the arrow keys, and press **q** to quit.
-   **A screen full of `~` characters appears.** Git opened Vim. Press **Esc**, type `:q!`, and press Enter. Then set `core.editor` as in the last lesson.
-   **A command is still running and you want out.** Press **Ctrl+C**.

### Errors you'll probably see this month

**`fatal: pathspec 'indx.html' did not match any files`**: a typo in a file name. Run `ls` to see the real names, or press Tab to autocomplete them.

**`Author identity unknown`**: Git doesn't know your name and email yet.

```text
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.
```

Run the two `git config` commands from the last lesson (with your noreply email), then commit again.

**`nothing added to commit but untracked files present`**: you ran `git commit` before `git add`. Stage the file first. Module 2 explains why Git makes you do both.

:::quiz
Q: `git log` printed a long list and the bottom line shows `(END)`. The terminal won't take new commands. What do you do?
- [ ] Close VS Code and reopen it
  That works, but it's slow, and nothing is broken.
- [x] Press `q`
  You're in a scrolling pager; `q` quits it and returns you to the prompt.
- [ ] Type `git exit`
  There's no such command, and the pager would just treat the keys as scrolling input.

Q: A classmate's tutorial tells you to commit a file called `.env` so the project "just works" for everyone. What's the problem?
- [ ] `.env` files are too large for GitHub
  Size isn't the issue; they're usually tiny.
- [x] `.env` files usually hold secrets, and Git history keeps them even after you delete the file
  Once pushed, a secret should be treated as public. Share a template like `.env.example` with fake values instead.
- [ ] Git can't track files whose names start with a dot
  It can; `.gitignore` itself starts with a dot and is committed in almost every project.
:::
