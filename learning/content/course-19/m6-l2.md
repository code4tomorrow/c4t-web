:::objectives
- Compare `RandomForestClassifier` and `HistGradientBoostingClassifier` on identical folds, each with suitable preprocessing.
- Use permutation importance and single-feature scores to find a column that leaks the target.
- Detect repeated entities and switch to `StratifiedGroupKFold` so no customer is split across folds.
- Measure how much each leak inflated the score, and report which model wins once both are fixed.
:::

A streaming service hands you an export: one row per customer per month for the last quarter, and a column saying whether that customer cancelled by the end of the quarter. The question from the product team is simple: "Should we use a random forest or gradient boosting to predict cancellations?" You'll answer it three times. The first two answers will be wrong, and finding out why is the point.

Here is the finished picture, so you know where the steps lead.

```mermaid caption="The same race, run three times, with one leak removed each time"
flowchart LR
    A[Export: 2,390 rows] --> B["Race 1: all columns, rows shuffled"]
    B -->|"top feature recorded after the outcome"| C["Race 2: leak dropped, rows shuffled"]
    C -->|"same customer on both sides"| D["Race 3: leak dropped, customers grouped"]
    D --> E[Honest winner]

## Step 1: Load the export and read its data dictionary

The code below builds a realistic stand-in for the export. In a real project this would be `pd.read_csv(...)`; generating it lets everyone get identical numbers. The first two lines cap boosting at one CPU thread, which the note after this step explains.

```python run
import sklearn
from threadpoolctl import threadpool_limits
threadpool_limits(limits=1, user_api="openmp")

import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 800
customers = pd.DataFrame({
    "customer_id": np.arange(n),
    "plan": rng.choice(["basic", "standard", "premium"], n, p=[0.5, 0.35, 0.15]),
    "contract": rng.choice(["monthly", "annual"], n, p=[0.6, 0.4]),
    "region": rng.choice(["north", "south", "east", "west"], n),
})
price = customers.plan.map({"basic": 9.99, "standard": 15.99, "premium": 22.99})
customers["monthly_fee"] = (price * rng.uniform(0.8, 1.0, n)).round(2)  # personal discounts
engagement = rng.normal(0, 1, n)                                         # never recorded
customers["tenure_start"] = rng.integers(1, 48, n)
risk = (-1.0 - 1.1 * engagement + 0.9 * (customers.contract == "monthly")
        - 0.03 * customers.tenure_start + 0.4 * (customers.plan == "basic"))
customers["cancelled"] = (rng.random(n) < 1 / (1 + np.exp(-risk))).astype(int)

rows = []
for c in customers.itertuples():
    for month in range(rng.integers(2, 5)):
        rows.append({
            "customer_id": c.customer_id, "month": month + 1, "plan": c.plan,
            "contract": c.contract, "region": c.region, "monthly_fee": c.monthly_fee,
            "tenure_months": c.tenure_start + month,
            "logins_30d": max(0, int(rng.normal(12 + 5 * engagement[c.customer_id]
                                                - 3 * c.cancelled * month, 3))),
            "support_tickets_30d": rng.poisson(0.4 + 0.5 * c.cancelled),
            "payment_failures": rng.poisson(0.15 + 0.35 * c.cancelled * (c.contract == "monthly")),
            "days_since_last_login": int(rng.exponential(20) + 10) if c.cancelled
                                     else int(rng.exponential(5)),
            "cancelled": c.cancelled,
        })
export = pd.DataFrame(rows)
for col in ["plan", "contract", "region"]:
    export[col] = export[col].astype("category")

print(export.shape, "| customers:", export.customer_id.nunique(),
      "| cancelled share:", round(export.cancelled.mean(), 3))
print(export.drop(columns=["plan", "region"]).head(4).to_string())
```

:::note
`HistGradientBoosting` runs on every CPU core by default. That is fast on your own machine, but on a busy shared computer, or inside a parallel grid search where every worker also grabs every core, the threads fight and a two-second fit can take a minute. The scikit-learn docs call this oversubscription. `threadpool_limits` caps the threads; in Colab you can delete those lines without harm.
:::

The data team's dictionary for the columns, exactly as they wrote it:

| Column | Meaning |
| --- | --- |
| `plan`, `contract`, `region`, `monthly_fee` | account details |
| `tenure_months` | months since sign-up, at that monthly snapshot |
| `logins_30d`, `support_tickets_30d`, `payment_failures` | activity in the 30 days before the snapshot |
| `days_since_last_login` | days between the last login and the date this file was exported |
| `cancelled` | 1 if the customer cancelled by the end of the quarter |

Read the dictionary again before moving on. One row in it should worry you.

## Step 2: Race 1, with every column

The forest needs the three text columns one-hot encoded. Boosting can use them directly because they have pandas `category` dtype and `categorical_features="from_dtype"` is the default. A helper runs both models on the same folds so we can reuse it for every race.

```python run
from sklearn.compose import make_column_transformer
from sklearn.ensemble import HistGradientBoostingClassifier, RandomForestClassifier
from sklearn.model_selection import StratifiedGroupKFold, StratifiedKFold, cross_val_score
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import OneHotEncoder

categorical = ["plan", "contract", "region"]
all_columns = categorical + ["monthly_fee", "tenure_months", "logins_30d",
                             "support_tickets_30d", "payment_failures", "days_since_last_login"]

def make_models():
    forest = make_pipeline(
        make_column_transformer((OneHotEncoder(handle_unknown="ignore"), categorical),
                                remainder="passthrough"),
        RandomForestClassifier(n_estimators=100, random_state=0))
    boosting = HistGradientBoostingClassifier(random_state=0)
    return {"forest": forest, "boosting": boosting}

def race(columns, cv, groups=None):
    scores = {}
    for name, model in make_models().items():
        scores[name] = cross_val_score(model, export[columns], export.cancelled,
                                       cv=cv, groups=groups, scoring="roc_auc")
        print(f"{name:>9}: ROC AUC {scores[name].mean():.3f} ± {scores[name].std():.3f}")
    return scores

row_folds = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
results = {"race 1: all columns": race(all_columns, row_folds)}
```

Both models score about 0.99. Cancellation is a hard problem, driven by things nobody records, like how much someone actually enjoys the service. A near-perfect score on a hard problem is a reason to investigate, not to celebrate.

## Step 3: Interrogate the winner

Ask the model what it relies on. We hold out a quarter of the customers (with `GroupShuffleSplit`, so no customer is on both sides), fit boosting on the rest, and shuffle one column at a time on the held-out rows.

```python run
from sklearn.inspection import permutation_importance
from sklearn.metrics import roc_auc_score
from sklearn.model_selection import GroupShuffleSplit

train_idx, test_idx = next(GroupShuffleSplit(test_size=0.25, random_state=0)
                           .split(export, groups=export.customer_id))
train, held_out = export.iloc[train_idx], export.iloc[test_idx]
booster = make_models()["boosting"].fit(train[all_columns], train.cancelled)
perm = permutation_importance(booster, held_out[all_columns], held_out.cancelled,
                              scoring="roc_auc", n_repeats=5, random_state=0)
print(pd.Series(perm.importances_mean, index=all_columns).sort_values(ascending=False).round(3))

print("\nROC AUC of each numeric column on its own:")
for col in all_columns[3:]:
    auc = roc_auc_score(export.cancelled, export[col])
    print(f"  {col:>22}: {max(auc, 1 - auc):.3f}")
```

Shuffling `days_since_last_login` wipes out more than 0.35 of AUC; the next most important column costs 0.016. On its own, with no model at all, that column separates cancellers from stayers with an AUC around 0.97.

Now go back to the dictionary: *days between the last login and the date this file was exported*. The export happened after the quarter ended. Customers who cancelled stopped logging in, so by export day they had been away for weeks. The column is a consequence of the outcome. On the day you'd actually use the model, at a monthly snapshot before anyone has cancelled, this value doesn't exist in this form. That is **target leakage**, and the only fix is to drop the column (or rebuild it from data stamped before the snapshot).

## Step 4: Race 2, with the leak removed

```python run
clean_columns = [c for c in all_columns if c != "days_since_last_login"]
results["race 2: leak dropped"] = race(clean_columns, row_folds)
```

About 0.89 to 0.90, with boosting ahead. These look like believable numbers for a cancellation model, and this is where most notebooks stop. But look at the first line Step 1 printed: 2,390 rows and only 800 customers.

```python run
rows_per_customer = export.groupby("customer_id").size()
print("rows per customer:", rows_per_customer.value_counts().sort_index().to_dict())
fees_per_customer = export.groupby("customer_id").monthly_fee.nunique().max()
print("distinct monthly_fee values:", export.monthly_fee.nunique(),
      "| max distinct fees within one customer:", fees_per_customer)
```

Every customer has 2 to 4 rows, all sharing one label. And `monthly_fee`, thanks to personal discounts, is close to a fingerprint: 467 distinct values for 800 customers, and never more than one per customer. With rows shuffled into folds, most validation rows have a sibling row from the same customer in training, with the same fee and the same answer. The models can score well by recognizing customers instead of predicting behaviour. That is **train-test contamination** through a repeated entity, the same trap as the repeat patients in Module 3, now hiding behind a leak you already fixed.

## Step 5: Race 3, with customers kept together

`StratifiedGroupKFold` keeps every customer's rows in a single fold while balancing the cancelled share across folds.

```python run
customer_folds = StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=0)
results["race 3: customers grouped"] = race(clean_columns, customer_folds,
                                            groups=export.customer_id)

f, b = results["race 3: customers grouped"].values()
print("\nfold by fold, forest minus boosting:", (f - b).round(3))
```

Both scores fall again, and the order flips: the forest is now ahead by about 0.02, and it wins in four of the five folds. Boosting's lead in Race 2 came from memorizing customers slightly better, not from predicting new ones better.

## Step 6: See how much of each score was real

```python run alt="Line chart of mean ROC AUC for the forest and boosting across three races: about 0.99 with all columns, about 0.89 to 0.90 after dropping the leak, and about 0.82 to 0.84 with customers grouped, where the lines cross and the forest ends ahead" caption="Each fix removed part of the score that would never have shown up in production."
import matplotlib.pyplot as plt

labels = list(results)
x = np.arange(len(labels))
fig, ax = plt.subplots(figsize=(7, 3.4))
means = {name: [results[label][name].mean() for label in labels]
         for name in ["forest", "boosting"]}
for name, color in [("forest", "#2a78d6"), ("boosting", "#eb6834")]:
    other = means["boosting" if name == "forest" else "forest"]
    ax.plot(x, means[name], marker="o", markersize=8, lw=2, color=color, label=name)
    for xi, m, o in zip(x, means[name], other):
        ax.annotate(f"{m:.3f}", (xi, m), textcoords="offset points",
                    xytext=(10, 4 if m >= o else -11), fontsize=8)
ax.set_xticks(x, [label.split(": ")[1] for label in labels])
ax.set_xlim(-0.3, 2.5)
ax.set_ylim(0.79, 1.0)
ax.set_ylabel("mean ROC AUC")
ax.legend(frameon=False)
ax.grid(alpha=0.3)
```

The leak was worth about 0.10 of AUC and the contamination another 0.06 to 0.09. Together they were larger than any difference between the two model families, which is the general lesson: fix the evaluation first, then compare models.

## The finished evaluation

Here is the honest comparison as one reusable function. It refuses to run if you pass it a column on a "known leaks" list, and it always groups by customer.

```python run title="honest_race.py"
KNOWN_LEAKS = {"days_since_last_login", "cancelled"}

def honest_race(data, columns, group_col="customer_id", target="cancelled", seed=0):
    leaks = KNOWN_LEAKS & set(columns)
    if leaks:
        raise ValueError(f"leaky columns passed in: {sorted(leaks)}")
    folds = StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=seed)
    table = {}
    for name, model in make_models().items():
        s = cross_val_score(model, data[columns], data[target], cv=folds,
                            groups=data[group_col], scoring="roc_auc")
        table[name] = {"mean AUC": s.mean().round(3), "std": s.std().round(3)}
    return pd.DataFrame(table).T

print(honest_race(export, clean_columns, seed=1))
```

With a different fold seed the forest still leads, by a little less (about 0.01). Rerunning with new seeds is a cheap check that a result isn't an accident of one particular split, and here it says the forest's lead is real but small.

:::quiz
Q: Why did Step 3 hold out data with `GroupShuffleSplit` instead of a plain `train_test_split`?
- [ ] `permutation_importance` only accepts grouped data
  It accepts any held-out set; the grouping is about what the importances mean.
- [x] So the importances reflect predictions for unseen customers, not customers the model already memorized
  If held-out rows had siblings in training, columns that fingerprint customers (like `monthly_fee`) would look more useful than they are.
- [ ] Because a plain split would put the leaky column only in the training set
  Splitting rows never removes columns; both sets always have every column.

Q: Race 2's scores (about 0.89 to 0.90) looked believable. What was the clue that they were still inflated?
- [x] 2,390 rows came from only 800 customers, each with one label shared across their rows
  Repeated entities with a shared label let a model score by recognition, so row-shuffled folds overstate performance on new customers.
- [ ] Boosting beat the forest
  Either model winning is plausible; the problem was in how the folds were built.
- [ ] The standard deviation across folds was too small
  The spread was ordinary; the issue was that validation rows weren't truly new.

Q: After all fixes the forest leads by about 0.02. What should you do before telling the product team "use the forest"?
- [ ] Nothing, a lead in 4 of 5 folds is proof
  Five folds is a small sample, and boosting hasn't been tuned at all.
- [x] Give both models a comparable tuning budget on the same grouped folds, and repeat with other fold seeds
  A 0.02 gap between untuned defaults can easily reverse after tuning, so the comparison should hold up under both before it drives a decision.
- [ ] Switch to row-shuffled folds to get more stable numbers
  Stable but wrong numbers are worse than noisy honest ones.
:::

:::takeaways
- A near-perfect score on a hard problem is a prompt to investigate; check the top permutation-importance feature and each column's solo AUC.
- For every column, ask when its value becomes known. Anything recorded after the moment of prediction is target leakage.
- Count rows per entity. If customers, patients, or devices repeat, split with `GroupKFold` or `StratifiedGroupKFold`.
- Leakage can change which model wins, not just how good both look. Fix the evaluation before comparing models.
:::
