Here is an experiment that surprises most people. Take a classifier's scores for 500 positive examples and freeze them. Then keep adding negatives drawn from the same distribution as before: 500, then 2,000, then 10,000, then 50,000. The model hasn't changed at all. Watch what two popular metrics say about it.

```python run alt="Line chart: as the positive share falls from 50% to 1%, ROC AUC stays near 0.9 while average precision drops from about 0.91 to about 0.19" caption="Same model, same score distributions, more negatives."
import matplotlib.pyplot as plt
import numpy as np
from sklearn.metrics import average_precision_score, roc_auc_score

rng = np.random.default_rng(0)
pos = rng.normal(1.8, 1.0, 500)          # scores the model gives positives
neg_pool = rng.normal(0.0, 1.0, 50_000)  # scores it gives negatives

rows = []
for n_neg in [500, 2_000, 10_000, 50_000]:
    scores = np.r_[pos, neg_pool[:n_neg]]
    y = np.r_[np.ones(500), np.zeros(n_neg)]
    rows.append((y.mean(), roc_auc_score(y, scores), average_precision_score(y, scores)))
    print(f"positives {y.mean():6.1%}   ROC AUC {rows[-1][1]:.3f}   AP {rows[-1][2]:.3f}")

share, auc, ap = zip(*rows)
fig, ax = plt.subplots(figsize=(6, 3.2))
ax.plot(share, auc, marker="o", lw=2, color="#2a78d6", label="ROC AUC")
ax.plot(share, ap, marker="o", lw=2, color="#eb6834", label="average precision")
ax.set_xscale("log")
ax.invert_xaxis()
ax.set_xlabel("share of positives (log scale)")
ax.set_ylim(0, 1)
ax.grid(alpha=0.3)
ax.legend(frameon=False)
```

ROC AUC drifts from 0.911 to 0.896. Average precision (AP) collapses from 0.914 to 0.185. Both are telling the truth; they answer different questions.

## Why ROC AUC hardly notices the pile of negatives

The ROC curve's x-axis is the false positive rate: false alarms divided by *all* negatives. When the negatives grow from 500 to 50,000, a 2% false positive rate goes from 10 false alarms to 1,000. The rate is unchanged, so ROC AUC is unchanged. The person reading the alerts, though, now wades through 1,000 false alarms to find a few hundred real cases.

Precision is the metric that feels that pile: true positives divided by everything flagged. **Average precision** walks down the ranked list from the most confident prediction and averages the precision at each point where a new true positive is found. A model that guesses at random scores an AP equal to the positive share (0.01 when 1% are positive), so always compare AP to the prevalence, not to 0.5.

:::trace Build average precision one flag at a time
```python
# Eight items, sorted from highest score to lowest.
# 1 = a real positive, 0 = a false alarm
ranked = [1, 1, 0, 1, 0, 0, 1, 0]
total_pos = sum(ranked)
hits = 0
precisions = []
for rank, label in enumerate(ranked, start=1):
    if label == 1:
        hits += 1
        precisions.append(hits / rank)
ap = sum(precisions) / total_pos
print(round(ap, 3))
```
:::

The fourth positive shows up at rank 7, when only 4 of the 7 flags are real, so it contributes 0.571. The scikit-learn function `average_precision_score` gives the same 0.830 for these items when no two scores tie.

## What `class_weight="balanced"` really changes

Now a realistic dataset: 3,000 parts off a production line, about 4.6% of them defective. `class_weight="balanced"` gives each class a weight of `n_samples / (2 * n_in_class)`, so every defect counts about 21 times as much as a good part in the loss.

```python run
import numpy as np
from scipy.stats import spearmanr
from sklearn.datasets import make_classification
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import average_precision_score, recall_score, roc_auc_score
from sklearn.model_selection import train_test_split
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.utils.class_weight import compute_class_weight

X, y = make_classification(n_samples=3000, n_features=12, n_informative=6,
                           n_redundant=2, weights=[0.96], class_sep=1.3,
                           random_state=3)
print("defects:", y.sum(), "of", len(y))
print("balanced weights [good, defect]:",
      compute_class_weight("balanced", classes=np.array([0, 1]), y=y).round(2))

X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.3, stratify=y, random_state=0)
plain = make_pipeline(StandardScaler(), LogisticRegression()).fit(X_train, y_train)
weighted = make_pipeline(StandardScaler(),
                         LogisticRegression(class_weight="balanced")).fit(X_train, y_train)

for name, model in [("plain", plain), ("balanced", weighted)]:
    p = model.predict_proba(X_test)[:, 1]
    flags = model.predict(X_test)
    print(f"{name:>8}: AP {average_precision_score(y_test, p):.3f}  "
          f"ROC AUC {roc_auc_score(y_test, p):.3f}  flagged {flags.sum():>3}  "
          f"recall {recall_score(y_test, flags):.2f}  mean probability {p.mean():.3f}")

rho = spearmanr(plain.predict_proba(X_test)[:, 1], weighted.predict_proba(X_test)[:, 1])[0]
print(f"rank correlation between the two models' scores: {rho:.3f}")
```

Look at the columns that measure *ranking*: AP and ROC AUC are almost identical, and the two models order the test parts with a rank correlation of 0.97. What changed is the scale. The average predicted probability jumped from about 0.05 (the real defect rate) to about 0.23, so far more parts cross the default 0.5 cutoff and recall rises.

For logistic regression, reweighting mostly slides the intercept, which is the same thing as moving the threshold. For trees and forests it can do more, because the weights change which split looks purest, so the ranking itself can shift. Either way, the probabilities a weighted model prints are no longer the chance of a defect. Module 7 shows how to repair them.

:::note
`class_weight="balanced"` is shorthand for passing `sample_weight` to `fit`, with each row getting its class's weight. Fitting the plain pipeline with `logisticregression__sample_weight=weights[y_train]` produces exactly the same coefficients.
:::

## Resampling: copy rows, drop rows, or invent rows

Instead of weighting rows, you can change which rows the model sees.

-   **Random oversampling** repeats positives until the classes balance. For many models this behaves like integer weights, but flexible models such as k-NN or deep trees can memorize the copies.
-   **Random undersampling** throws away negatives. Training gets fast, but you discard information, so it is often repeated on many different subsamples whose models are then averaged.
-   **SMOTE** creates synthetic positives on the line between a positive and one of its nearest positive neighbours. It lives in the separate `imbalanced-learn` library (`pip install imbalanced-learn` in Colab), whose `imblearn.pipeline.Pipeline` applies samplers during `fit` only.

For a strong model judged by a ranking metric such as AP, resampling often adds little beyond what a plain model with a well-chosen threshold already gives, so test it with cross-validation instead of assuming it helps. What is never optional is *where* it happens.

```mermaid caption="Resample the training part of each fold; score on rows the sampler never touched"
flowchart LR
    A[All training rows] --> B[Split into folds]
    B --> C[Training part]
    B --> D[Validation part]
    C --> E[Resample or weight]
    E --> F[Fit the model]
    F --> G[Score]
    D -->|untouched| G
```

## Choose the threshold from what each mistake costs

Suppose a missed defect costs the factory 20 times as much as an unnecessary inspection. If a model's probabilities are trustworthy, flagging a part pays off whenever `p × 20 > (1 − p) × 1`, which means `p > 1/21 ≈ 0.048`. That is the textbook optimum, and it is far below 0.5.

`TunedThresholdClassifierCV` finds the threshold empirically: it cross-validates the model, tries 100 cutoffs on each validation fold, and keeps the one with the best score. Give it the cost as a scorer (negated, because it maximizes).

```python run
from sklearn.metrics import confusion_matrix, make_scorer
from sklearn.model_selection import TunedThresholdClassifierCV

def total_cost(y_true, y_pred):
    tn, fp, fn, tp = confusion_matrix(y_true, y_pred, labels=[0, 1]).ravel()
    return 1 * fp + 20 * fn

neg_cost = make_scorer(lambda yt, yp: -total_cost(yt, yp))

for name, model in [("plain", plain), ("balanced", weighted)]:
    tuned = TunedThresholdClassifierCV(model, scoring=neg_cost, cv=5,
                                       random_state=0).fit(X_train, y_train)
    textbook = (model.predict_proba(X_test)[:, 1] >= 1 / 21).astype(int)
    print(f"{name:>8}: tuned threshold {tuned.best_threshold_:.3f}   test cost: "
          f"at 0.5 = {total_cost(y_test, model.predict(X_test))}, "
          f"tuned = {total_cost(y_test, tuned.predict(X_test))}, "
          f"at 1/21 = {total_cost(y_test, textbook)}")
print("flag nothing:", total_cost(y_test, np.zeros_like(y_test)))
```

The plain model's tuned threshold (about 0.11) sits in the same low range as the textbook 0.048, and both cut its cost well below what the 0.5 default costs. The balanced model wants a threshold near 0.59, and the textbook 1/21 is a disaster for it, because its "probabilities" are inflated. Once each model has its own tuned threshold their costs (281 and 251) are close, and with only about 41 defects in the test set that gap is within noise. The lesson: tune the threshold for whichever model you deploy, and only use cost formulas on probabilities you have checked.

## Two ways to combine models: voting and stacking

A single model has blind spots. Different kinds of model often have *different* blind spots, so combining them can cancel some errors.

-   **Soft voting** (`VotingClassifier(voting="soft")`) averages the members' `predict_proba`. Hard voting takes a majority of predicted labels and throws away confidence, so soft is usually better when every member gives probabilities.
-   **Stacking** (`StackingClassifier`) trains a small *final estimator* on the members' predictions. To keep that honest, it builds those predictions with internal cross-validation (`cv=5` by default), so the final model learns from out-of-fold predictions, never from a member grading its own homework.

```python run
from sklearn.ensemble import RandomForestClassifier, StackingClassifier, VotingClassifier
from sklearn.model_selection import StratifiedKFold, cross_val_score
from sklearn.neighbors import KNeighborsClassifier

members = [
    ("logreg", make_pipeline(StandardScaler(), LogisticRegression())),
    ("knn", make_pipeline(StandardScaler(), KNeighborsClassifier(n_neighbors=15))),
    ("forest", RandomForestClassifier(n_estimators=100, random_state=0)),
]
candidates = dict(members)
candidates["soft vote"] = VotingClassifier(members, voting="soft")
candidates["stack"] = StackingClassifier(members, final_estimator=LogisticRegression(), cv=5)

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=1)
for name, model in candidates.items():
    ap = cross_val_score(model, X, y, cv=cv, scoring="average_precision")
    print(f"{name:>9}: AP {ap.mean():.3f} ± {ap.std():.3f}")
```

The three members are about equally good (AP near 0.71) and very different in how they work: a linear boundary, a neighbourhood vote, and a forest of axis-aligned splits. Both ensembles beat all three by about 0.03. The standard deviations are large, though, because each validation fold holds only about 27 defects. Before you claim the ensemble wins, compare the models fold by fold on the same splits, as you'll do in the Build-along.

:::warning
**Three ways rare-class work goes wrong.**

1.  **Resampling before splitting.** If you oversample the whole dataset and then cross-validate, copies of the same positive sit in training and validation folds. k-NN and deep trees "recognize" them and the scores soar. Resample inside the fold, or use `imblearn.pipeline.Pipeline`.
2.  **Picking the threshold on the test set.** The threshold is a hyperparameter. Choose it with cross-validation on the training data, as `TunedThresholdClassifierCV` does, then check it once on the test set.
3.  **Reading a weighted model's `predict_proba` as a real probability.** After `class_weight="balanced"`, a printed 0.6 might correspond to a true defect rate of 0.1.
:::

:::quiz
Q: A model's scores stay the same, but the test set now has ten times as many negatives. What happens to its ROC AUC and AP?
- [ ] Both drop by about the same amount
  ROC AUC divides false alarms by the number of negatives, so adding negatives from the same distribution leaves it about where it was.
- [x] ROC AUC stays about the same and AP falls
  The false positive *rate* is unchanged, but the *count* of false alarms grows tenfold, so precision at every recall level falls.
- [ ] Both stay the same, because the model didn't change
  The model didn't change, but AP depends on how many negatives compete with each positive in the ranked list.

Q: You switch a logistic regression to `class_weight="balanced"`. Which change should you expect?
- [ ] AP rises sharply because the model now ranks defects much better
  For logistic regression the weights mostly shift the intercept; the ordering of examples barely moves, so AP stays close.
- [x] More rows are flagged at the default threshold and the predicted probabilities get larger
  The weighting pushes every score toward the rare class, which is why recall at 0.5 rises and the probabilities stop matching real rates.
- [ ] Nothing, because weights only matter for tree models
  Weights change the loss for any model that accepts them; here they move the intercept a long way.

Q: Missing a positive costs 9 and a false alarm costs 1, and the model's probabilities are well calibrated. Where should the threshold go?
- [ ] 0.9
  That would flag only very confident cases, the opposite of what an expensive miss calls for.
- [ ] 0.5
  0.5 is right only when both mistakes cost the same.
- [x] 0.1
  Flag when `p × 9 > (1 − p) × 1`, which gives `p > 1/10`.

Q: Why does `StackingClassifier` use internal cross-validation to build the inputs for its final estimator?
- [x] So the final estimator learns from predictions the members made on rows they didn't train on
  In-sample predictions are overconfident, so a final model trained on them would trust whichever member overfits most.
- [ ] To tune each member's hyperparameters
  Stacking doesn't tune the members; put a search object in as a member if you want that.
- [ ] Because voting classifiers need it too
  `VotingClassifier` simply averages fitted members and uses no internal cross-validation.
:::

:::takeaways
- When positives are rare, report AP (and compare it with the positive share) or a cost, not accuracy or ROC AUC alone.
- `class_weight` and resampling mostly move the decision boundary toward the rare class; they rarely improve how well a model ranks, and they distort its probabilities.
- Resampling belongs inside each training fold, never before the split.
- A threshold is a decision about costs. Tune it with cross-validation on training data, and check it once on the test set.
- Soft voting and stacking help when the members are similarly strong and make different mistakes.
:::
